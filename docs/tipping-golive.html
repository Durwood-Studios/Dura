Close the code gaps

blocks everything below

All three are cheap. Two of them only become dangerous the moment a live key exists, which is why they come first.

Apply the rate-limit migration

proven missing

rateLimit() fails open by design, so with no table the “10 checkouts / 5 min / IP” guard on your only money endpoint does nothing at all. The file is now in supabase/migrations/Need To Run/; paste it into the SQL editor, then move it to Already Ran/. 

20260630000001_rate_limits.sql   — safe, uses IF NOT EXISTS

Close the uncancellable subscription path

chargeback risk

The tip modal only ever sends interval: "once", but the endpoint still accepts "month" and builds a real recurring subscription. There is no customer portal, no cancel UI, and the webhook ignores every subscription event — a monthly charge a supporter cannot stop is how a thank-you becomes a dispute.

Drop "month" from TIP_INTERVALS in src/lib/payments/tips.ts. One line, and it matches what the UI actually offers. Wire the billing portal instead only if you want recurring support.

Pin the Stripe API version

silent drift

new Stripe(key) in src/lib/payments/stripe.ts takes the SDK default. That is 2026-06-24.dahlia today and happens to match your registered endpoint — so a routine stripe bump would move your requests while the endpoint stays pinned, and nothing would warn you.

Stripe dashboard, live mode

produces the two secrets

Leave the sandbox through the account picker first — sandbox and live keep entirely separate keys, webhooks, and data.

Confirm the live account is activated

dashboard

The charges_enabled: false I measured came from the sandbox account and says nothing about your live one. In live mode, an “Activate payments” banner means onboarding is still outstanding; no banner means you are good.

Create the live webhook endpoint

required

The endpoint registered today is livemode: false. Its signing secret will not verify live events — constructEvent throws and every tip webhook returns 400. 

URL     https://dura.dev/api/tips/webhook
Event   checkout.session.completed
→ copy the new whsec_… — it is NOT the one in .env.local

Create a restricted key

dashboard

Stripe recommends a restricted key over sk_live_. Tipping needs exactly one permission — Checkout Sessions: Write. Webhook verification is a local HMAC and needs none. The resulting rk_live_… drops straight into STRIPE_SECRET_KEY.

Turn on receipt emails

easy to miss

Settings → Customer emails → Successful payments. Nothing in DURA emails a receipt; the webhook only logs. Without this, supporters get a card charge and no paper trail, which is the other common route to a dispute.

2

Vercel environment

the moment it goes live

Settings → Environment Variables, scoped to Production only. Then redeploy — Vercel does not apply env changes to existing deployments, and skipping the redeploy is why a correct key appears not to work.

Set both secrets together

production scope 
STRIPE_SECRET_KEY       rk_live_…
STRIPE_WEBHOOK_SECRET   whsec_…   (the live one from stage 1)

Leave .env.local on the test keys. A live key there means npm run dev takes real money. Neither value belongs in the repo.

3

Prove it with one real dollar

then refund it

Live mode cannot be tested with test cards. Send yourself a $1 tip with a real card and check all four signals before trusting it.

The four signals

end to end 
1  Checkout opens        redirect to checkout.stripe.com
2  Return lands          /support?status=thanks
3  Webhook delivers      200 in Stripe → Webhooks → attempts
4  Receipt arrives       email to the card holder

Vercel runtime logs should carry the Tip received: 100 usd (payment) line from the webhook handler. Refund the dollar from the Stripe dashboard when you are done.

If anything goes wrong, the off switch already exists

Delete STRIPE_SECRET_KEY from Vercel and redeploy. getStripe() returns null, both endpoints return 503, and the tip modal shows its “Tipping isn’t available right now” notice with a link back to learning. No error state, no broken checkout, no half-charged supporter.

That graceful-degradation contract is the reason this is a low-risk launch: the failure mode of DURA's money surface is that it politely disappears. Rule 7 holds throughout — a tip unlocks nothing, so tipping being down costs a learner exactly nothing.

Not blocking, worth scheduling

  • Tip modal accessibility. No role="dialog", no aria-modal, no Escape handler, no focus trap, no backdrop dismiss. This is the money surface and currently the least accessible dialog in the app — the useFocusTrap work in A11Y-T1 should cover it.
  • isTippingEnabled() is dead code. Never imported, and its comment claims it hides the UI. It doesn't — users click, wait on a fetch, then learn it's unavailable. Either wire it into the button or delete it.
  • Unverified thank-you. success_url omits {CHECKOUT_SESSION_ID}, so /support?status=thanks greets anyone who visits the URL. Harmless while it grants nothing, but it isn't evidence of payment.
  • Webhook runs through Supabase middleware. The matcher doesn't exclude api/tips/webhook, so updateSession executes on every Stripe delivery. A Supabase hiccup turns into a 500 and a retry storm.
  • No event idempotency. Harmless while the handler only logs — but it is described as the entry point for future side effects, and Stripe redelivers.
  • Zero tests touch tips or payments.
