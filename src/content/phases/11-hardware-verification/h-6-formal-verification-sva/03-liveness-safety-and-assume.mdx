## Why this matters

Consider the assertion: "if a request is made, an acknowledge will eventually arrive." A simulator can run forever without ever seeing a request — and the assertion passes. Is the design correct? Unknown. The assertion was never actually exercised. This is called a **vacuous pass** — and it's one of the most dangerous failure modes in formal verification.

The three concepts in this lesson — safety, liveness, and assume — are what turn formal from "I ran some assertions" into "I have a mathematical claim about this design's correctness."

## Safety vs liveness — the structural split

Every formal property belongs to one of two categories.

### Safety — bad things never happen

A safety property says: "In every reachable state, this condition holds." If it's violated, there's a finite prefix (a specific input sequence) that produces the failure.

```systemverilog
// Safety: the FIFO never overflows
property p_fifo_no_overflow;
    @(posedge clk) disable iff (!rst_n)
        !(fifo_full && wr_en && !rd_en);
endproperty
assert property (p_fifo_no_overflow);

// Safety: FSM never reaches an illegal state
property p_no_illegal_state;
    @(posedge clk) disable iff (!rst_n)
        state inside {IDLE, FETCH, EXECUTE, WRITEBACK};
endproperty
assert property (p_no_illegal_state);

// Safety: AXI address must be aligned to transfer size
property p_addr_aligned;
    @(posedge clk) disable iff (!rst_n)
        awvalid |-> (awaddr[1:0] == 2'b00);    // word-aligned
endproperty
assert property (p_addr_aligned);
```

Safety is what most DV engineers start with. The formal tool explores all reachable states (bounded) and finds any that violate the safety condition.

### Liveness — good things eventually happen

A liveness property says: "From any reachable state, this condition will eventually become true." Violations require an infinite trace — the condition was never reached. In bounded model checking, liveness is approximated as "within N cycles."

```systemverilog
// Liveness: every request eventually gets acknowledged
property p_req_eventually_ack;
    @(posedge clk) disable iff (!rst_n)
        req |-> ##[1:100] ack;     // ack within 100 cycles — bounded liveness
endproperty
assert property (p_req_eventually_ack);

// Liveness: interrupt eventually cleared
property p_irq_eventually_cleared;
    @(posedge clk) disable iff (!rst_n)
        irq |-> ##[1:1000] !irq;
endproperty
assert property (p_irq_eventually_cleared);
```

The `[1:N]` bound makes these bounded liveness properties — they're technically safety properties over N cycles, but they capture the spirit of "this eventually happens." True unbounded liveness requires tools that support `$eventually` or equivalent LTL operators.

### $eventually — SVA's liveness operator

For tools that support it (Jasper, VC Formal with LTL mode):

```systemverilog
// True unbounded liveness: req implies ack eventually (no cycle bound)
property p_req_unbounded_ack;
    @(posedge clk) disable iff (!rst_n)
        req |-> s_eventually ack;
endproperty
assert property (p_req_unbounded_ack);
```

`s_eventually` (strong eventually) is checked over all infinite traces. This requires the tool to prove that no infinite trace exists where req is set but ack never arrives. Bounded model checking tools can't prove this directly; unbounded formal (IC3/PDR algorithm) can.

## Vacuity — assertions that always pass but prove nothing

A **vacuous pass** occurs when an assertion's antecedent is never activated. The assertion reports "pass" because it's never tested:

```systemverilog
// If req is never asserted in the formal environment, this always passes.
property p_never_tested;
    @(posedge clk)
        req |-> ##[1:5] ack;   // antecedent: req; consequent: ack within 5 cycles
endproperty
assert property (p_never_tested);
```

If the formal environment never generates a `req` signal, the implication is vacuously true — "for all cases where req is true (there are none), ack follows." This is a mathematical truth that proves nothing about the DUT.

### Detecting vacuity with cover property

The fix: add a `cover property` that explicitly checks the antecedent fires:

```systemverilog
// Antecedent coverage — this MUST succeed for the assertion to be non-vacuous
cover property (
    @(posedge clk) disable iff (!rst_n)
        req
);

// Or more directly: cover the full antecedent activation
cover property (
    @(posedge clk) disable iff (!rst_n)
        $rose(req)
);
```

If the cover property fails (0 hits), the assertion above is vacuous. Always check antecedent coverage before declaring formal closure.

## assume property — constraining the environment

Formal tools generate ALL possible input sequences. Most are physically impossible — no real system would drive awvalid in burst mode while simultaneously resetting. Without constraints, the formal tool explores these unrealistic states and produces counterexamples that don't correspond to real bugs.

`assume property` constrains what the environment (inputs) is allowed to do:

```systemverilog
// Assume: reset is only de-asserted after a minimum hold
// (prevents unrealistic "reset for 0 cycles" scenarios)
assume property (
    @(posedge clk)
        $rose(rst_n) |-> ##[4:$] rst_n   // hold for at least 4 cycles
);

// Assume: valid is only asserted when data is known (no X driving)
assume property (
    @(posedge clk)
        awvalid |-> !$isunknown(awaddr)
);

// Assume: interrupts are not asserted during reset
assume property (
    @(posedge clk)
        !rst_n |-> !irq
);
```

Assumptions narrow the formal search space to realistic scenarios. **Too many assumptions** makes formal too easy — it may never find real bugs. **Too few assumptions** produces false counterexamples from unrealistic inputs.

The discipline: every assumption needs a justification comment explaining what physical constraint it models.

### The assume/assert danger

An assumption that is incorrect (tighter than reality) makes formal unsound — it proves properties that only hold under the unrealistic assumption, not in the real system.

```systemverilog
// DANGEROUS: this assumption prevents the formal tool from
// ever exploring concurrent writes — but concurrent writes DO happen in silicon.
assume property (
    @(posedge clk)
        wr_en_a |-> !wr_en_b   // "only one write at a time"
);
// If this is wrong, the assertion that passes under this assumption
// may fail in silicon under concurrent writes.
```

Before adding an assumption, verify it describes a genuine hardware constraint, not just "the testbench never does this."

## Deadlock freedom — a key formal target

Deadlock: the FSM enters a state from which no transition can occur, or two agents wait for each other forever.

```systemverilog
// Deadlock freedom: from any non-idle state, the FSM eventually returns to IDLE
property p_no_deadlock;
    @(posedge clk) disable iff (!rst_n)
        (state != IDLE) |-> ##[1:200] (state == IDLE || state == DONE);
endproperty
assert property (p_no_deadlock);

// Or more specifically: state machine always makes progress
// (no cycle where state stays the same for more than 5 cycles)
property p_fsm_progress;
    @(posedge clk) disable iff (!rst_n)
        !(state [*6]);      // state cannot hold the same value for 6 consecutive cycles
                            // NOTE: requires that state is more than 1 bit wide for
                            //       this to be meaningful
endproperty
```

Deadlock is a liveness violation: the system gets stuck (bad state) and never escapes. Formal is excellent at proving deadlock freedom because it explores all reachable states.
