## Where assertions sit

An assertion is a statement: "this should always be true, or fire an error if not."

Two kinds:

- **Immediate assertion** — checked at the line where written. Like a runtime assert in C.
- **Concurrent assertion** — checked continuously over clock cycles. The SVA construct that makes property checking powerful.

```systemverilog
// Immediate (procedural)
initial begin
    assert (reset_state == IDLE) else $error("Bad init");
end

// Concurrent (clock-synchronous)
assert property (@(posedge clk) disable iff (!rst_n)
    req |-> ##[1:5] ack
);
```

The concurrent form is the heart of SVA: it says "whenever req is high, ack must be high within 1-5 cycles after."

## Property syntax — sequences and implication

```systemverilog
// Sequence: a temporal pattern
sequence req_then_ack;
    req ##[1:5] ack;
endsequence

// Property: a check using sequences
property p_req_ack;
    @(posedge clk) disable iff (!rst_n)
        $rose(req) |-> ##[1:5] $rose(ack);
endproperty

// Assertion: the check itself
assert property (p_req_ack)
    else `uvm_error("ASSERT", "req without ack within 5 cycles")
```

Operators:

- `##N` — exactly N cycles
- `##[N:M]` — between N and M cycles
- `|->` — overlapping implication (consequent starts same cycle as antecedent end)
- `|=>` — non-overlapping implication (consequent starts next cycle)
- `$rose(x)` — x transitioned 0 → 1
- `$fell(x)` — x transitioned 1 → 0
- `$stable(x)` — x didn't change
- `throughout` — condition holds throughout a sequence
- `within` — one sequence contained within another

## Simulation vs formal

| Aspect   | Simulation                           | Formal                               |
| -------- | ------------------------------------ | ------------------------------------ |
| Stimulus | You supply                           | Tool generates symbolic              |
| Coverage | What you ran                         | Exhaustive (for bounded depth)       |
| Speed    | Linear in scenarios                  | Exponential in design size           |
| Best for | System integration, dynamic behavior | Protocol correctness, corner cases   |
| Output   | Pass/fail per run                    | Mathematical proof or counterexample |

Simulation runs YOUR stimulus and checks YOUR properties. Formal explores ALL POSSIBLE stimulus that satisfies your constraints and checks the property holds in every case.

Formal's exponential complexity limits it to bounded designs — a FIFO of depth 16 with 8-bit data is tractable; a full SoC isn't. Modern formal tools use bounded model checking (BMC) with cycle limits (e.g., "prove this property for the first 50 cycles starting from any reachable state").

## When formal beats simulation

- **Deadlock freedom** — can the FSM get stuck? Formal answers yes/no with a counterexample if yes.
- **Protocol correctness** — does AXI never violate the spec? Formal proves invariants over all sequences.
- **Buffer-overflow safety** — can the FIFO overflow? Formal explores reachable states.
- **Combinational properties** — output X always equals input Y XOR input Z, for any input combination.

Random simulation might miss the one specific input sequence that breaks the property. Formal cannot miss it.

## When simulation beats formal

- **Large designs** — full SoC verification is impractical for formal.
- **Dynamic behavior** — software interaction, complex memory hierarchies.
- **Performance verification** — does the design meet throughput targets?
- **System integration** — does the chip behave correctly with realistic firmware?

The combination is the modern flow: formal for block-level protocols and corner cases, simulation for system-level integration.

## Counterexamples — reading formal output

When formal fails, it produces a counterexample — a specific sequence of inputs that violates the property. Reading it:

```
Property: axi_aw_valid_stable
Failed at: cycle 7

Cycle | rst_n | awvalid | awready | awaddr
  0   |   0   |    0    |    0    |  ----
  1   |   1   |    0    |    0    |  ----
  2   |   1   |    1    |    0    |  0x100
  3   |   1   |    1    |    0    |  0x100
  4   |   1   |    1    |    0    |  0x100
  5   |   1   |    1    |    0    |  0x100
  6   |   1   |    1    |    0    |  0x200   <- VIOLATION: awaddr changed
  7   |   1   |    1    |    0    |  0x200
```

The counterexample tells you exactly what input pattern broke the property. Often this reveals a real DUT bug. Sometimes it reveals an over-specified assertion (the property is wrong, not the design).
