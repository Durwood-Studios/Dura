## The UVM component tree

A UVM testbench is a tree of components rooted at a `uvm_test`:

```
uvm_test
└── uvm_env
    ├── uvm_agent (per interface/protocol)
    │   ├── uvm_sequencer
    │   ├── uvm_driver
    │   └── uvm_monitor
    └── uvm_scoreboard
```

Each piece has a responsibility:

- **uvm_test** — top-level. Picks which sequences run.
- **uvm_env** — owns the agents and scoreboards. Container.
- **uvm_agent** — one per protocol interface (one for AXI, one for APB, etc.). Bundles the driver, monitor, sequencer for that interface.
- **uvm_sequencer** — picks the next stimulus item from a sequence and hands it to the driver.
- **uvm_driver** — converts a transaction (high-level) into pin wiggles on the interface.
- **uvm_monitor** — observes the interface (without driving) and reconstructs transactions.
- **uvm_scoreboard** — receives observed transactions from monitors and checks they match the expected behavior.

The pattern: STIMULUS flows DOWN (sequencer → driver → interface → DUT); RESULTS flow UP (DUT → interface → monitor → scoreboard).

## A minimal agent

```systemverilog
class my_driver extends uvm_driver #(my_transaction);
    `uvm_component_utils(my_driver)
    virtual my_if vif;

    function new(string name, uvm_component parent);
        super.new(name, parent);
    endfunction

    function void build_phase(uvm_phase phase);
        if (!uvm_config_db#(virtual my_if)::get(this, "", "vif", vif))
            `uvm_fatal("DRV", "No virtual interface set")
    endfunction

    task run_phase(uvm_phase phase);
        forever begin
            my_transaction tr;
            seq_item_port.get_next_item(tr);
            drive_to_interface(tr);
            seq_item_port.item_done();
        end
    endtask

    task drive_to_interface(my_transaction tr);
        @(posedge vif.clk);
        vif.valid <= 1'b1;
        vif.data  <= tr.data;
        @(posedge vif.clk iff vif.ready);
        vif.valid <= 1'b0;
    endtask
endclass
```

What this driver does:

1. Gets a virtual interface handle in `build_phase` (UVM's setup phase).
2. In `run_phase` (main sim execution), forever: get a transaction, drive it, ack.
3. The `drive_to_interface` task is the protocol-specific logic — handshake the valid/ready, hold for one cycle, etc.

The monitor is similar but passive:

```systemverilog
class my_monitor extends uvm_monitor;
    `uvm_component_utils(my_monitor)
    virtual my_if vif;
    uvm_analysis_port #(my_transaction) ap;

    function new(string name, uvm_component parent);
        super.new(name, parent);
        ap = new("ap", this);
    endfunction

    task run_phase(uvm_phase phase);
        forever begin
            @(posedge vif.clk iff vif.valid && vif.ready);
            my_transaction tr = my_transaction::type_id::create("tr");
            tr.data = vif.data;
            ap.write(tr);
        end
    endtask
endclass
```

The monitor:

1. Observes the interface but never drives it.
2. When it sees a valid handshake, reconstructs a transaction.
3. Publishes the transaction via an `uvm_analysis_port` — any subscriber (scoreboard, coverage collector) receives it.

## TLM — the connection model

Transactions flow between components via TLM (Transaction-Level Modeling) ports:

- **Sequencer → Driver** uses `uvm_seq_item_pull_port`. The driver requests; the sequencer responds.
- **Monitor → Scoreboard** uses `uvm_analysis_port`. The monitor broadcasts; any number of subscribers receive.

The connection happens in the parent's `connect_phase`:

```systemverilog
function void connect_phase(uvm_phase phase);
    driver.seq_item_port.connect(sequencer.seq_item_export);
    monitor.ap.connect(scoreboard.analysis_export);
endfunction
```

The pattern enforces a clean separation: driver and sequencer know about each other through a port abstraction, not via direct handles. This is what enables replacing components without rewriting the testbench.

## The UVM factory — substitution without editing

UVM's factory pattern lets you substitute one class for another at runtime. The pattern:

```systemverilog
// Standard class
class normal_driver extends uvm_driver #(my_transaction);
    `uvm_component_utils(normal_driver)
    // ... regular implementation
endclass

// Error-injection variant
class error_inject_driver extends normal_driver;
    `uvm_component_utils(error_inject_driver)
    // Override behavior to inject errors
endclass

// In your test:
class error_test extends uvm_test;
    function void build_phase(uvm_phase phase);
        normal_driver::type_id::set_type_override(error_inject_driver::get_type());
        env = my_env::type_id::create("env", this);
    endfunction
endclass
```

The environment builds normally, but every `normal_driver` instance is silently replaced by `error_inject_driver`. The testbench wiring isn't edited; only the test class is.

This is how DV teams maintain ONE testbench that runs dozens of different tests — coverage tests, regression tests, error-injection tests — without forking the testbench.

## Phases — the UVM execution model

UVM standardizes when things happen via PHASES. The main ones:

```
build_phase     → components instantiate their sub-components
connect_phase   → TLM connections established
end_of_elab     → testbench fully built; one last check
run_phase       → simulation runs (forever loops live here)
extract/check   → after sim, gather and verify final state
report_phase    → print summary
```

Phases happen in order. Each phase is implicit barrier-synchronized across all components. You override the phases you care about; the rest do nothing.

The phase model is why UVM testbenches are predictable — every component's `build_phase` completes before any `connect_phase` starts, so connections can rely on all components existing.
