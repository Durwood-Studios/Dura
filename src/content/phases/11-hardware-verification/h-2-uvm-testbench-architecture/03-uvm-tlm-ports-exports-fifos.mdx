## The TLM connection model

TLM (Transaction-Level Modeling) defines a set of interfaces for moving objects between components. The two endpoints are:

- **Port** — the initiator. Lives on the component that wants to SEND or REQUEST. Contains a handle that points to the other end.
- **Export / Imp** — the responder. Lives on the component that RECEIVES or RESPONDS. Implements the actual method.

The rule: a port connects TO an export. Never port-to-port. Never export-to-export.

```
Component A          Component B
┌──────────┐         ┌──────────┐
│ put_port │────────▶│put_export│
│  (calls) │         │(responds)│
└──────────┘         └──────────┘
```

## Port types — blocking vs non-blocking

```systemverilog
// Blocking put: caller blocks until receiver accepts
uvm_blocking_put_port #(my_txn) put_p;

// Non-blocking put: returns immediately with success/failure
uvm_nonblocking_put_port #(my_txn) try_put_p;

// Both: combined interface
uvm_put_port #(my_txn) combined_p;

// Blocking get: caller blocks until sender has something
uvm_blocking_get_port #(my_txn) get_p;

// Peek: like get but doesn't consume the transaction
uvm_blocking_peek_port #(my_txn) peek_p;
```

Matching rule: port type must match export type. A `blocking_put_port` connects to a `blocking_put_export` or a `put_export` (combined). Mismatches produce elaboration-time errors.

## Analysis ports — the broadcast pattern

The most common TLM connection in UVM is the analysis port — one monitor broadcasting to multiple subscribers:

```systemverilog
class my_monitor extends uvm_monitor;
    `uvm_component_utils(my_monitor)
    uvm_analysis_port #(my_txn) ap;   // Broadcast port

    function new(string name, uvm_component parent);
        super.new(name, parent);
        ap = new("ap", this);
    endfunction

    task run_phase(uvm_phase phase);
        my_txn tr;
        forever begin
            sample_from_interface(tr);
            ap.write(tr);   // Fan-out to ALL connected subscribers
        end
    endtask
endclass
```

The `uvm_analysis_port::write()` is non-blocking and fans out to every connected `uvm_analysis_export`. You can have zero subscribers (no error) or ten subscribers — all receive the same transaction object. (Be careful: if a subscriber modifies the transaction, all subsequent subscribers see the modification. Clone before modifying.)

## uvm_analysis_export and uvm_analysis_imp

A scoreboard receives from the analysis port via an export:

```systemverilog
class my_scoreboard extends uvm_scoreboard;
    `uvm_component_utils(my_scoreboard)
    // Imp = implementation: directly calls a method on THIS component
    uvm_analysis_imp #(my_txn, my_scoreboard) analysis_export;

    function new(string name, uvm_component parent);
        super.new(name, parent);
        analysis_export = new("analysis_export", this);
    endfunction

    // Called automatically when ap.write() fires
    function void write(my_txn tr);
        // Check tr against expected
        $display("[SB] received: data=0x%h", tr.data);
    endfunction
endclass
```

`uvm_analysis_imp #(T, COMP)` is a special imp (implementation) type that calls `write(T)` on the `COMP` component. The scoreboard implements `write()` as a regular function — no explicit `forever` loop needed.

## Multiple analysis exports on one component

A scoreboard receiving from TWO monitors (request side and response side) needs two exports:

```systemverilog
// Use the macro to create two uniquely-named imp types
`uvm_analysis_imp_decl(_req)   // Creates uvm_analysis_imp_req
`uvm_analysis_imp_decl(_rsp)   // Creates uvm_analysis_imp_rsp

class dual_sb extends uvm_scoreboard;
    `uvm_component_utils(dual_sb)
    uvm_analysis_imp_req #(req_txn, dual_sb) req_ap;
    uvm_analysis_imp_rsp #(rsp_txn, dual_sb) rsp_ap;

    function void write_req(req_txn tr);  // Called for req transactions
        req_q.push_back(tr);
    endfunction

    function void write_rsp(rsp_txn tr);  // Called for rsp transactions
        check(req_q.pop_front(), tr);
    endfunction
endclass
```

The `_decl` macros generate unique imp types whose `write()` calls the correspondingly-named `write_req()` / `write_rsp()` functions.

## uvm_tlm_fifo — decoupling producer and consumer

When a producer and consumer run at different rates, a FIFO buffers between them:

```systemverilog
// In the environment connect_phase:
uvm_tlm_fifo #(my_txn) fifo;
fifo = new("fifo", this);

// Driver's put_port → FIFO's put_export
driver.put_port.connect(fifo.put_export);

// Monitor's get_port → FIFO's get_export
monitor.get_port.connect(fifo.get_export);
```

The FIFO's depth is a constructor argument:

```systemverilog
fifo = new("fifo", this, 16);   // 16-entry deep FIFO
```

With depth 0 (synchronous): producer blocks until consumer is ready.
With depth N: producer can fill up to N before blocking.

## Connecting in connect_phase

```systemverilog
class my_env extends uvm_env;
    `uvm_component_utils(my_env)
    my_agent      agent;
    my_scoreboard sb;

    function void connect_phase(uvm_phase phase);
        // Monitor's analysis port → Scoreboard's analysis export
        agent.monitor.ap.connect(sb.analysis_export);

        // Alternatively: driver seq_item_port already connected inside agent
        // (agent's connect_phase handles internal connections)
    endfunction
endclass
```

The parent's `connect_phase` makes CROSS-COMPONENT connections. Each component's own `connect_phase` makes INTERNAL connections (driver port to sequencer export).
