## Why this matters

The H5-01 sequence pattern drives transactions at the DUT and moves on. Many protocols require the other direction too: the sequence sends a READ request, and then needs to receive the returned data to check it against the expected value, or to generate the next request based on what was read.

Without response handling, sequences are one-way. With it, they model full protocol round-trips.

## Start with something familiar

A numbered claim ticket lets a customer match a returned item to the original request.

## The mental model

> Sequence responses need correct sequence and transaction identification, bounded queues, and consumption by the intended requester.

## The response flow

```
Sequence                    Sequencer           Driver              DUT
   │                           │                  │                  │
   ├──start_item(tr)──────────►│                  │                  │
   │◄──(blocked)──────────────◄│                  │                  │
   ├──finish_item(tr)─────────►│                  │                  │
   │                           ├──get_next_item──►│                  │
   │                           │◄──(tr returned)──│                  │
   │                           │                  ├──drive signals──►│
   │                           │                  │◄──(DUT responds)─│
   │                           │                  ├──put_response────►│──(into response queue)
   │                           │                  ├──item_done───────►│
   ├──get_response(rsp)───────►│◄───(rsp taken)───│                  │
```

The driver calls `put_response(rsp)` after the DUT responds. The sequencer queues the response. The sequence calls `get_response(rsp)` to retrieve it.

## Driver side: put_response()

```systemverilog
class axi_read_driver extends uvm_driver #(axi_txn);
    `uvm_component_utils(axi_read_driver)
    virtual axi_if vif;

    task run_phase(uvm_phase phase);
        forever begin
            axi_txn req;
            seq_item_port.get_next_item(req);

            // Drive the read address channel
            @(posedge vif.clk);
            vif.arvalid <= 1'b1;
            vif.araddr  <= req.addr;
            @(posedge vif.clk iff vif.arready);
            vif.arvalid <= 1'b0;

            // Wait for read data channel
            @(posedge vif.clk iff vif.rvalid);

            // Build the response transaction
            axi_txn rsp = axi_txn::type_id::create("rsp");
            rsp.set_id_info(req);   // CRITICAL: copy the ID from the request
            rsp.data  = vif.rdata;
            rsp.resp  = vif.rresp;
            rsp.addr  = req.addr;

            seq_item_port.item_done(rsp);   // Sends response and acks in one call
            // OR equivalently:
            // seq_item_port.put_response(rsp);
            // seq_item_port.item_done();
        end
    endtask
endclass
```

`set_id_info(req)` copies the request's sequence ID into the response. Without this, the sequencer doesn't know which sequence to route the response to.

## Sequence side: get_response()

```systemverilog
class axi_read_seq extends uvm_sequence #(axi_txn);
    `uvm_object_utils(axi_read_seq)
    bit [31:0] expected_data[];

    task body();
        axi_txn req, rsp;
        foreach (expected_data[i]) begin
            req = axi_txn::type_id::create("req");
            start_item(req);
            req.op   = AXI_READ;
            req.addr = i * 4;
            finish_item(req);

            // Wait for the DUT response
            get_response(rsp);

            // Check the returned data
            if (rsp.data !== expected_data[i]) begin
                `uvm_error("RD_CHECK",
                    $sformatf("addr=0x%h: expected 0x%h, got 0x%h",
                        req.addr, expected_data[i], rsp.data))
            end
        end
    endtask
endclass
```

`get_response(rsp)` blocks until a response with a matching ID arrives in the queue. The sequence then inspects `rsp.data`, `rsp.resp`, etc.

## Response IDs — why they matter

When multiple sequences run on the same sequencer, responses must route to the right sequence. The mechanism is the sequence ID embedded in the transaction.

```systemverilog
// The sequencer assigns each sequence a unique ID when start() is called.
// put_response() stores the response, tagged with its ID.
// get_response() retrieves only responses matching the calling sequence's ID.
```

Without `set_id_info(req)` in the driver, every response has ID=0. The sequencer routes it to whichever sequence asks first — nondeterministic and almost always wrong in multi-sequence testbenches.

The debug symptom: responses are retrieved by the wrong sequence, producing incorrect data comparisons even when the DUT is correct.

## Response handler callback — non-blocking alternative

Blocking in `body()` on `get_response()` works, but adds latency: the next request waits until the previous response arrives. For pipelined protocols (AXI, PCIe), you want to issue multiple requests before any response arrives.

Use `use_response_handler(1)` and override `response_handler()`:

```systemverilog
class pipelined_read_seq extends uvm_sequence #(axi_txn);
    `uvm_object_utils(pipelined_read_seq)
    int outstanding;
    bit [31:0] check_data[int];   // indexed by addr

    function new(string name = "pipelined_read_seq");
        super.new(name);
        use_response_handler(1);   // Enable callback mode
    endfunction

    // Called automatically when a response arrives — non-blocking
    function void response_handler(uvm_sequence_item response);
        axi_txn rsp;
        if (!$cast(rsp, response)) return;
        if (rsp.data !== check_data[rsp.addr]) begin
            `uvm_error("PIPELINE_CHK",
                $sformatf("Addr 0x%h: exp=0x%h got=0x%h",
                    rsp.addr, check_data[rsp.addr], rsp.data))
        end
        outstanding--;
    endfunction

    task body();
        axi_txn req;
        outstanding = 0;
        for (int i = 0; i < 16; i++) begin
            req = axi_txn::type_id::create($sformatf("req%0d", i));
            start_item(req);
            req.op   = AXI_READ;
            req.addr = i * 4;
            check_data[req.addr] = expected[i];
            finish_item(req);
            outstanding++;
        end
        // Wait for all responses to arrive via response_handler
        wait (outstanding == 0);
    endtask
endclass
```

This issues all 16 reads without waiting for any response, then waits for all responses to arrive via the callback. AXI-style out-of-order responses are handled correctly because each response is matched by ID.

## Choosing between the two patterns

| Pattern                       | Use when                                                         |
| ----------------------------- | ---------------------------------------------------------------- |
| In-body `get_response()`      | Protocol is non-pipelined (one req, then one rsp, then next req) |
| `response_handler()` callback | Protocol allows outstanding transactions (AXI, PCIe, USB)        |

APB and SPI are sequential — in-body `get_response()`. AXI and PCIe are pipelined — use the callback pattern.
