## Why this matters

The H5-01 lesson showed `seq.start(sequencer)` running one sequence at a time. Production testbenches are more complex: a background traffic generator, an error-injection sequence, and a directed test sequence all run concurrently on the same sequencer. The sequencer must decide which sequence gets to send the next transaction. That decision is arbitration, and getting it wrong produces testbenches where one sequence silently starves another.

Arbitration bugs are among the hardest DV bugs to diagnose: the simulation passes, coverage looks normal, but one scenario the starvation prevents is the exact scenario that hides the DUT bug.

## The four arbitration modes

UVM sequencers support four built-in arbitration policies, set via `set_arbitration()`:

```systemverilog
sequencer.set_arbitration(UVM_SEQ_ARB_FIFO);       // Default
sequencer.set_arbitration(UVM_SEQ_ARB_STRICT_FIFO);
sequencer.set_arbitration(UVM_SEQ_ARB_WEIGHTED);
sequencer.set_arbitration(UVM_SEQ_ARB_RANDOM);
```

### UVM_SEQ_ARB_FIFO (default)

Sequences are granted access in first-in, first-out order. A sequence that calls `start_item` first gets the sequencer first, regardless of priority. Most testbenches use this; it's the simplest and most predictable.

```
Sequence A starts_item at t=0  ──► served first
Sequence B starts_item at t=0  ──► served second (same cycle → A wins by call order)
Sequence A starts_item at t=5  ──► served third
```

### UVM_SEQ_ARB_STRICT_FIFO

Respects sequence priority. A sequence with a higher `priority` argument in `start()` always beats a lower-priority one, regardless of who called `start_item` first.

```systemverilog
// Background traffic: low priority
bg_seq.start(sequencer, .priority(10));

// Error injection: high priority, always preempts
err_seq.start(sequencer, .priority(200));
```

With `STRICT_FIFO`, the high-priority sequence gets every item it needs before the low-priority sequence can proceed. Useful for watchdog sequences that must fire at specific moments.

### UVM_SEQ_ARB_WEIGHTED

Each competing sequence gets a share of accesses proportional to its priority value. Priority 200 vs priority 100: the first sequence gets roughly 2× as many slots. Not strict starvation, but biased.

### UVM_SEQ_ARB_RANDOM

The sequencer randomly selects which waiting sequence goes next. Priority is ignored. Useful for stress-testing with nondeterministic interleaving — produces rare orderings that FIFO-based testing misses.

## Lock — exclusive access with queuing

`lock()` asks the sequencer for exclusive access. Queued: if another sequence holds the lock, `lock()` blocks until the current holder releases.

```systemverilog
class atomic_read_modify_write_seq extends uvm_sequence #(my_txn);
    `uvm_object_utils(atomic_read_modify_write_seq)

    task body();
        my_txn rd, wr;

        // --- LOCK: no other sequence can interleave here ---
        m_sequencer.lock(this);

        rd = my_txn::type_id::create("rd");
        start_item(rd);
        rd.op = READ;
        rd.addr = 32'hABCD_0000;
        assert(rd.randomize() with { op == READ; });
        finish_item(rd);   // Read completes

        wr = my_txn::type_id::create("wr");
        start_item(wr);
        wr.op   = WRITE;
        wr.addr = rd.addr;
        wr.data = rd.data | 32'h0000_0001;   // Set bit 0
        finish_item(wr);   // Write back — must be atomic with read

        // --- UNLOCK ---
        m_sequencer.unlock(this);
    endtask
endclass
```

While this sequence holds the lock, no other sequence can call `get_next_item` on the sequencer — even a higher-priority one. The lock guarantees the read and write are consecutive transactions with no interleaving.

`unlock()` releases the lock. If you forget to call it, the sequencer is permanently blocked — a deadlock. Wrap lock/unlock in try/finally patterns where your simulator supports it.

## Grab — immediate exclusive access

`grab()` is similar to `lock()` but jumps the queue instead of waiting at the end:

```systemverilog
// grab() takes effect immediately — kicks out whoever was waiting
m_sequencer.grab(this);
// ... exclusive transactions ...
m_sequencer.ungrab(this);
```

The distinction:

- `lock()` waits for the current transaction to complete, then goes to the front of the queue.
- `grab()` takes effect on the next call to `get_next_item`, preempting any pending `start_item`.

Use `grab()` when you need to inject a sequence at a specific moment regardless of what else is happening — for example, a sequence that fires when a hardware interrupt is detected and must respond before any other activity.

## Starvation — the classic failure mode

```systemverilog
// This testbench has a starvation bug
initial begin
    fork
        forever begin
            bg_seq.randomize();
            bg_seq.start(sequencer);   // Runs a 10,000-transaction burst
        end
        begin
            #5000;  // Wait 5000 time units, then fire error injection
            err_seq.start(sequencer);  // STARVED — bg_seq holds the sequencer for 10K txns
        end
    join_any
end
```

The background sequence issues 10,000 transactions without releasing. The error sequence never runs.

Fix: either split the background sequence into shorter bursts that yield more frequently, or use priority + `STRICT_FIFO` so the error sequence can preempt:

```systemverilog
// Background traffic: small bursts, yielding often
class bg_traffic_seq extends uvm_sequence #(my_txn);
    task body();
        repeat (10) begin   // 10 transactions per burst, not 10,000
            my_txn tr = my_txn::type_id::create("tr");
            start_item(tr);
            assert(tr.randomize());
            finish_item(tr);
        end
    endtask
endclass
```

With small bursts, the error injection sequence gets to run between them.
