## The shift in mindset

Directed testing: an engineer enumerates scenarios — "send a write to address 0; then a write to 0xFF; then a write to 0x100..." Each scenario hand-written.

Constrained-random: an engineer describes the SPACE of valid transactions, and the solver generates random instances. One class definition produces thousands of unique scenarios.

```systemverilog
class write_txn;
    rand bit [31:0] addr;
    rand bit [31:0] data;
    rand bit [3:0]  strb;

    constraint addr_aligned   { addr[1:0] == 2'b00; }
    constraint strb_meaningful { strb != 4'b0000; }
    constraint addr_range      { addr inside { [32'h0000_0000 : 32'h0001_FFFF] }; }
endclass

// Usage
write_txn tx = new();
repeat (1000) begin
    tx.randomize();
    drive(tx);   // Each iteration is a unique, valid write
end
```

The solver picks `addr`, `data`, `strb` values that satisfy all constraints. 1000 unique writes — far more scenario coverage than anyone would write by hand.

## rand vs randc

```systemverilog
rand  bit [3:0] x;    // Each randomize() picks fresh — may repeat
randc bit [3:0] y;    // Cycles through all 16 values before repeating
```

`randc` is useful when you want to GUARANTEE coverage of every value in the range. `rand` is faster and produces more "interesting" distributions but doesn't guarantee value-set coverage.

## Constraint relationships

Constraints can relate multiple fields:

```systemverilog
class burst_txn;
    rand bit [7:0]  len;
    rand bit [31:0] addr;

    // Aligned to len bytes
    constraint align { (addr % len) == 0; }

    // Don't cross a 4 KB boundary (AXI requirement)
    constraint no_4k_cross {
        ((addr & 32'hFFFF_F000) == ((addr + len - 1) & 32'hFFFF_F000));
    }
endclass
```

## Soft constraints — overridable defaults

```systemverilog
constraint c_default_small {
    soft addr inside { [0 : 32'h0FFF] };   // Soft: prefer small but allow override
}
```

`soft` constraints can be overridden by an external `randomize() with` call. Use them for sensible defaults that specific tests want to relax.

## Inline overrides

In a specific test, override constraints without editing the class:

```systemverilog
tx.randomize() with { addr inside { [32'h1_0000 : 32'h2_0000] }; };
```

This adds an extra constraint for this one randomize call — useful when the same transaction class is reused across many tests with different address ranges.

## Distribution control

```systemverilog
constraint c_data {
    data dist {
        32'h0          := 30,    // 30% weight: zero
        [32'h1:32'hFF] := 50,    // 50%: small
        [32'h100:32'hFFFF_FFFF] := 20   // 20%: large
    };
}
```

`dist` controls the probability distribution. Useful when uniform distribution doesn't exercise corner cases — bias toward boundary values that are most likely to find bugs.

## Solver conflicts

When constraints can't be simultaneously satisfied, the solver fails:

```systemverilog
constraint c1 { x > 100; }
constraint c2 { x < 50; }
// randomize() returns 0; tx is unchanged
```

Debugging:

1. Disable constraints one at a time (`tx.c1.constraint_mode(0);`) to find which conflict.
2. Use simulator's constraint debugging (Questa's `-debug_solver`, VCS's `-constraint_debug`).
3. Avoid over-constraint: each constraint should have a clear necessity.
