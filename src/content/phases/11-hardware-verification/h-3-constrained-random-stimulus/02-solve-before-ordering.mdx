## Why this matters

Imagine you're generating burst-write transactions. Each burst has a `len` field (1–16 beats) and an `addr` field that must be aligned to `len × 4` bytes. Your constraint looks correct — but after 10,000 randomizations, the coverage report shows that `len=16` almost never occurs.

The solver is choosing `addr` first from a large space, then solving `len` such that alignment holds. Because most addresses only divide evenly by small values of `len`, the solver gravitates toward `len=1`. The constraint is right; the ordering is wrong.

`solve-before` exists to fix this.

## How the SV solver works

The IEEE 1800-2023 solver treats all `rand` variables and constraints as a constraint satisfaction problem (CSP). In principle it picks a satisfying assignment simultaneously. In practice, solvers use variable ordering heuristics to decompose the problem, and those heuristics can produce biased distributions when constraint relationships are asymmetric.

The default variable-ordering heuristic varies between simulators (Questa, VCS, Xcelium all differ). This is why a testbench that "works" in one simulator can have a completely different distribution in another — both satisfy the constraints, but the coverage profiles differ. `solve-before` makes the ordering explicit and portable.

## solve-before syntax

```systemverilog
class burst_txn;
    rand bit [3:0]  len;   // 1-16 beats
    rand bit [31:0] addr;

    // Alignment: addr must be a multiple of len*4
    constraint c_align { (addr % (len * 4)) == 0; }

    // Alignment range: addr in 4 KB window
    constraint c_range { addr inside { [0 : 32'h0000_0FFF] }; }

    // Tell the solver: pick len FIRST, then pick addr satisfying c_align
    // Without this, the solver may pick addr first and bias toward small len.
    constraint c_order { solve len before addr; }

    constraint c_len { len inside { [1:16] }; }
endclass
```

With `solve len before addr`, the solver:

1. Picks `len` uniformly in [1:16].
2. Picks `addr` from values that satisfy `c_align` given the chosen `len`.

Result: `len` is uniformly distributed across 1–16. Without `solve-before`, small `len` values dominate because they have more satisfying `addr` values.

## Constraint implication — the -> operator

The implication operator `->` (if A then B) creates conditional constraints:

```systemverilog
class mem_txn;
    rand bit [1:0]  txn_type;   // 0=read, 1=write, 2=atomic, 3=prefetch
    rand bit [7:0]  data;
    rand bit        poison;

    // Poison bit: only relevant for writes and atomics
    constraint c_poison {
        (txn_type inside {1, 2}) -> (poison inside {0, 1});  // free
        !(txn_type inside {1, 2}) -> (poison == 0);           // force 0 for reads/prefetch
    }
endclass
```

The implication `A -> B` is logically equivalent to `(!A) || B` — if A is false, the constraint is vacuously satisfied; if A is true, B must also be true.

A common mistake: writing a one-sided implication and expecting it to enforce BOTH directions.

```systemverilog
// WRONG INTENT: engineer wants poison=1 to ONLY occur with writes
constraint c_bad { poison -> (txn_type == 1); }
// This says: IF poison=1 THEN type=1. But it does NOT say IF type=0 THEN poison=0.
// poison=0 with type=0,2,3 is legal. poison=1 with type=0 is forbidden.
// The intent is right but only half the story.

// CORRECT: add the reverse
constraint c_correct {
    poison -> (txn_type inside {1, 2});
    // Now: poison=1 forces type to be write or atomic.
    // type=0 (read) doesn't force poison, but combined with not-meeting-antecedent,
    // poison can be 0 or 1. If you ALSO want type=read to REQUIRE poison=0:
    (txn_type == 0) -> (poison == 0);
}
```

## Bidirectional constraints vs solve-before

Bidirectional constraints are symmetric — they restrict the joint distribution. `solve-before` affects only the distribution, not the set of legal values.

```systemverilog
// This constraint is bidirectional — it restricts (len, addr) pairs:
constraint c_align { (addr % (len * 4)) == 0; }

// This ordering hint only affects distribution, not legality:
constraint c_order { solve len before addr; }

// Both together: solve-before makes the distribution of (len, addr) more uniform.
// Without it, the pair distribution is biased toward small len.
```

Think of it this way:

- Constraints define the FEASIBLE SET (which values are legal).
- `solve-before` affects SAMPLING within that feasible set (which legal values are chosen more often).

## When solve-before is NOT the answer

`solve-before` cannot rescue an over-constrained or inherently asymmetric problem. If:

- Only 1% of `addr` values are `len=16` aligned in your address range, then even with `solve len before addr`, hitting `len=16` requires that `addr` is in the small set of aligned values.
- You genuinely want uniform coverage of all `(len, addr)` combinations, you need a `dist` directive or a directed sequence for the corner cases.

`solve-before` helps when the feasible set IS large enough to support uniform distribution but the solver's ordering heuristic produces a biased sample.
