## Why this matters

Where should coverage sampling happen? NOT in the driver (it doesn't see DUT responses). NOT in the sequence (it doesn't see what actually occurred on the interface). The right place is the MONITOR — it observes both what was driven and what the DUT responded.

But the monitor shouldn't contain coverage logic either. Coverage requirements change; the monitor's job (faithfully reconstructing transactions from the interface) doesn't. The right architecture:

```
Monitor (observe + publish)
    │  uvm_analysis_port #(txn)
    ├──→ Scoreboard (check correctness)
    ├──→ Coverage Collector A (functional coverage)
    └──→ Coverage Collector B (protocol coverage)
```

The analysis port broadcasts to all subscribers. Adding or removing a coverage collector doesn't touch the monitor.

## uvm_subscriber — the canonical subscriber

`uvm_subscriber` is a UVM base class that provides an analysis export and requires you to implement `write()`. It's the simplest path to a coverage collector:

```systemverilog
class axi_write_cov extends uvm_subscriber #(axi4_lite_write_txn);
    `uvm_component_utils(axi_write_cov)

    axi4_lite_write_txn cur;

    covergroup cg_write;
        cp_addr : coverpoint cur.awaddr[15:12] {
            bins zones[] = { [0:15] };
        }

        cp_strb : coverpoint cur.wstrb {
            bins full    = { 4'b1111 };
            bins partial = default;
        }

        cx : cross cp_addr, cp_strb;
    endgroup

    function new(string name, uvm_component parent);
        super.new(name, parent);
        cg_write = new();
    endfunction

    // write() is called automatically by the analysis port every time
    // the monitor publishes a transaction.
    function void write(axi4_lite_write_txn t);
        cur = t;
        cg_write.sample();
    endfunction
endclass
```

`uvm_subscriber #(T)` automatically provides:

- An analysis export (`analysis_export`) that accepts type T.
- A pure virtual `write(T t)` method you must implement.

The covergroup samples `cur` which is set to the received transaction. This is the production pattern used in every UVM testbench.

## Connecting subscriber to monitor in the environment

```systemverilog
class axi_env extends uvm_env;
    `uvm_component_utils(axi_env)

    axi_agent        agent;
    axi_scoreboard   scoreboard;
    axi_write_cov    write_cov;    // Coverage collector

    function void build_phase(uvm_phase phase);
        agent      = axi_agent::type_id::create("agent", this);
        scoreboard = axi_scoreboard::type_id::create("scoreboard", this);
        write_cov  = axi_write_cov::type_id::create("write_cov", this);
    endfunction

    function void connect_phase(uvm_phase phase);
        // Monitor broadcasts to both scoreboard and coverage collector
        agent.monitor.ap.connect(scoreboard.analysis_export);
        agent.monitor.ap.connect(write_cov.analysis_export);
        // uvm_analysis_port supports multiple subscribers (fan-out)
    endfunction
endclass
```

The `uvm_analysis_port` supports unlimited fan-out — one `ap.write(txn)` call in the monitor calls `write()` on every connected subscriber. Connecting a second coverage collector costs one line in `connect_phase`.

## uvm_analysis_imp — when you need multiple write() methods

A scoreboard that receives transactions from two monitors (one per protocol) can't use `uvm_subscriber` (only one write()). Instead, use `uvm_analysis_imp` with a tag:

```systemverilog
// Declare two typed analysis exports
`uvm_analysis_imp_decl(_write_channel)
`uvm_analysis_imp_decl(_read_channel)

class axi_scoreboard extends uvm_scoreboard;
    `uvm_component_utils(axi_scoreboard)

    uvm_analysis_imp_write_channel #(axi_write_txn, axi_scoreboard) write_export;
    uvm_analysis_imp_read_channel  #(axi_read_txn,  axi_scoreboard) read_export;

    function void build_phase(uvm_phase phase);
        write_export = new("write_export", this);
        read_export  = new("read_export",  this);
    endfunction

    // Called when write monitor publishes
    function void write_write_channel(axi_write_txn t);
        check_write(t);
    endfunction

    // Called when read monitor publishes
    function void write_read_channel(axi_read_txn t);
        check_read(t);
    endfunction
endclass
```

The macro `uvm_analysis_imp_decl(_suffix)` generates an analysis imp with a method named `write_suffix()`. This pattern enables one component to receive from multiple sources with type safety.

## Sampling strategy — when to sample

The covergroup samples on each `write()` call. But WHEN is write() called? The monitor decides:

```systemverilog
class axi_monitor extends uvm_monitor;
    task run_phase(uvm_phase phase);
        forever begin
            // Option A: sample on transaction completion
            @(posedge vif.clk iff vif.bvalid && vif.bready);
            txn = reconstruct_txn_from_interface();
            ap.write(txn);   // Triggers ALL subscribers including coverage
        end
    endtask
endclass
```

Two common sampling points and what they cover:

| Sampling point           | Covers                                         | Misses                           |
| ------------------------ | ---------------------------------------------- | -------------------------------- |
| Transaction start (AW+W) | What was requested (stimulus coverage)         | The DUT's response (BRESP)       |
| Transaction complete (B) | Full round-trip including response             | Transactions that don't complete |
| Both                     | Full visibility — two analysis ports, two cg's | Nothing                          |

For protocol coverage (did we exercise every request type?), sample at start. For correctness-checking coverage (did every request get a valid response?), sample at completion. Many covergroups need both.

## Coverage collector vs direct sampling

An alternative to the subscriber pattern: call `cg.sample()` directly inside the monitor. This works but creates tight coupling:

```systemverilog
// Anti-pattern: coverage inside the monitor
task run_phase(uvm_phase phase);
    forever begin
        @(transaction_complete);
        txn = reconstruct();
        cg.sample(txn);        // Coverage coupled to monitor
        ap.write(txn);
    end
endtask
```

Problems: the monitor is now responsible for coverage — a separate verification concern. To add a new coverage metric, you edit the monitor. To disable coverage in a gate-level simulation, you edit the monitor. The subscriber pattern avoids all of this.
