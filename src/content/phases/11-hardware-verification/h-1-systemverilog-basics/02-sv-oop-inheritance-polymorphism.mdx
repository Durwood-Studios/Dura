## Why this matters

When you open any UVM class definition — `uvm_driver`, `uvm_monitor`, `uvm_scoreboard` — the first line is always something like `class my_driver extends uvm_driver #(my_txn)`. Everything downstream flows from that `extends`. Without understanding inheritance and polymorphism, UVM reads as magic. With it, UVM reads as a straightforward application of well-known OOP patterns in SystemVerilog syntax.

## Inheritance — extending a base class

```systemverilog
// Base class: generic transaction
class base_txn;
    rand bit [31:0] addr;
    rand bit [7:0]  data;
    int             tag;

    function new(int t = 0);
        tag = t;
    endfunction

    virtual function void print();
        $display("[base_txn] addr=0x%h data=0x%h tag=%0d", addr, data, tag);
    endfunction
endclass

// Derived class: adds burst capability
class burst_txn extends base_txn;
    rand int unsigned len;
    constraint c_len { len inside { [1:16] }; }

    function new(int t = 0);
        super.new(t);   // Call parent constructor
    endfunction

    // Override the print method
    virtual function void print();
        $display("[burst_txn] addr=0x%h data=0x%h len=%0d tag=%0d",
                 addr, data, len, tag);
    endfunction
endclass
```

Key mechanics:

- `extends base_txn` — `burst_txn` inherits all fields and methods from `base_txn`.
- `super.new(t)` — explicitly calls the parent's constructor. Always required when the parent constructor has required arguments.
- The derived class CAN access `addr`, `data`, `tag` directly — they're inherited.
- The derived class CAN override methods declared `virtual` in the parent.

## Polymorphism — one handle, many types

The power: a base-class handle can hold a derived-class object.

```systemverilog
base_txn  bh;        // Base-class handle
burst_txn bt = new();
bt.addr = 32'hDEAD;
bt.len  = 4;

bh = bt;             // Legal: derived IS-A base
bh.print();          // Calls burst_txn::print() — polymorphic dispatch!
```

`bh` is typed as `base_txn`, but it holds a `burst_txn`. When `print()` is called, SystemVerilog dispatches to the ACTUAL object type, not the handle type. This is polymorphism.

This is exactly how UVM's analysis ports work: they hold `uvm_sequence_item` handles that are actually protocol-specific transactions.

## $cast — safe downcast

Going the other direction (base handle → derived type) requires a runtime check:

```systemverilog
base_txn  bh;
burst_txn bt;

// Dynamic cast — safe
if (!$cast(bt, bh)) begin
    `uvm_fatal("CAST", "Handle is not a burst_txn")
end
// If $cast succeeds, bt now holds the derived object

// Static cast (no check) — DANGEROUS, avoid
bt = burst_txn'(bh);   // Compiles but silently corrupts if types don't match
```

`$cast` returns 0 on failure (type mismatch) instead of crashing. Always use `$cast` for downcasts. UVM's factory uses `$cast` internally every time it returns a component.

## Virtual methods — the dispatch contract

A method declared `virtual` in the base class can be overridden in any derived class:

```systemverilog
class base_txn;
    virtual function void print();   // virtual = overridable
        $display("base");
    endfunction

    function void fixed_method();    // non-virtual = NOT overridable
        $display("always base");
    endfunction
endclass

class derived_txn extends base_txn;
    virtual function void print();   // Override
        $display("derived");
    endfunction
    // fixed_method() cannot be overridden; base's version always runs
endclass
```

Rule: if you think a method might ever need per-type behavior, declare it `virtual` in the base class. Forgetting `virtual` is a common bug — the wrong version runs silently.

## Abstract classes — the pure virtual pattern

Sometimes a base class exists only to define an interface, not an implementation:

```systemverilog
virtual class base_checker;   // "virtual class" = abstract — cannot be instantiated
    pure virtual function bit check(base_txn expected, base_txn actual);
    // No implementation — derived classes MUST provide one
endclass

class uart_checker extends base_checker;
    virtual function bit check(base_txn expected, base_txn actual);
        uart_txn exp_u, act_u;
        $cast(exp_u, expected);
        $cast(act_u, actual);
        return (exp_u.data == act_u.data && exp_u.parity == act_u.parity);
    endfunction
endclass
```

This pattern lets a scoreboard hold a `base_checker` handle and call `check()` without knowing the specific protocol. The factory swaps in `uart_checker` at runtime. UVM's entire component tree uses this pattern.
