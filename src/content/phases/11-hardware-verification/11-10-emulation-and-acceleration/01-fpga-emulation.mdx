## Why this matters

A modern smartphone SoC contains between 10 and 20 billion transistors. Running a software boot sequence through RTL simulation — the tool you have used throughout this phase — executes roughly 1,000 to 10,000 clock cycles per second on a workstation at SoC scale. Booting a Linux kernel requires somewhere between 100 million and 1 billion clock cycles depending on the design. At those speeds, one boot attempt takes between several hours and nearly two weeks of wall-clock time — and software bring-up requires hundreds of boot iterations as drivers and RTL change. No verification schedule survives that arithmetic.

This is not a failure of simulation. RTL simulation is the right tool for unit-level verification, CDC analysis, UVM testbench development, and assertion-based formal proofs — everything you have practiced in this phase. It is the wrong tool at the scale where you need software running on the hardware to find the bugs that only appear when an operating system drives real driver code through real device models. <VocabTooltip slug="fpga-emulation">FPGA emulation</VocabTooltip> exists to close that gap. Understanding where the gap is, and what you trade away to close it, is what makes you able to choose the right tool for a verification problem rather than defaulting to the one you already know.

## A scale problem that simulation cannot solve

Imagine you have been asked to translate a 600-page Russian novel into English. One approach: translate word by word, look up every word in the dictionary, write each translated word one at a time. This is RTL simulation — it models every gate transition, every flip-flop edge, every wire in the design. For a chapter, this is fine. For the full novel, it takes years.

Now imagine you can hire a team of professional translators who work in parallel — some handle chapter 1, others chapter 2, others chapter 3. They all use the same dictionary (the same RTL), but they run in parallel and at human reading speed rather than word-by-word. This is <VocabTooltip slug="fpga-emulation">FPGA-based emulation</VocabTooltip>: the RTL design is compiled onto real reconfigurable hardware (FPGAs), where actual transistors implement the logic. The design runs at hardware speeds — not at software simulation speeds.

> **FPGA emulation is not simulation of the design. It IS the design, running on reconfigurable silicon.**

The throughput difference is not incremental. A high-end simulator running on a 64-core workstation might achieve 100 kHz of effective clock frequency for a 100 million gate design. The same design running on a commercial emulation platform (Cadence Palladium, Synopsys ZeBu, Mentor Veloce) runs at 1–10 MHz — a factor of 10 to 100 in raw throughput — and that gap widens as the design grows, because simulation performance degrades with design size while emulation degrades much more slowly.

## What an emulation compiler does

You cannot take RTL written for an ASIC and load it directly onto an FPGA. An <VocabTooltip slug="emulation-compiler">emulation compiler</VocabTooltip> is the tool that bridges that gap. It performs a multi-stage transformation that is distinct from both synthesis-for-ASIC and FPGA synthesis-for-production.

```text
RTL Design (SystemVerilog, VHDL, or mixed)
         │
         ▼
┌─────────────────────────────────────────────────────┐
│ EMULATION COMPILER PIPELINE                         │
│                                                     │
│  1. Elaboration + Elaboration Checks                │
│     — resolves parameters, generates, instances     │
│     — flags constructs not synthesizable to FPGA    │
│                                                     │
│  2. Partitioning                                    │
│     — design is too large for one FPGA              │
│     — compiler cuts design across multiple FPGAs    │
│     — minimizes inter-FPGA signal bandwidth         │
│                                                     │
│  3. Clock Model Transformation                      │
│     — ASIC has hundreds of clocks with exact phases │
│     — FPGAs have limited PLL outputs               │
│     — compiler implements multi-clock designs       │
│       using time-multiplexing or virtual clocks     │
│                                                     │
│  4. Instrumentation for Debug                       │
│     — inserts trace capture logic (ICE probes)      │
│     — adds scan chains for state readback           │
│     — compresses visibility to fit FPGA resources   │
│                                                     │
│  5. FPGA Synthesis + Place and Route                │
│     — targets emulator-specific FPGA fabric         │
│     — optimizes for clock rate, not for area/power  │
└─────────────────────────────────────────────────────┘
         │
         ▼
Bitfile(s) loaded onto emulation hardware
```

The <VocabTooltip slug="partition">partition</VocabTooltip> step is one of the hardest. A large SoC might require 8 to 64 FPGAs to implement, connected by a high-speed interconnect backplane. Every signal that crosses an FPGA boundary adds one clock cycle of latency (the signal must be serialized, transmitted across the backplane, and deserialized). Timing-critical paths that cross FPGA boundaries run slower than they would in the ASIC. The compiler minimizes cuts across timing-critical paths, but it cannot eliminate this effect entirely.

## Standalone emulation versus in-circuit emulation

FPGA emulation operates in two distinct modes that serve different verification goals.

### Standalone emulation

The RTL design runs on the emulation hardware, and its testbench also runs on the emulation hardware or on a closely connected host processor. No physical external hardware is connected. This mode looks like simulation from the verification engineer's perspective — you write testbench code, exercise the DUT, collect coverage — but it runs orders of magnitude faster.

Standalone emulation is the mode used for:

- Software bring-up: booting an operating system and running device drivers against the hardware model
- Long-duration regression runs that would take weeks in simulation
- Power estimation: running real workloads to collect switching activity for power analysis

```text
Host Workstation
 ┌─────────────────────────────────────┐
 │ Testbench / Software Stack          │
 │  (runs on host CPU or co-process)   │
 └──────────────────┬──────────────────┘
                    │ SCE-MI or DPI transactor
                    ▼
 ┌─────────────────────────────────────┐
 │ Emulation Hardware                  │
 │  ┌──────────┐  ┌──────────┐         │
 │  │  FPGA 0  │  │  FPGA 1  │  ...    │
 │  │  (RTL)   │  │  (RTL)   │         │
 │  └──────────┘  └──────────┘         │
 └─────────────────────────────────────┘
```

The interface between the host software and the emulated hardware uses a protocol called SCE-MI (Standard Co-Emulation Modeling Interface) or its successor DPI-based transactor models. This protocol governs how test stimulus from the host gets clocked into the emulation hardware and how results come back. The protocol is a verified standard; the transactor models are where verification engineers write the hardware-side of the testbench.

### In-circuit emulation (ICE)

<VocabTooltip slug="in-circuit-emulation">In-circuit emulation</VocabTooltip> connects the emulation
hardware directly to physical target hardware — the PCB that the ASIC will eventually populate. The
emulation box replaces the ASIC socket. Real I/O signals from the physical board drive the emulated
design; the emulated design drives real I/O back to the physical board.

```text
Physical Target Board (PCB)
 ┌───────────────────────────────────┐
 │  Power Rails, Connectors,         │
 │  External Memory (DDR4 DIMM),     │
 │  Network PHY, USB Controller      │
 │              │                    │
 │              │  real I/O signals  │
 └──────────────┼────────────────────┘
                │
          FPGA I/O Pins
                │
 ┌──────────────▼────────────────────┐
 │  Emulation Hardware               │
 │  (ASIC RTL running on FPGAs)      │
 └───────────────────────────────────┘
```

ICE enables the verification team to run real software on real peripheral hardware before the ASIC exists. A firmware team can start porting bootloaders and BIOS while RTL is still changing. A driver team can validate that a USB controller's register map matches what the kernel driver expects. These bugs — mismatches between hardware spec and software assumption — are among the most expensive if they reach silicon, and ICE is often the only way to find them at scale before tape-out.

The constraint in ICE mode is clock frequency. Physical I/O signals transition at the board's operating frequency — DDR4 at 3200 MT/s, PCIe at 8 GT/s — but the emulation hardware runs at 1–5 MHz. The emulation platform handles this with clock domain controllers and I/O timing adapters, but not every interface protocol can be emulated at reduced frequency. Protocols with hardware-enforced timeout requirements (USB enumeration timeouts, PCIe training sequences) sometimes require special handling or protocol-level stubs.

## The debug visibility problem

When you run RTL simulation with a UVM testbench, every signal in the design is observable at every clock edge. You can probe `u_core/u_alu/result_reg` without changing anything in the design. Simulation has perfect observability by construction — the simulator models every signal mathematically and records it.

FPGA emulation does not. The signals inside an FPGA are implemented as real electrical circuits. To read a signal, you need either a physical probe on a pin or logic inside the FPGA that captures the signal value and routes it to an output. Every gate you spend on debug instrumentation is a gate you cannot spend on design logic. Every signal you want to observe needs a path to the outside world.

Commercial emulation platforms address this with instrumented trace buffers:

```text
Design Logic                     Debug Infrastructure
┌─────────────────────────┐     ┌──────────────────────────────┐
│  u_cpu/execute/result   │────▶│  Trigger Logic               │
│  u_dma/state_reg        │────▶│  (fires when condition met)  │
│  u_mac/tx_count[15:0]   │────▶│          │                   │
│  u_usb/ep0_state        │────▶│          ▼                   │
│         ...             │     │  Trace Buffer (on-chip RAM)  │
│  (up to N signals)      │     │  N signals × M cycles deep   │
└─────────────────────────┘     │          │                   │
                                │          ▼                   │
                                │  Readout over PCIe/Ethernet  │
                                │  to host workstation         │
                                └──────────────────────────────┘
```

The key constraints:

- You must declare which signals you want to observe **before** running. You cannot add a new signal to the trace buffer after a run without recompiling and re-loading the bitfile — a process that can take hours.
- The trace buffer has finite depth. A typical configuration captures 4K to 256K cycles of the selected signals. For a bug that requires millions of cycles to reproduce, trace depth determines whether you can capture it at all.
- Not all signals are available for probing. Signals inside heavily optimized or time-multiplexed logic may be inaccessible.

This is the fundamental visibility trade-off: simulation gives you infinite observability at the cost of speed; emulation gives you speed at the cost of observability.

## Choosing the right tool for each verification task

The decision is not "simulation OR emulation" — it is "which task belongs to which tool." Experienced verification teams use both, with a clear separation of responsibility.

| Verification Task                         | Right Tool                    | Why                                                   |
| ----------------------------------------- | ----------------------------- | ----------------------------------------------------- |
| Unit-level block verification             | RTL Simulation                | Full observability; fast iteration; waveform debug    |
| UVM constrained-random regression         | RTL Simulation                | Coverage-driven; small DUT size manageable            |
| CDC analysis                              | Static CDC tool               | Tool-specific, no simulation needed                   |
| Formal property proofs                    | Formal verification           | Exhaustive; not achievable in simulation or emulation |
| Software bring-up / OS boot               | Emulation (standalone)        | Orders-of-magnitude faster than simulation            |
| Firmware/driver integration               | Emulation (standalone or ICE) | Real software stack; interface fidelity               |
| Board-level hardware/software integration | ICE                           | Real peripheral hardware; real I/O protocols          |
| Long-duration power analysis              | Emulation (standalone)        | Needs real workloads; simulation too slow             |
| Final physical timing sign-off            | Post-layout simulation        | Gate-level with extracted parasitics                  |

One mistake verification teams make is using emulation for tasks that belong to simulation. Emulation is expensive — commercial emulation platforms cost millions of dollars to purchase and require experts to operate. Running a 10,000-cycle UVM unit test on an emulator wastes a resource that another team needs for a week-long OS boot. Emulation is the right tool when scale demands it; simulation is the right tool when scale permits it.

## What you learned

- RTL simulation achieves roughly 1–10 kHz of effective clock throughput for SoC-scale designs; FPGA emulation achieves 1–10 MHz — a gap of two to four orders of magnitude that makes OS boot and software bring-up practically infeasible in simulation.
- An emulation compiler transforms RTL through elaboration, partitioning across multiple FPGAs, clock model transformation, debug instrumentation, and FPGA-specific synthesis — a pipeline distinct from both ASIC synthesis and production FPGA synthesis.
- Standalone emulation connects a host-side testbench or software stack to emulated RTL for tasks like OS boot and power analysis; in-circuit emulation connects real physical I/O hardware to the emulated design for hardware/software integration, at the cost of clock frequency mismatch with protocols that have wall-clock timing requirements.
- FPGA emulation provides radically reduced debug observability compared to simulation: signals must be pre-selected before a run, trace buffers have finite depth, and adding new probes requires recompiling the bitfile; the response is precise trigger conditions and iterative binary-search of the problem space.
- Verification task placement — simulation for unit-level and coverage-driven regression, formal for exhaustive proofs, emulation for scale and software integration — is an explicit engineering decision, not a default; using the wrong tool wastes expensive resources.
