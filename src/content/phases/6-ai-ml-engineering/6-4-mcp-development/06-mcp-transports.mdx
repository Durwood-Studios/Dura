## Why this matters

The MCP protocol defines what messages look like. The transport defines how they travel. Pick the wrong one and you fight deployment constraints — running stdio in the cloud, or standing up a long-lived SSE stream when you needed a stateless HTTP endpoint. Worse, you might pick a transport the spec deprecated and ship code that future clients refuse to talk to.

The current MCP spec (`2025-11-25`) defines exactly two transports the spec author tells you to use: **stdio** for local subprocesses, and **Streamable HTTP** for everything remote. The older HTTP+SSE transport from 2024 is **deprecated** — covered here only so you can recognize it in older tutorials and migrate off it.

## stdio: local process communication

The **stdio** transport runs the MCP server as a child process. The client writes newline-delimited JSON-RPC messages to the server's stdin and reads responses from its stdout. `stderr` is free — use it for logs without polluting the protocol stream.

This is what Claude Desktop, Claude Code, and most editor integrations use for local servers. The server inherits the user's filesystem permissions; there is no network exposure.

```javascript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";

const server = new McpServer({
  name: "local-tools",
  version: "1.0.0",
});

server.tool("hello", "Say hello", {}, async () => ({
  content: [{ type: "text", text: "Hello from stdio!" }],
}));

// Newline-delimited JSON-RPC on stdin/stdout. stderr is yours for logging.
const transport = new StdioServerTransport();
await server.connect(transport);
```

The client configuration tells the host how to spawn the process:

```json
{
  "mcpServers": {
    "local-tools": {
      "command": "node",
      "args": ["./local-tools-server.js"],
      "env": { "API_KEY": "sk-abc123" }
    }
  }
}
```

**Use stdio when:** local development, CLI workflows, personal automation, anything where the server runs on the same machine as the client. The spec says clients SHOULD prefer stdio when possible — it's the lowest-overhead, lowest-attack-surface option.

**Limitations:** local only. The client must be able to spawn the process. Credentials come from environment variables — there is no OAuth flow for stdio servers (the auth spec explicitly excludes them).

## Streamable HTTP: the canonical remote transport

The **Streamable HTTP** transport replaced HTTP+SSE starting with spec version `2025-03-26` and is the only remote transport the current spec endorses. Single endpoint, supports both POST and GET, scales horizontally, and includes resumability for unreliable networks.

### The single endpoint

The server exposes one MCP path (e.g., `/mcp`) that accepts both POST and GET:

- **POST** — every client → server message. Body is a single JSON-RPC request, response, or notification (batching was removed in `2025-11-25`).
- **GET** — opens a server → client SSE stream for unsolicited messages (notifications, progress updates, sampling requests).

Every client `Accept` header MUST include both `application/json` and `text/event-stream`. The server picks the response format: a single JSON body for synchronous results, or an SSE stream upgrade for streamed responses and long-running operations.

```javascript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StreamableHTTPServerTransport } from "@modelcontextprotocol/sdk/server/streamableHttp.js";
import express from "express";

const app = express();
const server = new McpServer({ name: "remote-tools", version: "1.0.0" });

server.tool(
  "search",
  "Search documents",
  { query: { type: "string", description: "Search query" } },
  async ({ query }) => ({
    content: [{ type: "text", text: `Results for: ${query}` }],
  })
);

const transport = new StreamableHTTPServerTransport({
  // Cryptographically secure session IDs; assigned at initialize.
  sessionIdGenerator: () => crypto.randomUUID(),
});

await server.connect(transport);

app.post("/mcp", (req, res) => transport.handleRequest(req, res));
app.get("/mcp", (req, res) => transport.handleRequest(req, res));
app.delete("/mcp", (req, res) => transport.handleRequest(req, res));

app.listen(3001);
```

### Sessions

The spec defines an optional session model via the `MCP-Session-Id` HTTP header. On `initialize`, the server can return a `MCP-Session-Id` (cryptographically secure, opaque to the client). The client then echoes that header on every subsequent request.

- **No session** — pure stateless deployment, every request is independent. Good for serverless.
- **Sessioned** — the server can keep per-connection state (subscriptions, in-flight operations). Sessions survive across HTTP requests so long as the client sends the header.

The server can 404 a stale session ID to force re-initialization. The client can `DELETE` the endpoint to terminate a session cleanly.

### Resumability

Server-sent events on the GET stream carry SSE `id:` fields. If the client's connection drops mid-stream, it reconnects with HTTP header `Last-Event-ID: <last-id-received>` and the server replays from that cursor. This is per-stream and the SDK handles it for you — the lesson here is that you must use stable, monotonic IDs if you're implementing the transport yourself.

### The protocol-version header

Every HTTP request after `initialize` MUST carry the negotiated protocol version:

```http
POST /mcp HTTP/1.1
Host: tools.example.com
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2025-11-25
MCP-Session-Id: 1f8b...
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"method":"tools/call", ...}
```

Missing header → server assumes `2025-03-26` (the first Streamable HTTP version) for backwards compatibility. Invalid value → server returns `400 Bad Request`. This per-request version stamp catches version drift even when a session is long-lived.

**Use Streamable HTTP when:** the server runs anywhere a client cannot spawn it. Production deployments, multi-tenant SaaS, serverless functions, team-shared internal tools, web clients, mobile clients. The spec's only remote transport.

## DNS rebinding and Origin validation

A Streamable HTTP server is a real HTTP server, and that brings real HTTP threats. The spec requires two specific defenses:

```javascript
// Required: validate Origin on every request
app.use("/mcp", (req, res, next) => {
  const origin = req.get("Origin");
  const allowed = ["https://app.example.com", "https://claude.ai"];
  if (origin && !allowed.includes(origin)) {
    return res.status(403).send("Forbidden origin");
  }
  next();
});

// Required for local servers: bind to loopback only, not 0.0.0.0
app.listen(3001, "127.0.0.1");
```

Skipping these is how DNS-rebinding attacks turn a local MCP server into a remote exploit pivot. The spec doesn't ask politely — it says servers **MUST** validate `Origin` and local servers **SHOULD** bind to `127.0.0.1`.

## What about HTTP+SSE? (deprecated)

You'll see older tutorials use a **two-endpoint HTTP+SSE** pattern: a `/sse` GET endpoint for the persistent stream, and a separate `/messages` POST endpoint for client requests. That was the original 2024-11-05 remote transport. It was **deprecated in spec `2025-03-26`** in favor of the single-endpoint Streamable HTTP.

If you inherit a server using it, the migration is mostly mechanical:

1. Collapse `/sse` and `/messages` into one `/mcp` endpoint.
2. Have that endpoint handle both `GET` (was your SSE stream) and `POST` (was your `/messages` handler).
3. Replace the `SSEServerTransport` import with `StreamableHTTPServerTransport`.
4. Add `MCP-Session-Id` and `MCP-Protocol-Version` header handling.
5. Update your client config — drop separate stream/message URLs, point to one endpoint.

New clients increasingly refuse to negotiate with HTTP+SSE servers. Migrate.

## Custom transports

The spec explicitly allows custom transports — WebSocket, named pipes, Unix domain sockets, whatever fits your environment — as long as they satisfy two contracts:

1. Carry JSON-RPC messages bidirectionally with the right framing.
2. Preserve the lifecycle (`initialize` handshake, capability negotiation, version exchange, shutdown).

Use this escape hatch sparingly. Every custom transport is one more thing every client has to support before they can talk to you.

## Choosing the right transport

The decision matrix is now much shorter than it used to be:

| Factor                    | stdio                 | Streamable HTTP                     |
| ------------------------- | --------------------- | ----------------------------------- |
| Network required          | No                    | Yes                                 |
| Server runs               | Same machine as user  | Anywhere                            |
| Server-initiated messages | Via stdout (always)   | Via GET SSE stream (when open)      |
| Sessions                  | Implicit (subprocess) | Optional `MCP-Session-Id` header    |
| Resumability              | Not needed            | Built in via `Last-Event-ID`        |
| Horizontal scaling        | N/A                   | Easy (stateless) / Hard (sessioned) |
| Auth model                | Env variables         | OAuth 2.1 (covered in 07)           |
| Spec version-stamp        | Implicit              | `MCP-Protocol-Version` header       |

If the server runs locally, use **stdio**. If it runs anywhere else, use **Streamable HTTP**. Reach for custom only when neither fits.

## What you learned

- The current MCP spec endorses exactly two transports: **stdio** for local servers, **Streamable HTTP** for everything remote.
- HTTP+SSE (the original 2024 two-endpoint transport) is **deprecated**. Migrate to Streamable HTTP — collapse `/sse` and `/messages` into one `/mcp` endpoint and add the spec headers.
- Streamable HTTP uses **one endpoint** for both POST (client → server) and GET (server → client SSE stream), with optional sessions (`MCP-Session-Id`), built-in resumability (`Last-Event-ID`), and a per-request `MCP-Protocol-Version` header.
- HTTP-based servers MUST validate `Origin` and local servers SHOULD bind to `127.0.0.1` — these are spec requirements, not suggestions, because DNS-rebinding attacks are a real threat to MCP deployments.
