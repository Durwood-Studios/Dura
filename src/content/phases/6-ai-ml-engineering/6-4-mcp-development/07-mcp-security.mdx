## Why this matters

An MCP server is an API that an AI model calls autonomously. The model decides when to invoke tools and what arguments to pass, sometimes based on untrusted user input. If your server blindly executes what it receives, you have built an injection vector with a natural-language interface.

This is not theoretical. The MCP ecosystem has been shipping for ~18 months as of mid-2026, and the advisory trail through that window is real:

- **CVE-2025-6514** (CVSS 9.6): RCE in `mcp-remote` v0.0.5–0.1.15 when connecting to a malicious server.
- **CVE-2025-68143/-68144/-68145**: chained vulns in Anthropic's `mcp-server-git` enabling RCE via a crafted `.git/config`.
- **CVE-2025-65719**: RCE in a Kubectl MCP server via a malicious-website attack vector.
- SSRF in Microsoft's MarkItDown MCP server exposing AWS instance metadata.
- A "tool redefinition" attack class where a malicious server in a multi-server host overrides legitimate tools to redirect calls.
- Design-level vulnerability disclosures in 2026 showing the same class of failures keep recurring — the spec's MUST/SHOULD language exists for a reason.

The spec writes its security requirements as `MUST` and `SHOULD` because the actual MCP ecosystem has paid the tuition. Every section below maps to a control the spec requires or a failure pattern that bit a real shipped server.

## Input validation

The `inputSchema` (and `outputSchema`, since `2025-11-25`) in your tool definition provides structural validation — the SDK rejects requests that do not match the JSON Schema. Structural validation is necessary but never sufficient. You must validate the **semantics** of inputs in your handler.

```javascript
server.tool(
  "query_database",
  "Execute a read-only SQL query",
  { sql: { type: "string", description: "A SELECT query" } },
  async ({ sql }) => {
    // Structural validation already happened (SDK ensures sql is a string).
    // Semantic validation: you ensure it is safe.
    const normalized = sql.trim().toUpperCase();

    const forbidden = ["INSERT", "UPDATE", "DELETE", "DROP", "ALTER", "CREATE", "TRUNCATE"];
    for (const keyword of forbidden) {
      if (normalized.includes(keyword)) {
        return {
          content: [{ type: "text", text: `Blocked: ${keyword} statements are not allowed.` }],
          isError: true,
        };
      }
    }

    if (sql.includes(";")) {
      return {
        content: [{ type: "text", text: "Blocked: multiple statements not allowed." }],
        isError: true,
      };
    }

    try {
      const rows = await db.all(sql);
      return { content: [{ type: "text", text: JSON.stringify(rows, null, 2) }] };
    } catch (error) {
      return {
        content: [{ type: "text", text: `Query failed: ${error.message}` }],
        isError: true,
      };
    }
  }
);
```

For filesystem tools, validate paths against directory traversal. For URL-based tools, validate against an allowlist. Never trust that the model will only send reasonable inputs — it might be following a prompt injection embedded in conversation context.

```javascript
import path from "node:path";

// Path validation: resolved path must stay under the allowed root.
function isPathSafe(requestedPath, allowedRoot) {
  const resolved = path.resolve(allowedRoot, requestedPath);
  return resolved.startsWith(path.resolve(allowedRoot));
}

// URL validation against an allowlist (this is how MarkItDown should have shipped).
function isUrlAllowed(url, allowedDomains) {
  try {
    const parsed = new URL(url);
    if (!["http:", "https:"].includes(parsed.protocol)) return false;
    // Block cloud-metadata addresses outright.
    if (
      parsed.hostname === "169.254.169.254" ||
      parsed.hostname === "metadata.google.internal" ||
      parsed.hostname.startsWith("10.") ||
      parsed.hostname.startsWith("127.")
    ) {
      return false;
    }
    return allowedDomains.includes(parsed.hostname);
  } catch {
    return false;
  }
}
```

That second function is exactly the kind of allowlist the MarkItDown SSRF would have needed. A URL-fetching tool with no validation is one prompt injection away from leaking your cloud credentials.

## The consent contract

The `2025-11-25` spec defines a consent model that runs through every primitive. The client is expected to put the user in the loop at specific decision points:

- **Tool invocations** — the user MUST consent. Clients should not silently auto-approve tools in production unless the user has explicitly opted in to that tool.
- **Sampling requests** — when your server calls back to the client's LLM via `sampling/createMessage`, the user MUST approve. Clients SHOULD let users view and edit the prompt before it goes to the model, and review the response before it comes back to your server.
- **Elicitation forms** — the spec explicitly **forbids** form-mode elicitation for passwords, API keys, or tokens. If your server needs a secret, use URL-mode elicitation (out-of-band browser flow) — never ask for a credential in the form schema.
- **Roots disclosure** — the client MUST get user consent before exposing filesystem paths to your server.

Your server cannot enforce these contracts on the client. But your server SHOULD design as if they exist — never assume a tool call has been silently auto-approved, never request credentials in a form elicitation, never ask a user to paste secrets into the conversation.

```javascript
// Wrong: asking for an API key via form-mode elicitation.
// The spec forbids this — the host SHOULD refuse.
await server.requestElicitation({
  message: "Enter your GitHub token",
  requestedSchema: {
    type: "object",
    properties: { token: { type: "string" } },
    required: ["token"],
  },
});

// Right: URL-mode elicitation that sends the user through OAuth.
await server.requestElicitation({
  mode: "url",
  url: "https://app.example.com/connect-github?session=" + sessionId,
  message: "Connect your GitHub account",
});
```

## Roots: the filesystem permission contract

The **Roots** primitive lets a client tell a server which filesystem paths it's allowed to see. The spec is narrow on purpose:

- Root URIs **MUST** use the `file://` scheme. No `https://`, no `git://`, no custom schemes.
- The client is the source of truth — servers cannot push roots, only request them via `roots/list`.
- The user MUST consent before any path is exposed.
- Servers MUST validate every path operation against the granted roots and MUST reject anything outside the boundary, including path traversal attempts (`../`, symlinks pointing outside the root, etc.).

A server that accepts a tool argument like `{ "path": "/etc/passwd" }` and reads it without checking against the current roots is the design pattern behind multiple 2025 file-server CVEs. The Roots primitive exists so you can write the check once and apply it everywhere.

```javascript
async function withinAnyRoot(absolutePath) {
  const { roots } = await client.listRoots(); // cached, refreshed on notification
  return roots.some((r) => {
    const rootPath = new URL(r.uri).pathname;
    return path.resolve(absolutePath).startsWith(path.resolve(rootPath));
  });
}

server.tool(
  "read_file",
  "Read a file from the workspace",
  { path: { type: "string" } },
  async ({ path: requestedPath }) => {
    const resolved = path.resolve(requestedPath);
    if (!(await withinAnyRoot(resolved))) {
      return {
        content: [{ type: "text", text: "Refused: path is outside any granted root." }],
        isError: true,
      };
    }
    return { content: [{ type: "text", text: await fs.readFile(resolved, "utf8") }] };
  }
);
```

## Authentication

For remote MCP servers running over Streamable HTTP, the spec endorses **OAuth 2.1 with PKCE-S256** as the canonical auth model. It's an entire contract — Protected Resource Metadata (RFC 9728), Resource Indicators (RFC 8707), Client ID Metadata Documents — and it gets its own lesson. For the security overview, three rules from that lesson matter here:

1. **PKCE with S256 is MUST.** Anything weaker (plain code verifier, no PKCE) is non-conformant — clients are required to refuse.
2. **Token passthrough is FORBIDDEN.** An MCP server **MUST NOT** forward the client's token to upstream APIs it calls on the client's behalf. The server must obtain its own credentials. Token passthrough collapses every audience boundary — one stolen token now hits multiple services.
3. **Stdio servers MUST NOT use the OAuth spec.** They read credentials from environment variables — the parent client is the authorization boundary, not OAuth.

For development against an HTTP server that hasn't wired up OAuth yet, a static bearer token check is fine — just understand it's a dev shortcut, not a production posture.

```javascript
import express from "express";

const app = express();

// DEV ONLY — production servers use OAuth 2.1 with PKCE (see lesson 09).
function authenticateDev(req, res, next) {
  const authHeader = req.headers.authorization;
  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    res.set("WWW-Authenticate", 'Bearer realm="mcp"');
    return res.status(401).json({ error: "Missing bearer token" });
  }
  const token = authHeader.slice(7);
  if (!isValidDevToken(token)) {
    return res.status(403).json({ error: "Invalid token" });
  }
  req.userId = getUserIdFromToken(token);
  next();
}

app.post("/mcp", authenticateDev, async (req, res) => {
  await handleMcpRequest(req, res);
});
```

For stdio servers, authentication is implicit — the server runs as a child process of the user's own shell with their filesystem permissions. But you still must validate inputs, because the model may forward content from anywhere in the conversation.

## Rate limiting

The spec says servers **MUST rate-limit tool invocations** as a security best practice, but it doesn't tell you how — that's implementation-defined. The reason this is a security control (not just a cost control) is that a model in a loop, or a malicious prompt that tricks the model into a fork bomb of tool calls, can saturate downstream APIs and exhaust quota in seconds.

```javascript
class RateLimiter {
  constructor(maxRequests, windowMs) {
    this.maxRequests = maxRequests;
    this.windowMs = windowMs;
    this.requests = new Map();
  }

  isAllowed(key) {
    const now = Date.now();
    const windowStart = now - this.windowMs;
    const timestamps = (this.requests.get(key) || []).filter((t) => t > windowStart);

    if (timestamps.length >= this.maxRequests) return false;

    timestamps.push(now);
    this.requests.set(key, timestamps);
    return true;
  }
}

const limiter = new RateLimiter(30, 60_000); // 30 calls per minute per key

server.tool(
  "search_api",
  "Search external API",
  { query: { type: "string" } },
  async ({ query }, { sessionId }) => {
    // Key the limit per session so one client can't starve others.
    if (!limiter.isAllowed(`search_api:${sessionId}`)) {
      return {
        content: [{ type: "text", text: "Rate limit exceeded. Try again in a moment." }],
        isError: true,
      };
    }
    return { content: [{ type: "text", text: JSON.stringify(await externalApi.search(query)) }] };
  }
);
```

In production, key the limit on the authenticated user identity (or session ID for unauthenticated dev). Logging-only rate limits (alert, but don't block) are a useful first step on a new server — see what real usage looks like before you ship a hard cap.

## Audit logging

The spec defines a Logging utility (`logging/setLevel`, `notifications/message`) using RFC 5424 syslog levels (`debug` through `emergency`). That's the standardized channel for **server-emitted** logs the client can subscribe to. For server-side **audit** logging — what tool was called, by whom, with what arguments, with what result — you write your own structured log to stdout (or your log pipeline) so a forensic investigation has a trail.

```javascript
function auditLog(toolName, args, result, metadata) {
  const entry = {
    timestamp: new Date().toISOString(),
    tool: toolName,
    arguments: redactSecrets(args),
    success: !result.isError,
    userId: metadata.userId || "anonymous",
    sessionId: metadata.sessionId,
    durationMs: metadata.durationMs,
    // For OAuth-protected servers, also log token jti/aud for revocation traceability.
    tokenJti: metadata.tokenJti,
  };
  console.log(JSON.stringify(entry));
}

function withAuditLog(toolName, handler) {
  return async (args, metadata) => {
    const start = Date.now();
    try {
      const result = await handler(args, metadata);
      auditLog(toolName, args, result, { ...metadata, durationMs: Date.now() - start });
      return result;
    } catch (error) {
      auditLog(
        toolName,
        args,
        { isError: true },
        { ...metadata, durationMs: Date.now() - start, error: error.message }
      );
      throw error;
    }
  };
}
```

`redactSecrets` is non-optional — never log raw tokens, raw passwords, or raw PII. If you can't think of a value that needs to be redacted in your tool's arguments, look harder.

## The principle of least privilege

Give each MCP server the minimum permissions it needs. A server that reads files should not have write access. A server that queries a database should use a read-only role. A server that calls one API should not have credentials for others.

```javascript
// Bad: one server with god-mode access.
const godServer = {
  tools: ["read_file", "write_file", "delete_file", "query_db", "modify_db", "send_email"],
  dbUser: "admin",
  fileAccess: "/",
};

// Good: separate servers with minimal permissions.
const fileReader = {
  tools: ["read_file", "list_files"],
  fileAccess: "/project/docs", // scoped to one directory
  readOnly: true,
};

const dbQuery = {
  tools: ["query_database"],
  dbUser: "readonly_user", // read-only DB role
  allowedTables: ["users", "logs"], // scoped to specific tables
};
```

Separate concerns into separate servers. If a file-reading server is compromised, it cannot touch the database. If the database server has a bug, it cannot delete files. Defense in depth starts at architecture — and in a multi-server host, the spec's lack of cross-server isolation means architecture is the only defense you get.

## What the advisory trail taught us

The CVEs at the top of this lesson all map to specific failures. The MCP ecosystem is now far enough into production that the failure patterns repeat — save yourself the embarrassment:

- **`mcp-remote` RCE (CVE-2025-6514)** — a client trusted untyped server output and passed it to a shell. Always treat tool results as untrusted data, never as executable instructions. The `annotations` field on tools is explicitly marked untrusted in the spec for this reason.
- **`mcp-server-git` chain (CVE-2025-68143/-68144/-68145)** — a server read a config file under user control and used values from it without sanitization. Any user-controllable input is an attacker-controlled input — `.git/config`, environment variables, file headers, all of it.
- **MarkItDown SSRF** — a URL-fetching tool with no allowlist hit cloud metadata at `169.254.169.254` and leaked AWS instance credentials. Allowlist the URLs your tools can fetch, block private IP ranges, block cloud-metadata hostnames.
- **Tool redefinition** — a malicious server in a multi-server host registered a tool with the same name as a legitimate one and silently intercepted calls. Clients are responsible for namespacing across servers; servers are responsible for not assuming uniqueness.

The pattern is the same in every entry: someone treated untrusted input as trusted, or skipped a check the spec said was MUST. Every control in this lesson exists because something downstream of a missing check made headlines.

## What you learned

- **Input validation must go beyond JSON Schema** — validate semantics (safe SQL, allowed paths, allowlisted URLs, blocked cloud-metadata IPs) because models may forward untrusted content from prompt injections.
- The spec defines a **consent contract**: tool invocations require user approval, sampling requires user approval, form-mode elicitation MUST NOT collect credentials (use URL mode), and Roots disclosure requires user consent.
- **Roots use `file://` only** and bound every filesystem operation. Validate against them; reject path traversal.
- **Token passthrough is FORBIDDEN** — servers must obtain their own credentials for upstream APIs.
- **Rate limiting** and **audit logging** are MUST controls — rate limit per session/user; redact secrets in logs.
- **Least privilege** is the architecture-level defense: one capability per server, scoped credentials, no cross-server trust.
- The advisory trail from 2025 through 2026 is what the spec language is _for_. Every MUST has a story behind it.
