## Why this matters

Tools are the most common reason to build an MCP server. They let AI models take actions — query a database, create a file, call an API, run a calculation. When a model sees a well-described tool, it can decide when and how to use it based on the user's request. The quality of your tool definitions directly determines how reliably the model will use them.

## Anatomy of a tool definition

Every MCP tool has three required parts: a **name**, a **description**, and an **inputSchema**. The name is a unique identifier. The description tells the model what the tool does and when to use it. The inputSchema is a JSON Schema object that defines the expected arguments.

The `2025-11-25` spec adds several optional fields that polish how the tool surfaces in clients: `title` (human-friendly UI label), `icons[]` (visual icon refs), `outputSchema` (JSON Schema for the structured result), `annotations` (server hints about behavior — covered later), `execution.taskSupport` (whether the tool can run as a Task), and `_meta` (server-defined extras). Required pieces below, optional fields layered in as we go.

```javascript
// A tool definition for getting weather data
const weatherTool = {
  name: "get_weather",
  description:
    "Get the current weather for a given city. Use this when the user asks about weather conditions, temperature, or forecasts for a specific location.",
  inputSchema: {
    type: "object",
    properties: {
      city: {
        type: "string",
        description: "The city name, e.g. 'Portland' or 'San Francisco'",
      },
      units: {
        type: "string",
        enum: ["fahrenheit", "celsius"],
        description: "Temperature units. Defaults to fahrenheit.",
      },
    },
    required: ["city"],
  },
};
```

The description is the most important part. The model reads it to decide whether to call the tool. Be specific about when the tool should be used and what it returns. Vague descriptions lead to unreliable tool use.

## Implementing tool handlers

When the MCP SDK receives a `tools/call` request, it routes it to your handler function. The handler receives the tool name and arguments, does the work, and returns a result.

```javascript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";

const server = new McpServer({
  name: "weather-server",
  version: "1.0.0",
});

// Register a tool with its handler
server.tool(
  "get_weather",
  "Get current weather for a city",
  {
    city: { type: "string", description: "City name" },
    units: { type: "string", enum: ["fahrenheit", "celsius"] },
  },
  async ({ city, units = "fahrenheit" }) => {
    const response = await fetch(
      `https://api.weather.example/current?city=${encodeURIComponent(city)}&units=${units}`
    );
    const data = await response.json();

    return {
      content: [
        {
          type: "text",
          text: `${city}: ${data.temperature}°${units === "celsius" ? "C" : "F"}, ${data.condition}`,
        },
      ],
    };
  }
);
```

The return value must follow MCP's content format — an array of content blocks. The most common type is `text`, but you can also return `image` (base64-encoded) or `resource` (embedded resource data).

## A database query tool

Here is a more practical example — a tool that queries a SQLite database:

```javascript
server.tool(
  "query_database",
  "Run a read-only SQL query against the application database. Only SELECT statements are allowed.",
  {
    sql: {
      type: "string",
      description: "A SELECT SQL query to execute",
    },
  },
  async ({ sql }) => {
    // Validate: only allow SELECT statements
    const trimmed = sql.trim().toUpperCase();
    if (!trimmed.startsWith("SELECT")) {
      return {
        content: [{ type: "text", text: "Error: Only SELECT queries are allowed." }],
        isError: true,
      };
    }

    try {
      const rows = await db.all(sql);
      return {
        content: [
          {
            type: "text",
            text: JSON.stringify(rows, null, 2),
          },
        ],
      };
    } catch (error) {
      return {
        content: [{ type: "text", text: `Query error: ${error.message}` }],
        isError: true,
      };
    }
  }
);
```

Notice the `isError: true` field. This tells the model the tool call failed, so it can inform the user or try a different approach instead of treating error text as a successful result.

## Structured output and outputSchema

Returning a wall of JSON-stringified text in a `text` content block works, but the model has to re-parse it every time. The `2025-11-25` spec added two paired fields that fix this: `outputSchema` on the tool definition, and `structuredContent` on the result.

```javascript
server.tool(
  "get_weather",
  "Get current weather for a city",
  // inputSchema
  { city: { type: "string", description: "City name" } },
  // outputSchema — declares the shape of structuredContent
  {
    type: "object",
    properties: {
      city: { type: "string" },
      temperature: { type: "number" },
      units: { type: "string", enum: ["F", "C"] },
      condition: { type: "string" },
    },
    required: ["city", "temperature", "units"],
  },
  async ({ city }) => {
    const data = await fetchWeather(city);
    return {
      // structuredContent — typed JSON the model can rely on
      structuredContent: {
        city,
        temperature: data.temperature,
        units: "F",
        condition: data.condition,
      },
      // content[] — the human-readable rendering, kept for backward compat
      content: [
        {
          type: "text",
          text: `${city}: ${data.temperature}°F, ${data.condition}`,
        },
      ],
    };
  }
);
```

When a tool declares `outputSchema`, the SDK validates `structuredContent` against it before returning. Clients that prefer typed access (modern ones do) read `structuredContent`; older clients fall back to the `content` blocks. Always include both unless you control every client that will call you.

## Tool annotations (and why the spec marks them untrusted)

Tools can carry `annotations` — server-provided hints about how the tool behaves. The spec defines a few standard ones: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, and `title`.

```javascript
server.tool(
  "delete_file",
  "Delete a file from the workspace",
  { path: { type: "string" } },
  async ({ path }) => {
    await fs.unlink(path);
    return { content: [{ type: "text", text: `Deleted ${path}` }] };
  },
  {
    annotations: {
      title: "Delete file",
      readOnlyHint: false,
      destructiveHint: true,
      idempotentHint: false,
      openWorldHint: false,
    },
  }
);
```

**Critical contract:** annotations are **untrusted unless the server is trusted**. A malicious or compromised server can lie — claim `destructiveHint: false` on a tool that wipes your drive. Clients use annotations to inform UX (badging dangerous tools, default-deny on destructive ones), but they MUST NOT use annotations as the sole authorization signal. The real authorization signal is the user's explicit consent at call time, plus whatever the server actually has permission to do.

Treat annotations as a UX courtesy the model can read alongside the description, not as a security boundary.

## Linking to the Tasks primitive

The `2025-11-25` spec introduced **Tasks** — a durable state machine for long-running operations. A tool can opt into Tasks via `execution.taskSupport`:

```javascript
server.tool(
  "run_test_suite",
  "Run the full integration test suite (typically 5–10 minutes)",
  { branch: { type: "string" } },
  async ({ branch }, { task }) => {
    // Task-aware handler: report progress to the task object if present.
    if (task) {
      await task.update({ status: "working", progress: "Cloning…" });
    }
    const results = await runSuite(branch, task);
    return {
      structuredContent: results,
      content: [{ type: "text", text: `Passed ${results.passed}/${results.total}` }],
    };
  },
  {
    execution: {
      taskSupport: "optional", // also: "required" or "forbidden"
    },
  }
);
```

`taskSupport: "required"` means the tool only works when wrapped in a Task. `"optional"` (the common case) means the client can choose to wrap. `"forbidden"` means short-running only — never wrap in a Task. The Tasks primitive itself gets its own lesson — for now, know that this is the hook that lets a tool participate in long-running flows.

## Error handling patterns

MCP distinguishes between two kinds of errors. **Protocol errors** (invalid JSON-RPC, unknown method) are returned as JSON-RPC error responses. **Tool execution errors** (bad input, API failure) are returned as normal results with `isError: true`.

```javascript
// Protocol error — the MCP SDK handles this automatically
{
  "jsonrpc": "2.0",
  "id": 5,
  "error": {
    "code": -32601,
    "message": "Method not found"
  }
}

// Tool execution error — you return this from your handler
{
  "content": [
    { "type": "text", "text": "Failed to fetch weather: API rate limit exceeded" }
  ],
  "isError": true
}
```

Always handle errors in your tool handlers. An unhandled exception will crash the server. Wrap async operations in try/catch and return meaningful error messages that help the model (and the user) understand what went wrong.

## Listing tools

When a client sends `tools/list`, the server returns all registered tools with their definitions. The model uses these definitions to understand what is available.

```javascript
// The server responds to tools/list with:
{
  "tools": [
    {
      "name": "get_weather",
      "description": "Get current weather for a city",
      "inputSchema": {
        "type": "object",
        "properties": {
          "city": { "type": "string" }
        },
        "required": ["city"]
      }
    },
    {
      "name": "query_database",
      "description": "Run a read-only SQL query",
      "inputSchema": {
        "type": "object",
        "properties": {
          "sql": { "type": "string" }
        },
        "required": ["sql"]
      }
    }
  ]
}
```

Write descriptions as if you are explaining the tool to a colleague who has never seen your codebase. That colleague is the model.

## What you learned

- MCP tools are defined with a **name**, **description**, and **inputSchema** (JSON Schema) that tells the model what arguments to provide.
- Tool handlers execute the work and return **content blocks** — text, images, or embedded resources — with an optional `isError` flag for failures.
- The `2025-11-25` spec added **`outputSchema` + `structuredContent`** — declare the shape of typed JSON output and return both `structuredContent` and `content[]` for forward/backward compatibility.
- Tool **annotations** (`destructiveHint`, `readOnlyHint`, etc.) inform UX but are **untrusted unless the server is trusted** — never use them as a sole authorization signal.
- **`execution.taskSupport`** opts a tool into the Tasks primitive for long-running operations (`required` / `optional` / `forbidden`) — covered in depth in the Tasks lesson.
- Good **descriptions** are critical — they are the model's only guide for deciding when and how to use each tool.
