## Why this matters

Most MCP servers do work: they query, fetch, compute, transform. Some kinds of work need _reasoning_ — summarize this changelog, decide whether this commit is risky, choose between two refactoring approaches. The naive answer is "the server runs its own LLM," but that's expensive, opinionated (which model? which API key?), and creates auth surface the spec is trying to avoid.

Sampling is the spec's answer: your server asks the _client's_ model to do the reasoning, with the user in the loop. The server sends a `sampling/createMessage` request, the client surfaces it to the user for approval, the user-approved prompt goes to whatever model that client is using, and the response comes back to the server. The model stays in the client. The reasoning happens with the user's knowledge. The server gets the answer.

In `2025-11-25` sampling went one step further: a sampling call can itself include tools, letting the model run a multi-turn loop entirely within the server's request. Same primitive, much more capable.

## The basic sampling call

A `sampling/createMessage` request asks the client's model to generate a completion from a set of messages. Shape mirrors what you'd send to any chat-style LLM API:

```javascript
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";

const server = new McpServer({ name: "review-tools", version: "1.0.0" });

server.tool(
  "summarize_changelog",
  "Summarize a changelog into a 3-sentence release note",
  { changelog: { type: "string" } },
  async ({ changelog }, { sample }) => {
    const result = await sample({
      messages: [
        {
          role: "user",
          content: {
            type: "text",
            text: `Summarize this changelog into exactly 3 sentences for a release note. Lead with what users will notice; end with any breaking change.\n\n${changelog}`,
          },
        },
      ],
      maxTokens: 400,
      systemPrompt: "You are a precise technical writer.",
    });

    return {
      content: [{ type: "text", text: result.content.text }],
    };
  }
);
```

The handler in the server can't directly invoke the client's model — that would defeat the consent boundary. It calls `sample()`, the SDK turns that into a `sampling/createMessage` request, and the client renders an approval UI before running the actual model call.

## Model preferences

You can't pick a specific model by name — the spec is deliberately model-agnostic. But you can express _preferences_ the client uses to pick the right model from what it has access to:

```javascript
const result = await sample({
  messages: [...],
  maxTokens: 1000,
  modelPreferences: {
    hints: [{ name: "claude-3-5-sonnet" }, { name: "gpt-4o" }],
    costPriority: 0.5,         // 0.0 = ignore cost, 1.0 = minimize cost
    speedPriority: 0.3,         // 0.0 = ignore latency, 1.0 = minimize latency
    intelligencePriority: 0.9,  // 0.0 = ignore capability, 1.0 = maximize capability
  },
});
```

`hints[]` is an ordered list of model names you'd prefer; the client uses these as guidance, not commands. The three priority fields are 0.0–1.0 weights — the client picks a model that best satisfies the weighted preference. For deeply technical reasoning, set `intelligencePriority` high; for a quick tag-line, lean on `speedPriority`.

The spec is explicit that the client makes the final choice. A server that hard-codes `claude-3-5-sonnet` and breaks when the client only has `gpt-4o` is doing it wrong — degrade gracefully and let the client decide.

## The consent contract

Sampling is the primitive most amenable to abuse. A malicious server could ask the client to run prompts that leak conversation history, exfiltrate context, or burn the user's API budget. The spec defends with hard rules:

- **User MUST approve every sampling request.** Clients render the prompt for review before sending it to the model.
- **Clients SHOULD let users edit the prompt** before it goes to the model — the user owns the final wording.
- **Clients SHOULD let users review the response** before it comes back to the server — the user can redact, decline, or modify what the server sees.
- **`includeContext: "thisServer" | "allServers"`** values are **soft-deprecated** in `2025-11-25`. Originally they let a server request the client include prior conversation content; the abuse potential proved too high. New code should leave `includeContext` unset and pass any needed context explicitly through the `messages` array — content the user can see.

```javascript
// Don't do this in new code:
await sample({
  messages: [...],
  includeContext: "allServers", // soft-deprecated — visibility into other servers' context
});

// Do this — explicit context the user can see in the approval UI:
await sample({
  messages: [
    {
      role: "user",
      content: { type: "text", text: `Given this PR diff:\n\n${diff}\n\nIs it safe to merge?` },
    },
  ],
});
```

The user MUST see what the server is asking the model to see. Hiding context behind a flag breaks that contract.

## Tool use during sampling (new in 2025-11-25)

The most consequential `2025-11-25` addition: a sampling call can include tools. When the model wants to call one, the call surfaces back through the client (with user approval, naturally), executes, and the result flows back into the same sampling loop. The server gets a final answer that may have involved several tool turns inside the model's reasoning.

```javascript
server.tool(
  "investigate_incident",
  "Investigate a production incident using all available debugging tools",
  { incidentId: { type: "string" } },
  async ({ incidentId }, { sample }) => {
    const result = await sample({
      messages: [
        {
          role: "user",
          content: {
            type: "text",
            text: `Investigate incident ${incidentId}. Use the available tools to fetch logs, metrics, and recent deploys. Produce a root-cause summary.`,
          },
        },
      ],
      maxTokens: 4000,
      // 2025-11-25: declare tools available to the model during this sampling call.
      tools: [
        {
          name: "get_logs",
          description: "Fetch the last N log lines for a service",
          inputSchema: {
            type: "object",
            properties: { service: { type: "string" }, lines: { type: "number" } },
            required: ["service"],
          },
        },
        {
          name: "get_metrics",
          description: "Fetch a metrics window",
          inputSchema: {
            type: "object",
            properties: { metric: { type: "string" }, since: { type: "string" } },
            required: ["metric"],
          },
        },
      ],
      toolChoice: "auto", // "auto" | "required" | "none"
    });

    return {
      content: [{ type: "text", text: result.content.text }],
    };
  }
);
```

`toolChoice` controls the model's behavior:

- `"auto"` — model decides whether to call tools (the common case).
- `"required"` — model MUST call at least one tool before responding (force-research patterns).
- `"none"` — disable tools for this turn even though they're declared (occasionally useful for "summarize without exploring further").

Tool-use-during-sampling is gated by a separate client capability: `sampling.tools`. A client that supports `sampling` but not `sampling.tools` will reject the request if you include the `tools[]` field. Capability-check before you rely on it.

## Capability negotiation

Sampling support is advertised by the **client** during `initialize`. Servers MUST check:

```javascript
server.onInitialize((req) => {
  const sampling = req.capabilities?.sampling;
  if (!sampling) {
    // Disable tools that depend on sampling; surface this as a limitation.
    server.disableTool("summarize_changelog");
    server.disableTool("investigate_incident");
    return;
  }
  if (!sampling.tools) {
    // Sampling works, but not with tool use — fall back to single-turn calls.
    server.disableTool("investigate_incident");
  }
});
```

Old clients may not implement sampling at all. Older-still clients might implement basic sampling but not the 2025-11-25 tools extension. Your server gracefully degrades or it ships broken in the wild.

## When NOT to use sampling

The temptation is to sample for every decision. Resist it. Sampling has real costs:

- **Latency** — each sampling round-trip adds the client's user-approval friction plus the model's inference time.
- **Cost** — the user pays for the inference. Servers calling sampling in tight loops are how API bills explode.
- **Trust surface** — every sampling call is a prompt the user has to review. Spamming approvals trains users to click through, eroding the consent contract.

Reserve sampling for genuinely ambiguous reasoning: should I take this destructive action? How should I categorize this freeform input? Summarize this long document. Deterministic decisions (string matching, numeric thresholds, schema validation) should run in your server's own code, not via the client's model.

## What you learned

- **Sampling** (`sampling/createMessage`) lets a server ask the client's model for a completion — reasoning, summarization, categorization — without bringing its own model or API key.
- **Model preferences** (`hints[]`, `costPriority`, `speedPriority`, `intelligencePriority`) guide the client's model choice, but the client makes the final pick.
- **The consent contract is hard**: user MUST approve every sampling call; clients SHOULD let users edit prompts and review responses; `includeContext: "thisServer" | "allServers"` is soft-deprecated because it hid context from the user.
- **Tool use during sampling** (new in 2025-11-25) lets the model call provided `tools[]` mid-loop. Gated by the separate `sampling.tools` capability. `toolChoice`: `auto` / `required` / `none`.
- **Capability negotiation matters** — check `capabilities.sampling` and `capabilities.sampling.tools` during `initialize` and degrade gracefully.
- **Don't sample for everything** — reserve it for genuinely ambiguous reasoning. Deterministic decisions belong in your server's own code.
