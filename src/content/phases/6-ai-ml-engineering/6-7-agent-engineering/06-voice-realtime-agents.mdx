## Why this matters

A voice assistant must manage timing as well as meaning. If it continues speaking after interruption, loses the user’s last words, or executes a stale tool request, even a correct text answer can become an unusable conversation.

## Start with something familiar

A live conversation requires listening while another person speaks and stopping promptly when interrupted.

## The mental model

> Realtime agents coordinate audio, turn detection, interruption, and tool actions under latency and privacy constraints.

## Two architectures

A pipeline converts audio to text with speech recognition, sends that text to a language model, then converts the answer to audio with speech synthesis. Separate components can be inspected and replaced independently. However, partial transcripts, serial network calls, and mismatched timing require coordination.

An end-to-end speech model accepts audio and produces audio within a model session. This can preserve more conversational cues and reduce some handoffs. It also couples your application to the provider’s session, audio formats, and interruption semantics. Neither architecture guarantees a latency target or regulatory eligibility.

The OpenAI Realtime API and Gemini Live API provide documented realtime capabilities. Check their current model lists, supported transports, session limits, prices, and availability before integration. Do not copy a model identifier from an old comparison table into a production contract.

## Measure the whole turn

Measure from the user finishing a turn to the first audible response, and separately measure response completion. Speech detection, upload, inference, tool latency, and playback buffering all contribute. A provider’s time-to-first-byte is not the same as the user hearing an answer.

For an illustrative serial pipeline, suppose end-of-turn detection takes 250 ms, final transcription 150 ms, model work 400 ms, and synthesis plus playback buffering 200 ms. The total is 1,000 ms before useful audio. These are exercise assumptions, not published provider performance. Streaming components can overlap some work, but measure the overlap instead of subtracting it twice.

Set a target for your actual context. A casual conversation and a slow external account lookup have different expectations. Acknowledge a long lookup briefly rather than filling the delay with invented results.

## Interruption is state management

When the user starts speaking again, stop or cancel stale playback and decide whether the pending model output should be discarded. The conversation record must reflect what was actually heard, not an entire response that never played. Provider-specific APIs define how to clear audio buffers or truncate a conversation item; test those semantics explicitly.

Tool execution needs a separate rule. Interrupting speech does not automatically undo a submitted booking. Keep operation IDs and distinguish prepared, submitted, and confirmed actions. If a user changes the requested time before submission, invalidate the old approval. If the action was already submitted, first determine the result.

## Privacy and access

Audio can contain names, health information, background conversations, and biometric cues. Decide whether recordings or transcripts are needed, who can access them, and when they expire. Use server-held provider credentials or an officially supported short-lived client credential flow; never embed a long-lived API key in a browser.

For regulated work, verify the specific provider contract, endpoint, data handling, and modality with the responsible reviewer. A pipeline does not automatically establish compliance, and an end-to-end model does not automatically rule it out. Treat voice recognition as input, not identity proof.

## What you learned

- Pipeline and end-to-end speech have different integration tradeoffs.
- Measure audible response timing rather than only a server metric.
- Cancellation of audio and cancellation of actions are different operations.
- Verify audio privacy and endpoint terms for the specific deployment.
