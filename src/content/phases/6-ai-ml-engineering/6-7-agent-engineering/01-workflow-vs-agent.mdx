## Why this matters

Most production AI systems labeled "agents" are not agents. They're workflows — code paths with LLM calls slotted in at predefined steps. Calling them "agents" is fashionable, but it obscures the real engineering decision: how much runtime flexibility you're willing to pay for in exchange for unpredictability.

The 2025-2026 agentic wave amplified this confusion. Teams reached for true agents (LLMs that direct their own tool use and reasoning) when a deterministic workflow would have shipped faster, cost less, and failed less surprisingly. This lesson teaches you the framework that the industry has converged on — Anthropic's _Building Effective Agents_ (2024-12-19) — so you can make this decision deliberately on every new system you design.

## The distinction (Anthropic, 2024-12)

> **Workflows** are systems where LLMs and tools are orchestrated through predefined code paths.
>
> **Agents** are systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks.

In a workflow, your code decides the next step based on the LLM's output. In an agent, the LLM decides the next step itself.

```javascript
// Workflow: code decides what happens next
const classification = await classify(input);
if (classification.intent === "refund") {
  const refundDecision = await assessRefund(input, classification);
  return formatRefundResponse(refundDecision);
} else if (classification.intent === "shipping") {
  return await lookupShippingStatus(input);
}

// Agent: the model decides what happens next, turn by turn,
// based on tools available and prior turn results
const result = await runAgent({
  systemPrompt:
    "You are a customer service agent. You have tools for refunds, shipping lookup, and escalation. Decide what to do.",
  tools: [refundTool, shippingTool, escalationTool],
  userMessage: input,
});
```

Both can produce the same answer for "where is my package." Only the agent might decide on its own to _also_ offer a refund when it notices the package is late. That flexibility is the value an agent adds. The unpredictability of how it decides is the cost.

## The five workflow patterns

Anthropic names five recurring workflow patterns. Before reaching for an agent, ask whether one of these covers your use case.

### 1. Prompt chaining

Decompose a task into a fixed sequence of LLM calls where each step's output feeds the next.

```
[user input] → LLM 1: extract entities → LLM 2: rank entities → LLM 3: write response
```

Use when the task has clean stages and intermediate validation between stages is cheap and useful.

### 2. Routing

A small LLM (or simple classifier) picks which downstream path handles the input.

```
[user input] → router LLM (small/cheap) → one of N specialized prompts/models
```

Use when different input types need genuinely different handling — a question for a different model, a different prompt, or even a different non-LLM pipeline. The router is a switch statement that learns.

### 3. Parallelization

Run several LLM calls concurrently on parts of the input, then aggregate. Two flavors:

- **Sectioning** — split the input into independent pieces (review each PR file in parallel; analyze each customer review separately) then combine.
- **Voting** — run the same task multiple times with different prompts or models, then take majority/median to reduce variance.

Use when latency matters more than the marginal cost of duplicate calls.

### 4. Orchestrator-workers

A central LLM dynamically decomposes a task into subtasks and delegates each to a worker LLM. The orchestrator integrates the results.

```
[task] → orchestrator (plan + delegate) → worker A, worker B, worker C → orchestrator (integrate)
```

This is _close to_ a real agent — it's the most flexible workflow pattern. The distinction: the orchestrator's behavior is constrained by code (single planning step → fixed delegation → single integration step), not free-roaming model-driven control.

### 5. Evaluator-optimizer

One LLM produces a response, another LLM (or rubric) evaluates it; the loop continues until the evaluator passes.

```
[task] → generator LLM → evaluator LLM → (pass: done; fail: feed critique back) → generator LLM …
```

Use when you have a clear quality bar that can be evaluated automatically and a meaningful chance the first attempt won't meet it.

If your task fits any of these five patterns, **build the workflow, not the agent.** You get more predictable cost, more debuggable behavior, and faster shipping.

## When to actually reach for an agent

An agent is the right call when _all three_ of these are true:

1. **The set of next-step decisions is too large to enumerate in code.** If a switch statement over plausible next actions has more than a handful of branches, an LLM dynamically choosing is more honest than your hand-coded heuristic.
2. **The path to the answer varies between requests in ways you can't predict.** Customer-support escalation, debugging an unfamiliar codebase, exploring an unfamiliar API — the value is exactly that you don't know in advance what steps the system will need.
3. **You can absorb the cost of unpredictability.** Agents will sometimes loop, take an unexpected path, or burn tokens on dead ends. Production systems that can't tolerate that need a workflow.

The most successful agentic production systems in 2025-2026 cluster in three surfaces where all three conditions hold:

- **Coding assistants** — the space of "what to do next" in an unknown codebase is vast and per-task.
- **Browser automation** — the same flow can hit a different DOM, a different login wall, a different error each time.
- **Customer-support escalation** — the long tail of unusual cases doesn't fit a fixed decision tree.

Notably absent: routine data extraction, content generation with a fixed structure, classification, summarization, translation. Those are workflow problems all the way down.

## The cost-of-flexibility analysis

Quantitatively, agents cost more than workflows on every axis:

| Axis                | Workflow                                   | Agent                                                   |
| ------------------- | ------------------------------------------ | ------------------------------------------------------- |
| Token cost per task | Predictable (fixed call count)             | Variable (model decides how many turns)                 |
| Latency             | Predictable (sum of call latencies)        | Variable (model decides loop length)                    |
| Debuggability       | Easy — every step is in your code          | Hard — model's decisions are opaque without good traces |
| Failure modes       | Tractable (each call may fail; you handle) | Open-ended (loops, dead ends, hallucinated tools)       |
| Test surface        | Small (test each step)                     | Large (test possible trajectories)                      |

Anthropic's recommendation, which the field has adopted: **start with the simplest workflow that solves the problem.** Only escalate to an agent when the workflow's rigidity is actively blocking the use case. The escalation should be a deliberate decision with a written justification, not a reflex.

## Production framing in 2026

Two patterns have crystallized:

- **Workflows ship first; agents replace workflows piecewise as cases reveal themselves.** Most production AI starts as a routing workflow over specialized prompts. Only when a workflow's branches multiply past usefulness does a team replace one branch with a true agent.
- **The harness matters more than the model for agent quality.** The SWE-bench community openly acknowledges that the _same base model in different scaffolds_ varies by 15+ percentage points. The implication for your work: spend more design time on the agent's tools, prompts, approval gates, and failure handling than on which model you picked.

The MCP module (6-4) covered the protocol agents use to reach tools. This module — 6-7 — covers what to do once your agent is reaching for tools in production.

## What you learned

- **The defining axis between workflow and agent is who controls the next-step decision** — code (workflow) or the LLM itself (agent).
- **Five workflow patterns** cover most production needs: **prompt chaining**, **routing**, **parallelization** (sectioning + voting), **orchestrator-workers**, **evaluator-optimizer**.
- **Three conditions to justify an agent**: enumerable-in-code decision space is too large, per-request path varies unpredictably, AND your system can absorb the cost of unpredictability.
- **Cost-of-flexibility tradeoff**: agents cost more than workflows on every axis — tokens, latency, debuggability, test surface, failure modes. Reach for them deliberately, not reflexively.
- **The harness matters more than the model.** Spend design time on tools, prompts, approval gates, and failure handling. The SWE-bench evidence is unambiguous.
- **Production framing**: workflows ship first; agents replace specific workflow branches piecewise as the long tail of cases reveals itself.
