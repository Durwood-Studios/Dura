## Why this matters

Code-writing agents are the flagship production agent surface of 2025-2026. They're the surface most learners use daily — through Claude Code, Cursor, OpenAI Codex, Windsurf, or a competitor. They're also the surface where production patterns crystallized fastest, because feedback loops are tight: a bad code change fails a test, the agent retries, the next attempt is measurably better or worse.

This lesson is the case study capstone of the module. It applies what you've learned about workflow vs agent (lesson 01), observability (02), cost engineering (03), prompt injection (04), browser/computer use (05), and voice (06) to the one agent surface most developers experience first-hand. DURA itself was built with one of these tools — so the lesson doubles as transparency about how this curriculum exists.

## Two product categories

Code-writing agents fall into two lanes that solve different problems:

### "Edits code" (IDE-embedded)

The agent lives in your editor. You highlight a region, hit a shortcut, and it rewrites that region. The unit of work is "this function," "this file," "this selection." The human is in the editor, reading the diff before accepting.

**Examples:** Cursor, Windsurf (the IDE), GitHub Copilot Workspace, Google Antigravity, Kiro.

**Best for:** known codebase, scoped change, human review on every edit.

### "Ships features" (terminal / autonomous)

The agent runs in the terminal or a managed environment. You give it a task ("fix the failing CI on this branch," "implement feature X according to the linked spec"), and it iterates — reads code, edits multiple files, runs tests, retries on failure — until it ships a PR or fails.

**Examples:** Claude Code (Anthropic-native CLI, what built DURA), OpenAI Codex (terminal-capable), Devin / Devin Terminal (Cognition, "autonomous junior engineer"), Aider (OSS git-aware CLI).

**Best for:** larger tasks, unfamiliar codebase exploration, multi-file refactors, CI fixes, work the human doesn't want to babysit step-by-step.

In production teams in 2026, the common pattern is **both** — Cursor (or competitor) for inline edits during exploration, Claude Code (or competitor) for full features that ship.

## SWE-bench-Verified — what it does and doesn't tell you

SWE-bench Verified is the canonical coding-agent benchmark — real GitHub issues from real repos, with verified test cases. Frontier scaffolds cluster in the **85-94%** range as of mid-2026.

**Important caveat:** different benchmark trackers report different leaders. One source ranks GPT-5.5 #1 at 88.7% (released 2026-04-23); another puts Claude Mythos Preview #1 at 93.9%. **Don't quote a single "winner" without checking the official leaderboard at [swebench.com](https://www.swebench.com/) the day you write or read.** Benchmark rankings drift weekly.

What SWE-bench-Verified _does_ tell you reliably:

- **Frontier scaffolds are in the 85-94% band.** The top of the leaderboard isn't 60% anymore. Coding agents work in 2026; they didn't reliably work in 2024.
- **Harness matters more than the model.** The SWE-bench community openly acknowledges that the _same base model in different scaffolds_ varies by **15+ percentage points**. This is the most important production lesson the benchmark teaches.

What it _doesn't_ tell you:

- How well an agent works on your specific codebase.
- How it behaves on tasks longer than typical issues.
- Cost per task in production.
- How it handles ambiguous specifications, missing context, or pushback from human reviewers.

Choose tooling on the dimensions that matter to your work, not on the leaderboard's top row.

## Five production patterns that crystallized in 2025-2026

The wave produced a few patterns that now look obvious in retrospect. They appear across every successful coding agent regardless of which underlying model it uses.

### 1. Planning + execution loops

The agent emits a plan first, then executes it step-by-step with re-planning on failure. The plan is visible to the user; the user can edit it before execution starts.

```
[task] → agent (emit plan) → [user reviews plan] → agent (execute step 1) → [check]
        → agent (execute step 2) → [check] → ... → [done or re-plan]
```

Why it matters: separating "decide what to do" from "do it" lets the human catch wrong plans cheaply. Without a visible plan, the human only catches mistakes after wrong code is written.

### 2. Multi-file edits as atomic diff packages

The agent edits multiple files together and presents the diff as one reviewable unit. The unit either gets accepted whole or rejected whole. Per-file editing creates inconsistent intermediate states; atomic multi-file is the production discipline.

Implementation patterns vary — some tools use a virtual filesystem layer that commits atomically; some use git stash + apply. The user-facing behavior is the same: one diff, accept or reject.

### 3. Test-driven agent loops

The agent runs tests after each edit, feeds the failures back as the next turn's input, retries. This is the dominant pattern in Claude Code, OpenAI Codex, Aider — anywhere the codebase has a test suite.

```
edit → run tests → green: done | red: feed failure trace → edit → run tests → ...
```

The discipline shifts code-writing agent quality dramatically. Without it, agents write code that looks right but fails. With it, the test suite becomes the ground truth and the agent iterates against it.

This is also why **codebases with strong test coverage benefit disproportionately from coding agents.** Untested codebases force the agent to guess at correctness; tested codebases give it a feedback signal.

### 4. The harness-matters-more discipline

The SWE-bench observation generalizes: how an agent is wrapped — what tools it has, how its prompt is structured, what context it gets, how its outputs are validated — affects results more than which model is inside. This is the under-appreciated finding of the 2025-2026 wave.

Practical implication: when choosing or building coding tooling, spend your design time on the **harness** (which files to load into context, which tools to expose, which tests to run, which approval gates to apply, how failures get fed back) rather than on whether you got the latest model version yesterday.

### 5. Two-tool workflows are normal

Most developers in 2026 use _both_ an editor agent (Cursor / Windsurf) for inline edits during exploration _and_ a shipping agent (Claude Code / Codex / Devin) for full features. Single-tool workflows are now the minority.

The two-tool pattern works because the lanes solve different problems: the editor agent gives you tight feedback on small edits with your full attention; the shipping agent runs longer-horizon tasks while you do other work. They're complements, not competitors.

## Connecting back to the module

This module's seven lessons all show up in code-writing agents:

- **Lesson 01 (Workflow vs Agent)** — the test-driven loop _is_ an evaluator-optimizer workflow when the rubric is the test suite. Most successful coding agents are evaluator-optimizer workflows masquerading as agents. The "true agent" mode kicks in when no test exists for the failure (e.g., "this PR violates a code-style heuristic the linter can't catch").
- **Lesson 02 (Observability)** — Claude Code, Cursor, Codex all emit traces. Production teams running them at scale wire Langfuse or LangSmith to see why a session burned 200K tokens.
- **Lesson 03 (Cost engineering)** — coding agents are the canonical model-routing surface. Cursor's Composer 2.5 explicitly markets the routing of cheap-and-fast for inline edits vs frontier for hard problems. Stacking cache + batch + routing puts coding-agent costs at single-digit cents per task.
- **Lesson 04 (Prompt injection at agent depth)** — coding agents ingest untrusted code and have full filesystem + network capability. A package's README with an injection payload could in principle hijack a code agent. Real exploits in 2025-2026 are still rare for coding agents specifically, but the threat model is unchanged.
- **Lesson 05 (Computer Use / Browser Agents)** — some coding agents (Devin variants, Computer Use mode in Claude Code) browse documentation or check API responses while coding. Same Lethal Trifecta considerations apply.
- **Lesson 06 (Voice / Realtime)** — voice-driven coding agents exist as a research curiosity but haven't become mainstream production patterns yet.

This pattern — every module lesson showing up in every production agent — is why module 6-7 exists. Coding agents are the most-developed instance of the general agent-engineering discipline.
