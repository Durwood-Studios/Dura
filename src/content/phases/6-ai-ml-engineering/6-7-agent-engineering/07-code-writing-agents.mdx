## Why this matters

A coding agent can produce a large plausible patch faster than a reviewer can inspect it. Useful automation therefore depends on a feedback loop that exposes incorrect assumptions early and leaves a concrete result that can be tested and reviewed.

## Start with something familiar

A mechanic inspects the actual engine, makes a bounded repair, then tests it instead of trusting a plausible description.

## The mental model

> A coding agent needs repository context, constrained edits, executable checks, and review of the resulting behavior.

## Scope the task before editing

Editor assistance may complete or revise a small code region. A broader coding agent can inspect a repository, edit multiple files, run commands, and propose a change. Products may support both modes; interface labels do not define a reliable boundary between their capabilities.

Write an observable acceptance condition. “Improve reliability” is vague. “After an offline save, the draft remains available after reload and sends once after reconnect” identifies behavior to test. Find existing conventions, relevant tests, and the data path before changing code.

## The inspect, edit, test, review loop

Consider a form that loses its text on a network failure. First inspect where input state lives, when persistence occurs, and what the submission callback does. Reproduce the failure with a controlled rejected request. Then make the smallest change that preserves the draft and reports the failed delivery honestly.

Run a test that failed before the fix. Also check that a successful submission still clears the draft at the intended time. A passing test is useful only if it exercises the behavior: asserting that a mocked helper was called does not prove text survives reload.

Review the resulting diff for unrelated edits, hidden persistence changes, authorization changes, and new dependency assumptions. Generated code can be syntactically correct while violating an application invariant such as offline operation.

## The harness shapes the evidence

The harness is the environment around the model: repository access, tools, prompts, permissions, context selection, command output, and stopping rules. A missing test runner or truncated failure log can prevent self-correction even when the model could understand the bug.

Changing both the model and harness at once makes it difficult to identify which change improved results. Compare them on the same representative tasks, with a fixed budget and the same acceptance criteria. Record success, regressions, review effort, cost, and time; do not count only patches generated.

SWE-bench evaluates repository issue resolution in defined setups. Its leaderboard distinguishes benchmark variants and systems. Check the exact dataset and evaluation procedure before comparing scores. A benchmark result does not establish correctness for your application, and no universal percentage advantage for a particular harness follows from a single comparison.

## Keep untrusted repository data within its boundary

A source comment, dependency README, test fixture, or issue quote can contain instructions aimed at an agent. Treat it as task data unless it comes from an authorized instruction source. Never let a fetched document grant permission to expose credentials, erase unrelated files, or publish a change.

Use an isolated checkout for risky experiments, preserve existing user edits, and restrict commands to the task. A failing test is evidence to investigate; deleting it or weakening its assertion merely hides the failure. Review generated tests too, because they can encode the same misunderstanding as the implementation.

## Stop with a reviewable result

A good handoff states the changed behavior, relevant test evidence, and remaining limitations. If a required integration cannot run, identify what was tested locally and what remains unverified. A patch should not be called deployed, merged, or production-ready solely because it builds.

## Guided practice

An agent changes a retry handler and adds a test that mocks the retry handler to always succeed. The test passes. Which evidence is missing, and what would you test instead?

<details>
<summary>Compare your reasoning</summary>

The test bypasses the changed behavior. Exercise the real handler with a controllable network boundary: fail the first request, inspect durable saved state, reload or reinitialize, succeed the retry, and verify no duplicate delivery. Also test cancellation or reset during a pending request. The assertions should observe user state and delivery effects, not only mock invocation.

## What you learned

- Define behavior that can be observed before editing.
- Use tests that exercise the changed logic and its boundaries.
- Evaluate model and harness changes with controlled comparisons.
- Review the patch and distinguish local verification from deployment.
