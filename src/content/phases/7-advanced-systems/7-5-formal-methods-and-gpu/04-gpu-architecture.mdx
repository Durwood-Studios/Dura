## Why this matters

A parallel kernel can still spend most of its time waiting for memory or executing with inactive lanes. Understanding how threads share execution and storage helps explain those bottlenecks. Hardware counts and theoretical bandwidth alone do not predict application speed: measure a specific kernel on a specific device.

## Start with something familiar

A group carrying a wide load moves efficiently together, but conflicting directions slow the group. Likewise, nearby threads often benefit from similar work and nearby memory addresses.

## The mental model

> A GPU schedules groups of threads across shared execution resources. Resident threads provide work to schedule; they are not a count of physical arithmetic units.

## Threads, warps, and streaming multiprocessors

NVIDIA CUDA groups 32 threads into a **warp**. A thread block runs on one streaming multiprocessor (SM), and multiple blocks may reside on that SM when resources permit. A warp instruction operates on its active lanes. This SIMT programming model resembles SIMD execution, but it provides each thread with its own logical state.

A warp does not guarantee that every instruction finishes in one clock. Issue throughput, instruction latency, active masks, and hardware generation affect execution. Modern NVIDIA devices support independent thread scheduling; code must use the appropriate synchronization primitives rather than assuming implicit lockstep cooperation.

Consider a hypothetical SM supporting 64 resident warps: 64 × 32 = 2,048 resident threads. That describes capacity for thread state, not 2,048 arithmetic units. When one warp cannot issue because a dependency is unresolved, another ready warp may issue. Enough independent work can hide some latency; it does not eliminate the memory operation or guarantee every stall disappears.

## Worked example: branch divergence

```c
// Teaching fragment: a and b are per-thread values.
if (threadIdx.x % 2 == 0) {
    result = a * b;
} else {
    result = a + b;
}
```

Even and odd lanes request different work. Generated code may use masked paths or predication. Do not infer a fixed path order or an exact twofold slowdown from the source alone. Instruction costs and compiler decisions matter.

The condition `threadIdx.x < 16` also splits the first warp; contiguous halves do not make the condition uniform. In contrast, for a one-dimensional block, `threadIdx.x / 32 == 0` has the same result throughout each full warp. This can make a particular branch warp-uniform, but changing a condition is valid only if it preserves the intended algorithm.

## The memory hierarchy

| Storage | Role | Important limit |
| --- | --- | --- |
| Registers | Per-thread logical working values, allocated from SM resources | High usage can limit residency; spills use memory |
| Shared memory | Programmer-managed storage shared within a block | Capacity, bank conflicts, and synchronization |
| L1 cache | Hardware-managed reuse near execution units | Organization and sharing vary by device |
| L2 cache | Reuse across SMs | Capacity and access pattern |
| Device global memory | Large addressable storage | Traffic, locality, and bandwidth |

Sizes and timings are architecture-specific. Shared memory can reduce repeated global loads when threads reuse staged data, but loading and synchronizing the tile costs work too. More shared memory is not automatically faster.

## Worked example: address locality

For a 32-lane warp reading four-byte floats, compare these addresses:

```c
// Consecutive lanes: base + 0, 4, 8, ... 124 bytes
float adjacent = global_array[i];

// Stride 64: base + 0, 256, 512, ... 7936 bytes
float scattered = global_array[i * 64];
```

The adjacent pattern permits efficient coalescing when alignment is suitable. The strided pattern touches widely separated regions for the same 128 bytes of useful values. Actual memory transactions depend on the architecture, alignment, caches, and instruction; do not equate either expression with a universal number of DRAM transactions or a fixed speed ratio.

When comparing versions, hold the data and result constant, warm up appropriately, use device-aware timing, and inspect achieved bandwidth and memory-access metrics. A faster kernel that computes different results is not an optimization.

## Occupancy and its limits

**Occupancy** is resident active warps divided by the supported maximum. Registers, shared memory, threads, block limits, and allocation granularity all constrain residency.

Suppose an SM has 164 KiB available for blocks and each block requests 64 KiB. Considering shared memory alone, at most floor(164 / 64) = 2 blocks fit. The remaining 36 KiB cannot fit another equal-sized block. At 8 KiB per block the corresponding upper bound is 20, but another resource may impose a lower limit in either case.

Thus increasing shared memory can reduce the resource bound without necessarily changing actual occupancy. Higher occupancy can help hide latency, but it is not a performance score: reducing redundant loads or register spills may improve runtime despite lower occupancy.

## What you learned

- Warps group threads; resident thread counts are not physical arithmetic-unit counts.
- Non-uniform branch paths can waste lane capacity, with no universal slowdown factor.
- Consecutive aligned addresses generally use memory traffic more efficiently than scattered addresses.
- Shared memory can support reuse, while its per-block allocation constrains residency.
- Occupancy is a resource metric; validate performance using correct results and measured runtime.
