## Why this lesson exists

In a vendor HAL world, blinking an LED looks like:

```c
HAL_GPIO_TogglePin(GPIOD, GPIO_PIN_12);
HAL_Delay(500);
```

This is fine code. It's also opaque code — it hides the question "what's actually happening." Every embedded engineer who can only operate at this level eventually hits a wall:

- The HAL doesn't expose the peripheral feature they need.
- The HAL has a bug.
- The HAL is wrong about timing.
- The HAL doesn't exist for the chip in question (a small ARM chip from an obscure vendor).

The path past the wall is reading the reference manual and writing direct-register code. Once you can do that, you can work on ANY chip, with or without a HAL.

The threshold concept: **a memory-mapped peripheral is just memory at a known address with a known layout, and writing to it changes hardware state.** Once that lands, every peripheral on every chip is approachable the same way.

## What "memory-mapped I/O" actually is

On Cortex-M, peripherals (GPIO, UART, timers, ADC, etc.) are accessed by READING and WRITING addresses in a reserved region of the memory map. The CPU executes a normal load/store instruction; the bus routes the access to the peripheral instead of memory; the peripheral changes state.

For STM32F4:

- `0x00000000` – `0x1FFFFFFF` — Code region (flash aliased; vector table)
- `0x20000000` – `0x3FFFFFFF` — SRAM
- `0x40000000` – `0x5FFFFFFF` — **Peripherals**
- `0x60000000` – `0xDFFFFFFF` — External RAM/devices
- `0xE0000000` – `0xFFFFFFFF` — Cortex-M private peripherals (NVIC, SysTick, etc.)

Each peripheral has a base address in the peripheral region and a set of registers at fixed offsets from that base. The STM32F4 reference manual (RM0090) is the source of truth: a thousand-page PDF that lists every peripheral, every register, every bit.

You learn to use a chip by reading its reference manual. That skill is portable across vendors. There is no shortcut.

## The smallest useful peripheral — GPIO

GPIO (General-Purpose I/O) is the simplest peripheral: pins that you set high or low (output) or read from (input). Every chip has GPIO. Every "blink an LED" program toggles a GPIO pin.

STM32F4 Discovery has an LED on pin PD12 (GPIO port D, pin 12). To blink it, we need to:

1. Enable the clock to GPIO port D. (Peripherals don't run without their clock enabled — the RCC peripheral is gatekeeper.)
2. Configure pin PD12 as a digital output.
3. Toggle the pin.

From the STM32F4 reference manual:

### RCC — Reset and Clock Control

- Base address: `0x40023800`
- `AHB1ENR` register at offset `0x30` — bit 3 enables GPIOD clock.

### GPIOD — Port D

- Base address: `0x40020C00`
- `MODER` register at offset `0x00` — two bits per pin; `0b01` = output mode.
- `ODR` register at offset `0x14` — output data; bit N is the output state of pin N.

## Setting it up in C

```c
#include <stdint.h>

// Register addresses, taken from the reference manual.
#define RCC_BASE         0x40023800UL
#define GPIOD_BASE       0x40020C00UL

#define RCC_AHB1ENR     (*(volatile uint32_t *)(RCC_BASE + 0x30))
#define GPIOD_MODER     (*(volatile uint32_t *)(GPIOD_BASE + 0x00))
#define GPIOD_ODR       (*(volatile uint32_t *)(GPIOD_BASE + 0x14))

#define RCC_AHB1ENR_GPIODEN  (1U << 3)    // Bit 3 enables GPIOD clock
#define LED_PIN              12           // PD12 — green LED on STM32F4 Discovery

int main(void) {
    // 1. Enable clock to GPIOD
    RCC_AHB1ENR |= RCC_AHB1ENR_GPIODEN;

    // 2. Configure PD12 as output (MODER bits 24-25 = 0b01)
    GPIOD_MODER &= ~(0b11U << (LED_PIN * 2));   // Clear the two bits
    GPIOD_MODER |=  (0b01U << (LED_PIN * 2));   // Set output mode

    // 3. Toggle PD12 forever
    while (1) {
        GPIOD_ODR ^= (1U << LED_PIN);

        // Crude busy-wait delay. Lesson E3 covers proper timing.
        for (volatile int i = 0; i < 500000; i++) { }
    }

    return 0;
}
```

The Makefile, linker script, and startup code from Lesson E1 work unchanged. `make` produces `firmware.bin`. Flash to the board with `st-flash write firmware.bin 0x08000000`. The green LED blinks.

But you didn't come here to copy-paste. You came here to understand. Let's read this line by line.

## Why `volatile` — operationally

Look at the register macro:

```c
#define GPIOD_ODR  (*(volatile uint32_t *)(GPIOD_BASE + 0x14))
```

The `(volatile uint32_t *)` cast is doing real work. Without `volatile`, GCC's optimizer would do this transformation:

```c
// What you wrote
GPIOD_ODR ^= (1U << LED_PIN);
for (volatile int i = 0; i < 500000; i++) { }
GPIOD_ODR ^= (1U << LED_PIN);

// What GCC might compile to (without volatile)
//   "ODR isn't used in the loop, so I can hoist the second toggle
//    up and combine it with the first — they cancel out, so emit nothing."
```

The result: GCC silently optimizes your LED toggles away. Nothing happens. You stare at a dead LED for hours.

`volatile` is the keyword that tells GCC "every read and write of this thing must happen, in source order, no exceptions." For memory-mapped peripherals where reads/writes have hardware side effects, `volatile` is mandatory. Forgetting it is the single most common "why doesn't my embedded code work" mistake.

Operational summary:

- `volatile` is required for any memory-mapped peripheral register.
- `volatile` is required for any variable shared between an ISR and main code (Lesson E3).
- `volatile` is required for variables monitored externally (e.g., by a debugger).
- `volatile` is NOT a synchronization primitive — it doesn't give you atomicity across threads. (Lesson E4 covers this.)

## Bit manipulation patterns

Embedded C uses bit-shift and mask patterns constantly. Three operations recur in every peripheral driver you'll ever write:

### Set a bit (read-modify-write)

```c
GPIOD_ODR |= (1U << LED_PIN);    // Set bit LED_PIN to 1, leaving others alone
```

Reads the current ODR value, ORs in the bit, writes back. The non-target bits are preserved.

### Clear a bit

```c
GPIOD_ODR &= ~(1U << LED_PIN);   // Clear bit LED_PIN, leaving others alone
```

`~` inverts the mask so the target bit becomes 0; AND preserves the others and clears the target.

### Toggle a bit

```c
GPIOD_ODR ^= (1U << LED_PIN);    // Flip bit LED_PIN
```

XOR with 1 flips a bit; XOR with 0 preserves it.

### Set a multi-bit field

For MODER, each pin has TWO bits (input / output / alt-function / analog). To set pin 12 to output (`0b01`):

```c
GPIOD_MODER &= ~(0b11U << (12 * 2));  // Clear both bits for pin 12
GPIOD_MODER |=  (0b01U << (12 * 2));  // Set them to 0b01
```

The two-step (clear, then set) is necessary because OR can only set bits — it can't change a 1 to a 0. Always clear before setting when writing to a multi-bit field.

## The hidden race — read-modify-write under interrupt

`|=` on a register is `read → modify → write`. Three CPU instructions on Cortex-M:

```assembly
LDR  r0, [r1]        ; Load ODR value
ORR  r0, r0, #0x1000 ; Set bit 12
STR  r0, [r1]        ; Store ODR value
```

If an interrupt fires between the LDR and the STR, and the interrupt handler ALSO modifies the same register, the main code's write will UNDO the interrupt handler's write.

```c
// In main:
GPIOD_ODR |= (1U << 12);    // Set PD12 high

// In an interrupt handler that fires mid-sequence:
GPIOD_ODR |= (1U << 13);    // Set PD13 high

// What actually happens at the bus:
//   main reads ODR (PD13=0)
//   ISR runs: reads ODR (PD13=0), sets PD13, writes (PD13=1)
//   main resumes: ORs in PD12 mark on its STALE copy, writes (PD13=0)
//   PD13 is now wrong.
```

For GPIO specifically, STM32 provides BSRR (Bit Set/Reset Register) — a write-only register where writing a 1 to a bit SETS the corresponding ODR bit, and writing a 1 to bit N+16 CLEARS the corresponding ODR bit. BSRR is single-write — no read-modify-write race:

```c
#define GPIOD_BSRR (*(volatile uint32_t *)(GPIOD_BASE + 0x18))

// Atomic set
GPIOD_BSRR = (1U << 12);
// Atomic clear
GPIOD_BSRR = (1U << (12 + 16));
```

For other peripherals without a BSRR-style register, the fix is to disable interrupts during the read-modify-write. We'll cover that in Lesson E3.

The takeaway for now: **`|=` and `&=` on shared registers are not atomic on Cortex-M.** When the same register can be touched by both main and an ISR, use a single-write mechanism (BSRR) or disable interrupts around the access.

## What you can now do

You've written embedded code from the reference manual without a vendor HAL. Specifically:

- You can find a peripheral register's address from its base + offset.
- You can read a bit-field definition and translate it into a C bit-mask.
- You know what `volatile` does and when to use it.
- You can recognize a read-modify-write race when one matters.
- You can blink an LED on any Cortex-M chip given its reference manual.

The next lessons add timing precision (interrupts, timers, SysTick) and peripheral complexity (UART, SPI, I2C, ADC). All of them build on the register-access patterns from this lesson.

## Hands-on exercise

Set up the program above. The exercise has three parts:

1. **Build and flash.** Verify the LED blinks. If it doesn't, run `arm-none-eabi-objdump -h firmware.elf` and confirm `.text` is at the right address — Lesson E1's first diagnostic.
2. **Read the register state.** Open the chip in OpenOCD or a debugger and watch `GPIOD_ODR` change as the LED toggles. The change should be visible at the address you computed: `0x40020C14`.
3. **Switch to BSRR.** Replace the `^=` toggle with a paired BSRR sequence:
   ```c
   if (led_on) GPIOD_BSRR = (1U << (12 + 16));  // Clear
   else        GPIOD_BSRR = (1U << 12);          // Set
   led_on = !led_on;
   ```
   The LED should still blink. The behavior is the same; the write semantics are different — and now interrupt-safe.
