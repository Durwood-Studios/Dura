## Why this lesson exists

E2 ended with a teaser: read-modify-write races between main code and ISRs. This lesson makes that operationally concrete. By the end, you can write ISRs that don't break the rest of your firmware AND you can use DMA to move bytes without the CPU touching them.

The threshold concept: **ISRs run BETWEEN main-code instructions, not between main-code statements.** A statement like `counter++` is two or three instructions (load, increment, store). An ISR can fire between any pair of them. Embedded engineers who internalize this write correct interrupt-driven code; engineers who don't write code that works in testing and fails in the field.

## NVIC — the interrupt controller

Cortex-M's NVIC (Nested Vectored Interrupt Controller) handles up to 240 peripheral interrupts plus the 16 core exceptions. To use an interrupt:

1. The vector table entry for that interrupt must point at a real handler (not `Default_Handler`).
2. The peripheral must be configured to generate the interrupt.
3. The NVIC must enable that interrupt.
4. The peripheral interrupt-enable bit must be set.

For a USART2 RX interrupt:

```c
#define NVIC_ISER1   (*(volatile uint32_t *)(0xE000E104))
#define USART2_IRQn  38   // From the chip's interrupt vector table

void enable_usart2_rx_irq(void) {
    // Enable in NVIC: ISER[1] bit (38 - 32) = bit 6
    NVIC_ISER1 |= (1U << (USART2_IRQn - 32));
}
```

The vector table from E1 expands. Add the USART2 handler at index 38 + 16 = 54:

```c
__attribute__((section(".isr_vector")))
const void * const vector_table[] = {
    &_estack,              //  0
    Reset_Handler,         //  1
    NMI_Handler,           //  2
    HardFault_Handler,     //  3
    // ... entries 4-53 ...
    USART2_IRQHandler,     // 54 — IRQ 38 (USART2)
    // ... rest
};
```

## ISR pattern — keep it short

The ISR runs with interrupts (mostly) disabled. While it's running, your latency-sensitive code is waiting. The rule:

> ISR work = clear-the-flag + enqueue-the-event. Heavy work goes in main.

A USART RX ISR done right:

```c
volatile uint8_t rx_buffer[64];
volatile uint8_t rx_head = 0;
volatile uint8_t rx_tail = 0;

void USART2_IRQHandler(void) {
    if (USART2_SR & SR_RXNE) {              // RX register not empty
        uint8_t byte = USART2_DR;            // Read clears the flag

        uint8_t next = (rx_head + 1) % 64;
        if (next != rx_tail) {               // Buffer not full
            rx_buffer[rx_head] = byte;
            rx_head = next;
        }
        // Else: drop the byte. Better than overrun.
    }
}
```

What this ISR does NOT do:

- It does not call `printf` (too slow, may not be reentrant).
- It does not take a mutex (priority inversion — Lesson E4).
- It does not allocate memory (heap is not ISR-safe in most embedded environments).
- It does not loop indefinitely.

Main code drains the ring buffer:

```c
int rx_pop(uint8_t *out) {
    // Disable USART2 IRQ while we touch the indices to avoid races
    NVIC_ICER1 = (1U << 6);                 // ICER = clear-enable
    int has_data = (rx_head != rx_tail);
    if (has_data) {
        *out = rx_buffer[rx_tail];
        rx_tail = (rx_tail + 1) % 64;
    }
    NVIC_ISER1 = (1U << 6);                 // Re-enable
    return has_data;
}
```

The `volatile` on the indices is mandatory — without it, GCC may cache `rx_head` in a register and never see the ISR's updates. We covered this in E2; now it bites.

## Interrupt priority and BASEPRI

Cortex-M assigns each interrupt a priority number (0 = highest). Higher-priority interrupts preempt lower-priority ones. Two configurable controls:

- **`NVIC_IPRn`** — per-interrupt priority. Typical mapping: 4 priority bits, 16 levels.
- **`BASEPRI`** — Cortex-M core register. Masks interrupts of priority >= BASEPRI value. Setting BASEPRI = `0x10` blocks all interrupts of priority 1 and lower while leaving priority 0 free.

Critical sections use BASEPRI rather than wholesale disabling:

```c
static inline uint32_t enter_critical(void) {
    uint32_t prev = __get_BASEPRI();
    __set_BASEPRI(0x10);    // Block priorities >= 1
    __ISB();
    return prev;
}

static inline void exit_critical(uint32_t prev) {
    __set_BASEPRI(prev);
}

// Use:
uint32_t state = enter_critical();
// ... read-modify-write on shared state ...
exit_critical(state);
```

Why not just `__disable_irq()` (which sets PRIMASK)? Because PRIMASK blocks ALL interrupts including the highest-priority safety-critical ones (e.g., motor overcurrent shutoff). BASEPRI lets you keep the truly critical ISRs running while gating the application-level ones.

## DMA — the third actor

DMA controllers move bytes between memory and peripherals (or memory and memory) without CPU involvement. A configured DMA channel is told: "move N bytes from this source to this destination, then interrupt me." The CPU does other work while DMA runs.

For STM32F4's DMA2 Stream 0 (ADC1):

```c
void adc_dma_setup(uint16_t *dst, uint16_t count) {
    // Enable DMA2 clock
    RCC_AHB1ENR |= (1U << 22);

    // Disable stream before configuring (required)
    DMA2_S0CR &= ~(1U << 0);
    while (DMA2_S0CR & (1U << 0)) { }

    DMA2_S0PAR  = (uint32_t)&ADC1_DR;       // Source: ADC1 data register
    DMA2_S0M0AR = (uint32_t)dst;             // Destination: caller's buffer
    DMA2_S0NDTR = count;                     // Number of items

    // Memory increment, peripheral fixed, half-word transfers, transfer-complete IRQ
    DMA2_S0CR =
        (1U << 10) |    // MINC: memory increment
        (1U << 13) |    // MSIZE = 16-bit
        (1U << 11) |    // PSIZE = 16-bit
        (1U << 4);      // TCIE: transfer complete interrupt enable

    // Start: enable stream
    DMA2_S0CR |= (1U << 0);
}

void DMA2_Stream0_IRQHandler(void) {
    if (DMA2_LISR & (1U << 5)) {            // TCIF0
        DMA2_LIFCR = (1U << 5);              // Clear flag
        adc_buffer_ready = 1;                // Tell main
    }
}
```

What just happened: the ADC samples a sensor, DMA copies each sample into our buffer, and when the buffer is full DMA fires an interrupt. The CPU was never involved in the per-sample copy — it can run UI code, process other sensors, or sleep.

DMA buffer rules:

- The buffer MUST be in SRAM (DMA typically can't reach flash).
- The buffer MUST be aligned per the transfer size (16-bit transfers need 2-byte alignment).
- The buffer MUST live for the full transfer duration (NO stack-local DMA buffers).
- Main code must NOT touch the buffer while DMA is active.

## When to use what

| Situation                                                 | Use                                       |
| --------------------------------------------------------- | ----------------------------------------- |
| Single byte arrives sporadically (UART command interface) | ISR + ring buffer                         |
| Bulk data stream (audio, ADC sweep, frame buffer)         | DMA                                       |
| Periodic event with tight timing (PWM update)             | Timer + interrupt                         |
| Latency budget < ISR overhead (~50 cycles)                | Polling (rare; budget violation is rarer) |

The pattern: ISRs handle event arrival; DMA handles bulk transfer; timers schedule periodic work. A complete real-time system uses all three.

## What's next

Lesson E4 introduces RTOS fundamentals — tasks, queues, mutexes, and the priority-inversion failure mode that bit Mars Pathfinder. The deferred-work pattern this lesson introduced (ISR enqueues; main drains) maps directly to RTOS queue semantics: the ISR posts to a queue; a task wakes when the queue has data. Once you have an RTOS, you stop writing your own ring buffers and use the kernel's.
