## Why this matters

You restructured a struct from AoS to SoA based on everything in this module. You re-run the benchmark and the latency improved by... nothing measurable. The lesson said SoA should help, the cache analysis says fewer lines should be touched, but the numbers are the same.

Several explanations are possible: the changed loop may not dominate runtime, measurements may be noisy, the compiler may already optimize it, or memory traffic may not be the bottleneck. Use profiling to discriminate among these possibilities before attributing the result to a particular resource.

The measurement comes first.

## Start with something familiar

A low speedometer reading shows little progress but does not tell you whether the cause is a steep hill, a red light, or an empty fuel tank.

## The mental model

> Hardware counters measure events with model-specific definitions. Low instructions per cycle is a symptom compatible with several bottlenecks, not a diagnosis of cache misses by itself.

## perf stat: the five-second assessment

`perf stat` attaches to a process, counts hardware events using the CPU's <VocabTooltip slug="performance-monitoring-unit">Performance Monitoring Unit</VocabTooltip> (PMU), and prints a summary. You do not need to recompile your binary or add instrumentation.

```bash
## Why this matters
perf stat ./order_book_bench

# Example output:
# Performance counter stats for './order_book_bench':
#
#          3,245.21 msec task-clock     #  0.998 CPUs utilized
#                 5      context-switches
#                 0      cpu-migrations
#             1,024      page-faults
#    9,876,543,210      cycles                    # 3.04 GHz
#    3,211,567,890      instructions              # 0.32  insn per cycle
#       12,456,789      branches
#          567,890      branch-misses             # 4.56% of all branches
#       89,234,567      cache-references
#       45,678,901      cache-misses              # 51.18% of cache refs
#
#        3.252 seconds time elapsed
```

The critical numbers:

| Metric                       | Good   | Investigate if                     |
| ---------------------------- | ------ | ---------------------------------- |
| Instructions per cycle (IPC) | 2–4    | < 1.0 (memory-bound or serialized) |
| LLC (L3) miss rate           | < 0.5% | > 2%                               |
| Branch miss rate             | < 1%   | > 5% on the hot path               |
| `cycles` / `instructions`    | < 1    | > 4 (severe stall)                 |

In the example above, IPC is 0.32 — the CPU issues fewer than one instruction per clock. It is memory-bound: for every 3 cycles spent doing work, 9 cycles are spent waiting for cache lines. This is the profile of an AoS loop with high LLC miss rate. No amount of algorithmic optimization will help until the data layout changes.

## Targeting specific events

```bash
# Count L1, L2, L3 data cache misses separately
perf stat -e L1-dcache-misses,L2-load-misses,LLC-load-misses \
          -e dTLB-load-misses,iTLB-load-misses \
          ./order_book_bench

# Output (hypothetical):
#     12,300,456  L1-dcache-misses
#      4,567,890  L2-load-misses
#      2,345,678  LLC-load-misses    ← these go to DRAM: ~70ns each
#         89,012  dTLB-load-misses   ← TLB misses → page walks
#          1,234  iTLB-load-misses

# A high LLC-load-misses count with a high dTLB-load-misses count
# suggests you need huge pages (TLB) AND better data layout (LLC).

# Count false-sharing specifically:
# mem_load_retired.l3_miss + look for high cycle counts on specific cachelines
perf c2c record -g ./order_book_bench
perf c2c report
# c2c ("cache-to-cache") shows lines contested between CPUs — the
# exact signature of false sharing.
```

## perf record + perf annotate: finding the line

`perf stat` tells you the program is cache-bound. `perf record` tells you _where_.

```bash
# Sample cache misses at the instruction level
perf record -e LLC-load-misses -g ./order_book_bench

# Display hottest functions
perf report --sort comm,dso,sym

# Annotate a specific function with per-instruction miss counts
perf annotate --symbol=update_book_level
```

A typical annotated output:

```asm
       ↓ 0.12%   │  48:  movq   (%rbx,%rax,8), %rcx   ← 0.12% of samples
       ↑ 83.4%   │  4c:  movq   (%rdx,%rcx,8), %rsi   ← THIS IS THE MISS
                 │  50:  addq   %rdi, %rsi
       ↓ 0.07%   │  54:  movq   %rsi, (%rdx,%rcx,8)
```

Line `4c` — a load through an order-ID-to-level pointer — accounts for 83% of LLC misses. This is the order-to-level lookup in the book update path. The order ID is sequential, but the level pointer it maps to is scattered in memory. The fix: use an intrusive data structure where the order carries its own level reference, eliminating the indirection.

## Valgrind cachegrind: deterministic simulation

`perf` measures real hardware events; it requires root or `perf_event_paranoid` = -1 and is nondeterministic (samples, not counts). `cachegrind` simulates a cache hierarchy deterministically — it counts every miss exactly — at the cost of 20–50× slowdown.

```bash
# Run cachegrind with custom cache parameters matching your CPU
valgrind --tool=cachegrind \
         --I1=32768,8,64 \   # L1 instruction: 32K, 8-way, 64B lines
         --D1=32768,8,64 \   # L1 data: 32K, 8-way, 64B lines
         --LL=33554432,16,64 \ # L3: 32M, 16-way, 64B lines
         ./order_book_bench

# Produces: cachegrind.out.<pid>

# Annotate source with per-line miss counts
cg_annotate cachegrind.out.<pid> --auto=yes

# Example output:
# Ir       I1mr   ILmr   Dr       D1mr    DLmr    Dw       D1mw    DLmw
# 1.23B    4.5K   4.5K   512M     45.6M   23.4M   128M     2.3M    1.2M
#                                  ^ D1 read misses: 45.6M on 512M reads = 8.9%
```

The `DLmr` column (Last-Level cache read misses) is the most important: these are accesses that go to DRAM. A DLmr rate above 5% on a hot loop is a red flag.

## Practical workflow: measure-change-measure

```bash
# Step 1: Establish baseline
perf stat -e cycles,instructions,LLC-load-misses ./bench > baseline.txt

# Step 2: Make layout change (e.g. AoS → SoA)

# Step 3: Measure again
perf stat -e cycles,instructions,LLC-load-misses ./bench > after.txt

# Step 4: Diff
diff baseline.txt after.txt
# If LLC-load-misses dropped 50% and IPC improved from 0.32 to 1.8, the change worked.
# If metrics are the same, the loop was not cache-bound — find the actual bottleneck.
```
