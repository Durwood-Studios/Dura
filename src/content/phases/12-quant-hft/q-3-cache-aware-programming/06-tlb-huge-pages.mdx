## Why this matters

You have applied every cache lesson so far: the order book's price-level array is SoA, aligned to 64-byte lines, NUMA-local, prefetched. The p50 latency is excellent. But the p99.9 tail is still spiking — the worst 1 in 1,000 messages takes 3× longer than the median, with no obvious cause. The CPU isn't waiting for cache lines; it is waiting for something that happens _before_ cache lines are fetched: translating the virtual address into a physical address.

This is the <VocabTooltip slug="tlb">TLB miss</VocabTooltip> — the overlooked twin of the cache miss.

## Start with something familiar

An address directory can remember more territory when each entry describes a larger district, but larger districts also constrain how space is allocated.

## The mental model

> A TLB caches address translations. Larger pages can increase translation coverage per entry, while allocation, fragmentation, and page-management tradeoffs still matter.

## Virtual memory and translation

Every address your program uses is a _virtual_ address. The CPU maps virtual addresses to physical RAM addresses through a <VocabTooltip slug="page-table">page table</VocabTooltip>, a multi-level data structure managed by the OS. On x86-64 with 4K pages, the translation traverses four page-table levels:

```
Virtual address (48 bits):
 [PML4 index 9b] [PDPT index 9b] [PD index 9b] [PT index 9b] [offset 12b]
       │                │               │              │
       ▼                ▼               ▼              ▼
  PML4 table      PDPT table       PD table       PT table → physical page
```

Four memory reads — each of them a cache-miss candidate — to translate one virtual address. The <VocabTooltip slug="tlb">Translation Lookaside Buffer</VocabTooltip> (TLB) caches recently-used translations so most accesses skip this walk. But the TLB has limited capacity:

| TLB level     | Entries (typical Skylake) | Coverage at 4K pages |
| ------------- | ------------------------- | -------------------- |
| L1 DTLB       | 64 entries                | 256 KB               |
| L2 TLB        | 1,536 entries             | 6 MB                 |
| STLB (shared) | 1,536 entries             | 6 MB                 |

An order book that tracks 2,000 price levels with each level's data touching a separate 4K page can overflow the L2 TLB. Every TLB miss triggers a <VocabTooltip slug="page-walk">page walk</VocabTooltip> — four sequential memory accesses, potentially to cold DRAM — costing 50–200 ns. On a machine processing 1 million messages per second, a 1% TLB miss rate adds hundreds of nanoseconds to the average latency.

## Huge pages: the fix

Instead of 4K pages, the OS can back memory with 2MB pages (or 1GB pages). With 2MB pages:

| TLB level | Entries          | Coverage at 2MB pages |
| --------- | ---------------- | --------------------- |
| L1 DTLB   | 32 entries (2MB) | **64 MB**             |
| L2 TLB    | 1,024 entries    | **2 GB**              |

A 64-entry 2MB TLB covers 64 MB — enough for an entire order book, a ring buffer, and a strategy's working set in fewer TLB entries than 4K pages needed for 256 KB. TLB coverage scales by 512× for the same number of entries.

## Allocating huge pages explicitly

```cpp
#include <sys/mman.h>
#include <cstddef>
#include <stdexcept>
#include <cstdio>

// Allocate size bytes backed by 2MB huge pages
// size must be a multiple of 2MB = 2 * 1024 * 1024
void* alloc_huge(size_t size) {
    // MAP_HUGETLB requests 2MB pages; MAP_HUGE_2MB is explicit
    void* p = mmap(nullptr, size,
                   PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB | MAP_HUGE_2MB,
                   -1, 0);
    if (p == MAP_FAILED) {
        // Fallback: system may have no huge pages reserved.
        // Reserve with: echo 512 > /proc/sys/vm/nr_hugepages
        throw std::runtime_error{"mmap MAP_HUGETLB failed — check nr_hugepages"};
    }
    return p;
}

void free_huge(void* p, size_t size) {
    munmap(p, size);
}

// Usage: back the order book's price arrays with huge pages
static constexpr size_t HUGE = 2 * 1024 * 1024;
static constexpr size_t BOOK_SIZE = 4 * HUGE;  // 8 MB, 4 huge pages

struct alignas(64) OrderBook {
    void init() {
        // Allocate all price-level arrays in one huge-page mapping
        _backing = alloc_huge(BOOK_SIZE);
        // Place arrays within the backing store
        bid_prices = reinterpret_cast<int64_t*>(_backing);
        ask_prices = bid_prices + MAX_LEVELS;
        bid_sizes  = reinterpret_cast<int32_t*>(ask_prices + MAX_LEVELS);
        ask_sizes  = bid_sizes + MAX_LEVELS;
    }

    static constexpr int MAX_LEVELS = 65536;
    int64_t* bid_prices{};
    int64_t* ask_prices{};
    int32_t* bid_sizes{};
    int32_t* ask_sizes{};
private:
    void* _backing{};
};
```

Verify huge-page backing after allocation:

```bash
# Find the virtual address range of your process's huge-page mapping
grep -A4 'AnonHugePages' /proc/<pid>/smaps | grep -B4 'AnonHugePages: [^0]'
# AnonHugePages: 8192 kB means 4 × 2MB huge pages are in use.

# Check how many huge pages are available system-wide
cat /proc/sys/vm/nr_hugepages          # pre-allocated huge pages
cat /proc/sys/vm/nr_free_hugepages     # available right now

# Reserve 256 × 2MB = 512 MB of huge pages (run as root or with CAP_SYS_ADMIN)
echo 256 > /proc/sys/vm/nr_hugepages

# Pin them permanently across reboots (add to /etc/sysctl.conf):
# vm.nr_hugepages = 256
```

## Transparent Huge Pages: the trade-off

Linux Transparent Huge Pages (THP) automatically promotes contiguous 4K page groups to 2MB pages without explicit `MAP_HUGETLB`. This sounds like a free win, but THP has a fatal flaw for latency-critical processes:

**THP promotion happens asynchronously, in the background, and causes page-table rescans during promotion that introduce latency spikes of tens of microseconds.** The khugepaged kernel daemon wakes periodically, finds candidate regions, locks the page table, and promotes them — during which your strategy thread can be briefly stalled.

For HFT:

| Method                   | Latency impact                                  | When to use                                    |
| ------------------------ | ----------------------------------------------- | ---------------------------------------------- |
| `MAP_HUGETLB` (explicit) | None at runtime — pages are pre-allocated       | Order book, ring buffers, hot-path allocations |
| THP (transparent)        | Rare multi-microsecond spikes during promotion  | Background allocations, off-path data          |
| THP disabled             | No promotion spikes; high TLB pressure possible | When explicit huge pages cover all hot data    |

Production HFT processes typically disable THP (`echo never > /sys/kernel/mm/transparent_hugepage/enabled`) and manually back every hot-path allocation with explicit `MAP_HUGETLB`.

## When huge pages don't help

Huge pages reduce TLB pressure only when the working set is large enough that TLB entries are the constraint. If your entire order book fits in the L1 TLB's 256 KB coverage at 4K pages (64 entries × 4K), adding huge pages offers no benefit and consumes physically contiguous memory unnecessarily. Profile first:

```bash
perf stat -e dTLB-load-misses,dTLB-loads ./strategy
# If dTLB-load-misses / dTLB-loads > 0.001 (0.1%), TLB pressure is real.
```

## Worked task

Explain how a hypothetical 512-entry TLB covers memory with 4 KiB pages versus 2 MiB pages. Calculate both coverages and explain why exceeding coverage does not imply every access misses or that huge pages always improve latency.

<details>
<summary>Reveal a worked answer</summary>

512 times 4 KiB is 2 MiB; 512 times 2 MiB is 1 GiB. These figures assume the stated entry count applies to that page size, which is not universal hardware behavior. Actual miss rate depends on access locality, associativity, other translation levels, and competing mappings. Huge pages can reduce translation pressure but have allocation and memory-management costs. Measure the intended workload and actual page sizes rather than infer a guaranteed improvement from coverage arithmetic.

</details>

Does a working set larger than a TLB's coverage force every repeated access to miss?
