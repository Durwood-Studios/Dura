## Why this matters

You have a struct for a <VocabTooltip slug="limit-order-book">limit order</VocabTooltip> quote — a bid price, an ask price, a bid size, and an ask size. You keep an array of 1,000 of them, one per tracked symbol. Every 100 microseconds, your pricing model iterates that array and computes the mid-price for each symbol.

You write the obvious loop. It feels fast. But on a profiler, that loop is slow. Not "a little slow" — it is burning three times the cycles the math requires. The prices are all there. The cache should be warm. So where is the time going?

It is going into cache lines you loaded but never used. The struct holds four fields. When you read the bid price of symbol 0, the CPU pulls in 64 bytes — a full cache line. But you only use 8 of those bytes (the bid price). The other 56 bytes — ask price, bid size, ask size — arrive in the same load and sit unused in the cache line, displacing something else that was useful. Your cache is full of data you never touched.

<VocabTooltip slug="structure-of-arrays">Structure-of-arrays</VocabTooltip> is the fix.

## Start with something familiar

Reading only the price column is easier when prices occupy consecutive pages rather than being interleaved with unrelated customer details.

## The mental model

> Structure-of-arrays groups the fields a scan needs, while array-of-structs groups the fields of one record. Useful memory traffic depends on the actual access pattern and layout.

## The two layouts

Consider this quote struct:

```cpp
// AoS: Array-of-Structs (the intuitive layout)
struct Quote {
    int64_t bid_price;  // 8 bytes
    int64_t ask_price;  // 8 bytes
    int32_t bid_size;   // 4 bytes
    int32_t ask_size;   // 4 bytes
};                      // 24 bytes total

Quote quotes[1024];     // 24,576 bytes
```

In memory, this lays out as:

```
[bid0|ask0|bsz0|asz0] [bid1|ask1|bsz1|asz1] [bid2|ask2|bsz2|asz2] ...
 ← 24 bytes ──────→    ← 24 bytes ──────→    ← 24 bytes ──────→
```

A 64-byte cache line spans roughly 2.6 quotes. When you load `quotes[0].bid_price`, you also pull in `quotes[0].ask_price`, `quotes[0].bid_size`, `quotes[0].ask_size`, and a fraction of `quotes[1]`.

If the loop only touches `bid_price`, two-thirds of every loaded cache line is wasted bandwidth.

Now the SoA transformation:

```cpp
// SoA: Structure-of-Arrays
struct QuoteBook {
    int64_t bid_price[1024];  // 8,192 bytes
    int64_t ask_price[1024];  // 8,192 bytes
    int32_t bid_size[1024];   // 4,096 bytes
    int32_t ask_size[1024];   // 4,096 bytes
};

QuoteBook book;
```

In memory, all 1,024 bid prices are contiguous:

```
[bid0|bid1|bid2|bid3|bid4|bid5|bid6|bid7] ...
 ← one 64-byte cache line has 8 bid prices →
```

When the mid-price loop loads `book.bid_price[0]`, it gets `bid_price[0]` through `bid_price[7]` in one cache line. Every byte of the load is useful. The loop processes 8× more data per cache miss.

## The mid-price loop: AoS vs SoA

```cpp
// AoS version — poor cache utilization
void compute_mids_aos(const Quote* quotes, int64_t* mids, int n) {
    for (int i = 0; i < n; ++i) {
        mids[i] = (quotes[i].bid_price + quotes[i].ask_price) / 2;
    }
}
// Each iteration: load 24-byte struct (touches 2 cache lines for alignment reasons),
// use 16 bytes, discard 8 bytes of size data.
// The compiler cannot vectorize this because the two fields are interleaved.

// SoA version — full cache utilization + auto-vectorization
void compute_mids_soa(const QuoteBook& book, int64_t* mids, int n) {
    for (int i = 0; i < n; ++i) {
        mids[i] = (book.bid_price[i] + book.ask_price[i]) / 2;
    }
}
// Each iteration: bid_price and ask_price are separate contiguous arrays.
// GCC/Clang vectorize this with AVX2 automatically: 4 mids per cycle.
// Cache lines are 100% utilized.
```

Force the compiler to tell you what it did:

```bash
# GCC vectorization report
g++ -O3 -mavx2 -fopt-info-vec-optimized mids.cpp -o mids 2>&1 | grep vectorized

# Clang vectorization report
clang++ -O3 -mavx2 -Rpass=loop-vectorize mids.cpp -o mids
```

Under AoS, the interleaved layout prevents auto-vectorization — the compiler cannot generate a contiguous SIMD load because bid_price and ask_price do not form a contiguous array. Under SoA, both fields are contiguous arrays and the loop vectorizes automatically with no intrinsics required.

## When AoS is correct

SoA is not always faster. The transformation has a cost when your access pattern touches all fields of one element together.

| Access pattern                                             | Better layout |
| ---------------------------------------------------------- | ------------- |
| Process one field across all elements                      | SoA           |
| Process all fields of one element                          | AoS           |
| SIMD/vectorized computation over one field                 | SoA           |
| Single-element lookup (e.g. "get the full quote for AAPL") | AoS           |

For a quote book where updates arrive one symbol at a time (ITCH Add/Execute/Cancel), but pricing loops process all symbols together, you often need **both**: AoS for the update path (write all fields of one element), SoA for the computation path. The solution is to keep the authoritative store in AoS and maintain a SoA mirror for the computation path, flushed after each update batch.

```cpp
struct QuoteBook {
    // AoS store for individual updates — O(1) random access
    Quote     quotes[1024];

    // SoA mirror for vectorized computation — refreshed in batch
    int64_t   bid_price_vec[1024];
    int64_t   ask_price_vec[1024];

    void flush_to_soa(int count) {
        for (int i = 0; i < count; ++i) {
            bid_price_vec[i] = quotes[i].bid_price;
            ask_price_vec[i] = quotes[i].ask_price;
        }
        // Compiler vectorizes this gather automatically
    }
};
```

The flush is a <VocabTooltip slug="gather-load">gather</VocabTooltip> — reading strided elements from the AoS array and writing them densely into the SoA mirror. It is not free, but if you run the pricing loop thousands of times per second and update individual quotes hundreds of times per second, the flush cost amortizes.

## Measuring the difference

```cpp
#include <chrono>
#include <cstdint>
#include <numeric>

static constexpr int N = 1024;

// AoS
struct Quote { int64_t bid, ask; };
Quote q_aos[N];

// SoA
struct QuoteSoA { int64_t bid[N], ask[N]; } q_soa;

int64_t bench_aos() {
    int64_t sum = 0;
    auto t0 = std::chrono::steady_clock::now();
    for (int iter = 0; iter < 100'000; ++iter)
        for (int i = 0; i < N; ++i)
            sum += (q_aos[i].bid + q_aos[i].ask) >> 1;
    auto t1 = std::chrono::steady_clock::now();
    auto ns = std::chrono::duration_cast<std::chrono::nanoseconds>(t1 - t0).count();
    // ns / (100'000 * N) = ns per mid computation
    (void)ns;
    return sum;
}

int64_t bench_soa() {
    int64_t sum = 0;
    auto t0 = std::chrono::steady_clock::now();
    for (int iter = 0; iter < 100'000; ++iter)
        for (int i = 0; i < N; ++i)
            sum += (q_soa.bid[i] + q_soa.ask[i]) >> 1;
    auto t1 = std::chrono::steady_clock::now();
    auto ns = std::chrono::duration_cast<std::chrono::nanoseconds>(t1 - t0).count();
    (void)ns;
    return sum;
}
```

On a Skylake-X machine with warm cache, SoA is typically 3–5× faster for this pattern. The gap is larger as N grows (more cache pressure) and smaller as N shrinks (the whole AoS array fits in L1).
