## Why this matters

An order-management system can create many objects under load. General-purpose allocation cost depends on the allocator, thread behavior, object sizes, and memory state. A bounded pool can make storage policy explicit, but it needs correct lifetime handling and measured performance.

One design option is to reserve bounded storage during initialization and reuse it. Define exhaustion and reclamation instead of assuming unlimited capacity or zero runtime work.

## Start with something familiar

A numbered set of reusable workstations needs a checkout ledger so nobody reuses a station while its previous worker still owns it.

## The mental model

> A bounded object pool combines storage with an ownership and lifetime protocol. Reusing an address does not make stale handles valid, and exhaustion must have an explicit result.

## The arena allocator

The simplest correct allocator is a bump-pointer arena: a large contiguous block of memory with a pointer that advances forward with each allocation. Deallocation is a no-op; the entire arena is freed at once.

```cpp
#include <cstddef>
#include <memory>
#include <new>
#include <utility>
// Single-threaded raw storage; all live objects must end before reset.
class Arena {
public:
    explicit Arena(std::size_t capacity)
        : storage_(std::make_unique<std::byte[]>(capacity)), capacity_(capacity) {}
    Arena(const Arena&) = delete;
    Arena& operator=(const Arena&) = delete;
    [[nodiscard]] void* alloc(std::size_t size,
        std::size_t alignment = alignof(std::max_align_t)) noexcept {
        if (size == 0 || alignment == 0 || (alignment & (alignment - 1)) != 0)
            return nullptr;
        if (size > capacity_ - cursor_) return nullptr;
        void* candidate = storage_.get() + cursor_;
        std::size_t space = capacity_ - cursor_;
        if (!std::align(alignment, size, candidate, space)) return nullptr;
        cursor_ = static_cast<std::byte*>(candidate) - storage_.get() + size;
        return candidate;
    }
    void reset() noexcept { cursor_ = 0; }
    std::size_t used() const noexcept { return cursor_; }
    std::size_t remaining() const noexcept { return capacity_ - cursor_; }
private:
    std::unique_ptr<std::byte[]> storage_;
    std::size_t capacity_;
    std::size_t cursor_ = 0;
};
template<class T, class... Args>
T* arena_new(Arena& arena, Args&&... args) {
    void* storage = arena.alloc(sizeof(T), alignof(T));
    if (!storage) throw std::bad_alloc{};
    return ::new (storage) T(std::forward<Args>(args)...);
}
```

Arenas are useful when objects share a clear lifetime boundary. Reset only after required destructors have run and no outstanding users remain. Alignment padding and reserved but unused storage still consume capacity, and contiguous allocation does not guarantee ideal cache or TLB behavior.

## The typed object pool

This single-threaded bounded pool returns a slot-and-generation handle. Access through get(handle), then release through free(handle). A generation mismatch rejects stale releases. Slot bookkeeping is constant time; constructing or destroying T has its own cost, and a T that allocates internally can still use the heap.

When objects have non-trivial lifetimes — orders that arrive and are cancelled at different times — a bump-pointer arena does not suffice. You need a pool that supports individual deallocation while keeping objects contiguous and avoiding malloc:

```cpp
#include <array>
#include <cstddef>
#include <cstdint>
#include <limits>
#include <optional>
#include <utility>
// Single-threaded pool: handles identify lifetimes, not merely addresses.
template<class T, std::size_t Capacity>
class ObjectPool {
    static_assert(Capacity > 0);
public:
    struct Handle { std::size_t slot; std::uint64_t generation; };
    ObjectPool() {
        for (std::size_t index = 0; index < Capacity; ++index) next_[index] = index + 1;
    }
    ObjectPool(const ObjectPool&) = delete;
    ObjectPool& operator=(const ObjectPool&) = delete;
    template<class... Args>
    std::optional<Handle> alloc(Args&&... args) {
        if (head_ == Capacity) return std::nullopt;
        const auto slot = head_;
        values_[slot].emplace(std::forward<Args>(args)...);
        // If construction throws, the free list is still unchanged.
        head_ = next_[slot];
        return Handle{slot, generations_[slot]};
    }
    T* get(Handle handle) noexcept {
        if (handle.slot >= Capacity || !values_[handle.slot] ||
            generations_[handle.slot] != handle.generation) return nullptr;
        return &*values_[handle.slot];
    }
    bool free(Handle handle) noexcept {
        if (!get(handle)) return false;
        values_[handle.slot].reset();
        if (generations_[handle.slot] == std::numeric_limits<std::uint64_t>::max())
            return true; // Retire this slot rather than wrap and accept an ancient handle.
        ++generations_[handle.slot];
        next_[handle.slot] = head_;
        head_ = handle.slot;
        return true;
    }
    bool empty() const noexcept { return head_ == Capacity; }
private:
    std::array<std::optional<T>, Capacity> values_{};
    std::array<std::uint64_t, Capacity> generations_{};
    std::array<std::size_t, Capacity> next_{};
    std::size_t head_ = 0;
};
```

The optional values and bookkeeping occupy bounded arrays inside the pool. Their footprint includes alignment, occupancy state, generations, and free-list entries; it is larger than Capacity times sizeof(T). Stale handles are rejected, while a returned pointer must not be retained past a release.

## std::pmr: wiring pool allocators into standard containers

C++17's `std::pmr` (polymorphic memory resources) lets you plug custom allocators into `std::vector`, `std::list`, `std::unordered_map`, and other containers without template gymnastics:

```cpp
#include <memory_resource>
#include <vector>
#include <array>
#include <cstdint>

// Pre-allocated 8 MB backing buffer — no malloc at all
alignas(64) std::array<std::byte, 8 * 1024 * 1024> buf;

// monotonic_buffer_resource is the std::pmr equivalent of Arena
std::pmr::monotonic_buffer_resource mono_res{buf.data(), buf.size(),
    std::pmr::null_memory_resource()}; // exhaustion throws instead of using an upstream heap

// Use it with a standard container
std::pmr::vector<int64_t> prices{&mono_res};  // uses buf, not the global heap
prices.reserve(65536);                          // no malloc — allocates from buf

// A single-threaded pool resource can reuse allocations by size:
std::pmr::unsynchronized_pool_resource pool_res{&mono_res};
// unsynchronized = single-threaded; pool_res does not lock
std::pmr::vector<void*> active_orders{&pool_res}; // illustrative pointer slots
```

`monotonic_buffer_resource` can obtain more storage from its upstream resource when its initial buffer fills. This example supplies null_memory_resource to reject that growth. Its allocations and the pool resource still have bookkeeping costs; measure rather than claim a fastest possible allocator.
