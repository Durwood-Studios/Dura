## Why this matters

You have two threads. One receives market-data packets off the wire and writes them into a buffer. The other reads from that buffer and runs your strategy. The obvious tool — a `std::mutex` — is forbidden here, because a thread that blocks on a contended lock can be put to sleep by the kernel for microseconds, and microseconds are the entire game. So you reach for a lock-free queue.

Then it works in testing, ships to production, and one day a price field reads as garbage — but only on the ARM-based colo box, never on your x86 laptop. The packet was written. The reader saw the "ready" flag. The price was still stale. Nothing in your code is "wrong" in the line-by-line sense. The bug lives in a layer most programmers never look at: the rules that say _when one thread's writes become visible to another thread, and in what order_. That layer is the C++ memory model, and this lesson is how you stop being afraid of it.

## Start with something familiar

A sealed handoff needs both a completed package and a rule telling the receiver when opening it is safe.

## The mental model

> Release and acquire operations can establish visibility of preceding writes when the acquire observes the appropriate release. Atomic flags alone do not make unrelated non-atomic payload accesses safe.

## First principles: a write is not an event with a time

Picture two people editing a shared document, each on their own laptop, syncing over a flaky connection. Person A types a paragraph, then ticks a checkbox that says "paragraph done." Person B is watching the checkbox. The instant it ticks, B starts reading the paragraph.

The trap: there is no global clock. B's laptop might receive the checkbox-tick _before_ it receives the paragraph text. From B's view the checkbox is on but the paragraph is empty. Nothing is broken — the two changes propagated in a different order than A made them.

A multicore CPU is exactly this. Each core has its own store buffer and cache. When core A writes the price and then writes the "ready" flag, core B is allowed to observe those two writes **in the opposite order**, unless something forces an ordering. The compiler is allowed to reorder them before the CPU even sees them. The hardware is allowed to reorder them after. "It happened first in the source code" buys you nothing across threads.

A <VocabTooltip slug="data-race">data race</VocabTooltip> is when two threads access the same memory location, at least one access is a write, and nothing orders them. In C++ a data race is not "you might read a stale value." It is **undefined behavior** — the standard places no constraint on what your program does. The compiler may have assumed the race could not happen and optimized accordingly. So the first job is never to read or write shared mutable data with a plain `int`.

## The mental model

> **An `std::atomic` write is more than indivisible — it is a synchronization point that can carry an ordering promise with it.** Picture every shared write as a package and every shared read as a delivery. `memory_order` is the shipping class you pay for: `relaxed` ships the package alone with no guarantee about anything else in the truck; `release`/`acquire` is a sealed pallet — when the reader takes delivery of the `release` write, _everything that was on the truck before it_ is guaranteed to have arrived too.

Hold that image. The entire correctness of a lock-free queue is one `release` write on the producer paired with one `acquire` read on the consumer, forming a guarantee the standard calls _happens-before_.

## The mechanism: std::atomic and memory_order

`std::atomic<T>` (from `<atomic>`) gives you operations that are indivisible — no torn reads, no torn writes — and that take a `std::memory_order` argument controlling how the operation orders the _other, non-atomic_ memory around it.

There are five orderings you need. Here they are with their actual, standard-defined meaning — no approximations:

```cpp
#include <atomic>

std::atomic<int> flag{0};
int payload = 0;  // plain, non-atomic — shared, but protected by the atomic

// memory_order_relaxed:
//   Atomicity only. No ordering w.r.t. any other memory operation.
//   Use when the value is independent of everything else (e.g. a counter
//   you only read after all threads join).
flag.store(1, std::memory_order_relaxed);
int c = flag.load(std::memory_order_relaxed);

// memory_order_release (store-side):
//   No prior read/write in THIS thread may be reordered after this store.
//   It "publishes" everything written before it.
payload = 42;                                // (1) write the data
flag.store(1, std::memory_order_release);    // (2) publish — (1) cannot move after (2)

// memory_order_acquire (load-side):
//   No subsequent read/write in THIS thread may be reordered before this load.
//   If it reads a value written by a release store, it "receives" everything
//   that release published.
if (flag.load(std::memory_order_acquire) == 1) {  // (3) receive
    int v = payload;                              // (4) guaranteed to see 42 — (4) cannot move before (3)
}

// memory_order_acq_rel:
//   For read-modify-write ops (fetch_add, exchange, compare_exchange).
//   Acts as acquire on the load half AND release on the store half.

// memory_order_seq_cst (the default):
//   Everything acq_rel gives, PLUS a single total order over all seq_cst
//   operations that every thread agrees on. The strongest and the slowest.
```

When an acquire operation observes the appropriate release, preceding writes are ordered before the receiving thread's subsequent accesses through happens-before. This is a standard publication pattern, not a blanket protection for unrelated accesses or future overwrites. Relaxed atomics alone do not publish non-atomic payloads safely.

A crucial subtlety: release-acquire only synchronizes the two threads that touch _that specific atomic with those orderings_. It does **not** impose a single global order that all threads agree on — that is the extra, more expensive thing <VocabTooltip slug="memory-order-seq-cst">`seq_cst`</VocabTooltip> buys. For a producer handing to one consumer, you never need the global order, so paying for `seq_cst` is wasted cycles (it inserts a full barrier — `mfence` on x86, `dmb ish` on ARM).

Why the ARM-only bug from the opening: x86 has a strongly-ordered memory model where ordinary stores already behave almost like release stores, so a buggy queue using `relaxed` where it needed `release` _appears_ to work. ARM (and POWER) are weakly ordered — they actually reorder — so the same code corrupts data. The memory model is the contract; the hardware decides how much slack it takes.

## Building a correct SPSC ring buffer

A <VocabTooltip slug="spsc-ring-buffer">single-producer/single-consumer (SPSC) ring buffer</VocabTooltip> is the canonical lock-free structure for one thread feeding another. Exactly one thread calls `push`, exactly one calls `pop`. That constraint is what lets us avoid the read-modify-write atomics entirely — each index is written by only one thread.

The invariant: the buffer is empty when `head == tail`, full when advancing `tail` would collide with `head`. The producer owns `tail`, the consumer owns `head`. The only cross-thread communication is the two atomic indices.

```cpp
#include <atomic>
#include <cstddef>
#include <optional>
#include <array>

template <typename T, std::size_t Capacity>
class SpscRing {
    // One slot is always left empty so head == tail unambiguously means "empty"
    // (not "full"). So usable capacity is Capacity - 1.
    static_assert((Capacity & (Capacity - 1)) == 0, "Capacity must be a power of two");

    std::array<T, Capacity> buffer_{};

    // Producer writes tail_, consumer reads it. Consumer writes head_,
    // producer reads it. Each index has exactly one writer thread.
    alignas(64) std::atomic<std::size_t> head_{0};  // next slot to read
    alignas(64) std::atomic<std::size_t> tail_{0};  // next slot to write
    // alignas(64): keep head_ and tail_ on separate cache lines so the two
    // threads don't false-share. (Phase Q lesson q-3 — false sharing.)

    static constexpr std::size_t mask = Capacity - 1;

public:
    // Called by the PRODUCER thread only.
    bool push(const T& item) {
        // We own tail_. relaxed load is fine — no other thread writes it.
        const std::size_t tail = tail_.load(std::memory_order_relaxed);
        const std::size_t next = (tail + 1) & mask;

        // Read the consumer's head with ACQUIRE: we must see the consumer's
        // most recent progress so we don't overwrite a slot it hasn't read.
        if (next == head_.load(std::memory_order_acquire)) {
            return false;  // full
        }

        buffer_[tail] = item;  // (A) write the payload into the slot

        // RELEASE publishes (A): when the consumer's acquire-load of tail_
        // observes this new value, it is guaranteed to see buffer_[tail].
        tail_.store(next, std::memory_order_release);
        return true;
    }

    // Called by the CONSUMER thread only.
    std::optional<T> pop() {
        // We own head_. relaxed load — no other thread writes it.
        const std::size_t head = head_.load(std::memory_order_relaxed);

        // ACQUIRE on tail_: if it pairs with the producer's release store,
        // we are guaranteed to see the payload write (A) it published.
        if (head == tail_.load(std::memory_order_acquire)) {
            return std::nullopt;  // empty
        }

        T item = buffer_[head];  // (B) safe to read — happens-after the release

        // RELEASE publishes that this slot is free, so the producer's
        // acquire-load of head_ sees the slot is reusable.
        head_.store((head + 1) & mask, std::memory_order_release);
        return item;
    }
};
```

Walk the happens-before edge, because it is the whole lesson:

1. Producer writes `buffer_[tail] = item` — step **(A)**, a plain write.
2. Producer does `tail_.store(next, release)` — this _publishes_ (A).
3. Consumer does `tail_.load(acquire)` and reads `next` (the value the producer stored in step 2).
4. Because the acquire read observed the release store's value, **(A) happens-before (B)**. The consumer's `buffer_[head]` read at step **(B)** is guaranteed to see `item`, not stale memory.

Remove the ordering — make both `relaxed` — and step 4 evaporates. On x86 it might still pass. On ARM, step (B) can read the slot _before_ (A)'s write has propagated, and you get the garbage-price bug. The `release`/`acquire` pair is not decoration; it is the proof.

Why `relaxed` is correct for the producer's load of its _own_ `tail_`: only the producer writes `tail_`, so there is no inter-thread ordering to establish — the program order within one thread already guarantees the producer sees its own latest write.

## When you do need read-modify-write: compare_exchange and the ABA problem

SPSC dodges the hard part because each index has one writer. The moment you have multiple producers or multiple consumers, two threads race to update the same index, and you need an atomic <VocabTooltip slug="compare-exchange">read-modify-write</VocabTooltip>: `compare_exchange_weak(expected, desired)`. It atomically checks "does this atomic still equal `expected`? If so, set it to `desired` and return true; otherwise load the current value into `expected` and return false." The classic loop:

```cpp
std::atomic<Node*> head_;

void push(Node* new_node) {
    Node* old_head = head_.load(std::memory_order_relaxed);
    do {
        new_node->next = old_head;
        // Try to swing head_ from old_head to new_node. If another thread
        // changed head_ since our load, CAS fails, refreshes old_head, retry.
    } while (!head_.compare_exchange_weak(
        old_head, new_node,
        std::memory_order_release,   // on success: publish new_node->next
        std::memory_order_relaxed)); // on failure: only a retry, no publish
}
```

Now the danger. The <VocabTooltip slug="aba-problem">ABA problem</VocabTooltip>: `compare_exchange` only checks that the _value_ is unchanged, not that _nothing happened_. Suppose the head pointer is `A`. Thread 1 reads `A`, then stalls. Thread 2 pops `A` (head now `B`), pops `B` (head now `C`), frees `A`, then allocates a new node that the allocator happens to place at the _same address_ `A`, and pushes it (head now `A` again). Thread 1 wakes up, runs its `compare_exchange`: head still equals `A`, so it succeeds — and splices in a `next` pointer computed from a structure that no longer exists. The value matched; the world underneath it did not.

Two real mechanisms defeat ABA:

- **Tagged pointers / version counters.** Pack a monotonically increasing counter alongside the pointer in one atomically-swappable word (e.g. `std::atomic<TaggedPtr>` where `TaggedPtr` is `{pointer, uint64 tag}`). Every successful CAS bumps the tag, so even if the pointer recycles to `A`, the tag differs and the stale CAS fails. This needs a double-width CAS (x86-64: `cmpxchg16b`).
- **Deferred reclamation** so a node's memory is never reused while another thread might still hold a pointer to it: hazard pointers (each thread publishes the pointers it is currently using; memory is freed only once no hazard pointer references it) or epoch-based reclamation / RCU.

SPSC ring buffers sidestep ABA entirely — there is no shared pointer being CAS'd, only two single-writer indices — which is exactly why HFT hot paths prefer them when the topology allows.

## Lock-free is not wait-free

These terms are precise progress guarantees, not vibes:

- <VocabTooltip slug="lock-free">**Lock-free**</VocabTooltip>: at least *one* thread makes progress
  in a bounded number of steps, system-wide. No thread can be blocked by another holding a lock
  (there are no locks). But an individual thread can be starved indefinitely — its
  `compare_exchange` can fail forever because others keep winning.
- <VocabTooltip slug="wait-free">**Wait-free**</VocabTooltip>: *every* thread completes its
  operation in a bounded number of its own steps, regardless of what other threads do. No
  starvation, ever. Strictly stronger and strictly harder to build.
- <VocabTooltip slug="obstruction-free">**Obstruction-free**</VocabTooltip>: the weakest — a thread
  completes in bounded steps *if it runs in isolation* (other threads paused). The CAS-loop `push`
  above is lock-free by definition: whenever a thread's `compare_exchange` fails, it failed
  precisely because some other thread's CAS succeeded, so the system as a whole always makes
  progress in a bounded number of steps. Lock-freedom is strictly stronger than obstruction-freedom,
  so the push trivially satisfies obstruction-freedom too — but it is **not** wait-free, because an
  individual thread can lose the race an unbounded number of times.

A CAS-loop algorithm can provide lock-free system-wide progress while one participant repeatedly loses a race. The bounded SPSC algorithm has no source-level retry loop, but a wait-free implementation claim also depends on its atomic primitives and payload operations. Bounded abstract steps are not a wall-clock latency guarantee under preemption, interrupts, or hardware delays.
