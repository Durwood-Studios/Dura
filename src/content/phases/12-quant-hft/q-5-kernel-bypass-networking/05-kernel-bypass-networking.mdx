## Why this matters

You have written a strategy that decides in 200 nanoseconds. You have a lock-free SPSC ring (Lesson Q4) handing market-data events to it with no contention. Then you measure end to end and the number is 8 microseconds, not 200 nanoseconds. The other 7.8 microseconds vanished somewhere between the wire and your code.

They vanished inside the operating system. A packet arriving on the network card does not appear in your program — it appears in the kernel, which interrupts a CPU, copies the bytes, walks the TCP/IP stack, wakes your process, and only then lets `recv()` hand you the data. Every one of those steps costs time, and for a venue where a fill depends on single-digit microseconds, that overhead is the difference between trading and watching. This lesson explains where the time goes and the two families of fixes the industry uses: full kernel bypass (DPDK) and the lighter-weight alternatives (io_uring, AF_XDP).

## Start with something familiar

One delivery system hands batches to the existing sorting office; another operates its own sorting machinery and inherits the responsibilities that office handled.

## The mental model

> io_uring coordinates I/O with the kernel through shared submission and completion structures. Poll-mode kernel-bypass designs move more packet handling into user space and change ownership, resource, and operational requirements.

## First principles — what happens to a packet on Linux today

Start from the normal path, the one every socket program you have ever written uses. A packet lands on the network interface card — the **NIC**, the hardware that connects the machine to the network. On stock Linux, four things then happen before your code runs:

1. **Notification and polling.** Linux networking commonly combines hardware notification with polling mechanisms such as NAPI. An interrupt enters a handler; that transition is not necessarily a scheduler switch to another process. Do not assume one full interrupt and process switch for every packet.

2. **The copy.** The kernel receives the packet into kernel memory, then later copies it into your process's memory when you call `recv()`. That is one full pass over the bytes that does no useful work — pure data movement across the kernel/user boundary.

3. **Protocol processing.** The kernel walks the packet up the stack: Ethernet, then IP, then TCP or UDP. It checks checksums, reassembles segments, manages connection state. For TCP this is substantial bookkeeping. (Computer Networking, prerequisite `5-2-computer-networking`, covers what these layers do — here we care only that processing them takes time.)

4. **The system call.** Your program asks for the data with `recv()`, which is a **system-call** — a controlled transition from your unprivileged user-mode code into the privileged kernel. Crossing that boundary, and crossing back, costs time on every call, and modern CPU mitigations for speculative-execution vulnerabilities made it more expensive than it once was.

The kernel works hard to soften some of this. **Interrupt-coalescing** lets the NIC batch several packets behind a single interrupt instead of one interrupt per packet, trading a little latency for far less CPU overhead under load. NAPI switches the kernel from interrupt-driven to polling under high traffic. These help throughput. They do not get you to the latency floor an HFT path needs, because the architecture still routes every packet through the kernel, a copy, and a syscall.

## The mental model

> **The kernel network stack is a shared, general-purpose, safe intermediary between your code and the wire. Kernel bypass deletes the intermediary: the application talks to the NIC directly, trading the kernel's safety and sharing for the raw speed of a dedicated, single-purpose path.** Everything in this lesson is a point on the spectrum between "let the kernel do it" and "do it all yourself."

Hold that picture. DPDK is the far "do it all yourself" end. io_uring and AF_XDP sit in the middle — they keep the kernel involved but remove its most expensive habits.

## Kernel bypass — the idea

**Kernel-bypass** means user-space code reads and writes packets directly to and from the NIC, with the kernel network stack removed from the data path. The packet does not get an interrupt, does not get copied into kernel memory, does not get walked up a TCP/IP stack by the kernel. Your process owns the NIC's queues and reads raw frames straight from hardware.

To make that work, three problems must be solved, and the solutions are the same across every bypass framework:

- **The NIC must be handed to user space.** Linux normally owns the device. Bypass frameworks bind the NIC to a pass-through driver — **VFIO** (the modern, IOMMU-protected choice) or the older **UIO** — that exposes the device's registers and memory to a user process instead of to the kernel's networking driver. This is `uio-vfio` in your vocabulary list: the kernel mechanisms that let user space safely drive a device.

- **The application talks to the NIC through a descriptor ring.** A **descriptor-ring** is a circular array, in memory shared between the NIC and the CPU, of small records ("descriptors") that each point to a buffer. On receive, the NIC writes incoming packets into the buffers and marks the matching descriptors "ready"; the application reads ready descriptors and processes the packets. This is the same ring buffer idea you built in Q4 — a producer (the NIC hardware) and a consumer (your code) sharing a circular array — except here one end is silicon.

- **The packet buffers must use a stable physical address.** The NIC moves data by **DMA** (Direct Memory Access — the device reads and writes RAM itself, without the CPU copying byte by byte), and DMA needs physical addresses that do not move. Bypass frameworks allocate packet buffers from **hugepages** — memory pages of 2 MB or 1 GB instead of the usual 4 KB — which reduces TLB pressure (fewer page-table entries to cache) and gives large, pinned, physically contiguous regions the NIC can DMA into safely. **Zero-copy** falls out of this: the NIC DMAs the packet once into a hugepage buffer your code already owns, and your code reads it in place. There is no second copy across a kernel boundary, because there is no kernel boundary.

## DPDK — polling the NIC directly

DPDK (the Data Plane Development Kit) is the dominant open-source kernel-bypass framework. Its core abstraction is the **poll-mode-driver** (PMD): a user-space NIC driver that does not use interrupts at all. Instead, a CPU core sits in a tight loop asking the NIC "any packets? any packets? any packets?" — **busy-polling**.

This is the trade at the heart of DPDK. There is no interrupt, so there is no interrupt latency and no context switch into the kernel. There is no syscall, so there is no user/kernel transition per packet. The price: **a core spins at 100% CPU forever**, whether packets are arriving or not, because polling means continuously checking. You dedicate a physical core (pinned, isolated from the scheduler) to doing nothing but watching the NIC. For an HFT firm that has decided microseconds are worth more than a core, this is an obvious trade. For a web server handling sporadic traffic, burning a core to poll an idle NIC is wasteful — which is exactly why kernel bypass is a specialist tool, not a default.

Here is a DPDK receive loop. The API names here — `rte_eth_rx_burst`, `rte_mbuf`, `rte_pktmbuf_free` — are **real** DPDK functions; DPDK is a fast-moving project and exact signatures and initialization boilerplate are version-sensitive, so treat this as the shape of a real loop rather than a drop-in program, and check the `rte_ethdev.h` headers for the DPDK version you actually link against.

```c
// dpdk_rx_loop.c — the hot receive path of a DPDK application.
// Conceptual: real DPDK programs add EAL init, port config, and a
// mempool setup before this loop. API per DPDK rte_ethdev.h.
#include <rte_ethdev.h>
#include <rte_mbuf.h>

#define RX_BURST_SIZE 32   // Read up to 32 packets per poll. Batching
                           // amortizes per-call overhead — one function
                           // call drains many packets, not one each.

// This function never returns. It runs on a core that does nothing else.
static void run_rx_loop(uint16_t port_id, uint16_t queue_id) {
    // A burst is a small array of pointers to packet buffers.
    // rte_mbuf is DPDK's packet-buffer struct; it lives in a hugepage
    // mempool the NIC DMAs incoming packets into. No copy happens here.
    struct rte_mbuf *bufs[RX_BURST_SIZE];

    for (;;) {  // Busy-poll forever. This core sits at 100% CPU by design.
        // rte_eth_rx_burst returns the number of packets actually
        // retrieved from the NIC's RX descriptor ring (0 to RX_BURST_SIZE).
        // It is NOT a syscall and does NOT block — it reads the ring and
        // returns immediately, even with nothing waiting.
        const uint16_t n = rte_eth_rx_burst(port_id, queue_id,
                                            bufs, RX_BURST_SIZE);

        if (n == 0) {
            continue;  // Nothing yet. Poll again. (This is the "burn".)
        }

        for (uint16_t i = 0; i < n; i++) {
            // The packet bytes are already in our address space, in the
            // hugepage buffer the NIC DMAed into. rte_pktmbuf_mtod gives
            // a typed pointer to the packet data — zero copies so far.
            const uint8_t *data = rte_pktmbuf_mtod(bufs[i], const uint8_t *);
            const uint16_t len  = rte_pktmbuf_pkt_len(bufs[i]);

            // Hand 'data'/'len' to the parser. In Phase Q this is where a
            // Nasdaq ITCH decoder (Lesson Q6) reads the market-data message
            // straight out of the buffer — no recv(), no kernel, no copy.
            handle_market_data(data, len);

            // We own this buffer. Return it to the mempool so the NIC can
            // reuse it for a future packet. Forgetting this leaks buffers
            // until the pool is exhausted and receive silently stalls.
            rte_pktmbuf_free(bufs[i]);
        }
    }
}
```

Walk the loop against the four kernel costs from the start of the lesson. The interrupt: gone — we poll. The copy: gone — the NIC DMAs into a buffer we already own and we read it in place. Protocol processing: gone from the kernel — if you want UDP, you parse it yourself in `handle_market_data`, which for a fixed market-data feed is a handful of field reads, not a general TCP state machine. The syscall: gone — `rte_eth_rx_burst` reads a memory ring, it does not enter the kernel. Four sources of latency, deleted, in exchange for one core spinning forever.

## When bypass is the wrong answer — io_uring

DPDK is the right tool when you have decided to dedicate hardware to the network path. Many systems want most of the win without dedicating a core or rebuilding their entire I/O model around a NIC they no longer let Linux manage. For them, Linux gained **io_uring** (kernel 5.1, 2019; heavily extended since).

io_uring attacks one specific cost from the list above: the syscall. The classic model is one system call per I/O operation — every `read()`, every `write()`, every `recv()` crosses the user/kernel boundary. io_uring replaces that with two ring buffers shared between your process and the kernel:

- The **submission-queue** (SQ): your code writes I/O requests ("read this socket into this buffer") into a ring the kernel reads.
- The **completion-queue** (CQ): the kernel writes results ("that read finished, here is how many bytes") into a ring your code reads.

Because both rings live in memory shared with the kernel, you can submit many operations and reap many completions while crossing the syscall boundary rarely — or, with the kernel's SQ-poll mode, having a kernel thread poll the submission queue so your submissions cost no syscall at all. The mental model: io_uring turns "ask the kernel one thing, wait, ask again" into "drop a stack of requests on a conveyor belt and pick up the finished ones whenever you like."

```c
// io_uring_submit_recv.c — submit a receive without a per-call syscall.
// Uses liburing, the standard user-space wrapper over the io_uring
// syscalls (io_uring_setup / io_uring_enter). API per liburing headers.
#include <liburing.h>

// 'ring' was set up once at startup with io_uring_queue_init().
// We reuse it for the life of the connection — no per-operation setup.
static void post_recv(struct io_uring *ring, int fd,
                      void *buf, size_t len) {
    // Grab a free slot in the submission queue. This is a memory write
    // into the shared ring — NOT a syscall.
    struct io_uring_sqe *sqe = io_uring_get_sqe(ring);

    // Describe the operation: receive from 'fd' into 'buf'. Still no
    // syscall — we are only filling in a descriptor in shared memory.
    io_uring_prep_recv(sqe, fd, buf, len, 0);

    // io_uring_submit tells the kernel "there are entries to process."
    // With SQ-poll enabled, a kernel thread is already watching the ring
    // and even this call can be elided — submission becomes syscall-free.
    io_uring_submit(ring);
}

// Later, reap completions. We can drain many at once: one trip to the
// completion ring yields every receive the kernel has finished, instead
// of one recv() syscall per packet.
static void drain_completions(struct io_uring *ring) {
    struct io_uring_cqe *cqe;
    unsigned head;
    unsigned count = 0;

    // io_uring_for_each_cqe walks the completion ring in shared memory.
    io_uring_for_each_cqe(ring, head, cqe) {
        if (cqe->res < 0) {
            // Negative result is -errno. Handle the error explicitly —
            // a silently dropped completion is a hung connection later.
            handle_recv_error(-cqe->res);
        } else {
            // cqe->res is the byte count received into the buffer we
            // posted. Process it, then we must mark this CQE seen below.
            handle_received_bytes((size_t)cqe->res);
        }
        count++;
    }
    // Advance the ring past everything we consumed, in one step.
    io_uring_cq_advance(ring, count);
}
```

io_uring keeps the kernel in the path — it still owns the NIC, still runs the TCP/IP stack, still copies in many configurations. What it removes is the syscall tax and the one-operation-at-a-time blocking model. It is the right tool when you want a large, measurable latency and throughput improvement over `epoll` + `recv` without surrendering the NIC to a bypass framework or burning a dedicated polling core.

## AF_XDP — the middle ground

Between DPDK and io_uring sits **AF_XDP**, a Linux socket address family (added in kernel 4.18) built on **eBPF** and the XDP (eXpress Data Path) hook. **eBPF** is the in-kernel virtual machine that runs small, verified programs at hooks throughout the kernel; XDP is the hook that runs an eBPF program at the earliest possible point on packet receive — in the NIC driver, before the kernel allocates its usual packet structures.

AF_XDP uses XDP to redirect chosen packets straight into a user-space buffer ring, achieving near-DPDK receive performance for those packets while leaving the rest of the NIC's traffic on the normal kernel stack. The trade against DPDK: AF_XDP keeps the NIC under Linux's control (you do not unbind it with VFIO), so the machine stays a normal Linux host — other processes still get networking — at the cost of somewhat higher per-packet overhead than full bypass. It is the pragmatic middle: most of the bypass win, none of the "this NIC no longer belongs to Linux" commitment.

A one-line placement of the three:

```
recv() / epoll     →  io_uring        →  AF_XDP            →  DPDK
kernel does all       kernel does all     kernel driver        user-space
syscall per op        rings, few          XDP-redirects        owns NIC,
                      syscalls            into user ring        polls, burns
                                          (NIC stays Linux)     a core
slowest ───────────────────────────────────────────────────────── fastest
```
