## Why this matters

You have a `Strategy` class that must call a `fill_handler` whenever an execution report arrives. The fill handler is one of three concrete types depending on which execution venue is active — but which one is chosen at startup from configuration, not at compile time. You need to store the handler by value (no owning pointer, no heap) inside `Strategy` and call it with zero overhead on the hot path.

The moment you reach for a `virtual` base class you are paying: a heap allocation to create the polymorphic object, a vtable pointer in every instance, and an indirect branch on every call. `std::function` sidesteps the virtual machinery but may heap-allocate the callable if it does not fit in its internal small buffer. The answer that HFT frameworks converge on is a _custom type-erased wrapper_ — an object that holds a fixed-size buffer (big enough for the largest concrete type), stores function pointers for call/copy/move/destroy in a hand-rolled vtable, and falls back to the heap only for oversized types the author decided were startup-time paths.

## The standard tools and their costs

```cpp
#include <functional>   // std::function, std::move_only_function (C++23)
#include <any>          // std::any

// std::function<void(int)>:
//   - Stores ANY callable: function pointer, lambda, functor, member pointer.
//   - Has a small-buffer: callables fitting in ~48 bytes (implementation-defined)
//     are stored inline with no heap allocation.
//   - Callables LARGER than the buffer go on the heap (one dynamic allocation
//     per construction/copy). This is the latency land mine.
//   - Copyable: captures by copy, the contained callable must be copy-constructible.
//   - The call operator dispatches through a function pointer inside the object,
//     NOT through a vtable — it is one indirect call, same cost as a vtable call.

// std::move_only_function<void(int)> (C++23):
//   - Same idea but requires only movable callables.
//   - Avoids the const correctness gotcha of std::function.
//   - Same SBO trade-off: buffer size is implementation-defined.

// std::any:
//   - Type-erases any CopyConstructible object but provides only type-unsafe
//     retrieval via std::any_cast. Mostly used for configuration, not hot-path dispatch.
```

The critical line is _"callables LARGER than the buffer go on the heap."_ The buffer size is not specified in the standard — it is roughly 24–48 bytes in practice (libstdc++, libc++). A lambda capturing a `std::shared_ptr` and two `std::string` fields will spill to the heap. On a hot path called a million times per second, that is one allocation that poisons your latency tail. The fix is not "use smaller lambdas" — it is _custom type erasure with a buffer you control_.

## Building a minimal type-erased callable

The pattern: allocate a fixed `std::aligned_storage` (or a `char` array with `alignas`) large enough for the target type, construct the callable in that storage with placement new, and store three function pointers — call, move, destroy — in a plain old struct (the hand-rolled vtable).

```cpp
#include <cstddef>
#include <utility>
#include <new>
#include <cassert>
#include <type_traits>

// A type-erased callable that fits callables up to kBufBytes bytes
// inline. Heap-fallback on overflow (never on the hot path if callables
// are sized correctly).
template <typename Sig, std::size_t kBufBytes = 64>
class InlineFunction;   // only the specialisation below is defined

template <typename Ret, typename... Args, std::size_t kBufBytes>
class InlineFunction<Ret(Args...), kBufBytes> {
public:
    InlineFunction() = default;

    // Construct from any callable F.
    // Fails at compile time if F is too large and we want to enforce
    // no-heap. Relax the static_assert to allow a heap fallback.
    template <typename F,
              typename = std::enable_if_t<!std::is_same_v<std::decay_t<F>, InlineFunction>>>
    InlineFunction(F&& f) {
        using DecayF = std::decay_t<F>;
        static_assert(sizeof(DecayF) <= kBufBytes,
            "Callable too large for InlineFunction's inline buffer. "
            "Increase kBufBytes or decompose the lambda.");
        static_assert(alignof(DecayF) <= alignof(std::max_align_t));

        // Construct F in the inline buffer.
        ::new (static_cast<void*>(&buf_)) DecayF(std::forward<F>(f));

        // Write function pointers into the vtable struct.
        vtable_.call    = [](const void* buf, Args... args) -> Ret {
            return (*reinterpret_cast<const DecayF*>(buf))(
                std::forward<Args>(args)...);
        };
        vtable_.move_construct = [](void* dst, void* src) {
            ::new (dst) DecayF(std::move(*reinterpret_cast<DecayF*>(src)));
        };
        vtable_.destroy = [](void* buf) {
            reinterpret_cast<DecayF*>(buf)->~DecayF();
        };
    }

    // Move-construct: copy the vtable struct and move-construct the callable.
    InlineFunction(InlineFunction&& other) noexcept {
        vtable_ = other.vtable_;
        if (vtable_.move_construct)
            vtable_.move_construct(&buf_, &other.buf_);
    }

    ~InlineFunction() {
        if (vtable_.destroy) vtable_.destroy(&buf_);
    }

    // Call: one indirect function pointer — same cost as a virtual dispatch.
    Ret operator()(Args... args) const {
        assert(vtable_.call && "calling an empty InlineFunction");
        return vtable_.call(&buf_, std::forward<Args>(args)...);
    }

    explicit operator bool() const { return vtable_.call != nullptr; }

private:
    // The function-pointer vtable — a plain struct, NOT a class hierarchy.
    struct Vtable {
        Ret  (*call)          (const void*, Args...) = nullptr;
        void (*move_construct)(void* dst, void* src) = nullptr;
        void (*destroy)       (void*)                = nullptr;
    };

    alignas(std::max_align_t) char buf_[kBufBytes]{};
    Vtable vtable_{};
};
```

The cost of calling `operator()`: one load of `vtable_.call`, then one indirect jump through that pointer. This is identical to a virtual call — the difference is that the vtable is per-object (stored inside the `InlineFunction`) rather than per-class (stored in read-only segment). The heap cost for construction is zero for any callable ≤ 64 bytes, which covers virtually all HFT lambdas.

> **Why not just use `std::function`?** For callables that fit in its internal SBO buffer (implementation-defined size, typically 24–48 bytes), `std::function` has the same zero-heap cost and you should use it. Write a custom `InlineFunction` only when (a) you need to control the exact buffer size to guarantee no heap allocation for your specific callable types, (b) you need a move-only wrapper (use `std::move_only_function` in C++23 first), or (c) you need to embed the erased callable directly in a struct that has a fixed layout requirement.

## std::move_only_function (C++23)

C++23 adds `std::move_only_function<Sig>` to `<functional>`. It fixes two `std::function` annoyances for HFT use:

1. **No spurious copy requirement.** `std::function` requires the stored callable to be copyable (because `std::function` itself is copyable). This rules out lambdas capturing `std::unique_ptr` or other move-only state. `std::move_only_function` has no copy constructor, so it can hold any movable callable.
2. **Correct const-propagation.** `std::function::operator()` is `const` but calls the callable non-const — a long-standing correctness problem. `std::move_only_function` ties `const`-ness of the call to the signature.

```cpp
#include <functional>  // std::move_only_function (C++23)
#include <memory>

std::unique_ptr<int> up = std::make_unique<int>(42);

// Captures a unique_ptr — not copyable, but movable.
std::move_only_function<int()> fn =
    [p = std::move(up)]() { return *p; };   // OK with move_only_function

// std::function<int()> fn = [p = std::move(up)]() { return *p; };
// ^^^ compile error: lambda not CopyConstructible
```

On the hot path, prefer `std::move_only_function` over `std::function` when you need move-only callables. The SBO semantics are implementation-defined but equivalent.
