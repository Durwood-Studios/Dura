## Why this matters

An order arrives. Your strategy decides to trade. It constructs an `Order` object: `Order* o = new Order(price, qty);`. That one line can take anywhere from 50 nanoseconds (heap in fast path, thread-local cache) to several microseconds (allocation under pressure, TLB miss, lock contention). The exact cost is non-deterministic — it depends on fragmentation history, other threads' allocation patterns, and the allocator's internal state.

Non-determinism on the hot path is the enemy. An allocator that is usually fast but occasionally slow produces exactly the tail latency that loses races. The solution is to never call the global allocator on the hot path at all.

## Start with something familiar

Reserving a correctly sized workbench does not assemble the object on it, and taking the object apart does not dispose of the workbench.

## The mental model

> Raw storage, object construction, destruction, and storage release are separate lifetime operations. Placement construction needs sufficient size and alignment and does not itself allocate the backing storage.

## First principles: why malloc is slow

The global allocator solves a hard problem: arbitrary sizes, arbitrary lifetimes, multi-threaded access, and no leaks. To solve it, it maintains complex free-list data structures, acquires locks under contention, and sometimes calls `mmap` to grow the heap — a system call. Every one of those mechanisms has a cost that your hot path does not need to pay, because your hot path allocates _known-size objects with known lifetimes_.

The three allocators HFT teams use instead, from simplest to most flexible:

1. **Bump-pointer (arena) allocator**: pre-allocates a large contiguous block once; gives memory by advancing a pointer. Reset by moving the pointer back to the start. O(1) alloc, O(1) reset, no individual free.
2. **Slab pool (object pool)**: one pool per object type, backed by a pre-allocated array; free list of available slots returned as a stack. O(1) alloc, O(1) free.
3. **Stack allocator**: serves memory from a stack frame or a stack-like region. Useful for temporaries.

## The bump-pointer arena

An <VocabTooltip slug="arena-allocator">arena allocator</VocabTooltip> is a single large memory block with a cursor. Allocation bumps the cursor forward. There is no individual free — the entire arena is released (or reset) at once, at a natural epoch boundary (end of a trading day, end of a burst, end of a request).

```cpp
#include <cstddef>
#include <memory>
#include <new>
// Single-threaded raw storage; destroy live objects before reset.
template <std::size_t N>
class Arena {
    static_assert(N > 0);
public:
    [[nodiscard]] void* allocate(std::size_t size,
        std::size_t alignment = alignof(std::max_align_t)) noexcept {
        if (size == 0 || alignment == 0 || (alignment & (alignment - 1)) != 0)
            return nullptr;
        if (size > N - cursor_) return nullptr;
        void* candidate = buffer_ + cursor_;
        std::size_t space = N - cursor_;
        if (!std::align(alignment, size, candidate, space)) return nullptr;
        cursor_ = static_cast<std::byte*>(candidate) - buffer_ + size;
        return candidate;
    }
    void reset() noexcept { cursor_ = 0; }
    std::size_t used() const noexcept { return cursor_; }
private:
    alignas(std::max_align_t) std::byte buffer_[N];
    std::size_t cursor_ = 0;
};
```

Typical use: allocate the arena as a thread-local or a global, serve all per-tick temporaries from it, and `reset()` at the end of each tick. There is no fragmentation because nothing is individually freed; the bump always moves forward.

## Placement new: constructing in pre-allocated storage

<VocabTooltip slug="placement-new">Placement new</VocabTooltip> constructs an object at an address
you already hold, without invoking the global allocator. The syntax is `new (ptr) T(args...)`. The
resulting object lives in whatever storage `ptr` points to — on the stack, in an arena, in a pool.

```cpp
#include <cstdint>
#include <utility>   // std::forward

// A market-data event struct used in the example below.
struct MarketEvent {
    std::uint64_t timestamp_ns;
    std::int64_t  price;
    std::uint32_t quantity;
    char          symbol[8];

    MarketEvent(std::uint64_t ts, std::int64_t p, std::uint32_t q)
        : timestamp_ns(ts), price(p), quantity(q) {}
};

// Construct a MarketEvent inside an Arena — zero heap involvement.
Arena<1 << 20> g_tick_arena;  // 1 MiB, constructed once at startup

MarketEvent* make_event(std::uint64_t ts, std::int64_t p, std::uint32_t q) {
    void* mem = g_tick_arena.allocate(sizeof(MarketEvent),
                                      alignof(MarketEvent));
    if (!mem) return nullptr;

    // Construct in-place: no malloc, no lock, no syscall.
    return new (mem) MarketEvent(ts, p, q);
    // Destructor: when the arena is reset(), objects in it are simply
    // abandoned. If MarketEvent had a non-trivial destructor you would
    // need to call it explicitly: event->~MarketEvent(); before the reset.
}
```

The critical rule: you are responsible for calling the destructor manually (`ptr->~T()`) before the memory is reused, if `T` has a non-trivial destructor. For POD/trivially-destructible types (the common case for hot-path structs in HFT), you can skip this.

## Object pool for fixed-size objects

An <VocabTooltip slug="object-pool">object pool</VocabTooltip> (slab pool) gives you O(1) allocation AND O(1) individual free — at the cost of serving only one object size.

```cpp
#include <array>
#include <cstddef>
#include <cstdint>
#include <new>

// Fixed-capacity pool of T objects. T must be trivially destructible
// OR you must call T's destructor in release() before the slot is reused.
// Pool is pre-allocated; every acquire/release is a pointer pop/push.
template <typename T, std::size_t Capacity>
class SlabPool {
public:
    SlabPool() {
        // Pre-populate the free stack: slot i's free pointer points to slot i.
        // We avoid constructing Ts here — their memory is uninitialised.
        for (std::size_t i = 0; i < Capacity; ++i)
            free_[i] = reinterpret_cast<T*>(storage_[i].data());
        top_ = Capacity;
    }

    // Acquire a slot and construct T in it.
    template <typename... Args>
    [[nodiscard]] T* acquire(Args&&... args) noexcept {
        if (top_ == 0) return nullptr;  // pool exhausted
        T* slot = free_[--top_];
        return new (slot) T(std::forward<Args>(args)...);  // placement new
    }

    // Explicitly call T's destructor (if non-trivial) and return the slot.
    void release(T* p) noexcept {
        if (!p) return;
        p->~T();                    // explicit destructor call
        free_[top_++] = p;          // push the slot back onto the free stack
    }

private:
    // Storage: raw byte arrays, one per slot, correctly aligned for T.
    alignas(T) std::array<std::byte, sizeof(T)> storage_[Capacity];

    // Free list: a stack of pointers into storage_.
    T* free_[Capacity];
    std::size_t top_;
};
```

Acquire is `top_--` and a placement new. Release is a destructor call and `top_++`. No lock, no syscall, no fragmentation. Pool exhaustion is an out-of-capacity error the system must handle (typically by logging and dropping the allocation, not by blocking).

## std::pmr: plugging custom allocators into standard containers

C++17 introduced `std::pmr` (polymorphic memory resource) so that standard containers — `vector`, `string`, `unordered_map` — can use your custom allocator without templating on the allocator type.

```cpp
#include <memory_resource>
#include <vector>
#include <array>

// A monotonic_buffer_resource is the standard-library arena allocator:
// bump-pointer on a fixed buffer, no individual free.
std::array<std::byte, 4096> buf;
std::pmr::monotonic_buffer_resource pool{buf.data(), buf.size()};

// A pmr::vector uses `pool` for every allocation instead of malloc.
std::pmr::vector<std::int64_t> prices{&pool};
prices.reserve(64);  // goes into `buf`, not the heap

// When `prices` is destroyed, it calls pool's deallocate, which is a no-op
// for monotonic_buffer_resource (memory is freed when the pool is destroyed).
```

`std::pmr::monotonic_buffer_resource` is a standards-compliant arena. You can also implement your own by inheriting from `std::pmr::memory_resource` and overriding `do_allocate`, `do_deallocate`, and `do_is_equal`.

The PMR design keeps the container code unchanged — `std::pmr::vector<T>` is the same template as `std::vector<T>` from the user's perspective — but routes memory through your resource. This is the pragmatic path for introducing custom allocation into code that uses STL containers without rewriting all the container uses.
