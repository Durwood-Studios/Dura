## Why this matters

You have a market-data normaliser that must handle Nasdaq ITCH, CBOE pitch, and an internal synthetic feed — three different decoders. The obvious design: a `FeedDecoder` base class with a virtual `decode()` method. It works, scales, and costs you a vtable lookup and an indirect branch on every packet. At a hundred million packets per day, that branch is mispredicted a meaningful fraction of the time and eats nanoseconds.

One alternative is <VocabTooltip slug="crtp">CRTP</VocabTooltip>, which selects a derived implementation through template instantiation. This can expose calls to inlining and other optimization, but inlining and performance are not guaranteed. A constrained free function can be simpler when member-style mixins are unnecessary.

## Start with something familiar

A form can select one supplier at printing time instead of looking up a supplier each time an order arrives.

## The mental model

> Template policies choose behavior during instantiation. An if constexpr discarded branch is still parsed, but dependent code in it need not be instantiated for the chosen policy.

## The problem CRTP solves

<VocabTooltip slug="dynamic-polymorphism">Dynamic polymorphism</VocabTooltip> (virtual functions)
dispatches at _runtime_ through a pointer in a <VocabTooltip slug="vtable">vtable</VocabTooltip>.
The CPU cannot always predict where the pointer leads, flushes the pipeline on a mispredict, and the
linker must keep the vtable structure around so `dynamic_cast` can work. On the hot path this is
three costs for one abstraction.

<VocabTooltip slug="static-polymorphism">Static polymorphism</VocabTooltip> resolves the type at
compile time. The compiler sees through the template, inlines the correct implementation, and the
vtable is never emitted. CRTP is the most common C++ spelling of static polymorphism.

## The mechanism: CRTP

The pattern is this: the base class takes itself as a template parameter. The derived class inherits from the base class instantiation of itself:

```cpp
#include <cstdint>
#include <span>

// Base: knows the derived type at compile time via the template parameter.
// No virtual keyword anywhere — no vtable, no runtime dispatch.
template <typename Derived>
class FeedDecoder {
public:
    // down-cast to Derived and call its decode implementation.
    // static_cast is safe here: the invariant of CRTP is that Derived
    // inherits from FeedDecoder<Derived> and nothing else calls this.
    void decode(std::span<const std::byte> packet) {
        static_cast<Derived*>(this)->decode_impl(packet);
    }

    // Provide a default that Derived can override selectively.
    std::uint64_t sequence_number() const {
        return static_cast<const Derived*>(this)->sequence_number_impl();
    }

protected:
    std::uint64_t seq_{0};
};

// Derived A: Nasdaq ITCH.
class ItchDecoder : public FeedDecoder<ItchDecoder> {
public:
    void decode_impl(std::span<const std::byte> packet) {
        // Parse ITCH fixed-width binary directly.
        // The compiler inlines this — no virtual call, no indirect branch.
        if (!packet.empty()) ++seq_;
    }

    std::uint64_t sequence_number_impl() const { return seq_; }
};

// Derived B: internal synthetic feed.
class SyntheticDecoder : public FeedDecoder<SyntheticDecoder> {
public:
    void decode_impl(std::span<const std::byte> packet) {
        // Different format, different logic, same interface.
        if (packet.size() >= 4) ++seq_;
    }

    std::uint64_t sequence_number_impl() const { return seq_ * 2; }
};

// A generic consumer templated on the decoder type.
// At compile time, only ONE path exists in the final binary.
template <typename DecoderT>
void process_feed(DecoderT& dec, std::span<const std::byte> pkt) {
    dec.decode(pkt);   // inlined: no vtable load, no indirect branch
}
```

The downcast requires the base subobject actually to belong to the expected Derived object; inheriting from a CRTP specialization alone does not enforce that invariant. A protected constructor blocks direct construction but still permits an unrelated derived class to misuse the specialization. If exact-derived construction matters, use a carefully restricted constructor/friend design and account for construction/destruction lifetime rules.

> **Mental model.** CRTP is the template equivalent of `virtual`: it says "the base class expresses an interface, derived classes supply implementations." The difference is that CRTP bakes the choice into the type at compile time, so the call becomes a direct, inlined call instead of an indirect one. The class hierarchy exists; the runtime dispatch does not.

## Policy-based design: composing behaviour at compile time

CRTP expresses an "is-a" relationship. <VocabTooltip slug="policy-class">Policy classes</VocabTooltip> express "configured with" — injected as template parameters, they supply swappable behaviour with no runtime cost. Alexandrescu's _Modern C++ Design_ popularised this; HFT infrastructure uses it everywhere.

```cpp
#include <cstdint>
#include <cstring>   // std::memcpy

// Policy A: transmit using a raw UDP socket (or mock).
struct UdpTransport {
    void send(const void* buf, std::size_t len) noexcept {
        // In production: sendto(sockfd, buf, len, 0, &addr, sizeof addr)
        (void)buf; (void)len;   // placeholder
    }
    static constexpr bool kBatched = false;
};

// Policy B: batch sends into a kernel-bypass ring (e.g. DPDK).
struct DpdkTransport {
    void send(const void* buf, std::size_t len) noexcept {
        // rte_eth_tx_burst(...) — no copy, no syscall
        (void)buf; (void)len;
    }
    static constexpr bool kBatched = true;
};

// OrderSender is parameterised on Transport. The policy class is injected
// at construction and methods may be inlined — zero overhead.
// empty-base-optimization: if Transport has no data members, sizeof(OrderSender)
// is the same as if Transport were not there.
template <typename Transport>
class OrderSender : private Transport {
public:
    void send_order(std::uint64_t order_id, std::int64_t price, std::uint32_t qty) {
        // Build a tiny wire frame on the stack — no heap allocation.
        struct Frame { std::uint64_t id; std::int64_t price; std::uint32_t qty; };
        Frame frame{order_id, price, qty};

        // This call is inlined and, with DPDK, becomes an rte_mbuf enqueue.
        // With UDP it becomes a sendto. The decision is compile-time.
        Transport::send(&frame, sizeof frame);

        if constexpr (Transport::kBatched) {
            // Only compiled in for batched transports.
            flush_batch();
        }
    }

private:
    void flush_batch() { /* flush the DPDK TX ring */ }
};
```

The `if constexpr` branch exists only in the binary for transports where `kBatched` is `true`. The dead branch is dead-code-eliminated by the compiler before any linking happens — not at runtime, at compile time.

> The <VocabTooltip slug="empty-base-optimization">empty-base optimisation</VocabTooltip> (EBO): when you use `private` inheritance to inject a policy, and that policy has no data members, the compiler is permitted to make it occupy zero bytes in the derived class. Private inheritance of a stateless policy is the canonical way to inject behaviour without cost. If you held the policy as a `Transport transport_` member variable instead, you would pay at least 1 byte (compilers cannot make a named member zero bytes).

## CRTP for mixins: sharing implementation across unrelated types

A third use of CRTP is a <VocabTooltip slug="mixin">mixin</VocabTooltip>: a base that adds methods to whatever derives from it, using only the derived class's public interface.

```cpp
#include <cstdint>

// Mixin: adds a non-virtual clone method to any Derived that provides
// a copy constructor. Works on any class, no modification needed.
template <typename Derived>
struct Cloneable {
    Derived clone() const {
        return static_cast<const Derived&>(*this);  // invokes copy constructor
    }
};

// Any class can mixin this without any other base.
class OrderTicket : public Cloneable<OrderTicket> {
public:
    explicit OrderTicket(std::uint64_t id) : id_(id) {}
    std::uint64_t id() const { return id_; }
private:
    std::uint64_t id_;
};

// usage: auto copy = ticket.clone();  — no virtual, no heap
```

This pattern avoids the <VocabTooltip slug="barton-nackman-trick">Barton-Nackman trick</VocabTooltip> of defining friend operators and keeps each mixin focussed on a single concern.

## When NOT to use CRTP

CRTP is the right tool when the type is known at compile time. It becomes the wrong tool when:

- **The type is chosen at runtime** (loaded from config, determined by user input, selected by a factory). A virtual function is correct there; refusing to pay 5 ns for a function that runs once a minute is premature optimisation.
- **You are building a plugin system** where the concrete type must be unknown to the caller's translation unit. Concepts and virtual dispatch are the right tools.
- **The codebase is not template-heavy** and the maintainer cost of deeply nested template hierarchies exceeds the latency win.

The HFT rule of thumb: CRTP on the hot path (message handler, order sender, book update), virtual where the concrete type is dynamic (admin console, configuration loader, logging backends).
