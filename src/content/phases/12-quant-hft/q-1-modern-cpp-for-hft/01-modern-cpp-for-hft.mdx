## Why this matters

In a high-frequency trading system, the code path from "a market-data packet arrived" to "an order left the network card" is the whole business. It runs millions of times a day, and the only number that matters is how long the _slowest_ runs take. Median latency is marketing; the tail is the P&L.

In that world, ordinary C++ habits become bugs. Returning a `std::vector` by value looks innocent — until you learn whether it copied or moved. A `virtual` function looks like good design — until you measure the branch misprediction it costs on every call. Throwing an exception looks like clean error handling — until you discover the compiler kept a slow path alive in your hot loop just in case.

This lesson is the subset of ISO/IEC 14882:2024 — the standard the C++ committee calls **C++23** — that HFT teams actually write in, and the equally important subset they refuse to write on the hot path. Every feature here exists to answer one question: _how do I get the abstraction without paying for it at runtime?_

## Start with something familiar

Handing over a suitcase differs from copying its contents, but a label saying transferable does not itself move anything.

## The mental model

> C++ move operations can transfer resources; std::move is a cast enabling overload selection. Returning an eligible named local permits copy elision, while explicit ownership and lifetime rules remain necessary.

## First principles: where does the time go?

Before any feature, the mental frame. On a modern CPU, a few operations dominate the latency budget:

- **A heap allocation** (`new`, or a `std::vector` that grows) is hundreds of nanoseconds and can touch a global lock. On the hot path, it is forbidden.
- **A cache miss** — reading memory that isn't in L1/L2 — is ~100 ns. Data layout matters more than instruction count.
- **A branch misprediction** — the CPU guessed wrong about which way an `if` went — flushes the pipeline, ~15 ns. A `virtual` call is an indirect branch the CPU often can't predict.
- **A copy of a large object** is bounded by memory bandwidth — and is pure waste if the source was about to be destroyed anyway.

Modern C++ gives you tools to eliminate the last item entirely (move semantics), to delete work before the program even runs (constexpr), and to build layered abstractions the compiler flattens to nothing (templates). The features below are not academic — each one removes a specific item from that list.

> **Mental model.** C++ abstractions express ownership and behavior while giving an optimizer useful information. The language does not require them to compile into identical hand-written C instructions; verify correctness and inspect measured code.

## Move semantics: stop copying things that are about to die

Start with the oldest waste in C++: copying an object whose original is immediately thrown away.

To make sense of moves you need one distinction. An **lvalue** is an expression that names a persistent object you could take the address of — a variable like `book`. An **rvalue** is a temporary with no lasting name — the result of `make_book()`, or anything you've explicitly marked as expendable. (This is the <VocabTooltip slug="lvalue-rvalue">lvalue/rvalue</VocabTooltip> value-category split.)

Before C++11, a function returning a big object had to copy it. **Move semantics** lets you instead _steal_ the guts of an expiring object — transfer its internal pointer rather than duplicate the data it points to.

The mechanism is the **rvalue reference**, written `T&&`. A `T&&` parameter binds only to rvalues — to temporaries the caller has agreed are expendable.

```cpp
#include <cstddef>
#include <cstring>
#include <utility>   // std::move, std::exchange

// A toy fixed-capacity order buffer that owns a heap block.
// Real HFT code avoids the heap entirely on the hot path; this owns one
// so the copy-vs-move difference is visible.
class OrderBuffer {
public:
    explicit OrderBuffer(std::size_t capacity)
        : data_(new char[capacity]), size_(capacity) {}

    ~OrderBuffer() { delete[] data_; }

    // Copy constructor: DUPLICATES the heap block. Bandwidth-bound, slow.
    OrderBuffer(const OrderBuffer& other)
        : data_(new char[other.size_]), size_(other.size_) {
        std::memcpy(data_, other.data_, size_);
    }

    // Move constructor: STEALS the pointer, leaves `other` empty but valid.
    // `noexcept` is load-bearing: std::vector only moves (instead of copying)
    // its elements on reallocation if their move constructor is noexcept.
    OrderBuffer(OrderBuffer&& other) noexcept
        : data_(std::exchange(other.data_, nullptr)),  // take ptr, null the source
          size_(std::exchange(other.size_, 0)) {}

    std::size_t size() const { return size_; }

private:
    char* data_;
    std::size_t size_;
};

OrderBuffer make_buffer() {
    OrderBuffer local(4096);
    return local;   // moved out (or elided — see RVO below), never copied
}
```

`std::move` does **not** move anything. It is a cast: it turns an lvalue into an rvalue reference so the move constructor becomes eligible. The work happens in the move constructor you wrote.

```cpp
OrderBuffer a(4096);
OrderBuffer b(std::move(a));  // b steals a's block. a is now empty-but-valid.
// Reading a.size() is fine (it's 0); using a as if it still owned data is a bug.
```

The contract after a move: the moved-from object is in a _valid but unspecified_ state. You may destroy it or assign to it; you may not assume it still holds its old value.

## RVO: the copy that never happened

Look again at `make_buffer()`. It constructs `local` and returns it. You might expect a move on the way out. Often there is not even a move — the object is built directly in the caller's storage.

This is **copy elision**. Under C++23, the named-return case (returning a named local — historically called **NRVO**) is a permitted optimization the compiler will almost always take. The unnamed case — `return OrderBuffer(4096);` — is _mandatory_ elision since C++17: the standard forbids the compiler from emitting any copy or move there at all.

```cpp
OrderBuffer guaranteed() {
    return OrderBuffer(4096);  // C++17+: NO copy, NO move. Built in place. Guaranteed.
}
```

> **Mental model.** Returning an eligible local can enable elision or implicit move according to the type and language rules. Avoid an unnecessary std::move on that local; do not generalize this into a claim that every return value always moves or has zero cost.

## Perfect forwarding: passing arguments through without a copy

A generic wrapper — a logger, a factory, an object pool's `emplace` — needs to accept any arguments and pass them to a constructor _exactly as it received them_. An rvalue argument should stay an rvalue (so it can be moved); an lvalue should stay an lvalue (so it is not stolen out from under the caller).

The tool is the **forwarding reference** (also called a universal reference): a `T&&` where `T` is a template parameter being deduced. It is _not_ the same as a plain rvalue reference, even though it looks identical — the deduction context changes the meaning. It binds to both lvalues and rvalues and remembers which it got.

```cpp
#include <utility>   // std::forward
#include <vector>

template <typename T, typename... Args>
T& emplace_into(std::vector<T>& pool, Args&&... args) {
    // Args&&... here is a FORWARDING reference (Args is deduced), not an
    // rvalue reference. std::forward preserves each argument's value category:
    // rvalues stay movable, lvalues stay copy-only.
    return pool.emplace_back(std::forward<Args>(args)...);
}
```

`std::forward<Args>(args)` is a conditional cast: it yields an rvalue reference when the caller passed an rvalue, and an lvalue reference when the caller passed an lvalue. Using `std::move` here instead would be a bug — it would unconditionally treat _every_ argument as expendable, silently stealing from lvalues the caller still needs.

> The rule of thumb HFT code lives by: **`std::move` on an rvalue reference you own; `std::forward` on a forwarding reference you are passing through.** Move where the type is fixed, forward where the type was deduced.

## constexpr and consteval: delete the work before the program runs

The cheapest computation is the one that already happened at compile time. `constexpr` marks a function or variable as _usable_ in a constant expression — the compiler may evaluate it during compilation if the inputs are known then.

```cpp
#include <array>
#include <cstdint>

// Tick sizes for a venue, computed once at compile time into a lookup table.
// No runtime loop, no initialization order problem, lives in read-only memory.
constexpr std::array<std::int64_t, 8> make_tick_table() {
    std::array<std::int64_t, 8> table{};
    std::int64_t tick = 1;
    for (std::size_t i = 0; i < table.size(); ++i) {
        table[i] = tick;
        tick *= 10;   // 1, 10, 100, ... price increments by decimal band
    }
    return table;
}

constexpr auto kTickTable = make_tick_table();  // built by the compiler, not at startup
```

C++23 widened `constexpr` substantially — more of the standard library and language is usable in constant expressions than in earlier standards. But `constexpr` only _permits_ compile-time evaluation; if you call the function with runtime inputs, it runs at runtime.

When you want to _guarantee_ compile-time evaluation, use **consteval** (an "immediate function," added in C++20 and available in C++23). A `consteval` function that the compiler cannot evaluate at compile time is a compile error, not a runtime fallback.

```cpp
// consteval: MUST run at compile time. Encodes a fixed-point price scale so a
// typo'd exponent fails the build instead of producing a wrong runtime value.
consteval std::int64_t price_scale(int decimal_places) {
    std::int64_t scale = 1;
    for (int i = 0; i < decimal_places; ++i) scale *= 10;
    return scale;
}

constexpr std::int64_t kUsdScale = price_scale(4);  // OK: evaluated at compile time
// int n = read_config(); price_scale(n);           // ERROR: n is not a constant
```

In HFT this matters because startup-time initialization and runtime branching both cost something. A table baked into the binary has no initialization cost and lives in cache-friendly read-only memory.

## Concepts vs SFINAE: constraining templates without the pain

Templates are how C++ achieves <VocabTooltip slug="zero-cost-abstraction">zero-cost abstraction</VocabTooltip> — code generic over types that compiles down to the same instructions as a hand-specialized version, with no runtime dispatch. But an unconstrained template accepts _any_ type, and a mismatch historically produced a wall of unreadable errors deep inside the template body.

The old way to constrain a template was **SFINAE** — "Substitution Failure Is Not An Error." You wrote machinery (`std::enable_if`) that made the template silently drop out of overload resolution when a type didn't qualify. It worked, but it was write-only code and its errors were notorious.

C++20 introduced **concepts** — named, readable predicates on types — and C++23 keeps them as the standard tool. A concept says, in one place, what a type must support. Compare the two ways to require "a type you can add to itself":

```cpp
#include <concepts>
#include <type_traits>

// --- The SFINAE way (pre-C++20): works, but the intent is buried. ---
template <typename T,
          typename = std::enable_if_t<std::is_arithmetic_v<T>>>
T twice_sfinae(T value) { return value + value; }

// --- The concepts way (C++20/23): the constraint IS the signature. ---
template <std::integral T>          // std::integral is a standard concept
T twice(T value) { return value + value; }

// Or spell the requirement out with a requires-clause:
template <typename T>
    requires std::integral<T> || std::floating_point<T>
T twice_either(T value) { return value + value; }
```

When you call `twice("hello")`, the concept version tells you, in plain language, that `const char*` does not satisfy `std::integral` — at the call site. The SFINAE version buries the same failure in a substitution-failure cascade. Same runtime cost (zero — it's all compile time); dramatically better diagnostics and readability. HFT codebases standardized on concepts the moment compilers shipped them, because template-heavy code with bad errors is template-heavy code nobody can maintain.

## std::span: a non-owning view of contiguous memory

A C habit that survives into a lot of C++ is passing a buffer as two arguments: a pointer and a length. The two can disagree. `std::span<T>` (added in C++20, part of C++23) packages them into one object: a non-owning view over a contiguous sequence — a pointer plus a count, with bounds you can query and range-based iteration.

```cpp
#include <span>
#include <cstdint>
#include <cstring>   // std::memcpy

// Parse a fixed-layout market-data message out of a received frame.
// span owns nothing — it points into a buffer someone else manages,
// so there is no allocation and no copy. Pass it by value (it's two words).
std::int32_t read_price(std::span<const std::byte> frame) {
    // Read through subspan, not raw .data(): subspan() is the bounds-aware
    // path — it can be checked (and in a debug build will fault on overrun),
    // whereas frame.data() + 8 throws span's length away and is unchecked.
    std::int32_t price = 0;
    std::span<const std::byte> field = frame.subspan(8, sizeof(price));  // price at byte offset 8
    std::memcpy(&price, field.data(), sizeof(price));
    return price;
}

// A std::array, a std::vector, or a raw C array all convert to a span
// with no copy. The function above works with all three callers unchanged.
```

`std::span` does not own the memory and does not free it — the lifetime belongs to whatever the span points into. Pass it _by value_: it is small (pointer + size), and copying it copies only the view, never the data. It replaces the fragile pointer-plus-length idiom with one type that carries its own length and can be bounds-checked, at zero runtime cost over the raw pointer.

## What HFT teams refuse on the hot path

Modern C++ is large. The HFT dialect is defined as much by exclusions as inclusions. On the latency-critical path (not necessarily elsewhere in the system), these are commonly banned:

- **Exceptions.** Throwing is acceptable cost-wise; the problem is that the _possibility_ of throwing constrains the optimizer and the unwinding tables bloat the binary. Hot-path code is often compiled `-fno-exceptions` and returns errors as values (e.g. an error enum or a `std::expected`, which C++23 added).
- **RTTI** (run-time type information — `dynamic_cast`, `typeid`). It implies runtime type lookups and the per-class metadata that goes with them. Built with `-fno-rtti`.
- **Runtime polymorphism** (`virtual` functions). A virtual call is an indirect branch through a vtable — an extra memory load and a branch the CPU frequently mispredicts. The fix is compile-time polymorphism: templates and concepts, which the compiler resolves and inlines. The abstraction survives; the indirect jump does not.
- **Heap allocation** (`new`, growing containers). Hundreds of nanoseconds and a possible lock. Hot-path data lives in pre-allocated buffers, object pools, or on the stack.

These are design tradeoffs, not universal bans. Compilers can devirtualize calls, moves may execute work, and constexpr functions can run at runtime when constant evaluation is not required. Choose a correct contract and measure the actual implementation.
