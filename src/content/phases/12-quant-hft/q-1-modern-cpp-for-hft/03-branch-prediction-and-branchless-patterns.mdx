## Why this matters

Your order router checks, on every incoming packet, whether the sequence number is valid. The sequence number is almost always valid — gaps happen perhaps once a day. The branch that handles the gap is therefore cold, and the branch that continues the fast path is hot. Without annotation, the compiler lays out the code in source order. The predictor learns the pattern eventually, but the branch instruction itself still costs a slot and the cold-path instructions pollute the instruction cache.

A single `[[unlikely]]` attribute moves the cold path out of the main flow, making the instruction cache hold only the hot path. That is the smallest possible change — one keyword — for a measurable gain on a path that executes a hundred million times a day.

A sign suggesting the usual route helps a planner, but it does not guarantee the route stays fastest when traffic changes.

> Likely and unlikely attributes guide optimization without changing program semantics. Branchless source is not proof of branchless machine code or better latency.

## The mechanism: CPU branch prediction

The CPU begins executing instructions _before_ it knows whether a branch is taken. This is <VocabTooltip slug="speculative-execution">speculative execution</VocabTooltip>: it guesses "taken" or "not taken" based on the <VocabTooltip slug="branch-prediction">branch predictor</VocabTooltip>'s history. If the guess is right, the speculatively-executed instructions are committed and cost nothing extra. If the guess is wrong — a <VocabTooltip slug="branch-misprediction">misprediction</VocabTooltip> — the pipeline is flushed, the speculative work is discarded, and the CPU starts again on the correct path. On a modern x86-64, this <VocabTooltip slug="pipeline-flush">pipeline flush</VocabTooltip> costs roughly 10–20 cycles.

The branch predictor is excellent at learned patterns: a loop condition that is true 99% of the time will almost always be predicted correctly after a few iterations. The two cases where you must help it:

1. A branch the predictor has never seen before (startup, a cold handler).
2. A branch that is correlated with external data it cannot track (market data content, protocol type bytes).

## [[likely]] and [[unlikely]]: layout hints

C++20's `[[likely]]` and `[[unlikely]]` attributes on a branch arm tell the compiler — and therefore the code layout — which path the CPU should optimise for. The compiler emits the "likely" path as fall-through in the instruction stream and the "unlikely" path as a forward jump out of line.

```cpp
#include <cstdint>

// A SoupBinTCP/ITCH receive loop. Packet gaps are extremely rare
// (maybe once a day), so the gap handler should be cold and off the
// main path.
void process_packet(std::uint64_t expected_seq, std::uint64_t actual_seq) {
    if (actual_seq == expected_seq) [[likely]] {
        // Hot path: 99.9999% of the time we land here.
        // [[likely]] lays this out as fall-through in the binary, keeping
        // it in the instruction cache with the surrounding loop code.
        process_message();
    } else [[unlikely]] {
        // Cold path: gap detected. Slow, infrequent, off-line in the binary.
        // [[unlikely]] puts this after a jump so it does not pollute i-cache.
        handle_gap(expected_seq, actual_seq);
    }
}
```

Two important notes:

- The attributes are **hints to the compiler for layout**; they do not change the branch predictor's runtime behaviour. A CPU that has observed this branch is taken 50% of the time will continue to guess 50%, regardless of the attribute. The attribute helps instruction cache density and the optimizer's inlining/hoisting decisions; it does not make the hardware predictor smarter.
- Use them where profiling shows the branch is on a frequently-executed path AND the probability is highly lopsided. Adding `[[likely]]` to a 60/40 branch is noise.

## Branchless arithmetic: eliminating the branch entirely

For comparisons in tight loops — clamping a quantity, selecting the minimum of two prices — the branch itself (even when perfectly predicted) consumes instruction bandwidth and potentially delays out-of-order execution. The alternative is a <VocabTooltip slug="conditional-move">conditional move</VocabTooltip> (`cmov` on x86-64): a single instruction that selects between two values based on a condition, with no branch and no prediction penalty.

The C++ idiom that reliably generates `cmov` is the ternary expression on integer or pointer types:

```cpp
#include <cstdint>
#include <algorithm>   // std::min, std::max, std::clamp

// A quantity cap: hard-coded maximum is 100,000 shares.
// The ternary compiles to a cmov on x86-64 — no branch.
// Equivalent to std::min but spelled out to show intent.
constexpr std::uint32_t kMaxShares = 100'000;

[[nodiscard]] std::uint32_t cap_quantity(std::uint32_t requested) noexcept {
    return requested > kMaxShares ? kMaxShares : requested;  // -> cmov
}

// Best-bid update: keep the higher of two prices.
// The compiler may implement integer selection with cmov or a branch.
[[nodiscard]] std::int64_t update_best_bid(
        std::int64_t current_best, std::int64_t new_price) noexcept {
    return new_price > current_best ? new_price : current_best;
}

// Tick-size clamped quantity: between minimum lot and maximum lot.
// Precondition: lot_min <= lot_max. This clamps; it does not round to a lot multiple.
[[nodiscard]] std::uint32_t lot_round(
        std::uint32_t qty, std::uint32_t lot_min, std::uint32_t lot_max) noexcept {
    return std::clamp(qty, lot_min, lot_max);
}
```

`std::min`, `std::max`, and a conditional expression express selection. Their emitted instructions depend on the compiler, target, and surrounding code; inspect the actual build.

## When branchless is NOT the answer

A C++ conditional expression evaluates only the selected operand. A compiler may use branches or conditional instructions, but it must preserve that language behavior. This null check is valid:

```cpp
#include <cstdint>

[[nodiscard]] std::int64_t read_price(const std::int64_t* p) noexcept {
    return p != nullptr ? *p : 0;
}
```

Replacing the conditional with arithmetic multiplication is different: multiplying a dereferenced value by zero does not prevent the dereference. Never access an invalid pointer to compute an operand you intend to discard later. Conditional selection also cannot make a dangling non-null pointer valid.

Integer and floating-point selection can compile differently across targets and optimization contexts. Inspect generated instructions and benchmark representative inputs; source syntax alone does not promise `cmov` or better latency. Preserve correctness before choosing a measured implementation.

## Measuring misprediction rate

Before rewriting any branch, measure it. On Linux, `perf stat` reports hardware performance counters:

```bash
# Run the binary and collect counters until it exits.
# branch-misses / branches is the misprediction rate (%).
perf stat -e branches,branch-misses ./order_router 2>&1 | grep -E "branches|branch-misses"
```

An aggregate misprediction percentage does not identify the latency contribution of a particular branch. Profile the critical path and compare end-to-end distributions before and after a change; there is no universal percentage below which improvement is impossible.

```bash
# Pinpoint which branch mispredicts most:
perf record -e branch-misses:u ./order_router
perf report   # shows source locations of the most-mispredicted branches
```
