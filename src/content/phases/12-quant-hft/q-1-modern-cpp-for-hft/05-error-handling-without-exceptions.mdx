## Why this matters

You parse an ITCH message. Three things can go wrong: the buffer is too short, the message type is unknown, and the price field is out of range. With exceptions you throw three different exception types and the caller catches them. With `-fno-exceptions` the throws are program termination and you must design a different channel for errors.

The classical alternative — returning an error code as an `int` or an out-parameter — works but is fragile: callers can ignore error codes, there is no type enforcement that the error was checked, and composing a three-step parser requires three nested `if (err) return err` checks.

`std::expected<T, E>` solves this: it is a type that is either a `T` (success) or an `E` (error), and the type system forces the caller to handle both cases. It is a regular value — you can return it, store it, pass it — with no heap allocation and no runtime overhead.

## The mechanism: std::expected

`std::expected<T, E>` (header `<expected>`, C++23) is a tagged union that holds either a `T` value or an `E` error. On the success path, the storage is a `T`. On the failure path, it holds an `E`.

```cpp
#include <expected>  // C++23
#include <cstdint>
#include <span>
#include <string_view>

// An error type: a strongly-typed enum so callers cannot ignore which error occurred.
// Having a small enum rather than a heap-allocated string keeps error handling on-stack.
enum class ParseError : std::uint8_t {
    BufferTooShort,
    UnknownMessageType,
    PriceOutOfRange,
};

// Helper: turn an error into a human-readable string for logging.
// Called on the failure path only — not hot.
constexpr std::string_view describe(ParseError e) noexcept {
    switch (e) {
        case ParseError::BufferTooShort:     return "buffer too short";
        case ParseError::UnknownMessageType: return "unknown message type";
        case ParseError::PriceOutOfRange:    return "price out of range";
    }
    return "unknown error";
}

// Return type: either a parsed price (uint32_t) or a ParseError.
// No heap, no exception, no implicit error-channel.
[[nodiscard]] std::expected<std::uint32_t, ParseError>
parse_price(std::span<const std::byte> buf) noexcept {
    if (buf.size() < 36) {
        return std::unexpected(ParseError::BufferTooShort);  // failure branch
    }
    if (std::to_integer<char>(buf[0]) != 'A') {
        return std::unexpected(ParseError::UnknownMessageType);
    }
    // Read the 4-byte big-endian price at offset 32.
    std::uint32_t raw = 0;
    for (int i = 0; i < 4; ++i) {
        raw = (raw << 8) | std::to_integer<std::uint32_t>(buf[32 + i]);
    }
    if (raw == 0) {
        return std::unexpected(ParseError::PriceOutOfRange);
    }
    return raw;  // success: implicit conversion to std::expected<uint32_t, ParseError>
}
```

The caller checks the result:

```cpp
auto result = parse_price(packet);
if (result) {
    // result.value() is the uint32_t price
    std::uint32_t price = *result;  // operator* is shorthand for value()
    process(price);
} else {
    // result.error() is the ParseError
    log_warning(describe(result.error()));
}
```

## Monadic chaining: and_then, transform, or_else

Three steps in sequence — parse the message type, then parse the price, then convert to ticks — each of which can fail, produce three nested if-statements in the classical style. `std::expected` provides monadic operations that chain these flatly:

```cpp
#include <expected>
#include <cstdint>
#include <span>

// Three independent parse steps, each returning expected<T, ParseError>.
[[nodiscard]] std::expected<char, ParseError>
    parse_type(std::span<const std::byte> buf) noexcept;

[[nodiscard]] std::expected<std::uint32_t, ParseError>
    parse_raw_price(std::span<const std::byte> buf) noexcept;

[[nodiscard]] std::expected<std::int64_t, ParseError>
    to_ticks(std::uint32_t raw_price) noexcept;

// Monadic chain: stops at the first error, passes the success value forward.
// No nested ifs. The [[nodiscard]] ensures the result is checked.
[[nodiscard]] std::expected<std::int64_t, ParseError>
parse_add_order_price(std::span<const std::byte> buf) noexcept {
    return parse_type(buf)
        .and_then([&](char /*type*/) { return parse_raw_price(buf); })
        .and_then([](std::uint32_t raw)  { return to_ticks(raw); });
}
```

- `and_then(f)`: if the value is present, call `f(value)` and return its `expected`; if the value is an error, propagate the error without calling `f`. This is the flatMap / bind of monadic composition.
- `transform(f)`: if the value is present, call `f(value)` and wrap the result in a success; propagate errors unchanged.
- `or_else(f)`: called when the value is an error; `f` can recover or return a different error.

The chain reads left to right: "parse type, then parse raw price, then convert to ticks — bail at the first failure." Under `-O3` this compiles to the same machine code as three nested ifs, with no function call overhead.

## -fno-exceptions: what it removes

The compiler flag `-fno-exceptions` (GCC and Clang) disables exception support throughout the translation unit. The effects:

- `throw` becomes `std::terminate()` (a deliberate crash — the compiler will tell you if you try to throw, and the program aborts at runtime if unhandled)
- **Unwinding tables** — the `.eh_frame` and `.gcc_except_table` sections that tell the runtime how to unwind the stack when an exception is thrown — are not emitted. These tables can be megabytes on a large binary; removing them shrinks the binary and reduces the ELF sections the dynamic linker must process.
- The **zero-overhead exception path** — code the compiler emitted to keep open the possibility of unwinding — is removed. Functions marked `noexcept` under normal compilation still emit a small landing pad in case a `throw` slips through; `-fno-exceptions` removes those landing pads entirely.

On the hot path the practical effect is subtle: the binary is smaller and the instruction cache has fewer competing sections, but the per-instruction latency of `throw`-free code is already nearly identical to exception-free code because of the zero-overhead model. The real benefit is the **unwinding tables and the binary size** — and the signal it sends to the optimiser that it can assume no function in this unit will propagate an exception.

## Designing the error type

A good error type for a `std::expected` in HFT is:

- **Small**: fits in one or two registers. An `enum class` backed by `uint8_t` or `uint32_t` is ideal.
- **Typed**: strong enough that the compiler errors if you mix error types from two unrelated systems.
- **Self-describing**: `describe(e)` or a `std::format` specialisation so the logging path does not need a stack trace.
- **Not heap-allocated**: `std::string` as the error type forces heap allocation on every error path — the opposite of what you want.

Do NOT use `std::variant<T, std::string>` as a poor-man's expected for hot-path code. The string allocation kills the point.
