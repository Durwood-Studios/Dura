## Why this matters

In the previous lesson you wired up Nasdaq <VocabTooltip slug="itch-protocol">ITCH</VocabTooltip> for market data and OUCH for order entry — tight binary protocols where every field is a fixed-width integer at a known byte offset. They are fast and they are proprietary. They work on Nasdaq.

The day your firm connects to a second venue, the binary dialect changes. A European exchange, a bank's single-dealer platform, an institutional broker's smart order router — almost none of them speak ITCH/OUCH. They speak FIX. When an order silently fails to reach the market and the broker's connectivity desk asks you to "send us the FIX log," you need to read that log and find the broken field yourself. This lesson makes a raw FIX byte stream as legible to you as a line of code.

## Start with something familiar

An envelope's byte count and seal cover precise boundaries; changing the separator used for display changes the actual envelope bytes.

## The mental model

> FIX TagValue uses SOH-delimited fields with defined header order, byte length, and checksum boundaries. A readable pipe character is a display convention, not the wire delimiter.

## The protocol, from first principles

Imagine two trading systems that have never met, written by different teams, in different languages, on different continents, that must agree on exactly what "buy 100 shares of IBM at $142.50, limit" means — down to the byte. They cannot share a struct definition. They cannot assume the same integer width or endianness. What they can do is agree on a tiny, self-describing text format: a list of numbered fields, each one a number, an equals sign, a value, and a separator.

That is FIX. <VocabTooltip slug="fix-protocol">FIX</VocabTooltip> (Financial Information eXchange) is a messaging standard, first published in 1992 to replace order-by-telephone between Fidelity and Salomon Brothers, now governed by the FIX Trading Community. A FIX message is a flat sequence of fields. Each field is a numeric **tag**, an `=`, a value, and a terminator.

```
8=FIXT.1.1 | 9=65 | 35=D | 49=BUYSIDE | 56=SELLSIDE | 34=2 | ... | 10=062
```

Read that as: "field 8 is `FIXT.1.1`, field 35 is `D`, field 9 is `65`…". The number on the left is not data — it is the _name_ of the field. Tag 35 always means "message type." Tag 55 always means "symbol." The dictionary of tag numbers is the shared contract; the values are the conversation.

The real terminator is not a `|`. It is a single byte: <VocabTooltip slug="soh-delimiter">ASCII SOH</VocabTooltip> (Start of Heading, decimal 1, written `\x01`). It is non-printable, which is why FIX logs are usually shown with `|` or `^` substituted for readability. Tools that print raw FIX replace SOH so you can see field boundaries; the wire only ever carries `\x01`.

## The mental model

> **A FIX message is a dictionary serialized as `tag=value` pairs, separated by the SOH byte (`\x01`), wrapped in three structural fields: tag 8 (BeginString) opens it, tag 9 (BodyLength) measures it, tag 10 (CheckSum) closes it. Everything between 9 and 10 is the message; 8, 9, and 10 are the envelope that lets a receiver find where the message starts, how long it is, and whether it arrived intact.**

Hold that three-field envelope in your head. Almost every FIX parsing bug is a confusion about the envelope — counting the wrong bytes for BodyLength, or computing CheckSum over the wrong range.

## The mechanism — the tag=value wire format

A FIX field is three things concatenated with no spaces:

```
<tag><ASCII '='><value><ASCII SOH>
```

So the field "message type is NewOrderSingle" is the seven bytes `3`, `5`, `=`, `D`, `\x01`. Written with SOH shown as `|`: `35=D|`.

The key tags you will see on every order-entry message:

| Tag | Name         | Meaning                                                                   | Example    |
| --- | ------------ | ------------------------------------------------------------------------- | ---------- |
| 8   | BeginString  | Protocol version. MUST be the first field.                                | `FIXT.1.1` |
| 9   | BodyLength   | Byte count of everything after tag 9 up to (not incl.) tag 10             | `65`       |
| 35  | MsgType      | What kind of message this is. `D` = NewOrderSingle, `8` = ExecutionReport | `D`        |
| 49  | SenderCompID | Who sent it (session identity)                                            | `BUYSIDE`  |
| 56  | TargetCompID | Who it is for (session identity)                                          | `SELLSIDE` |
| 34  | MsgSeqNum    | Per-session message sequence number                                       | `2`        |
| 11  | ClOrdID      | Client order ID — the sender's unique handle for this order               | `ORD-0001` |
| 55  | Symbol       | The instrument                                                            | `IBM`      |
| 54  | Side         | `1` = Buy, `2` = Sell                                                     | `1`        |
| 38  | OrderQty     | Quantity                                                                  | `100`      |
| 40  | OrdType      | `1` = Market, `2` = Limit                                                 | `2`        |
| 44  | Price        | Limit price (present when OrdType is Limit)                               | `142.50`   |
| 10  | CheckSum     | Integrity check. ALWAYS the last field, ALWAYS 3 digits.                  | `062`      |

Three of those tags are structural and have strict ordering rules baked into the standard:

- **Tag 8 (`BeginString`)** is unconditionally first. A receiver scans for `8=` to find the start of a message in a TCP stream.
- **Tag 9 (`BodyLength`)** is unconditionally second. Its value is the number of bytes from the SOH that ends tag 9 up to (and including) the SOH that ends the last field _before_ the checksum. In practice: everything between `9=...\x01` and `10=...\x01`.
- **Tag 10 (`CheckSum`)** is unconditionally last.

`BeginString` is `FIXT.1.1` for FIX 5.0 SP2. This is the part that trips people up: starting with FIX 5.0, the standard split the transport version (carried in tag 8, always `FIXT.1.1`) from the application version (FIX.5.0SP2, carried separately in tag 1128 `ApplVerID` when needed). The `T` in `FIXT` is "transport." Pre-5.0 messages carried both in tag 8 — for example, `FIX.4.2`. This lesson uses FIXT.1.1 because that is what a FIX 5.0 SP2 session sends.

## The CheckSum — get this byte-exact

<VocabTooltip slug="checksum">CheckSum</VocabTooltip> (tag 10) is the one computation in FIX you
must get exactly right, because every counterparty validates it and a wrong checksum gets your
message dropped before anyone reads the order.

The rule from the FIX specification:

> The checksum is the sum of the ASCII values of every byte in the message **up to but not including the CheckSum field itself**, taken **modulo 256**, formatted as a **3-digit zero-padded decimal** number.

"Up to but not including the CheckSum field" means: sum every byte from the `8` of `8=FIXT.1.1` through the SOH (`\x01`) that terminates the field immediately before `10=`. The SOH bytes are included in the sum — they are real bytes on the wire (decimal 1 each). The `10=062\x01` field itself is _not_ summed.

Worked by hand for the field `35=D\x01` in isolation:

```
'3' = 51
'5' = 53
'=' = 61
'D' = 68
SOH =  1
        ───
sum  = 234   →   234 % 256 = 234   →   "234"
```

The modulo 256 is what keeps the result in one byte regardless of message length. The 3-digit zero-padding means a checksum of 7 is transmitted as `007`, never `7`. We will compute a full-message checksum in code in a moment.

## NewOrderSingle — `35=D`

<VocabTooltip slug="new-order-single">NewOrderSingle</VocabTooltip> is the workhorse message: "place
one order." Its MsgType is `D`. The application-layer fields that matter for a plain limit order:

```
8=FIXT.1.1 | 9=<len> | 35=D | 49=BUYSIDE | 56=SELLSIDE | 34=2 |
52=20260616-13:45:30.000 | 11=ORD-0001 | 55=IBM | 54=1 |
60=20260616-13:45:30.000 | 38=100 | 40=2 | 44=142.50 | 10=<sum>
```

Field by field, separating envelope from order:

- `8`, `9`, `10` — the envelope (BeginString, BodyLength, CheckSum).
- `49`, `56`, `34`, `52` — session identity and sequencing: who, to whom, message number, sending time. These belong to the <VocabTooltip slug="session-layer">session layer</VocabTooltip> (covered below), even though they ride in the same message.
- `11` (<VocabTooltip slug="clordid">ClOrdID</VocabTooltip>) — the client's unique ID for this order. You generate it; the venue echoes it back on every report so you can correlate. It MUST be unique per session per day.
- `55` Symbol = IBM, `54` Side = 1 (Buy), `38` OrderQty = 100, `40` OrdType = 2 (Limit), `44` Price = 142.50.
- `60` TransactTime — when the order was created on your side.

The minimum required application fields for a NewOrderSingle in FIX 5.0 SP2 are ClOrdID (11), Side (54), TransactTime (60), and OrdType (40), plus an instrument block (Symbol 55 or a SecurityID block) and a quantity. Price (44) is required when OrdType is Limit and omitted for a Market order. A venue that receives a Limit order with no tag 44 will send you a rejection — and now you know to look at tag 44 first.

## ExecutionReport — `35=8`

Every order's life — accepted, partially filled, fully filled, rejected, canceled — is reported back to you in a stream of <VocabTooltip slug="execution-report">ExecutionReport</VocabTooltip> messages, MsgType `8`. This is the single most important message to read fluently, because it is how you learn what actually happened to your order.

```
8=FIXT.1.1 | 9=<len> | 35=8 | 49=SELLSIDE | 56=BUYSIDE | 34=3 |
52=20260616-13:45:30.105 | 37=EXEC-99 | 11=ORD-0001 | 17=E-1 |
150=0 | 39=0 | 55=IBM | 54=1 | 38=100 | 14=0 | 151=100 |
6=0 | 10=<sum>
```

The report-specific tags:

- `37` OrderID — the venue's ID for the order (distinct from your ClOrdID 11, which it echoes back).
- `17` ExecID — unique ID for _this execution report_.
- `150` ExecType — what event triggered this report. `0` = New (acknowledged), `F` = Trade (a fill), `4` = Canceled, `8` = Rejected.
- `39` OrdStatus — the order's overall state. `0` = New, `1` = Partially filled, `2` = Filled, `8` = Rejected.
- `14` CumQty — cumulative quantity filled so far.
- `151` LeavesQty — quantity still working (open). `CumQty + LeavesQty` equals OrderQty for a live order.
- `6` AvgPx — average fill price so far.

Read the example above: ExecType 0 + OrdStatus 0 + CumQty 0 + LeavesQty 100 = "your order was accepted and is now fully working in the book, nothing filled yet." When a fill arrives, you would see `150=F`, `39=1` or `39=2`, a non-zero `14`, and a shrinking `151`.

## Session layer vs application layer — the line that organizes everything

FIX is two protocols wearing one wire format. Keeping them mentally separate is what turns FIX from a wall of numbers into a structured system.

The <VocabTooltip slug="session-layer">session layer</VocabTooltip> guarantees an ordered, gap-free, recoverable conversation between two endpoints. It owns:

- **Sequence numbers (tag 34).** Every message in a session is numbered. If you receive seqnum 5 after 3, you know 4 was lost and you send a ResendRequest.
- **Heartbeats (`35=0`) and TestRequest (`35=1`).** Keep the connection proven-alive during quiet periods.
- **Logon (`35=A`) / Logout (`35=5`).** Establish and tear down the session, negotiate the heartbeat interval.
- **ResendRequest (`35=2`) / SequenceReset (`35=4`).** Recover from gaps.

The <VocabTooltip slug="application-layer">application layer</VocabTooltip> is the actual business: NewOrderSingle (`D`), ExecutionReport (`8`), OrderCancelRequest (`F`), OrderCancelReplaceRequest (`G`), and the rest. These messages carry the order semantics — symbol, side, quantity, price.

The classic FIX session runs over a single long-lived TCP connection. The session layer's sequencing and the application layer's orders share that one stream. When you debug, the first question is always _which layer_: a duplicate-seqnum or comp-ID-mismatch problem is session; a missing-price or unknown-symbol rejection is application.

## When classic FIX is too slow — FIXP and FAST

Classic FIX over TCP carries text fields and a heavyweight session protocol. Parsing `tag=value` strings and the TCP/session overhead cost microseconds — fine for institutional order flow, too slow for the latency-sensitive tier. The FIX Trading Community published two separate standards to address this, and it is worth knowing precisely what each one does, because they solve different problems.

**FAST** (FIX Adapted for STreaming) is an _encoding_. It replaces the verbose `tag=value` ASCII with a compact binary representation driven by a shared XML template: fields whose values rarely change between messages are omitted entirely (operators like "copy," "increment," "constant"), integers are packed as stop-bit-encoded bytes instead of decimal strings, and the tag numbers themselves disappear because the template defines field order. <VocabTooltip slug="fast-encoding">FAST</VocabTooltip> is used predominantly for high-volume _market data_ dissemination, where the same fields repeat across millions of messages and the compression and parse-speed wins are large. FAST changes how a message is _written on the wire_; it does not change the session protocol.

**FIXP** (FIX Performance session layer) is a _session protocol_. <VocabTooltip slug="fixp">FIXP</VocabTooltip> is a lightweight replacement for the classic FIX session layer, designed to run over both reliable transports (TCP) and unreliable ones (UDP multicast), with explicit support for point-to-point order entry. It defines its own lean framing, sequencing, and flow types (idempotent, recoverable, unsequenced, none) so a venue can pick exactly the delivery guarantee a given flow needs instead of paying for full recoverable sequencing on everything. FIXP changes how the _conversation is managed_; it is encoding-agnostic and is frequently paired with a binary encoding such as SBE (Simple Binary Encoding) rather than FAST for order entry.

The mental split:

- **FAST** = squeeze the _bytes_ (an encoding). Mostly market data.
- **FIXP** = slim the _session_ (a session layer). Order entry and market data both.

A venue's connectivity spec will tell you exactly which combination it offers — for example, "FIXP session over TCP with SBE encoding" for binary order entry, alongside a classic FIX-over-TCP gateway for everyone else. Knowing the three are independent layers — encoding, session, transport — is what lets you read that spec correctly.
