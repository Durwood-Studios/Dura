## Why this lesson matters

A trading strategy is only as good as the prices it sees. Before any model runs, before any order goes out, something has to turn a stream of bytes off a network socket into "AAPL just traded 100 shares at \$184.52." That something is a market-data handler, and on Nasdaq it speaks a protocol called <VocabTooltip slug="itch">ITCH</VocabTooltip>.

Here is the part that surprises people coming from web development: there is no JSON, no XML, no text at all. ITCH is raw binary — fixed-width fields, big-endian integers, prices encoded as integers with the decimal point implied. A single wrong assumption (you read a field as little-endian, or you let the C++ compiler insert padding into your struct) and every price you decode is garbage. The feed does not tell you that you are wrong. Your book just fills with nonsense and your strategy trades on it.

This lesson teaches you to read those bytes correctly, and to write the parser that does it at the speed an HFT system needs.

## First principles: why a binary protocol at all

Imagine you are Nasdaq. On a busy day you publish tens of millions of messages — every order added, executed, and cancelled across thousands of symbols. Every member firm subscribes to the same firehose. Two pressures dominate every design decision:

1. **Bandwidth.** A text format like `{"type":"add","price":184.52,"shares":100}` is roughly 40 bytes for what binary does in 4. Multiply by tens of millions of messages and text becomes physically too large to push down a wire in time.
2. **Decode speed.** Parsing text means scanning for delimiters, allocating strings, converting `"184.52"` to a number. Binary means: the price is the four bytes at offset 32, read them as an integer, done. No scanning, no allocation, no parsing — a memory read and a byte-swap.

So Nasdaq made the opposite of every choice a web API makes. Every field is a fixed number of bytes at a fixed offset. Numbers are stored in <VocabTooltip slug="big-endian">big-endian</VocabTooltip> byte order (most-significant byte first — the network convention). Prices are integers, not floats. This is a <VocabTooltip slug="fixed-width-binary">fixed-width binary</VocabTooltip> protocol, and it is built for one reader: a program, going as fast as possible.

The mirror image of ITCH is <VocabTooltip slug="ouch">OUCH</VocabTooltip> — the protocol you use to send orders _to_ Nasdaq. ITCH flows exchange→you (<VocabTooltip slug="market-data-feed">market data</VocabTooltip>, read-only, broadcast to everyone). OUCH flows you→exchange (<VocabTooltip slug="order-entry">order entry</VocabTooltip>, your private session). Same binary philosophy, opposite direction.

## The mental model

> **An ITCH message is a C struct that was written to a socket.** The exchange did not "serialize" anything in the web sense — it took a fixed-layout record in memory, fixed the byte order to big-endian, and sent the raw bytes. Your job as a parser is to lay the same struct over the incoming bytes and undo the byte-swap. Get the layout and the endianness right and decoding is nearly free.

Hold onto that picture. Everything below is a consequence of it: the fixed offsets, the packing, the byte-swaps, the integer prices.

## The ITCH message anatomy

Every ITCH 5.0 message begins with a one-byte <VocabTooltip slug="message-type">message type</VocabTooltip> that tells you which struct follows. A few of the message types you handle constantly:

| Type byte | Message                                                                          | Meaning                                                                           |
| --------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `'S'`     | <VocabTooltip slug="system-event-message">System Event</VocabTooltip>            | Market-wide events: start of messages, market open, market close, end of messages |
| `'A'`     | <VocabTooltip slug="add-order-message">Add Order</VocabTooltip> (no attribution) | A new visible order joined the book                                               |
| `'F'`     | Add Order with MPID                                                              | Same as `'A'` but carries the attributing market participant ID                   |
| `'E'`     | <VocabTooltip slug="order-executed-message">Order Executed</VocabTooltip>        | Shares of a resting order traded                                                  |
| `'X'`     | <VocabTooltip slug="order-cancel-message">Order Cancel</VocabTooltip>            | Shares of a resting order were cancelled (partial cancel)                         |
| `'D'`     | Order Delete                                                                     | A resting order was removed entirely                                              |
| `'P'`     | <VocabTooltip slug="trade-message">Trade (non-cross)</VocabTooltip>              | A trade involving a non-displayed (hidden) order                                  |

The first several fields are common across most message types. Using Add Order (`'A'`) as the worked example, the byte layout — every offset and width straight from the published Nasdaq TotalView-ITCH 5.0 spec — is:

```
Offset  Width  Field                  Type / encoding
------  -----  ---------------------  ------------------------------------
  0       1    Message Type           ASCII 'A'
  1       2    Stock Locate           big-endian u16  (per-symbol index into the day's symbol directory)
  3       2    Tracking Number        big-endian u16  (Nasdaq-internal)
  5       6    Timestamp              big-endian 48-bit, nanoseconds since midnight
 11       8    Order Reference Number big-endian u64  (unique id for this order's lifetime)
 19       1    Buy/Sell Indicator     ASCII 'B' (buy) or 'S' (sell)
 20       4    Shares                 big-endian u32  (number of shares)
 24       8    Stock                  8 ASCII bytes, right-padded with spaces (e.g. "AAPL    ")
 32       4    Price                  big-endian u32, 4 implied decimal places
------  -----  ---------------------  ------------------------------------
Total: 36 bytes
```

Three things in this table earn the most attention, because they are where parsers go wrong:

**The timestamp is 6 bytes, not 8.** ITCH 5.0 stores nanoseconds since midnight (US/Eastern) in a 48-bit field — there is no standard 48-bit integer type in C++. You read it into a `uint64_t` by hand. A day has fewer than 10^14 nanoseconds, which fits in 48 bits, so Nasdaq saved two bytes per message. At tens of millions of messages a day, that is real bandwidth.

**The price is an integer with an <VocabTooltip slug="implied-decimal">implied decimal</VocabTooltip>.** The Price field is an unsigned 32-bit integer with **4 implied decimal places**. The bytes `0x00 0x1C 0x50 0xD8` are `1,855,704` as a big-endian integer, which means \$185.5704. To get dollars you divide by 10,000. The feed never sends `185.5704` as a floating-point number — floats are not exactly representable for decimals, they are slower to compare, and they are non-deterministic across compilers. An integer is exact, fast, and identical on every machine. (Phase Q's IEEE 754 lesson is why this matters: `0.1 + 0.2 != 0.3` in binary floating point. Prices stay integers precisely to dodge that.)

**The <VocabTooltip slug="order-reference-number">order reference number</VocabTooltip> is the key for everything that follows.** When an `'E'` (executed), `'X'` (cancel), or `'D'` (delete) arrives later, it references this same 64-bit number — it does _not_ repeat the symbol or price. Your handler keeps a hash map from order reference number to the resting order so it can apply those follow-up messages. Reconstructing the book is exactly: Add inserts, Execute/Cancel/Delete look up the reference number and modify.

## The mechanism: a correct C++ parser

Now the code. Two failure modes dominate, and the code exists to defeat both:

1. **Struct padding.** By default a C++ compiler is free to insert padding bytes between struct members so each lands on a natural alignment boundary. A struct laid over wire bytes with hidden padding reads every field after the first gap from the wrong offset. You must tell the compiler: pack tight, no padding.
2. **Endianness.** Your CPU (x86-64, ARM) is little-endian. ITCH is big-endian. Every multi-byte integer must be byte-swapped on read.

```cpp
#include <cstdint>
#include <cstring>   // std::memcpy
#include <bit>       // std::byteswap (C++23), std::endian
#include <string>
#include <string_view>

// ITCH fields have no padding — the wire format is byte-exact. We pack the
// struct so its layout matches the bytes on the wire 1:1. Without this, the
// compiler may insert alignment padding and every offset after the first
// misaligned field is wrong.
#pragma pack(push, 1)
struct ItchAddOrderRaw {
    char     message_type;            // 'A'
    uint16_t stock_locate;            // big-endian on the wire
    uint16_t tracking_number;         // big-endian on the wire
    uint8_t  timestamp[6];            // 48-bit big-endian ns since midnight
    uint64_t order_reference_number;  // big-endian on the wire
    char     buy_sell_indicator;      // 'B' or 'S'
    uint32_t shares;                  // big-endian on the wire
    char     stock[8];                // ASCII, space-padded, not byte-swapped
    uint32_t price;                   // big-endian, 4 implied decimal places
};
#pragma pack(pop)
static_assert(sizeof(ItchAddOrderRaw) == 36,
              "Add Order must be exactly 36 bytes — packing is wrong if not");

// Convert a big-endian value on the wire to host order. On a little-endian
// host this is a byte swap; on a (rare) big-endian host it is a no-op. We
// branch on std::endian::native so the same source is correct on both.
template <typename T>
[[nodiscard]] T from_big_endian(T wire_value) noexcept {
    if constexpr (std::endian::native == std::endian::little) {
        return std::byteswap(wire_value);   // C++23
    } else {
        return wire_value;
    }
}

// The decoded, host-order representation we actually work with.
struct AddOrder {
    uint16_t    stock_locate;
    uint64_t    timestamp_ns;             // nanoseconds since midnight
    uint64_t    order_reference_number;
    bool        is_buy;
    uint32_t    shares;
    std::string symbol;                   // trimmed of trailing spaces
    uint32_t    price_raw;                // integer, 4 implied decimals
};

// Read the 6-byte big-endian timestamp into a uint64_t. There is no 48-bit
// integer type, so we accumulate byte by byte, most-significant first.
[[nodiscard]] uint64_t read_timestamp_48(const uint8_t bytes[6]) noexcept {
    uint64_t value = 0;
    for (int i = 0; i < 6; ++i) {
        value = (value << 8) | bytes[i];   // big-endian: byte[0] is most significant
    }
    return value;
}

// Parse 36 bytes of an Add Order message. We copy into the packed struct
// (std::memcpy is the only well-defined way to reinterpret raw bytes — a
// reinterpret_cast<ItchAddOrderRaw*> would be undefined behavior due to
// strict aliasing and possible misalignment).
[[nodiscard]] AddOrder parse_add_order(const uint8_t* buffer) noexcept {
    ItchAddOrderRaw raw{};
    std::memcpy(&raw, buffer, sizeof(raw));

    // Trim trailing spaces from the 8-byte fixed symbol field.
    std::string_view sym(raw.stock, 8);
    const auto end = sym.find_last_not_of(' ');
    std::string symbol = (end == std::string_view::npos)
                             ? std::string{}
                             : std::string(sym.substr(0, end + 1));

    return AddOrder{
        .stock_locate           = from_big_endian(raw.stock_locate),
        .timestamp_ns           = read_timestamp_48(raw.timestamp),
        .order_reference_number = from_big_endian(raw.order_reference_number),
        .is_buy                 = (raw.buy_sell_indicator == 'B'),
        .shares                 = from_big_endian(raw.shares),
        .symbol                 = std::move(symbol),
        .price_raw              = from_big_endian(raw.price),
    };
}

// Price is an integer with 4 implied decimals. Convert to dollars only at the
// display boundary; the engine keeps the integer (exact, fast to compare).
[[nodiscard]] double price_to_dollars(uint32_t price_raw) noexcept {
    return static_cast<double>(price_raw) / 10000.0;
}
```

A few deliberate choices worth calling out:

- `std::byteswap` and `std::endian` are real C++23 standard-library facilities (`<bit>`). Before C++23 you would write the byte swap by hand or use a compiler builtin like `__builtin_bswap32`. Phase Q targets C++23, so we use the standard one.
- `std::memcpy` into the packed struct — never `reinterpret_cast` over the buffer — because the incoming bytes may be unaligned and the cast violates strict aliasing. `memcpy` is the defined, optimizer-friendly way; on a real build it compiles to the same loads as a cast would, without the undefined behavior.
- The decoded `AddOrder` keeps `price_raw` as the integer. We convert to a `double` only when a human needs to read it. The matching engine compares integers.

## The framing layer: SoupBinTCP

There is a gap in the story so far. ITCH messages are variable length — an Add Order is 36 bytes, a System Event is 12, a Trade is different again. If you are reading a TCP stream, how do you know where one message ends and the next begins? TCP gives you a byte stream with no message boundaries.

Nasdaq's answer is a thin framing protocol called <VocabTooltip slug="soupbintcp">SoupBinTCP</VocabTooltip>. It sits _under_ ITCH and does three jobs: it delimits each message with a length, it labels what kind of packet it is, and it numbers the data messages so a client can detect a gap.

Every SoupBinTCP packet on the wire is:

```
Offset  Width  Field          Encoding
------  -----  -------------  --------------------------------------------
  0       2    Packet Length  big-endian u16 — bytes that FOLLOW (type + payload)
  2       1    Packet Type    ASCII char (e.g. 'S' = sequenced data, 'H' = heartbeat)
  3       N    Payload        the bytes (for 'S', this is one ITCH message)
```

So the read loop is: read 2 bytes → that is the length L → read L more bytes → the first is the packet type, the rest is the payload. The length prefix is what turns a boundary-less TCP stream back into discrete messages.

The packet type that carries market data is `'S'` — a **Sequenced Data Packet**. "Sequenced" is the load-bearing word. SoupBinTCP guarantees that sequenced packets are numbered 1, 2, 3, … with no gaps and no duplicates _within a session_. The protocol does not put the <VocabTooltip slug="sequence-number">sequence number</VocabTooltip> in every packet — that would waste bytes. Instead, the server tells you the sequence number of the _first_ sequenced packet at login, and you count from there: the Nth sequenced packet you receive is sequence number `first + N - 1`.

Why does this matter? Because TCP can drop a connection, and the multicast variant of these feeds (UDP) can drop packets outright. The sequence number is how you _know_ you missed something:

> **Mental model for recovery:** you keep a counter of the next sequence number you expect. Every sequenced packet bumps it by one. If the connection drops and you reconnect, SoupBinTCP lets you log in and request "resume from sequence number K" — the server replays everything from K forward. The sequence number is the bookmark that makes a gap detectable and recoverable. Without it, a dropped packet means a silently-wrong order book and you never know.

SoupBinTCP also defines a Login Request/Accept handshake, Logout, Heartbeats (so each side knows the other is alive), and a Debug packet. The pieces you must internalize: **length prefix delimits, packet type discriminates, sequence number detects loss.**

## OUCH: sending orders back

ITCH is read-only — it is the whole market broadcast to every member. To actually trade you need a private, authenticated session that sends _your_ orders to Nasdaq. That is OUCH, and it rides on the very same SoupBinTCP framing (your client sends _Unsequenced_ Data Packets, type `'U'`; the exchange sends sequenced acknowledgments back).

The three OUCH client messages you send most:

| Type byte | Message       | Meaning                                                                          |
| --------- | ------------- | -------------------------------------------------------------------------------- |
| `'O'`     | Enter Order   | Submit a new order: your order token, side, shares, symbol, price, time-in-force |
| `'U'`     | Replace Order | Modify a live order (change shares or price) by referencing its token            |
| `'X'`     | Cancel Order  | Cancel a live order by its token                                                 |

The exchange replies with its own OUCH messages — `'A'` Order Accepted, `'E'` Executed, `'C'` Canceled, `'J'` Rejected — so your execution layer always knows the live state of every order it sent. OUCH carries an **order token**: a client-assigned identifier you put on the Enter Order, and that every acknowledgment echoes back, so you can match a reply to the order that caused it. (Note the byte values overlap with ITCH but the protocols are separate — `'X'` is Cancel Order in OUCH and Order Cancel in ITCH; context, not the byte alone, tells you which.)

The symmetry is the whole point: **ITCH in, OUCH out, SoupBinTCP framing both.** Decode the world with one, act on it with the other.

## What you learned

- **ITCH is fixed-width big-endian binary, decoded by laying a struct over the bytes.** Each message starts with a one-byte type (`'S'` system event, `'A'` add order, `'E'` executed, `'X'` cancel, `'P'` trade), and every field sits at a fixed offset with a fixed width — no delimiters, no parsing, just reads.
- **Prices are integers with 4 implied decimal places**, divided by 10,000 only at the display boundary. The feed never sends a float, so the value is exact and identical on every machine — and the order reference number, not the symbol, is the key that ties follow-up Execute/Cancel/Delete messages back to a resting order.
- **A correct C++ parser needs two things the compiler won't give you for free:** `#pragma pack(1)` so no alignment padding shifts your field offsets (guard it with `static_assert(sizeof == 36)`), and a big-endian-to-host byte swap (`std::byteswap`, C++23) on every multi-byte integer. Use `std::memcpy` into the packed struct, never a `reinterpret_cast`.
- **SoupBinTCP frames the variable-length payload:** a 2-byte big-endian length prefix delimits each packet, a 1-byte packet type discriminates it (`'S'` = sequenced data carrying one ITCH message), and consecutive sequence numbers let you detect a dropped packet and request a replay — the difference between a recoverable gap and a silently-corrupted book.
- **ITCH flows in (market data, read-only), OUCH flows out (order entry, private session).** OUCH's core client messages are Enter Order (`'O'`), Replace Order (`'U'`), and Cancel Order (`'X'`), carrying an order token the exchange echoes on every acknowledgment. Both protocols ride the same SoupBinTCP framing.
