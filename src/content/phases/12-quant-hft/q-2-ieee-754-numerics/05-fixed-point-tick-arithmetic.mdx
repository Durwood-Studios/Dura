## Why this matters

Decimal price input can be corrupted by an imprecise conversion or an unchecked rounding policy. For example, truncating a scaled inexact value can choose a neighboring grid value. The safer contract is to parse decimal text into checked integer units and validate the permitted grid explicitly.

The value 183.50 is exactly representable in binary64: it equals 367/2. It is not an example of representation error. Values such as 0.1 repeat in binary; representation error and later arithmetic rounding must be examined for the actual value and conversion, not inferred from the presence of a decimal point.

The fix is to never use `double` for prices. This lesson shows the replacement.

> Fixed-point prices combine an integer value with an explicit scale or tick rule. Parsing, grid validation, multiplication, and rounding still require checked contracts.

## The fundamental observation

Prices in financial markets are <VocabTooltip slug="tick-size">discrete</VocabTooltip>. Equity prices on US exchanges move in increments of `$0.0001` (one-hundredth of a cent) for sub-penny pricing, or `$0.01` for most retail-visible prices. There is no such thing as a trade at `$183.500000001`. The matching engine's price grid is finite and regular.

That regularity makes floating-point the wrong tool. You do not need an arbitrary approximation of a real number. You need exact representation of one of a finite set of values. Integers are exact. So: represent prices as integers, where the integer counts <VocabTooltip slug="ticks">ticks</VocabTooltip> from zero.

```
tick size  = $0.0001           (one ten-thousandth of a dollar)
tick price = price_dollars / 0.0001
           = price_dollars * 10000

$183.50 → 1835000   (exact, no rounding)
$0.01   → 100       (exact)
$0.0001 → 1         (the minimum price increment, the tick itself)
```

The integer `1835000` is the <VocabTooltip slug="integer-price">integer price</VocabTooltip> (also called <VocabTooltip slug="raw-price">raw price</VocabTooltip> or the ITCH term: <VocabTooltip slug="implied-decimal">4-decimal implied format</VocabTooltip>). The <VocabTooltip slug="price-scale">price scale</VocabTooltip> is 10000.

Nasdaq ITCH 5.0 sends all prices in this exact format: a 4-byte unsigned integer, 4 implied decimal places. When ITCH says `Price = 1835000`, the price is `$183.5000`. No float involved anywhere in the exchange-to-strategy path.

## Integer price arithmetic

Addition, subtraction, and comparison of integer prices are exact with no rounding — because integers have exact arithmetic at the precision you care about.

```cpp
#include <cstdint>
#include <cassert>
#include <stdexcept>
#include <format>

// Integer price: ticks from 0, scale = 10000 (4 decimal places).
// 32-bit unsigned handles prices up to 429496.7295 dollars — sufficient for most equities.
// For options or indices, use int64_t for prices up to ~922 trillion ticks.
using Price = int64_t;
constexpr int64_t PRICE_SCALE = 10'000;  // ticks per dollar

// Convert a nominal dollar value to an integer price.
// Converts via int64 math to avoid float rounding.
// Precondition: price_x10000 must already be the price in ten-thousandths of a dollar.
inline Price from_ticks(int64_t raw_ticks) noexcept { return raw_ticks; }

// Display a tick price as a decimal string — never convert to double for display.
std::string price_to_string(Price p) {
    int64_t dollars  = p / PRICE_SCALE;
    int64_t fraction = p % PRICE_SCALE;
    return std::format("{}.{:04d}", dollars, fraction);
}

// Spread: best_ask - best_bid, in ticks.
inline Price spread(Price best_bid, Price best_ask) noexcept {
    return best_ask - best_bid;
}

// Mid price: (bid + ask) / 2.
// Result is in half-ticks. Store as int64_t × 2 if you need precision,
// or truncate — but document the choice.
inline Price mid_price_truncated(Price bid, Price ask) noexcept {
    return (bid + ask) / 2;  // truncates; half-tick is lost
}

// Convert integer price to double ONLY for display or model input.
// Never use the result to drive order entry.
inline double to_double(Price p) noexcept {
    return static_cast<double>(p) / static_cast<double>(PRICE_SCALE);
}
```

Key properties:

- `spread()` and comparison are single CPU instructions — no floating-point unit involved.
- `price_to_string()` uses only integer division and the `format` library — exact.
- `to_double()` exists but is documented as a one-way boundary: you convert _out_ to a model, never back in.

## Overflow analysis

The choice of `int64_t` is deliberate. Let's verify the headroom:

```cpp
// int64_t max: 9,223,372,036,854,775,807
// PRICE_SCALE:                       10,000
// Maximum whole-dollar price at scale 10,000: 922,337,203,685,477 dollars
// (922 trillion dollars — far above any instrument price)

// Overflow can still occur in intermediate calculations.
// Example: computing total notional value of a position.
int64_t shares  = 1'000'000;   // 1M shares
Price   price   = 1'835'000;   // $183.50 in ticks

// Naive: shares * price — but 1e6 * 1.835e6 = 1.835e12
// int64_t can hold up to ~9.2e18, so this fits.
int64_t notional_ticks = shares * price;  // = 1,835,000,000,000 ticks
// In dollars: notional_ticks / PRICE_SCALE = $183,500,000

// The dangerous case: shares * price * some_multiplier
// Always check before multiplying large values.
```

P&L and notional accumulation require their own accuracy, scale, rounding, and overflow contracts. A wider integer extension can increase headroom where supported, but neither it nor conversion to double automatically makes reconciliation error acceptable. Match the representation to the stated accounting or model requirement.

## Round-trip safety

The one place you might convert from a human-readable decimal string to a tick price is config parsing or order input. Do it correctly:

```cpp
#include <cstdint>
#include <limits>
#include <optional>
#include <string_view>
using Price = std::int64_t;
constexpr Price PRICE_SCALE = 10000;
// Nonnegative decimal text only: no sign, currency prefix, or whitespace.
std::optional<Price> parse_price(std::string_view text) {
    if (text.empty()) return std::nullopt;
    const auto dot = text.find('.');
    const auto whole = text.substr(0, dot);
    if (whole.empty()) return std::nullopt;
    const Price maximum = std::numeric_limits<Price>::max();
    const Price whole_limit = maximum / PRICE_SCALE;
    Price dollars = 0;
    for (char digit : whole) {
        if (digit < '0' || digit > '9') return std::nullopt;
        const Price value = digit - '0';
        if (dollars > (whole_limit - value) / 10) return std::nullopt;
        dollars = dollars * 10 + value;
    }
    Price fraction = 0;
    if (dot != std::string_view::npos) {
        const auto tail = text.substr(dot + 1);
        if (tail.empty() || tail.size() > 4) return std::nullopt;
        for (char digit : tail) {
            if (digit < '0' || digit > '9') return std::nullopt;
            fraction = fraction * 10 + (digit - '0');
        }
        for (std::size_t index = tail.size(); index < 4; ++index) fraction *= 10;
    }
    const Price scaled = dollars * PRICE_SCALE;
    if (fraction > maximum - scaled) return std::nullopt;
    return scaled + fraction;
}
```

Notice: no `double` anywhere. The parsing goes directly from decimal characters to integer ticks. Sub-tick precision (a fifth decimal place) is correctly rejected.

## The three advantages of integer prices

Knowing why the industry standardized on integer prices lets you defend the decision in design reviews:

**1. Exact representation.** Any price at the venue's tick granularity is exactly representable as a 64-bit integer. Zero rounding, ever, on the values that matter. `double` represents at most 15-16 significant decimal digits; at a price of `$10,000.0001`, the fourth decimal place is at the 9th significant digit — still safe in double, but why carry the risk?

**2. Comparison is bitwise.** `bid < ask` on two `int64_t` values is a single `cmp` instruction. On `double` it is also a single instruction (`ucomisd`) but the CPU must handle NaN and signed-zero edge cases. For an order book that runs this comparison millions of times per second, the integer path is simpler and has no exceptional cases.

**3. No floating-point unit required.** Integer arithmetic runs on the integer execution units. In an ITCH parsing loop that fills the order book, never touching the FPU means the FPU stays cold and available for the model that runs downstream. Integer units on modern CPUs have higher throughput than the FPU for simple operations.
