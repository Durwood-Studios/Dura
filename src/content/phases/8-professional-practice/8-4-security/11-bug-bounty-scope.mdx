## Why this matters

A public website has a vulnerability-reporting address, but that does not imply permission to run every test against every connected service. A useful researcher reads the program’s actual scope and preserves a minimal, reproducible report.

## Start with something familiar

A workshop invitation identifies which tools and areas a visitor may use. Discovering another unlocked room does not expand that invitation. Security-testing scope works the same way.

## The mental model

> A program’s written authorization, target scope, exclusions and reporting rules define the permitted engagement. Technical reachability and a possible reward do not expand permission.

## The mechanism

The fictional program permits testing only a supplied local demo account and in-process authorization fixture. It excludes real customer records, third-party services, denial-of-service tests and social engineering. The approved objective is to demonstrate one cross-account access flaw using synthetic accounts, then stop once the minimal evidence is collected.

A report should state target/build, authorized account setup, reproduction steps, expected/actual behavior, minimal impact evidence and suggested mitigation/retest. Avoid copying unnecessary records or secrets. If a test unexpectedly reaches real data or an excluded system, stop and use the program’s specified reporting channel rather than exploring further.

Program rules may define disclosure timing, confidentiality, safe-harbor language and reward eligibility. Read the current terms; this lesson does not interpret them as a universal legal guarantee. A valid report is not automatically eligible for payment, and a duplicate or out-of-scope issue may be handled differently.

Use the local fixture from the previous lesson to prepare a report without contacting anyone. Demonstrate alice’s unauthorized b1 access, then propose owner enforcement and positive/negative retests. Record only synthetic A/B content. Do not actually submit the report or send messages as part of this exercise.

Good reporting separates confirmed facts from hypotheses and avoids overstated severity. A program can fix a defect more effectively when the report explains the exact boundary failure and its reproducible conditions.

## Practice

The local demo links to an external identity provider. Does that link put the provider in scope? What should happen if unexpected real data appears?
