## Why this matters

Notifications are the nervous system of any product with social features — likes, follows, comments, alerts, payment confirmations. They seem deceptively simple: "just send a push when X happens." But at scale, notification systems expose every hard problem in distributed systems simultaneously: fan-out (one event triggers millions of deliveries), multi-channel routing (push vs. email vs. SMS), at-least-once delivery guarantees, deduplication, rate limiting per recipient, and the write amplification that comes when a celebrity with 50 million followers posts something.

The notification system is a frequent system design interview question precisely because it requires you to make trade-offs that cannot be resolved by "add more cache." Working through it in full prepares you for any problem where event-driven fan-out and delivery guarantees intersect.

## Requirements

**Functional requirements (agreed scope for this interview):**

1. When a trigger event occurs (new post, new follower, comment, like), send a notification to the relevant recipient(s).
2. Support three delivery channels: in-app notification bell, email, and mobile push (APNs/FCM).
3. Users can configure per-channel preferences (e.g., disable email for likes, keep push for mentions).
4. Delivered notifications appear in an inbox with read/unread state.
5. Notifications are delivered within 30 seconds of the triggering event for most users.

**Out of scope:** SMS delivery, rich-media push cards, notification scheduling, A/B testing of notification copy.

**Non-functional requirements:**

- Scale: 500 million DAU. Each user generates on average 2 notification-triggering events per day (1 billion events/day).
- Fan-out: the median user has 200 followers; the 99th percentile has 10,000 followers; celebrities have up to 50 million.
- Latency: in-app notification visible in < 30 seconds for 99% of recipients.
- Delivery guarantee: at-least-once for all channels. Duplicates are acceptable; missed notifications are not.
- Durability: notification inbox retained for 90 days.

# --- READ VOLUME (inbox fetches) ---
# Each DAU checks their inbox ~5x/day on average
inbox_reads_per_day   = DAU * 5               # 2.5B reads/day
inbox_reads_per_second = inbox_reads_per_day / 86_400  # ~29K QPS

The celebrity fan-out problem is the design crux. A single post by a 50M-follower celebrity triggers 50 million deliveries in seconds. No synchronous architecture survives this — fan-out must be asynchronous and throttled.

## Data model

```sql
-- Notification events (the source of truth — what happened)
CREATE TABLE notification_events (
  id              BIGSERIAL PRIMARY KEY,
  event_type      VARCHAR(64) NOT NULL,  -- 'new_follower', 'post_liked', 'comment', etc.
  actor_id        BIGINT NOT NULL,       -- user who triggered the event
  target_id       BIGINT NOT NULL,       -- user who RECEIVES the notification
  reference_type  VARCHAR(32),           -- 'post', 'comment', 'user' — what the event is about
  reference_id    BIGINT,
  -- idempotency_key prevents duplicate rows when the producer retries on failure
  idempotency_key VARCHAR(64) UNIQUE NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Notification inbox (per-user, denormalized for fast reads)
-- Sharded by target_id — each shard owns a range of user IDs
CREATE TABLE notification_inbox (
  id              BIGSERIAL,
  target_id       BIGINT NOT NULL,       -- recipient user
  event_id        BIGINT NOT NULL REFERENCES notification_events(id),
  is_read         BOOLEAN NOT NULL DEFAULT FALSE,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (target_id, id)            -- clustered by recipient for fast pagination
) PARTITION BY RANGE (target_id);       -- partition by user ID range

-- Index for paginated inbox: "give me the 20 newest notifications for user 42"
CREATE INDEX idx_inbox_user_time
  ON notification_inbox(target_id, created_at DESC, is_read);

-- User notification preferences
CREATE TABLE notification_preferences (
  user_id         BIGINT PRIMARY KEY,
  email_enabled   BOOLEAN NOT NULL DEFAULT TRUE,
  push_enabled    BOOLEAN NOT NULL DEFAULT TRUE,
  -- JSON allows per-event-type overrides without schema migration per new event type
  -- e.g. {"post_liked": {"email": false, "push": true}}
  channel_overrides JSONB NOT NULL DEFAULT '{}'
);

-- Delivery log: tracks per-channel delivery status for retry logic
CREATE TABLE notification_delivery_log (
  id              BIGSERIAL PRIMARY KEY,
  event_id        BIGINT NOT NULL REFERENCES notification_events(id),
  target_id       BIGINT NOT NULL,
  channel         VARCHAR(16) NOT NULL,  -- 'push', 'email', 'in_app'
  status          VARCHAR(16) NOT NULL,  -- 'pending', 'delivered', 'failed', 'bounced'
  attempts        SMALLINT NOT NULL DEFAULT 0,
  last_attempted  TIMESTAMPTZ,
  delivered_at    TIMESTAMPTZ,
  error_detail    TEXT
);

CREATE INDEX idx_delivery_retry
  ON notification_delivery_log(status, last_attempted)
  WHERE status IN ('pending', 'failed') AND attempts < 5;
```

## Fan-out strategies

The hardest problem in the notification system is the celebrity fan-out. Two fundamentally different approaches exist:

> **Fan-out-on-write pushes deliveries to recipients at event creation time. Fan-out-on-read builds the inbox lazily when the recipient opens it. The right choice depends on your follower-count distribution.**

```
FAN-OUT-ON-WRITE (push model):
  When @celebrity posts:
    1. Write event to notification_events (1 write)
    2. Enqueue 50M fan-out jobs (50M queue messages)
    3. Workers process jobs: write to each follower's notification_inbox

  ✓ Inbox reads are O(1) — just query your own pre-built inbox
  ✓ Delivery latency is predictable (queue drains at known rate)
  ✗ A single celebrity post creates 50M writes — massive write amplification
  ✗ A user with 50M followers who posts, then immediately deletes,
    still triggers 50M writes before the delete is processed

FAN-OUT-ON-READ (pull model):
  When @celebrity posts:
    1. Write event to notification_events (1 write)
    2. Store the event reference in a "celebrity feed" list

  When any follower checks their inbox:
    1. Query notification_events for all users they follow (expensive join)
    2. Merge with their own inbox

  ✓ No write amplification at event creation time
  ✗ Inbox read is O(following_count) — reading from a user following 10K people
    requires 10K lookups per inbox open
  ✗ Latency for inbox rebuild grows with social graph size

HYBRID (production standard):
  Regular users (< 10K followers): fan-out-on-write (fast inbox reads)
  Celebrity users (≥ 10K followers): fan-out-on-read (avoid write amplification)

  Inbox read logic:
    1. Fetch pre-written inbox entries (from followed non-celebrities)
    2. Fetch recent events from celebrity feeds the user follows
    3. Merge and sort by time
    4. Cache the merged result for 30 seconds
```

## Architecture

```python
# Event ingestion service — receives events from upstream services
# (post-service, like-service, follow-service, etc.)

import json
import hashlib
from typing import Optional

def ingest_event(
    event_type: str,
    actor_id: int,
    target_id: int,
    reference_type: Optional[str],
    reference_id: Optional[int],
    idempotency_key: str
) -> dict:
    """
    Ingest a notification-triggering event.
    Returns immediately (202 Accepted) — all heavy work is async.

    Why idempotency_key? If the caller retries after a network timeout,
    we must not insert a duplicate event. The UNIQUE constraint on
    idempotency_key makes the INSERT idempotent at the database level.
    """
    try:
        row = db.execute(
            """
            INSERT INTO notification_events
              (event_type, actor_id, target_id, reference_type, reference_id, idempotency_key)
            VALUES (%s, %s, %s, %s, %s, %s)
            ON CONFLICT (idempotency_key) DO NOTHING
            RETURNING id
            """,
            [event_type, actor_id, target_id, reference_type, reference_id, idempotency_key]
        )
        if not row:
            # Idempotency_key collision — already processed, not an error
            return {"status": "duplicate", "event_id": None}

        event_id = row["id"]

        # Publish to Kafka for async fan-out processing
        # The message is small — just the event ID. Workers load full data from DB.
        kafka_producer.send(
            topic="notification.events.raw",
            value=json.dumps({"event_id": event_id}),
            key=str(target_id).encode()  # partition by recipient for ordering
        )

        return {"status": "accepted", "event_id": event_id}

    except Exception as e:
        # Ingest failures must be surfaced — callers will retry
        raise RuntimeError(f"Failed to ingest event: {e}") from e
```

## Retry logic and dead-letter queues

```python
import time
from enum import Enum

class DeliveryChannel(str, Enum):
    PUSH  = "push"
    EMAIL = "email"
    IN_APP = "in_app"

# Exponential backoff schedule per channel
# Push is cheap to retry; email carries sender reputation risk if over-retried
RETRY_CONFIG = {
    DeliveryChannel.PUSH:  {"max_attempts": 5, "backoff_seconds": [10, 30, 120, 600, 3600]},
    DeliveryChannel.EMAIL: {"max_attempts": 3, "backoff_seconds": [60, 600, 7200]},
    DeliveryChannel.IN_APP: {"max_attempts": 1, "backoff_seconds": []},  # in-app is best-effort
}

def process_push_delivery(event_id: int, target_id: int) -> None:
    """Deliver a push notification with retry logic."""
    log = get_or_create_delivery_log(event_id, target_id, DeliveryChannel.PUSH)
    config = RETRY_CONFIG[DeliveryChannel.PUSH]

    if log["attempts"] >= config["max_attempts"]:
        # Exhausted retries — move to dead-letter queue for manual inspection
        send_to_dead_letter_queue({
            "event_id": event_id,
            "target_id": target_id,
            "channel": DeliveryChannel.PUSH,
            "reason": "max_retries_exceeded"
        })
        update_delivery_status(log["id"], "failed")
        return

    try:
        prefs = get_user_preferences(target_id)
        if not prefs["push_enabled"]:
            # User opted out — mark delivered (no actual delivery needed)
            update_delivery_status(log["id"], "skipped_opted_out")
            return

        device_token = get_device_token(target_id)
        if not device_token:
            update_delivery_status(log["id"], "skipped_no_device")
            return

        # Build the push payload
        payload = build_push_payload(event_id, target_id)

        # Send via APNs/FCM — may raise on network error or invalid token
        push_gateway.send(device_token=device_token, payload=payload)

        update_delivery_status(log["id"], "delivered")

    except DeviceTokenInvalidError:
        # Token expired — delete it so we stop attempting
        delete_device_token(target_id)
        update_delivery_status(log["id"], "failed_invalid_token")

    except Exception as e:
        # Transient failure — schedule retry
        attempt = log["attempts"]
        if attempt < len(config["backoff_seconds"]):
            delay = config["backoff_seconds"][attempt]
            schedule_retry(event_id, target_id, DeliveryChannel.PUSH, delay_seconds=delay)
        update_delivery_attempt(log["id"], error_detail=str(e))
```

## Bottlenecks and mitigations

```
Bottleneck 1: Celebrity fan-out write storm
  Scenario: @celebrity with 50M followers posts. 50M inbox writes in seconds.
  Mitigation:
    Hybrid fan-out: celebrities (> 10K followers) never trigger inbox writes.
    Followers' inbox reads merge pre-built rows + celebrity event feeds.
    Fan-out workers for regular users drain at a controlled rate.

Bottleneck 2: Push gateway rate limits
  Scenario: APNs and FCM impose per-app rate limits.
  At 2.3M push deliveries/sec we exceed any single gateway connection pool.
  Mitigation:
    Shard push workers by target_id range.
    Each shard maintains its own connection pool to APNs/FCM.
    Distribute across multiple registered sender IDs if platform allows.

Bottleneck 3: Notification inbox table write pressure
  Scenario: 1B fan-out writes/day to notification_inbox = 11,574 writes/sec.
  Mitigation:
    Partition notification_inbox by target_id (e.g., 256 partitions).
    Each partition on its own Postgres instance (or Aurora shard).
    Writes to different partitions never contend.

Bottleneck 4: Duplicate notifications on retry
  Scenario: Push worker sends push, APNs ACKs, but network fails before
  the worker can record "delivered" in the log. Worker retries → duplicate push.
  Mitigation:
    Idempotency keys on push payloads — APNs and FCM both support apns-collapse-id
    and collapse_key respectively. Collapse keys deduplicate at the gateway:
    if the same collapse_key arrives twice, only one notification is delivered.

Bottleneck 5: Unread count cache invalidation
  Scenario: Unread count is shown in the app header. If derived from a DB
  count(*) query, it hits the database on every page load for every user.
  Mitigation:
    Maintain a Redis counter per user: INCR user:{id}:unread_count on fan-out,
    DECR (or reset) when the user marks notifications read.
    Counter reads are O(1) and never touch the database.
```

## What you learned

- A notification system's core difficulty is the celebrity fan-out problem: one event triggering millions of writes is unsustainable with pure fan-out-on-write.
- The hybrid strategy — fan-out-on-write for regular users, fan-out-on-read for celebrities — balances write amplification against read-time merge cost.
- Message queues with per-channel retry policies and dead-letter queues provide at-least-once delivery guarantees without synchronous blocking on the event ingest path.
- Idempotency keys at the ingest layer and collapse keys at the push gateway layer together prevent duplicate notifications even when workers retry after partial failure.
- Decoupling the unread count into a Redis counter removes an otherwise catastrophic database scan from every page load.
