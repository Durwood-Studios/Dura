## Why this matters

Your service is degraded. Users are complaining. Your team is arguing about whether to ship the new feature or stop everything to fix reliability. Without shared, measurable targets, this argument never resolves — the loudest voice wins. Service Level Objectives give every team member the same scoreboard so reliability decisions become engineering problems, not politics.

For teams practicing SRE or any modern operations discipline, error budgets are how you prevent two failure modes simultaneously: SRE teams that say "no" to every release in the name of reliability, and product teams that ship constantly and ignore stability. The error budget is the mathematical middle ground — you get to spend exactly as much reliability as you can afford, no more.

## Start with something familiar

A travel allowance permits some delays, but repeated overruns require changing the plan.

## The mental model

> An SLO defines a target for a measured service indicator; an error budget quantifies permitted bad outcomes over a window.

## From "the site is slow" to a number

Before naming any concept, consider what it means to manage a service without reliability targets. An on-call engineer wakes up at 2 AM. The monitoring dashboard shows "elevated error rate." But elevated compared to what? Is 0.5% errors on a checkout service acceptable? What about 2%? Without a baseline, every incident is a subjective debate.

A **Service Level Indicator** (SLI) is a carefully defined metric that captures one dimension of user experience. A good SLI is:

- Directly measurable from your infrastructure
- Directly correlated to user pain
- Expressed as a ratio or rate, not a raw count

Common SLIs:

- Request success rate: `successful_requests / total_requests`
- Latency percentile: "99th percentile of request duration"
- Availability: "fraction of minutes the service returned successful responses"

> _An SLI is just a number that tells you how your service is actually performing from the user's perspective._

## SLOs: the target

A **Service Level Objective** (SLO) is a target value (or range) for an SLI, measured over a rolling window. It is an internal commitment — your team's goal for itself.

```yaml
# An SLO document for a payment processing service
service: payment-processor
slos:
  - name: availability
    sli: "successful HTTP responses / total HTTP responses"
    # Exclude 4xx client errors — those aren't our reliability problem
    exclude: "status_code >= 400 AND status_code < 500"
    target: 99.9% # 43.8 minutes of downtime allowed per month
    window: 30d # Rolling 30-day window, not calendar month

  - name: latency
    sli: "p99 request duration"
    target: "< 500ms" # 99% of requests complete in under 500ms
    window: 30d

  - name: checkout-success
    sli: "successful checkout completions / checkout attempts"
    target: 99.5% # Business-critical — tighter than general availability
    window: 7d # Weekly window for faster feedback
```

## SLAs: the external contract

A **Service Level Agreement** (SLA) is a contractual obligation to a customer, usually with financial penalties for violations. Teams often choose a stricter internal SLO to provide a buffer, but actual SLA terms, measurement windows, exclusions, and remedies must be read from the contract.

```
Internal SLO: 99.9% availability  ← what your team targets
External SLA: 99.5% availability  ← what you promise customers

The 0.4% gap is your safety margin.
If your SLO fails, you have time to fix it before the SLA triggers.
```

## Error budgets: your reliability currency

The error budget is the inverse of your SLO target: it is the amount of unreliability you are _allowed_ to have.

```javascript
// Error budget math
function calculateErrorBudget(sloTarget, windowDays) {
  const totalMinutes = windowDays * 24 * 60;

  // How much downtime is allowed?
  const allowedDowntimeMinutes = totalMinutes * (1 - sloTarget / 100);

  return {
    sloTarget: `${sloTarget}%`,
    windowDays,
    totalMinutes,
    allowedDowntimeMinutes: allowedDowntimeMinutes.toFixed(1),
    // Mental model: this is your "budget" to spend on risky deployments
    // and incidents before customers feel real pain
  };
}

console.log(calculateErrorBudget(99.9, 30));
// { sloTarget: "99.9%", windowDays: 30, totalMinutes: 43200,
//   allowedDowntimeMinutes: "43.2" }

console.log(calculateErrorBudget(99.99, 30));
// { sloTarget: "99.99%", windowDays: 30, totalMinutes: 43200,
//   allowedDowntimeMinutes: "4.3" }
// Four nines = 4 minutes of downtime budget per month
```

## Burn rate: how fast you're spending the budget

Burn rate tells you how quickly you're consuming your error budget relative to the expected pace. A burn rate of 1 means you're spending exactly at the budgeted rate — you'll use the full budget by the end of the window. A burn rate of 5 means you're spending 5× faster than sustainable.

```javascript
function calculateBurnRate(currentErrorRate, sloTarget) {
  // errorBudgetFraction = 1 - (sloTarget / 100)
  // e.g., for 99.9% SLO: errorBudgetFraction = 0.001
  const errorBudgetFraction = 1 - sloTarget / 100;

  // Burn rate = actual error rate / budgeted error rate
  const burnRate = currentErrorRate / errorBudgetFraction;

  let severity;
  if (burnRate > 14.4) {
    // At this rate, you'll exhaust your 30-day budget in under 2 hours
    severity = "page-immediately";
  } else if (burnRate > 6) {
    // Budget exhausted in under 5 days
    severity = "page-within-1-hour";
  } else if (burnRate > 1) {
    // Burning faster than sustainable, but not emergency
    severity = "ticket-and-monitor";
  } else {
    // Within budget
    severity = "no-action";
  }

  return { burnRate: burnRate.toFixed(2), severity };
}

// Service with 99.9% SLO currently seeing 2% error rate
console.log(calculateBurnRate(0.02, 99.9));
// { burnRate: "20.00", severity: "page-immediately" }
// 2% errors on a 99.9% SLO = burning budget 20× faster than allowed
```

## The error budget policy

The policy answers: _what do we do when the budget is running low?_

```yaml
# Example error budget policy
error_budget_policy:
  thresholds:
    healthy: # > 50% budget remaining
      action: "normal release cadence"

    at_risk: # 25-50% remaining
      action: "reduce release velocity"
      steps:
        - "increase canary deployment percentage"
        - "add reliability work to sprint backlog"

    critical: # < 25% remaining
      action: "reliability sprint"
      steps:
        - "pause non-critical feature releases"
        - "engineering team shifts to reliability work"
        - "root-cause all recent incidents"

    exhausted: # 0% remaining (SLO violated)
      action: "freeze releases"
      steps:
        - "no new features until budget recovers"
        - "incident review with leadership"
        - "SLO target re-evaluation"
```

The policy transforms error budgets from metrics into decisions. It removes the need for a debate: "we have 15% budget left, the policy says reliability sprint."
