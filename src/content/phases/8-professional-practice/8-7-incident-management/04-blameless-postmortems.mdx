## Why this matters

Every incident is expensive twice. First, during the outage itself — lost revenue, engineering time, user trust eroded. Second, after the outage, if nothing changes and the same failure recurs. The post-mortem is what determines whether the second cost is zero or compounding. A post-mortem that assigns blame and moves on produces zero learning. A post-mortem that identifies systemic weaknesses and ships action items converts a painful incident into permanent improvement.

Blameless culture is not about ignoring responsibility — it is about recognizing that humans in complex systems will always make errors, and that the system is responsible for making those errors survivable. When blame is removed from the equation, engineers report incidents honestly, participate in post-mortems openly, and propose improvements without fear of career consequences. Blame-heavy cultures produce hidden incidents, underreporting, and the same failures recurring for years.

## Why "the engineer made a mistake" is never the root cause

Imagine a surgeon who leaves a sponge inside a patient. The hospital could fire the surgeon ("they were careless") and move on. Or it could ask: why doesn't our surgical checklist require a sponge count before closure? Why doesn't our equipment have RFID tags that alert if something is left behind? Why was this surgeon on their 14th consecutive hour when the error occurred?

The surgeon's mistake is real. It is also the last link in a chain of systemic failures that made the mistake possible, probable, and uncaught. Firing the surgeon doesn't shorten the chain.

> _A blameless post-mortem asks: "What made this failure possible?" — not "Who caused this failure?"_

## The post-mortem document structure

A post-mortem is not a bug report. It is a structured artifact that captures what happened, why it happened (at the systemic level), and what the organization will do to prevent recurrence.

```markdown

**Severity**: SEV-2
**Duration**: 15 minutes (14:32–14:47 UTC)

## Root Cause Analysis

### What happened (surface level)

A configuration variable `PAYMENT_TIMEOUT_MS` was renamed to
`PAYMENT_REQUEST_TIMEOUT` in v2.4.1. The old variable name was still
referenced in the request handler. Node.js read `undefined` for the
timeout, which defaulted to 0ms — causing every payment validation
request to immediately time out.

### Five Whys

**Why** did checkout fail?
→ Payment validation requests timed out immediately.

**Why** did they time out?
→ The timeout was read as `undefined`, which evaluated to 0ms.

**Why** was it `undefined`?
→ The config variable was renamed in the new version but the read path
still referenced the old name.

**Why** wasn't this caught before deploy?
→ The integration test suite uses mocked payment responses and does not
test against real config variable names.

**Why** doesn't the integration test use real config?
→ The test environment was set up 18 months ago with hardcoded values
for speed; config validation was never added to CI.

**Root cause**: No CI step validates that all required configuration
variables are present and non-undefined at startup. A renamed variable
cannot fail fast during testing.

---

## Contributing Factors (not root cause, but made this worse)

1. **20-minute MTTD**: The error rate exceeded threshold at 14:25 but the
   alert didn't fire until 14:32. Our alert requires 3 consecutive minutes
   above threshold — this is tuned for noise reduction but delayed detection
   by 7 minutes.

2. **No canary deployment**: v2.4.1 was deployed to 100% of traffic
   immediately. A 5% canary would have limited blast radius while detection occurred.

3. **No startup config validation**: The service starts successfully even
   with critical config variables missing — it only fails at request time.

---

## Action Items

| Priority | Action                                                                                                                | Owner | Due        |
| -------- | --------------------------------------------------------------------------------------------------------------------- | ----- | ---------- |
| P0       | Add startup config validation to payment-service that throws on undefined required vars                               | Bob   | 2026-06-17 |
| P1       | Add integration test that boots the service with production config schema and validates all required vars are present | Carol | 2026-06-20 |
| P1       | Enable canary deployments for payment-service (5% for 10 min before full rollout)                                     | Dave  | 2026-06-22 |
| P2       | Reduce MTTD by changing alert to 1-minute window with higher threshold (tune for faster detection without more noise) | Alice | 2026-06-24 |

---

## What went well

- IC declared incident and opened channel within 2 minutes of alert
- Rollback decision was made quickly — 6 minutes from alert to rollback start
- All stakeholder updates followed the established template
- Resolution was communicated clearly with a timeline for next steps
```

## The Five Whys in practice

The Five Whys is a technique for following the causal chain from symptom to system. The rule: keep asking "why" until you reach something the organization can actually fix. If your final "why" is "the engineer made a mistake," you stopped too early.

```javascript
// Modeling a Five Whys analysis as a chain
function fiveWhys(symptom, chain) {
  // Each item in the chain: { observation, why }
  // The final item's "why" should be a systemic root cause the org can fix

  const analysis = chain.reduce(
    (acc, step, index) => {
      acc.push({
        level: index + 1,
        observation: step.observation,
        why: step.why,
        // Is this a human error or a system property?
        isSystemic:
          !step.observation.toLowerCase().includes("engineer forgot") &&
          !step.observation.toLowerCase().includes("developer made"),
      });
      return acc;
    },
    [{ level: 0, observation: symptom, why: "See chain below" }]
  );

  const rootCause = chain[chain.length - 1];
  const stoppedAtBlame = chain.some(
    (step) =>
      step.observation.toLowerCase().includes("forgot") ||
      step.observation.toLowerCase().includes("mistake") ||
      step.observation.toLowerCase().includes("didn't know")
  );

  return {
    chain: analysis,
    rootCause: rootCause.why,
    // A good Five Whys analysis never stops at blame
    warning: stoppedAtBlame
      ? "⚠️ Analysis may have stopped at human error — dig deeper for system cause"
      : null,
  };
}

const analysis = fiveWhys("Payment service is returning 100% errors", [
  {
    observation: "Payment validation requests are timing out",
    why: "Timeout config variable is undefined",
  },
  {
    observation: "Config variable is undefined at runtime",
    why: "Variable was renamed but read path was not updated",
  },
  {
    observation: "Rename was not caught in testing",
    why: "Tests use hardcoded values, not real config variables",
  },
  {
    observation: "Tests don't validate config",
    why: "No CI requirement to test config completeness at startup",
  },
]);

console.log("Root cause:", analysis.rootCause);
console.log("Warning:", analysis.warning ?? "None — systemic root cause found");
```

## Evaluating action items

The quality of a post-mortem is measured by the quality of its action items. A good action item is specific, owned, time-boxed, and addresses a contributing factor or root cause — not a symptom.

```javascript
// Framework for evaluating post-mortem action items
function evaluateActionItem(item) {
  const checks = [
    {
      name: "specific",
      pass: !item.description.includes("improve") && !item.description.includes("better"),
      // "Improve monitoring" is not specific. "Add alert for config variable undefined at startup" is.
    },
    {
      name: "has-owner",
      pass: item.owner && item.owner !== "team",
      // "Team" is not an owner. One named person is.
    },
    {
      name: "has-due-date",
      pass: !!item.dueDate,
      // Without a date, action items are wishes.
    },
    {
      name: "addresses-cause",
      pass: item.addressedFactor !== "symptom",
      // Fixing the immediate symptom without fixing what made it possible = recurrence
    },
    {
      name: "preventive-not-reactive",
      // "Write a runbook for this failure" = reactive. Good.
      // "Add test that prevents this class of failure" = preventive. Better.
      pass: item.type !== "purely-reactive",
    },
  ];

  const failingChecks = checks.filter((c) => !c.pass);
  return {
    quality:
      failingChecks.length === 0 ? "good" : failingChecks.length <= 1 ? "acceptable" : "weak",
    issues: failingChecks.map((c) => c.name),
  };
}

// Example: weak action item
console.log(
  evaluateActionItem({
    description: "Improve our deployment process to be safer",
    owner: "team",
    dueDate: null,
    addressedFactor: "symptom",
    type: "purely-reactive",
  })
);
// { quality: "weak", issues: ["specific", "has-owner", "has-due-date", "preventive-not-reactive"] }

// Example: good action item
console.log(
  evaluateActionItem({
    description:
      "Add startup validation to payment-service that throws ConfigError if PAYMENT_REQUEST_TIMEOUT is undefined",
    owner: "bob-torres",
    dueDate: "2026-06-17",
    addressedFactor: "root-cause",
    type: "preventive",
  })
);
// { quality: "good", issues: [] }
```

## What you learned

- Blameless post-mortems trace failures to systemic causes — missing safeguards, absent tests, insufficient monitoring — rather than individual errors, because fixing systems prevents recurrence while assigning blame does not
- The Five Whys technique follows the causal chain until it reaches something the organization can change; stopping at "human error" leaves the chain incomplete
- An incident timeline distinguishes events (what happened) from contributing factors (what made it worse) from root cause (what made it possible)
- Strong action items are specific, owned by one person, time-boxed, and address a contributing factor or root cause — not the surface symptom
- Post-mortem quality is measured by whether action items actually ship and prevent the same class of failure from recurring

You now have the full incident management stack: from defining reliability targets through SLOs and error budgets, to running on-call rotations with quality runbooks, to executing structured incident response, to learning from failures through blameless post-mortems. These practices together define what it means to operate production software responsibly.
