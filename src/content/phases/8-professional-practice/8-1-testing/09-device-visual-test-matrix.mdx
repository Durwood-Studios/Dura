## Why this matters

A page passes a desktop screenshot comparison while its submit button disappears behind a mobile keyboard. Mobile quality needs functional, visual and device-specific evidence together.

## Start with something familiar

Checking a coat on one mannequin does not establish its fit on every wearer or while sitting down. A test matrix selects meaningful conditions rather than multiplying screenshots without a purpose.

## The mental model

> Select devices and conditions from supported users and risks. Pair stable visual baselines with behavior checks; browser emulation and pixel similarity are useful evidence with clear limits.

## The mechanism

Start with the promised device/browser support and observed users, then choose representative risk combinations. For a lesson-note form, the initial matrix might include a narrow 320 CSS-pixel web viewport, a current desktop browser, an actual lower-memory Android device and an actual iOS device if supported. Record OS/browser/build, viewport, text scale, input method, connectivity and the task. This is a sample plan, not a claim that those four rows cover every mobile environment.

Use a deterministic local fixture to learn visual comparisons. Save the following as note.spec.ts in a Playwright Test project. It serves no external site and has no private data.

```typescript
import { test, expect } from '@playwright/test';

test('narrow note form keeps the action visible and operable', async ({ page }) => {
  await page.setViewportSize({ width: 320, height: 568 });
  await page.setContent(`<style>*{box-sizing:border-box}body{margin:0;padding:16px;font:16px sans-serif}main{max-width:28rem}textarea{display:block;width:100%;min-height:8rem}button{min-height:48px;margin-top:12px}</style><main><label for="note">Practice note</label><textarea id="note"></textarea><button type="button">Save locally</button><p role="status"></p></main><script>document.querySelector('button').addEventListener('click',()=>{document.querySelector('[role=status]').textContent='Saved in this fixture';});</script>`);
  await page.getByLabel('Practice note').fill('A long note remains editable.');
  await page.getByRole('button', { name: 'Save locally' }).focus();
  await page.keyboard.press('Enter');
  await expect(page.getByRole('status')).toHaveText('Saved in this fixture');
  const bounds = await page.getByRole('button').boundingBox();
  expect(bounds).not.toBeNull();
  if (!bounds) throw new Error('Missing action geometry');
  expect(bounds.x).toBeGreaterThanOrEqual(0);
  expect(bounds.x + bounds.width).toBeLessThanOrEqual(320);
  await expect(page).toHaveScreenshot('note-320.png', { animations: 'disabled' });
});
```

The button’s message is deliberately a fixture acknowledgement; it does not persist the note. Run the test in a configured Playwright project, inspect the initial image, then deliberately accept that baseline using the documented snapshot workflow. On later failures, inspect actual/expected/difference images and classify intended change versus regression. Do not automatically update every baseline to make CI green.

Keep browser/OS/fonts/test data stable for comparable screenshots. Mask only unrelated unstable regions with a documented reason; masking the form would hide the feature under test. A visual match does not prove keyboard operation, persistence, semantics or screen-reader usability. The functional assertions cover a few separate behaviors, not all accessibility requirements.

Real-device checks still need virtual keyboard occlusion, text scaling, orientation, touch behavior, memory pressure and interrupted connectivity appropriate to the feature. Browser viewport emulation does not run the actual Android/iOS operating system or native keyboard. Record untested matrix rows rather than reporting a universal mobile pass.
