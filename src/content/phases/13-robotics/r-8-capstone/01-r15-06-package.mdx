## The capstone framing

Lessons R1–R7 built the literacy. R8 builds the deliverable. The capstone is a complete R15.06-2025 risk-assessment package for a simulated cobot cell of your choosing — a pick-and-place station, a collaborative-assembly station, a machine-tending application. You select the cell, you do the analysis, you produce the documents, you hash-anchor the package via /verify.

The package will be evaluated against the same criteria a customer or auditor would use. The grading rubric below is exactly the rubric an experienced integrator applies when they receive a package for review.

## Step 1 — Define the cell

In one page, document:

- **Application** — what the cell does, what part(s) it handles, what production rate.
- **Robot** — vendor, model, payload, reach, joint count. Confirm PFL-capability if you're using PFL mode.
- **End-effector** — geometry, payload weight, how it grips. PFL-relevant: any sharp edges, any pinch points, any rigid surfaces > 1 cm².
- **Operator interaction model** — what does the human do, where do they stand, when do they reach in, what handover happens.
- **Operating modes** — which ISO 10218-1:2025 collaborative mode is active in normal operation, which mode for setup, which mode for maintenance.

A common mistake at this step: spending three pages on the cell description and one page on the actual safety analysis. The cell-definition page is for grounding the analysis; it is not the analysis.

## Step 2 — ISO 12100 risk assessment

Walk the four-step ISO 12100 process explicitly. Each step is its own section.

### 2a. Determination of limits

Spatial, temporal, use limits. What's inside the cell, when is it operational, who uses it, what foreseeable misuse exists.

### 2b. Hazard identification

A table of every identified hazard. Columns: hazard ID, source (robot motion / end-effector / energy / chemical / etc.), affected human action, severity, frequency, possibility of avoidance. Use the ISO 12100 hazard taxonomy as a checklist — don't invent your own.

### 2c. Risk estimation

For each hazard, a risk score using whatever method you choose (HRN, ISO 13849-1 risk graph, etc.). Document the method explicitly.

### 2d. Risk evaluation

For each hazard, evaluate whether the risk is acceptable as-is or requires reduction. If reduction is required, name the safety function that will reduce it (this is the link to Step 3).

The traceability from hazard → safety function is the single most important auditable artifact in the package. Without it, an auditor cannot verify that the safety functions cover the identified hazards.

## Step 3 — Safety-function design (ISO 13849 / IEC 62061)

For each safety function identified in Step 2d, a one-page sheet documenting:

- **Function** — what the safety function does ("e-stop drops drive power within 100 ms of activation").
- **Trigger** — what causes it to fire.
- **Action** — what response occurs.
- **Sensors / logic / actuators** — the architecture (Category B / 1 / 2 / 3 / 4 per ISO 13849 or HFT per 62061).
- **Required PL or SIL** — the target from the risk graph or matrix.
- **Achieved PL or SIL** — based on the components used (MTTF_D, DC_avg, CCF for 13849; HFT and architectural constraints for 62061).
- **Gap** — required vs achieved. If gap > 0, redesign required.

For PL ↔ SIL: do NOT use a lookup table to claim equivalence (Lesson R3). State PL and SIL as the respective standards define them; if the cell uses both 13849 and 62061 for different functions, that's fine — document each in its native framing.

## Step 4 — Collaborative-mode declaration (ISO 10218-1:2025)

For each operational state, the active collaborative mode and the supporting safety functions. From Lesson R4:

- **Setup mode** — typically HG (Hand Guiding). Safety functions: enabling-device monitoring, speed-limit monitoring.
- **Normal operation** — typically SSM (Speed and Separation Monitoring) or PFL (Power and Force Limiting), depending on the application.
- **Maintenance mode** — typically SMS (Safety-rated Monitored Stop) or full lockout-tagout.

The transitions between modes are themselves safety functions (Lesson R4) and need to appear in the Step 3 design sheets.

### 4a. PFL applications — Annex A force/pressure budget

If any operational state uses PFL, this section is required. From Lesson R5, an Annex A force/pressure budget is a table:

- **Row per body region** the operator's body could contact (forehead, sternum, hand, finger, etc.).
- **Quasi-static threshold** from ISO 10218-1:2025 Annex A.
- **Transient threshold** from Annex A.
- **Measured or calculated value** at this body region given the cell's geometry, payload, and speed.
- **Margin** — measured vs limit, with the % margin documented.

A package without an Annex A force/pressure budget for a PFL application is incomplete by definition. The validation references RIA TR R15.806 for the measurement methodology if measurement was performed; if calculation, the calculation method is documented.

## Step 5 — Cybersecurity overlay (ISO 10218-1:2025 × IEC 62443)

From Lesson R7. The cybersecurity section includes:

- **Zone-and-conduit diagram** in 62443 notation, with the safety controller, application controller, teach pendant, and plant network as separate zones.
- **SL target** for each zone with one sentence of justification.
- **The four 10218-1:2025 overlay requirements** mapped to specific zones and conduits:
  - Secure boot — safety controller zone, confirmed by vendor documentation.
  - Signed firmware updates — robot controller zone, confirmed by vendor documentation.
  - Safety-controller network segmentation — the conduit between application and safety controllers, with the safety-protocol restriction documented.
  - Teach-pendant authentication — pendant zone, with auth policy documented (password, biometric, or RFID; auto-lock interval; privileged-operation elevation).

If any of the four overlay requirements cannot be satisfied (e.g., the robot model in use doesn't support secure boot), this is a residual risk that must appear in Step 6.

## Step 6 — Residual risk register

Every hazard from Step 2 that was NOT reduced to acceptable by a safety function, AND every overlay requirement from Step 5 that could not be fully satisfied, appears in the residual risk register. Each entry has:

- The hazard or unsatisfied requirement.
- Why it cannot be further reduced (technical, economic, or operational reason).
- The residual control — operator training, procedural lockout, signage, PPE.

A package with zero residual risks is suspicious; real installations always have residuals.

## Step 7 — Sign-off and hash-anchoring

The package is a single PDF (or markdown bundle) with all the above sections. The final pages include:

- **Sign-off** — the integrator who produced the package, the customer who accepts it, the date.
- **Verification record** — the hash-anchor produced via /verify.

To produce the verification record:

1. Finalize the package — no more edits.
2. Compute SHA-256 of the finalized file.
3. Submit the hash to /verify (the DURA verification layer).
4. /verify returns a signed certificate with the hash and timestamp.
5. The signed certificate is appended to the package as Appendix V.

A reviewer can later recompute SHA-256 of the package (excluding Appendix V), compare to the hash on the certificate, and verify the signature against the DURA public key. If all three match, the package is provably the exact bytes that were anchored at the timestamp shown. After-the-fact edits to hide gaps would invalidate the hash and be visible.

## The grading rubric

The same rubric an experienced integrator applies when reviewing a package for a customer:

| Section                   | Acceptable                                                               | Incomplete                                                |
| ------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------- |
| Cell definition           | 1 page, sufficient to ground the analysis                                | Missing operator-interaction model                        |
| ISO 12100 risk assessment | All four steps explicit, with hazard → safety function traceability      | Steps merged or traceability absent                       |
| Safety-function design    | One sheet per function with required vs achieved PL/SIL and gap analysis | PL ↔ SIL conflated, or gap analysis missing               |
| Collaborative mode        | Mode named per operational state, with supporting safety functions       | Cell described as "collaborative" without naming the mode |
| Annex A budget (if PFL)   | Table of body regions × thresholds × measured/calculated with margins    | Missing entirely, or thresholds cited without measurement |
| Cybersecurity overlay     | Zone-and-conduit diagram + four 10218-1:2025 additions mapped            | "Conforms to 62443" with no overlay mapping               |
| Residual risk register    | Honest list with controls                                                | Empty or implausibly short                                |
| Hash anchor               | /verify certificate present in Appendix V                                | Missing or invalid                                        |

## How to submit

When your package is ready:

1. Compute SHA-256 of the package file.
2. Visit `/verify` and submit the hash with the package title "R15.06-2025 Risk Assessment — [your cell name]".
3. Save the signed certificate returned by /verify.
4. Append it to your package as Appendix V.
5. Publish the package wherever you publish portfolio work (GitHub, personal site, LinkedIn). Include the /verify URL so reviewers can audit the anchor.

The /verify URL is the credentialing layer for this capstone. A hiring manager who has heard "I did the DURA Phase R capstone" can paste the hash into /verify and see the certificate. That's the alternative to a vendor cert — verifiable, portfolio-grounded proof of work.

## What's next

You've completed Phase R. The hash-anchored capstone package is portfolio evidence: a hiring manager or customer can audit it directly via /verify. Phase R's next iteration depends on your trajectory:

- If you're targeting **manufacturing engineering more broadly**, Phase M takes the standards-discipline mindset you built here and applies it to ISO 9001 quality, AS9100 aerospace, IATF 16949 automotive, ISA-95/88 process control, MTConnect / OPC UA shop-floor integration, and the Lean/Six Sigma operational frameworks.
- If you're targeting **safety-certified ROS 2 production**, the next step is hands-on with Apex.Grace and a deeper dive into ISO 26262 ASIL D. That curriculum lives outside DURA today.
- If you're targeting **functional safety more generally** (across machinery beyond robots), IEC 61508 itself + ISO 13849 deeper architecture work is the natural progression.

Whatever the next direction, you now have what Phase R promised: the standards literacy to read, write, and certify safety work in 2025-vintage robotics.
