## Why this matters

A cell can have well-designed production and setup behavior yet leave a gap while switching between them. Releasing an enabling device, turning a key or resetting a fault must not be assumed to establish all conditions for automatic movement. Review transitions as carefully as stable states.

## Start with something familiar

A railway handover is incomplete if one controller stops protecting a section before the next confirms responsibility. The handover itself needs a protocol. A robot application's protective functions need similarly explicit continuity when the operating state changes.

## The mental model

> Request a transition, establish its required conditions, confirm the receiving protection, then authorize the new behavior. On failure or ambiguity, retain the specified protective response instead of treating a mode label as proof.

## Separate state, request, reset and start

A mode request expresses an intention to change behavior. A confirmed state indicates that the required conditions are established. A reset acknowledges or clears a permitted condition according to the design. A start command initiates movement when the design permits it. These are not interchangeable events.

For a teaching example, use states `GUIDED_SETUP`, `TRANSITION_HOLD`, `AUTO_READY`, `AUTO_RUNNING` and `FAULT_STOP`. Maintenance energy isolation belongs to a separate task-specific procedure; a software state named `MAINTENANCE` does not physically isolate stored energy.

| Transition | Conditions and resulting behavior to specify |
| --- | --- |
| Guided setup → transition hold | Request accepted; guiding movement ends using the specified protective response; relevant protection remains active. |
| Transition hold → auto ready | Required state confirmed; correct automatic-operation safeguards/configuration active; occupancy/access conditions established. No automatic trajectory starts merely because the state changes. |
| Auto ready → auto running | Valid deliberate start under the required conditions; motion remains protected throughout. |
| Any state → fault stop | Defined response to the fault; retain or establish protection appropriate to the hazard, including gravity/energy where relevant. |
| Fault stop → ready state | Cause addressed, required reset and checks completed; no direct jump to arbitrary prior motion solely from reset. |

This is a conceptual review model, not executable safety-controller software. The application may need other states, concurrent protective functions or supported transitions. Derive them from the actual tasks and manufacturer's architecture.

## Which conditions are safety-related?

“Production recipe downloaded” might be a process prerequisite. “Protective field active and valid for this motion” may be part of a safety-related condition if preventing harm depends on it. A procedural authorization can be important without being a sensor signal or standalone PL-rated function.

For every condition relied upon for safety, identify its source, failure behavior, required integrity and validation evidence. Derive required performance from the applicable robot/application requirements and risk assessment; speed and payload alone do not produce a universal PL d rating. The [2025 ISO 10218 update described by A3](https://www.automate.org/robotics/news/updated-iso-10218-major-advancements-in-industrial-robot-safety-standards-now-available) retains distinct robot and application responsibilities with more explicit functional requirements.

## Maintain protection during the handover

Do not disable a relied-upon protective function simply because the new state was requested. Confirm the necessary replacement or continuing protection before permitting the newly hazardous behavior. Analyze asynchronous updates, stale confirmation, communication loss and timeout.

A confirmed standstill can be a useful transition condition, but “always home position with an empty trajectory queue” is not a universal standard rule. A home position could itself be hazardous, and some supported transitions may preserve adequate protection during motion. Specify and validate the actual safe condition rather than copying a universal checklist.

Where the design requires standstill, distinguish a command from confirmation. Where it requires personnel-clear conditions, a released key or a clear boundary beam alone may not establish that nobody remains inside. Consider whole-body access, hidden positions and the intended restart procedure.

## Analyze both directions

Changing from setup to automatic operation can introduce unexpected motion. Changing from production to intervention can expose stored energy, gravity or process hazards. Neither direction is always harmless or universally “the most dangerous.” Trace the hazards in each direction.

For example, return from maintenance needs the approved restoration procedure: people and tools accounted for, isolation restored/removed under the authorized process, safeguards verified, and controlled readiness/start behavior. Entering maintenance needs its own energy-control and access conditions. A key switch is an input to the process, not proof that the physical task is safe.

[HSE's machine-intervention guidance](https://www.hse.gov.uk/paper/machine-interventions.htm) emphasizes planned safe intervention. Its scope is operational guidance; the actual robot control functions and isolation procedures still follow the applicable application requirements.

## Evidence for the transition review

Keep a state/transition model with triggers, conditions, accepted behavior and failed-condition responses. Link safety-related conditions to function specifications and evidence. Test normal transitions, rejected requests, held inputs, simultaneous requests, communication failure, power restoration and reset/start behavior where relevant.

Record the configuration, authorization roles and validation results. A transition diagram is useful because it makes omissions visible, not because drawing a diagram itself certifies the system.

## What you learned

- Model states, requests, guarded transitions and failure responses explicitly.
- Distinguish process prerequisites from safety-related conditions and their evidence.
- Maintain the required protective conditions throughout transitions instead of assuming a mode label is sufficient.
- Analyze missing guards and both return directions, including isolation, occupancy and unintended restart.
