## Why the math matters here

In Lesson R3-2, the ISO 13849 path to a Performance Level went through a chart lookup: Category × MTTFd × DC → PL. The chart is fast but opaque — you can't see the probability arithmetic behind it.

IEC 62061 shows the arithmetic explicitly. Every subsystem contributes a numerical PFHD (average probability of dangerous failure per hour). The system PFHD is the sum of subsystem contributions. You compare the sum to the SIL band table.

This explicitness is a double-edged tool. It gives auditors a traceable record they can verify component by component. It also exposes calculation errors that a chart lookup would mask.

## The system structure IEC 62061 uses

An IEC 62061 analysis structures the safety function as a chain of **subsystems**. A subsystem is a group of elements that together perform a distinct portion of the safety function — typically sensors (input subsystem), logic (logic subsystem), and actuators (output subsystem).

Each subsystem has:

- One or more **elements** (individual components or channels).
- An **architecture** — how elements are arranged (single, redundant, voted).
- A **PFHD contribution** calculated from the element failure rates and architecture.

The system PFHD is the sum: PFHD_system = PFHD_input + PFHD_logic + PFHD_output.

## Type A vs Type B subsystems

IEC 62061 (and its parent IEC 61508) distinguishes two types of subsystem based on failure-mode knowledge:

**Type A:** All failure modes of all constituent elements are well-defined and well-known (e.g., a relay with documented fail-open and fail-closed rates from a data sheet). No complex internal behavior.

**Type B:** The subsystem has complex internal behavior such that all failure modes cannot be exhaustively defined (e.g., a programmable safety controller with firmware). Type B is conservative — it's harder to achieve a given SIL from a Type B subsystem.

The distinction matters for the **architectural constraint**: Type B subsystems require more Hardware Fault Tolerance than Type A subsystems to achieve the same SIL.

**Hardware Fault Tolerance (HFT)** is the minimum number of additional faults (beyond the single worst-case fault) a subsystem can tolerate while still performing the safety function. HFT = 0 means a single fault can prevent the function. HFT = 1 means two simultaneous faults are needed to prevent the function. HFT = 2 means three.

## The architectural constraint table

IEC 62061 Table 4 (for Type A) and Table 5 (for Type B) define the minimum HFT required to claim each SIL. Here are the constraints (simplified):

**Type A subsystems (well-known failure modes):**

| SIL   | Minimum HFT if Safe Failure Fraction < 60% | ... < 90% | ... ≥ 90% |
| ----- | ------------------------------------------ | --------- | --------- |
| SIL 1 | 1                                          | 0         | 0         |
| SIL 2 | 2                                          | 1         | 0         |
| SIL 3 | 3                                          | 2         | 1         |

**Type B subsystems (complex failure modes, e.g., programmable logic):**

| SIL   | Minimum HFT if Safe Failure Fraction < 60% | ... < 90% | ... ≥ 90% |
| ----- | ------------------------------------------ | --------- | --------- |
| SIL 1 | 1                                          | 1         | 0         |
| SIL 2 | 2                                          | 1         | 1         |
| SIL 3 | 3                                          | 2         | 2         |

**The constraint in action:** A programmable safety controller (Type B) claiming SIL 2 with a Safe Failure Fraction (SFF) of 92% requires HFT ≥ 1. That means it must be in a 1oo2 or 2oo3 architecture — a single-channel (1oo1) programmable controller CANNOT claim SIL 2 regardless of how good its PFHD number is. The architectural constraint is a hard structural floor.

This is the mechanism that prevents the "pile up cheap components to hit the number" workaround. Even if a 1oo1 Type B controller has an excellent PFHD, the architectural constraint blocks the SIL 2 claim.

## Computing subsystem PFHD

### Single-channel (1oo1) architecture

For a single-channel subsystem with one element of dangerous failure rate λ_D (dangerous failures per hour):

> PFHD_1oo1 = λ_D × (1 − DC)

Where DC is the fraction of dangerous failures detected by built-in diagnostics (same concept as ISO 13849's DC). The undetected fraction (1 − DC) is what actually threatens the safety function.

### 1oo2 (redundant) architecture

Two independent channels, each with dangerous failure rate λ_D_A and λ_D_B. A dangerous system failure requires both channels to fail dangerously without detection.

Simplified IEC 62061 formula for 1oo2 (ignoring CCF for now):

> PFHD_1oo2 ≈ λ_D_A_U × λ_D_B_U × T₁

Where:

- λ_D_A_U = λ_D_A × (1 − DC) — dangerous undetected rate for channel A.
- λ_D_B_U = λ_D_B × (1 − DC) — dangerous undetected rate for channel B.
- T₁ = the proof-test interval in hours (typically 8760 h = 1 year).

Adding the common-cause failure contribution (which a single point of failure can make both channels fail together):

> PFHD_1oo2_total = PFHD_1oo2_independent + β × (λ_D_A + λ_D_B)/2

Where β is the common-cause failure fraction (typically 0.02–0.10 depending on CCF measures).

### Worked example

A 1oo2 safety-rated light-curtain pair:

- λ_D = 5 × 10⁻⁸ /h per channel (from data sheet)
- DC = 0.99 (continuous self-test per Annex E) → λ_D_U = 5 × 10⁻⁸ × 0.01 = 5 × 10⁻¹⁰ /h
- T₁ = 8760 h (annual proof test)
- β = 0.02 (separated channels, different supply)

Independent contribution:

> PFHD_ind = (5 × 10⁻¹⁰) × (5 × 10⁻¹⁰) × 8760 = 2.19 × 10⁻¹⁵ /h

CCF contribution:

> PFHD_ccf = 0.02 × (5 × 10⁻⁸) = 1 × 10⁻⁹ /h

Total subsystem PFHD:

> PFHD_input ≈ 1.00 × 10⁻⁹ /h (CCF dominates — this is typical for 1oo2 designs)

Compare to SIL band: SIL 2 = PFHD ≥ 10⁻⁷ to < 10⁻⁶. This subsystem is within SIL 3 (10⁻⁸ to 10⁻⁷) numerically — but the architectural constraint check for Type A with SFF ≥ 99% at SIL 3 requires HFT ≥ 1. Since this is 1oo2 (HFT = 1), the constraint is satisfied. SIL 3 claim for this subsystem is supportable.

## Building the system PFHD

Once each subsystem's PFHD is computed, sum them:

> PFHD_system = PFHD_input + PFHD_logic + PFHD_output

Compare the sum to the SIL band table (IEC 62061 Table 3):

| SIL   | PFHD range       |
| ----- | ---------------- |
| SIL 1 | ≥ 10⁻⁶ to < 10⁻⁵ |
| SIL 2 | ≥ 10⁻⁷ to < 10⁻⁶ |
| SIL 3 | ≥ 10⁻⁸ to < 10⁻⁷ |

If the sum falls within the target SIL's band AND all subsystems pass their architectural constraint checks, the safety function claim is substantiated.

**The system-level trap:** individual subsystems can each be well within SIL 2, but if the logic subsystem alone contributes PFHD = 8 × 10⁻⁷ /h, the system total will exceed SIL 2's upper bound regardless of how excellent the input and output subsystems are. The weakest (highest PFHD) subsystem usually dominates.

## The audit trail this produces

An IEC 62061 package for a safety function includes:

1. Subsystem breakdown diagram.
2. Per-element failure rate source (data sheet reference + λ_D value).
3. DC justification per Annex E.
4. Per-subsystem PFHD calculation (showing the formula, values, and result).
5. Subsystem type (A or B) + SFF + HFT + architectural constraint check.
6. System PFHD sum and SIL band comparison.

An auditor verifies the chain element-by-element. There is no "summary number" to accept or reject — every assumption is visible.
