## Why software is different

In Lesson R3-3, you calculated PFHD for hardware subsystems. The math worked because hardware failures are (modeled as) random — a component fails at a statistical rate λ_D that you can look up on a data sheet.

Software doesn't fail randomly. A software defect is a fixed property of the code: either the code has a bug or it doesn't. If a safety function has been running for six months without triggering the bug's condition, the next six months are just as likely to trigger it as the first six. There is no wear-out model; there is no λ for software bugs.

IEC 62061 calls hardware failures **random hardware failures** and software failures **systematic failures**. Systematic failures cannot be quantified by probability; they are addressed by development process discipline. This is the fundamental reason software gets a separate treatment in the standard.

> **PFHD formulas do not apply to software. SIL for software is achieved by applying the right development process, not by computing a failure rate.**

## The software SIL target

When a safety function is rated to SIL N, the software component(s) within that function inherit a software SIL target of SIL N. The target drives which development practices are mandatory.

IEC 62061 Section 6 defines the Software Safety Lifecycle — the structured set of activities, documentation, and verification steps that a software component must go through to support a given SIL claim.

The lifecycle maps onto the classical V-model:

```
Requirements ─────────────────────────────► System validation test
    └─ Software safety requirements ──────► Software validation test
           └─ Software architecture ──────► Software integration test
                  └─ Module design ────────► Module test
                         └─ Coding ────────► Unit test
```

Each step on the left has a verification step on the right. The documentation from each step is part of the safety file — the package that an assessor reviews. Missing a step means missing a verification — and the assessor will find the gap.

## Development constraints by SIL

IEC 62061 Annex D provides a table of software design techniques with their IEC 62061 applicability at SIL 1, SIL 2, and SIL 3. The designations are:

- **HR** (Highly Recommended) — effectively mandatory; non-use requires documented justification.
- **R** (Recommended) — use should be considered.
- **—** (Not Recommended) — use should be avoided; use requires documented justification.

### Language and tooling constraints

| Technique                              | SIL 1 | SIL 2 | SIL 3 |
| -------------------------------------- | ----- | ----- | ----- |
| Strongly-typed language                | HR    | HR    | HR    |
| Language subset with excluded features | R     | HR    | HR    |
| Validated compiler / translator        | R     | HR    | HR    |
| Static analysis of source code         | R     | HR    | HR    |

**Practical impact:** For SIL 2, you are effectively required to use a strongly-typed language with documented exclusions of unsafe features (in C/C++: excluded are unconstrained pointer arithmetic, implicit casts, dynamic allocation in safety paths, recursion in time-critical paths). A validated compiler — one that has been qualified per IEC 62061 / EN 50128 compiler qualification requirements — is HR. In practice this means using tools like LDRA, Polyspace, or the vendor's qualified toolchain for the safety controller.

### Coding practices

| Technique                            | SIL 1 | SIL 2 | SIL 3 |
| ------------------------------------ | ----- | ----- | ----- |
| Defensive programming                | HR    | HR    | HR    |
| Limited use of interrupts            | HR    | HR    | HR    |
| No dynamic objects (heap allocation) | R     | HR    | HR    |
| Limited use of global variables      | R     | HR    | HR    |
| Structured programming (no GOTO)     | HR    | HR    | HR    |

**Defensive programming** in a safety context means anticipating invalid inputs, out-of-range sensor values, and unexpected state transitions — and responding to them by transitioning to a defined safe state rather than undefined behavior.

### Verification requirements

| Technique                         | SIL 1 | SIL 2 | SIL 3 |
| --------------------------------- | ----- | ----- | ----- |
| Formal proof of correctness       | —     | R     | HR    |
| Structural coverage (MC/DC)       | R     | HR    | HR    |
| Software fault injection testing  | R     | HR    | HR    |
| Independent software verification | R     | HR    | HR    |

**Modified condition/decision coverage (MC/DC)** is a coverage metric used in DO-178C (aviation) and required at SIL 2 and above in IEC 62061. It ensures that each condition in a decision has been independently exercised in a way that affects the decision outcome. Achieving MC/DC typically requires 2^n − 1 or more test cases per n-condition decision.

**Independent verification** at SIL 2 means the software is reviewed and tested by a person or team who did not write it. At SIL 3, the independence requirement is stronger (typically a separate organizational unit or external assessor).

## The safety file for software

The output of a conforming software development process is a **software safety file** — the collected documentation that an assessor uses to evaluate whether the software SIL claim is substantiated. A complete file includes:

1. **Software safety requirements specification (SSRS)** — derived from the system-level safety requirements. Each requirement is uniquely identified and traceable upward to a system hazard and downward to a test case.

2. **Software architecture description** — the decomposition of the software into modules, with identification of which modules participate in the safety function and the interfaces between them.

3. **Module design documents** — design-level description of each module, including inputs, outputs, state machines, and defensive programming responses.

4. **Source code** — with evidence of the coding-practice constraints applied (language subset compliance, static analysis results, no heap allocation in safety paths, etc.).

5. **Test documentation** — unit test results with MC/DC coverage evidence; integration test results; validation test results against the SSRS.

6. **Verification and validation records** — evidence of independent review at the appropriate SIL level.

The SSRS-to-test traceability matrix is what auditors check first: every safety requirement must have at least one test that specifically exercises it, and the test result must be "pass." Missing rows in the traceability matrix are missing coverage — a finding.

## What this means for robot safety controllers

Most modern robot safety controllers run application-level safety logic programmed by the integrator — typically in a graphical IEC 61131-3 language (Structured Text, Function Block Diagram, Ladder Diagram). This application logic participates in the safety function and must conform to the software SIL requirements.

In practice:

- The **controller's OS and base firmware** are covered by the manufacturer's safety qualification. The manufacturer provides a safety manual specifying which configuration is covered.
- The **application safety logic** written by the integrator is the integrator's scope. It must conform to the SIL target of the safety function.

A common scope-underestimation: an integrator receives a pre-certified safety controller and assumes the SIL rating covers their application logic. It does not. The manufacturer's SIL rating covers the platform. The integrator's logic is their responsibility, subject to IEC 62061's software requirements for the SIL target.

## What's next

You've now covered the hardware and software dimensions of a SIL-rated safety function. Lesson R3-5 addresses the time dimension: proof-test intervals — how often the safety function must be exercised to maintain the PFHD calculation's validity — and the maintenance obligations that come with them. Proof-test intervals are a frequent gap in operational safety programs: the PFH calculation is done at design time, but the calculation is only valid if the assumed test interval is actually kept in the field.
