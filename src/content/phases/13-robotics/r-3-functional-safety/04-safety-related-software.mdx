## Why this matters

A controller can execute the wrong stop logic perfectly. Hardware reliability calculations do not discover an omitted requirement, an unsafe state transition or a misconfigured parameter. Software assurance must connect the intended safety behavior to the actual implementation and evidence that it behaves as required.

## Start with something familiar

A reliable calculator will repeatedly give the wrong engineering answer if you enter the wrong equation. Checking its battery does not check your model. Software review needs both correct execution and a correct specification.

## The mental model

> Hazard → software requirement → design/code/configuration → verification → application validation. Trace both directions so that no safety requirement lacks evidence and no unexplained behavior hides outside the specification.

## Systematic failures are a different problem

A code or configuration defect is systematic: a particular combination of state, inputs and timing can trigger it repeatedly. Long failure-free operation may provide useful operational evidence but does not, by itself, substantiate the absence of such defects or establish a software SIL. Neither “the next six months are equally likely to fail” nor “no bugs occurred, so software PFH_D is zero” follows from the observation.

Random hardware failure models concern a different mechanism. Do not insert an arbitrary software defect rate into the hardware PFH_D sum. Requirements analysis, design constraints, verification, change control and validation address the systematic failure problem.

## Establish the applicable software route

[IEC 62061:2021](https://webstore.iec.ch/en/publication/59927) identifies software requirements in Clause 8, including software use cases and verification independence. It distinguishes machinery control-system integration from the design of complex programmable electronic subsystems, which is outside its scope.

For a project, establish whether the work is parameterization, application programming using the supported language/library, or development/modification of the underlying programmable platform. Record the applicable standard edition, safety-function requirement, manufacturer's safety manual, toolchain constraints and verification responsibilities. A SIL number alone does not identify every required technique.

Do not import a generic “SIL 1/2/3” checklist or an aviation/railway tool rule and label it an IEC 62061 requirement. Terms such as mandatory, recommended and highly recommended have meaning in the specific source and context; a dash in a table does not universally mean “prohibited.” Check the actual applicable clause and permitted alternatives.

## Connect development to evidence

A V-model is a useful organization for linking design artifacts to their checks:

```text
Safety requirements       <-> application validation
Software requirements     <-> requirement-based verification
Architecture/interfaces   <-> integration tests and reviews
Module design and code    <-> module tests and static analysis
```

These are relationships, not a demand to put each artifact in a separate document. A controlled repository can hold requirements, models, code, test results, reviews and change history while preserving the necessary traceability and independence.

For each safety requirement, record a stable identifier, source, conditions, expected response and timing. Test normal cases, boundaries, invalid inputs and relevant faults. Review whether the requirements themselves are complete and whether software interacts safely with the rest of the machine.

A requirement such as “stop safely” is not testable enough. An application-specific version identifies the triggering signal, allowed operating modes, defined response, response-time limit and restart conditions. Those values must come from the actual safety-function specification, not this lesson's example.

## Worked example: decision coverage is not the whole argument

Consider a teaching-only permission expression:

```text
permit = guardClosed AND resetAccepted
```

This is not a complete restart-safety design. It is a small Boolean expression for examining test evidence.

Tests `(false,false) -> false` and `(true,true) -> true` exercise both decision outcomes. They do not isolate the effect of each condition. The three cases `(true,true) -> true`, `(false,true) -> false`, and `(true,false) -> false` show each condition independently affecting the decision.

This illustrates modified condition/decision coverage (MC/DC), explained in [NASA's tutorial](https://ntrs.nasa.gov/citations/20010057789). MC/DC is not generally “2^n−1 tests”; suitable simple expressions can achieve it with n+1 tests, while coupling and expression structure need careful analysis. NASA's aviation-focused explanation is a source for the testing concept, **not** evidence that every IEC 62061 SIL 2 application has an identical MC/DC mandate.

Even perfect structural coverage of this expression would not prove that `resetAccepted` has the right lifecycle, that automatic restart is prevented, or that the guard input is trustworthy. Requirements, state transitions, fault response and application validation remain essential.

## Platform and application responsibilities

The platform supplier's evidence has defined versions, features, restrictions and assumptions. The integrator must follow the safety manual, control configuration and develop/verify the application within the supported scope. Changing firmware, libraries or tool versions can change the validity of that evidence.

A useful application evidence set includes requirements and traceability; architecture and interfaces; controlled source and configuration; reviews and analysis results; requirement-based tests and justified coverage; integration/application validation; unresolved anomalies and their disposition; and version/change records. Select the required independence and techniques from the applicable route, rather than inventing a universal organizational structure for each SIL.

> You stop treating “runs on certified hardware” or “all branches covered” as a complete software argument. You look for a traced requirement and justified evidence for each safety-relevant behavior.

## What you learned

- Distinguish systematic software defects from random hardware failure calculations.
- Establish the software route and supplier constraints before selecting development and verification techniques.
- Trace requirements through design, controlled implementation, verification and application validation.
- Analyze structural-coverage evidence without mistaking it for a complete safety argument.
