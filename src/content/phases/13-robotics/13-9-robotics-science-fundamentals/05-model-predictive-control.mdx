## Why this matters

A controller can use a model to compare possible future actions before choosing the next command. Model predictive control (MPC) makes that choice explicit through an optimization problem. Its predictions depend on the model, state estimate, constraints, and solver; a feasible prediction is not a guarantee of safe physical behavior.

Think of planning several moves in chess, making one move, then reconsidering after the board changes. MPC similarly plans ahead but applies the first action before updating its information.

> Predict candidate trajectories, choose a feasible low-cost sequence, apply its first input, and repeat from the new estimate. Handle model error, infeasibility, and solver timing as part of the controller design.

## Optimization starting points

An objective assigns a cost to each candidate action sequence; constraints define the feasible set of permitted sequences. Minimization chooses the lowest-cost feasible candidate, not the lowest-cost forbidden one. For x = [2, 3] and diagonal Q = diag(1, 2), the quadratic cost xᵀQx is 1×2² + 2×3² = 22. Positive weights penalize deviations, while actuator and state bounds remain explicit constraints. The worked controller below uses a finite candidate set so you can verify the selection without assuming access to a general optimization solver.


## Formulate the problem

For a linear discrete-time model x_next = A x + B u, choose a horizon N and input sequence u_0 through u_(N−1). Predict states from the current estimate. Penalize tracking error e_i = x_i − reference_i and input effort with a sum of e_iᵀ Q e_i + u_iᵀ R u_i, plus a terminal cost e_Nᵀ P e_N if used.

State and input constraints describe the permitted predictions. Q and P are normally positive semidefinite, and R positive definite, in the standard convex quadratic formulation. A terminal cost alone does not automatically prove stability; applicable assumptions, terminal conditions, feasibility, and controller design matter.

At each sample, solve or approximately solve the stated problem within its time budget. Apply the first input and use the next state estimate for another solve. Replanning supplies feedback, but robustness to uncertainty requires appropriate design and analysis.

## Worked example: finite candidates, explicit limits

Use the teaching model x_next = x + u, initial x = 0, target x = 1, horizon two, and input candidates −0.5, 0, 0.5. Require −1 ≤ x ≤ 1 at every predicted step. Define cost as the sum, over the two next states, of (x−1)² + 0.1u².

For sequence [0.5, 0.5], predicted states are 0.5 and 1.0. Cost is 0.25 + 0.025 + 0 + 0.025 = 0.30. For [0.5, 0], states are 0.5 and 0.5; cost is 0.25 + 0.025 + 0.25 = 0.525. Both satisfy the stated constraints; the first has lower cost among these two candidates.

Apply only the first input, 0.5. If the next measured state is 0.4, replan from 0.4 rather than assuming the predicted 0.5 occurred. Enumerating a few discrete candidates is a teaching approximation, not a general continuous quadratic-programming solver.

## Feasibility and computation

An empty feasible set is a result the controller must handle. Do not silently apply zero and label it safe; zero input may still violate a state constraint in a moving system. Define an appropriate verified fallback or supervisory response for infeasibility, failed state estimates, and missed deadlines.

A longer horizon can reveal future constraints but increases problem size. Runtime does not universally grow quadratically: formulation, solver, sparsity, warm starts, and stopping criteria matter. Increasing the horizon does not guarantee lower closed-loop tracking error in every implementation.

Ordinary PID does not solve this constrained prediction problem, but it can coexist with feedforward, trajectory planning, anti-windup, and supervisory constraints. Replacing PID with MPC does not automatically prevent real joint-limit violations. State-estimation error, model mismatch, latency, and protection outside the optimizer still matter.

## What you learned

- Formulate predicted dynamics, tracking/input costs, and explicit constraints.
- Apply the first input and replan from updated state information.
- Analyze horizon and solver trade-offs without a universal runtime or performance promise.
- Distinguish predicted feasibility from robust control and independent protection requirements.
