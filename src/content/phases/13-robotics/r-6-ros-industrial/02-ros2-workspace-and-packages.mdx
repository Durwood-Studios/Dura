## Why workspace hygiene matters

A ROS 2 workspace is not a folder you dump files into. It is a structured build environment that colcon (the build tool) expects to find in a specific layout, with specific manifest files. If the layout is wrong, the build fails silently or with errors that send beginners down the wrong debugging path for hours.

Getting the workspace right on the first try is the difference between spending three hours on "environment setup" and spending three hours writing actual code. This lesson removes the setup tax.

## The workspace layout

A ROS 2 workspace has four directories that colcon manages:

```
my_ws/
├── src/          ← your packages live here (human-edited)
├── build/        ← colcon's build artifacts (do not edit)
├── install/      ← installed packages, ready to source (do not edit)
└── log/          ← colcon build logs
```

The `src/` directory is the only one you create manually. The other three are generated by colcon. Never put packages in `build/` or `install/` — they are overwritten on every build.

## Creating a Python package

ROS 2 packages come in two flavors: `ament_cmake` (C++) and `ament_python` (Python). For Python nodes:

```bash
# From inside the workspace root (my_ws/)
cd src
ros2 pkg create --build-type ament_python my_robot_nodes
```

This creates:

```
src/my_robot_nodes/
├── my_robot_nodes/        ← Python module (same name as package)
│   └── __init__.py
├── resource/
│   └── my_robot_nodes     ← marker file required by ament_python
├── test/
│   ├── test_copyright.py
│   ├── test_flake8.py
│   └── test_pep257.py
├── package.xml            ← package manifest (required)
└── setup.py               ← entry points for executables
```

## package.xml — the build-system contract

The `package.xml` file tells colcon what this package is, what it depends on, and how to build it. A minimal `package.xml` for a Python package that subscribes to sensor data:

```xml
<?xml version="1.0"?>
<?xml-model href="http://download.ros.org/schema/package_format3.xsd"
            schematypens="http://www.w3.org/2001/XMLSchema"?>
<package format="3">
  <name>my_robot_nodes</name>
  <version>0.1.0</version>
  <description>Minimal publisher and subscriber example.</description>
  <maintainer email="you@example.com">Your Name</maintainer>
  <license>Apache-2.0</license>

  <!-- Build toolchain -->
  <buildtool_depend>ament_python</buildtool_depend>

  <!-- Runtime dependencies -->
  <depend>rclpy</depend>
  <depend>std_msgs</depend>
  <depend>sensor_msgs</depend>

  <!-- Test dependencies (linting, etc.) -->
  <test_depend>ament_copyright</test_depend>
  <test_depend>ament_flake8</test_depend>
  <test_depend>ament_pep257</test_depend>
  <test_depend>python3-pytest</test_depend>

  <export>
    <build_type>ament_python</build_type>
  </export>
</package>
```

The `<depend>` elements drive colcon's dependency ordering. If package B depends on package A, colcon builds A first. Missing a dependency here means your package builds in isolation on your machine (because everything is already installed) but fails on a fresh machine or CI.

## setup.py — registering executable scripts

For Python packages, `setup.py` maps script names to Python entry points:

```python
from setuptools import find_packages, setup

package_name = 'my_robot_nodes'

setup(
    name=package_name,
    version='0.1.0',
    packages=find_packages(exclude=['test']),
    data_files=[
        ('share/ament_index/resource_index/packages',
            ['resource/' + package_name]),
        ('share/' + package_name, ['package.xml']),
    ],
    install_requires=['setuptools'],
    zip_safe=True,
    maintainer='Your Name',
    maintainer_email='you@example.com',
    description='Minimal publisher and subscriber example.',
    license='Apache-2.0',
    tests_require=['pytest'],
    entry_points={
        'console_scripts': [
            # 'cli_name = package.module:function'
            'my_publisher = my_robot_nodes.publisher_node:main',
            'my_subscriber = my_robot_nodes.subscriber_node:main',
        ],
    },
)
```

The `console_scripts` list is how `ros2 run my_robot_nodes my_publisher` works — it calls the `main()` function in `my_robot_nodes/publisher_node.py`.

## Writing a publisher node

Create `my_robot_nodes/publisher_node.py`:

```python
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class MinimalPublisher(Node):
    """
    Publishes a counter message every 500 ms on the 'chatter' topic.

    Topic naming convention: use snake_case, group by namespace
    (/robot/arm/joint_states, not JointStates or jointStates).
    """

    def __init__(self) -> None:
        super().__init__('minimal_publisher')
        # QoS depth=10: keep the last 10 messages in the queue
        self._publisher = self.create_publisher(String, 'chatter', 10)
        # Timer fires every 0.5 s; ROS 2 timers are clock-accurate
        self._timer = self.create_timer(0.5, self._timer_callback)
        self._count = 0

    def _timer_callback(self) -> None:
        msg = String()
        msg.data = f'Hello, world: {self._count}'
        self._publisher.publish(msg)
        self.get_logger().info(f'Publishing: "{msg.data}"')
        self._count += 1


def main(args: list[str] | None = None) -> None:
    rclpy.init(args=args)
    node = MinimalPublisher()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        # Always destroy and shutdown — prevents resource leaks
        node.destroy_node()
        rclpy.shutdown()
```

## Writing a subscriber node

Create `my_robot_nodes/subscriber_node.py`:

```python
import rclpy
from rclpy.node import Node
from std_msgs.msg import String


class MinimalSubscriber(Node):
    """
    Subscribes to 'chatter' and logs each received message.

    The topic name must match the publisher exactly — case-sensitive.
    In production: use topic remapping in launch files rather than
    hardcoding names in the node itself.
    """

    def __init__(self) -> None:
        super().__init__('minimal_subscriber')
        # Same QoS depth as the publisher — mismatched QoS is a common gotcha
        self.create_subscription(
            String,
            'chatter',
            self._listener_callback,
            10,
        )

    def _listener_callback(self, msg: String) -> None:
        self.get_logger().info(f'Received: "{msg.data}"')


def main(args: list[str] | None = None) -> None:
    rclpy.init(args=args)
    node = MinimalSubscriber()
    try:
        rclpy.spin(node)
    except KeyboardInterrupt:
        pass
    finally:
        node.destroy_node()
        rclpy.shutdown()
```

## Building and running

```bash
# From the workspace root (my_ws/)
colcon build --packages-select my_robot_nodes

# Source the install overlay (must be done in every new terminal)
source install/setup.bash

# Terminal 1: run the publisher
ros2 run my_robot_nodes my_publisher

# Terminal 2: run the subscriber
ros2 run my_robot_nodes my_subscriber

# Terminal 3: verify message flow without running a node
ros2 topic echo /chatter
ros2 topic hz /chatter   # verify ~2 Hz rate (500 ms period)
```

## Underlays and overlays

Every `source install/setup.bash` command adds the current workspace's install directory to `$AMENT_PREFIX_PATH` and `$PYTHONPATH`. This is called **sourcing the overlay**.

The chain is:

```
/opt/ros/jazzy/setup.bash     ← underlay (ROS 2 base install)
    ↓ sourced first
~/my_ws/install/setup.bash    ← overlay (your packages extend the underlay)
```

If you have two workspaces, each overlay extends the previous. If two workspaces define the same package, the most recently sourced overlay wins. This causes the "I changed the code but the old version is running" bug — you sourced an overlay that has a stale build.

**The clean-build rule:** when changing `package.xml`, `setup.py`, or adding/removing files, always run `colcon build` again before testing. `ros2 run` uses the installed copies, not the source copies.

## Three common colcon build errors

**Error 1: `ModuleNotFoundError: No module named 'my_robot_nodes'`**

Root cause: `setup.py` entry point module path is wrong, or `packages=find_packages(exclude=['test'])` didn't find the package because the directory lacks `__init__.py`.

Fix: confirm `src/my_robot_nodes/my_robot_nodes/__init__.py` exists (the inner directory is the Python module; the outer directory is the ROS package).

**Error 2: `stderr: CMake Error — No such file or directory`**

Root cause: `package.xml` says `ament_cmake` but the package was created as `ament_python`, or vice versa. The build type must match `<export><build_type>`.

Fix: check the `<export>` section in `package.xml` and confirm it matches the scaffolded build files.

**Error 3: `[ERROR] [launch]: Caught exception in launch (see debug for traceback)`**

Root cause: a node was installed correctly but the entry point function (`main`) raised an exception at import time — usually a missing dependency that's installed on your machine but not in `package.xml`.

Fix: run `ros2 run my_robot_nodes my_publisher` directly (not via launch) to see the raw Python traceback, identify the missing import, and add it to `package.xml`.
