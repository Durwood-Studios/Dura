## Why a hardware abstraction layer matters

Without ros2_control, every controller that wants to move a joint has to know the robot's specific communication protocol: USB HID for a hobby servo, EtherCAT for an ABB IRC5, the Universal Robots RTDE protocol for a UR arm. When you switch robots, you rewrite the controller.

<VocabTooltip slug="ros2-control">ros2_control</VocabTooltip> inverts this. The controller talks to
a generic interface: "set joint_1 position to 1.2 rad." The hardware interface translates that into
whatever the physical hardware needs. The controller does not change when you swap robots.

This is the same abstraction pattern as POSIX between application and OS, or JDBC between application code and a specific database.

## The three-layer architecture

```
┌──────────────────────────────────────────────┐
│              CONTROLLERS                      │
│  JointTrajectoryController                   │
│  JointGroupVelocityController                │
│  ForwardCommandController                    │
│  (loaded/activated by the controller manager)│
└────────────────────┬─────────────────────────┘
                     │  reads/writes StateInterface + CommandInterface
┌────────────────────▼─────────────────────────┐
│         CONTROLLER MANAGER (CM)              │
│  - owns the real-time update loop            │
│  - manages controller lifecycle              │
│  - exposes /controller_manager/* services    │
└────────────────────┬─────────────────────────┘
                     │  owns ResourceManager, calls read()/write()
┌────────────────────▼─────────────────────────┐
│           HARDWARE INTERFACES                │
│  robot_hardware::SystemInterface plugin      │
│  (one per physical robot or simulation)      │
│  read()  → update state interfaces           │
│  write() ← apply command interfaces         │
└──────────────────────────────────────────────┘
```

**Controllers** implement motion logic — PID, trajectory following, gravity compensation. They see joints as a list of StateInterfaces (current position, velocity, effort) and CommandInterfaces (position command, velocity command, effort command).

**Controller Manager** is the scheduler. It runs the update loop at a fixed rate (typically 1 kHz for position control, 500 Hz for most cobots). It activates and deactivates controllers and enforces that only one controller owns any given command interface at a time.

**Hardware Interfaces** are the boundary to the real world. They implement `read()` and `write()` — called by the CM every loop cycle. `read()` copies the robot's current state into the StateInterfaces; `write()` copies the CommandInterfaces into the robot command buffer.

## The control YAML — wiring everything together

The ros2_control configuration lives in a YAML file referenced from the URDF (or launched separately). For a 2-joint simulated arm:

```yaml
# ros2_control.yaml
controller_manager:
  ros__parameters:
    update_rate: 1000 # Hz — real-time loop rate

    # Declare which controllers to load at startup
    joint_trajectory_controller:
      type: joint_trajectory_controller/JointTrajectoryController

    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster

joint_trajectory_controller:
  ros__parameters:
    joints:
      - joint_1
      - joint_2
    command_interfaces:
      - position # this controller commands position
    state_interfaces:
      - position
      - velocity
    # Tolerances for trajectory execution
    constraints:
      stopped_velocity_tolerance: 0.01 # rad/s
      goal_time: 5.0 # seconds to reach the goal
    gains:
      joint_1:
        p: 100.0
        i: 0.5
        d: 10.0
        i_clamp: 10.0
      joint_2:
        p: 80.0
        i: 0.5
        d: 8.0
        i_clamp: 8.0
```

The URDF must declare the `<ros2_control>` block that describes the hardware interface and its interfaces:

```xml
<!-- Inside the URDF, after the kinematic chain -->
<ros2_control name="simple_arm_hardware" type="system">
  <hardware>
    <!-- For simulation: use the mock hardware (always installed) -->
    <plugin>mock_components/GenericSystem</plugin>
  </hardware>

  <joint name="joint_1">
    <command_interface name="position">
      <param name="min">-3.14159</param>
      <param name="max"> 3.14159</param>
    </command_interface>
    <state_interface name="position"/>
    <state_interface name="velocity"/>
    <state_interface name="effort"/>
  </joint>

  <joint name="joint_2">
    <command_interface name="position">
      <param name="min">-1.5708</param>
      <param name="max"> 1.5708</param>
    </command_interface>
    <state_interface name="position"/>
    <state_interface name="velocity"/>
    <state_interface name="effort"/>
  </joint>
</ros2_control>
```

`mock_components/GenericSystem` is the built-in hardware interface for testing: it mirrors command interfaces directly to state interfaces, simulating a perfect robot.

## Writing a hardware interface plugin

For a real robot, you write a hardware interface that inherits from `hardware_interface::SystemInterface`:

```cpp
// my_robot_hardware/my_robot_hardware.hpp
#pragma once

#include <string>
#include <vector>
#include "hardware_interface/system_interface.hpp"
#include "hardware_interface/types/hardware_interface_return_values.hpp"
#include "rclcpp/rclcpp.hpp"

namespace my_robot_hardware {

class MyRobotHardware : public hardware_interface::SystemInterface {
public:
  // Called once at startup — parse parameters, open communications
  hardware_interface::CallbackReturn on_init(
    const hardware_interface::HardwareInfo & info) override;

  // Return the list of StateInterface objects this hardware exports.
  // Called once after on_init; the CM registers these with controllers.
  std::vector<hardware_interface::StateInterface> export_state_interfaces() override;

  // Return the list of CommandInterface objects this hardware exports.
  std::vector<hardware_interface::CommandInterface> export_command_interfaces() override;

  // Called when a controller that needs this hardware is activated.
  // Establish communication, enable servos, verify connection.
  hardware_interface::CallbackReturn on_activate(
    const rclcpp_lifecycle::State & previous_state) override;

  // Called when all controllers that need this hardware are deactivated.
  // Disable servos, close communications gracefully.
  hardware_interface::CallbackReturn on_deactivate(
    const rclcpp_lifecycle::State & previous_state) override;

  // THE REAL-TIME LOOP — called every control cycle.
  // MUST be deterministic. MUST NOT allocate memory. MUST NOT block.
  hardware_interface::return_type read(
    const rclcpp::Time & time, const rclcpp::Duration & period) override;

  hardware_interface::return_type write(
    const rclcpp::Time & time, const rclcpp::Duration & period) override;

private:
  // Position state (populated by read(), exposed to controllers)
  std::vector<double> position_state_;
  // Position command (written by controllers, consumed by write())
  std::vector<double> position_command_;
};

}  // namespace my_robot_hardware
```

The `read()` / `write()` contract is strict:

```cpp
hardware_interface::return_type MyRobotHardware::read(
  const rclcpp::Time & /*time*/, const rclcpp::Duration & /*period*/)
{
  // This runs at 1 kHz. Rules:
  // 1. Do NOT call ROS logging here (allocates memory → priority inversion)
  // 2. Do NOT sleep or block
  // 3. Do NOT call non-realtime code
  //
  // Correct pattern: read from a double buffer populated by a separate
  // communication thread; copy to position_state_ atomically.
  for (std::size_t i = 0; i < position_state_.size(); ++i) {
    // Assuming comm_buffer_ is updated by a separate real-time-safe thread
    position_state_[i] = comm_buffer_.joint_positions[i];
  }
  return hardware_interface::return_type::OK;
}

hardware_interface::return_type MyRobotHardware::write(
  const rclcpp::Time & /*time*/, const rclcpp::Duration & /*period*/)
{
  for (std::size_t i = 0; i < position_command_.size(); ++i) {
    comm_buffer_.joint_commands[i] = position_command_[i];
  }
  // Trigger the communication thread to send the commands to hardware
  comm_buffer_.command_ready.store(true, std::memory_order_release);
  return hardware_interface::return_type::OK;
}
```

## Activating controllers at runtime

The controller manager exposes lifecycle-management services. From the command line:

```bash
# List available controllers
ros2 control list_controllers

# List available hardware interfaces
ros2 control list_hardware_interfaces

# Activate a controller
ros2 control set_controller_state joint_trajectory_controller active

# Activate/deactivate via the spawner (use in launch files)
ros2 run controller_manager spawner joint_trajectory_controller
ros2 run controller_manager unspawner joint_trajectory_controller
```
