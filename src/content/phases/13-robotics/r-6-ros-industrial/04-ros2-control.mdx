## Why this matters

A trajectory controller and a robot driver exchange more than joint names. They must agree on command type, state feedback, lifecycle readiness, and timing. A controller that loads successfully may still be unable to claim the required hardware interfaces.

Think of a hardware interface as a socket with a documented electrical contract. Matching the connector name is insufficient if one side supplies voltage and the other expects a current command.

> Match each joint's command and state interfaces, then verify activation and the read–update–write cycle. Framework configuration is not evidence of real-time deadlines or physical safety.

## Three responsibilities

The controller computes commands from goals and state. The controller manager coordinates controllers and the update cycle. Hardware components expose interfaces and implement communication with the simulated or actual device.

In the common synchronous cycle, hardware `read()` updates state, controller `update()` computes commands, and hardware `write()` sends them. Hardware lifecycle callbacks such as `on_activate()` are distinct from a controller's activation; do not assume that activating one controller necessarily opens or closes the hardware connection. Use the installed distribution's hardware and controller lifecycle rules.

The abstraction does not require every robot vendor to use the same interface, nor does it eliminate driver-specific requirements. Select a supported driver rather than inventing a transport or assuming a controller works on all robots.

## Worked configuration for two simulated joints

This fragment assumes a compatible simulated hardware component exposing position commands plus position and velocity states for `joint_1` and `joint_2`. It is not a complete launch or robot description.

```yaml
controller_manager:
  ros__parameters:
    update_rate: 100
    arm_trajectory:
      type: joint_trajectory_controller/JointTrajectoryController
    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster

arm_trajectory:
  ros__parameters:
    joints: [joint_1, joint_2]
    command_interfaces: [position]
    state_interfaces: [position, velocity]
```

The requested 100 Hz is a teaching setting, not a measured deadline guarantee. The hardware description and launch must provide compatible interfaces and load/configure/activate the desired components.

For the position command interface, the [Jazzy trajectory-controller documentation](https://control.ros.org/jazzy/doc/ros2_controllers/joint_trajectory_controller/doc/userdoc.html) describes forwarding desired positions. Adding arbitrary PID gains to this example does not create a torque PID loop. Other supported interface combinations have different behavior and feedback requirements.

## Verify readiness and execution

Check which interfaces are exported and claimed, and whether the controller is active. A joint name or interface mismatch is a concrete reason activation may fail. Confirm measured state uses the correct units and semantics before interpreting a trajectory result.

For a trajectory action, distinguish acceptance from completion and inspect its reported result and tolerances. Do not treat a successful transport call as proof that the commanded motion occurred. Test nominal goals, unavailable hardware, stale feedback, and rejected goals in the chosen simulation before any authorized real-device integration.

## Timing and failure behavior

A periodic update needs a bounded execution budget. Uncontrolled blocking I/O, memory allocation, locks, and logging in a critical path can affect timing. Actual requirements and implementation choices depend on the system; setting update_rate does not establish deterministic behavior.

When communication fails, the driver and supervisor need defined error handling. Sending an arbitrary zero command can mean different things for position, velocity, or effort interfaces and is not automatically a safe response. Separate application error handling from independently validated physical protective functions.

- Configure a two-joint trajectory controller with explicit names and interface types.
- Separate controller update, hardware read/write, and lifecycle transitions.
- Verify timing, failures, and execution results without inferring machinery safety.
