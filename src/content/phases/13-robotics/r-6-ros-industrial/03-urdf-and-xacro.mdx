## Why this matters

ROS 2 nodes communicate through topics, services, and actions — but they have no built-in notion of physical geometry. When MoveIt computes a motion plan, it needs to know: where are the robot's links, what are the joint limits, and what is the collision geometry to check for self-collisions and workspace obstacles?

The URDF (Unified Robot Description Format) is the answer. It's an XML file that describes the robot's kinematic tree: links connected by joints, with geometry for visualization, geometry for collision checking, and mass/inertia properties for dynamics.

XACRO (XML Macros for ROS) is the template language that makes URDF maintainable. A 6-axis robot arm has six identical-looking joint entries that differ only in parameter values — XACRO lets you write one macro and call it six times.

Think of URDF as an assembly drawing expressed as a tree: links are bodies and joints connect their frames. Visual appearance, collision geometry, and inertial behavior are separate descriptions.

> A model can look correct while its collision or inertial description is wrong. Verify the expanded model, frames, and limits for the intended tool and task.

## URDF structure: links and joints

A URDF is a tree. Nodes in the tree are **links** (rigid bodies). Edges are **joints** (connections between links with a defined motion type). Every URDF has exactly one root link (conventionally named `base_link`).

```xml
<?xml version="1.0"?>
<robot name="simple_arm">

  <!-- ===================== BASE LINK ===================== -->
  <link name="base_link">
    <visual>
      <!-- A simple cylinder as a placeholder for the robot base -->
      <geometry>
        <cylinder radius="0.1" length="0.05"/>
      </geometry>
      <material name="gray">
        <color rgba="0.5 0.5 0.5 1.0"/>
      </material>
    </visual>
    <collision>
      <!-- Collision geometry can differ from visual — keep it simple -->
      <geometry>
        <cylinder radius="0.1" length="0.05"/>
      </geometry>
    </collision>
    <inertial>
      <!-- Mass and inertia tensor — required for dynamic simulation -->
      <!-- For a uniform cylinder: Ixx = Iyy = m(3r²+h²)/12, Izz = mr²/2 -->
      <mass value="2.0"/>
      <inertia ixx="0.017" ixy="0.0" ixz="0.0"
               iyy="0.017" iyz="0.0" izz="0.010"/>
    </inertial>
  </link>

  <!-- ===================== LINK 1 ===================== -->
  <link name="link_1">
    <visual>
      <origin xyz="0 0 0.2" rpy="0 0 0"/>
      <geometry>
        <!-- Using a mesh file for real robots; box as placeholder here -->
        <box size="0.06 0.06 0.4"/>
      </geometry>
      <material name="blue">
        <color rgba="0.2 0.4 0.8 1.0"/>
      </material>
    </visual>
    <collision>
      <origin xyz="0 0 0.2" rpy="0 0 0"/>
      <geometry>
        <box size="0.06 0.06 0.4"/>
      </geometry>
    </collision>
    <inertial>
      <origin xyz="0 0 0.2" rpy="0 0 0"/>
      <mass value="1.0"/>
      <inertia ixx="0.014" ixy="0.0" ixz="0.0"
               iyy="0.014" iyz="0.0" izz="0.002"/>
    </inertial>
  </link>

  <!-- ===================== JOINT 1 ===================== -->
  <!-- Connects base_link → link_1; revolute = limited rotation -->
  <joint name="joint_1" type="revolute">
    <parent link="base_link"/>
    <child link="link_1"/>
    <!-- Origin: where the joint frame is in the parent link frame -->
    <origin xyz="0 0 0.025" rpy="0 0 0"/>
    <!-- Axis of rotation in the child link frame -->
    <axis xyz="0 0 1"/>
    <!-- Joint limits: all required for revolute joints -->
    <limit lower="-3.14159"
           upper="3.14159"
           effort="50.0"
           velocity="1.57"/>
  </joint>

  <!-- ===================== LINK 2 ===================== -->
  <link name="link_2">
    <visual>
      <origin xyz="0 0 0.15" rpy="0 0 0"/>
      <geometry>
        <box size="0.05 0.05 0.3"/>
      </geometry>
      <material name="blue"/>
    </visual>
    <collision>
      <origin xyz="0 0 0.15" rpy="0 0 0"/>
      <geometry>
        <box size="0.05 0.05 0.3"/>
      </geometry>
    </collision>
    <inertial>
      <origin xyz="0 0 0.15" rpy="0 0 0"/>
      <mass value="0.5"/>
      <inertia ixx="0.004" ixy="0.0" ixz="0.0"
               iyy="0.004" iyz="0.0" izz="0.001"/>
    </inertial>
  </link>

  <!-- ===================== JOINT 2 ===================== -->
  <joint name="joint_2" type="revolute">
    <parent link="link_1"/>
    <child link="link_2"/>
    <!-- Joint sits at top of link_1 (0.4 m up from joint_1 origin) -->
    <origin xyz="0 0 0.4" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>  <!-- Rotates around Y axis (elbow bend) -->
    <limit lower="-1.5708"
           upper="1.5708"
           effort="30.0"
           velocity="1.57"/>
  </joint>

  <!-- ===================== END EFFECTOR FRAME ===================== -->
  <!-- A fixed frame at the tool flange — no motion -->
  <link name="tool_flange"/>

  <joint name="joint_flange" type="fixed">
    <parent link="link_2"/>
    <child link="tool_flange"/>
    <origin xyz="0 0 0.3" rpy="0 0 0"/>
  </joint>

</robot>
```

## Joint types — the short reference

| Type         | Motion               | When to use                                 |
| ------------ | -------------------- | ------------------------------------------- |
| `revolute`   | Rotation with limits | Standard robot joints, hinges               |
| `continuous` | Unlimited rotation   | Wheels, conveyor rollers                    |
| `prismatic`  | Linear with limits   | Linear axes, telescoping links              |
| `fixed`      | No motion            | Tool flanges, sensor mounts, visual markers |
| `floating`   | 6 DOF free motion    | Base-mounted mobile robots in simulation    |
| `planar`     | 3 DOF in a plane     | Rarely used; planar robot bases             |

## XACRO — making URDF maintainable

A 6-axis arm has six nearly-identical joint entries. Writing each by hand means six copies of the same structure that must be updated in six places when dimensions change. XACRO solves this with macros:

```xml
<?xml version="1.0"?>
<robot name="arm6dof" xmlns:xacro="http://www.ros.org/wiki/xacro">

  <!-- ===================== PARAMETERS ===================== -->
  <xacro:property name="link_width" value="0.06"/>
  <xacro:property name="pi" value="3.14159265"/>

  <!-- ===================== LINK MACRO ===================== -->
  <!--
    Usage: <xacro:arm_link name="link_1" length="0.4" mass="1.0"/>
    Avoids repeating the visual+collision+inertial pattern for every link.
  -->
  <xacro:macro name="arm_link" params="name length mass">
    <link name="${name}">
      <visual>
        <origin xyz="0 0 ${length/2}" rpy="0 0 0"/>
        <geometry>
          <box size="${link_width} ${link_width} ${length}"/>
        </geometry>
        <material name="blue">
          <color rgba="0.2 0.4 0.8 1.0"/>
        </material>
      </visual>
      <collision>
        <origin xyz="0 0 ${length/2}" rpy="0 0 0"/>
        <geometry>
          <box size="${link_width} ${link_width} ${length}"/>
        </geometry>
      </collision>
      <inertial>
        <origin xyz="0 0 ${length/2}" rpy="0 0 0"/>
        <mass value="${mass}"/>
        <!-- Simplified inertia for a uniform box; use real values for dynamics -->
        <inertia ixx="${mass*(link_width**2 + length**2)/12}"
                 ixy="0" ixz="0"
                 iyy="${mass*(link_width**2 + length**2)/12}"
                 iyz="0"
                 izz="${mass*link_width**2/6}"/>
      </inertial>
    </link>
  </xacro:macro>

  <!-- ===================== JOINT MACRO ===================== -->
  <xacro:macro name="revolute_joint"
               params="name parent child origin_xyz origin_rpy axis lower upper effort velocity">
    <joint name="${name}" type="revolute">
      <parent link="${parent}"/>
      <child link="${child}"/>
      <origin xyz="${origin_xyz}" rpy="${origin_rpy}"/>
      <axis xyz="${axis}"/>
      <limit lower="${lower}" upper="${upper}"
             effort="${effort}" velocity="${velocity}"/>
    </joint>
  </xacro:macro>

  <!-- ===================== INSTANTIATE ===================== -->
  <link name="base_link"/>

  <xacro:arm_link name="link_1" length="0.4" mass="1.0"/>
  <xacro:arm_link name="link_2" length="0.3" mass="0.6"/>

  <xacro:revolute_joint
    name="joint_1" parent="base_link" child="link_1"
    origin_xyz="0 0 0" origin_rpy="0 0 0"
    axis="0 0 1"
    lower="${-pi}" upper="${pi}"
    effort="50.0" velocity="1.57"/>

  <xacro:revolute_joint
    name="joint_2" parent="link_1" child="link_2"
    origin_xyz="0 0 0.4" origin_rpy="0 0 0"
    axis="0 1 0"
    lower="${-pi/2}" upper="${pi/2}"
    effort="30.0" velocity="1.57"/>

</robot>
```

Process XACRO into a URDF before passing it to tools that don't speak XACRO natively:

```bash
# One-shot XACRO → URDF
xacro arm6dof.urdf.xacro > arm6dof.urdf

# Or pass through robot_state_publisher at launch (preferred)
```

## robot_state_publisher and the tf2 transform tree

The <VocabTooltip slug="robot-state-publisher">`robot_state_publisher`</VocabTooltip> node connects the model and joint state:

1. Reads the URDF from its `robot_description` parameter.
2. Listens on `/joint_states` for the current joint positions.
3. Broadcasts every joint transformation to the <VocabTooltip slug="tf2">tf2</VocabTooltip> transform tree.

Every ROS 2 tool — RViz, MoveIt, Nav2, sensor fusion — uses tf2 to look up "where is frame X relative to frame Y right now?" The robot_state_publisher keeps that answer current.

```python
# In a launch file:
from launch import LaunchDescription
from launch_ros.actions import Node
from launch_ros.parameter_descriptions import ParameterValue
from launch.substitutions import Command, FindExecutable

def generate_launch_description():
    robot_description_content = Command([
        FindExecutable(name='xacro'), ' ',
        '/path/to/arm6dof.urdf.xacro',
    ])

    robot_state_publisher_node = Node(
        package='robot_state_publisher',
        executable='robot_state_publisher',
        output='screen',
        parameters=[{
            'robot_description': ParameterValue(robot_description_content, value_type=str),
            # Use sim time when running in Gazebo
            'use_sim_time': False,
        }],
    )
    return LaunchDescription([robot_state_publisher_node])
```

## Three URDF errors that break motion planning

**Error 1: Missing `<collision>` elements**

Motion planners use the collision geometry for self-collision checking and obstacle avoidance. A link with `<visual>` but no `<collision>` is invisible to the planner. The robot will happily plan paths that drive links through obstacles or itself.

Fix: every link that can collide must have a `<collision>` element. When you don't have a mesh, use a conservative bounding box.

**Error 2: Mass and inertia all zeros**

Gazebo and dynamics-based controllers require nonzero, physically plausible mass and inertia. A link with `<mass value="0.0"/>` causes the simulator to throw warnings and produce unstable dynamics — the link either freezes or goes to infinity.

Fix: use the link's approximate geometry and a reasonable density to compute mass and inertia. For teaching models, document the geometry and mass assumptions and label the simplification. For actual dynamics, use appropriate identified or supplier data and assess model error; a guessed effective density is not sufficient validation.

**Error 3: Joint limits missing or too tight**

MoveIt's joint-space motion planner respects the URDF joint limits. If the limits are tighter than the real robot's limits, the planner will fail to find solutions in parts of the workspace that the physical robot can reach. If they are wider than the physical limits, the planner will produce trajectories the controller rejects.

Fix: use the manufacturer's published joint limits, not guesses. For ROS packages supplied by vendors (Universal Robots, Fanuc, ABB), their official ROS packages may supply the appropriate model and calibration workflow; verify unit-specific calibration where required — use those rather than writing your own.
