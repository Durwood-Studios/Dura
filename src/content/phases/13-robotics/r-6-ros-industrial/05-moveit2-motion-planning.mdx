## Why motion planning is not just IK

Inverse kinematics gives you one set of joint angles that puts the end-effector at a target pose. But:

- The path FROM the current configuration TO the IK solution might pass through a table, a fixture, or the robot itself.
- There may be multiple IK solutions; some are reachable without collisions, others are not.
- The IK solution might require passing through a kinematic singularity.
- Even if the target is reachable, the trajectory must satisfy velocity and acceleration limits.

<VocabTooltip slug="moveit">MoveIt</VocabTooltip> solves all of this. It represents the world as a
<VocabTooltip slug="planning-scene">planning scene</VocabTooltip> — the robot model, plus every
obstacle — and runs a sampling-based or optimization-based planner to find a collision-free path
from start to goal in configuration space.

## MoveIt 2 architecture

```
User code (Python/C++) → MoveGroupInterface
        ↓ action: /move_action
  MoveGroup node (the planner)
        ↓ loads URDF, SRDF, kinematics.yaml, joint_limits.yaml
  Planning Pipeline
        ↓ Request + PlanningScene + Constraints → Path
  OMPL / CHOMP / PILZ (planning algorithms)
        ↓ result: joint trajectory
  Trajectory Execution Manager
        ↓ action: /joint_trajectory_controller/follow_joint_trajectory
  ros2_control JointTrajectoryController
        ↓ read/write
  Hardware Interface → physical robot
```

The key configuration files that live in the robot's MoveIt package:

| File                             | Purpose                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------ |
| `config/robot.urdf.xacro`        | Robot model with ros2_control block                                            |
| `config/robot.srdf`              | Semantic description: planning groups, end-effectors, disabled collision pairs |
| `config/kinematics.yaml`         | IK solver selection per planning group                                         |
| `config/joint_limits.yaml`       | Optional per-joint velocity/acceleration overrides for MoveIt                  |
| `config/ompl_planning.yaml`      | OMPL planner parameters                                                        |
| `config/moveit_controllers.yaml` | Maps MoveIt trajectory output to ros2_control controllers                      |

For UR arms, the `ur_moveit_config` package provides all of these. You can start working immediately:

```bash
# Launch UR5e in simulation with MoveIt
ros2 launch ur_moveit_config ur_moveit.launch.py \
  ur_type:=ur5e use_fake_hardware:=true launch_rviz:=true
```

## Planning group and SRDF

The SRDF (Semantic Robot Description Format) tells MoveIt about logical groupings of joints. A 6-axis arm typically has one planning group (`manipulator`) containing all six joints, plus an end-effector group.

```xml
<!-- config/robot.srdf — excerpt -->
<robot name="simple_arm">
  <!-- Planning group for the arm -->
  <group name="arm">
    <joint name="joint_1"/>
    <joint name="joint_2"/>
  </group>

  <!-- End-effector link -->
  <end_effector name="gripper_ee"
                parent_link="tool_flange"
                group="arm"/>

  <!-- Disable self-collision between links that cannot contact each other -->
  <!-- Without this, the planner wastes time checking impossible collisions -->
  <disable_collisions link1="base_link" link2="link_1" reason="Adjacent"/>
  <disable_collisions link1="link_1" link2="link_2" reason="Adjacent"/>
</robot>
```

The `<disable_collisions>` entries dramatically speed up planning by removing impossible checks from the collision matrix.

## Planning and execution with Python

```python
"""
moveit_example.py — plan and execute two types of motion goals.

Run against URSim or Gazebo with MoveIt launched.
"""

import math
import rclpy
from rclpy.node import Node
from moveit.planning import MoveItPy
from moveit.core.robot_state import RobotState
from geometry_msgs.msg import Pose, Point, Quaternion
from shape_msgs.msg import SolidPrimitive
from moveit_msgs.msg import CollisionObject


class MoveItExample(Node):
    """Demonstrates joint-space and Cartesian planning with MoveIt 2."""

    def __init__(self) -> None:
        super().__init__('moveit_example')

        # MoveItPy is the Python binding to the MoveIt MoveGroupInterface
        self._robot = MoveItPy(node_name='moveit_py')
        self._arm = self._robot.get_planning_component('arm')
        self._logger = self.get_logger()

    def plan_joint_space_goal(self) -> bool:
        """
        Move to a joint configuration directly.

        Use joint-space goals when:
        - The target pose has multiple IK solutions and you want a specific one
        - You're moving to a known "home" configuration
        - Cartesian path constraints are not needed
        """
        # Set the start state (current robot state)
        self._arm.set_start_state_to_current_state()

        # Specify the goal as named state from SRDF, or as joint values
        goal_state = RobotState(self._robot.get_robot_model())
        goal_state.set_joint_group_positions(
            'arm',
            [math.radians(30), math.radians(45)],   # [joint_1, joint_2]
        )
        self._arm.set_goal_state(robot_state=goal_state)

        # Plan
        plan_result = self._arm.plan()
        if plan_result:
            self._logger.info('Joint-space plan succeeded.')
            # Execute — blocks until trajectory completes
            self._robot.execute(plan_result.trajectory, controllers=[])
            return True
        else:
            self._logger.error('Joint-space plan FAILED. Check for collisions or joint limits.')
            return False

    def plan_cartesian_goal(self, target_pose: Pose) -> bool:
        """
        Move the end-effector to a Cartesian pose.

        Use Cartesian goals when:
        - The application specifies a workpiece pose (welding seam, pick location)
        - The exact orientation of the tool matters
        - Constraints on the path direction matter less than the endpoint

        MoveIt will find the IK solution and plan in joint space internally.
        """
        self._arm.set_start_state_to_current_state()
        self._arm.set_goal_state(
            pose_stamped_msg=target_pose,
            pose_link='tool_flange',          # the link to position at target_pose
        )
        plan_result = self._arm.plan()
        if plan_result:
            self._robot.execute(plan_result.trajectory, controllers=[])
            return True
        return False

    def plan_cartesian_path(self, waypoints: list[Pose]) -> bool:
        """
        Move the end-effector through a sequence of Cartesian waypoints
        in a straight-line path.

        Use compute_cartesian_path when:
        - The tool must follow a straight line (seam welding, dispensing)
        - Intermediate poses must be respected, not just start and end
        - You need > 90% fraction of waypoints followed

        Limitation: Cartesian paths can fail near singularities.
        Always check the returned fraction (1.0 = all waypoints reached).
        """
        # compute_cartesian_path is on the planning component
        fraction, trajectory = self._arm.compute_cartesian_path(
            waypoints=waypoints,
            max_step=0.01,              # max step size in meters
            jump_threshold=0.0,         # 0.0 disables joint jump detection
        )

        if fraction < 0.9:
            self._logger.warning(
                f'Cartesian path only achieved {fraction:.0%} of waypoints. '
                'Check for singularities or collisions along the path.'
            )
            return False

        self._robot.execute(trajectory, controllers=[])
        return True

    def add_box_obstacle(self) -> None:
        """
        Add a box collision object to the planning scene.
        The planner will route around it automatically.
        """
        planning_scene_monitor = self._robot.get_planning_scene_monitor()

        with planning_scene_monitor.read_write() as scene:
            collision_object = CollisionObject()
            collision_object.header.frame_id = 'base_link'
            collision_object.id = 'obstacle_box'

            box = SolidPrimitive()
            box.type = SolidPrimitive.BOX
            box.dimensions = [0.2, 0.2, 0.5]   # x, y, z dimensions in meters

            box_pose = Pose(
                position=Point(x=0.5, y=0.0, z=0.25),
                orientation=Quaternion(w=1.0),
            )

            collision_object.primitives = [box]
            collision_object.primitive_poses = [box_pose]
            collision_object.operation = CollisionObject.ADD

            scene.apply_collision_object(collision_object)

        self._logger.info('Added obstacle box to planning scene.')
```

## Reading planning failures

MoveIt planning failures cluster in three patterns:

**Failure 1: "No motion plan found"**

The OMPL planner ran its timeout (default 5 s) without finding a valid collision-free path.

Diagnostic:

- Is the goal reachable? Check in RViz — does the goal pose appear inside the robot's reach envelope?
- Is the goal blocked by an obstacle? Visualize the planning scene in RViz (display: PlanningScene).
- Are joints at their limits? A joint at its limit cannot move in one direction.

Fix: increase planning time (`plan_request_params.max_velocity_scaling_factor`), simplify the scene, or change the goal.

**Failure 2: "IK solution not found"**

The Cartesian goal pose has no IK solution — it is either out of reach, or the IK solver cannot find a joint configuration that puts the end-effector there without violating joint limits.

Diagnostic:

- Verify the goal position is inside the robot's reach envelope.
- Check the goal orientation — it may require a wrist configuration the arm cannot achieve from the start state.

Fix: try an alternative goal orientation, or plan in joint space with a pre-computed IK solution.

**Failure 3: "Plan succeeded, execution failed"**

The plan was computed but the trajectory execution was rejected by the controller.

Common causes:

- The trajectory's start state does not match the actual robot state (robot moved between plan and execute).
- Joint velocity or acceleration in the trajectory exceeds controller limits.
- The ros2_control action server is not active.

Fix: call `set_start_state_to_current_state()` immediately before planning (not earlier), and verify the JointTrajectoryController is active with `ros2 control list_controllers`.
