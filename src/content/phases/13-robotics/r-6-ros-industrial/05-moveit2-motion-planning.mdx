## Why this matters

An inverse-kinematics solution describes a configuration, not a collision-free route to it. A motion planner considers a path through a model of the robot and environment. The result is only as applicable as that model and its current state.

Think of a route planner using a map: a valid destination does not establish a clear route, and yesterday's road map may miss today's closure. Planning success and completing the journey are different events.

> Provide the correct model, frames, state, and scene; plan; inspect the result; then separately handle execution. A Cartesian endpoint does not require a straight Cartesian path.

## Model and planning inputs

A robot description and semantic configuration identify links, joints, groups, and named states. Use the actual configured planning-group and end-effector names. Do not supply a two-joint vector to a six-joint group or assume a generic name such as arm exists for every vendor configuration.

The start state must be valid and sufficiently current. The environment model must include relevant obstacles and attached objects in the correct frames. A missing collision shape or incorrectly placed fixture can produce a plan that is clear only in the software model.

A joint-space goal specifies configuration values. A pose goal specifies an endpoint position and orientation. A Cartesian path requirement constrains intermediate motion too; it requires a suitable supported planning method and validation of the complete requested segment.

## Worked MoveItPy planning fragment

Assume a simulation already provides a configured MoveItPy instance named `robot`, with planning group `arm`, reference frame `base_link`, and tool link `tool_link`. These are explicit example names; substitute the actual configuration. This fragment requests a plan and does not execute hardware motion.

```python
from geometry_msgs.msg import PoseStamped

arm = robot.get_planning_component("arm")
arm.set_start_state_to_current_state()
goal = PoseStamped()
goal.header.frame_id = "base_link"
goal.pose.position.x = 0.35
goal.pose.position.y = 0.10
goal.pose.position.z = 0.40
goal.pose.orientation.w = 1.0
arm.set_goal_state(pose_stamped_msg=goal, pose_link="tool_link")
result = arm.plan()
if not result:
    raise RuntimeError("Planning failed; inspect state, scene, and request")
trajectory = result.trajectory
```

The [official MoveItPy tutorial](https://moveit.picknik.ai/main/doc/examples/motion_planning_python_api/motion_planning_python_api_tutorial.html) documents pose goals using `PoseStamped`, planning results, and scene-monitor updates. Check the API version in your pinned environment. A bare `Pose` lacks the frame header required by this parameter.

## Scene and result review

For a box obstacle, record a unique object ID, shape dimensions, pose, and reference frame. Apply it through the supported planning-scene interface and verify that the planner's scene actually contains it before requesting a plan. Visualizing the box elsewhere is not proof that the planning scene received it.

Review planning success, trajectory contents, joint names, limits, timing, scene applicability, and the start state before requesting execution in an authorized simulation. Treat the execution response as its own result. A successful plan does not prove that a controller accepted or completed motion.

If a Cartesian routine returns only part of a required path, preserve that result as incomplete. Do not execute ninety percent of a required path merely because it exceeds an arbitrary threshold. The task may require all of it; a partial segment needs its own explicit application decision and validation.

## Diagnose instead of retrying blindly

For an unreachable goal, inspect frames, target pose and kinematic limits. For a start-state collision, inspect the current state, attached tool and environment geometry. For a timeout, investigate the request, planner configuration and complexity; a longer timeout may help but does not prove feasibility.

Keep logs and the relevant model/scene versions so the failure can be reproduced. Model-based collision checking does not replace the physical protective system for a real robot.
