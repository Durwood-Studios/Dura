## Why this matters

A configuration change can affect the conditions under which a protective function was validated. A compromised maintenance workstation may therefore matter even if it never directly commands motion. Trace the path from access to consequence instead of labeling the whole cell secure because it has a firewall.

Think of a locked workshop with a separate cabinet of setup tools. Locking the front door helps, but authorized entry should not automatically grant permission to alter every machine setting. Different actions need different boundaries.

> Trace who can change what, through which interface, and with what physical consequences. Security controls and safety validation must support each other without treating one as proof of the other.

## Use the relevant standard scope

ISO 10218-1:2025 includes cybersecurity among its robot requirements. The applicable controlled clauses and manufacturer documentation determine the product obligations; this lesson does not invent a universal four-control checklist.

The [ISA/IEC 62443 series](https://www.isa.org/standards-and-publications/isa-standards/isa-iec-62443-series-of-standards) addresses industrial automation and control security across organizational, system, and component concerns. Its system-design risk-assessment work includes identifying the system, dividing it into zones and conduits, and determining security requirements from risk. This is relevant to controllers with physical consequences; it is incorrect to say that the family treats them merely as ordinary office computers.

A component certificate, a selected target security level, and a validated application are different evidence. Do not assign every cell a default SL 2, or translate a security level into a functional-safety PL or SIL.

## Model assets and allowed communication

A **zone** groups assets with shared security requirements. A **conduit** represents communication between zones under shared requirements. These are risk-model concepts; drawing two VLANs does not by itself establish separation or enforcement. [ISA's lifecycle overview](https://gca.isa.org/hubfs/21-29%20-%20ISAGCA/ISAGCA%20Security%20Lifecycles%20whitepaper%20FINAL.pdf) explains the zone/conduit assessment workflow.

For a fictional cell, consider the robot controller, safety-related control equipment, pendant, engineering workstation, production systems, and vendor support path. Record actual interfaces and authority. Some functions share hardware; do not assume that every controller is a separately networked device or that an ordinary application channel can modify safety limits.

For each connection, identify purpose, direction, permitted actions, authentication/authorization, integrity protection, monitoring, and failure behavior. A remote maintenance path needs particular attention because occasional use can still carry configuration authority.

## Worked example: configuration authority

A maintenance laptop can connect to a controller and change a configured workspace limit. The initial diagram shows only a production-data connection and omits the laptop.

The missing asset and conduit hide a consequential action. Investigate who can authenticate, which role can change the limit, whether changes require controlled confirmation, how the active configuration is identified, and what validation follows a change. Preserve logs and configuration versions, but do not treat a log as a preventive control.

Potential measures include limiting network access, role-based configuration rights, supported authenticated updates, and change review. Their availability and adequacy depend on the actual equipment and risk assessment. Disabling required protection to make a security control work is not an acceptable integration shortcut.

## Distinguish safeguards and their evidence

Secure boot and signed updates can support software authenticity and integrity when correctly implemented, but do not prove that authenticated software is free of defects. Authentication identifies a principal; authorization limits its actions. Network filtering reduces reachable interfaces; it does not alone validate the controller's response to an allowed message.

Plan patching, backup, restoration, and incident response around operational and safety requirements. A security update may require compatibility and change-impact checks. A communication failure must have a specified response; a firewall should not be assumed to create an independently validated safe stop.

## What you learned

- Trace access and configuration authority to possible application consequences.
- Model actual assets and communication requirements, including maintenance paths.
- Distinguish security controls, standards evidence, and safety validation.
