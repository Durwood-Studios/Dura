## The 2025 cybersecurity addition

Until ISO 10218-1:2025, robot safety standards had essentially no cybersecurity content. The framing was physical: protect humans from kinetic hazards (mechanical motion, electrical, thermal). Network-side threats were considered out-of-scope or handled by separate cybersecurity standards that the integrator was expected to apply in parallel.

ISO 10218-1:2025 changes the framing. Cybersecurity is now a SAFETY requirement, because a robot is a cyber-physical system: network-side compromise can cause physical injury. A malicious command sent to a robot controller is not an information-security problem — it's a kinetic-hazard problem.

The integration with IEC 62443 (the OT-security standard family that Phase 8 covers in depth) is the part most risk assessments fumble. The new section in ISO 10218-1:2025 says, roughly: "for the baseline OT-security posture, conform to IEC 62443. Additionally, satisfy the following robot-specific requirements." The structure is **reference + overlay**, not duplication. Skipping the overlay because "we already have 62443" misreads the standard.

## Why a generic OT-security baseline isn't enough

IEC 62443 is excellent and load-bearing for any industrial system. It defines:

- **Zones and conduits.** Segmentation. The control network is a zone; the engineering network is a zone; the corporate network is a zone; traffic between them flows through conduits with documented security controls.
- **Security levels (SL 1–4).** Threat-actor-capability framing. SL 1 is "casual misuse"; SL 4 is "nation-state attacker with significant resources."
- **Defense-in-depth controls.** Authentication, encryption, logging, patching cadence, intrusion detection.

This is the right baseline. What 62443 alone does NOT do is address the **safety-controller surface** — the channel through which malicious traffic could become an uncommanded physical motion. In a robot cell, this surface is unusually exposed:

- The safety controller is, by design, networked to the application controller (so the application can request safety-rated stops, mode transitions, and limit changes).
- The teach pendant is, by design, capable of overriding safety functions during commissioning (zone definitions can be edited, soft limits can be adjusted).
- The robot controller's firmware can be updated remotely in many deployments.

Generic OT-security treats these as ordinary networked components. ISO 10218-1:2025 treats them as safety-critical and adds requirements that reflect that.

## The four robot-specific additions

ISO 10218-1:2025's robot-specific cybersecurity overlay adds four requirements on top of the 62443 baseline. Naming them in your risk assessment is what an assessor will look for.

### 1. Secure boot of the safety controller

The safety controller must verify its own firmware integrity at boot. If the firmware has been tampered with, the controller fails to start (and fails into a known-safe state). This prevents the rootkit attack: malicious firmware that disables safety functions but reports normal status.

The implementation is hardware-anchored — a trust root in the controller's MCU, signed firmware images, and a boot sequence that halts on signature mismatch. Add-on software can't supply this; the robot has to ship with it.

### 2. Signed firmware updates

Firmware updates (controller, teach pendant, safety controller) must be cryptographically signed by the manufacturer. The robot accepts only signed updates from an authorized signing key. This prevents the supply-chain attack: a malicious update package distributed through a compromised dealer channel or in-cell USB device.

Critically, the standard does NOT permit "the customer can disable signature verification for development." The verification is permanent. This is a friction the standard accepts: you cannot side-load custom firmware on a robot certified to 10218-1:2025, full stop.

### 3. Network segmentation for the safety controller

The safety controller must sit in a separate network zone from the application controller. The conduit between them is narrow: only the specific safety-protocol traffic (PROFIsafe, CIP Safety, openSAFETY) is permitted. The application controller cannot reach the safety controller via arbitrary IP traffic.

This is stricter than the generic 62443 zone-and-conduit pattern. In 62443, zone boundaries are typically firewalls or VLANs. For the safety controller specifically, the boundary is a protocol-aware gateway, not just a packet filter.

### 4. Teach-pendant authentication

The teach pendant — the handheld device used to program and commission the robot — must require operator authentication. Idle pendants must auto-lock. Privileged operations (zone modification, soft-limit adjustment, safety-function override) must require elevated authentication.

This addresses the "left the pendant on the bench" attack: a casual passerby (a bad-actor employee, a visitor on a tour) cannot just pick up an unattended pendant and reprogram the cell.

## Mapping to a zone-and-conduit diagram

A competent 10218-1:2025 risk assessment includes a zone-and-conduit diagram per IEC 62443's notation, with the four robot-specific overlay requirements traceable to specific zones and conduits. The diagram typically has:

> **Zone: Safety controller** — secure-boot, signed updates, SL target ≥ 2.
> **Zone: Application controller** — 62443 baseline, SL target ≥ 2.
> **Zone: Teach pendant** — authentication required, auto-lock; SL target ≥ 2.
> **Zone: Plant network** — 62443 baseline, SL target depends on plant.
> **Conduit: Safety ↔ Application** — protocol-restricted (safety bus only).
> **Conduit: Pendant ↔ Application** — authenticated session.
> **Conduit: Plant ↔ Application** — firewalled, monitored.

The four 10218-1:2025 additions are NOT separate zones — they're requirements on the zones and conduits that 62443 already defines. The integration is in the security-level targets and the specific controls on each zone, not in re-drawing the topology.

## Why teach-pendant authentication is a safety requirement

A common misread: pendant authentication is "an HR thing" — about traceability and accountability, not safety. That framing is wrong, and the standard treats it as wrong.

A teach pendant has authority to modify safety zones. If anyone can pick up the pendant and shrink a separation distance, weaken a force limit, or disable a safety-rated monitored stop, then the safety functions are no longer reliable. The certification of the safety functions was based on documented configuration; an unauthenticated configuration change invalidates the certification for the duration of the change.

Authentication on the pendant is the technical control that keeps the certified configuration the actual configuration. That makes it a safety requirement under ISO 10218-1:2025, not a productivity-or-trace requirement under HR policy.

## What this means for the capstone

Lesson R8 (the capstone) requires you to produce a complete R15.06-2025 risk-assessment package for a simulated cell. The cybersecurity section of that package must:

- Reference IEC 62443 explicitly for the baseline.
- Include a zone-and-conduit diagram.

- State the SL target for each zone with justification.

A capstone without those elements will be marked incomplete, just as a capstone without an Annex A force/pressure budget for the PFL portions would be marked incomplete. The 2025 cybersecurity content is not optional curriculum — it's required content.
