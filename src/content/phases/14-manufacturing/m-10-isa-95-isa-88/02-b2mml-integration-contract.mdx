## Why this matters

A manufacturing message is well-formed XML but refers to an unknown material revision. An XML parser can accept a document that an operations system must reject. Integration needs both structural and business checks.

## Start with something familiar

A correctly filled shipping form may still name a destination that does not exist. The form’s shape and the shipment’s meaning require different validation.

## The mental model

> B2MML supplies XML-schema representations of manufacturing information models. Schema validity supports structure; identifiers, units, authorization and retry behavior still require an agreed business contract.

## The mechanism

B2MML is MESA’s XML implementation of ISA-95 information models, distributed as XML Schema definitions, or XSDs. An XML document can be well formed while failing its XSD. Passing an XSD still does not establish that a material ID exists, that a quantity is appropriate or that the sender may release production.

Pin the actual schema package/version and namespace used by both parties. Do not mix an example from one version with files from a moving repository branch and call the result validated. Preserve MESA attribution when using its schemas. A transport such as HTTP carries the message but does not replace the model or business agreement.

For this lesson, use the following plain-text projection of a proposed production request. It is deliberately not represented as a conforming B2MML XML document:

```text
request identity: B17
material: AL-4 revision C
quantity: 200 kg
equipment requirement: mixer capacity at least200kg
status: requested
```

Before implementing a selected B2MML message type, map each concept to the chosen schema/version and document the receiving application’s rules. The receiver checks that AL-4/C is known, kg is the agreed unit, the requested quantity is valid and the sender has the required authority. A retry of B17 with identical content can return recorded status; a changed quantity under the same identity should follow an explicit conflict policy rather than create duplicate work.

Test layers independently: malformed XML; schema-invalid content; valid structure with unknown material; unauthorized sender; duplicate identical request; conflicting retry. Do not claim the projection above passed XSD validation: that requires constructing the actual message and running it against the pinned schema set. The exercise trains the mapping and acceptance contract before a real system integration.

## Practice

The XML validates against the chosen XSD, but AL-4 revisionC is absent from the receiving system. Should schema success create a production order anyway?

<details><summary>Compare the reasoning</summary><p>No. Schema conformance does not establish a valid business reference. Reject or hold the request under the agreed policy and retain the reason and request identity.</p></details>

## What you learned

- Distinguish XML shape from business meaning.
- Pin schema and identifier/unit contracts.
- Test authorization and retry conflicts separately from schema validity.
