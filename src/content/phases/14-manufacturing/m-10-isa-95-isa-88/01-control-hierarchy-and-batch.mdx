## Why this matters

An order for 200 kilograms and a valve-open command operate at different responsibilities and time scales. Treating them as interchangeable messages creates unclear ownership, duplicate production, and missing records. A factory integration needs a shared activity model before it needs another endpoint.

## Start with something familiar

In a restaurant, a customer order, a kitchen schedule, and the cook's burner adjustment describe related work at different levels. Moving the order screen to another room does not turn it into a stove controller. Activities and physical network placement are separate descriptions.

## The mental model

> ISA-95 organizes manufacturing and business activities; ISA-88 separates batch recipes and procedural work from equipment capability. Neither model alone specifies network security or guarantees message delivery.

## Classify the activity before the device

The ISA-95 hierarchy distinguishes the physical process (level 0), sensing and manipulating it (1), monitoring and control (2), manufacturing operations management (3), and business planning and logistics (4). A product name such as PLC or SCADA is not a complete activity classification: one implementation can contain multiple functions.

Enterprise resource planning (ERP) coordinates business resources; a manufacturing execution system (MES) supports operations execution and records. A production request may travel toward operations while actual quantities and resource use return toward planning. This does not mandate a particular API, JSON schema, network address, or VLAN.

## Separate recipe from equipment

For batch work, a recipe describes what is to be made and how the process is intended to proceed. A control recipe applies to a particular batch. ISA-88's procedural vocabulary includes procedure, unit procedure, operation, and phase. A phase is a procedural element such as a defined charge or heat action; it is not interchangeable with this course's learning phases. Equipment models describe resources capable of performing that work. The recipe and equipment interaction must have defined states, parameters, and exceptions.

In a teaching mixer, the batch request specifies recipe revision R3, batch B17, and 200 kg target. Operations assigns an available mixer; the control sequence executes the authorized charge, mix, and discharge work. Actual output is 198 kg. The record must distinguish the target from the actual result and preserve B17/R3 rather than overwriting the target with 198.

## Integration contracts prevent duplicate work

A message being received twice should not silently create a second batch. In a proposed application contract, give each request a stable identifier and keep its accepted status. A retry of the same identifier can return that status. A conflicting retry with changed recipe parameters should be rejected for review. This is an application design example, not a claim that ISA-95 prescribes these exact fields.

Define who may release a batch, what happens when equipment is unavailable, how exceptions are recorded, and which acknowledgement means acceptance versus completion. A network diagram cannot answer those questions by itself.
