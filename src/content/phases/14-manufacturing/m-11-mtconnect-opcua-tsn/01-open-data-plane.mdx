## Where this lesson sits

M10 established the ISA-95 control hierarchy and identified the integration contracts at each boundary. M11 turns to the specific open standards that implement those contracts on the OT side: **MTConnect** (the open machine-tool data standard), **OPC UA** (the broader industrial interop framework), and **IEC/IEEE 60802** (the Time-Sensitive Networking profile for industrial automation). Together these are the **open data plane** of modern factory IT.

## MTConnect — the domain-specific schema

MTConnect (current version: 2.x, with ongoing minor releases) is the open machine-tool data standard. It defines:

- A **domain-specific information model** for machine tools: spindles, axes, controllers, alarms, paths, conditions, samples. The model is what makes a CNC's data labeled and consistent across vendors.
- A **REST/XML interface** for retrieval. A consumer issues HTTP GET against `/probe` (capability discovery), `/current` (current state), `/sample` (time-series samples), `/asset` (tool tables, fixture offsets).
- **Royalty-free, vendor-neutral.** Maintained by the Association for Manufacturing Technology (AMT) and an open community. No license fees for implementation or consumption.

MTConnect is narrow in scope by design. It is NOT trying to be a general industrial interoperability framework. It is trying to be the right schema for machine-tool data — and within that scope, it's the de-facto standard. Most modern CNCs (Mazak, DMG MORI, Haas, Okuma, Fanuc-based controllers, Siemens Sinumerik) ship with an MTConnect endpoint built into the controller or available as an add-on agent.

## OPC UA — the broader interop framework

OPC UA (Open Platform Communications Unified Architecture, formalized as IEC 62541) is the broader industrial interoperability framework. It defines:

- A **service-oriented architecture** with discovery, browsing, subscriptions, method invocation, secure session management.
- A **rich information model** — OPC UA objects, variables, methods, types, references — that can carry domain-specific schemas as Companion Specifications.
- **Transport-agnostic** — OPC UA Binary over TCP is the dominant transport; OPC UA over HTTPS / JSON over WebSockets also exist; OPC UA over MQTT exists for cloud integration.
- **Built-in security** — authentication, encryption, access control. Mature, widely-deployed cryptographic posture.

OPC UA is the dominant L2-L3 boundary protocol in modern factory IT. MES vendors expose OPC UA; SCADA platforms aggregate OPC UA; PLCs and controllers from major vendors ship with OPC UA servers.

OPC UA's information-model layer is what enables **Companion Specifications** — domain-specific schemas published by industry working groups that OPC UA exposes natively. Examples:

- OPC UA Companion Specification for MTConnect (machine tools).
- OPC UA Companion Specification for Robotics.
- OPC UA Companion Specification for PackML (packaging machinery).
- OPC UA Companion Specification for ISA-95 (the L3-L4 information flow itself).

## The MTConnect ↔ OPC UA relationship

The most common misread of these two standards: that they're rivals to pick between. They are not.

The **official OPC UA Companion Specification for MTConnect** (jointly published by the OPC Foundation and AMT in the late 2010s, with ongoing maintenance) is the canonical integration path:

- A machine-tool vendor exposes data via MTConnect (REST/XML, the domain-specific schema).
- That data is also accessible via the OPC UA Companion Specification — the SAME information model, exposed over OPC UA's service-oriented interface.
- A consumer (MES, SCADA, MES) can read either path. They get equivalent data.

The reason both exist: MTConnect REST/XML is simple, browser-accessible, and easy to integrate into HTTP-based analytics; OPC UA is the broader OT framework that already carries non-machine-tool data (PLCs, sensors, SCADA) and provides better-integrated security and subscription semantics. Modern factories typically run both transports — MTConnect REST/XML for engineering / analytics access, OPC UA Companion for the production-system integration into MES.

A factory that picks ONE and treats it as a vendor lock-in choice has misread the standards landscape. The two are complementary and the Companion Specification is the bridge.

## IEC/IEEE 60802 — TSN for industrial automation

Time-Sensitive Networking (TSN) is an extension to standard Ethernet that adds deterministic timing — bounded latency, low jitter, scheduled traffic — to commodity Ethernet hardware. TSN is the convergence layer that increasingly replaces vendor-specific real-time Ethernet variants (Profinet IRT, EtherNet/IP TIME-SYNC, EtherCAT, Sercos III) for industrial automation.

The standard that defines the TSN profile for industrial automation is **IEC/IEEE 60802** — a joint IEC and IEEE 802.1 standard. The joint publication is important:

- Earlier curricula sometimes cite **IEEE 2050** as the relevant standard. IEEE 2050 was a different working effort; the consensus has moved to IEC/IEEE 60802 as the joint standard. Citing IEEE 2050 in 2026-vintage material reads as out of date.
- The IEC + IEEE joint publication reflects that TSN needs both networking-stack (IEEE 802.1) and automation-domain (IEC) buy-in to deploy. The joint number is the modern citation.

IEC/IEEE 60802 specifies:

- Time synchronization (IEEE 802.1AS-Rev, derived from PTP).
- Scheduled traffic via Time-Aware Shaper (802.1Qbv).
- Frame preemption (802.1Qbu).
- Stream reservation and admission control.
- Tooling and configuration management for industrial deployments.

The practical consequence: a TSN-capable factory network can carry both real-time control traffic (with bounded latency guarantees) and conventional IT traffic (best-effort) on the SAME physical network. This is the consolidation that earlier real-time Ethernet variants couldn't deliver — each variant required its own dedicated network.

## Producing the verify artifact

The /verify artifact for this lesson is a working bridge sandbox: a small piece of code that consumes data from an MTConnect endpoint (simulated or real) and re-publishes it via an OPC UA server using the Companion Specification mapping. The sandbox should:

- Include a documented MTConnect data source (an open simulator like the MTConnect agent reference implementation works).
- Implement the MTConnect → OPC UA mapping per the Companion Specification at least for spindle speed, axis positions, and one alarm condition.
- Expose the bridged data via OPC UA Binary on a documented endpoint.
- Include a client test that reads the OPC UA endpoint and verifies the values match the upstream MTConnect.
- Be assembled as a single repository, hash-anchored via /verify, certificate appended.

The sandbox demonstrates the structural point: MTConnect and OPC UA are not rivals — they're co-deployable, and the Companion Specification is the bridge.

## What this lesson teaches you to do

After this lesson you should be able to:

- Read a machine-tool vendor's data-integration documentation and identify which protocols (MTConnect REST, OPC UA Companion, vendor-proprietary) are exposed.
- Recommend the right integration path for a new MES connection based on what the MES supports.
- Cite IEC/IEEE 60802 as the current TSN profile for industrial automation, and recognize the IEEE 2050 mis-citation in older material.
- Build the bridge sandbox as a portfolio artifact demonstrating the integration competence.
