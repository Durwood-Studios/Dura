## Why this matters

No engineer who designs hardware is immune to manufacturability problems. A pocket with a 1 mm fillet drawn in 10 minutes can require a $300 custom tool and add two hours to cycle time. A hole that looks fine on screen turns out to be unreachable by any standard tool holder at the required angle. These problems surface in CAM — and if you have never opened CAM software, they surface as expensive surprises when the machinist calls.

Understanding CAM also matters for anyone writing manufacturing software. DNC servers, scheduling systems, machine monitoring dashboards, and digital twin platforms all consume the artifacts that CAM produces: toolpath files, setup sheets, post-processed G-code, simulation reports. Knowing what those artifacts mean — and what decisions produced them — is the difference between software that fits the shop floor and software that the machinists route around.

## What is CAM software?

Think of CAM (Computer-Aided Manufacturing) software as a compiler. Your 3D model is the source code: it describes the desired shape, but says nothing about how to achieve it. The CAM system is the compiler: it takes that description, combines it with constraints (available tools, machine travel limits, material properties), and emits the machine instructions — G-code — that produce the shape.

> **CAM is just a compiler: geometry in, cutting instructions out, with a human making the optimization decisions in between.**

The same model fed to two different machinists with two different sets of tool choices will produce two different programs with different cycle times and surface finishes. The geometry is deterministic; the CAM decisions are engineering judgment.

## The six stages of a CAM workflow

### Stage 1 — Import and repair geometry

CAM software works from solid model files. The standard interchange format is **STEP** (`.step` or `.stp`), which preserves solid body geometry across CAD systems. Importing a STEP file creates a B-rep (boundary representation) solid: a collection of faces, edges, and vertices that define the exact shape.

Common import problems that require repair before you can generate toolpaths:

- Open shells (faces that don't form a closed solid)
- Tiny slivers and gaps from tolerancing mismatches between CAD systems
- Duplicate faces at coincident surfaces

CAM systems include geometry repair tools; some problems must be fixed back in the originating CAD model.

### Stage 2 — Define the setup

The **setup** answers three questions: Where is the origin (work zero)? What direction is Z-up? How is the part held?

```javascript
// Setup definition — every CAM operation in this setup inherits these values
const machiningSetup = {
  id: "SETUP-1",
  description: "Top face operations — vise hold on bottom",
  wcs: {
    origin: "top_left_corner_of_part", // this becomes G54 X0 Y0 Z0
    zAxis: "+Z up from part top face",
    xAxis: "+X along the long edge",
  },
  // Stock defines the raw material the machine starts with
  stock: {
    type: "rectangular",
    // Stock is always LARGER than the finished part — the extra is what gets cut away
    x_mm: 105.0, // finished part: 100 mm — 2.5 mm extra each side
    y_mm: 55.0, // finished part: 50 mm — 2.5 mm extra each side
    z_mm: 22.0, // finished part: 20 mm — 2 mm extra on top only (bottom is reference)
    material: "6061-T6 aluminum",
  },
  fixture: {
    type: "vise",
    jaw_height_mm: 40,
    // Jaw height matters: tools must never plunge into the vise jaws
    // CAM uses this for collision avoidance
  },
};
```

Getting the origin wrong here means every feature in the program is offset by the same amount — a systematic error that produces an entire batch of scrap parts before anyone notices.

### Stage 3 — Select tooling and cutting parameters

A **cutting tool** is defined by its geometry (diameter, number of flutes, corner radius, length) and its allowable cutting parameters for the given material. Every parameter is a tradeoff:

```javascript
const endmill_12mm_3fl = {
  id: "T3",
  description: "12mm 3-flute carbide endmill",
  diameter_mm: 12,
  flutes: 3,
  corner_radius_mm: 1.0,
  overall_length_mm: 75,
  flute_length_mm: 30, // maximum cutting depth before shank contact

  // Cutting parameters for 6061-T6 aluminum
  cutting_params: {
    spindle_speed_rpm: 8000,
    feed_rate_mmpm: 2160, // mm/min
    // chip_load = feed_rate / (spindle_speed × flutes)
    // = 2160 / (8000 × 3) = 0.090 mm/tooth — within recommended range
    chip_load_mm: 0.09,

    // Axial depth of cut (stepdown) — how deep per pass
    // Adaptive clearing allows deep stepdown because radial engagement is low
    stepdown_mm: 20.0, // full flute length — aggressive but valid for adaptive

    // Radial engagement (stepover) — percentage of tool diameter
    // For adaptive: 10-20% for aluminum keeps chip load consistent
    stepover_pct: 15, // 15% of 12mm = 1.8mm radial cut per pass
  },
};

// Chip load check function — catches programming errors before they break tools
function checkChipLoad(feedRate_mmpm, spindleRpm, flutes) {
  const chipLoad = feedRate_mmpm / (spindleRpm * flutes);
  const recommendations = {
    too_low: { range: [0, 0.025], risk: "Rubbing — work hardening, tool wear, poor finish" },
    low: { range: [0.025, 0.05], risk: "Acceptable but not optimal" },
    optimal: { range: [0.05, 0.15], risk: "None — target this range for aluminum" },
    high: { range: [0.15, 0.25], risk: "High cutting forces — check fixturing rigidity" },
    too_high: { range: [0.25, Infinity], risk: "Tool breakage likely" },
  };

  let category = "optimal";
  for (const [cat, { range }] of Object.entries(recommendations)) {
    if (chipLoad >= range[0] && chipLoad < range[1]) {
      category = cat;
      break;
    }
  }

  return {
    chipLoad_mm: chipLoad.toFixed(4),
    category,
    risk: recommendations[category].risk,
    recommendation:
      category === "optimal"
        ? "Parameters are within recommended range"
        : `Adjust feed rate. Target chip load: 0.05–0.15 mm/tooth`,
  };
}

console.log(checkChipLoad(2160, 8000, 3));
// → { chipLoad_mm: "0.0900", category: "optimal", risk: "None...", recommendation: "Parameters are within recommended range" }
```

### Stage 4 — Define toolpath operations

A **toolpath operation** combines a tool, a set of geometry (faces, edges, or sketched boundaries), and a strategy. The strategy determines how the tool moves through the material:

| Strategy              | What it does                                               | Best for                                  |
| --------------------- | ---------------------------------------------------------- | ----------------------------------------- |
| **Adaptive clearing** | Constant radial engagement, trochoidal path, high stepdown | Bulk material removal — pockets, profiles |
| **Contour (2D)**      | Follows the profile at constant Z depths                   | Outer walls, slots, profile cuts          |
| **Pocket**            | Back-and-forth or offset raster inside a closed boundary   | Flat-bottomed pockets                     |
| **Drill**             | Point-to-point with canned cycle output                    | Holes                                     |
| **Scallop**           | 3D surface follow with constant stepover                   | Curved surfaces, freeform                 |
| **Parallel**          | Raster across a surface at constant Z steps                | Flat surfaces, finishing passes           |

The typical operation sequence for a prismatic part:

1. **Adaptive clearing** — remove 90% of the stock fast (high MRR)
2. **Contour** (roughing) — clean up walls, leaving 0.2 mm stock
3. **Contour** (finishing) — full-depth spring pass, remove the 0.2 mm
4. **Drill** — holes at specified locations

```javascript
// Simplified operation descriptor — mirrors what CAM systems serialize to JSON
const operations = [
  {
    id: "OP-001",
    name: "Adaptive Clearing",
    tool: "T3",   // 12mm endmill
    strategy: "adaptive",
    geometry: { type: "solid_body", boundingFaces: "all" },
    params: {
      stepdown_mm: 20.0,
      stepover_pct: 15,
      stockToLeave_mm: 0.3,   // leave material for finishing passes
      feedRate_mmpm: 2160,
      spindleRpm: 8000,
    },
    estimatedTime_sec: 420,
    estimatedMRR_cm3_min: 28.5,  // material removal rate
  },
  {
    id: "OP-002",
    name: "Contour Finish - Walls",
    tool: "T3",
    strategy: "contour_2d",
    geometry: { type: "face_selection", faces: ["outer_wall", "pocket_walls"] },
    params: {
      passes: 1,
      stepdown_mm: 22.0,    // full depth in one pass for finish
      stockToLeave_mm: 0,   // cut to final dimension
      feedRate_mmpm: 1500,  // slower for finish quality
      spindleRpm: 10000,
    },
    estimatedTime_sec: 95,
  },
  {
    id: "OP-003",
    name: "Drill 4x M5 Holes",
    tool: "T7",   // 4.2mm drill (tap drill for M5)
    strategy: "drill",
    geometry: { type: "hole_recognition", diameter_mm: 4.2 },
    params: {
      cycle: "G83",       // peck drill — aluminum chips need clearance
      peckDepth_mm: 3.0,
      finalDepth_mm: 14.0,
      feedRate_mmpm: 300,
      spindleRpm: 3000,
    },
    estimatedTime_sec: 30,
  },
];

const totalTime = operations.reduce((sum, op) => sum + op.estimatedTime_sec, 0);
console.log(\`Total estimated cycle time: \${Math.ceil(totalTime / 60)} min \${totalTime % 60} sec\`);
```

### Stage 5 — Simulate

Simulation runs the toolpath through a virtual machine before any G-code is sent to a real machine. A good simulation catches three categories of problems:

1. **Tool-material collisions** — the tool body or holder hits the stock in a way that wasn't intended (a rapid move that passes through material instead of over it)
2. **Machine collisions** — the spindle or tool holder crashes into the fixture, vise jaws, or machine table
3. **Gouging** — the tool removes material it shouldn't, creating a feature that's too deep or cutting into a wall

```javascript
// Simplified collision detection — real systems use CSG (constructive solid geometry)
class MachiningSimulator {
  constructor(setup) {
    this.stock = { ...setup.stock };  // mutable copy — simulation removes material
    this.fixture = setup.fixture;
    this.toolHolder = { diameter_mm: 40, length_mm: 80 };
    this.collisions = [];
  }

  checkMove(from, to, tool, moveType) {
    // Rapid moves should not enter the stock boundary
    if (moveType === 'rapid') {
      const entersStock = this.moveEntersStock(from, to);
      if (entersStock) {
        this.collisions.push({
          type: "rapid_into_stock",
          severity: "CRASH",
          from,
          to,
          message: \`Rapid move enters stock material — will break tool and crash machine\`
        });
      }
    }

    // Check tool holder clearance above fixture
    if (to.z_mm < this.fixture.jaw_height_mm + (this.toolHolder.length_mm - tool.flute_length_mm)) {
      this.collisions.push({
        type: "holder_collision",
        severity: "CRASH",
        position: to,
        message: \`Tool holder will contact fixture jaw at Z=\${to.z_mm}mm. Jaw height: \${this.fixture.jaw_height_mm}mm\`
      });
    }

    // Stub: real simulation would update stock geometry here (subtract swept volume)
  }

  moveEntersStock(from, to) {
    // Simplified: check if the straight-line path passes through the stock bounding box
    // Real implementation uses ray-AABB intersection
    const stockBounds = {
      xMin: 0, xMax: this.stock.x_mm,
      yMin: 0, yMax: this.stock.y_mm,
      zMin: -this.stock.z_mm, zMax: 0
    };
    // ... ray-box intersection logic would go here
    return false;  // placeholder
  }

  report() {
    const crashes = this.collisions.filter(c => c.severity === "CRASH");
    const warnings = this.collisions.filter(c => c.severity === "WARNING");
    return {
      safe: crashes.length === 0,
      crashes: crashes.length,
      warnings: warnings.length,
      details: this.collisions,

}
```

### Stage 6 — Post-process

The internal toolpath is controller-agnostic: it's just a sequence of positions, speeds, and motion types. The **post-processor** translates this into G-code syntax for a specific controller.

Different controllers have different requirements:

```gcode
; Fanuc 0i — standard G-code dialect
%
O1000
G17 G20 G40 G49 G80 G90
T1 M6
G43 H1
S8000 M3
G54
G0 X-12.960 Y-11.745
Z5.000
G1 Z-20.000 F500.
...
M30
%
```

```gcode
; Haas Next Generation Control — similar but different header format
%
(PROGRAM NAME - BRACKET_V3)
(DATE=DD-MM-YY - 17-06-26  TIME=HH:MM - 08:30)
(T1 D=12. - ZOFF=-73.5 - TOOL - 12MM 3FL ENDMILL)
N1 G0 G17 G40 G49 G80 G90
T1 M6
G0 G90 G54 X-12.96 Y-11.745 S8000 M3
G43 H1 Z5.
G1 Z-20. F500.
...
M30
%
```

The same toolpath produces different G-code because the post-processor formats it according to the target controller's syntax rules, comment conventions, and required preamble structure. Post-processors are configurable scripts — Fusion 360 and Mastercam both ship a library of post-processors for common controllers, and machinists customize them for their specific machine configurations.

## What you learned

- A CAM workflow has six ordered stages: import/repair geometry, define the setup (origin + stock + fixture), select tooling and cutting parameters, define operations with strategies, simulate for collisions, and post-process to controller-specific G-code.
- Stock dimensions must exceed the finished part dimensions — the extra material is what the machine cuts away; equal dimensions produce empty toolpaths.
- Toolpath strategy selection is driven by feature type: adaptive clearing removes bulk material efficiently, contour finishes walls, pocket clears flat-bottomed recesses, and drill handles hole patterns.
- Chip load = feed rate / (spindle speed × flutes); chip load too low causes rubbing and tool wear, chip load too high causes breakage — the target range depends on material and tool geometry.
- A post-processor is a configurable translation layer that converts the controller-agnostic internal toolpath into a specific controller's G-code dialect, which is why the same geometry produces syntactically different programs for different machines.
- Machining simulation catches three categories of problems before cutting: rapid-into-stock crashes, tool-holder collisions with fixtures, and gouging that would remove material from finished surfaces.
