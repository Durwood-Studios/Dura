## Why this matters

A button works on one page but changes color when moved into a sidebar. Adding a stronger selector fixes that screenshot while making the next change harder. You need a rule for where styles belong, not an endless contest to make selectors stronger.

## Start with something familiar

A shared workshop labels shelves for tools, parts and finished work. The labels do not make the objects better; they make placement predictable. Styles need similarly explicit ownership. **CSS architecture** is the set of conventions that makes style changes understandable across components and pages.

## The mental model

> First decide which category of rule may override another, then keep each component's rules close to its own name. A component should not need to know every page where it might appear.

## The mechanism

A **component boundary** is the part of the interface a rule owns. `.notice` owns a notice; `.notice--urgent` is a **modifier**, a class for a deliberate variation. This naming convention is ordinary CSS, not new browser syntax. Avoid `.sidebar article div button` when the actual intention is “this button's urgent variant”: moving the button would change that ancestor chain.

A **cascade layer** is a named precedence group introduced with `@layer`. The order statement below creates three groups. Within the same author origin, normal declarations in a later layer outrank normal declarations in an earlier layer before specificity is compared. This is not the entire cascade: origins and importance still matter. This exercise uses no animations, transitions, inline styles or `!important`.

Save this complete document as `notice.html` and open it in a modern browser:

```html
<!doctype html>
<html lang="en">
<meta charset="utf-8">
<title>Layered notice</title>
<style>
  @layer base, components, utilities;
  @layer base {
    body { font-family: sans-serif; margin: 2rem; }
    button { color: black; background: white; }
  }
  @layer components {
    .notice { border: 2px solid currentColor; padding: 1rem; }
    .notice__action { color: navy; padding: 0.75rem; }
    .notice__action--urgent { color: maroon; }
  }
  @layer utilities {
    .text-neutral { color: black; }
  }
</style>
<section class="notice">
  <p>Your draft needs review.</p>
  <button class="notice__action notice__action--urgent">Review</button>
</section>
</html>
```

The button is maroon: the two component class selectors have equal specificity, so their order breaks the tie. Adding `text-neutral` makes it black because the utilities layer comes later. A normal `.notice__action { color: green; }` outside all layers would beat these layered normal declarations, even if placed earlier. That is why importing a legacy stylesheet without a layer can defeat a planned architecture.

Do not reach for `!important` to preserve the model: important declarations reverse the layer ordering. Instead declare the intended layer order once, place legacy rules deliberately, and document exceptional overrides. Architecture is a maintainability choice, not a requirement that every project use the same naming scheme.

## Practice

Before editing, predict the result if you remove the urgent class, then add `text-neutral`. Explain which part of the decision is layer ordering and which part is source ordering.

## What you learned

- Layers make intended normal-rule precedence explicit before selector specificity.
- Component modifiers describe deliberate variants without coupling them to page ancestors.
- Unlayered and important declarations need deliberate review when adopting layers.
- A portability regression checks identical component classes in different containers.
