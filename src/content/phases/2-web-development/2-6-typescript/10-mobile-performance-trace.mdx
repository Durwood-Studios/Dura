## Why this matters

A list scrolls smoothly on a laptop but stutters on a low-end Android device. Network throttling alone cannot reproduce slow CPU, memory pressure, rendering cost or thermal behavior.

## Start with something familiar

Testing a delivery route with an empty truck does not establish performance when it is fully loaded on a steep road. Device capability and workload conditions must match the question being asked.

## The mental model

> Performance evidence belongs to a particular build, device, workload and measurement method. Separate transfer, main-thread work, rendering and memory; optimize the measured bottleneck and verify the user-visible result.

## The mechanism

At60Hz, a display interval is about16.7ms; at 120Hz it is about8.3ms. These are scheduling intervals, not universal guarantees that every tool reports the same frame metric. Android rendering tools and browser traces measure different portions of work, so identify the instrument and platform before comparing values.

The synthetic60Hz trace records frame durations12,14,35,13 and40ms during a list interaction. Two observed frames exceed16.7ms. The associated trace shows image decoding and a large synchronous list update during those long intervals. This suggests investigation targets; it does not prove causation without a controlled change and repeat measurement.

Record device model, OS, build mode, refresh rate, power/thermal state, data volume, cache state and the exact interaction. Profile an optimized/release-representative build; development instrumentation may distort timing. Include a representative low-end Android device rather than relying only on an emulator or desktop CPU throttle.

Candidate changes include right-sized images, bounded/virtualized list rendering and moving avoidable synchronous work away from the interaction. Verify correctness, accessibility and memory after each change. A smoother animation that drops records or makes controls unreachable is not an acceptable improvement.

Test cold start, repeated navigation, background/resume and growing data volume under bounded conditions. Monitor crashes or application-not-responding symptoms separately from frame timing. Preserve raw traces and compare repeated runs with the same setup; a single best run is weak evidence. This lesson uses supplied trace values and a written measurement plan, not an executed Android performance test.
