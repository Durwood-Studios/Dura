## Why this matters

An import works during development but disappears from the deployed page. The browser receives built files, not necessarily the source tree you edited. Knowing the transformation boundary helps you inspect the correct artifact instead of repeatedly changing working source code.

## Start with something familiar

A delivery service starts from a packing list, gathers the required items and produces labeled packages. It must find every listed item before delivery. A bundler similarly begins from an **entry point**, follows dependencies and emits files for a runtime to load.

## The mental model

> The build graph says which source modules contribute to output; the browser still has to load and execute that output. A successful build does not prove runtime behavior or hide secrets included in the bundle.

## The mechanism

A **bundle** is an emitted asset containing code assembled from modules. webpack's entry identifies where dependency discovery starts; output chooses the destination. A **loader** transforms a matching input module, while a **plugin** participates in broader build tasks. TypeScript syntax transformation is a build concern; browser APIs and supported runtime syntax remain deployment concerns.

The following is a complete three-file build fixture for a separate practice directory with compatible webpack 5 and webpack-cli installed. These snippets do not install dependencies into Dura. Record the installed versions and retain the package lock when reproducing a build.

`src/message.js`:

```javascript
export function message(name) {
  return `Hello, ${name}`;
}
```

`src/index.js`:

```javascript
import { message } from "./message.js";
document.querySelector("#result").textContent = message("learner");
```

`webpack.config.cjs` uses CommonJS configuration so its module format is explicit:

```javascript
const path = require("node:path");
module.exports = {
  mode: "production",
  entry: "./src/index.js",
  output: {
    path: path.resolve(__dirname, "dist"),
    filename: "main.js",
    clean: true,
  },
};
```

`path.resolve` makes the output directory absolute. `clean: true` removes old output from that directory before writing new assets; never point the output at source or unrelated files. Build with the local webpack executable, then serve an `index.html` containing `<p id="result"></p><script src="./dist/main.js"></script>` after the paragraph. That HTML fragment is an explicit excerpt to insert into an HTML document. The expected visible result is “Hello, learner”.

No loader is needed for this small JavaScript example. Adding a CSS import would require an appropriate transformation pipeline rather than assuming every imported file is ordinary browser JavaScript. A missing module path fails dependency resolution. A missing `#result` element instead fails at runtime: bundling cannot know that every page contains the expected element.

Anything substituted into client JavaScript must be treated as public. A build-time environment variable is not a secret vault after its value is embedded in a shipped asset. Also, production mode is an optimization setting, not a guarantee that all features are tested or all browser compatibility requirements are met.

## What you learned

- Entries define the starting points of a dependency graph; output defines built assets.
- Loaders transform matching modules while plugins participate in broader build work.
- Clean builds and browser checks test different contracts.
- Build-time substitution does not make client-side values secret.
