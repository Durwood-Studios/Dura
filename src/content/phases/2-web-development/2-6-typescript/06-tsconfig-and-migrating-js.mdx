## Why this matters

Knowing TypeScript syntax is not enough to use it on a real project. Every TypeScript project is driven by a configuration file — `tsconfig.json` — that controls what the compiler checks, how strictly it checks it, which files it includes, and how it resolves module imports. Two TypeScript projects with different `tsconfig.json` files can accept or reject the exact same code. When you join a team or open an existing codebase, the `tsconfig.json` is the first file to read.

Most real-world TypeScript work is not greenfield — it is migration. Hundreds of thousands of JavaScript projects exist right now that their teams want to gradually move to TypeScript. Doing a migration wrong means days of cascading errors, a broken build, and a frustrated team that reverts everything. Doing it right means converting one file at a time, never breaking the running application, and progressively tightening safety over weeks or months. This lesson gives you both the knowledge and the strategy.

## A configuration file as a contract

Think of `tsconfig.json` the way you would think of a building's blueprints. The blueprints do not build the building — they specify every constraint the builders must follow: load-bearing walls, electrical codes, ceiling heights. The TypeScript compiler reads `tsconfig.json` the same way: it is a set of constraints applied to every file the compiler touches. Change the blueprints and the same materials (your source code) may or may not pass inspection.

> _`tsconfig.json` is the contract between your source code and the TypeScript compiler — it defines what "correct" means for your project._

## Anatomy of tsconfig.json

A minimal but complete `tsconfig.json` for a Next.js project looks like this:

```json
{
  "compilerOptions": {
    // Target: which JavaScript version to emit
    // "ES2020" gives you nullish coalescing, optional chaining, BigInt
    "target": "ES2020",

    // lib: which built-in type definitions to include
    // "DOM" adds window, document, fetch; "ESNext" adds modern JS globals
    "lib": ["DOM", "DOM.Iterable", "ESNext"],

    // module: what module system to emit
    // "ESNext" keeps import/export; bundlers (Webpack, Turbopack) handle the rest
    "module": "ESNext",

    // moduleResolution: how TypeScript resolves import paths
    // "bundler" matches how Vite, Webpack, and Next.js actually resolve files
    "moduleResolution": "bundler",

    // strict: enables a bundle of strict checks (see below)
    // This is the single most important flag — always enable it on new projects
    "strict": true,

    // outDir: where emitted JavaScript goes (often unused with bundlers)
    "outDir": "./dist",

    // rootDir: the root of your TypeScript source files
    "rootDir": "./src",

    // jsx: how to transform JSX in .tsx files
    // "preserve" lets Next.js/Babel handle JSX transformation itself
    "jsx": "preserve",

    // paths: aliases for import paths — "@/components" → "src/components"
    "paths": {
      "@/*": ["./src/*"]
    },

    // incremental: caches build info to speed up subsequent compilations
    "incremental": true
  },
  "include": ["src/**/*.ts", "src/**/*.tsx"],
  "exclude": ["node_modules", "dist"]
}
```

## What `strict: true` actually enables

`strict: true` is a shorthand for enabling several individual flags at once. Understanding each flag helps you decide whether to start with full `strict` or add flags incrementally on a brownfield project.

```json
{
  "compilerOptions": {
    // "strict": true is equivalent to enabling ALL of these:

    // Forbids implicit `any` — parameters and variables must be annotated
    // if TypeScript cannot infer their type
    "noImplicitAny": true,

    // Adds `null` and `undefined` as distinct types that must be handled explicitly
    // Without this, every type secretly includes `null | undefined`
    "strictNullChecks": true,

    // Functions cannot be called with more arguments than they declare
    "strictFunctionTypes": true,

    // Class properties must be initialized in the constructor or marked as
    // possibly undefined — prevents "definitely assigned" bugs
    "strictPropertyInitialization": true,

    // `this` inside a function body must have an explicit type annotation
    // (prevents `this` being implicitly typed as `any`)
    "noImplicitThis": true,

    // Always-true conditions in `if` statements are flagged
    // (e.g. if you check `typeof x === "string"` when x can only be a string)
    "strictBindCallApply": true
  }
}
```

## Flags that help during migration

When migrating a JavaScript project, you do not enable everything at once. These flags are specifically designed for incremental adoption:

```json
{
  "compilerOptions": {
    // allowJs: lets TypeScript process .js files alongside .ts files
    // Without this, TypeScript ignores all your existing JavaScript
    "allowJs": true,

    // checkJs: runs type checks on .js files too (weaker than .ts — no annotations)
    // Useful for catching obvious errors in files you have not converted yet
    "checkJs": false,

    // noEmit: tells the compiler to check types but not emit any JavaScript
    // Useful when your bundler (Webpack, Turbopack) handles compilation
    "noEmit": true,

    // skipLibCheck: skips type-checking of .d.ts files in node_modules
    // Speeds up compilation and avoids errors in third-party type declarations
    // you cannot fix anyway
    "skipLibCheck": true,

    // esModuleInterop: lets you import CommonJS modules with default import syntax
    // import fs from 'fs' — without this, you must write import * as fs from 'fs'
    "esModuleInterop": true,

    // resolveJsonModule: allows importing .json files as typed objects
    "resolveJsonModule": true
  }
}
```

## Analyzing a real-world tsconfig

Before writing migration code, you need to be able to read an existing config and predict its behavior. Here is a tsconfig from a real production project — analyze it:

```json
{
  "compilerOptions": {
    "target": "ES2017",
    "module": "CommonJS",
    "lib": ["ES2017"],
    "strict": false,
    "noImplicitAny": true,
    "strictNullChecks": false,
    "allowJs": true,
    "checkJs": false,
    "outDir": "./build",
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src"],
  "exclude": ["node_modules", "**/*.test.ts"]
}
```

What can you tell from this config?

- `strict: false` but `noImplicitAny: true` — the team enabled one strict flag manually, not the bundle. This means `null` and `undefined` are **not** separated from other types (`strictNullChecks: false`), so `user.name` will not error even if `user` might be null.
- `allowJs: true`, `checkJs: false` — JavaScript files are allowed in the project but not type-checked. This is a project mid-migration.
- `target: "ES2017"` — the output runs on Node.js environments that support async/await natively, but not newer syntax like optional chaining (`?.`) or nullish coalescing (`??`).
- Tests are excluded from compilation entirely — a common pattern when a test runner handles test transpilation separately.

## A migration strategy: the strangler fig pattern

The safest way to migrate a JavaScript project is the **strangler fig** approach — you grow the new system (TypeScript) around the old one (JavaScript) without ever requiring the old system to stop working.

```
Phase 1: Add TypeScript infrastructure without touching source files
  ├── npm install --save-dev typescript @types/node
  ├── npx tsc --init   (generates tsconfig.json)
  ├── Set allowJs: true, noEmit: true, skipLibCheck: true
  └── Run tsc — should report zero errors (no .ts files yet)

Phase 2: Rename entry points first, fix errors file by file
  ├── Rename src/index.js → src/index.ts
  ├── Fix every type error in index.ts (annotate params, fix nulls)
  ├── Repeat for each file your entry point imports
  └── Never rename a file until the file that imports it is already .ts

Phase 3: Tighten the config progressively
  ├── Once all files are .ts, remove allowJs
  ├── Enable strictNullChecks: true — fix the new errors
  ├── Enable noImplicitReturns: true — fix the new errors
  └── Finally set strict: true — fix whatever remains

Phase 4: Add declaration files for any remaining JS dependencies
  └── npm install @types/<package> for each untyped dependency
```

The key invariant: **the project must build and run at every step**. Never leave the build broken overnight.

## Practical migration: before and after

Here is a realistic JavaScript module and its TypeScript equivalent after migration:

```javascript
// BEFORE: src/api/users.js  (JavaScript)
// No types — callers must guess what these functions expect

async function getUser(id) {
  const response = await fetch(`/api/users/${id}`);
  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }
  return response.json();
}

function formatUserName(user) {
  // What is `user`? Has to be guessed from callers
  return `${user.firstName} ${user.lastName}`.trim();
}

module.exports = { getUser, formatUserName };
```

```typescript
// AFTER: src/api/users.ts  (TypeScript)
// Types make every contract explicit — no guessing required

interface User {
  id: number;
  firstName: string;
  lastName: string;
  email: string;
  createdAt: string;
}

// Return type Promise<User> tells callers exactly what they get back
async function getUser(id: number): Promise<User> {
  const response = await fetch(`/api/users/${id}`);

  // TypeScript knows response.ok is boolean — no annotation needed here
  if (!response.ok) {
    throw new Error(`HTTP error: ${response.status}`);
  }

  // Cast needed because fetch().json() returns Promise<unknown>
  // We are asserting the API contract here — a good place for runtime validation
  return response.json() as Promise<User>;
}

// Both parameters are fully typed — the compiler catches call-site mistakes
function formatUserName(user: Pick<User, "firstName" | "lastName">): string {
  return `${user.firstName} ${user.lastName}`.trim();
}

export { getUser, formatUserName };
export type { User };
```

Notice the migration added:

- An `interface` that documents what the API returns
- Explicit parameter and return types on both functions
- A `Pick<User, ...>` utility type on `formatUserName` — it only needs two fields, so we do not require the full `User` object (caller-friendly)
- Named exports instead of `module.exports` (ESM syntax, which TypeScript prefers)

## What you learned

- `tsconfig.json` controls what the TypeScript compiler checks, how strictly it checks it, and which files it processes — two projects with different configs can accept or reject the same code.
- `strict: true` enables a bundle of safety flags; the two most impactful are `noImplicitAny` (no silent `any`) and `strictNullChecks` (null and undefined are distinct types).
- `allowJs: true` is the essential flag for incremental JavaScript-to-TypeScript migration — it lets `.js` and `.ts` files coexist in the same project.
- The strangler fig migration strategy keeps the project building at every step: add infrastructure, rename one file, fix its errors, repeat — never leave the build broken.
- `noEmit: true` separates type-checking (tsc's job) from code emission (your bundler's job) — the correct setup for most modern JavaScript toolchains.

You have completed the TypeScript module. You can now write typed code from scratch and bring TypeScript's safety to existing JavaScript projects — the foundation every typed React and Next.js codebase is built on.
