## Why this matters

Two teams want to release parts of one page independently. Splitting the repository is easy; deciding who owns navigation, authentication, styles and failure recovery is harder. A remote widget outage must not quietly erase the rest of the learner's work.

## Start with something familiar

A food hall lets vendors change their menus independently, while the building still owns entrances, electricity and shared rules. Independence needs boundaries and agreements. A **microfrontend** applies that idea to separately owned interface parts, sometimes delivered independently at runtime.

## The mental model

> Independent delivery trades a single release boundary for explicit compatibility and failure contracts. It is useful only when the coordination benefit outweighs duplicated runtime, testing and operations work.

## The mechanism

The **host** owns the containing page. A **remote** supplies a feature the host loads. webpack Module Federation is one mechanism for sharing modules between separate builds; it is not the definition of every microfrontend architecture. Route-level applications, server composition and shared packages have different tradeoffs.

Start with an interface before selecting a loader. The following complete browser module exposes a small feature. A mount function accepts a DOM container and a message; it returns cleanup that removes what the feature created. This example demonstrates the contract locally, not remote loading or isolation from hostile code.

```javascript
export function mount(container, { message }) {
  const button = document.createElement("button");
  button.type = "button";
  button.textContent = message;
  const onClick = () => { button.textContent = "Acknowledged"; };
  button.addEventListener("click", onClick);
  container.append(button);
  return () => {
    button.removeEventListener("click", onClick);
    button.remove();
  };
}
```

The host provides only the container it intends the feature to own. Unmount removes listeners as well as visible nodes, preventing duplicated behavior after navigation. A **compatibility contract** records the exported function names, parameter shapes, supported versions and ownership rules. It should say whether a remote can navigate, read shared state or start network requests; a container argument alone does not enforce those permissions.

For a runtime-loaded feature, define a bounded loading state, a fallback on timeout or rejection, and a way to recover without losing unrelated host state. Browser code loaded into the same page is not a security sandbox. Shared dependencies also need version decisions: declaring a library shared does not prove every remote works with the host's version. Authentication and authorization must remain enforceable at the data boundary rather than depending on a remote hiding buttons.

Choose a shared build when teams can coordinate releases and the added network/compatibility failure modes bring little benefit. Choose a split only with a reason, such as genuinely separate release ownership, and a test strategy covering host/remote combinations. Preserve a known-compatible asset version for rollback; pointing to an unversioned latest remote makes a past host deployment difficult to reproduce.

## What you learned

- A microfrontend split requires ownership and compatibility agreements beyond repository layout.
- Mount and cleanup contracts make repeated navigation testable.
- Availability, compatibility and authorization are different boundaries.
- Independent release value must justify additional runtime and operations costs.
