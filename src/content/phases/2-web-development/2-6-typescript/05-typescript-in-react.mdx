## Why this matters

React and TypeScript are the most common pairing in production web development today. Nearly every React codebase of meaningful size runs TypeScript. When you join a team or contribute to an open-source project, you will encounter typed components, typed hooks, and typed event handlers immediately. More importantly, TypeScript catches an entire class of React-specific bugs: passing the wrong prop type, forgetting to handle a loading state, calling a non-existent method on an event target.

The patterns in this lesson are the ones you will write dozens of times per week once you are working on a real application. Getting them right from the start means your components are self-documenting, your editor autocompletes prop names, and your teammates cannot accidentally misuse your components.

## The mental model

> Typed props and event handlers describe a component's public contract. State types must include every value the component can actually hold.

## Typing component props

Every React component receives props. Define their shape with an interface or type alias placed directly above the component:

```typescript
// Define the props interface above the component — always
interface ButtonProps {
  label: string;
  onClick: () => void;
  variant?: "primary" | "secondary" | "danger"; // optional with a literal union
  disabled?: boolean;
}

// The component receives props typed as ButtonProps
function Button({ label, onClick, variant = "primary", disabled = false }: ButtonProps) {
  return (
    <button
      onClick={onClick}
      disabled={disabled}
      className={`btn btn-${variant}`}
    >
      {label}
    </button>
  );
}

// TypeScript enforces this at every call site
<Button label="Save" onClick={() => console.log("saved")} />    // fine
<Button onClick={() => {}} />                                    // Error: 'label' is required
<Button label="Delete" onClick={handleDelete} variant="danger" /> // fine
```

> _A props interface is the public API of your component — TypeScript enforces it at every call site so you catch mismatches when you type them, not when they ship._

## The `children` prop

When a component renders its children (content placed between its tags), you need to type the `children` prop. Use `React.ReactNode` — the type that covers everything React can render:

```typescript
import type { ReactNode } from "react";

interface CardProps {
  title: string;
  children: ReactNode; // covers JSX, strings, numbers, null, arrays of any of these
}

function Card({ title, children }: CardProps) {
  return (
    <div className="card">
      <h2>{title}</h2>
      <div className="card-body">{children}</div>
    </div>
  );
}

// Usage — children is anything between the tags
<Card title="User Profile">
  <Avatar src="/alice.jpg" />
  <p>Alice has been a member since 2024.</p>
</Card>
```

## Typing `useState`

TypeScript infers the state type from the initial value. You only need to provide an explicit type argument when the initial value does not fully express the type:

```typescript
import { useState } from "react";

// Inference works perfectly here — count is number
const [count, setCount] = useState(0);

// Inference fails here — initial value is null, but state becomes User later
// Without the generic, state would be typed as "null" forever
interface User {
  id: number;
  name: string;
  email: string;
}

const [user, setUser] = useState<User | null>(null);
// user is "User | null" — TypeScript forces you to handle both cases
if (user !== null) {
  console.log(user.name); // Safe: TypeScript knows user is User here
}

// Arrays need an explicit type if the initial value is empty
const [items, setItems] = useState<string[]>([]);
// Without <string[]>, TypeScript would infer never[]
```

## Typing event handlers

React's synthetic events are generic over the element type. The pattern is `React.ChangeEvent<HTMLInputElement>` for input changes, `React.FormEvent<HTMLFormElement>` for form submits:

```typescript
import { useState } from "react";
import type { ChangeEvent, FormEvent } from "react";

interface LoginFormProps {
  onSubmit: (email: string, password: string) => void;
}

function LoginForm({ onSubmit }: LoginFormProps) {
  const [email, setEmail] = useState("");
  const [password, setPassword] = useState("");

  // ChangeEvent<HTMLInputElement> gives you access to e.target.value safely
  function handleEmailChange(e: ChangeEvent<HTMLInputElement>): void {
    setEmail(e.target.value);
  }

  // FormEvent<HTMLFormElement> lets you call e.preventDefault()
  function handleSubmit(e: FormEvent<HTMLFormElement>): void {
    e.preventDefault();
    onSubmit(email, password);
  }

  return (
    <form onSubmit={handleSubmit}>
      <input type="email" value={email} onChange={handleEmailChange} />
      <input type="password" value={password} onChange={(e) => setPassword(e.target.value)} />
      <button type="submit">Log in</button>
    </form>
  );
}
```

### Common event types

| Event           | Type                               |
| --------------- | ---------------------------------- |
| Input change    | `ChangeEvent<HTMLInputElement>`    |
| Textarea change | `ChangeEvent<HTMLTextAreaElement>` |
| Select change   | `ChangeEvent<HTMLSelectElement>`   |
| Form submit     | `FormEvent<HTMLFormElement>`       |
| Button click    | `MouseEvent<HTMLButtonElement>`    |
| Keyboard event  | `KeyboardEvent<HTMLInputElement>`  |

## Typing `useRef`

`useRef` is generic over the type of the value it holds. For DOM refs, you need the HTML element type:

```typescript
import { useRef, useEffect } from "react";

function VideoPlayer() {
  // Typed as HTMLVideoElement — gives full DOM API autocompletion
  // "null" is the initial value before the element mounts
  const videoRef = useRef<HTMLVideoElement>(null);

  useEffect(() => {
    // TypeScript knows videoRef.current might be null — forces the check
    if (videoRef.current) {
      videoRef.current.play();
    }
  }, []);

  return <video ref={videoRef} src="/demo.mp4" />;
}
```

For mutable refs that store values (not DOM nodes), provide the value type:

```typescript
// Tracks a timeout ID across renders without triggering re-renders
const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
```

## Discriminated unions for component variants

When a component can render in fundamentally different modes, a **discriminated union** on the props makes each mode's required properties explicit:

```typescript
// The "kind" property is the discriminant — it narrows the full union
type AlertProps =
  | { kind: "success"; message: string }
  | { kind: "error"; message: string; retryFn: () => void }
  | { kind: "loading"; label?: string };

function Alert(props: AlertProps) {
  // TypeScript narrows props based on the kind check
  if (props.kind === "success") {
    return <div className="alert-success">{props.message}</div>;
  }

  if (props.kind === "error") {
    // TypeScript knows retryFn is available here — it is in the error branch
    return (
      <div className="alert-error">
        {props.message}
        <button onClick={props.retryFn}>Retry</button>
      </div>
    );
  }

  // props.kind === "loading" here — TypeScript knows
  return <div className="alert-loading">{props.label ?? "Loading..."}</div>;
}

// TypeScript enforces the right props for each kind
<Alert kind="error" message="Failed to save" retryFn={handleRetry} /> // fine
<Alert kind="error" message="Failed to save" />                        // Error: retryFn missing
<Alert kind="success" retryFn={handleRetry} />                         // Error: retryFn not in success branch
```

## What you learned

- **Props interfaces** define the public API of a component; TypeScript enforces correct usage at every call site so prop mismatches are caught immediately.
- `useState<T>` requires an explicit type argument when the initial value (`null`, `[]`) does not fully express the type state will hold — without it, TypeScript infers too narrow a type.
- **Event handlers** are typed with React's generic event types (`ChangeEvent<HTMLInputElement>`, `FormEvent<HTMLFormElement>`) which give full access to the correct DOM properties.
- **Discriminated unions** on props model components with multiple modes — TypeScript narrows the props type in each branch, making required-per-mode properties fully enforced.
