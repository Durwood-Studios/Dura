## Why this matters

Your application's data has shapes. A user has a name, email, and ID. A product has a price, title, and stock count. An API response has a status, data, and optional error message. Whenever you pass these objects around — into functions, between components, across API boundaries — TypeScript needs to know their shape. Without that knowledge, it cannot catch a typo in a property name, a missing required field, or a function called with the wrong object structure.

Interfaces and type aliases are how you communicate object shapes to TypeScript. They are the most important TypeScript feature you will use every day. Defining them well is what separates a TypeScript codebase that catches bugs from one that merely adds verbosity.

## Describing objects: the blueprint mental model

Think of an interface as a **blueprint for a building**. The blueprint says "this building has a front door, three windows, and a basement." When someone builds something claiming to be this building, an inspector checks whether it matches. TypeScript is that inspector.

```typescript
// Blueprint: every User must have exactly these properties with these types
interface User {
  id: number;
  name: string;
  email: string;
}

// This object matches the blueprint — TypeScript accepts it
const alice: User = {
  id: 1,
  name: "Alice",
  email: "alice@example.com",
};

// This object is missing "email" — TypeScript rejects it
const bob: User = {
  id: 2,
  name: "Bob",
  // Error: Property 'email' is missing in type '...' but required in type 'User'
};
```

> _An interface is the blueprint for an object's shape — TypeScript checks every object against it when you apply the type._

## Optional and readonly properties

Real-world objects often have fields that are not always present, and fields that should never change after creation.

```typescript
interface Product {
  id: number;
  name: string;
  price: number;
  // "?" makes a property optional — its type becomes "string | undefined"
  description?: string;
  // "readonly" prevents reassignment after the object is created
  readonly createdAt: Date;
}

const shirt: Product = {
  id: 101,
  name: "Classic T-Shirt",
  price: 29.99,
  createdAt: new Date(),
  // description is omitted — fine because it is optional
};

// Attempting to overwrite a readonly property is a compile-time error
shirt.createdAt = new Date(); // Error: Cannot assign to 'createdAt' because it is a read-only property.
```

The `readonly` modifier is especially important for IDs, creation timestamps, and any value that should be set once and never changed. It documents intent and enforces it at the same time.

## Functions inside interfaces

Interfaces can also describe methods — the functions an object must have:

```typescript
interface Logger {
  log(message: string): void;
  error(message: string, code: number): void;
  // Method shorthand: equivalent to "warn: (message: string) => void"
  warn(message: string): void;
}

// Any object implementing this interface must provide all three methods
const consoleLogger: Logger = {
  log: (msg) => console.log(msg),
  error: (msg, code) => console.error(`[${code}] ${msg}`),
  warn: (msg) => console.warn(msg),
};
```

## Type aliases with `type`

A **type alias** creates a name for any type — not just objects. Use `type` for unions, intersections, function shapes, and tuples where `interface` cannot be used:

```typescript
// A union — interface cannot do this
type UserId = string | number;

// A function type — describes any function matching this signature
type Formatter = (value: number, currency: string) => string;

// A tuple — an array with exactly two elements of specific types
type Coordinate = [number, number];

const origin: Coordinate = [0, 0];
const formatUSD: Formatter = (value, currency) => `${currency}${value.toFixed(2)}`;
```

### Intersection types

Use `&` to combine multiple types into one that requires all properties from all members:

```typescript
interface Named {
  name: string;
}

interface Timestamped {
  createdAt: Date;
  updatedAt: Date;
}

// An intersection: the combined type has ALL properties from BOTH interfaces
type AuditedEntity = Named & Timestamped;

// Every AuditedEntity must satisfy Named AND Timestamped
const record: AuditedEntity = {
  name: "Alice",
  createdAt: new Date("2024-01-01"),
  updatedAt: new Date("2024-06-15"),
};
```

## Interface vs. type alias: when to use which

Both can describe object shapes. The practical rule for most codebases:

| Situation                                         | Prefer                                   |
| ------------------------------------------------- | ---------------------------------------- |
| Describing an object shape that might be extended | `interface`                              |
| Unions, intersections, mapped types, tuples       | `type`                                   |
| Public API of a library or module                 | `interface` (allows declaration merging) |
| Component props in React                          | Either — `interface` is conventional     |

The most important thing is consistency within a codebase. DURA uses `interface` for object shapes and `type` for everything else.

## Structural typing: shape is all that matters

TypeScript uses **structural typing** — it does not care what you call a type, only whether an object has the required properties with the right types. This is sometimes called "duck typing": if it walks like a duck and quacks like a duck, TypeScript treats it as a duck.

```typescript
interface Point {
  x: number;
  y: number;
}

// This object was never declared as a Point
const myCoord = { x: 10, y: 20, label: "origin" };

// TypeScript accepts it — myCoord has everything Point needs (plus an extra property)
function drawPoint(p: Point): void {
  console.log(`Drawing at (${p.x}, ${p.y})`);
}

drawPoint(myCoord); // Works — structural compatibility is all TypeScript checks
```

This is a key difference from languages like Java or C# where objects must explicitly declare which interfaces they implement. In TypeScript, the shape determines compatibility automatically.

## Index signatures: objects as maps

When you have an object where the keys are not known ahead of time — like a dictionary or a settings map — use an **index signature**:

```typescript
// An object where keys are strings and values are numbers
interface ScoreMap {
  [userId: string]: number;
}

const leaderboard: ScoreMap = {
  "user-1": 950,
  "user-2": 840,
  "user-3": 1200,
};

// TypeScript knows: looking up any string key gives a number (or undefined)
const score = leaderboard["user-1"]; // TypeScript infers: number
```

## What you learned

- **Interfaces** describe the shape of objects — required properties, optional properties (with `?`), readonly properties, and methods — and TypeScript checks every object against the blueprint.
- **Type aliases** created with `type` handle everything interfaces cannot: unions (`A | B`), intersections (`A & B`), tuples, and function signatures.
- **Structural typing** means TypeScript checks compatibility by shape, not by name — an object automatically satisfies an interface if it has the required properties.
- **Intersection types** (`A & B`) combine multiple types, requiring all properties from all members — useful for composing shared behaviors like auditing or timestamps.

The next lesson introduces **generics** — the feature that lets you write functions and types that work with multiple types while still preserving full type safety.
