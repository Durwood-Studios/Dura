## Why this matters

Without generics, you face a choice that should not exist: write a function once that works on any type (losing all type safety), or write the same function multiple times for each type (duplicating logic). Generics eliminate this dilemma. They are the feature that lets `Array.prototype.map`, `Promise`, `useState`, and nearly every other TypeScript abstraction preserve full type safety across any data type.

Reading a codebase that uses generics fluently — which every serious TypeScript project does — requires being able to recognize and understand them. Writing them unlocks the ability to build reusable, type-safe utilities, data structures, and API wrappers. This lesson is the conceptual leap that separates TypeScript beginners from practitioners.

## Start with something familiar

A container can preserve whatever item type it receives without assuming that every item is interchangeable.

## The mental model

> A generic parameter preserves a relationship between input and output types. It is more precise than discarding that relationship with any.

## The problem generics solve

Imagine you need a function that wraps any value in an object with a timestamp:

```typescript
// Approach 1: Use "any" — loses all type information
function wrapWithTimestamp(value: any): { value: any; timestamp: Date } {
  return { value, timestamp: new Date() };
}

// The return type is "any" — TypeScript cannot help us after this point
const wrapped = wrapWithTimestamp("hello");
wrapped.value.toFixed(2); // No error — but value is a string! Wrong at runtime.
```

```typescript
// Approach 2: Write the same function for each type — maintenance nightmare
function wrapString(value: string): { value: string; timestamp: Date } {
  return { value, timestamp: new Date() };
}
function wrapNumber(value: number): { value: number; timestamp: Date } {
  return { value, timestamp: new Date() };
}
// ... and so on for every type
```

Neither approach is good. Generics give you a third option.

## The generic solution: type parameters

A **type parameter** is a placeholder for a type that gets filled in when the function is called. By convention, single-letter uppercase names are used — `T` for a single type, `K`/`V` for key/value pairs, `A`/`B` for two related types.

```typescript
// "T" is a type parameter — a placeholder that TypeScript fills in per call
function wrapWithTimestamp<T>(value: T): { value: T; timestamp: Date } {
  return { value, timestamp: new Date() };
}

// TypeScript infers T = string from the argument
const wrappedString = wrapWithTimestamp("hello");
// wrappedString.value is type: string

// TypeScript infers T = number from the argument
const wrappedNumber = wrapWithTimestamp(42);
// wrappedNumber.value is type: number

// Now TypeScript catches the mistake — value is a string, not a number
wrappedString.value.toFixed(2); // Error: Property 'toFixed' does not exist on type 'string'
```

> _A generic is a function or type with a blank that TypeScript fills in with the actual type at each call site — getting type safety for free without duplication._

## Calling generics: explicit vs. inferred type arguments

TypeScript infers the type argument from the function's arguments most of the time. You can also provide it explicitly using angle brackets:

```typescript
function identity<T>(value: T): T {
  return value;
}

// Inferred — TypeScript figures out T = string
const a = identity("hello");

// Explicit — you tell TypeScript what T is
const b = identity<number>(42);

// Useful when inference cannot work — e.g., an empty array
const emptyList = identity<string[]>([]);
// TypeScript knows: emptyList is string[], not never[]
```

## Generic interfaces and type aliases

Generics apply to interfaces and type aliases too. This is how TypeScript models containers — arrays, promises, API responses — where the container shape is fixed but the contained data type varies.

```typescript
// A generic API response wrapper
interface ApiResponse<T> {
  data: T;
  status: number;
  message: string;
  error?: string;
}

// Reuse the same interface for any data shape
type UserResponse = ApiResponse<User>;
type PostListResponse = ApiResponse<Post[]>;

// TypeScript fully knows the shape of data in each case
function handleUserResponse(response: ApiResponse<User>): void {
  // response.data is type User — full autocompletion on its properties
  console.log(response.data.name);
  console.log(response.data.email);
}
```

## Type constraints with `extends`

Sometimes you need a generic that works on many types but not all types. Use `extends` to constrain what types the type parameter can be:

```typescript
// T must have a "length" property — arrays and strings both do, numbers do not
function getFirstHalf<T extends { length: number }>(collection: T): number {
  return collection.length / 2;
}

getFirstHalf([1, 2, 3, 4]); // fine: arrays have .length
getFirstHalf("hello world"); // fine: strings have .length
getFirstHalf(42); // Error: number doesn't have .length
```

A common constraint is `extends keyof SomeType` — constraining a type parameter to only the known property names of an object:

```typescript
// K must be a key that actually exists on T
// This is how Object.keys, lodash.pick, etc. are typed
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key]; // TypeScript knows the return type is T[K]
}

interface Config {
  host: string;
  port: number;
  debug: boolean;
}

const config: Config = { host: "localhost", port: 3000, debug: true };

const host = getProperty(config, "host"); // TypeScript infers: string
const port = getProperty(config, "port"); // TypeScript infers: number
getProperty(config, "timeout"); // Error: "timeout" not in Config
```

## Multiple type parameters

Functions can have more than one type parameter:

```typescript
// Maps keys of type K to values of type V in a new object
function zipToObject<K extends string, V>(keys: K[], values: V[]): Record<K, V> {
  const result = {} as Record<K, V>;
  keys.forEach((key, i) => {
    result[key] = values[i];
  });
  return result;
}

const scoreMap = zipToObject(["alice", "bob", "charlie"], [95, 87, 91]);
// TypeScript infers: Record<"alice" | "bob" | "charlie", number>
```

## A practical generic: a type-safe fetch wrapper

Here is a real-world use of generics — a fetch wrapper that lets callers declare what type they expect back:

```typescript
// The caller declares T — the expected shape of the response body
async function fetchJson<T>(url: string): Promise<T> {
  const response = await fetch(url);
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${url}`);
  }
  // The "as T" cast is the one place we trust the server matches our type
  return response.json() as Promise<T>;
}

interface Post {
  id: number;
  title: string;
  body: string;
}

// TypeScript knows the return type is Post — no manual casting needed at call sites
const post = await fetchJson<Post>("/api/posts/1");
console.log(post.title); // The annotation assumes the server shape; it has not validated it
```

## What you learned

- **Generics** let you write a function or type once and use it safely across any compatible type, eliminating the choice between `any` (unsafe) and code duplication.
- A **type parameter** (like `<T>`) is a placeholder filled in at each call site — TypeScript infers it from the arguments or you can provide it explicitly with `<SpecificType>`.
- **Type constraints** (`extends`) restrict what types a type parameter accepts — enabling you to access specific properties on `T` while still keeping the function generic.
- `keyof T` as a constraint limits a type parameter to the known property names of `T`, enabling fully type-safe property access patterns.
