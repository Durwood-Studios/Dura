## Why this matters

A team tests one build and uploads another, then calls the app released because the upload succeeded. Native distribution has separate build, signing, processing, review and availability stages.

## Start with something familiar

A manufactured item needs a serial number through inspection and shipment. A native application needs an equally traceable build identity so test evidence belongs to the artifact users receive.

## The mental model

> A release record binds source, configuration, signed artifact and store build identity to its test and rollout evidence. Upload acceptance is not review approval, availability or successful installation.

## The mechanism

For an iOS App Store workflow, create or select the correct app record, confirm bundle identity and version/build metadata, archive/sign with the authorized distribution configuration, upload using a supported tool, wait for processing and select the intended build for testing or submission. Store requirements and supported tool versions change; use the linked current platform guidance for the actual release.

Android distribution has its own signing and package identity, build/version requirements and release tracks. Do not transfer an iOS assumption directly to Play distribution. Protect signing credentials and use the organization’s approved account roles; this lesson neither supplies credentials nor authorizes publication.

The fictional release record is source revision R7, app version1.2.0, build42, staging tests passing. The uploaded artifact is build43 from R8, which changes camera permission configuration. The build42 evidence does not automatically establish build43 behavior. Repeat the affected native tests and record the artifact’s exact identity before submitting it.

A release checklist includes installation and upgrade from the prior supported version, draft/storage migration, offline behavior, native permissions, accessibility and account switching. Store privacy declarations should match actual SDK/data behavior, not a boilerplate answer. A staged rollout needs monitored failure signals, an owner and a response plan. Removing a release from availability does not automatically downgrade already-installed apps or reverse their data migration.

Practice with a written release packet or a permitted internal-testing channel before a public release. This exercise does not upload, sign or publish an app. The competency evidence is a traceable go/no-go decision using supplied build facts; actual distribution remains a separately executed platform workflow.
