## Why this matters

A browser shows an install icon, but the app fails when the connection disappears. Installation metadata and offline behavior are different contracts, and neither permits caching another learner’s private response indiscriminately.

## Start with something familiar

A traveler can carry a map before a trip, but an empty map case is not a map. An installable application also needs the actual resources and data required for the promised offline task.

## The mental model

> An offline feature names what is available, stores it before the network fails and reports what remains unavailable. A manifest describes the app; a service worker can mediate requests.

## The mechanism

A web app manifest provides installation-related metadata such as name and icons. A service worker is a browser-managed script with a separate lifecycle that can receive fetch events for controlled pages. It cannot directly manipulate the page DOM. Cache Storage stores request/response pairs; IndexedDB is a better fit for structured learner records with explicit ownership and updates.

A policy comes before worker code. For a teaching shell, choose exact public assets, such as a versioned stylesheet and offline help page. Cache successful same-origin GET responses for that declared set. Do not cache arbitrary authenticated API responses as though every user shares them. The request URL alone may not express whose private content the response contains.

A basic behavior table can be implemented with any suitable service-worker library:

| Request | Online behavior | Offline behavior |
| --- | --- | --- |
| Known versioned public shell asset | Fetch/store verified success | Return previously stored matching asset |
| Uncached public lesson | Fetch and report availability | Explain that this lesson was not saved |
| Private account API | Use authorized network flow | Do not substitute another identity's response |
| Local saved exercise | Read/write owner-scoped IndexedDB | Keep the same local record flow |

These are application choices, not a claim that a manifest automatically implements them. Cache writes can fail from quota or storage restrictions. Installation success is not proof that every resource is available; a readiness message should follow actual checks.

Test from a controlled page after the worker activates, and distinguish a first-ever offline visit from a later offline revisit. A first visit cannot download missing application code without a connection. Keep a visible explanation and a supported recovery route for absent content instead of an endless loading indicator.
