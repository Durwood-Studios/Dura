## Why this matters

A shared React Native component compiles for two platforms, but its keyboard and accessibility behavior differ. Sharing source reduces duplication; it does not replace platform verification.

## Start with something familiar

A recipe can be shared between kitchens while ovens still need separate calibration. Shared logic and platform behavior likewise need different evidence.

## The mental model

> Separate reusable application behavior from native rendering, lifecycle and capability adapters. Use documented platform differences deliberately and validate the same user task on each supported platform.

## The mechanism

React Native uses components such as View, Text and Pressable rather than browser DOM elements. Existing React state knowledge transfers, but CSS/browser APIs and native component behavior are not identical. The following complete component is a small in-memory practice counter; it requires a configured React Native project and is not executable in Dura’s browser JavaScript sandbox.

```tsx
import { useState } from 'react';
import { Platform, Pressable, ScrollView, StyleSheet, Text } from 'react-native';

export default function PracticeCounter() {
  const [count, setCount] = useState(0);
  return (
    <ScrollView contentContainerStyle={styles.container}>
      <Text accessibilityRole="header">Practice counter</Text>
      <Text>Completed practice repetitions: {count}</Text>
      <Pressable accessibilityRole="button" accessibilityLabel="Add one practice repetition"
        onPress={() => setCount(value => value + 1)} style={styles.button}>
        <Text>Add one</Text>
      </Pressable>
      <Text>Platform: {Platform.OS}</Text>
      <Text>This count is in memory and resets when the component is remounted.</Text>
    </ScrollView>
  );
}
const styles = StyleSheet.create({
  container: { padding: 24, gap: 16 },
  button: { minHeight: 48, padding: 12, borderWidth: 1, justifyContent: 'center' },
});
```

The functional state update uses the previous count. Pressable supplies a native interaction boundary; the accessibility role and label describe the action, but they still need actual screen-reader testing. ScrollView permits content to extend at larger text sizes. Neither that choice nor a minimum height guarantees every device layout.

Use Platform for small documented differences or platform-specific files for genuinely different adapters. Do not branch simply to conceal an unexplained bug. Native permissions, notifications and background behavior should have explicit contracts and platform tests rather than accidental browser substitutes.

Run the task on each supported native build: activate twice and observe 2, increase text size and reach the action, navigate with the platform screen reader, then remount and observe the disclosed reset. If persistence becomes a requirement, add a storage adapter with failure/owner/restore tests; do not relabel this in-memory counter as saved progress.

Record the actual React Native version, OS, device and build. TypeScript syntax checking alone cannot prove native rendering or accessibility. The applied exercise is a code review and test design until you execute those native builds; keep that evidence level visible.
