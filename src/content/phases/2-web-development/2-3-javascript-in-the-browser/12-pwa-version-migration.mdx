## Why this matters

An update is ready while a learner is editing. Forcing every tab to reload can discard unsaved work, while serving new code with an old data assumption can corrupt a record. Update behavior needs a compatibility plan.

## Start with something familiar

Replacing a train carriage while passengers are inside requires more than delivering the new carriage. You need a transition that accounts for who is using the old one and what they carry.

## The mental model

> Treat application code, service-worker caches and local record schema as separate versions that may coexist. A new worker being downloaded does not make every open page compatible with it.

## The mechanism

The service-worker lifecycle includes installation, waiting and activation. A newly installed worker can wait while an older worker controls existing pages. Forcing activation with skipWaiting and immediately taking control changes that coordination; it is not automatically the safest default for an editing application.

Consider page code A using record schema1 and code B using schema2. If both tabs remain open, the database migration needs an explicit policy for old writers. A record-version field helps identify data, but it does not by itself stop stale writes. Use an application compatibility check and safe persistence before asking the learner to reload. Retain a recoverable draft if conversion cannot complete.

An update policy should state:

| Decision | Evidence |
| --- | --- |
| Worker ready | Installation/precache actually succeeded |
| Reload offered | Draft persistence succeeded or unsaved work is explicitly handled |
| Old code still open | Reads/writes obey a declared compatibility window |
| Old caches removed | No supported active version still requires their assets |
| Migration failed | Previous valid data remains recoverable; error is visible |

Do not delete all caches and local databases under a broad cleanup label. Cache names are application-owned namespaces; IndexedDB contains different data. A failed migration should not be “repaired” by silently clearing progress.

A versioned update test uses two tabs and retained data: keep an edit in the old tab, deploy/activate the new worker in the test environment, then attempt old and new writes. Record which versions were present and verify the data after reload. A worker update log alone does not establish compatibility. Storage eviction and offline network conditions also need explicit behavior; no cache policy guarantees permanent browser retention.

## Practice

The new worker is installed, but a draft save failed. Should “Update ready” cause an immediate reload?
