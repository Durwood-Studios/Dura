## Why this matters

A server accepts a notification request, so the app marks the message read. The user’s device may be offline, the token stale or notification permission disabled. Delivery evidence must not be confused with user action.

## Start with something familiar

A postal counter accepting a parcel does not prove that its recipient opened it. Push delivery likewise has several acknowledgements with different meanings.

## The mental model

> Permission, token registration, provider acceptance, device presentation and user action are separate states. Push is a hint to retrieve current authorized data, not the authoritative record of a business event.

## The mechanism

In an Expo-based pipeline, the application obtains the appropriate permission and push token, then the backend submits a message through the configured push service toward APNs or FCM. Provider responses and receipts can reveal errors such as a device no longer being registered, but they are not proof that the person saw or acted on the message.

Use synthetic fixture states: token T1 was registered for account A; the user signs out; a queued notification is sent; the provider reports DeviceNotRegistered. The backend should deactivate that invalid token association and avoid repeated futile sends. It must also ensure sign-out and account switching remove or replace owner associations so private content is not routed to the wrong user.

Keep sensitive content out of lock-screen payloads unless the product’s privacy design explicitly permits it. Prefer a minimal event reference. When the user opens the app, authenticate and authorize retrieval of current content rather than trusting a notification payload as permission. Validate any navigation target against allowed routes; a push payload must not become arbitrary URL execution.

Design for delay, duplicates and out-of-order messages. Deduplicate user-visible effects by event identity where necessary and fetch authoritative state. Time-sensitive actions need expiry handling. Notification denial should leave the main app usable; reminders are optional delivery paths rather than a prerequisite for core data access.

Test configured native builds and actual provider credentials separately from the local state model. Record permission, token lifecycle, ticket/receipt results and observed device behavior without logging private message contents unnecessarily. This exercise does not send a push or claim delivery on a real device.

## Practice

The push service accepted event E1, but the app has no device receipt or user action. Which status is justified? What should a stale-token error trigger?
