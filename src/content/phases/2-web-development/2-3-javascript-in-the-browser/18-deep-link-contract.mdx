## Why this matters

A shared link opens the expected screen but exposes another user’s record because the route ID was treated as permission. Deep links connect navigation to untrusted external input.

## Start with something familiar

A street address helps a visitor find a building; it does not give them a key. A valid route likewise identifies a destination without authorizing its contents.

## The mental model

> Parse links with a URL parser, allow only the intended scheme/origin/routes and validate parameters. Then perform normal authentication and resource authorization when resolving the destination.

## The mechanism

The fixture accepts only HTTPS links on example.test with the path /lesson followed by a single numeric lesson ID. It rejects query/fragment data and credentials because this small route contract does not use them. Real products may support more shapes, but each must be explicit.

```javascript
import assert from 'node:assert/strict';
function lessonIdFromLink(raw) {
  if (typeof raw !== 'string' || raw.length > 2048) return null;
  try {
    const url = new URL(raw);
    if (url.origin !== 'https://example.test' || url.username || url.password || url.search || url.hash) return null;
    const match = /^\/lesson\/([1-9][0-9]{0,5})$/.exec(url.pathname);
    return match ? match[1] : null;
  } catch {
    return null;
  }
}
assert.equal(lessonIdFromLink('https://example.test/lesson/42'), '42');
for (const bad of ['javascript:alert(1)', 'https://example.test.evil.test/lesson/42', 'https://example.test/lesson/42?owner=bob', 'https://alice@example.test/lesson/42', 'https://example.test/lesson/%2e%2e/admin', 'not a url']) {
  assert.equal(lessonIdFromLink(bad), null);
}
console.log('deep-link parser checks passed');
```

Save the code as link.mjs and run it with Node. The parser returns an identifier only. A server or trusted data boundary must still decide whether the current user may read that lesson/resource. Never accept owner identity from the link as an authorization decision.

For a mobile app, distinguish cold start, an already-running app receiving a link, sign-in interruption and a missing/deleted destination. Preserve only a validated intended route across sign-in; do not create an arbitrary open redirect. Show an understandable unavailable/not-authorized state without leaking private resource details.

Operating-system app links or universal links require platform-specific association configuration and verification. A web parser test does not prove the OS routes a link to your installed app. Test verified domain association, fallback when not installed, and actual lifecycle behavior on supported devices. Avoid putting credentials, sensitive records or authentication tokens in URLs that can enter history and logs.
