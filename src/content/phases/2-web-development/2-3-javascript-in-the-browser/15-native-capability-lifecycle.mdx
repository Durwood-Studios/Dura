## Why this matters

A mobile screen assumes camera access because it worked once on a developer’s phone. Users can deny permission, revoke it later, background the app or run on a device without the expected capability. The feature needs a lifecycle contract.

## Start with something familiar

Borrowing a tool requires checking that it is available, obtaining permission and returning it when finished. A native camera session has the same obligations, even when a framework wraps the platform API.

## The mental model

> A cross-platform UI still runs within platform-specific lifecycle and permission rules. Model capability states explicitly and keep the core task usable when an optional capability is unavailable.

## The mechanism

A native app differs from a responsive web page: it has a packaged identity, platform lifecycle, native permission prompts and APIs whose availability depends on the device and build. React Native/Expo can share much application logic, but permission configuration and actual behavior still require platform tests.

For a receipt-capture feature, distinguish checking permission, permission granted, denied but requestable, denied with settings required, camera unavailable, active capture and interrupted capture. Request permission after the user chooses capture and explain the purpose. Do not repeatedly prompt after denial or block manual entry if scanning is optional.

Expo Camera exposes CameraView and a camera-permission hook in its documented SDK. The exact configured SDK and platform determine setup requirements. A camera component should be mounted only while the capture screen is active; release it when navigating away. Avoid keeping multiple active previews and preserve unsaved form data if the OS interrupts the capture flow.

The supplied scenario has three events: the user declines permission, then chooses manual entry; later they grant permission in Settings and return; finally the app is backgrounded during capture. A valid design must recheck current capability, permit the manual path and avoid claiming that an interrupted photo was saved.

Before release, test actual configured native builds on relevant Android/iOS devices: first request, denial, settings change, background/resume, unavailable hardware and storage failure after capture. A browser preview or successful TypeScript compile does not validate these cases. This lesson authors the state/acceptance contract; it does not build or execute a native camera application.

## Practice

If the user granted permission yesterday but revoked it in Settings today, why is a cached boolean insufficient? What should happen to their typed receipt amount?
