## Why this matters

WebSockets are the backbone of nearly every collaborative, real-time application you've used — Figma's multiplayer, Slack's live messages, GitHub's live PR notifications, online games. Once you understand how to open and maintain a WebSocket connection, you can build features that would be impossible or impractical with polling. More importantly, you'll understand why a connection drops and how to recover from it gracefully — which is the skill that separates a production WebSocket implementation from a fragile demo.

The browser's `WebSocket` API is deceptively small. You can open a connection in one line. But the real work is managing what happens when that connection is lost, flooded with messages, or shut down cleanly — and that's what this lesson covers in full.

## A phone call, not a letter

HTTP is like mailing letters: you send a letter (request), you wait, you get a letter back (response), and then the exchange is over. Every new request starts fresh.

<VocabTooltip slug="websocket">WebSockets</VocabTooltip> are like a phone call. Both sides dial in
once and then either party can talk whenever they want, without waiting for the other to ask a
question. The connection stays open until one side hangs up.

> _A WebSocket is just an HTTP connection that both parties agreed to repurpose into a persistent, two-way pipe._

## The handshake

The connection starts with a standard HTTP request — but with a special header that says "I'd like to upgrade this to a WebSocket."

```
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

The server replies:

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

That `101 Switching Protocols` status code is the <VocabTooltip slug="handshake">handshake</VocabTooltip> completing. After that single HTTP exchange, the TCP connection is repurposed. HTTP is gone. Both sides now speak the WebSocket framing protocol — small binary <VocabTooltip slug="frame">frames</VocabTooltip> that carry your messages.

You never write any of this manually. The browser handles the handshake entirely when you call `new WebSocket(url)`.

## Opening a connection

```javascript
// ws:// for unencrypted, wss:// for TLS-encrypted (always use wss:// in production)
const socket = new WebSocket("wss://example.com/chat");

// The browser fires "open" once the handshake completes
socket.addEventListener("open", () => {
  console.log("Connection established");

  // Send a JSON-encoded message — the server receives this as a string
  socket.send(JSON.stringify({ type: "join", room: "general" }));
});

// "message" fires every time the server sends a frame
socket.addEventListener("message", (event) => {
  // event.data is always a string (or Blob for binary data)
  const msg = JSON.parse(event.data);
  console.log("Received:", msg);
});

// "close" fires when either side closes the connection, or when the network drops
socket.addEventListener("close", (event) => {
  // event.code and event.reason explain why it closed
  console.log(`Closed: code=${event.code} reason=${event.reason}`);
});

// "error" fires before "close" when something goes wrong
socket.addEventListener("error", () => {
  // The error event carries no useful detail by design (security: avoid info leaks)
  // "close" will fire next with the actual code
  console.error("WebSocket error — connection will close");
});
```

## Connection states

A WebSocket has four states, accessible via `socket.readyState`. Sending a message on a non-open socket throws an error, so always guard before you send.

```javascript
// readyState values — the WebSocket API exposes these as constants
// WebSocket.CONNECTING === 0  — handshake in progress
// WebSocket.OPEN       === 1  — connected, safe to send
// WebSocket.CLOSING    === 2  — close handshake in progress
// WebSocket.CLOSED     === 3  — connection is gone

function sendSafely(socket, data) {
  if (socket.readyState !== WebSocket.OPEN) {
    // Queuing logic would go here in production
    console.warn("Cannot send — socket is not open");
    return false;
  }

  socket.send(JSON.stringify(data));
  return true;
}
```

The most common mistake beginners make is calling `socket.send()` in an event handler that fires before `"open"` — the `readyState` is still `CONNECTING` (0) and the call throws.

## Reconnection

Networks drop. Phones switch from WiFi to cellular. Servers restart. A production WebSocket client must reconnect automatically, with exponential backoff so it doesn't hammer a struggling server.

```javascript
class ReconnectingSocket {
  #url;
  #socket = null;
  #retryCount = 0;
  #maxRetryMs = 30_000; // Cap backoff at 30 seconds
  #onMessage;

  constructor(url, onMessage) {
    this.#url = url;
    this.#onMessage = onMessage;
    this.#connect();
  }

  #connect() {
    this.#socket = new WebSocket(this.#url);

    this.#socket.addEventListener("open", () => {
      // Reset the retry counter — we have a healthy connection again
      this.#retryCount = 0;
      console.log("WebSocket connected");
    });

    this.#socket.addEventListener("message", (event) => {
      this.#onMessage(JSON.parse(event.data));
    });

    this.#socket.addEventListener("close", () => {
      // Exponential backoff: 1s, 2s, 4s, 8s, … up to 30s
      // This prevents thundering herd when a server restarts
      const delay = Math.min(1000 * 2 ** this.#retryCount, this.#maxRetryMs);
      this.#retryCount++;
      console.log(`Reconnecting in ${delay}ms (attempt ${this.#retryCount})`);
      setTimeout(() => this.#connect(), delay);
    });

    this.#socket.addEventListener("error", () => {
      // "close" always follows "error" — reconnect logic lives there
    });
  }

  send(data) {
    if (this.#socket?.readyState === WebSocket.OPEN) {
      this.#socket.send(JSON.stringify(data));
    }
  }

  close() {
    // Remove the close listener before closing so we don't trigger reconnection
    this.#socket.removeEventListener("close", this.#connect);
    this.#socket.close(1000, "Client closed intentionally");
  }
}

// Usage
const chat = new ReconnectingSocket("wss://example.com/chat", (msg) => {
  console.log("New message:", msg);
});

chat.send({ type: "message", text: "Hello!" });
```

## Heartbeats

Some proxies and load balancers close idle TCP connections after 60-90 seconds of silence. A <VocabTooltip slug="heartbeat">heartbeat</VocabTooltip> is a lightweight periodic message that keeps the connection alive and also detects silently dropped connections.

```javascript
// Send a ping every 25 seconds — well within most proxy idle timeouts
function startHeartbeat(socket) {
  const interval = setInterval(() => {
    if (socket.readyState === WebSocket.OPEN) {
      socket.send(JSON.stringify({ type: "ping" }));
    } else {
      // Socket is gone — stop sending heartbeats
      clearInterval(interval);
    }
  }, 25_000);

  // Clean up when the connection closes
  socket.addEventListener("close", () => clearInterval(interval));

  return interval;
}
```

The server should reply with a `{ type: "pong" }` message. If the client doesn't receive a pong within a timeout window, it can assume the connection is silently dead and force a reconnect.

## What you learned

- The WebSocket handshake starts as an HTTP request with an `Upgrade` header — the server responds with `101 Switching Protocols` and the TCP connection becomes a persistent two-way pipe
- The browser's `WebSocket` API has four events (`open`, `message`, `close`, `error`) and four `readyState` values — always guard with `readyState === WebSocket.OPEN` before calling `send()`
- Production WebSocket clients must reconnect automatically using exponential backoff to avoid hammering a restarting server
- Heartbeat pings keep connections alive through proxy idle timeouts and reveal silently dropped connections before users notice
