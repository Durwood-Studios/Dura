## Why this matters

The bootloader from lesson 1 taught the concepts: flash layout, descriptor, signature verification, VTOR, rollback counter. MCUboot implements all of those concepts — plus interrupt vector remapping, secondary image encryption, key management, HSM integration, and a simulator for automated testing — in ~50,000 lines of C that have been reviewed by hundreds of engineers and deployed to billions of devices (via Zephyr alone).

The architectural knowledge from lesson 1 is why you understand MCUboot. This lesson is how you deploy it.

## MCUboot architecture overview

MCUboot extends lesson 1's concepts:

```
Flash layout (MCUboot):
┌─────────────────────┐ 0x08000000
│  MCUboot (bootloader)│ — Compiled from mcuboot/boot/cortex-m/
│  ~48 KB             │
├─────────────────────┤ 0x0800C000
│  Primary slot       │ — Currently running application
│  Application image  │   (includes MCUboot image header)
│  + image trailer    │
├─────────────────────┤ 0x08040000
│  Secondary slot     │ — Pending update or backup
│  Application image  │
│  + image trailer    │
├─────────────────────┤ 0x08070000
│  Scratch area       │ — Used by swap mode during OTA
└─────────────────────┘ 0x0807FFFF
```

The **image header** (prepended by `imgtool`) replaces lesson 1's descriptor. It contains magic bytes, image length, TLV pointer, and flags. The **image trailer** at the end of each slot contains the swap-type byte, boot magic, and counters. MCUboot reads the trailer to decide whether to boot the primary, swap slots, or roll back.

## Image signing with imgtool

```bash
# Install imgtool
pip3 install imgtool

# Generate an Ed25519 signing key pair (do this once; store private key securely)
imgtool keygen -k signing-key.pem -t ecdsa-p256   # or ed25519

# Extract public key for embedding in MCUboot binary
imgtool getpub -k signing-key.pem -e c > src/public_key.c

# Sign a compiled firmware binary
imgtool sign \
  --key signing-key.pem \
  --align 4 \
  --version 1.2.3 \
  --header-size 0x200 \
  --slot-size 0x30000 \
  --pad-header \
  build/firmware.bin \
  build/firmware_signed.bin
```

The signed binary includes:

- A 0x200-byte image header with version, length, and TLV pointer
- The application binary
- A TLV (Type-Length-Value) trailer with the Ed25519 signature

MCUboot verifies this signature at boot using the public key embedded in the MCUboot binary. An unsigned or incorrectly signed image is rejected before execution.

## Swap mode vs overwrite mode

**Swap mode** (default, recommended):

- MCUboot copies the secondary slot to the primary slot, saving the old primary into the secondary slot as a backup.
- If the new image confirms itself healthy, the swap is permanent.
- If the new image fails (crash, watchdog, assertion), MCUboot detects the failed boot attempt and swaps BACK to the old image.
- Downside: requires a scratch area (flash sector), and the swap takes longer than overwrite.

**Overwrite mode** (simpler, less safe):

- MCUboot copies the secondary slot directly to the primary, overwriting it.
- No rollback: if the new image is bad, the old image is gone.
- Use only when the system has a recovery mechanism (serial recovery mode, external flash backup).
- Faster and requires no scratch area.

Configure in `mcuboot_config.h`:

```c
/* mcuboot_config.h */
#define MCUBOOT_OVERWRITE_ONLY    /* Uncomment for overwrite mode */
/* Leave commented for swap mode (default) */

#define MCUBOOT_VALIDATE_PRIMARY_SLOT  1  /* Always verify signature on primary */
#define MCUBOOT_VALIDATE_SLOT0_ON_BOOT /* Also verify on every boot, not just on update */
```

## Application: confirming an update

The application must call the MCUboot image-confirm API after boot to signal that it's healthy. Without confirmation, MCUboot treats each boot as a failed attempt and rolls back:

```c
/* In the application's init function — after all hardware initializes successfully */
#include "bootutil/image.h"

void app_confirm_update_if_pending(void) {
    /* Check if we just booted a new (unconfirmed) image */
    struct boot_rsp rsp;
    /* MCUboot provides a status API — simplified here */
    if (boot_is_image_pending_confirm()) {
        int rc = boot_set_confirmed();   /* Mark this image as permanent */
        if (rc != 0) {
            /* Failed to write confirmation — try again or log */
        }
    }
}
```

If the application crashes before reaching this call (due to a firmware bug), MCUboot detects the failed-to-confirm state on the next boot and swaps back to the previous image.

## MCUboot with Zephyr (sysbuild)

MCUboot integrates directly into the Zephyr build system:

```yaml
# west.yml sysbuild configuration
sysbuild:
  cmake-args:
    - -DSB_CONFIG_BOOTLOADER_MCUBOOT=y

# Add to application prj.conf:
CONFIG_BOOTLOADER_MCUBOOT=y
CONFIG_MCUBOOT_SIGNATURE_KEY_FILE="signing-key.pem"
```

```bash
# Build application + MCUboot together
west build -b nrf52840dk/nrf52840 -- -DSB_CONFIG_BOOTLOADER_MCUBOOT=y

# The build produces:
# build/mcuboot/zephyr/zephyr.bin  — the MCUboot binary
# build/app/zephyr/zephyr.signed.bin  — signed application

# Flash both (mcuboot first, then application)
west flash --domain mcuboot
west flash --domain app
```

MCUboot handles the flash layout, linker scripts, and slot sizing automatically when integrated via sysbuild.

## Testing MCUboot with the simulator

MCUboot ships a Rust-based simulator (`sim/`) that tests swap logic, signature verification, and rollback without any hardware:

```bash
cd sim/
cargo test

# Output:
# test swap_within_state ... ok
# test swap_across_image ... ok
# test bad_signature_rejected ... ok
# test rollback_on_unconfirmed ... ok
# 47 tests passed
```

Run the simulator after any MCUboot configuration change to verify the swap logic still works correctly. This is free regression testing that any team contributing to MCUboot must pass.
