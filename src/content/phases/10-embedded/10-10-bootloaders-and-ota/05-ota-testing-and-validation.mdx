## Why this matters

A smart home company updates 50,000 thermostat firmware. The update causes a crash on first boot in 0.3% of devices (a hardware variant the test lab didn't have). Without phased rollout, all 50,000 devices get the bad update simultaneously. With phased rollout (10% → 25% → 100%), only 5,000 devices are affected before the fleet health metrics detect the anomaly and pause the rollout. 45,000 units are saved by the monitoring system.

The monitoring system that detected the anomaly requires: defined health metrics, telemetry from deployed devices, and rollout infrastructure that can pause. None of these are in the firmware — they're the OTA system built around the firmware. This lesson covers how to test the firmware side and how to structure the deployment process to protect the fleet.

## The OTA test matrix

Every OTA system must pass these tests before any deployment:

| Test ID | Scenario                                     | Expected result                                 | Risk if untested                                                           |
| ------- | -------------------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------- |
| OTA-01  | Happy path: complete update                  | Device boots new firmware, confirms healthy     | —                                                                          |
| OTA-02  | Invalid signature (bit flip in image)        | Bootloader rejects, boots old firmware          | Fleet accepts malicious images                                             |
| OTA-03  | CRC mismatch (download corruption)           | Transport discards, retries or reports error    | Corrupt image flashed, device bricks                                       |
| OTA-04  | Incomplete download (connection lost at 60%) | Transfer resumes from offset                    | Full re-download on reconnect (slow but OK) OR wrong image written (brick) |
| OTA-05  | Power fail during flash write                | Bootloader detects incomplete image, boots old  | Device bricks (no old image to boot)                                       |
| OTA-06  | New image crashes on first boot              | Bootloader detects unconfirmed boot, rolls back | Device runs bad firmware indefinitely                                      |
| OTA-07  | Version downgrade attempt                    | Bootloader rejects older version                | Attacker rolls back to vulnerable version                                  |
| OTA-08  | Wrong hardware variant                       | Transport or manifest rejects                   | Wrong firmware on hardware causes safety hazard                            |
| OTA-09  | Update during active sensor operation        | Update completes without disrupting sensor data | Loss of data or sensor misbehavior                                         |

## OTA-01: Happy path (baseline)

```bash
# Build and sign firmware v2.0.0
imgtool sign --key signing-key.pem --version 2.0.0 ... firmware_v2.bin

# Deploy to test device running v1.0.0
# Verify via serial console:
# - Boot log shows "Booting new image v2.0.0"
# - Application telemetry resumes within 5 seconds
# - boot_set_confirmed() called (check debug log)
# - Next boot: no rollback (verify version stays at v2.0.0)
```

## OTA-05: Power-fail during flash write (critical)

The most dangerous failure mode. Power loss during the flash write leaves the secondary slot in an unknown partial state.

Test setup:

- GPIO-controlled relay (or a bench power supply with scripting support) to cut VDD
- Firmware with GPIO marker at "flash sector erase start" and "flash write complete"

```c
/* In the OTA write function: toggle GPIO for logic analyzer correlation */
void ota_write_sector(uint32_t offset, const uint8_t *data, uint32_t len) {
    GPIOB->BSRR = (1U << 0);   /* PB0 high: sector erase start */
    flash_erase_sector(SECONDARY_SLOT_BASE + offset);
    GPIOB->BSRR = (1U << 16);  /* PB0 low: erase complete */

    GPIOB->BSRR = (1U << 1);   /* PB1 high: write start */
    flash_write(SECONDARY_SLOT_BASE + offset, data, len);
    GPIOB->BSRR = (1U << 17);  /* PB1 low: write complete */
}
```

Test procedure:

1. Start OTA update
2. Using logic analyzer trigger + relay: cut power 50 ms after first sector erase (mid-write)
3. Power on
4. **Expected**: MCUboot checks secondary slot image header magic bytes. Incomplete erase/write → corrupted magic → MCUboot validates primary slot only → boots old firmware.
5. Repeat with power cut at different offsets (25%, 50%, 75%, 99% of write)

The primary slot must survive a power fail during a secondary slot write. This is true because the bootloader never modifies the primary slot until AFTER it verifies the secondary slot is complete and valid.

If any power-cut scenario boots a firmware other than the last known-good image, the OTA implementation has a critical bug.

## OTA-06: Rollback on crash

Test that MCUboot rolls back when the application doesn't confirm:

```c
/* Test firmware that crashes immediately on boot */
#include "cortex_m_rt.h"

int main(void) {
    /* Deliberately crash without confirming */
    volatile uint32_t *null_ptr = NULL;
    (void)(*null_ptr);   /* HardFault → reset → MCUboot sees unconfirmed boot */
}
```

Test procedure:

1. Device running v1.0.0 (confirmed)
2. Deploy crashing test firmware signed as v2.0.0
3. MCUboot boots v2.0.0 → crashes → MCUboot increments boot counter
4. Repeat until boot counter threshold
5. **Expected**: MCUboot rolls back to v1.0.0; boot log shows "reverting to previous"
6. v1.0.0 telemetry resumes

Pass criterion: v1.0.0 operational after the crashing v2.0.0 update, no human intervention required.

## OTA-07: Version downgrade prevention

MCUboot's security counter / anti-rollback uses OTP fuses (on supported devices) or persistent flash counters to prevent booting older firmware versions:

```c
/* MCUboot configuration for anti-rollback */
#define MCUBOOT_HW_ROLLBACK_PROT  1   /* Enable hardware anti-rollback */

/* In imgtool, set the security counter (monotonic) */
imgtool sign \
  --key signing-key.pem \
  --security-counter 5 \
  ... firmware_v2.bin
```

MCUboot stores the highest seen security counter value in OTP fuses or persistent flash. An image with security-counter < stored value is rejected regardless of signature validity.

Test:

1. Deploy firmware with security-counter=5 (verified working)
2. Attempt to deploy firmware with security-counter=4 (a previous version, perhaps with known vulnerabilities)
3. **Expected**: MCUboot rejects the older image, continues booting v2.0.0
4. Boot log: "Security counter too low, rejecting image"

## Phased rollout and fleet health metrics

Never deploy an OTA update to 100% of the fleet simultaneously. Phased rollout:

```
Day 1: Deploy to 1% of fleet (canary)
Day 2: Monitor. If health metrics OK: deploy to 10%
Day 3: Monitor. If OK: deploy to 50%
Day 4: Monitor. If OK: deploy to 100%
```

Fleet health metrics that detect a bad update:

```python
# Pseudo-code for fleet health monitoring
ALERT_THRESHOLD = 0.02  # 2% crash rate is abnormal

def check_fleet_health(firmware_version):
    devices_on_version = query_fleet_db(firmware_version=firmware_version)
    crash_count = query_fleet_db(firmware_version=firmware_version,
                                  event="crash_within_1_hour_of_boot")

    crash_rate = crash_count / len(devices_on_version)

    if crash_rate > ALERT_THRESHOLD:
        pause_rollout(firmware_version)
        alert_ops_team(f"Version {firmware_version} crash rate {crash_rate:.1%} exceeds threshold")
        # Optionally: push rollback to affected devices
```

The 2% threshold is a starting point; adjust based on the fleet's baseline crash rate with known-good firmware. Alert thresholds that are too tight produce false alarms; too loose and you miss real problems.

## The golden image

Keep a "golden image" — the last known-good production firmware, signed and tested — archived separately from the release process. If a deployment goes badly and rollback via MCUboot doesn't work (perhaps because the update reached too many devices before detection), the golden image can be deployed directly:

```bash
# Emergency: deploy golden image to entire fleet
ota_push_emergency.sh \
  --image golden_image_v1.2.3_signed.bin \
  --target all \
  --priority critical \
  --bypass-rollout-control   # Skips phased rollout for emergency
```

The golden image must be a separate artifact from the production release, stored in a secure location, tested independently, and accessible without going through the normal release pipeline.
