## Why this matters

The bootloader from lessons 1-2 verifies every image it boots. But what decides which image lands in the secondary slot? The transport layer. If the transport is insecure, an attacker can serve any image — the bootloader's CRC will pass (attacker computed it), and only the Ed25519 signature will catch it. If the transport also verifies the signature before writing to flash, the attack surface shrinks further.

Defense in depth: verify at transport (does the image come from the right source?), verify at bootloader (is the image signed by the right key?). Both layers operating independently makes the system robust even if one layer is compromised.

## Responsibilities: transport vs bootloader

| Responsibility                          | Transport layer                                | Bootloader             |
| --------------------------------------- | ---------------------------------------------- | ---------------------- |
| Discover update availability            | Yes                                            | No                     |
| Download image                          | Yes                                            | No                     |
| Verify TLS certificate                  | Yes                                            | No                     |
| Check manifest (version, target device) | Yes                                            | No                     |
| Write image to secondary slot           | Yes                                            | No                     |
| Verify image CRC                        | Both (transport pre-check, bootloader at boot) | Yes                    |
| Verify image signature                  | Optional (transport)                           | Mandatory (bootloader) |
| Execute the update                      | No                                             | Yes                    |
| Rollback on failure                     | No (triggers the bootloader mechanism)         | Yes                    |

The transport layer handles discovery and delivery. The bootloader handles verification and execution. The two layers communicate via the flash slot (image written by transport, read by bootloader) and the persistent state (pending_update flag set by transport, read by bootloader).

## BLE OTA: chunked DFU

BLE has a Maximum Transmission Unit (MTU) of 20-244 bytes depending on negotiation. Firmware images are 100s of KB. The transport must chunk the image and assemble it in flash:

```c
/* BLE DFU — application side (pseudo-code for clarity) */

#define CHUNK_SIZE    128U    /* Bytes per BLE write */
#define FLASH_SECTOR  131072U /* Bytes per flash sector */

typedef struct {
    uint32_t total_size;
    uint32_t offset;
    uint32_t running_crc;
} dfu_state_t;

/* Called by BLE stack on each received chunk */
void on_dfu_data_received(const uint8_t *chunk, uint16_t len) {
    /* Erase flash sector when offset aligns with sector boundary */
    if ((dfu_state.offset % FLASH_SECTOR) == 0U) {
        flash_erase_sector(SECONDARY_SLOT_BASE + dfu_state.offset);
    }

    /* Write chunk to secondary slot */
    flash_write(SECONDARY_SLOT_BASE + dfu_state.offset, chunk, len);

    /* Update running CRC for final verification */
    dfu_state.running_crc = crc32_update(dfu_state.running_crc, chunk, len);
    dfu_state.offset += len;
}

/* Called after all chunks received */
bool dfu_finalize(uint32_t expected_crc) {
    if (dfu_state.running_crc != expected_crc) {
        /* CRC mismatch — download corrupted; erase secondary slot */
        flash_erase_range(SECONDARY_SLOT_BASE, dfu_state.total_size);
        return false;
    }
    /* Write pending-update flag to persistent state */
    persistent_state.pending_update = true;
    flash_write_persistent_state(&persistent_state);
    return true;
}
```

Chunked transfer with a running CRC means no complete-image CRC computation at the end (which would require reading back the entire secondary slot). The CRC is computed as each chunk arrives and verified against the expected value from the DFU manifest.

Nordic's DFU SDK (used with nRF52840 and MCUboot) implements this pattern in production, including retry logic and transfer resumption after BLE disconnection.

## MQTT OTA: delta updates and manifest-first approach

MQTT OTA is common in IoT fleets. The pattern:

```
Device ──subscribe──► "device/firmware/update/{device_id}" topic
Fleet manager ──publish──► manifest JSON on that topic
Device ──parses manifest, evaluates policy (is this newer? right target?)──►
Device ──downloads image from URL in manifest via HTTPS──►
Device ──writes to secondary slot, sets pending_update──►
Device ──reboots into MCUboot──►
```

A manifest JSON:

```json
{
  "manifest_version": 1,
  "firmware_version": "2.1.0",
  "target_hardware": "sensor-node-v3",
  "image_url": "https://firmware.example.com/release/sensor-node-v3-2.1.0.bin",
  "image_sha256": "a1b2c3d4...",
  "image_size": 131072,
  "signature": "base64-encoded-Ed25519-sig-over-all-above-fields",
  "rollout_percentage": 10
}
```

The device verifies the manifest signature before downloading the image. If the manifest is tampered (wrong URL, substituted hash), the signature check fails. Only if the manifest is valid does the device download and write the image.

The `rollout_percentage` field enables canary releases: only 10% of the fleet receives the update initially. After 48 hours with no failure reports, the percentage increases. This is how large IoT fleets (millions of devices) roll out firmware safely.

## HTTPS OTA: TLS alone is not enough

HTTPS with TLS server authentication protects against network eavesdropping and man-in-the-middle attacks against the connection. It does NOT protect against:

- A compromised update server that serves a malicious image
- A misconfigured CDN that caches the wrong version
- A developer who accidentally publishes the wrong binary

The complete security chain for HTTPS OTA:

1. **TLS with certificate pinning** — the device verifies the server's certificate against a pinned public key, not just against a trusted CA. This prevents certificate compromise attacks.
2. **HTTPS image download** — transport layer integrity (no MITM in transit)
3. **SHA-256 image hash verification** — integrity check from a signed manifest
4. **Ed25519 signature verification** — authenticity check in the bootloader

Certificate pinning in C using mbedTLS:

```c
/* Pinned server certificate (DER-encoded, embedded in firmware) */
static const uint8_t server_cert_der[] = {
    /* ... DER bytes of the known-good server certificate ... */
};

mbedtls_x509_crt server_cert;
mbedtls_x509_crt_init(&server_cert);
mbedtls_x509_crt_parse_der(&server_cert, server_cert_der, sizeof(server_cert_der));

mbedtls_ssl_conf_ca_chain(&ssl_conf, &server_cert, NULL);
mbedtls_ssl_conf_authmode(&ssl_conf, MBEDTLS_SSL_VERIFY_REQUIRED);
/* If the server presents a different certificate, TLS handshake fails */
```

Certificate pinning has a maintenance cost: when the server certificate expires or is rotated, pinned clients need an update to pin the new certificate. Mitigations: pin the CA certificate instead of the leaf, use long-lived certificates, or include both old and new pinned certificates during a rotation window.

## The SUIT manifest standard

IETF RFC 9019 defines the SUIT (Software Update for IoT) manifest — a standardized, CBOR-encoded format for describing firmware updates. SUIT manifests include:

- Target device class and hardware version
- Fetch instructions (where to download the image)
- Condition checks (minimum space, current version, etc.)
- Processing directives (decrypt before writing, apply delta)
- Signature (COSE-Sign, using Ed25519 or ECDSA)

SUIT separates the update POLICY (conditions, directives) from the image content. The bootloader evaluates the manifest before downloading anything. This is more expressive than a simple JSON manifest and is the direction the embedded industry is moving for standardized OTA.

MCUboot added experimental SUIT support in 2024. Zephyr's DFU subsystem targets SUIT as the manifest format for future versions.
