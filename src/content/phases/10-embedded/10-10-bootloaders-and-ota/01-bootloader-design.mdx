## Why this matters

An update must survive interrupted writes and reject unauthorized firmware before execution. These are separate requirements: two image slots help recovery, while authenticated image validation establishes which bytes may run. A signed but incompatible image can still fail, and a recoverable update scheme can still accept malicious code if its verification contract is wrong.

## Start with something familiar

A tamper-evident package must bind its contents as well as the shipping label. Authenticating a label that describes the contents with a weak checksum leaves room to replace those contents without changing the label.

## The mental model

> A bootloader validates bounded image bytes and authenticated metadata before execution, while persistent update state and rollback policy preserve a recoverable trusted path.

## Flash layout follows the exact device

Define the protected bootloader region, active and staging image slots, image metadata, and persistent update state. Align operations to the device's erase sectors and programming granularity. Logical A/B slots do not necessarily correspond to two physical flash banks; read-while-write and bank-swap behavior are device-specific.

Keep executable payload separate from metadata according to a documented image format. A length in an untrusted descriptor must be checked against the slot capacity before hashing or reading it. Check arithmetic for overflow and reject truncated headers, unsupported formats, wrong device identifiers, and impossible vector-table positions.

A flash map for one STM32F4 part is not a family-wide layout. Verify the exact part, flash density, boot aliases, RAM regions, and protection mechanisms before writing a linker script or programming option bytes.

## Bind the actual image to the signature

A CRC detects many accidental corruptions but is not collision-resistant. An attacker can construct different payload bytes with the same CRC. Therefore a signature over only magic, version, length, and CRC32 does **not** securely authenticate the payload, even when the signature itself is valid.

Use a vetted image-signing scheme that authenticates the image bytes or a cryptographic digest of them, together with all metadata that influences acceptance or execution. A conceptual manifest might contain:

- Format and target identifiers.
- Payload length and entry/vector location.
- A security counter or version used by rollback policy.
- A SHA-256 digest of the exact payload bytes.
- A signature over the canonical manifest encoding, including that digest.

Define byte order, field sizes, and domain separation in the format. Signing an in-memory C structure directly is fragile because padding, endianness, and representation can differ. Do not permit an unsigned field to override a signed field after verification.

The bootloader recomputes the image digest over the validated range and compares it with the authenticated manifest digest. It verifies the signature using the configured trusted public key and applies the target and rollback policy. The signing private key remains outside the device's verification path.

[MCUboot's image documentation](https://docs.mcuboot.com/signed_images.html) describes signing an image digest, and its [design specification](https://github.com/mcu-tools/mcuboot/blob/main/docs/design.md) defines which headers and protected metadata are included. Integrate a documented format rather than inventing a production boot protocol from this sketch.

## A validation outline, not a complete bootloader

The following C demonstrates ordering and bounds. The helper functions are application interfaces whose implementation must use the chosen format and vetted cryptographic library; they are not names of an SDK API. The manifest signature covers every field used by these checks, including `image_sha256`.

```c
#include <stdbool.h>
#include <stdint.h>
#include <stddef.h>
#include <string.h>

struct manifest {
    uint32_t format;
    uint32_t target;
    uint32_t image_length;
    uint32_t security_counter;
    uint8_t image_sha256[32];
    uint8_t signature[64];
};

extern bool supported_format_and_target(const struct manifest *m);
extern bool trusted_manifest_signature_valid(const struct manifest *m);
extern bool security_counter_allowed(uint32_t counter);
extern bool hash_image_sha256(const uint8_t *image, size_t length,
                              uint8_t digest[32]);

bool image_is_eligible(const struct manifest *m, const uint8_t *image,
                       size_t slot_capacity) {
    if (m == NULL || image == NULL) return false;
    if (m->image_length < 8u || m->image_length > slot_capacity) return false;
    if (!supported_format_and_target(m)) return false;
    if (!trusted_manifest_signature_valid(m)) return false;
    if (!security_counter_allowed(m->security_counter)) return false;

    uint8_t actual_digest[32];
    if (!hash_image_sha256(image, m->image_length, actual_digest)) return false;
    return memcmp(actual_digest, m->image_sha256, sizeof actual_digest) == 0;
}
```

Digest values are public comparison inputs here. This outline assumes the manifest and image cannot change between validation and use; enforce that through flash ownership and protection. It does not parse the wire format, protect keys, perform an atomic upgrade, or validate the stack and reset vector. Those are still required before execution.

## Recovery and rollback resistance are different

Download into a bounded staging area while retaining a trusted recovery path. Validate the complete artifact before marking it eligible. A selected upgrade mode may boot it provisionally and require the application to confirm health; an unconfirmed image can then revert according to that mode's persistent state machine.

Reverting an unhealthy trial image is a reliability feature. Rejecting an older vulnerable image is a security policy. Coordinate them so advancing a protected security counter does not destroy the only recoverable image before the new one is accepted. Define the commit point and test power loss on both sides of it.

A version number stored only in attacker-writable metadata does not enforce rollback resistance. The accepted counter or policy needs suitable protected persistent state and a recovery design appropriate to the threat model.

## Transfer control only after platform checks

For a Cortex-M application, verify that the initial stack pointer is aligned and lies in an allowed RAM region, and that the reset entry has the required Thumb-state bit and targets authenticated executable bytes. Account for the selected core's vector-table relocation support and alignment requirements.

Before handoff, place interrupts, pending exceptions, SysTick, peripherals, and clocks in the state expected by the application. Changing the main stack pointer inside ordinary C and then continuing compiler-generated stack accesses is unsafe; use a reviewed target-specific handoff routine or supported boot framework. A VTOR write alone is not a complete handoff.

## Guided practice

An attacker can alter payload bytes and arrange for the original CRC32 to remain unchanged. The signature covers only the payload length and CRC32. Does removing a version-zero signature bypass fix the whole design?

<details>
<summary>Trace the remaining attack</summary>

No. Removing the bypass ensures a signature is checked, but the signed CRC still does not uniquely bind the payload. Authenticate a cryptographic digest of the exact bounded image and all relevant metadata, recompute that digest, and check rollback and target policy. A valid signature over weakly bound metadata remains insufficient.

## What you learned

- Bind signatures to image bytes and execution-relevant metadata.
- Check ranges and platform constraints before reading or executing an image.
- Distinguish rollback resistance from recovery after a failed trial image.
- Verify persistent update transitions and the target-specific handoff separately.
