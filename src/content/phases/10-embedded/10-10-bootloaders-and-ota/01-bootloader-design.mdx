## Why this matters

Every device in the field eventually needs a firmware update. The mechanism that makes that safe — a bootloader — is also the first code that runs after reset. If the bootloader has bugs, the device bricks. If it has security holes, every device in your fleet becomes a remote code execution target. Industrial controllers, medical devices, consumer IoT, automotive ECUs: they all run a bootloader, and the decisions you make in its design propagate for the entire product lifetime.

The economic stakes are real. A failed OTA update on a device without a failsafe dual-bank architecture means a truck roll or a product recall. A bootloader that executes unsigned firmware means an attacker who intercepts a firmware update channel can own every device in your fleet simultaneously. These are not theoretical risks — they are the documented root cause of real product recalls and CVEs. Understanding how to design a bootloader correctly is one of the highest-leverage embedded skills you can have.

## The problem a bootloader solves

Imagine you ship a physical safe with a combination lock. The combination is welded into the metal at the factory. Later you discover the combination is wrong. There is no way to change it without physically opening the safe — which destroys the security.

A microcontroller without a bootloader has the same problem. Flash is the combination: the application image baked in at production. To change it, a programmer must be physically attached. Bootloaders are the mechanism that lets the safe change its own combination — over a network, over UART, over BLE — while maintaining the security and reliability guarantees that make a safe worth having.

> **A bootloader is just a small, trusted program that runs before the application, decides whether the application is trustworthy and valid, and either jumps to it or refuses to.**

## Flash layout — the foundation

Before writing a line of bootloader code, you must decide how flash is partitioned. This is a hardware-constrained design problem: flash on a Cortex-M device has a fixed size, a fixed erase granularity (sectors, not bytes), and a fixed location. The layout you choose determines which OTA strategies are even possible.

A minimal dual-bank layout on a 512 KB flash device:

```
Flash (0x08000000 — 0x0807FFFF, 512 KB)

┌──────────────────────────────────┐ 0x08000000
│  Bootloader (64 KB)              │ — Starts at reset vector; must NEVER be updated
│  Signature public key embedded   │
│  Interrupt vectors at top        │
├──────────────────────────────────┤ 0x08010000
│  Application Descriptor A (256B) │ — Magic, version, CRC, image length, signature
├──────────────────────────────────┤ 0x08010100
│  Application Image A (192 KB)    │ — The currently running application
│  Starts with its own vector table│
├──────────────────────────────────┤ 0x08040100
│  Application Descriptor B (256B) │ — Same format; describes the candidate image
├──────────────────────────────────┤ 0x08040200
│  Application Image B (192 KB)    │ — The pending update, or a backup
├──────────────────────────────────┤ 0x08070200
│  Persistent State (32 KB)        │ — Boot counter, selected bank, update flags
└──────────────────────────────────┘ 0x0807FFFF
```

The layout is expressed as a linker script so the compiler and linker enforce it:

```ld
/* bootloader.ld — linker script for the bootloader image only */
MEMORY
{
    /* Bootloader occupies the first 64K of flash */
    FLASH_BOOT (rx)  : ORIGIN = 0x08000000, LENGTH = 64K

    /* RAM is not partitioned — bootloader and app share it at different times */
    RAM (xrw)        : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .isr_vector :
    {
        KEEP(*(.isr_vector))    /* Vector table MUST be at flash origin */
    } > FLASH_BOOT

    .text :
    {
        *(.text*)
        *(.rodata*)             /* Public key lives here as a const array */
    } > FLASH_BOOT

    /* ... .data, .bss sections for bootloader's own RAM use ... */
}
```

A separate `app_a.ld` for the application sets `FLASH (rx) : ORIGIN = 0x08010100, LENGTH = 192K`. The application never needs to know about the bootloader or the other bank.

## Application descriptor — the trust contract

The bootloader needs to know whether an image is valid before jumping to it. Raw flash bytes tell you nothing. An **application descriptor** is a small, fixed-format struct written at a known address (the 256 bytes before each image) that the bootloader reads first:

```c
/* app_descriptor.h — shared between bootloader and application build */

#define APP_MAGIC    0xDEADC0DE    /* Arbitrary sentinel, must not appear by chance */
#define APP_DESC_VERSION 1

typedef struct __attribute__((packed)) {
    uint32_t magic;            /* Must equal APP_MAGIC */
    uint32_t version;          /* Monotonically increasing app version number */
    uint32_t image_length;     /* Byte count of the application image */
    uint32_t crc32;            /* CRC-32 over the application image bytes */
    uint8_t  ed25519_sig[64];  /* Ed25519 signature over (magic|version|length|crc32) */
    uint8_t  reserved[168];    /* Pad to 256 bytes */
} AppDescriptor;

/* Addresses defined by the linker scripts */
#define APP_A_DESC_ADDR   ((const AppDescriptor *)0x08010000)
#define APP_A_IMAGE_ADDR  (0x08010100)
#define APP_B_DESC_ADDR   ((const AppDescriptor *)0x08040200)
#define APP_B_IMAGE_ADDR  (0x08040300)
```

The bootloader's verification sequence must be:

1. Check `magic` — reject immediately if wrong (avoids reading garbage flash).
2. Validate `crc32` over the image bytes — detects bit errors and incomplete writes.
3. Verify the Ed25519 signature — proves the image was created by the private key holder.
4. Only then: relocate the vector table and jump.

Order matters here. Signature verification is computationally heavier than a CRC check, so you do the cheap structural check (magic, CRC) first to fast-fail on corrupt flash without burning cycles on crypto. But signature verification MUST happen before any jump — a valid CRC proves integrity (no corruption), but only a valid signature proves authenticity (no malicious substitution).

## The boot decision and dual-bank swap

At reset, the bootloader runs this logic:

```c
/* boot.c — bootloader entry point after startup.s */

#include "app_descriptor.h"
#include "crypto.h"   /* ed25519_verify(), using the public key in .rodata */
#include "crc.h"      /* crc32_compute() */
#include "flash.h"    /* flash_read_persistent_state(), flash_write_persistent_state() */

/* Public key compiled into the bootloader at build time — never in RAM, never writable */
static const uint8_t PUBLIC_KEY[32] __attribute__((section(".rodata.pubkey"))) = {
    /* 32 bytes of the Ed25519 public key corresponding to the private signing key */
    0xAB, 0xCD, /* ... rest of key bytes ... */
};

typedef enum { BANK_A = 0, BANK_B = 1 } Bank;

static bool verify_image(const AppDescriptor *desc, uint32_t image_base) {
    /* Step 1: structural sentinel — avoids misinterpreting erased flash (0xFF...FF) */
    if (desc->magic != APP_MAGIC) {
        return false;
    }

    /* Step 2: integrity — make sure flash write completed without corruption */
    uint32_t computed = crc32_compute((const uint8_t *)image_base, desc->image_length);
    if (computed != desc->crc32) {
        return false;
    }

    /* Step 3: authenticity — only images signed with our private key are executable.
       An attacker with a valid CRC but no signing key fails here. */
    uint8_t msg[16];
    memcpy(msg + 0,  &desc->magic,        4);
    memcpy(msg + 4,  &desc->version,      4);
    memcpy(msg + 8,  &desc->image_length, 4);
    memcpy(msg + 12, &desc->crc32,        4);
    return ed25519_verify(PUBLIC_KEY, msg, sizeof(msg), desc->ed25519_sig);
}

static void jump_to_app(uint32_t image_base) {
    /* The application's vector table is at image_base.
       Cortex-M VTOR (Vector Table Offset Register) redirects exception handling. */
    SCB->VTOR = image_base;

    /* Stack pointer is the first word; reset handler is the second. */
    uint32_t app_sp     = *(volatile uint32_t *)(image_base + 0);
    uint32_t app_entry  = *(volatile uint32_t *)(image_base + 4);

    /* Set the stack pointer before calling the application's reset handler */
    __set_MSP(app_sp);

    /* Typecast to a function pointer and call — this does NOT return */
    void (*app_reset_handler)(void) = (void (*)(void))app_entry;
    app_reset_handler();

    /* Should never reach here; loop if we do (defense in depth) */
    while (1) { }
}

void bootloader_main(void) {
    PersistentState state = flash_read_persistent_state();

    /* Increment boot counter — if we reboot 3 times without confirming a new image,
       fall back to the previously known-good bank */
    state.boot_counter++;
    if (state.boot_counter >= 3 && state.pending_update) {
        /* The candidate image caused repeated reboot loops — roll back */
        state.active_bank   = (state.active_bank == BANK_A) ? BANK_B : BANK_A;
        state.pending_update = false;
        state.boot_counter   = 0;
    }
    flash_write_persistent_state(&state);

    /* Try the active bank first */
    const AppDescriptor *primary_desc  = (state.active_bank == BANK_A)
                                         ? APP_A_DESC_ADDR : APP_B_DESC_ADDR;
    uint32_t primary_base = (state.active_bank == BANK_A)
                            ? APP_A_IMAGE_ADDR : APP_B_IMAGE_ADDR;

    if (verify_image(primary_desc, primary_base)) {
        jump_to_app(primary_base);
        /* jump_to_app does not return */
    }

    /* Primary bank failed verification — try the other bank before giving up */
    const AppDescriptor *fallback_desc  = (state.active_bank == BANK_A)
                                          ? APP_B_DESC_ADDR : APP_A_DESC_ADDR;
    uint32_t fallback_base = (state.active_bank == BANK_A)
                             ? APP_B_IMAGE_ADDR : APP_A_IMAGE_ADDR;

    if (verify_image(fallback_desc, fallback_base)) {
        jump_to_app(fallback_base);
    }

    /* Both banks failed — enter recovery mode (blink LED, wait for serial flash tool) */
    recovery_mode_enter();
}
```

The `boot_counter` + rollback pattern is critical. If the new image causes a hard fault, watchdog reset, or assertion failure before the application confirms itself as healthy (by clearing `pending_update`), the bootloader detects the repeated reboot loop and rolls back. The application must call a "commit this image" function during startup to confirm it is healthy.

## Vector table relocation — the detail that bricks devices

The Cortex-M vector table lives at address `0x00000000` by default, aliased to flash. When the bootloader jumps to an application at a non-zero address, the application's vector table is no longer at address 0. Without relocation, any interrupt the application takes will call bootloader ISR handlers — or, worse, whatever is in the bootloader's table. This causes silent misbehavior that is extremely hard to debug.

`SCB->VTOR = image_base` is the one-line fix. The Vector Table Offset Register tells the Cortex-M core where the active vector table is. The bootloader sets this to the application's base address before the jump. The application itself may also set it in its `SystemInit()` or startup code — this is redundant but harmless.

A device that bricks after a firmware update but works after full factory flash almost always has a VTOR bug.

## What you learned

- Flash partitioning for dual-bank OTA requires deliberate linker script design: bootloader, descriptor A, image A, descriptor B, image B, and persistent state each occupy defined, non-overlapping flash regions that match the erase granularity.
- A secure bootloader verifies images in order: magic sentinel (fast-fail on erased flash) → CRC (integrity, detects corruption) → Ed25519 signature (authenticity, defeats injection attacks). Skipping any step is a security regression.
- Vector table relocation via `SCB->VTOR` must happen before the jump to the application, not after, to close the interrupt-delivery race window between the two code regions.
- The boot counter in persistent state implements a rollback watchdog: if the application crashes before confirming itself healthy, the bootloader rolls back automatically, restoring the device to service without physical access.
- A version-based signature bypass is an authentication hole regardless of intent — every image, including factory images, must carry a valid signature.
