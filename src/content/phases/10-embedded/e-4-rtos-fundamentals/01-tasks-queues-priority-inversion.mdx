## When you need an RTOS

The superloop pattern from E2 looks like this:

```c
while (1) {
    read_sensor();
    process_data();
    update_display();
    handle_button();
}
```

Works fine until your timing requirements diverge: the sensor needs 1 ms response, the display needs 16 ms refresh, the button can wait 100 ms. A superloop runs everything at the speed of the slowest step. You need true concurrency.

An RTOS gives you tasks — independent threads of execution with their own priorities and stacks. The scheduler picks the highest-priority task that's ready to run, preempts lower-priority tasks, and switches context on each tick or blocking call.

The threshold concept: **once you have an RTOS, work decomposes into tasks that communicate via queues and synchronize via mutexes, instead of a single loop juggling everything.** The mental model shift is large; once it lands, embedded design gets dramatically simpler.

## FreeRTOS task basics

A FreeRTOS task is a function that loops forever and yields explicitly (or blocks on a kernel object):

```c
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

static QueueHandle_t sensor_queue;

void sensor_task(void *params) {
    (void)params;
    for (;;) {
        uint16_t sample = adc_read();
        xQueueSend(sensor_queue, &sample, portMAX_DELAY);
        vTaskDelay(pdMS_TO_TICKS(1));   // 1 ms
    }
}

void processor_task(void *params) {
    (void)params;
    uint16_t sample;
    for (;;) {
        // Block until a sample arrives — no busy-wait
        if (xQueueReceive(sensor_queue, &sample, portMAX_DELAY) == pdPASS) {
            process(sample);
        }
    }
}

void display_task(void *params) {
    (void)params;
    for (;;) {
        update_display();
        vTaskDelay(pdMS_TO_TICKS(16));  // ~60 Hz
    }
}

int main(void) {
    sensor_queue = xQueueCreate(32, sizeof(uint16_t));

    xTaskCreate(sensor_task,    "sensor", 256, NULL, 5, NULL);   // High priority
    xTaskCreate(processor_task, "proc",   512, NULL, 4, NULL);   // Medium
    xTaskCreate(display_task,   "disp",   384, NULL, 3, NULL);   // Lower

    vTaskStartScheduler();
    for (;;) { }                                                   // Never reached
}
```

Three tasks running concurrently on one CPU. The sensor task wakes every 1 ms, samples, posts. The processor task wakes whenever the queue has data and processes. The display task wakes every 16 ms. Each task blocks (yields the CPU) when waiting; the scheduler runs other tasks during the wait.

Priority guidance: highest priority for the most time-sensitive work, lowest for housekeeping. Within reason — there's a known anti-pattern of "make everything high priority because it feels important."

## Queues from ISRs

A USART RX ISR posts a byte to a queue; a task processes it:

```c
static QueueHandle_t uart_rx_queue;

void USART2_IRQHandler(void) {
    if (USART2_SR & SR_RXNE) {
        uint8_t byte = USART2_DR;
        BaseType_t woken = pdFALSE;
        xQueueSendFromISR(uart_rx_queue, &byte, &woken);
        portYIELD_FROM_ISR(woken);
    }
}

void uart_handler_task(void *params) {
    (void)params;
    uint8_t byte;
    for (;;) {
        if (xQueueReceive(uart_rx_queue, &byte, portMAX_DELAY) == pdPASS) {
            process_byte(byte);
        }
    }
}
```

Notice the `FromISR` suffix on the kernel call. ISR-context variants exist because the kernel needs to know it's running with interrupts disabled and a smaller stack. Calling `xQueueSend` (the non-ISR variant) from an ISR is a hard error — FreeRTOS will assert (in debug builds) or quietly corrupt state (in release).

The `portYIELD_FROM_ISR(woken)` triggers a context switch if the queue-send unblocked a higher-priority task. Without it, the higher-priority task waits until the next tick.

## Mutexes and priority inheritance

When two tasks share a resource (a SPI bus, a struct, a global counter), they need a mutex:

```c
static SemaphoreHandle_t spi_mutex;

void spi_write(const uint8_t *data, size_t len) {
    xSemaphoreTake(spi_mutex, portMAX_DELAY);
    for (size_t i = 0; i < len; i++) {
        spi_transfer_byte(data[i]);
    }
    xSemaphoreGive(spi_mutex);
}
```

FreeRTOS mutexes implement **priority inheritance**. If a high-priority task blocks on a mutex held by a low-priority task, the kernel temporarily boosts the low-priority task to the high task's priority until it releases the mutex. This is the fix for priority inversion.

## The Mars Pathfinder bug

In 1997 the Mars Pathfinder rover started resetting itself. The bug was priority inversion:

> A high-priority bus-management task waited on a mutex held by a low-priority meteorological task. A medium-priority communications task preempted the meteorological task, blocking it from releasing the mutex. The high-priority task missed its deadline; the watchdog detected the missed deadline; the system reset.

The fix: enable priority inheritance on the mutex (the medium task can no longer preempt the temporarily-boosted low task). The fix was deployed remotely after the bug was reproduced on the ground.

FreeRTOS mutexes have priority inheritance enabled by default; semaphores (which are similar but for signaling) do not. The choice matters:

- **Mutex** — protects a shared resource, implements priority inheritance, owned by the task that took it.
- **Semaphore (binary)** — signaling primitive, no inheritance, can be given by one task and taken by another.

A common bug: using a semaphore where a mutex is needed because "they look similar." This reintroduces the Pathfinder failure mode in your firmware.

## Stack sizing

Each task has its own stack, sized at creation. Underestimate and the task overflows into another task's memory (a corruption you'll spend days debugging). Overestimate and you waste RAM.

The standard practice:

1. Start at 512 bytes for small tasks, 1024 for medium, 2048+ for tasks with deep call chains or large local buffers.
2. Run `uxTaskGetStackHighWaterMark(task)` periodically to see the maximum stack usage observed. If it's < 50% of the allocation, you can shrink.
3. Never put large arrays as local variables in a task function — they live on the task's stack.

Stack overflow detection is configurable in FreeRTOS (`configCHECK_FOR_STACK_OVERFLOW`); enable it in development. The hook fires when a task overflows so you get a defined failure instead of silent corruption.

## When NOT to use an RTOS

The superloop is fine when:

- One main timing requirement dominates (e.g., a sensor at 100 Hz with everything else slack).
- The chip has < 16 KB SRAM (RTOS overhead per task is ~100 bytes + stack).
- The product is simple (a temperature controller, a button-and-LED toy).

Trade-offs at the margin: a thoughtful superloop with cooperative state machines can serve a surprising number of products. An RTOS adds debugging surface (priority inversions, stack overflows, race conditions across tasks) that a superloop avoids. Use the RTOS when the concurrency complexity exceeds what a superloop can elegantly express — not before.
