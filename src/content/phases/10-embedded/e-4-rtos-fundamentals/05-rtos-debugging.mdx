## Why this matters

An IoT gateway ships to 50,000 units. Six weeks after deployment, 1 in 400 units starts resetting every 2 hours. No crashlog. No reproducible trigger in the lab. The bug is a task starvation leading to a missed watchdog kick — the low-priority housekeeping task that pets the watchdog gets starved by two medium-priority tasks fighting over a shared SPI bus.

This is a known pattern. Recognized in under an hour by an engineer who has seen it. Unknown pattern. Costs two weeks and a firmware update to 50,000 units for an engineer who hasn't.

RTOS debugging fluency is a professional force multiplier.

## The five failure modes and their fingerprints

### 1. Stack overflow

**Symptom**: System crashes or produces garbage values unpredictably. Usually a HardFault, with the program counter in completely unexpected code.

**Root cause**: A task's stack grew beyond its allocated region and corrupted adjacent memory.

**Detection**:

```c
/* FreeRTOSConfig.h */
#define configCHECK_FOR_STACK_OVERFLOW  2

void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName) {
    /* pcTaskName has the task name (up to configMAX_TASK_NAME_LEN chars) */
    /* Log it via RTT or a GPIO toggle pattern before asserting */
    rtt_printf("STACK OVERFLOW in task: %s\n", pcTaskName);
    __BKPT(0);   /* Break in debug; in production, trigger controlled reset */
    while (1) { }
}
```

**Instrument**: After the system has been running for 30 minutes under load, call `uxTaskGetStackHighWaterMark` on every task. Any task with HWM < 20% of its allocation needs more stack.

### 2. Priority inversion (without inheritance)

**Symptom**: High-priority task misses deadlines at random intervals. System appears to work most of the time.

**Root cause**: A binary semaphore (no priority inheritance) is held by a low-priority task; a medium-priority task preempts it and prevents the mutex release, blocking the high-priority task.

**Detection**: Use FreeRTOS mutexes instead of binary semaphores for resource protection — mutexes implement priority inheritance by default. Binary semaphores should only be used for signaling (no resource ownership).

```c
/* WRONG: binary semaphore for resource protection */
SemaphoreHandle_t spi_guard = xSemaphoreCreateBinary();
xSemaphoreGive(spi_guard);  /* Start "available" */

/* RIGHT: mutex for resource protection */
SemaphoreHandle_t spi_mutex = xSemaphoreCreateMutex();
/* No initial Give needed — mutex starts "available" */
```

**Instrument**: Add a GPIO toggle when the high-priority task misses a deadline (compares actual execution time against budget). Capture with a logic analyzer.

### 3. Deadlock

**Symptom**: Multiple tasks freeze permanently. Watchdog fires. No work is done.

**Root cause**: Task A holds mutex 1 and waits for mutex 2; task B holds mutex 2 and waits for mutex 1. Neither can proceed.

```c
/* Deadlock recipe — do NOT do this */
void task_a(void *p) {
    for (;;) {
        xSemaphoreTake(mutex1, portMAX_DELAY);
        xSemaphoreTake(mutex2, portMAX_DELAY);  /* Task B holds mutex2 here */
        /* ... */
        xSemaphoreGive(mutex2);
        xSemaphoreGive(mutex1);
    }
}

void task_b(void *p) {
    for (;;) {
        xSemaphoreTake(mutex2, portMAX_DELAY);
        xSemaphoreTake(mutex1, portMAX_DELAY);  /* Task A holds mutex1 here → DEADLOCK */
        /* ... */
        xSemaphoreGive(mutex1);
        xSemaphoreGive(mutex2);
    }
}
```

**Fix**: Total ordering — always acquire mutexes in the same global order. Enforced by convention (comment at each lock site: "Lock order: mutex1, then mutex2") or by a lock-order checker.

**Detection**: Use a watchdog with a sufficiently short timeout. If the system deadlocks, the watchdog fires. The reset reason register tells you it was a watchdog reset, not a sporadic power glitch.

### 4. Task starvation

**Symptom**: Low-priority task makes no progress while higher-priority tasks are busy. In FreeRTOS with `configUSE_TIME_SLICING=1`, tasks of equal priority share the CPU; lower-priority tasks get nothing if a higher-priority task never blocks.

**Fingerprint**: Enable `configGENERATE_RUN_TIME_STATS` and `uxTaskGetRunTimeStats()`:

```c
/* FreeRTOSConfig.h for run-time stats */
#define configGENERATE_RUN_TIME_STATS     1
#define configUSE_TRACE_FACILITY          1
#define configUSE_STATS_FORMATTING_FUNCTIONS 1

/* Must provide a timer that counts faster than the RTOS tick,
   typically a free-running hardware timer at 10× tick rate */
#define portCONFIGURE_TIMER_FOR_RUN_TIME_STATS()  timer_init_for_stats()
#define portGET_RUN_TIME_COUNTER_VALUE()           timer_get_count()
```

```c
void print_task_stats(void) {
    char buf[512];
    vTaskGetRunTimeStats(buf);
    rtt_printf("%s\n", buf);
    /* Output: task name, absolute run time, % CPU */
}
```

A task with 0% CPU when it should be doing useful work is either blocked on a resource or starved. Print at intervals to observe.

**Fix**: Raise the starved task's priority, reduce the busy tasks' CPU usage (add blocking calls), or re-architect to ensure the critical task gets time.

### 5. ISR calling blocking kernel functions

**Symptom**: System crashes immediately when the ISR fires. HardFault with the stack showing a kernel function inside an ISR.

**Root cause**: An ISR calls `xQueueSend` instead of `xQueueSendFromISR`, or takes a mutex from an ISR. FreeRTOS will assert in debug builds; in release builds, it corrupts kernel state.

**Prevention**: Enable asserts in development:

```c
/* FreeRTOSConfig.h */
#define configASSERT(x)  if ((x) == 0) { taskDISABLE_INTERRUPTS(); for(;;){} }
```

This makes any FreeRTOS policy violation a deterministic hang rather than silent corruption — far easier to catch in development.

## GPIO instrumentation

The simplest RTOS instrumentation is a scope or logic analyzer on GPIO pins. Define a set of debug pins and toggle them at key points:

```c
/* debug_pins.h */
#define DBG_SENSOR_TASK_START()  GPIOE->BSRR = (1U << 8)
#define DBG_SENSOR_TASK_END()    GPIOE->BSRR = (1U << 24)   /* bit 8 + 16 = reset */
#define DBG_ISR_ENTRY()          GPIOE->BSRR = (1U << 9)
#define DBG_ISR_EXIT()           GPIOE->BSRR = (1U << 25)

/* In the task: */
void sensor_task(void *p) {
    for (;;) {
        DBG_SENSOR_TASK_START();
        adc_read();
        DBG_SENSOR_TASK_END();
        vTaskDelay(pdMS_TO_TICKS(1));
    }
}
```

A logic analyzer capture shows: which tasks are running, when ISRs fire, how long each task runs, whether tasks are blocked longer than expected. This is the poor-man's Tracealyzer and costs nothing except a few GPIO pins.

## Percepio Tracealyzer and equivalent tools

<VocabTooltip slug="tracealyzer">Tracealyzer</VocabTooltip> is a commercial tool that hooks into
FreeRTOS's trace facility and produces a visual timeline of all task switches, ISR entries/exits,
queue operations, and mutex acquisitions. The open-source alternative is Segger SystemView, which
integrates with SEGGER RTT and produces similar visualizations.

A Tracealyzer capture of a priority-inversion bug is immediately visible: the high-priority task's timeline shows a gap (blocked), the low-priority task's timeline shows it running while it should be releasing the mutex, and the medium-priority task's timeline shows it preempting the low task during that gap.

To enable Tracealyzer in FreeRTOS:

```c
/* FreeRTOSConfig.h */
#define configUSE_TRACE_FACILITY            1
#define INCLUDE_xTaskGetCurrentTaskHandle   1

/* Include the TraceRecorder library from Percepio */
#include "trcRecorder.h"
```

The free tier of Tracealyzer supports up to a few seconds of trace. Sufficient to catch most bugs.

## A debugging checklist before field deployment

Before shipping firmware to production:

1. Run `uxTaskGetStackHighWaterMark` on all tasks after 30 minutes of peak-load testing. All HWMs should be > 30%.
2. Verify `vApplicationStackOverflowHook` is implemented and tested.
3. Verify all resource-protection mutexes are `xSemaphoreCreateMutex()`, not binary semaphores.
4. Verify all ISRs use `FromISR` variants of kernel calls.
5. Enable an independent watchdog (IWDG on STM32) with a timeout that catches a deadlocked system. Verify the watchdog cannot be kicked from an ISR alone (so task starvation still triggers it).
6. Check `xPortGetMinimumEverFreeHeapSize()` — it should never approach zero during the test run.
7. Enable `configASSERT` in development; disable (or redirect to reset) in production if ROM is constrained.
