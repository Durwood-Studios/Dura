## Why this matters

A producer keeps adding sensor samples while the consumer stalls. A queue gives the system somewhere to put work, but finite capacity still requires a decision about blocking, loss or backpressure.

## Start with something familiar

A loading dock has a fixed number of spaces. When they fill, the next truck must wait or go elsewhere; painting another arrival arrow does not create capacity.

## The mental model

> A Zephyr message queue copies fixed-size items into bounded storage. Every send/get result and waiting policy belongs to the application contract, especially in interrupt context.

## The mechanism

Zephyr’s k_msgq supports fixed-size messages between threads and interrupt contexts with appropriate waiting restrictions. K_MSGQ_DEFINE declares storage and a queue. A nonblocking put uses K_NO_WAIT and must inspect the result instead of assuming the item was accepted.

This configuration fragment is for a Zephyr application, not a standalone host program:

```c
#include <zephyr/kernel.h>
#include <stdint.h>
K_MSGQ_DEFINE(samples, sizeof(uint32_t), 4, 4);
int submit_sample(uint32_t sample) {
    return k_msgq_put(&samples, &sample, K_NO_WAIT);
}
```

The function returns status to its caller so the caller can apply the declared overflow policy. The queue stores the value bytes, not a promise that the original stack variable will remain alive. A queue of pointers would have a different lifetime/ownership contract.

For a teaching logger, choose drop-newest with an observable dropped counter rather than blocking an interrupt handler. Counter updates need suitable synchronization in the actual execution context. A control application might need a different policy; silently reusing the logger rule would be unjustified. Consumer scheduling and processing rate determine whether backlog grows.

If four slots are occupied and a fifth sample arrives without waiting, the program must handle failure. A successful later receive frees capacity but does not retroactively store the dropped sample. Test empty receive, full send, normal ordering and recovery after the consumer resumes. Build against a pinned Zephyr version and chosen board; this conceptual fragment is not a claim that a hardware image was built or that a deadline was met.

## Practice

The queue is full and a no-wait put fails. The producer increments its accepted counter anyway. Which observable contract is broken?
