## Why this lesson exists

Most embedded courses teach you to install a vendor IDE (STM32CubeIDE, MCUXpresso, Code Composer Studio), click "New Project," and start writing application code. The IDE hides a toolchain that on Cortex-M consists of GCC, GNU ld, GNU as, and binutils. Behind every "build" button is a Makefile, a linker script, and a startup file you didn't write.

Hiding works until something breaks. When it breaks — and it always breaks — you need to read the linker script. So we start there.

The threshold concept: **a Cortex-M binary is not just compiled source code; it's compiled source code PLUS a linker script that places sections at hardware-meaningful addresses PLUS startup code that runs before main().** Once you've internalized this three-part view, every embedded "weirdness" makes sense.

## The four toolchain components

For ARM Cortex-M development, the canonical toolchain is `arm-none-eabi-*` — a cross-compiler built to target ARM, runs on whatever host you develop on (Linux, macOS, Windows). The four binaries:

```bash
arm-none-eabi-gcc      # C compiler — produces object files (.o)
arm-none-eabi-as       # Assembler — produces object files from .s
arm-none-eabi-ld       # Linker — combines .o + linker script → .elf
arm-none-eabi-objcopy  # ELF → binary (.bin) or Intel hex (.hex) for flashing
```

The flow:

```
source.c → gcc → source.o ─┐
startup.s → as → startup.o ├→ ld + linker.ld → firmware.elf → objcopy → firmware.bin
                          ─┘
```

`gcc` is usually invoked as a driver — it calls `as` and `ld` internally with the right flags. We'll do that. The `objcopy` step at the end produces the raw bytes the flash programmer expects.

Install the toolchain (Ubuntu/macOS via Homebrew):

```bash
# macOS
brew install --cask gcc-arm-embedded

# Ubuntu / Debian
sudo apt-get install gcc-arm-none-eabi

# Verify
arm-none-eabi-gcc --version
# arm-none-eabi-gcc (Arm GNU Toolchain) 14.x or similar
```

## The minimal program

Goal: build a program that runs on a Cortex-M target. We'll target Cortex-M4 (STM32F4 family) but the structure is the same for M0, M3, M7, M33.

The C source is trivial — an infinite loop. The interesting work is the linker script and startup code that surround it.

```c
// main.c
int main(void) {
    volatile int counter = 0;
    while (1) {
        counter++;
    }
    return 0;
}
```

`volatile` keeps the compiler from optimizing the increment away. We'll explain volatile properly in Lesson E2 — for now, take it as "don't let the compiler decide this variable is dead."

## The linker script — placing code at the right address

A Cortex-M target's memory map matters. The CPU expects:

- Reset vector at address `0x00000000`. On boot, the CPU loads the initial stack pointer from `0x00000000` and the reset handler address from `0x00000004`, then jumps to the reset handler.
- For STM32F4, flash is mapped at `0x08000000` AND aliased at `0x00000000` after a memory-remap. We'll write the binary as if it lives at `0x08000000`.
- RAM starts at `0x20000000`. SRAM is where stacks, heaps, BSS, and copied .data live.

The linker script tells `ld` how to lay sections out in this address space. Here's a minimal one:

```ld
/* linker.ld — minimal Cortex-M linker script for STM32F4 */

ENTRY(Reset_Handler)

MEMORY {
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
    SRAM  (rwx) : ORIGIN = 0x20000000, LENGTH = 192K
}

/* Stack grows downward from the top of SRAM */
_estack = ORIGIN(SRAM) + LENGTH(SRAM);

SECTIONS {
    /* Code + read-only data goes in flash */
    .text : {
        KEEP(*(.isr_vector))    /* Vector table FIRST in flash */
        *(.text*)               /* All other code */
        *(.rodata*)             /* Read-only data */
        _etext = .;             /* End of .text, used by startup code */
    } > FLASH

    /* Initialized data: lives in flash (as a copy source), runs from RAM */
    .data : {
        _sdata = .;             /* Start of .data in RAM */
        *(.data*)
        _edata = .;             /* End of .data in RAM */
    } > SRAM AT > FLASH

    /* Zero-initialized data lives in RAM */
    .bss : {
        _sbss = .;
        *(.bss*)
        *(COMMON)
        _ebss = .;
    } > SRAM
}
```

Reading this script:

- `ENTRY(Reset_Handler)` — the linker marks `Reset_Handler` as the program entry point in the ELF header (informational; the CPU uses the vector table).
- `MEMORY` — two memory regions: 1024 KB of flash starting at `0x08000000`, 192 KB of SRAM at `0x20000000`.
- `_estack` — symbol pointing at the top of SRAM. The vector table's first entry is the initial stack pointer; it points here.
- `SECTIONS` — instructs the linker on which output sections to create and where to place them.
- `> FLASH AT > FLASH` for `.text` — section is LOADED in flash and RUNS from flash.
- `> SRAM AT > FLASH` for `.data` — section RUNS from SRAM but the INITIAL VALUES are loaded in flash. Startup code copies them. This is why initialized globals "just work."

The symbols (`_etext`, `_sdata`, `_edata`, `_sbss`, `_ebss`) are how startup code knows where to find things at runtime.

## The startup code — what runs before main

When the CPU boots:

1. Loads stack pointer from `0x00000000` (vector table entry 0).
2. Loads program counter from `0x00000004` (vector table entry 1 — the reset handler).
3. Jumps to the reset handler.

The reset handler has work to do before calling main:

- Copy initialized data from flash to RAM (so `int counter = 5;` actually starts at 5).
- Zero the BSS section (so `static int total;` starts at 0).
- Then call main.

Here's the minimal startup file:

```c
// startup.c
#include <stdint.h>

extern uint32_t _sdata, _edata, _sbss, _ebss, _etext, _estack;
extern int main(void);

void Reset_Handler(void) {
    // Copy .data initializers from flash to RAM
    uint32_t *src = &_etext;
    uint32_t *dst = &_sdata;
    while (dst < &_edata) {
        *dst++ = *src++;
    }

    // Zero out .bss
    dst = &_sbss;
    while (dst < &_ebss) {
        *dst++ = 0;
    }

    // Call main
    main();

    // If main ever returns, hang
    while (1) { }
}

void Default_Handler(void) {
    // Spin on any unexpected interrupt
    while (1) { }
}

// Vector table — declared as the .isr_vector section that the linker
// script places at the start of flash (address 0x08000000 / 0x00000000).
__attribute__((section(".isr_vector")))
const void * const vector_table[] = {
    &_estack,           // Initial stack pointer
    Reset_Handler,      // 0x00000004 — Reset
    Default_Handler,    // 0x00000008 — NMI
    Default_Handler,    // 0x0000000C — HardFault
    // Cortex-M has more handlers but Default_Handler covers them for this lesson.
    // Lesson E3 covers the full vector table.
};
```

Key reads:

- `extern uint32_t _sdata;` — references the symbol the linker defined. Taking the address `&_sdata` gives the actual placement address.
- `__attribute__((section(".isr_vector")))` — tells GCC to place `vector_table` in the `.isr_vector` section. The linker script's `KEEP(*(.isr_vector))` ensures this lands FIRST in flash.
- The data-copy loop is the runtime mechanism that makes `int x = 5;` start as 5.

## Building

The Makefile:

```makefile
CC      = arm-none-eabi-gcc
OBJCOPY = arm-none-eabi-objcopy

CFLAGS  = -mcpu=cortex-m4 -mthumb -mfloat-abi=hard -mfpu=fpv4-sp-d16 \
          -Wall -Wextra -O0 -g -ffreestanding -nostartfiles
LDFLAGS = -T linker.ld -Wl,--gc-sections -nostdlib

OBJS = main.o startup.o

firmware.bin: firmware.elf
	$(OBJCOPY) -O binary $< $@

firmware.elf: $(OBJS) linker.ld
	$(CC) $(CFLAGS) $(LDFLAGS) -o $@ $(OBJS)

%.o: %.c
	$(CC) $(CFLAGS) -c -o $@ $<

clean:
	rm -f *.o firmware.elf firmware.bin
```

Flag breakdown:

- `-mcpu=cortex-m4` — generate code for the M4 instruction set.
- `-mthumb` — use Thumb-2 (the 16/32-bit mixed encoding Cortex-M uses).
- `-mfloat-abi=hard -mfpu=fpv4-sp-d16` — emit hardware floating-point instructions (M4F has an FPU).
- `-ffreestanding` — don't assume a hosted environment (no `printf`, no `_start`, just main).
- `-nostartfiles` / `-nostdlib` — we're providing our own startup; don't link the host's.
- `-T linker.ld` — use our linker script.

Build:

```bash
$ make
arm-none-eabi-gcc ... -c -o main.o main.c
arm-none-eabi-gcc ... -c -o startup.o startup.c
arm-none-eabi-gcc ... -o firmware.elf main.o startup.o
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
$ ls -la firmware.*
-rwxr-xr-x  1 user  staff   140 firmware.bin
-rwxr-xr-x  1 user  staff  5234 firmware.elf
```

The ELF is bigger than the .bin because the ELF carries section headers, debug info, and symbol tables. The .bin is the raw bytes that go in flash.

## Verifying with objdump

The most underused tool in embedded development:

```bash
$ arm-none-eabi-objdump -h firmware.elf
firmware.elf:     file format elf32-littlearm

Sections:
Idx Name          Size      VMA       LMA       File off  Algn
  0 .isr_vector   00000010  08000000  08000000  00010000  2**2
  1 .text         00000040  08000010  08000010  00010010  2**2
  2 .data         00000000  20000000  08000050  00020000  2**2
  3 .bss          00000004  20000000  20000000  00020000  2**2
```

VMA (Virtual Memory Address) = where it runs. LMA (Load Memory Address) = where it's loaded.

- `.isr_vector` at VMA `0x08000000` — vector table is FIRST in flash. Correct.
- `.text` at VMA `0x08000010` — code follows the 16-byte vector table.
- `.data` runs at VMA `0x20000000` (SRAM) but loads from LMA `0x08000050` (flash). The startup copy loop bridges the gap.
- `.bss` lives in SRAM with no flash backing — startup zeroes it.

To see the actual vector table bytes:

```bash
$ arm-none-eabi-objdump -s -j .isr_vector firmware.elf

Contents of section .isr_vector:
 8000000 00300020 11000008 25000008 25000008  .0. ....%...%...
```

In little-endian: `0x20003000` is the initial stack pointer (top of 192K SRAM at 0x20000000 + some offset based on `_estack`), `0x08000011` is the reset handler address (the `+1` bit is the Thumb-mode marker — Cortex-M always runs in Thumb), and the remaining entries are the default handler.

If you ever see `0x00000000` here, your vector table didn't get placed where you expected. Most "won't boot" problems are visible in this output.

## What you can now do

You've built a flashable binary from source without an IDE doing it for you. Specifically:

- You know what a linker script does and can write one.
- You know what startup code does and can read one.
- You can verify section placement with objdump.
- You can identify "where is my vector table" as the first question to ask when a Cortex-M binary won't boot.

## Hands-on exercise

Build the program above and verify with objdump:

1. Set up the toolchain (`arm-none-eabi-gcc --version` should work).
2. Create `main.c`, `startup.c`, `linker.ld`, `Makefile` from the listings above.
3. Run `make`.
4. Run `arm-none-eabi-objdump -h firmware.elf` and confirm sections are at the expected addresses.
5. Run `arm-none-eabi-objdump -d firmware.elf` and find `Reset_Handler` in the disassembly. Trace through it — can you see the copy loop?
6. (Optional) If you have an STM32F4 Discovery board, flash with `st-flash write firmware.bin 0x08000000` and observe... nothing (because we just loop). The successful build IS the test.
