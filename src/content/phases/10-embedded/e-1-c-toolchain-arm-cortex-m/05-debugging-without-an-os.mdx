## Why this matters

You've built firmware that builds and links correctly. Now you need to know what it's doing when it runs. Without some form of output channel, debugging an embedded program means toggling GPIOs and checking oscilloscopes — functional but slow.

There are three tools that professional embedded engineers reach for, each with a different overhead profile and capability set:

1. **Semihosting** — the CPU calls host OS services (including printf) via a BKPT instruction over JTAG. Dead simple. Has measurable overhead on every print.
2. **SEGGER RTT** — a small ring buffer in SRAM; the debug probe reads it autonomously, no CPU interruption. Near-zero overhead.
3. **GDB over OpenOCD** — source-level debugging: breakpoints, watchpoints, register inspection. Catches the bugs that logs can't see.

## Semihosting — the easy path with a cost

Semihosting uses ARM's debug interface to tunnel host OS calls (file I/O, `printf`, `exit`) through the JTAG/SWD connection. GCC's newlib-nano provides a `syscalls.c` that implements `_write` by triggering semihosting. With the debug probe attached, `printf` works and output appears on the host terminal.

```c
// Nothing to add — just use printf after linking -lrdimon and -specs=rdimon.specs
#include <stdio.h>

int main(void) {
    printf("hello from firmware\n");
    while (1) { }
}
```

Link flags:

```makefile
LDFLAGS += --specs=rdimon.specs -lrdimon
```

The catch: each `printf` call executes a `BKPT #0xAB` instruction. The debugger traps it, forwards the data to the host, and resumes the CPU. At 168 MHz, a single `printf("hello\n")` can stall the CPU for **hundreds of microseconds**. For timing-sensitive code — anything with ISRs, timers, or tight protocol windows — semihosting breaks the timing.

**Use semihosting only during early bring-up when timing doesn't matter. Remove it before any timing-sensitive testing.**

## SEGGER RTT — production-grade logging

SEGGER RTT (Real-Time Transfer) solves the overhead problem. Instead of calling the host on every print, RTT writes characters into a ring buffer in SRAM. The J-Link debug probe's DMA reads that buffer continuously, at the probe's own pace, without halting the CPU. From the CPU's perspective, logging is a memcpy into SRAM — typically under 100 ns.

### Setup

1. Download the SEGGER RTT library from segger.com/jlink (free). Drop `SEGGER_RTT.c` and `SEGGER_RTT.h` into your project.
2. Call `SEGGER_RTT_printf` instead of `printf`.

```c
#include "SEGGER_RTT.h"

int main(void) {
    SEGGER_RTT_printf(0, "ADC sample: %u\n", adc_read());
    while (1) {
        uint16_t val = adc_read();
        SEGGER_RTT_printf(0, "val=%u\n", val);
        for (volatile int i = 0; i < 100000; i++) { }
    }
}
```

On the host, run `JLinkRTTViewer` (GUI) or `JLinkRTTClient` (CLI) to read the stream. The output updates continuously without halting the chip.

### RTT without a J-Link

If your probe is an ST-Link or CMSIS-DAP (not J-Link), use **OpenOCD's RTT support** (OpenOCD 0.11+):

```bash
# In your OpenOCD config
rtt setup 0x20000000 0x4000 "SEGGER RTT"
rtt start
rtt server start 9090 0
```

Then `telnet localhost 9090` to see the stream.

## OpenOCD and GDB — source-level debugging

OpenOCD (Open On-Chip Debugger) bridges GDB to the debug probe over USB. Once connected, GDB can:

- Set breakpoints (halt at a source line)
- Set watchpoints (halt when memory at an address is read or written)
- Read/write registers and memory
- Step instruction-by-instruction

### Starting OpenOCD

```bash
# Start OpenOCD with an ST-Link and STM32F4 config
openocd \
  -f interface/stlink.cfg \
  -f target/stm32f4x.cfg
# OpenOCD starts a GDB server on port 3333
```

### Connecting GDB

```bash
arm-none-eabi-gdb firmware.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) break main
(gdb) continue
# GDB halts at main
(gdb) next          # Step one C line
(gdb) print counter # Print a variable
(gdb) info registers # All registers
```

Because you built with `-g` (debug info), GDB knows the mapping between machine instructions and C source lines. When GDB halts at a breakpoint, it shows you the C line, not the assembly.

### Watchpoints — finding silent memory corruption

The most powerful debugging tool in embedded: a **watchpoint** halts the CPU the instant a specific memory address is written.

```bash
(gdb) watch *(uint32_t *)0x20000100   # Halt when this address is written
(gdb) continue
# GDB halts and shows exactly which instruction wrote to that address
# and what the new value is
```

This finds stack-corruption bugs in seconds that would take hours of printf debugging. When a global variable mysteriously changes to a garbage value, a watchpoint on its address reveals the culprit instruction on the first occurrence.

Cortex-M hardware supports 4 watchpoints (via the DWT unit). GDB allocates them automatically for `watch` commands.

## Comparing the three approaches

| Approach    | CPU overhead                | Setup effort            | Catches bugs logging can't | Works at full speed? |
| ----------- | --------------------------- | ----------------------- | -------------------------- | -------------------- |
| Semihosting | High (hundreds of µs/print) | Minimal (link flags)    | No                         | No                   |
| SEGGER RTT  | ~100 ns/call                | Low (2 files)           | No                         | Yes                  |
| GDB/OpenOCD | Halts at events             | Medium (OpenOCD config) | YES                        | N/A (halts)          |

The professional workflow: RTT for continuous trace, GDB/watchpoints for hard bugs.
