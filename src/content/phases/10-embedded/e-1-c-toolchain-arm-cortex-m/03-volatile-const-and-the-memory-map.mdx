## Why this matters

Add or remove `-O2` from your Makefile. Watch a firmware bug appear or disappear. That is not compiler magic or a toolchain bug. It is missing `volatile`.

The optimizer's job is to generate code that behaves identically to the source _from the C program's perspective_. The key phrase is "from the C program's perspective" — which does not include hardware side effects. A read of a GPIO register is, from the compiler's perspective, just a read of a uint32_t variable. If the value never changes from C's viewpoint, the compiler is allowed — and at `-O2`, will — cache it in a register and reuse it forever. The hardware may have changed the register twenty times. The cached value is stale. Your firmware is wrong.

`volatile` is the word that tells the compiler: "this variable has externally observable behavior. Every access must happen. In source order. No caching."

## The volatile contract

The C11 standard (ISO/IEC 9899:2011 §6.7.3) defines volatile's guarantee:

> "An object that has volatile-qualified type may be modified in ways unknown to the implementation or have other unknown side effects. Therefore, any expression referring to such an object shall be evaluated strictly according to the rules of the abstract machine."

In practice:

1. **Every read generates a real load instruction.** No caching in a register, no hoisting out of a loop.
2. **Every write generates a real store instruction.** No dead-store elimination, no coalescing.
3. **Accesses happen in source order.** The compiler cannot reorder a volatile access past another volatile access.

What volatile does NOT do:

- It does not add atomicity. A 32-bit read is one instruction on Cortex-M, but a 64-bit read is two — an ISR between them sees a torn value. See lesson E3 for atomic patterns.
- It does not add memory barriers for hardware DMA. Use `__DMB()` for that.
- It does not protect against out-of-order CPU execution. On Cortex-M (in-order pipeline), this rarely matters, but it matters when working with DMA.

## When to use volatile

### Rule 1: Every peripheral register access

```c
// WITHOUT volatile — optimizer may decide "this never changes, cache it"
uint32_t *const ODR = (uint32_t *)(GPIOD_BASE + 0x14);
while (!(*ODR & (1U << 5))) { }   // Infinite loop possible: compiler reads ODR once

// WITH volatile — every loop iteration issues a real load
volatile uint32_t *const ODR = (volatile uint32_t *)(GPIOD_BASE + 0x14);
while (!(*ODR & (1U << 5))) { }   // Correct: always reads from hardware
```

The canonical pattern from the CMSIS headers: every peripheral register access goes through a `volatile` pointer. The stm32f4xx.h header defines the peripheral structs with `__IO` (which expands to `volatile`) on every field.

### Rule 2: Variables shared between main and an ISR

```c
// The ISR sets this flag when a byte arrives
volatile uint8_t rx_flag = 0;

void USART2_IRQHandler(void) {
    rx_flag = 1;    // write in ISR context
}

void process(void) {
    while (!rx_flag) { }   // read in main context
    // WITHOUT volatile: compiler proves rx_flag never changes in this function
    // and compiles this to an infinite spin on a register copy.
    // WITH volatile: every loop iteration reads rx_flag from SRAM.
}
```

This is the second most common embedded bug class. The ISR sets the flag; main never sees it because the optimizer already decided the flag doesn't change. Adding `volatile` is mandatory for any variable that can be modified by an ISR, DMA engine, or debugger.

### Rule 3: Busy-wait delay loops

```c
// Without volatile, optimizer removes the loop (it has no observable side effects)
for (volatile uint32_t i = 0; i < 1000000; i++) { }

// The volatile on i forces the increment to happen. Still a crude delay;
// use a timer for production code. But for a startup blink, this works.
```

## const — where read-only data lives

`const` tells the compiler: "this variable is never written after initialization." The C standard does not mandate where `const` data lives — that's linker-script territory — but GCC's ARM toolchain puts `const` globals in `.rodata`, which the linker script we wrote in lesson 01 places in flash.

Why this matters: flash is larger than SRAM on most microcontrollers. A 1 KB lookup table declared without `const` lives in SRAM (copied there at boot from flash). With `const`, it lives in flash directly. On a device with 256 KB flash and 64 KB SRAM, moving read-only tables to flash can be the difference between the firmware fitting and not fitting.

```c
// Lives in SRAM — wastes 1 KB of RAM
uint32_t sine_table[256] = { /* 256 values */ };

// Lives in flash — zero RAM cost
const uint32_t sine_table[256] = { /* 256 values */ };
```

Verify with objdump:

```bash
$ arm-none-eabi-objdump -t firmware.elf | grep sine_table
08001234 g     O .rodata   00000400 sine_table   # In flash if const
20000004 g     O .data     00000400 sine_table   # In SRAM if not
```

String literals are automatically `const` in C (though the type is `char *`, assigning them to `const char *` is correct style). `"Hello"` in your firmware lives in flash without any explicit `const`.

## const volatile — not a contradiction

A hardware register that the CPU can only read (not write) — like a hardware identification register — should be `const volatile uint32_t *`:

```c
// DBGMCU_IDCODE — device identity register, read-only at hardware level
const volatile uint32_t *const DBGMCU_IDCODE =
    (const volatile uint32_t *)0xE0042000;

uint32_t id = *DBGMCU_IDCODE;   // Reads from hardware; write would be a compile error
```

- `volatile` → the compiler must issue a real load every time; the hardware can change this value asynchronously.
- `const` → the C program cannot write to this location; the compiler rejects any attempt.
- Both together → the hardware side effect requires volatile; the program's intent to never write requires const.

This isn't common (most peripheral registers are read-write), but it appears in vendor headers for status-only registers.

## The optimization test

A reliable way to demonstrate missing volatile: write a tight loop, compile with `-O0` and `-O2`, examine the disassembly.

```c
uint8_t flag = 0;   // NOT volatile

void poll_loop(void) {
    while (!flag) { }
}
```

At `-O0`:

```asm
poll_loop:
  ldr  r3, =flag
  .L1:
  ldrb r0, [r3]     ; load flag from memory each iteration
  cmp  r0, #0
  beq  .L1          ; loop if zero
  bx   lr
```

At `-O2`:

```asm
poll_loop:
  ldr  r3, =flag
  ldrb r0, [r3]     ; load ONCE — hoisted out of the loop
  cmp  r0, #0
  bne  .Ldone
  .L1:
  b    .L1           ; INFINITE LOOP — optimizer proved flag is never written
  .Ldone:
  bx   lr
```

With `volatile uint8_t flag`:

At `-O2`:

```asm
poll_loop:
  ldr  r3, =flag
  .L1:
  ldrb r0, [r3]     ; must load each iteration — volatile
  cmp  r0, #0
  beq  .L1
  bx   lr
```

The `-O2` output with volatile matches the `-O0` output. The bug is gone and the performance is acceptable (one memory access per loop iteration, as intended).
