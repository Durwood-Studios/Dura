## Why this matters

Interrupt priorities determine which code runs when multiple interrupts fire simultaneously and which ISR can preempt which. An engineer who assigns priorities arbitrarily produces a system that:

- Fails to meet real-time deadlines under load because a low-priority "important" ISR gets preempted by a high-priority "convenience" ISR.
- Silently deadlocks if FreeRTOS ISR variants are called from ISRs above `configMAX_SYSCALL_INTERRUPT_PRIORITY`.
- Delays safety-critical shutoff ISRs with application-level ISRs during error recovery.

Priority assignment is a design decision that must be documented, reasoned about, and correct by construction — not guessed.

## Cortex-M priority mechanics

Cortex-M supports up to 256 priority levels, encoded in 8 bits per interrupt. In practice, chip vendors implement only the top N bits:

- STM32F4: 4 bits → 16 levels (0 = highest, 15 = lowest)
- nRF52: 3 bits → 8 levels (0 = highest, 7 = lowest)

A lower number means higher priority (runs first, can preempt higher-number priorities).

The CMSIS API:

```c
#include "core_cm4.h"   /* Or <stdint.h> with direct register access */

/* Set USART2 interrupt to priority 5 */
NVIC_SetPriority(USART2_IRQn, 5U);
NVIC_EnableIRQ(USART2_IRQn);

/* Read the assigned priority */
uint32_t pri = NVIC_GetPriority(USART2_IRQn);
```

## Priority grouping — preempt vs sub-priority

The 4 implemented priority bits can be split into a **preemption priority** field and a **sub-priority** field via the `PRIGROUP` register in the System Control Block:

```c
/* PRIGROUP values for 4-bit priority implementation:
   PRIGROUP 3 (0xXXXX & 0b0111): [PP.PP | SP.SP] — 4 preempt bits, 0 sub-priority
   PRIGROUP 4 (0xXXXX & 0b0011): [PP.PP | SP.SP] — 3 preempt bits, 1 sub-priority bit
   PRIGROUP 5:                    [PP | PP.SP] — 2 preempt bits, 2 sub-priority bits
   ...and so on */

/* FreeRTOS strongly recommends PRIGROUP 3 (all preempt, no sub-priority) */
NVIC_SetPriorityGrouping(3U);
```

**Preemption priority** determines whether one ISR can interrupt another. **Sub-priority** is only used to break ties when two ISRs of the same preemption priority are both pending simultaneously.

FreeRTOS documentation is explicit: set PRIGROUP to use all bits as preemption priority (`__NVIC_PRIO_BITS` preempt bits, 0 sub-priority bits). This avoids surprising behavior where two ISRs at different sub-priorities can't preempt each other.

## The three-tier priority model

A useful design for most embedded applications:

```
Priority 0–1:   Safety tier    — emergency stop, overcurrent shutoff, watchdog
Priority 2–5:   Application    — sensor ISRs, DMA completion, UART RX, timers
Priority 6–12:  Communication  — BLE, WiFi, USB data handlers
Priority 13–15: Housekeeping   — statistics, logging (never preempts anything critical)
```

```c
/* Example assignment for a motor controller */
NVIC_SetPriority(EXTI0_IRQn,       1U);   /* Emergency stop button — safety tier */
NVIC_SetPriority(TIM1_UP_IRQn,     2U);   /* PWM update — must not miss */
NVIC_SetPriority(ADC_IRQn,         3U);   /* Current sense ADC — must not miss */
NVIC_SetPriority(USART2_IRQn,      7U);   /* Debug UART — application */
NVIC_SetPriority(DMA1_Stream0_IRQn, 5U);  /* Bulk data DMA */
```

The emergency stop at priority 1 can preempt everything except priority 0 (reserved for truly catastrophic faults like NMI). The PWM update at priority 2 can't preempt the emergency stop. The debug UART at priority 7 can't preempt any of the above.

## FreeRTOS constraint: configMAX_SYSCALL_INTERRUPT_PRIORITY

FreeRTOS uses BASEPRI to implement critical sections — it masks interrupts at or below a configurable priority ceiling. ISRs that call FreeRTOS `FromISR` APIs (like `xQueueSendFromISR`) must have a priority NUMERICALLY HIGHER than (equal to or worse than) `configMAX_SYSCALL_INTERRUPT_PRIORITY`.

```c
/* In FreeRTOSConfig.h: */
#define configMAX_SYSCALL_INTERRUPT_PRIORITY  5U   /* On STM32 with 4-bit impl */
```

This means:

- ISRs at priority 5, 6, 7, ..., 15 MAY call `FromISR` variants.
- ISRs at priority 0, 1, 2, 3, 4 MUST NOT call any FreeRTOS API — they can't be masked by the kernel's critical sections.

An ISR at priority 2 that calls `xQueueSendFromISR` will crash or corrupt the kernel because it runs while the kernel's critical section is active.

```c
/* CORRECT: USART2 ISR at priority 7 (above configMAX_SYSCALL_INTERRUPT_PRIORITY = 5) */
/* Can safely call xQueueSendFromISR, xSemaphoreGiveFromISR, etc. */
void USART2_IRQHandler(void) {
    uint8_t byte = USART2_DR;
    xQueueSendFromISR(uart_queue, &byte, &higher_prio_woken);
}

/* WRONG: TIM1 ISR at priority 2 calls FreeRTOS API — undefined behavior */
void TIM1_UP_TIM10_IRQHandler(void) {
    /* DO NOT call xQueueSendFromISR here — priority 2 < configMAX_SYSCALL = 5 */
    /* Instead: set a volatile flag that main code or a lower-priority ISR checks */
    pwm_update_flag = 1;
}
```

The safety-tier and application-real-time ISRs don't use FreeRTOS APIs at all — they set flags or write to shared variables with explicit critical sections.

## Tail-chaining and late-arrival

Cortex-M has two hardware optimizations for back-to-back interrupts:

**Tail-chaining**: when an ISR completes and another interrupt is pending, the CPU skips the full exception exit/re-entry sequence (which would require saving and restoring registers) and directly vectors to the next ISR. The overhead is 6 cycles instead of 12 + 12. At 168 MHz, you save ~71 ns — meaningful for high-frequency ISRs.

**Late-arrival**: if a higher-priority interrupt arrives while the CPU is in the exception-entry sequence (pushing registers), the CPU switches to the higher-priority ISR immediately when register saving completes. The lower-priority ISR's entry is cancelled; it will re-enter after the higher one completes. This provides near-optimal response to high-priority interrupts even when another ISR was about to start.

Both are automatic. You don't configure them; you just benefit from them. The practical implication: back-to-back interrupts at the same or different priorities have lower overhead than separate interruptions.
