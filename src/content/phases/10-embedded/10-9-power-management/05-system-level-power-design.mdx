## Why this matters

An IoT soil-moisture sensor is designed with a 32-bit Cortex-M4 running at 168 MHz. After six months of optimization, the MCU enters Stop mode with 8 µA sleep current. But the battery life is only 3 months. Why? The soil sensor itself consumes 400 µA continuously (it has a capacitance-sensing circuit that requires constant current). The MCU optimization was irrelevant — the sensor dominated the budget and no one measured it.

System-level power design identifies which component dominates before spending time on MCU optimization.

## The energy budget model

For a duty-cycled device:

```
Energy per cycle = Σ (component_current × component_active_time)

Battery life = Battery_capacity_mAh / Average_current_mA
```

For a soil-moisture sensor node:

```
Cycle: 10-minute interval, active 200 ms for sense + transmit

Component         | Current  | Duration | Contribution
──────────────────|──────────|──────────|─────────────
MCU (active)      | 30 mA    | 50 ms    | 1.5 mAs
MCU (sleep)       | 0.050 mA | 550 s    | 27.5 mAs
Soil sensor       | 0.400 mA | 600 s    | 240 mAs   ← DOMINANT
LoRa TX           | 85 mA    | 150 ms   | 12.75 mAs
──────────────────|──────────|──────────|─────────────
Total             |          | 600 s    | 281.75 mAs

Average current = 281.75 mAs / 600 s = 0.470 mA = 470 µA
Battery life (2000 mAh) = 2000 / 0.470 ≈ 4,255 hours ≈ 177 days
```

The soil sensor's 400 µA continuous draw (50× the MCU sleep current) dominates. Reducing MCU sleep from 50 µA to 10 µA saves 0.04 mAs per cycle — 0.01% of the budget. The real optimization: use a soil sensor that can be powered down between readings. Replace 240 mAs with 0 mAs → new total ~41.75 mAs → average 70 µA → battery life 1,190 days (3.3 years).

**The lesson**: measure and model before optimizing. The highest-leverage optimization is rarely the one that looks obvious.

## Communication protocol power comparison

For a device that transmits 50 bytes once per 10 minutes:

| Protocol     | TX Power  | TX Duration | Energy/TX  | Sleep current | Notes                                |
| ------------ | --------- | ----------- | ---------- | ------------- | ------------------------------------ |
| BLE 5.0      | 0-20 dBm  | ~10 ms      | ~0.5 mAs   | 1-5 µA        | Short range; mesh via gateways       |
| LoRaWAN      | 17-20 dBm | 50-2000 ms  | 2-30 mAs   | 1-3 µA        | Long range; sub-GHz; varies by SF    |
| NB-IoT       | 20-23 dBm | 200-5000 ms | 15-100 mAs | 3-15 µA (PSM) | Licensed spectrum; cellular coverage |
| WiFi 802.11n | 20 dBm    | 5-50 ms     | 10-50 mAs  | 150-200 µA    | High bandwidth; difficult sleep      |
| Zigbee       | 5 dBm     | 10-50 ms    | 0.5-5 mAs  | 1-5 µA        | Mesh; 2.4 GHz; coordinator needed    |

For a 10-minute interval, 50-byte payload, outdoors:

- BLE: ~0.5 mAs + ~6 µA sleep = ~6.5 µA average → 3.5 years on 2000 mAh
- LoRaWAN SF9: ~10 mAs + ~2 µA sleep = ~4.0 µA average → ~4.7 years
- NB-IoT: ~50 mAs + ~3 µA (PSM) = ~9.0 µA average → ~2.5 years (but cellular coverage!)

The "right" choice depends on range requirements, infrastructure availability, and regulatory constraints — not just power. But understanding the power implications is how you evaluate trade-offs.

## MCU selection for power-constrained applications

If the application runs most of the time in sleep and wakes briefly to sample, the MCU's sleep current dominates (not its active performance). Cortex-M4 at 168 MHz → 30–50 mA active, ~80 µA Stop. A Cortex-M0+ at 48 MHz → 3-10 mA active, ~2 µA Stop. If active time is 0.1% of the cycle, the M0+ adds 4.5× less active contribution despite running 3.5× slower.

Common mistake: specifying a high-performance MCU because "we might need the compute" and then discovering the sleep power dominates. Start with the minimum adequate MCU; the interrupt latency and compute usually have more margin than expected.

## Sensor power modes

Most sensors (BME280, ICM-42688, MAX30102) have power modes:

- **One-shot / forced mode**: wake the sensor, take a reading, the sensor returns to sleep. Power ~20-50 µA during measurement only.
- **Normal / continuous mode**: sensor converts continuously. Power is always active current.

Always use one-shot mode for low-duty-cycle applications. The soil sensor example's 400 µA was continuous mode where forced mode would give ~400 µA for 5 ms per reading = 2 µAs vs 240 mAs per 10-minute cycle.

```c
/* BME280 forced mode for duty-cycled measurement */
void bme280_trigger_one_shot(bme280_t *dev) {
    /* Mode = 01 (forced) — sensor takes one measurement, returns to sleep */
    uint8_t ctrl = (0x02U << 5) | (0x05U << 2) | 0x01U;  /* Last 2 bits = forced */
    i2c_write_register(dev->bus, dev->addr, REG_CTRL_MEAS, ctrl);
    /* Wait for measurement complete (status.measuring = 0) */
    uint8_t status;
    do {
        delay_ms(5);
        i2c_read_register(dev->bus, dev->addr, REG_STATUS, &status);
    } while (status & 0x08U);   /* measuring bit */
    /* Now read the data registers — sensor is back in sleep mode */
}
```

## The power architecture checklist

Before finalizing a low-power product design:

1. **Energy budget model** — calculate mAs per cycle for every component; identify the top 3 consumers.
2. **Sensor power modes** — use one-shot / forced mode for all sensors; confirm with datasheet.
3. **Communication interval** — can you transmit less often? Each 10× reduction in frequency reduces radio contribution by ~9×.
4. **MCU sleep current** — verify with measurement (not datasheet typical); check for current leaks (pull resistors, output GPIOs floating).
5. **Clock gating** — gate all unused peripheral clocks before Stop entry.
6. **External components** — measure current draw of pull resistors, decoupling caps, and external ICs during sleep.
7. **SysTick in Stop mode** — verify SysTick is disabled before WFI (it wakes the CPU every ms).

Item 7 is the most commonly missed. SysTick is often enabled by HAL initialization and never disabled. One `SysTick->CTRL &= ~SysTick_CTRL_ENABLE_Msk;` before the WFI can eliminate 1000 unnecessary wakes per second.

## What you've learned in module 10-9

- Sleep, Stop, and Standby modes eliminate MCU dynamic power during idle; Stop mode (RAM retained, µA range) fits most sensor-node applications.
- Clock gating unused peripherals removes switching power from all logic clocked by those buses.
- Voltage scaling reduces static and dynamic power when operating at lower frequencies.
- Power profiling — measuring actual current with GPIO correlation — reveals what the firmware actually does, not what the datasheet says it should.
- FreeRTOS tickless idle eliminates wasted tick-rate wake-ups during long idle periods.
- System-level energy budget analysis identifies the dominant consumer before optimization begins — the biggest wins usually come from sensor duty-cycling or communication frequency, not MCU optimization.
