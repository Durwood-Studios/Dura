## Why this matters

A battery-powered sensor is specified to run for 1 year on two AA batteries (approximately 2,400 mAh combined). A rough model: 2,400 mAh / 8,760 hours = 274 µA average. The firmware team optimized the sleep mode and claims < 200 µA average. But no one has measured it — the claim is from datasheet numbers.

First measurement: 1.2 mA average. The firmware had SysTick enabled in Stop mode (SysTick wakes the CPU every 1 ms, preventing deep sleep). After fixing: 180 µA average. The product ships with a 1-year battery life instead of 2 months.

Measurement found the bug. Datasheet math did not.

## Measurement equipment

**Option 1: Bench ammeter or DMM in current mode (simple, low accuracy)**

- Connect in series with the supply line
- Best for: average current in stable operation (no fast transients)
- Limitation: can't capture microsecond transients; safe for < 100 mA

**Option 2: Shunt resistor + oscilloscope (accurate, requires setup)**

- Place a known-value resistor (e.g., 10 Ω) in series with VDD
- Measure voltage across it with the oscilloscope: V = I × R → I = V/R
- For 1 mA through 10 Ω: Vmeasured = 10 mV. Oscilloscope must resolve millivolts.
- Use a 1 Ω shunt for higher currents (1 mV/mA — easier to measure on a scope with low noise floor)

**Option 3: Nordic Power Profiler Kit 2 (PPK2, recommended for serious work)**

- A sub-10-µA resolution ammeter with USB streaming and a timeline visualization
- Captures current vs time with microsecond resolution
- Shows you exactly what the firmware is doing, correlated with GPIO markers
- ~$50 from Mouser/Digikey — inexpensive for the capability

**Option 4: J-Link Energy Profiler (for Segger J-Link users)**

- Built into the J-Link debug probe
- Millisecond resolution; adequate for Stop mode verification but not ISR-level analysis

## Setting up GPIO correlation

The key technique for power profiling: toggle GPIO pins at the entry/exit of every significant firmware phase. The oscilloscope (or PPK2 with GPIO input) shows you which code is running at each current level.

```c
/* Power profile GPIO markers */
#define PROFILE_ACTIVE_START()    GPIOA->BSRR = (1U << 5)   /* PA5 high = CPU active */
#define PROFILE_ACTIVE_END()      GPIOA->BSRR = (1U << 21)  /* PA5 low */

#define PROFILE_ADC_START()       GPIOA->BSRR = (1U << 6)
#define PROFILE_ADC_END()         GPIOA->BSRR = (1U << 22)

#define PROFILE_UART_START()      GPIOA->BSRR = (1U << 7)
#define PROFILE_UART_END()        GPIOA->BSRR = (1U << 23)

#define PROFILE_SLEEP_START()     GPIOA->BSRR = (1U << 8)
#define PROFILE_SLEEP_END()       GPIOA->BSRR = (1U << 24)

/* In enter_stop_mode: */
void enter_stop_mode(void) {
    PROFILE_SLEEP_START();
    /* ... WFI ... */
    PROFILE_SLEEP_END();
}
```

On the oscilloscope / PPK2, you now see: PA5 high → current at active CPU level, PA5 low → current at sleep level. Transitions correlate with what the code is doing.

## A typical sensor-node current waveform

A sensor that samples once per second, transmits via UART, then sleeps:

```
Current (mA)
│
│  ┌────┐    ┌──────────┐    ┌────┐
50│    │ ADC │  UART TX  │sleep│    │
│  │    │    │           │    │    │
10│  ┌──┘    └──────────┘    └──┐  │
│  │                            │  │
0.1│──┘                          └──│
   ─────────────────────────────────── time
   0ms       10ms      50ms      1000ms
```

Reading from this waveform:

- Active phase (ADC + UART): ~12 ms at ~30 mA average → 0.36 mAs per cycle
- Sleep phase: ~988 ms at ~0.1 mA → 0.0988 mAs per cycle
- Average current = (0.36 + 0.0988) / 1.0 = 0.459 mAs = 459 µA average

Measured, not estimated. The 459 µA average is higher than the target 274 µA — investigation needed.

## Identifying the dominant consumers

To reduce 459 µA to < 274 µA, find what's consuming more than expected:

**Step 1: Measure sleep current alone.** Disconnect everything except the MCU, put it in Stop mode, measure. Expected: 10–80 µA. If you measure 300 µA during "sleep," the firmware is not actually entering Stop mode (SysTick enabled? peripheral not gated? crystal oscillator running?).

**Step 2: Measure active current at idle (main loop, no peripherals).** Expected for 168 MHz Cortex-M4: 50–80 mA. If you measure 120 mA, something is drawing excess — check peripheral LEDs, pull resistors, external components.

**Step 3: Measure UART transmission current vs sleep + ADC.** Toggle GPIO at the start/end of each phase. Calculate mAs contribution per phase. The phase with disproportionate contribution is the optimization target.

Common findings in real firmware:

- UART transmission at a slow baud rate (9600) takes 10× longer than at 115200 → 10× more mAs per message
- SysTick enabled in Stop mode wakes the CPU every 1 ms → blocks deep sleep
- External pull resistors on I2C lines (4.7 kΩ on 3.3V = 700 µA continuous)
- LED on for the entire active phase (20 mA LED, always on = 20 mA extra)

## Battery life calculation

```
Average current: 270 µA (after optimization)
Battery capacity: 2,400 mAh (two AA alkaline, best case)
                  2,000 mAh (realistic, accounting for cutoff voltage)

Battery life = 2,000 mAh / 0.27 mA = 7,407 hours = 308 days ≈ 10 months
```

The realistic target was 1 year (8,760 hours). At 270 µA average, you're at 10 months — still short. Options:

- Reduce transmission frequency (once per 10 seconds instead of once per second → sleep duty cycle goes from 98.8% to 99.88% → cuts active contribution by 10×)
- Use a 3.6V lithium primary battery (3,000+ mAh) instead of AA alkaline
- Accept 10 months and refresh the batteries annually

The decision is a product decision informed by the measurement. Without measurement, you can't make this decision.
