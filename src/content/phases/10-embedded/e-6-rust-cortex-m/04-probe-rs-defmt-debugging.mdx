## Why this matters

Embedded debugging with `printf` to UART has two problems: (1) it's slow — each byte takes microseconds to transmit at 115200 baud, which disturbs timing in interrupt-heavy code; (2) it adds string-formatting code at the point of the log call, bloating the binary.

<VocabTooltip slug="defmt">defmt</VocabTooltip> solves both. At the log call site, it encodes the
format string as a single integer index (not the string). The integer is sent via
<VocabTooltip slug="rtt">SEGGER RTT</VocabTooltip> (a ring-buffer-in-RAM mechanism the debugger
reads without halting the CPU). The host tool (probe-rs) looks up the index in the ELF symbol table
and reconstructs the full formatted string. The target spends ~100 ns per log call; the host does
the work.

## Tool setup

```bash
# Install probe-rs
cargo install probe-rs-tools --locked

# Verify your debug probe is found
probe-rs list
# Expected: CMSIS-DAP or J-Link or ST-Link listed with serial number
```

```toml
# .cargo/config.toml — run 'cargo run' to flash and log
[target.thumbv7em-none-eabihf]
runner = "probe-rs run --chip STM32F407VGTx"

[build]
target = "thumbv7em-none-eabihf"
```

With this config, `cargo run` builds the binary, flashes it via the connected debug probe, resets the target, and streams defmt log output to the terminal. Round-trip: about 3-8 seconds.

## Adding defmt to a project

```toml
# Cargo.toml
[dependencies]
defmt          = "0.3"
defmt-rtt      = "0.4"    # RTT transport — send logs via the debug probe
panic-probe    = { version = "0.3", features = ["print-defmt"] }
```

```rust
// main.rs
use defmt_rtt as _;       // Linker symbol to enable RTT
use panic_probe as _;     // Panic handler that prints a backtrace via defmt

defmt::info!("System started, clocks: {} MHz", 168);
defmt::warn!("Sensor read timeout, retry {}", retry_count);
defmt::error!("Fatal: {} failed: {:?}", "I2C init", err);
```

Log levels: `trace!`, `debug!`, `info!`, `warn!`, `error!`. Level filtering happens at compile time (via Cargo features) — `DEFMT_LOG=warn cargo build` emits only warn and above, shrinking the binary.

## What defmt actually transmits

When the target executes `defmt::info!("Sensor read timeout, retry {}", retry_count)`:

1. At compile time: the format string is assigned an index (e.g., 42). The index is stored in the ELF symbol table, not in flash.
2. At runtime: the target sends `[42, retry_count_bytes]` via RTT — a few bytes, not the full string.
3. The host: probe-rs reads the RTT buffer, looks up index 42 in the ELF to get the format string, substitutes `retry_count`, and prints the full line.

Compare to UART printf at 115200 baud:

- `"Sensor read timeout, retry 5"` is 29 bytes → ~2.5 ms to transmit
- defmt RTT: 5 bytes → ~1 µs to transmit (RTT writes to RAM, read out-of-band)

For a firmware loop running at 10 kHz with logging, the UART approach would consume 25% of the loop budget. defmt consumes under 0.01%.

## Interpreting a panic backtrace

When a panic occurs (array out of bounds, unwrap on None, explicit `panic!()`), panic-probe prints a backtrace via defmt:

```
WARN panicked at 'attempt to subtract with overflow', src/sensor.rs:42:12
WARN  0: 0x0800_1234 - sensor::compensate_temperature
WARN     at src/sensor.rs:42:12
WARN  1: 0x0800_15A0 - sensor_task
WARN     at src/main.rs:78:5
WARN  2: embassy_executor::executor::run
WARN     at ...
```

The backtrace shows the exact source file, line, and function for each frame. On a Cortex-M without OS, this is only possible because the ELF file (built with `debug` profile) retains symbol information and probe-rs can unwind the stack using DWARF debug info.

Production builds use the `release` profile (`cargo build --release`), which enables optimizations but strips debug info. Ship the ELF with debug info separately (for post-mortem analysis) even when the stripped binary goes to flash. The stripping is done by `arm-none-eabi-strip` or `cargo objcopy`.

## GDB server mode for interactive debugging

For step-through debugging:

```bash
# Terminal 1: start probe-rs as a GDB server
probe-rs gdb --chip STM32F407VGTx

# Terminal 2: connect GDB
arm-none-eabi-gdb target/thumbv7em-none-eabihf/debug/firmware
(gdb) target remote :1337
(gdb) break main
(gdb) continue
(gdb) next
(gdb) print sensor_data
```

Or use VS Code with the `probe-rs` extension — it provides a full graphical debug UI (breakpoints, variable inspection, call stack) with one-click attach.

The probe-rs GDB server is typically faster than OpenOCD for Cortex-M targets and requires no OpenOCD config file — the chip name (`STM32F407VGTx`) is all the configuration needed.

## Measuring timing with defmt timestamps

```toml
# Cargo.toml — add Embassy time feature for defmt timestamps
[dependencies]
embassy-time = { version = "0.3", features = ["defmt-timestamp-uptime"] }
```

With this feature, every defmt log line is prefixed with the uptime in milliseconds:

```
0.000012 INFO  System started, clocks: 168 MHz
0.001045 INFO  Sensor initialized
1.001203 WARN  Sensor read timeout, retry 1
1.002156 INFO  Sensor read OK
```

This is essential for timing analysis: how long did init take? When exactly did the timeout occur? How long between reads? The microsecond-resolution timestamps answer all of these without a logic analyzer.
