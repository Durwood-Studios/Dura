## Why this matters

A project uses a qualified compiler and assumes its application is therefore approved. Toolchain evidence applies to a declared version, target and use, while the application still needs its own development and verification argument.

## Start with something familiar

A calibrated scale supports measurements within its stated range and conditions. It does not approve every recipe measured on it. Qualified tooling likewise provides scoped evidence rather than transferring a product approval.

## The mental model

> Check the toolchain’s exact qualification scope against the actual build. Tool identity, target support and library scope are separate facts from application correctness.

## The mechanism

Ferrocene is a Rust toolchain with publicly documented qualification material. Its documentation separates user operation, qualification planning and target support. A target that can be compiled is not necessarily covered by the same qualification scope as another target. The manual may also distinguish compiler/tool qualification from library use by end-user code.

Read the release-specific documents, not only a product homepage or a moving main-branch page. Build a small scope matrix:

| Project fact | Evidence to locate |
| --- | --- |
| Compiler/tool release | Exact installed version and corresponding qualification release |
| Host and target | Support/qualification status for the actual combination |
| Libraries and features | Applicable scope and restrictions, not assumptions from Rust syntax |
| Build options | Configuration allowed by the relevant usage guidance |
| Known issues | Release-specific issue/disposition record |
| Application | Its own requirements, unsafe boundaries, verification and change review |

For this exercise, a supplied fictional project P uses tool releaseR, targetT and an external libraryL. The supplied qualification summary listsT but explicitly excludesL’s end-use behavior. That is enough to reject the statement “L is qualified because the compiler is”. It does not mean L is automatically unusable; the project needs a justified treatment of the uncovered behavior.

A Rust type check can prevent classes of misuse but cannot establish timing, algorithm correctness or all behavior across unsafe/foreign interfaces. Record the build manifest, review the scope gaps and assign a responsible owner for the remaining evidence. The free exercise uses public documents and a synthetic manifest; it does not require purchasing a toolchain or claim that Ferrocene was installed or a qualified build was executed.

## Practice

The compiler release matches the documentation, but the target has changed since the review. Is the previous scope decision automatically valid?

<details><summary>Compare the reasoning</summary><p>No. Recheck the new host/target and library scope against the same release-specific documents and record the impact on the project evidence.</p></details>

- Read tool qualification as a scoped claim.
- Identify target and library coverage gaps.
- Retain application evidence beyond successful compilation.
