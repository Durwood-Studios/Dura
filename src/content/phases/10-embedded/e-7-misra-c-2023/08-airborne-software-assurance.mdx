## Why this matters

A team tested one software image and then rebuilt it with different compiler settings before delivery. The filenames match, but the bytes may not. In an assurance argument, knowing which artifact was verified is part of the work, not an administrative detail.

## Start with something familiar

A laboratory report identifies the sample it tested. Putting the report beside a different sample does not transfer the result. Software verification also applies to identified artifacts, configurations and conditions.

## The mental model

> Development assurance connects planned objectives to retained evidence for a specific software baseline. A passing test report cannot silently migrate to a different build or stand in for an approval decision.

## The mechanism

FAA AC20-115D recognizes DO-178C/ED-12C and related supplements as an acceptable means of showing compliance for software aspects of airborne systems and equipment. The advisory circular is not itself a mandatory regulation or the only possible means; choosing its means requires following applicable provisions. It also recognizes guidance addressing tools, model-based development, object orientation and formal methods. This lesson is an entry to evidence reasoning, not a reproduction of the licensed documents or a certification course.

**Development assurance** is the disciplined production and examination of evidence supporting confidence in development. A **baseline** identifies the agreed versions of requirements, source, build inputs and associated records. **Verification evidence** records what was checked, against which expectation, on which artifact and with what result. **Tool qualification** is a context-dependent assurance topic; using a popular compiler or analyzer does not automatically qualify it for every project use.

Consider a fictional bench display requirement A-7: for a permitted input code, the formatter produces the specified label; an unsupported code produces “UNKNOWN”. The exercise does not control flight equipment. Build B1 passes normal and unsupported-code tests. A later B2 uses a different generated lookup table and optimization setting, but someone attaches the B1 report to it.

The record must expose the change:

| Record | Information needed |
| --- | --- |
| Requirement | A-7 version and permitted-code/label table |
| Source/configuration | Formatter and generated-table revisions |
| Build | Compiler version, options and relevant dependencies |
| Artifact | Identity or digest of the actual tested image |
| Verification | Inputs, expected outputs, environment and actual results |
| Change review | B1→B2 differences and justified reverification scope |

An artifact digest helps identify bytes; it does not prove those bytes satisfy a requirement. Source review, requirements-based tests and any other applicable objectives remain distinct. Likewise, code coverage describes which code a test executed, not whether every needed requirement exists or every result is correct. Do not infer an assurance level or probabilistic safety claim from a coverage percentage.

The responsible project team must determine the effect of B2 on existing evidence under its approved plans. The developer can preserve the exact inputs, explain the change and produce new results, but cannot grant certification credit by renaming the output file.

## Practice

B2's source is unchanged, but a generated table came from a different input file. Which statement is stronger: “same source means same evidence” or “identify the changed build input and assess its verification impact”?

## What you learned

- FAA recognition of an assurance means is not a blanket product approval.
- Baselines include generated inputs and tool configuration as well as source.
- Changes require an explicit assessment of what evidence still applies.
- Identity, coverage, correctness and approval answer different questions.
