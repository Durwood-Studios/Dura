## Why this matters

A medical device project is audited for IEC 62304 Class C compliance. The code is MISRA-C:2023 conformant per Cppcheck output (zero warnings). The auditor asks: "Where is the deviation log? Which rules are adopted? Who reviewed the deviations? How do you know the analyzer is configured correctly?" The team has no answers. The audit fails on process, not code quality.

MISRA compliance is a process claim, not just a code property. The evidence package that supports the claim is what auditors look for.

## Step 1: Rule adoption decision

Not every project uses every MISRA rule. The project team's first MISRA decision is which rules they **adopt**. The adoption decision is documented, reviewed, and baselined before analysis begins.

A typical adoption document structure:

```
PROJECT: Sensor Node Firmware v3.0
MISRA EDITION: MISRA-C:2023
DATE: 2026-06-30
AUTHOR: J. Smith, Lead Engineer
APPROVED: K. Jones, Safety Manager

Rule Adoption Decisions:
━━━━━━━━━━━━━━━━━━━━━━
Mandatory rules (11): ALL ADOPTED — no deviations permitted.

Required rules (120): ALL ADOPTED with deviation permitted per
  project deviation policy.

Advisory rules (45):
  - Rules 18.4, 18.5 (pointer arithmetic): ADOPTED — deviation permitted
    for DMA address computation (pre-approved deviation template available).
  - Rule 21.3 (no malloc): ADOPTED — static allocation is project policy.
  - Rule 1.1 (C language standard): ADOPTED — C17 used, compiler flags
    validated to produce conforming compilation unit.

Guideline Re-categorization (GRC): None — all rules used at their
  standard MISRA categorization level.
```

The GRC mechanism allows projects to promote Advisory rules to Required (stricter) or demote Required to Advisory (less strict, with justification). Demotion requires a strong safety argument.

## Step 2: Static analyzer configuration verification

The analyzer itself must be configured correctly. An analyzer that misses findings is as bad as no analyzer. The configuration evidence:

```
Analyzer: Cppcheck 2.14.0 with MISRA-C:2023 addon
Target: ARM Cortex-M4 (32-bit int, 32-bit pointer, IEEE 754 float)
Configuration flags:
  --addon=misra
  --enable=all
  -DSTM32F407xx
  -Isrc/ -Ivendor/CMSIS/

Verification:
  Test suite run against known-violation test cases (Cppcheck MISRA test suite).
  All 11 Mandatory rule test cases detected: PASS.
  Selected Required rule test cases (30 of 120): PASS.
  Known false-positive test cases: 3 suppressed with inline comments.

Date run: 2026-06-30
```

The test suite run is key: it proves the analyzer is finding what it should. A correctly configured analyzer is part of the evidence.

## Step 3: Baseline analysis and triage

Run the analyzer on the full codebase and produce the baseline report. Categorize all findings:

```
BASELINE ANALYSIS REPORT — Sensor Node Firmware v3.0
Total findings: 287

Category breakdown:
  Mandatory rule violations:  0   (must be zero — fixed before baseline)
  Required rule violations:  12   (each must have a deviation or be fixed)
  Advisory rule violations:  45   (documented in deviation log)
  Tool suppressed (FP):      230  (documented with suppression rationale)
```

Every non-zero finding in the Mandatory category blocks release — fix it, don't deviate. Required violations each need a deviation document. Advisory violations need a deviation or a batch-deviation covering the pattern.

## Step 4: Deviation log entries

A complete deviation log entry:

```
DEVIATION LOG — Sensor Node Firmware v3.0
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Entry: DEV-2026-004
Rule: MISRA-C:2023 Rule 18.4 (Advisory)
Scope: src/dma_uart.c, lines 89 and 103
Source locations:
  dma_uart.c:89   DMA1_S6M0AR = (uint32_t)(tx_buf + tx_offset);
  dma_uart.c:103  DMA1_S6PAR  = (uint32_t)(rx_buf + rx_offset);

Justification:
  DMA source and destination address registers require absolute memory addresses.
  Computing these from a base buffer pointer and an offset is the only portable
  pattern for selecting sub-regions of a statically allocated DMA buffer.
  Array indexing (`tx_buf[tx_offset]`) produces a reference, not an address.

Safety analysis:
  tx_buf and rx_buf are statically allocated arrays of known size.
  tx_offset and rx_offset are range-checked prior to use (assertions in debug
  builds; bounds-checks in production at buffer-size constants).
  The pointer arithmetic cannot produce an out-of-bounds address given the
  preconditions.

Risk: LOW. The arithmetic is bounded and reviewed.
Impact if deviation not applied: Forced workaround (memcpy to a temporary
  with no offset) would increase memory use and reduce DMA efficiency.

Reviewed by: K. Jones, Safety Manager
Date: 2026-06-30
```

Each deviation must have: rule, scope, justification, safety analysis, risk rating, reviewer, date. The reviewer must be someone other than the author.

## Step 5: Inline suppression annotations

Each deviation location in source code gets an inline annotation that:

1. Tells the analyzer to suppress the finding at that location
2. References the deviation log entry

```c
/* MISRA-2023 Rule 18.4 deviation: see DEV-2026-004 */
/* cppcheck-suppress misra-c2012-18.4 */
DMA1_S6M0AR = (uint32_t)(tx_buf + tx_offset);
```

The analyzer does not flag this line. The deviation document provides the audit trail. The comment makes the deviation visible in code review without looking up the log.

## Step 6: CI gate and ongoing compliance

```yaml
# .github/workflows/safety-gate.yml
- name: MISRA conformance check
  run: |
    cppcheck --addon=misra --error-exitcode=1 \
      --enable=all --suppress=missingIncludeSystem \
      -DSTM32F407xx -Isrc/ -Ivendor/ \
      src/
  # Any new MISRA violation fails the CI job.
  # All deviations must have inline suppression annotations.
  # Suppressions without inline comments fail the annotation check below.

- name: Check deviation annotations present
  run: |
    python3 tools/check_suppressions.py src/
    # Verifies every cppcheck-suppress comment has a corresponding DEV- reference
```

The CI gate ensures new code cannot introduce MISRA violations without explicit deviation documentation. Engineers cannot silently add violations — the check fails and they must either fix the code or add a reviewed deviation entry.

## What a safety audit reviews

An ISO 26262 or IEC 62304 auditor reviewing the MISRA evidence will look for:

1. **Rule adoption document** — which rules are used, who decided, when
2. **Analyzer configuration evidence** — tool version, flags, test-suite verification
3. **Baseline analysis report** — total findings by category, all Mandatory = 0
4. **Deviation log** — one entry per Required/Advisory violation, with reviewer signatures
5. **Source code annotations** — inline suppression comments referencing deviation IDs
6. **CI integration** — proof the check runs on every commit, failures block merge

A project with zero Cppcheck warnings but missing items 1, 2, 4, or 5 fails the audit. The code is not the evidence — the process artifacts are.
