## Where MISRA fits

MISRA-C is a guidelines document published by the Motor Industry Software Reliability Association. MISRA-C:2023 is the current edition, released 2023, and is the modernized post-2012 version. It defines a C-language subset designed to reduce the risk of bugs in safety-critical software.

MISRA-C is NOT a separate language. It's a set of rules that restrict what C constructs you can use. The compiler doesn't enforce MISRA — that's a static-analyzer's job (Cppcheck, PC-lint, Polyspace, Helix QAC, Coverity, etc.).

When does MISRA apply?

- **Automotive** — ISO 26262 (functional safety) doesn't mandate MISRA but it's the dominant industry choice.
- **Aviation** — DO-178C doesn't mandate it but DO-330 (tool qualification) and the underlying safety goals push teams toward subset-based languages.
- **Medical** — IEC 62304 Class B and C software typically use MISRA.
- **Rail** — EN 50128 references coding standards including MISRA.
- **Any project that wants fewer bugs** — even non-safety-critical projects use MISRA voluntarily.

If your project isn't in one of these domains, MISRA is overhead. If it is, MISRA conformance is part of the deliverable.

## The three categories of rules

MISRA-C:2023 categorizes rules by compliance strength:

> **Mandatory** — must be followed. No exceptions. Deviation is not permitted.
> **Required** — must be followed unless a documented deviation justifies otherwise.
> **Advisory** — recommended; deviations need lighter documentation but should be tracked.

There are about 175 rules total in the 2023 edition. Roughly:

- 11 Mandatory rules
- ~120 Required rules
- ~45 Advisory rules

The Mandatory rules cover violations the C standard itself flags as undefined behavior — things like dereferencing a null pointer or modifying a string literal. These are not deviation candidates because the language itself can't guarantee anything if you violate them.

## Five rules that catch real bugs

Rather than enumerate all 175, let's look at five that catch bugs you've probably written or read in production code.

### Rule 10.1 — Operands shall not be of inappropriate essential type (Required)

C's implicit integer promotion is the source of an enormous number of bugs. Example:

```c
uint16_t a = 0xFFFF;
uint16_t b = 0x0001;
uint32_t c = a + b;
// What's in c?
// On most platforms: 0x00010000 (correct)
// Because: a and b promote to int (32-bit), add, then convert to uint32_t.
```

That's the easy case. Now:

```c
int16_t a = -1;
uint16_t b = 1;
if (a < b) {
    // Reached? It depends.
    // On most platforms: a promotes to int, b promotes to int, -1 < 1 is true.
    // But: the C standard's "usual arithmetic conversions" can convert int16_t
    // to unsigned if the platform's int is 16-bit (rare but legal),
    // making -1 become a large positive value and the comparison false.
}
```

Rule 10.1 forbids mixing signed and unsigned types in ways that can produce these surprises. Forces explicit casts that make the conversion visible to the reader.

### Rule 17.3 — Functions shall not be called without a prior declaration (Mandatory)

```c
// Forgot to #include the header
int main(void) {
    foo(42);   // Compiler assumes int foo() returning int
}

// In foo.c:
double foo(int x) { return x * 1.5; }
```

The caller and callee disagree on the return type. Stack misalignment, garbage return values, crashes. Mandatory because no deviation argument is valid.

### Rule 18.4 — The +, -, += and -= operators shall not be applied to an expression of pointer type (Advisory)

```c
int buf[10];
int *p = buf;
p += 3;        // Pointer arithmetic — error-prone
*p = 42;       // Wrote to buf[3]
```

Advisory rather than Required because pointer arithmetic is sometimes necessary. The rule pushes you toward array indexing (`buf[i]`) which is harder to get subtly wrong.

### Rule 13.1 — Initializer lists shall not contain persistent side effects (Required)

```c
int counter = 0;
int data[] = { counter++, counter++, counter++ };
// What's in data? The C standard says: unspecified order.
// Could be {0, 1, 2} or {2, 1, 0} or anything in between.
```

Rule 13.1 forbids this. Force readers to see side effects in deterministic order.

### Rule 21.3 — The memory allocation and deallocation functions of <stdlib.h> shall not be used (Required)

Dynamic allocation in safety-critical embedded code is widely avoided. Reasons:

- Heap fragmentation in long-running systems eventually causes allocation failures.
- Allocation latency is unbounded.
- Use-after-free and double-free are classes of bugs static analysis cannot fully catch.

Most MISRA-conformant projects use static allocation exclusively — every buffer is sized at compile time, no `malloc` anywhere.

## The deviation policy

For Required and Advisory rules, the project may DEVIATE if justified. A deviation document looks like:

```
RULE: MISRA-C:2023 Rule 18.4 (Advisory)
SCOPE: src/dma_driver.c, line 142
JUSTIFICATION: DMA setup requires pointer arithmetic to compute the
  destination address of each chunk. Array indexing produces equivalent
  code but obscures the relationship between the source-data layout and
  the DMA configuration. The use is contained, documented, and reviewed.
RISK ASSESSMENT: Low. The pointer arithmetic operates on a statically-
  allocated buffer with bounds known at compile time.
APPROVED BY: J. Smith, Safety Engineer, 2026-04-15
```

Deviation documents are auditable. Static analyzers can take deviation comments inline (`/* MISRA-2023-Rule-18.4: deviation, see ADR-014 */`) so the analyzer doesn't flag the violation on each build.

The discipline: deviations are FOR specific code locations, are JUSTIFIED with a clear technical reason, are REVIEWED by someone other than the author, and are REVISITED periodically. A project with dozens of "deviation" suppressions and no justification is not conforming — it's papering over violations.

## What Rust eliminates structurally

Many MISRA rules exist because C lets you do dangerous things. Rust's type system prevents many of these BY CONSTRUCTION:

| MISRA-C Rule                        | What it prevents             | Rust analog                                          |
| ----------------------------------- | ---------------------------- | ---------------------------------------------------- |
| 17.3 (function prior decl)          | Calling undeclared functions | Rust requires declarations and checks types          |
| 13.1 (init-list side effects)       | Unspecified evaluation order | Rust evaluates left-to-right deterministically       |
| 18.4 (pointer arithmetic)           | Out-of-bounds pointer ops    | Rust slices carry length; index is bounds-checked    |
| 21.3 (no malloc)                    | Unbounded allocation latency | `#![no_std]` programs have no allocator unless added |
| 10.1 (inappropriate essential type) | Implicit promotion surprises | Rust requires explicit casts; no implicit narrowing  |
| 9.1 (uninitialized read)            | Reading uninit memory        | Rust requires initialization before use              |

This doesn't mean Rust replaces MISRA-C — it means many of the disciplines MISRA enforces in C come "for free" in Rust. The discipline still exists; the language just enforces it for you.

## What MISRA does NOT prevent

MISRA-C is a coding-style discipline. It doesn't catch:

- Wrong algorithms (the code is conformant but solves the wrong problem).
- Race conditions (E3 / E4).
- Architecture-level bugs (the wrong task takes the wrong lock).
- Missing requirements (the safety case identified a hazard the code doesn't address).

Engineers who treat MISRA conformance as a complete safety practice are confused about what MISRA does. It's a SUBSET of safety engineering — necessary in regulated domains, not sufficient.
