## Why this matters

A STM32F4 running at 168 MHz uses a 16-bit timer register. A calculation involving this register plus a signed offset produces the wrong result in one product variant — the one where `int` is 32 bits (which is all modern ARM Cortex-M toolchains). The bug was silently introduced when the developer mixed `uint16_t` and `int16_t` in an arithmetic expression. MISRA Rule 10.1 flags exactly this pattern. The Cppcheck analyzer finds it in 30 seconds; the field investigation cost 3 days.

## Essential type model

MISRA-C:2023 introduces the **essential type** of an expression — the effective type that determines how an operand behaves in arithmetic. The essential types are:

| Category  | Examples                               |
| --------- | -------------------------------------- |
| Boolean   | `bool`, `_Bool`                        |
| Unsigned  | `uint8_t`, `uint16_t`, `uint32_t`      |
| Signed    | `int8_t`, `int16_t`, `int32_t`         |
| Character | `char`, `unsigned char`, `signed char` |
| Enum      | `enum Color { RED=0, GREEN=1 }`        |
| Floating  | `float`, `double`                      |

MISRA restricts operations that mix essential types in ways that change semantics through promotion.

## Integer promotion in practice

C promotes operands to `int` (or `unsigned int`) before most binary operations. On a 32-bit Cortex-M, `int` is 32 bits. This matters:

```c
uint8_t a = 200;
uint8_t b = 100;
uint8_t c = a + b;   /* a + b promotes to int: 300. Truncated to uint8_t: 44. */
                     /* Is 44 the intended result? Maybe. Is it documented? Rarely. */
```

The MISRA issue is not that truncation happens — it's that it happens silently. MISRA Rule 10.3 (Value shall not be assigned to variable of narrower essential type) flags this truncation.

The compliant fix:

```c
uint8_t c = (uint8_t)(a + b);    /* Explicit cast documents the truncation intent */
/* Or: */
uint16_t wide = (uint16_t)a + (uint16_t)b;
uint8_t c = (wide <= 0xFFU) ? (uint8_t)wide : 0xFFU;   /* Saturating */
```

## Shift operator rules (10.6, 10.7)

MISRA Rule 10.6: The right operand of a shift must not be negative or >= the width of the left operand.

```c
uint32_t mask = 1U << 32;    /* MISRA violation: shift by 32 on a 32-bit type = UB */
uint32_t mask2 = 1U << -1;   /* MISRA violation: negative shift = UB */

/* Compliant: */
uint32_t bit_n = 1U << (n & 0x1FU);   /* Ensure n < 32 before shifting */
```

MISRA Rule 10.1: The left operand of a shift must be unsigned.

```c
int32_t val = 0x80000000;
val << 1;    /* MISRA violation: left shift of a signed type with sign-bit set = UB */

/* Compliant: */
uint32_t uval = 0x80000000U;
uval << 1;   /* Defined: 0x00000000 with carry out */
```

## Bitwise complement (~)

Rule 10.1: The operand of `~` must be of unsigned type.

```c
uint8_t flags = 0x07;
uint8_t inverted = ~flags;   /* MISRA violation: ~ promotes to int (32-bit), result is int */
/* inverted = 0xFFFFFFF8 (int), then narrowed to uint8_t = 0xF8. Happens to be correct,
   but only because the truncation is harmless here. MISRA can't know that. */

/* Compliant: */
uint8_t inverted = (uint8_t)(~(uint32_t)flags);   /* Explicit widening, complement, explicit narrow */
/* Or use a mask: */
uint8_t inverted = flags ^ 0xFFU;                  /* XOR with 0xFF: MISRA-compliant inversion */
```

## Bitfield manipulation: the MISRA pattern

Register manipulation is the most common embedded pattern that violates MISRA integer rules. The safe pattern:

```c
/* MISRA-compliant register bit manipulation */

/* Set bit: cast to uint32_t at the outermost level */
GPIOD->BSRR = (uint32_t)(1UL << 12);

/* Clear bit via BRR */
GPIOD->BRR = (uint32_t)(1UL << 12);

/* Read-modify-write: cast required */
GPIOD->MODER = (GPIOD->MODER & ~(uint32_t)(0x3UL << (12 * 2)))
               | (uint32_t)(0x1UL << (12 * 2));

/* DO NOT: */
GPIOD->MODER |= (1 << 24);   /* (1 << 24): signed int, may be implementation-defined */
```

The pattern: use `U` suffix for unsigned literals, `UL` for 32-bit wide unsigned, explicit casts at truncation points.

## A MISRA-compliant CRC32 implementation

CRC computation involves bitwise shifts, XOR, and loop counts — a microcosm of the integer rules:

```c
/* MISRA-C:2023 compliant CRC-32 (IEEE 802.3 polynomial) */
#include <stdint.h>
#include <stddef.h>

#define CRC32_POLY  0xEDB88320UL   /* Reflected polynomial */

uint32_t crc32_compute(const uint8_t *data, size_t length) {
    uint32_t crc = 0xFFFFFFFFUL;

    /* MISRA 14.2: for-loop init/condition/increment must be simple */
    for (size_t i = 0U; i < length; i++) {
        /* Widen byte to uint32_t before XOR to avoid implicit promotion surprises */
        crc ^= (uint32_t)data[i];

        /* MISRA 10.6: right operand of shift must be < 32; use literal 1 */
        for (uint_fast8_t bit = 0U; bit < 8U; bit++) {
            if ((crc & 1UL) != 0UL) {
                crc = (crc >> 1U) ^ CRC32_POLY;
            } else {
                crc >>= 1U;
            }
        }
    }

    return crc ^ 0xFFFFFFFFUL;
}
```

Without MISRA:

```c
/* Non-compliant version (subtle UB risks) */
uint32_t crc32_bad(const uint8_t *data, int length) {    /* signed length */
    uint32_t crc = 0xFFFFFFFF;                           /* no U suffix */
    for (int i = 0; i < length; i++) {
        crc ^= data[i];                                   /* implicit promotion to int */
        for (int bit = 0; bit < 8; bit++) {
            if (crc & 1) {
                crc = (crc >> 1) ^ 0xEDB88320;           /* RHS: int, not uint32_t */
            } else {
                crc >>= 1;
            }
        }
    }
    return crc ^ 0xFFFFFFFF;
}
```

The non-compliant version works on 32-bit ARM with current GCC, but the signed `length` accepts negative values, the missing `U` suffixes rely on implicit type behavior, and the XOR with `data[i]` (uint8_t promoted to int) has an implicit narrowing that the compiler happens to handle correctly. MISRA's value is catching the cases where "happens to handle correctly" becomes "silently wrong" on a different toolchain or target.
