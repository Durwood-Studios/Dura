## Why this matters

A signal decoder passes its unit tests, but the vehicle integration uses different units and a slower update period. The function can be locally correct while the integrated behavior violates its requirement. Automotive software work needs evidence at both boundaries.

## Start with something familiar

A relay team can have four fast runners and still lose the baton. Testing a runner and testing the handoff answer different questions. Software units and their integration also need distinct observations tied to the actual requirements.

## The mental model

> An allocated software requirement connects system intent to a software contract. Unit tests examine local behavior; integration tests examine whether the pieces preserve that contract together.

## The mechanism

The public scope of ISO26262-6:2018 covers software-level development for automotive functional-safety applications, including software safety requirements, architecture, unit implementation/verification, integration and embedded-software testing. Functional safety addresses hazards from malfunctioning safety-related electrical/electronic systems; the cited part does not establish nominal performance requirements for every driving function.

An **allocated requirement** is a requirement assigned to a particular part of the design. **ASIL** means Automotive Safety Integrity Level: its assignment belongs to the applicable system safety analysis and lifecycle, not to a developer choosing a label because a function looks important. This lesson does not assign ASIL, prescribe its detailed techniques, or establish compliance with the full standard.

For a fictional bench-only indicator, the supplied contract SW-24 is: accept a message only when its sequence is newer within the specified sequence protocol and its age is at most100ms; otherwise show “unavailable”. A system owner has provided this contract for the exercise. It is not a recommended vehicle control rule. The source supplies age in milliseconds, while the interface adapter originally supplied seconds.

**Unit verification** can check the decision with already normalized inputs: age99,100,101ms; an older sequence; a new valid sequence. **Integration verification** must also check that the adapter uses the correct units, sequence identity and clock basis. “The unit passed” does not prove that 0.2 seconds was converted to200ms before comparison.

A review record should include the original allocated requirement, interface units, sequence assumptions, implementation revision, tests and actual results. If sequence wraparound is possible, its protocol must be specified; an ordinary greater-than comparison is not automatically correct. Do not silently select an arithmetic rule without the interface contract.

Now suppose a scheduler changes from10ms to80ms. A function called at age101ms still returns the expected result, but the time until the application next evaluates it changes. Revisit the end-to-end timing assumption with the system owner. Architecture decisions, resource behavior and test environments must remain part of the evidence rather than being replaced by a green unit-test badge.

## What you learned

- ISO26262 Part6 addresses a software-development lifecycle within automotive functional safety.
- Unit and integration checks support different parts of an allocated contract.
- Units, clocks, sequence protocols and scheduling are explicit assumptions.
- Test results alone do not assign ASIL or establish whole-standard conformance.

Reference: [ISO26262-6:2018 official scope](https://www.iso.org/standard/68388.html).
