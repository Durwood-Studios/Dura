## Why this matters

A medical-device team finds a display defect and a developer proposes a small patch. The patch may be small while its consequences are not: a shared library, a risk control or the release baseline could also change. Review must follow the affected behavior rather than the number of edited lines.

## Start with something familiar

Changing a recipe in a commercial kitchen requires knowing which meals use it and whether allergen information changes. Inspecting only the new ingredient misses the dependency network. A software lifecycle process similarly retains evidence of what was planned, built, verified, maintained and changed.

## The mental model

> A medical-software patch belongs to an identified product baseline and a controlled lifecycle. A local fix must carry its impact analysis and verification evidence; it does not independently validate the whole device.

## The mechanism

The public IEC scope describes IEC 62304:2006 with Amendment1:2015 as medical-device software lifecycle requirements, covering development and maintenance processes for software that is itself a medical device or part of one. It does not cover validation and final release of the medical device as a whole. Use the licensed, applicable edition and the project's quality/regulatory process for actual compliance work; this introduction does not reproduce its detailed objectives or assign a software safety class.

A **problem report** records observed behavior, conditions, affected versions and consequences needing assessment. **Change impact** asks which requirements, risk-control assumptions, interfaces, components and tests may be affected by the proposed correction.

Consider a fictional offline training display, not a clinical product. Report P-12 says a value of 1.05 is displayed as 1.5 after a string-formatting change. No learner should use these numbers for treatment. The existing requirement R-8 is to preserve exactly two decimal places from an already validated numeric input. A change record should name the affected formatter, the input assumptions, consumers and tests rather than only “fixed decimal bug”.

A bounded record can contain:

| Field | Example evidence |
| --- | --- |
| Baseline | Application revision and formatter dependency version |
| Problem | Input1.05, observed1.5, expected1.05 under R-8 |
| Proposed correction | Preserve the required decimal places in the shared formatter |
| Impact | Identify every display/export using the formatter and any related risk-control assumptions |
| Verification | Normal, zero, rounding-boundary and previously failing cases with retained outputs |
| Release decision | Named responsible review and unresolved anomalies; whole-device decisions remain separate |

A test of 1.05 alone would not examine changed rounding behavior. Conversely, the developer must not invent clinical acceptance thresholds to finish a ticket. Uncertain consequences go to the appropriate domain and quality reviewers.

## Practice

The corrected display passes, but exported CSV still uses the previous formatter. Is the problem report ready to close merely because the screenshot looks right?

<details><summary>Compare the impact review</summary><p>No. The shared behavior and its consumers were part of the stated scope. Record the export discrepancy, evaluate its consequence, and verify the intended requirement in each affected consumer before the responsible reviewer decides closure.</p></details>

## What you learned

- IEC62304 concerns medical-software lifecycle processes, with a stated whole-device scope boundary.
- A maintenance record traces the problem through affected requirements and consumers.
- Shared dependencies and unresolved anomalies require explicit impact decisions.
- An instructional checklist cannot establish standard conformance or clinical approval.

Reference: [IEC62304:2006+AMD1:2015 official scope](https://webstore.iec.ch/en/publication/22794).
