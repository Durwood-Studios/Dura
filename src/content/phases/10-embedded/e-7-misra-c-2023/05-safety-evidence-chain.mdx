## Why this matters

A timeout test passes, but nobody can explain why that timeout exists or what happens when it expires. A correct implementation of an arbitrary number is not enough when incorrect behavior could contribute to harm. You need to connect the code to a justified requirement and retain the limits of that justification.

## Start with something familiar

A bridge inspection follows a chain from the load it must carry to the design and the measurements that support using it. A photograph of one intact bolt cannot establish the whole bridge's adequacy. Software evidence also needs a chain, with each piece supporting a bounded claim.

## The mental model

> A test supports a specific requirement under specific conditions. The broader safety argument must explain why that requirement, those conditions and the system response are appropriate.

## The mechanism

A **hazard** is a potential source of harm; a software fault may contribute to a hazardous situation without being the whole situation. A **safety requirement** states behavior assigned to prevent or reduce a particular risk within a larger design. **Traceability** records the relationships among the concern, requirement, implementation, verification and revisions. An **assumption** is a condition the argument depends on but has not itself established.

Use this fictional diagnostic logger, which does not control equipment. A system engineer supplies requirement R-17: “If no valid sample arrives for more than 200 milliseconds, mark the displayed sample unavailable; a received malformed sample does not refresh its age.” The number is a scenario input, not a recommended physical safety timeout.

A trace row could read:

| Item | Evidence |
| --- | --- |
| Concern H-2 | A viewer mistakes stale data for a current observation |
| Assigned requirement R-17 | Mark unavailable after the specified age; reject malformed refresh |
| Design D-4 | Store timestamp only when shape and value validation succeed |
| Implementation | Named function and reviewed source revision |
| Tests T-1 through T-4 | Fresh sample, exact boundary, past boundary, malformed refresh |
| Assumptions | Clock units, time origin, monotonic behavior and polling delay are specified |

The distinction “more than” matters: at exactly 200 ms, this requirement has not yet expired; at 201 ms it has. If evaluation runs only every 50 ms, the observed display update can lag the mathematical threshold. That delay belongs in the system analysis; a unit test at 201 ms cannot establish a physical response deadline.

Configuration management identifies which requirement, source, test and result versions belong together. Review is not completed by filling every spreadsheet cell: a reviewer must examine whether the evidence actually supports the assigned behavior. Independence, rigor and required work products vary with the domain and project assurance plan. A passing local test is not authorization to operate a safety-related machine.

## Practice

A malformed row arrives at 190 ms and the implementation updates last_seen before checking the row. At 250 ms, the original valid sample is still displayed as current. Which trace link is broken?

## What you learned

- Traceability connects a bounded concern, assigned requirement, implementation and evidence.
- Boundary words and invalid-input behavior belong in executable checks.
- Timing assumptions include scheduling and observation delays.
- Software verification and system authorization are different responsibilities.
