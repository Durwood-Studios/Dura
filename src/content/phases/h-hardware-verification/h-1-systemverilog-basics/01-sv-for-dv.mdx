## Where this lesson sits

SystemVerilog is two languages sharing one syntax:

- A **synthesizable subset** used for RTL design (parts of `module`, `assign`, `always_ff`, `always_comb`).
- A **verification subset** that's a full object-oriented language with classes, dynamic arrays, queues, mailboxes, and randomization (the topic of H3).

Most DV engineers work in the verification subset 95% of the time. This lesson grounds that subset.

The IEEE 1800-2023 spec unified Verilog 2005 and the original SystemVerilog 2005 into one standard. Subsequent revisions (2009, 2012, 2017, 2023) added incremental features. The 2023 version is the current reference.

## Data types that aren't in Verilog

Verilog has `wire` and `reg`. SystemVerilog adds a cleaner set:

```systemverilog
logic       a;          // 4-state (0, 1, X, Z) — replaces wire AND reg
bit         b;          // 2-state (0, 1) — faster sim
int         i;          // 32-bit 2-state signed
longint     l;          // 64-bit 2-state signed
shortint    s;          // 16-bit
byte        x;          // 8-bit signed
real        r;          // floating point
string      msg;        // dynamic string

logic [31:0] word;      // 32-bit logic vector
logic [7:0][3:0] grid;  // 2D packed array
int data [];            // dynamic array (verification only)
int q[$];               // queue (verification only)
```

The rule of thumb:

- **`logic`** replaces `wire` and `reg` in synthesizable code. Use it everywhere unless you have a specific reason.
- **`bit`** is faster in simulation (2-state) but won't catch X/Z propagation bugs. Use for testbench-internal types where 4-state isn't needed.
- **`int`** is convenient for loop counters and testbench variables. Don't use in synthesizable code.

## Interfaces — bundling signals across module boundaries

In Verilog, connecting a 20-signal bus between modules requires 20 named port connections. Every signal repeated three times (module A's port list, module B's port list, the connecting wires). Bug-prone.

SystemVerilog interfaces bundle related signals:

```systemverilog
interface axi4_lite_if(input logic clk, input logic rst_n);
    logic        awvalid;
    logic        awready;
    logic [31:0] awaddr;
    logic        wvalid;
    logic        wready;
    logic [31:0] wdata;
    logic [3:0]  wstrb;
    // ... rest of AXI-Lite

    // Modports define directional views
    modport master (
        output awvalid, awaddr, wvalid, wdata, wstrb,
        input  awready, wready
    );
    modport slave (
        input  awvalid, awaddr, wvalid, wdata, wstrb,
        output awready, wready
    );
endinterface
```

Modules use the interface as a single port:

```systemverilog
module my_master(axi4_lite_if.master axi, input logic start);
    // Inside, access signals via the interface: axi.awvalid <= 1'b1;
endmodule
```

Two benefits:

1. **Add a signal** — define it in the interface, every module using it gets it for free.
2. **Direction enforcement** — modports make compile-time errors when a master tries to drive a slave-only signal.

For testbenches, an interface is the standard handoff between the DUT and the UVM driver/monitor (Lesson H2).

## Classes — the object system

SystemVerilog has classes. They're the foundation of UVM and constrained-random stimulus:

```systemverilog
class packet;
    rand bit [7:0] data;
    rand bit [3:0] dest;
    int           tag;

    function new(int t = 0);
        tag = t;
    endfunction

    function void print();
        $display("packet: tag=%0d data=0x%h dest=%0d", tag, data, dest);
    endfunction

    function void copy(packet src);
        this.data = src.data;
        this.dest = src.dest;
        this.tag  = src.tag;
    endfunction
endclass
```

Usage:

```systemverilog
packet pkt = new(42);          // Allocates with tag=42
pkt.randomize();                // Random values for rand fields
pkt.print();                     // Prints
```

Class instances live on the heap and are garbage-collected (when the last handle goes out of scope, the object is freed). This is the most important difference from synthesizable Verilog — classes are unsynthesizable; they exist only in simulation.

The `rand` modifier marks fields the randomizer can fill in. Lesson H3 dives into constraints.

## fork/join — concurrent processes

A testbench needs to drive stimulus AND monitor responses AND check timing simultaneously. SystemVerilog's `fork/join` does this:

```systemverilog
initial begin
    fork
        // Process 1: drive stimulus
        drive_stimulus();

        // Process 2: monitor outputs
        monitor_outputs();

        // Process 3: timeout watchdog
        begin
            #10000;
            $error("Timeout");
            $finish;
        end
    join_any   // Wait for ANY to finish (join_any), ALL (join), or NONE (join_none)
end
```

`join_any` is common in testbenches: wait for either the test to complete or the watchdog to fire, whichever comes first. `join_none` returns immediately and the processes continue in the background.

## Mailboxes and queues for inter-process communication

Two processes need to communicate. The synthesizable answer would be a FIFO IP block; the verification answer is a mailbox:

```systemverilog
mailbox #(packet) mbox = new();    // Holds packet objects, unbounded

// Producer process
packet pkt = new();
pkt.randomize();
mbox.put(pkt);                      // Send

// Consumer process
packet rx_pkt;
mbox.get(rx_pkt);                   // Receive (blocks until available)
```

UVM's TLM (Transaction-Level Modeling) ports are built on this mailbox concept. We'll see them in H2.

Queues `int q[$]` are similar but synchronous — both push and pop are non-blocking:

```systemverilog
int q[$];
q.push_back(42);
q.push_back(7);
int x = q.pop_front();   // 42
```

## Synthesizable vs verification — the contract

SystemVerilog's IEEE 1800-2023 standard defines the entire language. But only a SUBSET is synthesizable — the rest is for simulation only.

| Feature                       | Synthesizable           | Verification |
| ----------------------------- | ----------------------- | ------------ |
| `logic`, `bit`, `int` vectors | yes                     | yes          |
| `interface`, `modport`        | yes (with restrictions) | yes          |
| `class`, `new`                | NO                      | yes          |
| `mailbox`, `queue`            | NO                      | yes          |
| `fork/join`                   | restricted              | yes          |
| `randomize()`                 | NO                      | yes          |
| `assert`, `cover`             | yes (with care)         | yes          |
| `$display`, `$finish`         | NO                      | yes          |

The synthesizable subset is what gets turned into actual silicon by the synthesis tool. Anything verification-only is for the testbench — it executes during simulation but never reaches the chip.

DV engineers learn both, with the verification subset being their daily home.
