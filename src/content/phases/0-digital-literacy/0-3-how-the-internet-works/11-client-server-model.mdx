## Why this matters

Almost every networked system you'll ever build follows the same pattern: one side asks, the other side answers. Knowing this pattern by name lets you reason about web apps, mobile apps, APIs, databases, and microservices using a single mental model.

## Start with something familiar

Imagine asking a librarian for a book. You make the request; the librarian answers. The librarian can then ask another library for help.

## The mental model

> Client and server describe roles in a conversation, not permanent labels on a computer.

## The two roles

A **client** asks for things. A **server** waits for requests and answers them. That's the entire model.

- Your browser is a client.
- The DURA web server is a server.
- Your phone's weather app is a client.
- The weather service is a server.

A given machine can play either role depending on context. When your laptop fetches a webpage, it's a client. When you run a tiny dev server on the same laptop, it's also a server.

## The cycle

A request/response interaction follows this sequence:

1. Client decides it needs something.
2. Client sends a request.
3. Server processes it.
4. Server sends a response.
5. Client does something with the response.

That's a single round trip. A modern web page loads dozens or hundreds of these in parallel — one for the HTML, one for each image, one for each script, one for each font.

```text
Client                Server
  |                     |
  |  ─── request ───>   |
  |                     |  (does work)
  |  <── response ───   |
  |                     |
```

## Why this model wins

Servers can handle many clients at once. They can be upgraded centrally without anyone reinstalling the client. They can hold the data that all clients share. Clients stay simple — they need to know how to ask.

The downside: if the server goes down, clients cannot get new responses from it. Locally saved data can remain usable offline. The whole pattern depends on at least one party being reachable.

## Guided practice

A weather server asks another service for a forecast. Which role does the weather server have in that second conversation?

Predict on paper or in your head before opening the answer; no installation or internet connection is needed.

<details>
  <summary>Reveal the practice answer</summary>

It is the client of the other service because it initiates that request.
