## Why this matters

Git lives on your computer. If your hard drive dies, your local commits go with it. **GitHub** (and similar services like GitLab and Bitbucket) is where developers put their Git repositories on the internet, so they're safe, shareable, and collaborate-able. The combination of Git + GitHub is the bedrock of modern software development.

## Start with something familiar

Imagine keeping a notebook locally and sending copies of saved pages to a shared shelf. Others can send their saved pages back.

## The mental model

> Local commits and a remote repository are separate copies; pushing and pulling transfer and integrate history.

## Sign up for GitHub

Go to `github.com` and create an account. Choose a username and profile information you are comfortable sharing. An account is optional for completing this lesson.

You can study push and pull with the examples below without buying anything or uploading a repository.

## Create a repository

If you want to upload existing local commits, create a new empty repository named `my-first-repo`. Do not initialize it with a README, license, or other files: that would create an independent history before your first push. Choose its visibility deliberately.

Congratulations: you have a remote repository.

## Connect your local repo to it

If you already have local commits from the previous lesson and the remote is empty, this illustrative sequence connects them. Replace `yourname` with your account name. Authentication and a network connection are needed for the actual upload; the lesson practice below works offline.

```text
$ git remote add origin https://github.com/yourname/my-first-repo.git
$ git branch -M main
$ git push -u origin main
```

`git remote add` tells your local repo where the remote one lives. `git push` uploads your commits.

## The push/pull cycle

This becomes your daily rhythm:

1. **Pull** — `git pull` fetches remote changes and integrates them into your current branch.
2. **Work** — edit, add, commit locally.
3. **Push** — `git push` uploads your local commits.

If two people change the same file at the same time, Git tries to merge their changes automatically. When it can't, you get a **merge conflict** — Git asks you to inspect the overlapping edits and decide how to combine them. A conflict resolution may preserve parts of both versions.

## The README

Every repository should have a README — a Markdown file that explains what the project is, how to install it, and how to use it. It's the first thing visitors see on GitHub.

A good README doesn't have to be long. It has to answer "what is this and why should I care?"

## Guided practice
