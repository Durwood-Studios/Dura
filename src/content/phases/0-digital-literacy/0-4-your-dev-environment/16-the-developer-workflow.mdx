## Why this matters

You now know enough to do real work. This lesson ties everything together into the loop a working developer runs every day. Once this loop is muscle memory, you stop thinking about the tools and start thinking about the problem.

## Start with something familiar

Imagine drafting a notice, proofreading it, saving the approved copy, sharing it with staff, then posting it publicly.

## The mental model

> Each workflow step changes a different state: edited, checked, recorded, shared, and available to users.

## The five steps

1. **Write** — open your editor, change some code.
2. **Test** — run the code (manually or with automated tests) to confirm it works.
3. **Commit** — stage and snapshot your changes locally with a clear message.
4. **Push** — upload to GitHub so a remote copy is available to collaborators.
5. **Deploy** — get the change in front of real users (in your case for now, that means visiting it on the internet).

```text
write → test → commit → push → deploy
  ↑                                ↓
  └────────────────────────────────┘
```

You'll go around this loop dozens of times per day. The whole loop, for a small change, might take five minutes.

## Why this order matters

Each step is a checkpoint. If you skip one, you create a category of problems:

- **Skip testing** → bugs land in production.
- **Skip committing** → you lack a recorded snapshot to compare or return to.
- **Skip pushing** → only you have the code.
- **Skip deploying** → users never see the change.

The discipline isn't bureaucracy. It's a series of small safety nets, and skipping any of them costs more later than it saves now.

## Continuous Integration

**Continuous integration** (CI) runs automated checks as changes are integrated. **Continuous deployment** is a separate practice that can release passing changes automatically. A project can use CI while keeping deployment manual.

You don't need to set this up yet. But know it exists, because it's how real teams move fast without breaking everything.

## Guided practice

A test fails before you push. What should you investigate before sharing the change?

Predict on paper or in your head before opening the answer; no installation or internet connection is needed.

<details>
  <summary>Reveal the practice answer</summary>

Investigate the failure and rerun relevant checks after a repair. A local commit can preserve work, but a failed check is not evidence the change is ready for deployment.

</details>
