## Why this matters

An XML message validates against a schema but is rejected by the receiving payment community. Structural validity is one layer; the selected message version, usage profile and business rules also matter.

## Start with something familiar

A grammatically correct form can still be the wrong form for an office or contain inconsistent totals. Financial messages need both a valid structure and the correct shared business interpretation.

## The mental model

> Pin the message definition, version, external code sets and community usage rules. Schema validity does not establish authorization, settlement, correct amounts or acceptance by a particular network.

## The mechanism

ISO20022 provides a model and repository for financial business messages. The catalogue contains message definitions and associated documentation; communities adopt specific versions and usage guidelines. A message family name alone is not enough to select the exact schema and constraints.

The synthetic review packet says profileP requires message versionV, currencyC and a control count equal to the number of transaction records. A received packet uses versionV but declares three transactions while containing two. Even if its XML structure is valid, the business control fails. This is an illustrative profile rule, not a claim about a particular production message definition.

A validation pipeline checks safe parsing, exact schema/version, required community constraints, code-set values, control totals, identifiers and business authorization. Preserve the original message identity and validation result; reject or quarantine failures under the agreed protocol. Do not silently “repair” a payment amount or beneficiary field to make validation pass.

Use the official message definition and community profile to generate or validate actual XML. Avoid inventing a few XML tags and calling the fragment ISO20022-compliant. The lesson uses a plain-language packet so the difference between structural and business validation remains clear without pretending to execute a schema validator.

A successful message exchange still does not prove the underlying transfer settled. Tie acceptance and later status evidence to the transaction/ledger contract. Version upgrades need compatibility tests with the receiving community, not merely changing the namespace string.
