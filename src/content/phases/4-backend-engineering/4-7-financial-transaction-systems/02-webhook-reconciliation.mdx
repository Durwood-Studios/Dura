## Why this matters

A payment callback arrives twice or out of order. Treating every delivery as a fresh financial instruction can duplicate an entitlement or regress a completed transaction to an older state.

## Start with something familiar

A courier may deliver two copies of the same signed notice. Verify the notice, recognize its identity and compare it with the current record before changing the books.

## The mental model

> A webhook is an authenticated event delivery, not automatically a unique business action or the newest state. Verify the provider’s exact signature protocol, persist receipt identity and reconcile authoritative transaction state.

## The mechanism

Providers define their own signature format, timestamp tolerance, endpoint secrets and retry behavior. Stripe, for example, requires signature verification against the unmodified raw request body. Do not invent a generic HMAC format and call it compatible with a provider. Use the documented verifier for the configured endpoint/version and reject unverifiable requests before business processing.

After verification, validate event shape, account/environment ownership and supported event type. Atomically record the event ID and intended local effect, or durably enqueue it before acknowledging receipt. Returning success before durable acceptance can lose work; performing a side effect before recording its identity can duplicate work after a crash.

The synthetic sequence is eventE2 saying transactionT is succeeded, duplicateE2, then delayedE1 saying T is processing. The local record should not downgrade solely because E1 arrived later. Retrieve or reconcile the authoritative current transaction state under the provider’s documented semantics. Distinct event IDs can sometimes concern the same business object, so event deduplication is necessary but not a complete business idempotency policy.

This complete offline reducer assumes signature and account validation already succeeded. Its supplied authoritative state models reconciliation; it does not verify a real provider signature or call a payment API.

```python
seen_events = set()
local = {"status": "processing", "entitlement_count": 0}

def accept_verified_event(event_id, authoritative_status):
    if event_id in seen_events:
        return
    if authoritative_status not in ("processing", "succeeded"):
        raise ValueError("unsupported fixture state")
    if authoritative_status == "succeeded" and local["status"] != "succeeded":
        local["status"] = "succeeded"
        local["entitlement_count"] += 1
    seen_events.add(event_id)

accept_verified_event("E2", "succeeded")
accept_verified_event("E2", "succeeded")
accept_verified_event("E1", "succeeded")
assert local == {"status": "succeeded", "entitlement_count": 1}
assert seen_events == {"E1", "E2"}
print("webhook reducer passed")
```

The delayed E1 is reconciled against current succeeded state, not its old processing payload. This single-threaded in-memory reducer does not implement durable crash recovery, transaction reversal or arbitrary provider states.

Maintain a reconciliation job comparing local ledger/entitlement state with authoritative provider records. A webhook can be delayed, missed or temporarily rejected. Record actionable failure status without logging secrets, raw sensitive payloads or payment authentication data. Keep test and live environments separate.

This lesson uses a state sequence and a design record. It does not receive a real provider webhook or move funds. Provider-specific signature and retry behavior must be verified in its test environment before deployment.
