## Why this matters

A user disconnects an account, but a scheduled importer continues fetching transactions because it still holds a token. An open-banking integration must preserve the actual consent and authorization boundaries throughout its lifecycle.

## Start with something familiar

A visitor badge is not unlimited permission to enter every room forever. Its use depends on the visit’s scope, current permission and the building’s checks.

## The mental model

> Treat consent scope, authorization tokens, provider access state and retained-data policy as related but distinct records. Revocation must affect future collection under the applicable profile; it does not mean every retained record is automatically erased.

## The mechanism

This lesson uses the UK Open Banking customer-experience guidance, specifically its versioned v3.1.8 consent-dashboard example as a historical teaching reference, together with the current revocation guidance. It is not a claim that all jurisdictions share one API or consent lifetime. Before implementation, select the actual supported API/security profile and its current version.

For a synthetic account-information connection, record connection identity, provider, selected accounts, permitted data categories, purpose, expiry where applicable and current access status. Show the user which connection is active and how to disconnect it. A token is a credential; never place it in the dashboard, analytics or ordinary logs.

The local state fixture below only models whether a scheduled import is eligible. It is not an OAuth implementation and does not call a bank.

```python
def can_import(connection, now):
    return connection["status"] == "active" and now < connection["expires_at"] and "transactions" in connection["scopes"]

connection = {"status": "active", "expires_at": 200, "scopes": ["transactions"]}
assert can_import(connection, 100)
connection["status"] = "revoked"
assert not can_import(connection, 100)
connection["status"] = "active"
assert not can_import(connection, 200)
connection["scopes"] = ["balances"]
assert not can_import(connection, 100)
print("consent eligibility checks passed")
```

On disconnect, stop future scheduled collection and follow the provider’s documented revocation/access process. Distinguish requested, confirmed and failed revocation where the protocol has separate acknowledgements. A request failure must not leave the UI claiming confirmed provider revocation. Locally stopping jobs can still reduce collection while retry or user guidance resolves the remote state.

Handle race conditions: a queued job must recheck eligibility before a request, and an in-flight response needs the declared policy when revocation occurs during the request. Reconcile disconnections originating at the provider as well as in your own UI. Request the minimum supported scope rather than using broad access for convenience.

Retention or deletion of already collected records follows applicable obligations and the disclosed purpose/policy. Disconnecting future access and deleting history are different actions; explain them clearly. Production validation needs the actual provider sandbox, token handling, consent expiry/revocation, concurrency and security-profile conformance tests. This local predicate proves none of those remote guarantees.

## Practice

Can an unexpired token alone authorize a new import after consent is revoked? Does disconnect necessarily mean every previously retained record has been erased?
