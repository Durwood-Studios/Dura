## Why this matters

A batch loader commits ten records, loses its acknowledgement and retries. If the retry adds another ten copies, an operational interruption has changed the business data. An ETL pipeline needs explicit identity and recovery semantics.

## Start with something familiar

A warehouse clerk can receive the same delivery notice twice without receiving two trucks. The notice’s identity lets the clerk recognize a repeat; counting every message as a new delivery inflates inventory.

## The mental model

> Extraction, transformation and loading have separate contracts. Stable source identity plus transactional loading can make retries idempotent; transport retries alone do not create exactly-once business results.

## The mechanism

Extract reads source records. Transform validates and converts them to the destination schema. Load commits the accepted data. Specify which source version or event ID each row represents and whether updates replace prior values, append immutable events or require reconciliation.

The following complete standard-library SQLite fixture demonstrates transaction and uniqueness behavior locally; it is not a PostgreSQL performance or concurrency benchmark. The destination stores one reading per source_id. Repeating the same batch updates the same identities instead of adding duplicates. Validate the whole batch before beginning the write transaction.

```python
import sqlite3

def load_batch(db, rows):
    for source_id, rpm in rows:
        if not source_id or type(rpm) is not int or rpm < 0:
            raise ValueError("invalid reading")
    with db:
        db.executemany(
            "INSERT INTO readings(source_id,rpm) VALUES (?,?) "
            "ON CONFLICT(source_id) DO UPDATE SET rpm=excluded.rpm",
            rows,
        )

db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE readings(source_id TEXT PRIMARY KEY, rpm INTEGER NOT NULL)")
load_batch(db, [("r1", 10), ("r2", 20)])
load_batch(db, [("r1", 10), ("r2", 20)])
assert db.execute("SELECT COUNT(*) FROM readings").fetchone()[0] == 2
try:
    load_batch(db, [("r3", 30), ("r4", -1)])
except ValueError:
    pass
else:
    raise AssertionError("invalid batch accepted")
assert db.execute("SELECT COUNT(*) FROM readings").fetchone()[0] == 2
print("ETL checks passed")
```

An acknowledgement lost after commit leaves the caller uncertain, even though the database is correct. Retry the same stable identities, then reconcile destination state. Record batch identity, accepted/rejected counts and status. A watermark marking extraction progress must not advance before the corresponding load is durable; otherwise a crash can skip records permanently.

The upsert policy is a deliberate choice: a later value for r1 replaces its earlier value. It is wrong for a financial event log that must preserve immutable history, and out-of-order older data could overwrite newer data without a version rule. A periodic scheduler merely decides when to start work. Dependencies, bounded retries, overlap prevention and failure observability require an orchestration contract beyond a cron expression.
