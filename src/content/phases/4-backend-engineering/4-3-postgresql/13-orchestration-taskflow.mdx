## Why this matters

A cron job starts a report before its input load finishes. Moving the timer later may reduce failures while hiding the dependency. An orchestrator makes task order, retry policy and status explicit.

## Start with something familiar

A kitchen sends dessert only after the table has finished its main course, not merely when the clock reaches a guessed time. Workflow dependencies similarly express readiness rather than relying on accidental timing.

## The mental model

> A directed acyclic graph describes task dependencies; the orchestrator manages runs and task states. Task retries repeat work, so side effects must remain correct when executed more than once.

## The mechanism

In Apache Airflow3’s TaskFlow API, decorated Python task calls construct dependencies and pass small return values through the orchestrator’s communication mechanism. They are not ordinary immediate function calls during DAG definition. The following complete DAG uses a small in-memory fixture and no external service. It targets the documented Airflow3 SDK; it requires a separately configured Airflow environment.

```python
from datetime import datetime, timezone
from airflow.sdk import dag, task

@dag(schedule=None, start_date=datetime(2026, 1, 1, tzinfo=timezone.utc), catchup=False)
def reading_summary():
    @task()
    def extract():
        return [{"id": "r1", "rpm": 10}, {"id": "r2", "rpm": 20}]

    @task(retries=0)
    def validate(rows):
        if any(type(row["rpm"]) is not int or row["rpm"] < 0 for row in rows):
            raise ValueError("invalid input")
        return rows

    @task()
    def summarize(rows):
        return {"count": len(rows), "total_rpm": sum(row["rpm"] for row in rows)}

    @task()
    def check(summary):
        assert summary == {"count": 2, "total_rpm": 30}
        print("summary checked")

    check(summarize(validate(extract())))

reading_summary()
```

The graph is extract→validate→summarize→check. Under the default success-based dependency behavior, invalid input prevents the downstream summary/check from succeeding. Deterministic malformed data is not repaired by waiting and retrying the same task. A transient network failure may justify a bounded retry policy, but the side effect must be idempotent and timeout/overlap rules must be explicit.

To validate in an Airflow3 environment, place the DAG in the configured DAG discovery location, confirm its graph, trigger a manual run and inspect all four task states and the summary. Then change one fixture RPM to a negative value, trigger a separate run and confirm validation fails while downstream work does not publish a success result. Restore the fixture afterward. This authoring check does not claim the scheduler was executed locally.

Do not pass a huge dataset through small task-return metadata merely because the tiny example does. Real pipelines commonly pass durable artifact references and checksums, with controlled access and cleanup. A run’s logical data interval, retry attempt and physical wall-clock start are distinct; use a stable batch identity when recovering prior work.
