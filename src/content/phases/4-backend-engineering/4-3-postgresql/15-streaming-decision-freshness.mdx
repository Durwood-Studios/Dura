## Why this matters

A fraud decision uses a transaction count that is ten minutes old while the dashboard says real time. Processing quickly is not enough if the features represent stale or incomplete events.

## Start with something familiar

A weather station can transmit a reading instantly even if the measurement was taken yesterday. Event time and arrival time answer different questions.

## The mental model

> Preserve event identity, event time, processing time and feature version. A streaming result has a freshness and late-data policy; a decision should not silently treat missing or stale evidence as current.

## The mechanism

Event time is when the source says the event occurred; processing time is when the system handles it. Clock quality and delays affect both interpretation and windowing. A watermark is an engine-specific mechanism for bounding assumptions about late data and state cleanup, not proof that no older event can ever arrive.

The fixture counts unique events in the interval[100,160) seconds. Arrivals are E1 at event-time 110, E2 at 150, duplicate E1 and late-arriving E3 at 120. All three unique events belong to the same event-time interval. A policy that finalized the window before E3 must specify whether to revise the result, route a correction or deliberately exclude and report the late event.

```python
def window_count(events, start, end):
    ids = {event_id for event_id, event_time in events if start <= event_time < end}
    return len(ids)

initial = [("E1", 110), ("E2", 150), ("E1", 110)]
assert window_count(initial, 100, 160) == 2
assert window_count(initial + [("E3", 120)], 100, 160) == 3
assert window_count(initial + [("E4", 160)], 100, 160) == 2
print("streaming window checks passed")
```

This finite fixture does not implement a streaming engine, durable state or conflict detection for reused IDs with changed payloads. It makes event-time, deduplication and boundary rules inspectable.

For a fraud feature, record the feature’s as-of time and the age allowed by the decision policy. If stale, route to a declared fallback/review rather than pretending an old count is current. Evaluate model errors, latency, freshness and review capacity together. Offline model accuracy does not prove the online feature pipeline produces the same values at decision time.

A real deployment needs engine-specific late-data tests, checkpoint/recovery behavior, load measurements and monitoring for lag and dropped/corrected events. This lesson’s synthetic count and written decision record establish no real-time production guarantee.
