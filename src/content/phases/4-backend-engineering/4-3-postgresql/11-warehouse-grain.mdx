## Why this matters

A dashboard doubles revenue after a join, although no new sale occurred. The error often begins with an unstated grain: what exactly does one row represent? A warehouse model must preserve that meaning through loading and aggregation.

## Start with something familiar

A receipt and a line on that receipt are different counting units. Adding the receipt total once for every line counts the same purchase repeatedly. A fact table needs an equally explicit unit of observation.

## The mental model

> One fact-table row represents one declared business event or snapshot at a consistent grain. Dimensions describe its context. A join must preserve the intended cardinality before measures are summed.

## The mechanism

For this fixture, a sale fact is one order line identified by order_id and line_id. It stores product_id, quantity and line_amount in integer minor currency units. Product is a dimension with one row per product_id in this simplified current-state model. Amounts all use the same declared currency; cross-currency aggregation would need an explicit conversion policy.

```python
import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE product(product_id TEXT PRIMARY KEY, category TEXT NOT NULL);
CREATE TABLE sale(order_id TEXT, line_id INTEGER, product_id TEXT,
                  quantity INTEGER, line_amount INTEGER,
                  PRIMARY KEY(order_id,line_id));
INSERT INTO product VALUES ('p1','tools'),('p2','books');
INSERT INTO sale VALUES ('o1',1,'p1',2,1200),('o1',2,'p2',1,800);
""")
rows = db.execute("""
SELECT p.category, SUM(s.line_amount)
FROM sale s JOIN product p ON p.product_id=s.product_id
GROUP BY p.category ORDER BY p.category
""").fetchall()
assert rows == [('books', 800), ('tools', 1200)]
assert sum(amount for _, amount in rows) == 2000
print("warehouse checks passed")
```

The line amounts sum to 2000, not the order total multiplied by two lines. A separate order-level shipping charge should not be repeated on every line without a declared allocation rule. Measures have different additivity: balances measured at daily snapshots should not simply be summed across dates as if they were new deposits.

A historical dimension can have several versions per natural product ID. Joining facts to all versions duplicates facts. Use the appropriate surrogate/version key or a valid-time rule that identifies exactly one intended version. The simple primary key in this fixture prevents that duplication but does not implement historical dimension tracking.

Before publishing a report, reconcile input and output row counts, uniqueness and totals. Include an unmatched-dimension policy: an inner join can silently drop a fact whose product is absent. Decide whether to reject, quarantine or map to an explicit unknown member, and report that count. A successful SQL query is not evidence that the business metric is correct.
