## Why this matters

A GraphQL request returns data and errors together. Treating HTTP success as complete application success hides a missing field; treating every error as no data can discard usable results. The schema and response contract explain what happened.

## Start with something familiar

An order form asks for specific items from a catalog. The catalog defines what may be requested, but availability and permission still need checking when the order is fulfilled.

## The mental model

> A GraphQL operation selects fields from a typed schema. Selection is not authorization, and a response may contain partial data that must be interpreted with its errors.

## The mechanism

A schema describes fields and types. A query reads through those fields; variables supply operation inputs without constructing query text by string concatenation. A resolver is application logic that provides a field's value. Authorization still belongs in trusted server logic for the requested resource.

This complete teaching schema defines a nullable lesson lookup and a non-null title:

```graphql
type Lesson { id: ID!, title: String! }
type Query { lesson(id: ID!): Lesson }
```

A matching operation and separate variable object are:

```graphql
query LessonTitle($lessonId: ID!) {
  lesson(id: $lessonId) { id title }
}
```

```json
{"lessonId":"intro"}
```

These documents describe an API contract; running them requires a configured GraphQL server with resolvers. The exclamation mark marks a non-null contract. It does not make an absent database row appear. The nullable lesson can be null when no permitted result exists under the API's policy. If resolving a non-null field fails, the error affects the nearest nullable enclosing result; clients should not assume a title string exists merely because the HTTP layer succeeded.

Validate input shape and resource authorization independently. Limit expensive query work with a declared server policy; allowing arbitrary nested selection is not a guarantee of bounded database work. For a page, distinguish loading, permitted data, absent result and errors. Do not expose private diagnostic details in a public error message.

A useful test checks a permitted lesson, an absent lesson, an unauthorized request and a resolver failure. It compares the actual data/error shape with the schema, rather than looking only for status200. Schema evolution also needs consumer tests: changing a field's nullability can alter how failures propagate.
