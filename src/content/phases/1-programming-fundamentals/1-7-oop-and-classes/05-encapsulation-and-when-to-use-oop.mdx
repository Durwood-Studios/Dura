## Why this matters

Imagine a bank account class where any code anywhere in the codebase can do `account.balance = -9999`. The class has methods like `deposit()` and `withdraw()` that validate inputs — but if anyone can bypass them and set `balance` directly, those validations mean nothing.

<VocabTooltip slug="encapsulation">Encapsulation</VocabTooltip> is the practice of hiding an
object's internals so that outside code can only interact through a controlled
<VocabTooltip slug="interface">interface</VocabTooltip>. It is not about secrecy for its own sake —
it is about preventing invalid state. An object that controls its own data stays consistent. An
object whose data anyone can poke at is a source of hard-to-find bugs.

This final lesson also covers a question that trips up many new developers: when is OOP actually the right choice? The answer is not "always."

## The "capsule" analogy

A medicine capsule contains active ingredients inside a protective shell. You do not open the capsule and mix the powder into something else — you take it as designed. The shell controls how the contents are delivered.

Encapsulation works the same way. The class's internal data (the ingredients) is protected. Outside code interacts only with the public methods (the shell) — the designed, validated, safe way to work with the data.

> **Encapsulation means: hide what can break, expose what you need. The object controls its own state.**

## Private fields with `#`

In modern JavaScript, prefixing a property name with `#` makes it a true private field. Code outside the class cannot read or write it at all — not just "please don't," but enforced by the language.

```javascript
class BankAccount {
  // Private fields — accessible only within this class
  #balance;
  #owner;
  #transactionHistory;

  constructor(owner, initialBalance = 0) {
    if (initialBalance < 0) {
      throw new Error("Initial balance cannot be negative");
    }
    this.#owner = owner;
    this.#balance = initialBalance;
    this.#transactionHistory = [];
  }

  // Public method — the only way to add money
  deposit(amount) {
    if (amount <= 0) {
      throw new Error("Deposit amount must be positive");
    }
    this.#balance += amount;
    // Track every transaction internally — outside code never directly manages this
    this.#transactionHistory.push({ type: "deposit", amount, date: new Date() });
    console.log(`Deposited $${amount}. Balance: $${this.#balance}`);
  }

  // Public method — the only way to remove money
  withdraw(amount) {
    if (amount <= 0) throw new Error("Amount must be positive");
    if (amount > this.#balance) throw new Error("Insufficient funds");
    this.#balance -= amount;
    this.#transactionHistory.push({ type: "withdrawal", amount, date: new Date() });
    console.log(`Withdrew $${amount}. Balance: $${this.#balance}`);
  }

  // Read-only access to balance — callers can see it, but not set it
  get balance() {
    return this.#balance;
  }

  // Read-only access to owner name
  get owner() {
    return this.#owner;
  }

  // Return a copy so callers can read history but not mutate the internal array
  getHistory() {
    return [...this.#transactionHistory];
  }
}

const account = new BankAccount("Alice", 1000);
account.deposit(500); // Deposited $500. Balance: $1500
account.withdraw(200); // Withdrew $200. Balance: $1300

console.log(account.balance); // 1300 — reading via getter
console.log(account.owner); // Alice

// account.#balance = 999999; // SyntaxError — private field is truly inaccessible
// account.balance = 999999;  // This silently fails (no setter defined)

try {
  account.withdraw(5000);
} catch (e) {
  console.error(e.message); // Insufficient funds
}
```

## Getters and setters

A <VocabTooltip slug="getter">getter</VocabTooltip> is a method that looks like a property when accessed. A <VocabTooltip slug="setter">setter</VocabTooltip> is a method that runs when a property is assigned — letting you validate the value before it lands.

```javascript
class Temperature {
  #celsius;

  constructor(celsius) {
    // Use the setter so validation runs at construction too
    this.celsius = celsius;
  }

  // Setter validates input before storing
  set celsius(value) {
    if (value < -273.15) {
      throw new Error("Temperature cannot be below absolute zero");
    }
    this.#celsius = value;
  }

  // Getter exposes the stored value
  get celsius() {
    return this.#celsius;
  }

  // Derived getters — computed from the private field, always in sync
  get fahrenheit() {
    return (this.#celsius * 9) / 5 + 32;
  }

  get kelvin() {
    return this.#celsius + 273.15;
  }
}

const boiling = new Temperature(100);
console.log(boiling.celsius); // 100
console.log(boiling.fahrenheit); // 212
console.log(boiling.kelvin); // 373.15

boiling.celsius = 0; // Calls the setter — validation runs
console.log(boiling.fahrenheit); // 32

try {
  boiling.celsius = -500; // Throws — below absolute zero
} catch (e) {
  console.error(e.message);
}
```

## When to use OOP — and when not to

OOP is a tool. It solves real problems — but only when those problems match its strengths.

### Use OOP when:

**You have multiple things of the same kind, each with its own state.**

```javascript
// Good fit — each User has its own data and behavior
class User {
  constructor(id, name, email) { ... }
  updateEmail(email) { ... }
  deactivate() { ... }
}
```

**You have a clear hierarchy where subtypes share behavior but specialize it.**

```javascript
// Good fit — real IS-A relationship
class Notification { send() { ... } }
class EmailNotification extends Notification { send() { /* email */ } }
class PushNotification extends Notification { send() { /* push */ } }
```

**You want to hide complex internal state behind a clean interface.**

```javascript
// Good fit — internal complexity hidden, clean API exposed
class WebSocketConnection {
  #socket; #retryCount; #messageQueue;
  connect() { ... }
  send(data) { ... }
  disconnect() { ... }
}
```

### Skip OOP when:

**You are just grouping a few related functions that do not share state.**

```javascript
// OOP overkill:
class MathUtils {
  add(a, b) {
    return a + b;
  }
  multiply(a, b) {
    return a * b;
  }
}

// Better — just export functions:
export function add(a, b) {
  return a + b;
}
export function multiply(a, b) {
  return a * b;
}
```

**You only have one instance and no inheritance.**

```javascript
// OOP overkill for a one-off configuration loader:
class Config {
  constructor() {
    this.apiUrl = "...";
  }
  getApiUrl() {
    return this.apiUrl;
  }
}

// Better — just an object literal or a module constant:
export const config = { apiUrl: "..." };
```

**The hierarchy is forced — things are not genuinely IS-A related.**

```javascript
// Warning sign — is a Manager really just a "specialized Employee"?
// Or do they have fundamentally different roles and data?
// Forced hierarchies create fragile code.
class Employee { ... }
class Manager extends Employee { ... }
class SeniorManager extends Manager { ... }
class ExecutiveManager extends SeniorManager { ... }
// Stop. Use composition or separate classes.
```

## Analyzing a design decision

```javascript
// BEFORE: unprotected, anyone can corrupt state
class ShoppingCart {
  items = [];
  total = 0; // Bug waiting to happen — what if total and items fall out of sync?

  addItem(item) {
    this.items.push(item);
    this.total += item.price; // Caller could separately set total to 0...
  }
}

// AFTER: encapsulated — total is always derived, never stored separately
class ShoppingCart {
  #items = [];

  addItem(item) {
    if (!item.price || item.price <= 0) {
      throw new Error("Item must have a positive price");
    }
    this.#items.push(item);
  }

  removeItem(id) {
    this.#items = this.#items.filter((item) => item.id !== id);
  }

  // Derived from source of truth — guaranteed to be correct
  get total() {
    return this.#items.reduce((sum, item) => sum + item.price, 0);
  }

  get itemCount() {
    return this.#items.length;
  }

  // Expose a copy, not the internal array
  get items() {
    return [...this.#items];
  }
}

const cart = new ShoppingCart();
cart.addItem({ id: 1, name: "Widget", price: 9.99 });
cart.addItem({ id: 2, name: "Gadget", price: 24.99 });

console.log(cart.total); // 34.98
console.log(cart.itemCount); // 2

cart.removeItem(1);
console.log(cart.total); // 24.99 — always correct, can never drift
```

## What you learned

- Private fields (`#`) enforce encapsulation at the language level — not just by convention.
- Getters provide read-only access to derived or protected values; setters add validation when values change.
- Encapsulation prevents invalid state by ensuring all data changes go through controlled, validating methods.
- OOP works well for multiple instances of a thing with shared state and behavior, or clear IS-A hierarchies.
- Plain functions and objects are often better than a class when there is no shared state, no hierarchy, and only one instance.
- The sign of a bad class hierarchy: long chains of `extends` that feel forced rather than natural.
