## Why this matters

Picture this function:

```javascript
function makeNoise(animal) {
  if (animal.type === "dog") {
    console.log("Woof!");
  } else if (animal.type === "cat") {
    console.log("Meow!");
  } else if (animal.type === "bird") {
    console.log("Tweet!");
  }
  // every new animal type = another else if
}
```

Every time you add a new animal, you modify this function. This function now has to know about every animal type that will ever exist. That is fragile — a single missed case is a silent bug.

<VocabTooltip slug="polymorphism">Polymorphism</VocabTooltip> — the ability for different objects to
respond to the same method in their own way — removes this fragility. Each class handles its own
behavior. The calling code does not need to know which specific type it is dealing with.

## The "universal remote" analogy

A TV remote has a power button. Press it on a Sony TV and the Sony turns on. Press it on a Samsung TV and the Samsung turns on. Press it on a projector and the projector turns on. The button is the same. The response is specific to the device.

<VocabTooltip slug="polymorphism">Polymorphism</VocabTooltip> works the same way. Call
`.makeSound()` on any animal, and each animal responds according to its own nature — without the
caller needing to know what kind of animal it is.

> **Polymorphism means: one method name, each class defines what it does.**

## Method overriding

When a subclass defines a method with the same name as a parent method, the subclass version takes over for instances of that subclass. This is called <VocabTooltip slug="method-overriding">method overriding</VocabTooltip>.

```javascript
class Animal {
  constructor(name) {
    this.name = name;
  }

  // The parent provides a default behavior
  makeSound() {
    console.log(`${this.name} makes a sound.`);
  }

  describe() {
    console.log(`I am ${this.name}.`);
    // Call makeSound as part of describe — whichever version applies
    this.makeSound();
  }
}

class Dog extends Animal {
  // This OVERRIDES Animal's makeSound — Dog instances use this version
  makeSound() {
    console.log(`${this.name} says: Woof!`);
  }
}

class Cat extends Animal {
  makeSound() {
    console.log(`${this.name} says: Meow!`);
  }
}

class Duck extends Animal {
  makeSound() {
    console.log(`${this.name} says: Quack!`);
  }
}

const animals = [new Dog("Rex"), new Cat("Whiskers"), new Duck("Donald")];

// Same method call — three different behaviors — no if/else needed
for (const animal of animals) {
  animal.makeSound();
}
// Rex says: Woof!
// Whiskers says: Meow!
// Donald says: Quack!
```

## Calling the parent method with `super`

Sometimes you want to override a method but still include what the parent does — you are extending the behavior, not replacing it entirely.

```javascript
class Notification {
  constructor(message) {
    this.message = message;
    this.sentAt = new Date().toISOString();
  }

  send() {
    // Every notification logs to the audit trail — this is the base behavior
    console.log(`[${this.sentAt}] Notification: ${this.message}`);
  }
}

class EmailNotification extends Notification {
  constructor(message, recipient) {
    super(message);
    this.recipient = recipient;
  }

  send() {
    // Run the parent's send() first so the audit log still fires
    super.send();
    // Then add email-specific behavior
    console.log(`  → Emailed to: ${this.recipient}`);
  }
}

class SMSNotification extends Notification {
  constructor(message, phoneNumber) {
    super(message);
    this.phoneNumber = phoneNumber;
  }

  send() {
    super.send(); // Preserve the audit log
    console.log(`  → SMS sent to: ${this.phoneNumber}`);
  }
}

const notifications = [
  new EmailNotification("Your order shipped!", "alice@example.com"),
  new SMSNotification("Verification code: 4821", "+15555551234"),
];

// Dispatch all notifications without knowing their specific type
for (const n of notifications) {
  n.send();
}
// [timestamp] Notification: Your order shipped!
//   → Emailed to: alice@example.com
// [timestamp] Notification: Verification code: 4821
//   → SMS sent to: +15555551234
```

## Polymorphism in real code: a payment processor

```javascript
class PaymentMethod {
  constructor(amount) {
    this.amount = amount;
  }

  // Subclasses must override this — the base version is a fallback
  process() {
    throw new Error(`${this.constructor.name} must implement process()`);
  }

  receipt() {
    // Receipt format is the same for all — no override needed
    console.log(`Receipt: $${this.amount} charged via ${this.constructor.name}`);
  }
}

class CreditCard extends PaymentMethod {
  constructor(amount, lastFour) {
    super(amount);
    this.lastFour = lastFour;
  }

  process() {
    console.log(`Processing $${this.amount} on card ending in ${this.lastFour}...`);
    // Real implementation would call a payment gateway here
    return { success: true, method: "credit_card" };
  }
}

class PayPal extends PaymentMethod {
  constructor(amount, email) {
    super(amount);
    this.email = email;
  }

  process() {
    console.log(`Processing $${this.amount} via PayPal account: ${this.email}...`);
    return { success: true, method: "paypal" };
  }
}

// This function works with ANY PaymentMethod subclass — past, present, or future
function checkout(paymentMethod) {
  const result = paymentMethod.process();
  if (result.success) {
    paymentMethod.receipt();
  }
}

checkout(new CreditCard(49.99, "4242"));
// Processing $49.99 on card ending in 4242...
// Receipt: $49.99 charged via CreditCard

checkout(new PayPal(19.99, "user@example.com"));
// Processing $19.99 via PayPal account: user@example.com...
// Receipt: $19.99 charged via PayPal
```

## What you learned

- Method overriding lets a subclass replace an inherited method with its own implementation.
- `super.methodName()` calls the parent version from inside an override — useful when you want to extend, not fully replace.
- Polymorphism means one method name dispatches to different implementations depending on the object's actual type.
- A function that accepts a base class can work with any subclass without modification — this is the real power of polymorphism.
- Avoiding `if/else` or `switch` on type makes code easier to extend: add a new subclass, and existing functions automatically work with it.
