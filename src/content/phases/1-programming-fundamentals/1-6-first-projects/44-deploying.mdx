## Why this matters

A successful run on your laptop does not prove that someone else can load your project. Deployment is the process of preparing the files, placing them in a target environment, and checking what a visitor actually receives.

You can rehearse that reasoning offline. This lesson uses a fictional static-site release with a stated hosting contract; no account or paid service is required.

## Start with something familiar

Moving a stage production from rehearsal to a public venue requires the script, equipment, settings, and a recovery plan. Loading a truck is one step; confirming that the audience can see the performance is another.

## The mental model

> Deployment places an artifact and its configuration in a target environment. A completed build, a completed upload, and a healthy visitor experience are different states to verify.

## Read the target contract

An **artifact** is the set of files produced for release. A **static host** serves files; it does not run an arbitrary JavaScript server. For this exercise, the host serves the contents of a directory named `dist`, and its root URL must load `dist/index.html`.

The fictional project has a build script named `build`. Running `npm run build` produces `dist/index.html`, `dist/app.js`, and `dist/styles.css`. Here, npm is the command-line tool that reads named scripts from the project's `package.json`; `run build` executes that project's chosen build command. A real project's README must tell you its commands and output directory.

The HTML refers to `./app.js` and `./styles.css`. Uploading only the HTML would leave its behavior and styling missing. Upload the complete artifact, with those relative paths intact.

## Separate public configuration from secrets

Every file served to the browser is available to the visitor. Putting a secret into a JavaScript file, an HTML file, or a build-time variable that gets copied into either does not protect it. An environment variable is a way to supply configuration to a process; its name alone does not make the final output secret.

Our example requires no secrets. If a future feature requires a private credential, that operation needs a trusted server boundary. Do not invent a way to hide a credential in a static artifact.

## Plan verification and recovery

A **smoke check** verifies a few essential behaviors after release: load the root page, verify its styling, activate its main control, and reload the page. Keep the previous complete artifact until these checks pass. A **rollback** restores that known-good artifact when a new release fails.

Version-control history helps identify the source used for a build. A hosting service may offer automatic builds after a push, but the branch rules, build command, output directory, and deployment target must be configured and verified; a push alone is not proof of a working release.

## What you learned

- Match the build output to the hosting target's stated contract.
- Publish the complete artifact and verify the visitor's content, styling, and behavior.
- Restore a known-good artifact when a release fails essential checks.
- Keep private credentials out of files delivered to the browser.

## Connect forward

A repeatable release checklist turns your next project into something another person can verify and use.
