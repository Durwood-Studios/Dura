## Why this matters

Every meaningful program you write will eventually need to do more than one thing at a time — handle multiple network connections, keep a UI responsive while computing something expensive, or saturate multiple CPU cores to finish a job faster. The two fundamental primitives for concurrent execution are **threads** and **processes**. If you reach for the wrong one, you either pay an enormous performance tax or introduce security and stability bugs that are nightmarish to debug.

Understanding the difference is not academic trivia. It determines how you architect services, why certain bugs only appear under load, and what "isolated crash" means in production. The engineers who design reliable systems have this model so deeply internalized that they think with it automatically.

## A building full of offices

Before naming anything, picture a large office building. Each floor is rented by a different company. The company on floor 3 has its own locked server room, its own printers, its own filing cabinets. They can't accidentally walk into floor 7's server room because a locked door separates them. If a fire breaks out on floor 3, the sprinkler system on that floor can contain it without immediately burning down the whole building.

Now picture the individual employees on floor 3. They all share the same floor plan, the same printer, the same coffee machine, the same filing cabinets. When an employee needs to send a fax, they walk to the shared fax machine. They can leave a note in the shared filing cabinet and any colleague can read it immediately — no courier required.

This is the process/thread relationship.

> **A process is a floor. A thread is an employee on that floor.**

Each process gets its own isolated address space — its own virtual memory, file descriptors, and execution context. No other process can directly read or write that memory (barring explicit shared-memory mechanisms). Threads within the same process share everything: the heap, global variables, open file handles, the code itself. They each own only their own **stack** (the chain of function calls currently in progress) and their own register state (where in the code they're currently executing).

## What the OS actually stores

When you launch a program, the operating system creates a process. That process contains:

| Resource              | Scope      | Description                                          |
| --------------------- | ---------- | ---------------------------------------------------- |
| Virtual address space | Process    | The full memory map: code, heap, memory-mapped files |
| Open file descriptors | Process    | References to open files, sockets, pipes             |
| Signal handlers       | Process    | How signals like SIGTERM are handled                 |
| User/group IDs        | Process    | Who this process runs as                             |
| **Stack**             | **Thread** | Each thread's own function call chain                |
| **Program counter**   | **Thread** | Where this thread is currently executing             |
| **Registers**         | **Thread** | CPU register state for this thread                   |

A single-threaded program has exactly one thread — the main thread — with one stack and one program counter. A multi-threaded program has one process (one address space, one set of file descriptors) but multiple threads, each with their own private stack.

## What a context switch costs

The OS is constantly juggling many threads and processes on a limited number of CPU cores. It time-slices: each thread gets a slice of CPU time, then the OS pauses it and runs something else. The act of pausing one thread and resuming another is a **context switch**.

```c
// Pseudocode of what the OS kernel does during a context switch
// (massively simplified — real kernels do much more)

void context_switch(Thread *current, Thread *next) {
    // Save the current thread's CPU state to memory
    // so we can restore it exactly when it runs again
    save_registers(current->cpu_context);
    current->stack_pointer = get_cpu_stack_pointer();
    current->program_counter = get_cpu_program_counter();

    // Restore the next thread's previously-saved state
    // The CPU will resume executing as if it never stopped
    set_cpu_stack_pointer(next->stack_pointer);
    set_cpu_program_counter(next->program_counter);
    restore_registers(next->cpu_context);

    // If switching between PROCESSES (not just threads within one process),
    // we must also flush the TLB and switch page tables —
    // this is why cross-process switches are more expensive
    if (current->process != next->process) {
        switch_page_tables(next->process->page_table);
        flush_tlb();  // Translation Lookaside Buffer must be invalidated
    }
}
```

Switching between two threads in the same process is cheaper than switching between two processes because the memory mapping (page tables) stays the same. The address space doesn't need to change — only the registers and stack pointer do.

## Threads in Python, Go, and C

Different languages expose threads differently. Here's how you create and start a thread in three common systems languages:

```python
import threading
import time

def worker(name: str, iterations: int) -> None:
    # Each thread has its own stack, so 'name' and 'iterations'
    # are private to this invocation — no sharing needed
    for i in range(iterations):
        print(f"[{name}] step {i}")
        time.sleep(0.05)

# Thread creation: OS allocates a new stack for each thread
# but both threads share this process's heap and file descriptors
t1 = threading.Thread(target=worker, args=("Alpha", 3))
t2 = threading.Thread(target=worker, args=("Beta", 3))

t1.start()
t2.start()

# Main thread waits for both to finish before exiting
# Without join(), the process can exit while threads are still running
t1.join()
t2.join()
print("Both workers done")
```

```go
package main

import (
    "fmt"
    "sync"
    "time"
)

func worker(name string, iterations int, wg *sync.WaitGroup) {
    // wg pointer is shared — it lives on the heap, not the stack
    // All goroutines can safely call wg.Done() because sync.WaitGroup
    // is designed for concurrent access
    defer wg.Done()
    for i := range iterations {
        fmt.Printf("[%s] step %d\n", name, i)
        time.Sleep(50 * time.Millisecond)
    }
}

func main() {
    var wg sync.WaitGroup
    wg.Add(2)
    go worker("Alpha", 3, &wg)
    go worker("Beta", 3, &wg)
    wg.Wait()
    fmt.Println("Both workers done")
}
```

Go's goroutines are lightweight threads managed by the Go runtime, not directly by the OS. The runtime multiplexes many goroutines onto a smaller pool of OS threads — this is called M:N threading and is why you can run millions of goroutines without running out of OS thread resources.

## Processes vs threads: the trade-off table

|                 | Threads                                   | Processes                                            |
| --------------- | ----------------------------------------- | ---------------------------------------------------- |
| Memory overhead | Low (share heap)                          | High (separate address space)                        |
| Creation speed  | Fast                                      | Slow (must copy/fork address space)                  |
| Communication   | Shared memory (fast, dangerous)           | IPC — pipes, sockets, shared memory (safe, overhead) |
| Crash isolation | One thread crash can kill all threads     | Process crash doesn't affect other processes         |
| Use case        | CPU parallelism, shared-state concurrency | Isolation, security boundaries, microservices        |

Web browsers use both: one process per tab (isolation — a crashed tab doesn't crash the browser) and multiple threads within each tab (rendering thread, JavaScript thread, network thread).

## What you learned

- A **process** owns an isolated address space; a **thread** is an execution unit within a process that shares the heap and file descriptors but owns its own stack and registers
- Context switches between threads in the same process are cheaper than between processes because the page table and TLB don't need to change
- Threads are faster to create and cheaper for communication (shared memory), while processes provide crash isolation and security boundaries
- The OS saves and restores a thread's registers and stack pointer during context switches so execution resumes exactly where it left off
- Go's goroutines use M:N threading — many goroutines multiplexed onto fewer OS threads — which reduces OS-level overhead at high concurrency

With the mental model in place, the next lesson confronts what goes wrong when threads share memory without coordination: race conditions, mutexes, and the dreaded deadlock.
