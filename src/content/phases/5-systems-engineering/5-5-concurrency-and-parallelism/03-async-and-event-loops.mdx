## Why this matters

Thread-per-connection is the intuitive model for handling concurrent network requests: each incoming connection gets its own thread. It works until you try to handle 10,000 simultaneous connections. At that scale, you've allocated 10,000 stacks (each 1–8 MB), scheduled 10,000 threads, and most of them are sleeping, waiting for network I/O that hasn't arrived yet. Your server is spending its CPU time managing threads that aren't doing work.

This is the C10K problem — serving 10,000 concurrent clients — and it was unsolved in the late 1990s. The solution was a fundamentally different concurrency model: event-driven I/O with a single-threaded event loop. Node.js, Nginx, Redis, and Python's asyncio all use it. Understanding how it works explains why these tools scale the way they do and what their limitations are.

## Start with something familiar

A receptionist can take another call while waiting for a courier, but cannot do so while performing a long calculation without pause.

## The mental model

> Async waiting can release an event loop to process other work. Marking a function async does not move synchronous CPU work onto another thread or make that work interruptible.

## The waiting room problem

Imagine you run a restaurant and you have 50 tables. In one staffing model, you assign one waiter per table: 50 waiters. Most of the time, each waiter is standing by their table doing nothing — waiting for the customer to decide what to order, waiting for the kitchen to prepare the food. Ninety percent of their working time is idle.

In a better model, one skilled expediter handles all 50 tables. They're always moving: taking order from table 3, delivering food to table 7, refilling water at table 12. When any table needs attention, they respond. They never wait — when nothing is ready, they check what's next.

An event loop is the expediter. The tables are I/O operations (network reads, file reads, timer expirations). The expediter's "check what's next" is a syscall to `epoll` or `kqueue` that returns the set of file descriptors that are ready to be read or written right now.

> **An event loop is a single thread that repeatedly asks the OS "which I/O operations are ready?" and dispatches the corresponding callbacks.**

## What blocking I/O actually does to a thread

When a thread calls `read()` on a socket and no data has arrived yet, the OS suspends the thread. The thread's state is saved, it's moved off the CPU's run queue, and it won't execute again until the data arrives. The CPU is free to run other threads — but the blocked thread is wasting its stack space and kernel bookkeeping.

```c
// Blocking read — thread suspends here until data arrives or connection closes
ssize_t bytes = read(socket_fd, buffer, sizeof(buffer));
// Thread resumes here when the OS has data ready
```

With non-blocking I/O, the `read()` call returns immediately even if no data is available. Instead of blocking, it returns an error code (`EAGAIN` or `EWOULDBLOCK`) meaning "try again later — data isn't ready yet."

```c
// Set socket to non-blocking mode
fcntl(socket_fd, F_SETFL, O_NONBLOCK);

// Non-blocking read — returns immediately whether or not data is available
ssize_t bytes = read(socket_fd, buffer, sizeof(buffer));
if (bytes == -1 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
    // No data yet — don't block, go do something else
    // Register this fd with epoll so we're notified when data arrives
}
```

The event loop uses a system call like `epoll_wait` (Linux) or `kqueue` (macOS/BSD) to efficiently monitor thousands of file descriptors at once and return only the ones that are ready. This is the OS-level mechanism that makes single-threaded high-concurrency possible.

## The event loop in JavaScript (Node.js)

Node.js runs your JavaScript in a single thread on top of libuv, a C library that wraps the OS's async I/O mechanisms. The event loop is the central mechanism:

```
┌─────────────────────────────────────────────────────┐
│                     Event Loop                       │
│                                                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐  │
│  │  timers  │→ │  poll    │→ │  check (setImm.) │  │
│  │setTimeout│  │ I/O ready│  │                  │  │
│  │setInterval│  │ callbacks│  │                  │  │
│  └──────────┘  └──────────┘  └──────────────────┘  │
│                                                      │
│  JavaScript call stack always empty between phases   │
└─────────────────────────────────────────────────────┘
```

The critical rule: **JavaScript runs to completion**. When a callback fires, it runs uninterrupted until it returns. No other JavaScript runs in parallel. There are no race conditions because there is no parallel execution.

```javascript
// This runs in Node.js — one thread, but handling three "concurrent" HTTP requests

import http from "http";

const server = http.createServer((req, res) => {
  // This callback fires when a request arrives.
  // The I/O (reading the request body, writing the response)
  // is done asynchronously — this thread never blocks waiting for network.

  // Simulate reading from a database (non-blocking I/O)
  setTimeout(() => {
    // This callback fires when the "database query" completes.
    // Meanwhile, the event loop can handle OTHER incoming requests.
    res.writeHead(200, { "Content-Type": "text/plain" });
    res.end("Hello from single-threaded Node.js\n");
  }, 10); // pretend 10ms DB query
});

server.listen(3000, () => {
  console.log("Serving on port 3000");
  // If 10,000 clients connect simultaneously, each gets a callback scheduled.
  // All 10,000 are "in flight" concurrently, but only ONE runs at a time.
});
```

## Promises and async/await

Callbacks work but nest deeply and become hard to read. Promises represent a future value. `async/await` is syntax that makes promise-based code look synchronous.

```javascript
// Callback style — the "pyramid of doom"
function fetchUserProfile(userId, callback) {
  getUser(userId, (err, user) => {
    if (err) return callback(err);
    getPosts(user.id, (err, posts) => {
      if (err) return callback(err);
      getComments(posts[0].id, (err, comments) => {
        if (err) return callback(err);
        callback(null, { user, posts, comments });
      });
    });
  });
}

// Promise style — flat chaining, better error handling
function fetchUserProfile(userId) {
  return getUser(userId)
    .then((user) => getPosts(user.id).then((posts) => ({ user, posts })))
    .then(({ user, posts }) =>
      getComments(posts[0].id).then((comments) => ({ user, posts, comments }))
    );
}

// async/await — reads like synchronous code, runs asynchronously
async function fetchUserProfile(userId) {
  // await suspends THIS coroutine and yields control back to the event loop.
  // The thread is NOT blocked — it can run other callbacks while we "wait".
  const user = await getUser(userId);
  const posts = await getPosts(user.id);
  const comments = await getComments(posts[0].id);
  return { user, posts, comments };
}

// Parallel async operations — don't await sequentially when ops are independent
async function fetchUserProfileParallel(userId) {
  const user = await getUser(userId);

  // Promise.all starts both operations at once — doesn't wait for posts before starting comments
  const [posts, followers] = await Promise.all([getPosts(user.id), getFollowers(user.id)]);
  return { user, posts, followers };
}
```

## Python asyncio

Python's `asyncio` uses the same event loop concept with `async def` and `await`:

```python
import asyncio
import aiohttp  # async HTTP client — regular requests would block the event loop

async def fetch_data(session: aiohttp.ClientSession, url: str) -> dict:
    # await yields control to the event loop until the HTTP response arrives.
    # The event loop can process other coroutines during this wait.
    async with session.get(url) as response:
        return await response.json()

async def fetch_all(urls: list[str]) -> list[dict]:
    async with aiohttp.ClientSession() as session:
        # asyncio.gather runs all coroutines concurrently — like Promise.all
        # All HTTP requests are in flight at the same time, but only one
        # callback runs at a time (single-threaded model)
        tasks = [fetch_data(session, url) for url in urls]
        return await asyncio.gather(*tasks)

async def main() -> None:
    urls = [
        "https://jsonplaceholder.typicode.com/todos/1",
        "https://jsonplaceholder.typicode.com/todos/2",
        "https://jsonplaceholder.typicode.com/todos/3",
    ]
    results = await fetch_all(urls)
    for r in results:
        print(r["title"])

asyncio.run(main())
```

## The CPU-bound trap

Event loops excel at I/O-bound concurrency. They are terrible for CPU-bound work.

```python
import asyncio

async def cpu_bound_mistake() -> None:
    # This blocks the ENTIRE event loop for however long it takes.
    # While this runs, no other callbacks can fire — including health checks,
    # incoming requests, or timeout handlers.
    result = sum(range(100_000_000))  # 100M iterations on the main thread
    return result

## Why this matters
# so the event loop thread stays free to handle I/O
async def cpu_bound_correct() -> None:
    loop = asyncio.get_event_loop()
    # run_in_executor offloads to a thread pool — the event loop isn't blocked
    result = await loop.run_in_executor(None, lambda: sum(range(100_000_000)))
    return result
```

| Workload type                            | Best tool                                     | Why                                        |
| ---------------------------------------- | --------------------------------------------- | ------------------------------------------ |
| I/O bound (network, disk)                | Event loop (async/await)                      | Thread never really waits — OS handles I/O |
| CPU bound (encryption, image processing) | Thread pool or process pool                   | Need actual parallel CPU cores             |
| Mixed                                    | Async I/O + thread/process pool for CPU parts | Combine both models                        |
