## Why this matters

A pod runs as non-root, so a team assumes it cannot expose secrets or contact sensitive services. Workload privilege, API authorization and network reachability are different controls that need separate tests.

## Start with something familiar

A visitor may have no master key but still enter an unlocked room. Reducing one kind of privilege does not automatically close every route to a resource.

## The mental model

> Use layered workload, API and network controls with explicit scope. Admission policy checks pod configuration; RBAC checks Kubernetes API permissions; network policy depends on actual enforcement support and traffic paths.

## The mechanism

Kubernetes Pod Security Standards define privileged, baseline and restricted profiles. Pod Security Admission can warn, audit or enforce selected profiles and versions. A warning is not a rejection, and choosing restricted does not prove that every application-level security requirement is satisfied.

The fictional worker needs to read one ConfigMap, make outbound requests to one internal API and write temporary files. It does not need cluster-admin, host networking or a privileged container. Review its service account/RBAC, pod security context and allowed network paths separately. A read-only root filesystem may require a deliberately scoped writable temporary volume; security configuration must preserve the intended task.

Test an authorized ConfigMap read, an unauthorized Secret read, a prohibited privileged-pod admission and a disallowed network destination. Also test the valid outbound call and temporary write. If the cluster’s network plugin does not enforce NetworkPolicy, the presence of a policy object is not evidence that traffic is blocked.

Pin admission policy versions to the deployment’s reviewed upgrade policy and test changes before rollout. Inventory images, secrets, node/control-plane access and patch responsibilities. Container isolation is not a blanket boundary against every host or kernel vulnerability, and a non-root process can still misuse credentials it legitimately receives.

This is a security review matrix for a supplied workload. It does not apply cluster policies or run kubectl. Actual admission, RBAC and network tests on the configured cluster are required before claiming enforcement.

## Practice

If a namespace uses Pod Security Admission in warn mode, does a privileged-pod warning prove the pod was blocked? Does a NetworkPolicy object prove the network plugin enforced it?

<details><summary>Compare the reasoning</summary><p>No to both. Warn mode reports rather than enforces rejection, and network-policy behavior requires an enforcing implementation and actual traffic tests.</p></details>
