## Why this matters

A service mesh encrypts traffic, so a team assumes every request is authorized. Encryption can protect the channel while an authenticated service still calls a resource it should not access. Separate the controls before trusting the deployment.

## Start with something familiar

A staff badge identifies a person at a building entrance; it does not automatically open every laboratory. Workload identity and application permission have the same separation.

## The mental model

> A mesh can apply transport identity, routing and telemetry policies between workloads. Authentication establishes identity; authorization decides allowed actions. Application-level data ownership still needs its own checks.

## The mechanism

A mesh data plane handles workload traffic according to configuration distributed by its control plane. Implementations differ, so deployment mode, policy attachment and bypass paths matter. In Istio, PeerAuthentication controls peer transport authentication and AuthorizationPolicy controls allowed requests. The following reviewed namespace-level fragment requests strict mutual TLS; it is not a complete installation or authorization policy.

```yaml
apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: require-mtls
  namespace: practice
spec:
  mtls:
    mode: STRICT
```

A separate authorization design might allow only the orders workload identity to call the inventory reservation operation. State the identity, destination, operation and namespace scope explicitly; check actual policy matching against the chosen Istio version and deployment mode. A valid certificate is not evidence that every caller is entitled to every operation.

For the supplied review fixture, orders→reserve is allowed, reports→reserve is denied, and plaintext→reserve is denied. Orders requesting another tenant’s inventory is also denied by the application’s tenant check even if the mesh permits the service-to-service operation. These are acceptance expectations, not observed runtime results.

Mesh retries can amplify load and repeat side effects. A reservation operation needs an idempotency contract before retrying it automatically. Timeouts at client, proxy and server should have a coherent budget; adding independent large retries can turn a partial failure into overload. Record telemetry that distinguishes upstream failures, local policy denials and timeouts.

Validate allowed traffic as well as denials in an isolated installed mesh, including direct paths that might bypass enforcement. Inspect workload enrollment, policy scope, certificate behavior and telemetry. This lesson’s YAML and written matrix do not claim that a cluster or mesh was run. A successful policy parse is only one layer of evidence.
