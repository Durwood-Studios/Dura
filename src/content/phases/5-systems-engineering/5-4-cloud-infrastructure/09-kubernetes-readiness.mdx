## Why this matters

A container process is running while its API cannot accept requests. Restarting every such container can worsen a shared dependency outage. Kubernetes exposes different health signals because process existence, traffic readiness and recoverability are not the same.

## Start with something familiar

A restaurant may be open, have staff inside and still be unable to seat customers. A manager can route customers elsewhere without rebuilding the restaurant. Readiness and liveness similarly answer different operational questions.

## The mental model

> A controller reconciles desired workload state. A readiness check controls whether a workload should receive traffic; a liveness failure can trigger a restart and therefore needs a different justification.

## The mechanism

A Pod groups one or more containers with shared execution context. A Deployment manages replaceable replicas of an application through a desired-state specification. A Service provides stable access to selected endpoints; labels and selectors connect these objects. Kubernetes does not make local container storage a durable shared database.

For a stateless report API, declare two interchangeable replicas with an image identified by an immutable release reference. A readiness endpoint should reflect whether the instance can serve its intended traffic. A liveness endpoint should identify a condition where restarting that container is a reasonable response. A startup probe can allow initialization before the other configured probes begin.

Use this behavioral contract before authoring a manifest:

| Observation | Intended response |
| --- | --- |
| Initialization still within budget | Continue startup checking; do not declare ready yet |
| Shared database temporarily unavailable | Remove readiness if requests cannot be served; avoid a restart storm caused by a liveness dependency check |
| Process deadlocked beyond its local recovery budget | Fail liveness under the declared policy and observe restart behavior |
| Pod replaced during rollout | Route only when the replacement is ready; keep data outside ephemeral local files |

Probe thresholds and timing must be selected for the actual workload. A ready Pod can still fail a request; probes are observations, not a guarantee. Resource limits, graceful shutdown and rollout compatibility require separate tests.

For an existing test cluster, inspect the Deployment, Pods, Service selectors and EndpointSlices with the matching kubectl version. Verify desired versus available replicas and observe endpoint changes when readiness fails. Do not apply an unfamiliar manifest to production to learn the distinction. The acceptance task below is a configuration review, not a claim that a cluster was deployed.

## What you learned

- Trace desired replicas to selected ready endpoints.
- Separate startup, readiness and liveness failure actions.
- Review rollout and data durability beyond container count.
