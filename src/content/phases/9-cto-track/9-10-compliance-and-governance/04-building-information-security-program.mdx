## Why this matters

Most early-stage technology companies have security practices — MFA here, a password manager there, maybe a VPN. They do not have a security program. The difference matters when something goes wrong. Security practices are ad hoc responses to specific threats. A security program is a systematic approach to identifying risks, implementing controls proportionate to those risks, monitoring whether controls are working, and improving continuously. The first time a customer's security team sends you a 200-question vendor assessment, or the first time you experience a breach and need to demonstrate what your security posture was, the gap between "practices" and "program" becomes very expensive.

The CTO who builds a security program early — before the first enterprise deal, before the first breach, before the first compliance audit — discovers that the program pays for itself multiple times over. Common controls satisfy multiple frameworks simultaneously: the access review process you build for SOC 2 also satisfies ISO 27001 and GDPR. The incident response plan you write for your cyber insurance application also satisfies SOC 2's availability criteria. A well-designed program is not duplicated work per framework — it is one coherent system that generates evidence for every framework as a side effect.

## The anatomy of an information security program

A security program is not a collection of policies. It is a risk management system. Every element of the program exists to identify risks, reduce them to an acceptable level, and demonstrate that they are being managed. The structure maps to a continuous cycle:

**1. Risk identification** — What could go wrong, and how badly?

**2. Risk assessment** — How likely is each risk, and how severe would the impact be?

**3. Control selection** — Which controls reduce risk to an acceptable level?

**4. Control implementation** — Are the controls actually operating?

**5. Monitoring and metrics** — Are controls working? Is the risk landscape changing?

**6. Improvement** — What gaps did monitoring reveal? How do we close them?

> **An information security program is just risk management with receipts: you identify what you are worried about, show what you are doing about it, and prove it is working.**

## Building the risk register

The risk register is the foundation of the program. It is a living document — or, better, a tracked database — that maps identified risks to their likelihood, impact, current controls, and residual risk after controls are applied.

```typescript
// Risk Register data model
// The risk register is a living inventory of what you are worried about
// and what you are doing about it. It drives control prioritization,
// audit evidence, and board reporting.

interface Risk {
  id: string;
  category: RiskCategory;
  title: string;
  description: string;

  // Inherent risk: the risk if NO controls existed
  // Scored 1-5 on both axes; multiply for overall score
  inherentLikelihood: 1 | 2 | 3 | 4 | 5; // 1=rare, 5=almost certain
  inherentImpact: 1 | 2 | 3 | 4 | 5; // 1=negligible, 5=catastrophic

  // Current controls: what we are doing today to reduce this risk
  controls: SecurityControl[];

  // Residual risk: the risk AFTER controls are applied
  residualLikelihood: 1 | 2 | 3 | 4 | 5;
  residualImpact: 1 | 2 | 3 | 4 | 5;

  // Risk response strategy
  response: "mitigate" | "accept" | "transfer" | "avoid";
  acceptanceRationale?: string; // Required if response = "accept"

  // Ownership and review
  owner: string;
  lastReviewedAt: Date;
  nextReviewDue: Date;
}

type RiskCategory =
  | "access-control"
  | "data-breach"
  | "third-party"
  | "availability"
  | "insider-threat"
  | "physical"
  | "supply-chain"
  | "regulatory";

interface SecurityControl {
  id: string;
  name: string;
  type: "preventive" | "detective" | "corrective";
  automationLevel: "manual" | "partial" | "automated";
  // Which compliance frameworks does this control satisfy?
  // Design controls to satisfy multiple frameworks simultaneously
  satisfiesFrameworks: string[]; // ["SOC2-CC6.1", "ISO27001-A.9.4", "GDPR-Art.32"]
  lastTestedAt: Date;
  testResult: "passed" | "failed" | "not-tested";
}

// Example: populate the register for a common high-risk scenario
const credentialBreachRisk: Risk = {
  id: "RISK-007",
  category: "access-control",
  title: "Credential compromise leading to unauthorized production access",
  description:
    "An attacker obtains valid credentials for a production system through " +
    "phishing, credential stuffing, or dark web purchase of leaked credentials, " +
    "gaining access to production data.",

  // Without MFA, a single credential leak gives full access — high likelihood, catastrophic impact
  inherentLikelihood: 4,
  inherentImpact: 5,

  controls: [
    {
      id: "CTRL-001",
      name: "MFA enforcement on all production access",
      type: "preventive",
      automationLevel: "automated",
      // One control, three frameworks — this is the efficiency gain of common controls
      satisfiesFrameworks: ["SOC2-CC6.1", "ISO27001-A.9.4.2", "NIST-IA-5"],
      lastTestedAt: new Date("2026-04-01"),
      testResult: "passed",
    },
    {
      id: "CTRL-014",
      name: "Privileged access workstations for production access",
      type: "preventive",
      automationLevel: "partial",
      satisfiesFrameworks: ["SOC2-CC6.6", "ISO27001-A.9.4.4"],
      lastTestedAt: new Date("2026-03-15"),
      testResult: "passed",
    },
    {
      id: "CTRL-022",
      name: "AWS GuardDuty anomaly detection on API calls",
      type: "detective",
      automationLevel: "automated",
      satisfiesFrameworks: ["SOC2-CC7.2", "ISO27001-A.16.1.2"],
      lastTestedAt: new Date("2026-04-10"),
      testResult: "passed",
    },
  ],

  // MFA + anomaly detection reduces this significantly
  residualLikelihood: 2,
  residualImpact: 4,

  response: "mitigate",
  owner: "ciso@company.com",
  lastReviewedAt: new Date("2026-04-15"),
  nextReviewDue: new Date("2026-07-15"),
};

// Risk score calculation: multiply likelihood × impact
function riskScore(likelihood: number, impact: number): number {
  return likelihood * impact;
}

function riskTier(score: number): "critical" | "high" | "medium" | "low" {
  if (score >= 20) return "critical";
  if (score >= 12) return "high";
  if (score >= 6) return "medium";
  return "low";
}

const inherentScore = riskScore(
  credentialBreachRisk.inherentLikelihood,
  credentialBreachRisk.inherentImpact
);
// 4 × 5 = 20: critical inherent risk

const residualScore = riskScore(
  credentialBreachRisk.residualLikelihood,
  credentialBreachRisk.residualImpact
);
// 2 × 4 = 8: medium residual risk after controls

console.log(`Inherent: ${inherentScore} (${riskTier(inherentScore)})`);
console.log(`Residual: ${residualScore} (${riskTier(residualScore)})`);
console.log(`Risk reduction: ${Math.round((1 - residualScore / inherentScore) * 100)}%`);
```

## Common controls: one implementation, multiple frameworks

The most expensive mistake in compliance program design is treating each framework as a separate implementation effort. SOC 2 requires quarterly access reviews. ISO 27001 requires access reviews. GDPR requires you to verify that only authorized personnel access personal data. These are not three separate requirements — they are one requirement with three auditors.

A common control is a control designed to satisfy multiple frameworks simultaneously. Every control you add to your program should be evaluated for cross-framework coverage. The engineering cost of implementing a control is largely fixed; the compliance return scales with the number of frameworks it satisfies.

| Control                               | SOC 2 | ISO 27001 | GDPR         | HIPAA              |
| ------------------------------------- | ----- | --------- | ------------ | ------------------ |
| MFA on all production access          | CC6.1 | A.9.4.2   | Art. 32      | §164.312(d)        |
| Quarterly access reviews              | CC6.3 | A.9.2.5   | Art. 5(1)(f) | §164.308(a)(3)     |
| Audit logging with 12-month retention | CC7.2 | A.12.4    | Art. 30      | §164.312(b)        |
| Encryption at rest (AES-256)          | CC6.7 | A.10.1    | Art. 32      | §164.312(a)(2)(iv) |
| Vendor security review                | CC9.2 | A.15.2    | Art. 28      | §164.308(b)        |
| Security awareness training (annual)  | CC1.4 | A.7.2.2   | Art. 39      | §164.308(a)(5)     |
| Incident response plan and testing    | CC7.5 | A.16.1    | Art. 33-34   | §164.308(a)(6)     |
| Penetration testing (annual)          | CC4.1 | A.14.2.8  | Art. 32      | §164.308(a)(8)     |

When building your program, start from this cross-framework view. Implement each control once, configure it to generate evidence that satisfies every applicable framework, and map the evidence artifacts to each framework's specific requirement.

## Scaling the security program

The right security program structure depends on company stage. Hiring a CISO for a 30-person startup is the wrong investment. Not having a CISO function at a 500-person company handling healthcare data is a governance failure.

```python
# Security program maturity model
# Maps company characteristics to appropriate security investments.
# Use this as a calibration tool, not a rigid formula.

from dataclasses import dataclass, field
from typing import Optional

@dataclass
class CompanyProfile:
    headcount: int
    annual_revenue_usd: int
    handles_sensitive_data: bool       # PHI, PCI, government data
    enterprise_customers: int          # Customers with security review requirements
    public_company: bool

@dataclass
class SecurityProgramLevel:
    level: str
    description: str
    security_headcount: str
    key_investments: list[str]
    frameworks_typically_pursued: list[str]
    board_reporting_cadence: str

def recommend_security_program(company: CompanyProfile) -> SecurityProgramLevel:
    """
    Returns a calibrated security program recommendation.
    These are starting points; adjust based on threat model and industry.
    """

    # Level 1: Startup (<50 employees, <$5M ARR)
    # Security is a part-time function owned by CTO or senior engineer.
    if company.headcount < 50 and company.annual_revenue_usd < 5_000_000:
        return SecurityProgramLevel(
            level="Emerging",
            description="Security fundamentals owned by CTO or designated senior engineer",
            security_headcount="0.5 FTE (embedded in engineering)",
            key_investments=[
                # Foundation that everything else builds on
                "SSO + MFA enforcement across all tools (Okta, Google Workspace)",
                "Endpoint management (MDM) for all company devices",
                # Needed for first enterprise deals
                "SOC 2 Type I readiness (target: 6 months after founding)",
                # Qualifies for meaningful cyber insurance
                "Basic incident response runbook",
                # Required for any significant enterprise deals
                "Annual security awareness training for all staff",
            ],
            frameworks_typically_pursued=["SOC 2 Type I → Type II"],
            board_reporting_cadence="Quarterly summary in board deck",
        )

    # Level 2: Growth (50-200 employees, $5M-$50M ARR)
    # First dedicated security hire, typically a Security Engineer or Lead.
    elif company.headcount < 200 and company.annual_revenue_usd < 50_000_000:
        return SecurityProgramLevel(
            level="Developing",
            description="Dedicated security function, reporting to CTO",
            security_headcount="1-2 FTE (Security Engineer + vendor tools)",
            key_investments=[
                "SIEM/SOAR platform for centralized log analysis and alerting",
                # Production access management becomes complex at this size
                "Privileged access management (PAM) system",
                "Annual third-party penetration test",
                # First enterprise customers require this
                "Formal vendor risk assessment process",
                # Required for most healthcare/financial deals
                "SOC 2 Type II achieved",
                # Bug bounty signals maturity to enterprise security teams
                "Vulnerability disclosure policy (private bug bounty program)",
            ],
            frameworks_typically_pursued=["SOC 2 Type II", "ISO 27001 if EU customers require it"],
            board_reporting_cadence="Quarterly dedicated security update to audit committee",
        )

    # Level 3: Scale (200+ employees or >$50M ARR or sensitive data or public)
    # CISO as distinct leadership role, security team, formal GRC function.
    else:
        return SecurityProgramLevel(
            level="Mature",
            description="CISO + security team, formal GRC, board-level security committee",
            security_headcount="1 CISO + 3-8 FTE depending on size and industry",
            key_investments=[
                "Full security operations center (in-house or managed SOC)",
                "Comprehensive third-party risk management program",
                "Red team exercises (adversarial simulation, not just pen tests)",
                # Required for public companies
                "SOX security controls if publicly traded",
                # Required for significant healthcare/government revenue
                "HITRUST, FedRAMP, or sector-specific certifications",
                # Board oversight of cybersecurity risk (SEC requirement for public cos)
                "Dedicated board security committee or audit committee charter update",
                "Cyber insurance policy >$20M with reviewed coverage terms",
            ],
            frameworks_typically_pursued=[
                "SOC 2 Type II", "ISO 27001", "HITRUST or FedRAMP as applicable", "SOX"
            ],
            board_reporting_cadence="Monthly to security committee, quarterly to full board",
        )


# Security program metrics: what you report to the board
# Good metrics answer: "Is our security posture improving or degrading?"
# Bad metrics: things that always look fine (patching rate when you never track vulnerabilities)

security_metrics = {
    # How fast do we find problems?
    "mean_time_to_detect_days": {
        "description": "Average days from incident occurrence to detection",
        "target": "< 1 day for critical, < 7 days for high",
        "red_flag": "> 30 days (industry average is still ~200 days — beating this is table stakes)",
        "data_source": "SIEM incident timestamps",
    },
    # How fast do we fix them?
    "mean_time_to_respond_hours": {
        "description": "Average hours from detection to containment for critical incidents",
        "target": "< 4 hours critical, < 24 hours high",
        "red_flag": "> 48 hours for critical incidents",
        "data_source": "Incident response ticketing system",
    },
    # Are we staying current?
    "critical_patch_sla_compliance": {
        "description": "% of critical/high CVEs patched within defined SLA (e.g., 7 days critical, 30 days high)",
        "target": "> 95%",
        "red_flag": "< 80% (unpatched critical CVEs are the most common breach entry point)",
        "data_source": "Vulnerability scanner (Qualys, Rapid7, Wiz)",
    },
    # Is access hygiene being maintained?
    "access_review_coverage": {
        "description": "% of in-scope systems with completed quarterly access review",
        "target": "100%",
        "red_flag": "Any miss — a single uncompleted access review is a SOC 2 finding",
        "data_source": "GRC platform or access review audit log",
    },
    # Are people aware?
    "phishing_simulation_click_rate": {
        "description": "% of staff who click simulated phishing links",
        "target": "< 5% after training program is mature",
        "red_flag": "> 20% (humans are the most exploited attack surface)",
        "data_source": "Security awareness platform (KnowBe4, Proofpoint)",
    },
    # Are we reducing the attack surface?
    "vendor_risk_review_coverage": {
        "description": "% of vendors processing sensitive data with a completed security review",
        "target": "> 90%",
        "red_flag": "< 70% (supply chain attacks increasingly target vendors, not companies directly)",
        "data_source": "Vendor risk management platform or spreadsheet tracker",
    },
}

# Example usage
profile = CompanyProfile(
    headcount=85,
    annual_revenue_usd=12_000_000,
    handles_sensitive_data=True,  # healthcare data
    enterprise_customers=12,
    public_company=False,
)

recommendation = recommend_security_program(profile)
print(f"Security Program Level: {recommendation.level}")
print(f"Description: {recommendation.description}")
print(f"Staffing: {recommendation.security_headcount}")
print(f"\nKey investments:")
for inv in recommendation.key_investments:
    print(f"  • {inv}")
print(f"\nBoard reporting: {recommendation.board_reporting_cadence}")
```

## The incident response plan

Every security program needs an incident response plan before the first incident, not after. The plan does not need to anticipate every scenario. It needs to answer: who decides what, in what order, with what communication, within what timeframe.

The five phases every IRP must cover:

1. **Preparation** — Training, tooling, contact lists, legal counsel on retainer, cyber insurance policy reviewed
2. **Detection and analysis** — How do we know something happened? What makes it a "declared incident"? Who is the incident commander?
3. **Containment** — Stop the bleeding. Isolate affected systems. Preserve forensic evidence.
4. **Eradication and recovery** — Remove the attacker/malware. Restore from known-good backups. Verify integrity before going live.
5. **Post-incident review** — What happened? What would have caught it earlier? What controls do we add?

The most common failure in incident response is the "hero problem": one engineer who knows all the systems and makes all the decisions. When they are unavailable (asleep, sick, on vacation, overwhelmed), the response collapses. The IRP must be a document that a competent engineer who was not in the original incident could execute.

## What you learned

- A security program is a risk management system, not a collection of policies: it identifies risks, implements controls proportionate to residual risk, monitors effectiveness, and improves continuously through a structured cycle
- Risk registers quantify inherent risk (before controls) and residual risk (after controls) using likelihood × impact scoring; residual risk must fall within a defined organizational tolerance threshold — ad hoc acceptance of high-risk items is a governance failure
- Common controls designed to satisfy multiple frameworks simultaneously (SOC 2, ISO 27001, GDPR, HIPAA) eliminate redundant compliance work — quarterly access reviews, audit logging, and encryption at rest satisfy all four frameworks with a single implementation
- Security program maturity and staffing should be calibrated to company stage: a 30-person startup needs SSO, MDM, and SOC 2 readiness — not a CISO; a 500-person company handling healthcare data needs a CISO, a security team, and formal GRC
- Key security metrics for board reporting are operational (MTTD, MTTR, patch SLA compliance, access review coverage) — they measure whether the program is working, not whether it exists

Compliance and governance is not a destination you arrive at — it is a continuous practice that scales with your organization, your customer base, and the regulatory landscape that governs both.
