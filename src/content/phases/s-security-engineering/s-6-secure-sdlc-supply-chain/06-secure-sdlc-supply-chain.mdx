## Why this lesson exists

You can write flawless application code and still ship a backdoor. In March 2024, maintainer-level access to the `xz` compression library (`liblzma`) was used to plant a backdoor that targeted OpenSSH on many Linux systems — tracked as <VocabTooltip slug="cve">CVE</VocabTooltip>-2024-3094. The malicious code was not in any application's own source. It rode in through a dependency, hidden in test fixtures and a release tarball that differed from the public git history. A developer who reviewed only their own diffs would never have seen it.

That is the shape of the modern problem. The attack surface is no longer only _your code_ — it is every package you pull, every build step that runs, and every artifact you publish. This lesson covers the controls that defend the path from a developer's commit to a running binary: the scanners that gate the pipeline, the dependency risks that scanners miss, the inventory (SBOM) that lets you answer "am I affected" in minutes instead of days, and the signing and provenance that prove a binary is the one you actually built.

## First principles: the pipeline is the attack surface

Picture the path your code takes to production as a relay race. A developer commits source. A build server pulls dependencies and compiles. An artifact (a container image, a `.jar`, a binary) is produced. Something deploys it. At every handoff, someone could substitute a different baton and the next runner would never notice — unless each handoff is checked.

A <VocabTooltip slug="secure-sdlc">secure SDLC</VocabTooltip> (Software Development Life Cycle) is the discipline of putting a check at every handoff. The <VocabTooltip slug="ssdf">SSDF</VocabTooltip> — NIST's Secure Software Development Framework, published as **SP 800-218** — names those checks and groups them. It is not a tool; it is a vocabulary of practices that any toolchain can satisfy. Its four practice groups:

- **PO — Prepare the Organization.** Define security requirements, roles, and a toolchain _before_ writing code.
- **PS — Protect the Software.** Protect code and artifacts from tampering (access control, signing, integrity verification).
- **PW — Produce Well-Secured Software.** Design, review, test, and configure software to reduce vulnerabilities (this is where SAST/DAST/code review live).
- **RV — Respond to Vulnerabilities.** Find, assess, and remediate vulnerabilities after release — including in dependencies.

Keep these four letters in mind. Every concrete control below maps to one of them, and at the end you will wire them into a pipeline.

## The mental model

> A secure SDLC is a set of **gates on a conveyor belt**. Code rides the belt from commit to production. Each gate inspects a different property — your code, your dependencies, your running app, your artifact's origin — and a gate that fails stops the belt. No single gate is sufficient; the security comes from the belt, not from any one inspector.

Hold that picture. SAST, DAST, SCA, IAST, SBOM generation, and signing are all gates. The rest of the lesson is what each gate inspects and where it sits.

## The four scanners — what each one can and cannot find

The single most common mistake is treating "we run a security scanner" as one checkbox. There are four distinct scanner classes, and they find _disjoint_ categories of problems. Confusing them leaves real gaps.

| Scanner                                       | Full name                                | Sees                                                    | Finds                                                                            | Misses                                                                    |
| --------------------------------------------- | ---------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| <VocabTooltip slug="sast">SAST</VocabTooltip> | Static Application Security Testing      | Your source code, not running                           | Code-level flaws: SQL injection sinks, hardcoded secrets, unsafe deserialization | Anything that only appears at runtime or in config; flaws in dependencies |
| <VocabTooltip slug="dast">DAST</VocabTooltip> | Dynamic Application Security Testing     | A running instance, from outside (black-box)            | Runtime/config flaws: missing security headers, auth bypass, reflected XSS       | Code paths it never exercises; root cause (only sees symptoms)            |
| <VocabTooltip slug="sca">SCA</VocabTooltip>   | Software Composition Analysis            | Your dependency tree                                    | Known-vulnerable dependency versions (matched to CVE databases); license risk    | Zero-days; a malicious dependency with no published CVE yet               |
| <VocabTooltip slug="iast">IAST</VocabTooltip> | Interactive Application Security Testing | Your app from the inside, instrumented, while tests run | Runtime flaws with code-level root cause (fewer false positives than DAST)       | Code paths your test suite never triggers                                 |

The intuition that ties them together: **SAST reads the recipe, DAST tastes the dish, SCA checks the ingredients' recall notices, IAST watches the kitchen while it cooks.** You want all four because a poisoned ingredient (SCA) is invisible to someone reading the recipe (SAST), and a recipe flaw (SAST) may never surface in the one dish you tasted (DAST).

A concrete SAST example — the kind of finding a static scanner catches before the code ever runs:

```python
# VULNERABLE: user input concatenated into SQL — SAST flags this as a
# tainted-data-to-SQL-sink path (CWE-89, SQL Injection / OWASP A03:2021).
def find_user(conn, username):
    query = "SELECT * FROM users WHERE name = '" + username + "'"
    return conn.execute(query).fetchall()

# FIXED: parameterized query — the driver sends data and SQL separately,
# so the username can never be parsed as SQL. The taint path is broken,
# and the SAST finding clears.
def find_user(conn, username):
    query = "SELECT * FROM users WHERE name = ?"
    return conn.execute(query, (username,)).fetchall()
```

A SAST gate fails the build on the first version and passes the second. But notice what SAST cannot tell you: whether the `sqlite3` driver you imported carries a _known_ vulnerability of its own. Checking your dependencies against published vulnerability databases is SCA's job — and dependencies are where supply-chain risk concentrates. (As the next sections show, SCA catches the _known_-bad case; a freshly poisoned release with no CVE yet slips past it, which is why pinning and provenance also matter.)

## Where the danger actually concentrates: dependency risk

Your own code is a small fraction of what ships. A typical Node or Python service pulls in hundreds of transitive packages. Each is code you execute but did not write or review. Three attack classes dominate.

**1. Typosquatting.** An attacker publishes a package whose name is a near-miss of a popular one — <VocabTooltip slug="typosquatting">typosquatting</VocabTooltip>. A developer types `reqeusts` instead of `requests`, or `python3-dateutil` instead of `python-dateutil`, and installs hostile code. The defense is not vigilance (people mistype); it is pinning and review (below).

**2. Compromised maintainer / compromised dependency.** A legitimate, widely-used package is taken over and a malicious version published. Two canonical incidents:

- **event-stream (2018).** A popular npm package's maintainer handed the project to a volunteer who quietly added a dependency, `flatmap-stream`, containing code that targeted a specific cryptocurrency wallet app. Millions of downloads shipped the payload before discovery.
- **xz / liblzma (2024, CVE-2024-3094).** A maintainer built up over ~2 years inserted a backdoor into the release artifacts of a core compression library, targeting sshd. It was caught by a Postgres engineer noticing a half-second latency anomaly — not by any scanner.

The lesson from both: **a malicious version often has no CVE at the moment it ships.** SCA, which matches versions against known-vulnerability databases, is blind to a brand-new poisoned release. This is why provenance and signing (later sections) matter — they let you verify _where a build came from_, not merely _whether it's on a blocklist_.

**3. Dependency confusion.** If your build resolves package names against both a public registry and a private one, an attacker who publishes a package with your internal name (`acme-internal-auth`) at a _higher version number_ on the public registry can get your build to pull theirs instead. This is <VocabTooltip slug="dependency-confusion">dependency confusion</VocabTooltip>, disclosed publicly in 2021. The defense is explicit registry scoping and pinning — never let name resolution silently prefer the public source for a private name.

The unifying defense across all three is the <VocabTooltip slug="pinned-dependency">pinned dependency</VocabTooltip>: lock the exact version _and_ a cryptographic hash of its contents, so the resolver installs the exact bytes you reviewed and nothing else.

```bash
# A pinned, hash-checked install. The lockfile records both the version
# AND the SHA-256 of each artifact. If a registry serves different bytes
# for the same version, the hash check fails and the install aborts —
# this is what would have stopped a swapped artifact.

# Python (pip): require hashes for every package; a mismatch is fatal.
pip install --require-hashes -r requirements.txt

# requirements.txt entry produced by `pip-compile --generate-hashes`:
#   requests==2.32.3 \
#       --hash=sha256:70761cfe03c773ceb22aa2f671b4757976145175cdfca038c02654d061d6dcc6
```

Pinning does not prove a package is _safe_ — it proves it is the _same_ as what you reviewed. Those are different guarantees, and conflating them is a common error.

## Knowing what you ship: the SBOM

When the next xz-class vulnerability drops at 2 a.m., the only question that matters is: **"Are we running it, and where?"** If your answer is "let me grep every repo for a week," you are already losing. A <VocabTooltip slug="sbom">SBOM</VocabTooltip> — Software Bill of Materials — is the inventory that answers that question in seconds. It is a machine-readable list of every component in a build: name, version, hash, license, and supplier.

Two open standards dominate:

- <VocabTooltip slug="cyclonedx">**CycloneDX**</VocabTooltip> — an OWASP project, security-first,
  with first-class support for vulnerability and dependency-relationship data.
- <VocabTooltip slug="spdx">**SPDX**</VocabTooltip> — an ISO/IEC 5962 standard, originally
  license-focused, broadly used in compliance contexts.

Either is acceptable; the SSDF (practice PS.3) calls for producing one. Generate a CycloneDX SBOM with the open-source `syft` tool:

```bash
# Generate a CycloneDX SBOM (JSON) for a built container image.
# This is a PRODUCE step — run it in CI right after the artifact is built,
# and store the SBOM as a build output alongside the artifact.
syft acme/payments-api:1.4.2 -o cyclonedx-json > sbom.cdx.json

# Later — when a new CVE lands — scan the STORED SBOM, not a live rebuild.
# You can answer "are we affected" against last week's release in seconds.
grype sbom:./sbom.cdx.json
```

What an SBOM proves and does not prove, stated plainly:

- It **proves** what components were present in a build, so you can answer impact questions fast (this is the RV — Respond to Vulnerabilities — payoff).
- It does **not** prove those components are safe, nor that the artifact you are running matches the SBOM. An SBOM is an _inventory_, not a _guarantee_. The integrity link — "this SBOM describes this exact artifact" — comes from signing.

## Proving where a binary came from: signing and provenance

A signature answers "was this artifact tampered with after the publisher signed it?" <VocabTooltip slug="build-provenance">Build provenance</VocabTooltip> answers a deeper question: "what source, what builder, and what inputs produced this artifact?" You want both.

<VocabTooltip slug="sigstore">**Sigstore**</VocabTooltip> is an open-source project (a Linux
Foundation effort) that makes <VocabTooltip slug="artifact-signing">artifact signing</VocabTooltip>
practical without every developer managing long-lived private keys. Its CLI,
<VocabTooltip slug="cosign">**cosign**</VocabTooltip>, supports "keyless" signing: instead of a
stored key, it uses a short-lived certificate bound to an OIDC identity — OIDC (OpenID Connect) is
the standard that lets one system prove "this request really is the GitHub Actions workflow it
claims to be," so the signer's identity is the CI job itself, not a developer holding a key — and
records the signature in a public transparency log (Rekor, Sigstore's append-only ledger) so it can
be audited later.

```bash
# Sign a container image keyless — identity comes from the CI OIDC token,
# not a developer-held key. The signature is recorded in the Rekor
# transparency log so anyone can later confirm it was issued.
# (cosign v2+ makes keyless the default; the old COSIGN_EXPERIMENTAL=1
#  flag was removed and is no longer needed.)
cosign sign \
  --yes \
  registry.acme.io/payments-api@sha256:9f86d0818...   # sign the digest, NOT a tag

# Verify, asserting WHO signed and from WHICH workflow. A signature alone
# is not enough — you must pin the expected identity, or any valid signer
# would pass. This is the check a deploy gate runs before admitting an image.
cosign verify \
  --certificate-identity \
    "https://github.com/acme/payments-api/.github/workflows/release.yml@refs/heads/main" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  registry.acme.io/payments-api@sha256:9f86d0818...
```

Two non-obvious points are load-bearing here. First, you always sign and verify a **digest** (`@sha256:...`), never a mutable tag like `:latest` — a tag can be repointed at a different image after signing, which would defeat the whole exercise. Second, verification must assert the **expected signer identity and issuer**; checking only that "some signature exists" lets any attacker who can sign _anything_ pass the gate.

Provenance goes one step further than a signature. With cosign you can attach a signed **attestation** — a statement, in the in-toto format, describing how the artifact was built (source repo, commit, builder). The verifier then checks not only "this was signed" but "this was built from the commit and pipeline we expect."

## SLSA: a ladder for build integrity

<VocabTooltip slug="slsa">**SLSA**</VocabTooltip> ("Supply-chain Levels for Software Artifacts,"
pronounced "salsa") is a framework that turns "is our build trustworthy?" into discrete, checkable
levels. In **SLSA v1.0**, the **Build track** defines three levels (there is no L0 control; L0 only
means "no guarantees"):

| Level        | Requirement                                                                                                                         | What it guarantees                                                                                                                  |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Build L1** | The build process is scripted/automated and generates **provenance** describing how the artifact was built.                         | Consumers can see how it was built — but the provenance is not yet tamper-resistant. Stops accidental/ad-hoc builds.                |
| **Build L2** | Provenance is **signed**, and the build runs on a **hosted build platform** (not a developer laptop).                               | The provenance can be authenticated; a developer cannot silently forge it on their own machine.                                     |
| **Build L3** | The build platform provides **hardened, isolated builds** where the signing material is not accessible to user-defined build steps. | Even a malicious build script cannot forge provenance or exfiltrate the signing key. Defends against a compromised build _process_. |

The practical reading: each level closes off a class of "the build itself lied to you" attacks. L1 says "we wrote down how we built it." L2 says "and you can trust that record came from our real build system." L3 says "and not even our own build steps could have faked that record." A project moves up a level by adopting one concrete control — most commonly, moving builds onto a hosted platform that emits signed, isolated provenance (for example, the SLSA GitHub generator).

SLSA does not replace SAST/DAST/SCA. Those gates inspect the _software_; SLSA inspects the _build process that produced it_. Both are in scope for a secure SDLC; SLSA is the part the four scanners cannot see.

## Putting it together: a gated CI pipeline

Here is a defensive pipeline that maps each step to an SSDF practice group. This is the synthesis — the conveyor belt with all its gates, in the order they run.

```yaml
# .github/workflows/secure-build.yml
# A defensive CI pipeline. Each gate maps to a NIST SSDF (SP 800-218)
# practice group, noted in comments. A failed gate stops the belt.
name: secure-build
on:
  push:
    branches: [main]

jobs:
  build-and-verify:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      id-token: write # PS: needed for keyless cosign / OIDC provenance
      packages: write
    steps:
      - uses: actions/checkout@v4

      # PW.7 — SAST: scan our own source for code-level flaws. Fail on findings.
      - name: SAST (Semgrep)
        run: semgrep ci --error # non-zero exit fails the build

      # PW.4 / RV.1 — SCA: scan dependencies for KNOWN-vulnerable versions.
      - name: SCA (dependency vulnerabilities)
        run: grype dir:. --fail-on high

      # PS.1 — pinned, hash-verified install: install exactly the reviewed bytes.
      - name: Install (hash-pinned)
        run: pip install --require-hashes -r requirements.txt

      - name: Build image
        run: docker build -t registry.acme.io/payments-api:${{ github.sha }} .

      # PS.3 — SBOM: produce the inventory and keep it as a build output.
      - name: Generate SBOM (CycloneDX)
        run: syft registry.acme.io/payments-api:${{ github.sha }} -o cyclonedx-json > sbom.cdx.json

      # PS.2 — sign the artifact + attach build provenance (moves toward SLSA L2+).
      - name: Sign image and attest provenance
        run: |
          IMG=$(docker inspect --format='{{index .RepoDigests 0}}' registry.acme.io/payments-api:${{ github.sha }})
          cosign sign --yes "$IMG"
          cosign attest --yes --predicate sbom.cdx.json --type cyclonedx "$IMG"

  dast:
    # PW.8 — DAST: scan a RUNNING instance from the outside. Separate job
    # because it needs the app deployed to an ephemeral test environment.
    needs: build-and-verify
    runs-on: ubuntu-latest
    steps:
      - name: DAST (OWASP ZAP baseline)
        run: zap-baseline.py -t https://payments-api.test.acme.io
```

Read the mapping: SAST and DAST are **PW** (produce well-secured software), SCA spans **PW/RV**, pinned install + signing + SBOM are **PS** (protect the software), and the whole automated, scripted pipeline plus its emitted provenance is what earns SLSA Build L1/L2. The structure — not any single tool — is the security.

## What you learned

- **The four scanners find disjoint problems.** SAST reads your source, DAST tests a running instance, SCA checks dependencies against known-vulnerability databases, and IAST instruments the app during tests. You need all four because each is blind to what the others catch.
- **Dependency risk is where breaches concentrate.** Typosquatting, compromised maintainers (event-stream, xz / CVE-2024-3094), and dependency confusion all ship hostile code that has no CVE at the moment it lands — so blocklist-based SCA cannot see it. Pinning to a reviewed version plus a content hash is the structural defense.
- **An SBOM is an inventory, not a guarantee.** A CycloneDX or SPDX bill of materials lets you answer "are we affected, and where" in seconds when the next vulnerability drops; it does not prove the components are safe or that the artifact matches the list.
- **Signing proves integrity; provenance proves origin.** cosign (Sigstore) signs artifacts — always by digest, with the signer identity pinned on verify — and attestations describe how the artifact was built. SLSA Build L1–L3 turns "trust the build" into checkable levels, each closing off a class of build-process attacks.
- **The SSDF (SP 800-218) is the map.** PO/PS/PW/RV name where each gate belongs, and a real CI pipeline wires SAST, SCA, pinned installs, SBOM, signing, and DAST into one belt where a failed gate stops the line.

## Connect forward

You can now harden the path from commit to running binary. But controls that pass in CI can still be evaded in production, and even a perfectly gated pipeline produces an artifact that eventually gets attacked.
