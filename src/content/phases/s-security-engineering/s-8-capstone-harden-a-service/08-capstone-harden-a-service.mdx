## Why this lesson exists

You will almost never write a secure service from a blank file. You will inherit one. Someone shipped it under deadline, it works, it has users — and it has a broken access-control check on the orders endpoint, a string-concatenated SQL query, passwords stored as unsalted SHA-256, plaintext session cookies over HTTP, and no logs that would tell you an attacker ever showed up. Your job is to harden it without rewriting it, and to prove what you did to someone who will audit the claim.

This is the capstone of Phase S. Across s-1 through s-7 you built the parts: structured threat modeling, the OWASP Top 10 as vulnerable-code-to-fix, authentication and session security, applied cryptography, transport security, the secure SDLC, and detection plus incident response. Here you assemble them on one deliberately-vulnerable service. You will threat-model it, remediate each finding to a specific OWASP ASVS requirement, harden the authentication and crypto, stand up a detection rule, write an incident-response runbook, document the residual risk against NIST CSF 2.0, then bundle the package, hash it, and anchor it via DURA `/verify` so the artifact is auditable. The framing is defensive throughout: every technique here is something a defender does to their own system.

## The first-principles picture

Security is not a feature you add. It is a property you argue for. The argument has a fixed shape, and it is the same shape every credible engagement uses.

First you decide what you are protecting and from whom. A <VocabTooltip slug="threat-model">threat model</VocabTooltip> is the structured answer to "what can go wrong here?" — produced before you touch code, because a fix you can't trace back to a threat is a fix you can't justify spending time on. You draw a <VocabTooltip slug="data-flow-diagram">data-flow diagram</VocabTooltip> (the processes, data stores, and the data moving between them), mark the <VocabTooltip slug="trust-boundary">trust boundaries</VocabTooltip> (the lines where data crosses from less-trusted to more-trusted territory — the browser-to-server edge, the server-to-database edge), and walk each element asking the six STRIDE questions.

Then you find the concrete weaknesses. The <VocabTooltip slug="attack-surface">attack surface</VocabTooltip> is the set of points an outsider can poke — every endpoint, every input, every dependency. The OWASP Top 10 names the categories of weakness you find there, and OWASP ASVS names the _verifiable requirements_ a fix must satisfy. "I added a check" is a hope; "this endpoint now satisfies ASVS V4.1.1 — it enforces access control at a trusted server-side chokepoint" is a claim an auditor can test.

Then you watch. A control you can't see being bypassed is a control you can't trust. You emit <VocabTooltip slug="security-logging">security logs</VocabTooltip>, write a <VocabTooltip slug="detection-rule">detection rule</VocabTooltip> mapped to a known adversary technique in <VocabTooltip slug="mitre-attck">MITRE ATT&CK</VocabTooltip>, and write the <VocabTooltip slug="incident-response-runbook">runbook</VocabTooltip> the responder follows when it fires.

Finally you are honest about what you did _not_ fix. No service is fully secure; every engagement ends with <VocabTooltip slug="residual-risk">residual risk</VocabTooltip> — the risk that remains after your controls are in place — documented so the owner accepts it with open eyes rather than discovering it in an incident.

## The mental model

> **Hardening is a chain of justified claims: a threat model points at findings, each finding is remediated to a named verifiable requirement, each control is watched by a detection, and what you couldn't fix is written down as accepted residual risk.** Every artifact in your bundle is a link in that chain. A reviewer follows the chain from "here is what can go wrong" to "here is the exact requirement my fix satisfies" to "here is how I'd see it bypassed" to "here is what I knowingly left open." A fix with no threat behind it, or a threat with no detection in front of it, is a broken link.

Hold that picture. Everything below is one link in the chain, built on the same small vulnerable service.

## The service under test

Keep the target small enough to threat-model on one page. It is a Node/Express order service with three routes, a Postgres store, and password login. The vulnerable starting point (the kind you inherit):

```js
// app.vulnerable.js — the service as inherited. DO NOT ship this.
import express from "express";
import crypto from "node:crypto";
import { pool } from "./db.js";

const app = express();
app.use(express.json());

// LOGIN: passwords hashed with bare SHA-256, no salt, no rate limit.
app.post("/login", async (req, res) => {
  const { email, password } = req.body;
  // CWE-916: fast unsalted hash — trivially cracked from a DB dump.
  const hash = crypto.createHash("sha256").update(password).digest("hex");
  // CWE-89: SQL built by string concatenation — injectable.
  const sql = `SELECT id FROM users WHERE email = '${email}' AND pw = '${hash}'`;
  const { rows } = await pool.query(sql);
  if (rows.length === 0) return res.status(401).json({ error: "bad creds" });
  // Session id is the user id — guessable, no expiry.
  res.json({ session: rows[0].id });
});

// ORDER: returns ANY order by id with no ownership check.
app.get("/orders/:id", async (req, res) => {
  // CWE-639 (IDOR): no check that the caller owns this order.
  const { rows } = await pool.query("SELECT * FROM orders WHERE id = $1", [req.params.id]);
  res.json(rows[0] ?? null);
});

app.listen(8080); // plaintext HTTP on the wire.
```

Five findings live in those twenty lines: unsalted password hashing, SQL injection, a guessable session token, a missing authorization check, and plaintext transport. The rest of the lesson remediates them in the order a real engagement would — threat model first.

## Link 1 — the STRIDE threat model

<VocabTooltip slug="stride">STRIDE</VocabTooltip> is a checklist of six threat categories you apply
to each element of the data-flow diagram. The name is a mnemonic: **S**poofing (pretending to be
someone you are not), **T**ampering (modifying data or code), **R**epudiation (denying you did
something, with no log to prove otherwise), **I**nformation disclosure (leaking data), **D**enial of
service (making the system unavailable), and **E**levation of privilege (gaining rights you should
not have).

The data-flow diagram for the service has three elements and two trust boundaries:

```
[ Browser ] --(1)--> [ Order Service ] --(2)--> [ Postgres ]
   external           process              data store
            ^trust boundary 1     ^trust boundary 2
   (untrusted client → server)  (server → database)
```

Walking STRIDE per element produces the threat list that drives every later fix. The highest-risk entries:

| Element                                   | STRIDE category        | Threat                                                                  | Drives fix                  |
| ----------------------------------------- | ---------------------- | ----------------------------------------------------------------------- | --------------------------- |
| `/login` (process, boundary 1)            | Spoofing               | Credential stuffing / password reuse logs an attacker in as a real user | Argon2id + MFA + rate limit |
| `/login` (process, boundary 1)            | Tampering              | SQL injection via the `email` field rewrites the query                  | Parameterized query         |
| `/orders/:id` (process, boundary 1)       | Elevation of privilege | Any authenticated user reads any order by guessing the id               | Server-side ownership check |
| Browser → Service (data flow, boundary 1) | Information disclosure | Credentials and session token sent in cleartext over HTTP               | TLS 1.3                     |
| Postgres (data store, boundary 2)         | Information disclosure | A DB dump exposes crackable password hashes                             | Argon2id (slow KDF)         |
| `/login` (process)                        | Repudiation            | No log of failed or successful auth — can't reconstruct an incident     | Security logging            |

This table is the spine of the deliverable. Each row is a threat that points at exactly one fix and, later, at one detection. That traceability is what an auditor checks.

## Link 2 — remediate the OWASP findings to ASVS

Three of the findings map cleanly to OWASP Top 10 2021 categories, and each fix is verified against a specific OWASP ASVS 4.0 requirement. You cite the requirement so the claim is testable, not aspirational.

### A01 Broken Access Control → ASVS V4.1

The `/orders/:id` route is an <VocabTooltip slug="insecure-direct-object-reference">insecure direct object reference</VocabTooltip> (IDOR, CWE-639): it exposes an internal object id with no check that the caller is allowed to see _that_ object. This is the most common high-severity web finding, and OWASP ranked <VocabTooltip slug="broken-access-control">Broken Access Control</VocabTooltip> as A01 — the number-one category — in the 2021 Top 10. ASVS V4.1.1 requires access control enforced at a trusted server-side chokepoint; V4.2.1 requires that users cannot access records they do not own by manipulating an identifier.

The fix is a server-side ownership check. The caller's identity comes from the authenticated session — never from a value the client supplies:

```js
// SECURE: ownership enforced server-side from the session, not the URL.
app.get("/orders/:id", requireSession, async (req, res) => {
  // req.userId is set by requireSession from the verified session token.
  // The query filters by BOTH the order id AND the owning user, so an
  // attacker guessing another order's id gets nothing back — the access
  // decision is made by the database row, not by trusting the URL.
  const { rows } = await pool.query("SELECT * FROM orders WHERE id = $1 AND user_id = $2", [
    req.params.id,
    req.userId,
  ]);
  if (rows.length === 0) return res.status(404).json({ error: "not found" });
  res.json(rows[0]);
});
```

Returning `404` rather than `403` is deliberate: a `403` confirms the order exists, which leaks information (a Spoofing/disclosure aid). Denying the existence of records the caller cannot see is the conservative choice.

### A03 Injection → ASVS V5.3

The login query concatenates the `email` string straight into SQL — <VocabTooltip slug="injection">injection</VocabTooltip> (CWE-89). An attacker submitting `email` of `' OR '1'='1' --` rewrites the query's logic. OWASP ranks Injection as A03; ASVS V5.3.4 requires that data-store queries use parameterized interfaces (prepared statements / bound parameters) rather than string concatenation.

The fix is a <VocabTooltip slug="parameterized-query">parameterized query</VocabTooltip> — the driver sends the SQL template and the values on separate channels, so the value can never be parsed as SQL:

```js
// SECURE: parameters are bound, never concatenated. The driver sends the
// query text and the $1/$2 values separately; the database treats the
// values as data only — there is no string for an attacker to break out of.
const { rows } = await pool.query("SELECT id, pw_hash FROM users WHERE email = $1", [email]);
```

Note the rewrite also stops fetching by `pw` in the query at all. With a slow password hash (next section) you cannot match the hash in SQL — you fetch the stored hash by email, then verify the password in the application. That structural change is what the crypto fix demands.

### A02 Cryptographic Failures → ASVS V2.4 (password storage)

Bare SHA-256 is a <VocabTooltip slug="cryptographic-failure">cryptographic failure</VocabTooltip> (CWE-916: use of a password hash with insufficient computational effort). SHA-256 is a _fast_ hash — an attacker with a stolen `users` table can try billions of guesses per second on a GPU. OWASP ranks Cryptographic Failures as A02. The remediation is covered fully in the authn link below; ASVS V2.4.1 requires passwords stored salted and hashed with an approved one-way key-derivation/password-hashing function resistant to offline attacks (ASVS V2.4.3/V2.4.4 name PBKDF2 and bcrypt specifically); Argon2id is the algorithm OWASP's Password Storage Cheat Sheet and NIST guidance recommend first.

## Link 3 — harden authentication and crypto

### Password hashing: Argon2id

<VocabTooltip slug="password-hashing">Password hashing</VocabTooltip> is not encryption and not a
plain hash — it is a deliberately *slow*, *salted* one-way function whose cost you tune so verifying
a real login stays fast for you but mass-guessing stays expensive for an attacker.
<VocabTooltip slug="argon2id">Argon2id</VocabTooltip> won the 2015 Password Hashing Competition and
is memory-hard: it forces each guess to use a configured amount of RAM, which is what defeats cheap
GPU parallelism. It is the algorithm OWASP's Password Storage Cheat Sheet recommends first, and NIST
SP 800-63B requires a salted, memory-hard or iterated function for stored authenticators.

```js
// auth.js
import argon2 from "argon2"; // the `argon2` npm binding to the reference C lib

// OWASP Password Storage Cheat Sheet baseline for Argon2id: type id,
// >= 19 MiB memory, >= 2 iterations, parallelism 1. argon2 stores the
// salt and parameters INSIDE the returned encoded hash string, so there
// is no separate salt column to manage and no chance of reusing a salt.
const ARGON2_OPTS = {
  type: argon2.argon2id,
  memoryCost: 19456, // 19 MiB, in KiB
  timeCost: 2, // iterations
  parallelism: 1,
};

export async function hashPassword(plain) {
  // A fresh random salt is generated per call and embedded in the output.
  return argon2.hash(plain, ARGON2_OPTS);
}

export async function verifyPassword(stored, plain) {
  try {
    // Constant-time verification against the embedded salt + params.
    return await argon2.verify(stored, plain);
  } catch (err) {
    // A malformed stored hash must fail closed, never throw a 500 that
    // leaks which accounts have corrupt records.
    console.error("argon2 verify error", err);
    return false;
  }
}
```

The login handler now fetches the stored hash by email (parameterized) and verifies in the app:

```js
app.post("/login", loginRateLimit, async (req, res) => {
  const { email, password } = req.body;
  const { rows } = await pool.query("SELECT id, pw_hash, totp_secret FROM users WHERE email = $1", [
    email,
  ]);
  // Always run a verify even when the user is absent, against a dummy hash,
  // so the response time does not reveal whether the email exists (a timing
  // side channel that enables account enumeration).
  const stored = rows[0]?.pw_hash ?? DUMMY_ARGON2_HASH;
  const ok = await verifyPassword(stored, password);
  if (!ok || rows.length === 0) {
    logAuthEvent({ event: "auth_failure", email, ip: req.ip });
    return res.status(401).json({ error: "invalid credentials" });
  }
  // Password correct — now require the second factor (next section).
  return startMfaChallenge(res, rows[0]);
});
```

### Multi-factor: TOTP

<VocabTooltip slug="multi-factor-authentication">Multi-factor authentication</VocabTooltip> (MFA)
requires a second, independent proof of identity so a stolen or reused password alone cannot log an
attacker in — directly closing the Spoofing threat from the model.
<VocabTooltip slug="totp">TOTP</VocabTooltip> (Time-based One-Time Password, RFC 6238) derives a
6-digit code from a shared secret and the current 30-second time window; the authenticator app and
the server compute the same code independently.

```js
// mfa.js
import { authenticator } from "otplib"; // RFC 6238 TOTP implementation

// Verify the user's 6-digit code. otplib allows a small time-step window
// to tolerate clock skew; keep it tight (1 step) to limit the attack window.
export function verifyTotp(secret, token) {
  authenticator.options = { window: 1 };
  return authenticator.verify({ token, secret });
}
```

NIST SP 800-63B treats a memorized secret plus a TOTP authenticator as Authenticator Assurance Level 2. Pair MFA with a login rate limit so credential stuffing is throttled before the second factor is even reached.

### Data at rest: AEAD with nonce discipline

Some stored fields (a saved payment token, a user's address) need confidentiality _and_ integrity at rest. The correct primitive is <VocabTooltip slug="aead">AEAD</VocabTooltip> — <VocabTooltip slug="authenticated-encryption">authenticated encryption with associated data</VocabTooltip> — which encrypts the plaintext and produces an authentication tag in one operation, so any tampering with the ciphertext is detected on decryption. Use a vetted construction: AES-256-GCM or ChaCha20-Poly1305. Never invent a mode.

The single most common AEAD mistake is <VocabTooltip slug="nonce">nonce</VocabTooltip> reuse. A nonce is a number used once per key; reusing a nonce with the same key under GCM is catastrophic — it leaks the XOR of two plaintexts and can expose the authentication key. The discipline: a fresh random nonce per encryption, stored alongside the ciphertext.

```js
// field-crypto.js
import crypto from "node:crypto";

// AES-256-GCM. The 256-bit key comes from a KMS / env secret, never
// hardcoded. We return nonce + tag + ciphertext together so decrypt has
// everything it needs and we never reuse a nonce with this key.
export function encryptField(plaintext, key) {
  // 96-bit random nonce: the GCM-recommended size, fresh for EVERY call.
  // Reusing a nonce under the same key breaks GCM completely.
  const nonce = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv("aes-256-gcm", key, nonce);
  const ciphertext = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  const tag = cipher.getAuthTag(); // integrity tag — binds the ciphertext
  // Layout: [12-byte nonce][16-byte tag][ciphertext].
  return Buffer.concat([nonce, tag, ciphertext]);
}

export function decryptField(blob, key) {
  const nonce = blob.subarray(0, 12);
  const tag = blob.subarray(12, 28);
  const ciphertext = blob.subarray(28);
  const decipher = crypto.createDecipheriv("aes-256-gcm", key, nonce);
  decipher.setAuthTag(tag);
  // final() THROWS if the tag does not verify — tampering fails loudly
  // and the caller must treat a throw as "do not trust this data."
  return Buffer.concat([decipher.update(ciphertext), decipher.final()]).toString("utf8");
}
```

### Transport: TLS 1.3

The plaintext-HTTP finding is closed by terminating <VocabTooltip slug="tls-1-3">TLS 1.3</VocabTooltip> (RFC 8446) in front of the service. TLS 1.3 removed the legacy, broken <VocabTooltip slug="cipher-suite">cipher suites</VocabTooltip> of earlier versions, makes forward secrecy mandatory, and encrypts more of the handshake. In production a reverse proxy (nginx, Caddy) usually terminates TLS; the principle to verify is "minimum version 1.3, modern suites only."

```js
// For a Node listener terminating TLS directly (e.g. behind no proxy):
import https from "node:https";
import fs from "node:fs";

const tlsOptions = {
  key: fs.readFileSync(process.env.TLS_KEY_PATH),
  cert: fs.readFileSync(process.env.TLS_CERT_PATH),
  // Refuse anything below TLS 1.3. No fallback to 1.2/1.1/1.0 — old
  // versions carry downgrade and cipher weaknesses TLS 1.3 fixed.
  minVersion: "TLSv1.3",
};
https.createServer(tlsOptions, app).listen(8443);
```

ASVS V9.1.2 requires that only strong cipher suites are enabled, with the strongest set as preferred; V9.1.3 requires that only the latest recommended TLS versions are enabled "such as TLS 1.2 and TLS 1.3," with the latest version preferred — which nets out to TLS 1.2 or higher and, for this build, 1.3-only. Citing these makes the transport claim checkable.

## Link 4 — detection and the IR runbook

Controls fail silently unless you watch them. First, emit structured security logs — machine-parsable, not free-text — so a detection can run over them.

```js
// logging.js — structured security events. One JSON object per line so a
// log pipeline can index fields without regex-scraping prose.
export function logAuthEvent(fields) {
  console.log(
    JSON.stringify({
      ts: new Date().toISOString(),
      kind: "security",
      ...fields, // e.g. { event: "auth_failure", email, ip }
    })
  );
}
```

Then a <VocabTooltip slug="detection-rule">detection rule</VocabTooltip> mapped to a real adversary technique. MITRE ATT&CK catalogs adversary behavior; T1110 is **Brute Force**, and its sub-technique T1110.003 is **Password Spraying** — trying one common password against many accounts to stay under per-account lockouts. The detection: many `auth_failure` events from one IP across distinct emails in a short window.

```js
// detection.js — pseudocode for the rule a SIEM would run on the log stream.
// Mapped to MITRE ATT&CK T1110.003 (Password Spraying).
function detectPasswordSpray(events, windowMins = 5, distinctEmailThreshold = 10) {
  const byIp = groupBy(
    events.filter((e) => e.event === "auth_failure"),
    "ip"
  );
  for (const [ip, evs] of byIp) {
    const recent = withinLast(evs, windowMins);
    const distinctTargets = new Set(recent.map((e) => e.email)).size;
    // One source IP failing against many DIFFERENT accounts is the spray
    // signature — distinct from one user fat-fingering their own password.
    if (distinctTargets >= distinctEmailThreshold) {
      raiseAlert({
        technique: "T1110.003",
        ip,
        distinctTargets,
        severity: "high",
      });
    }
  }
}
```

When that alert fires, the on-call engineer follows the <VocabTooltip slug="incident-response-runbook">incident-response runbook</VocabTooltip>. NIST SP 800-61 **Rev. 2** defines the IR lifecycle in four phases; the runbook is written against them so nothing is improvised at 3 a.m. (NIST SP 800-61 **Rev. 3**, published 2025, retires the rigid four-phase lifecycle and re-organizes incident response around the six NIST CSF 2.0 functions you use in the next section — the four-phase structure here is the Rev. 2 model, still the most common shape for a service runbook):

1. **Preparation** — the logging, the detection, and this runbook already exist (that is this link). Contact list and access are pre-staged.
2. **Detection & Analysis** — the T1110.003 alert fired. Confirm scope: which IP, how many accounts, any _successful_ logins from that IP (escalate hard if yes — a spray that landed is now T1078, Valid Accounts).
3. **Containment, Eradication & Recovery** — block the source IP at the edge, force a password reset and session revocation for any account it authenticated to, confirm MFA is enforced on those accounts, then restore normal operation.
4. **Post-Incident Activity** — write the lessons-learned: was the threshold right, did MFA hold, what detection gap (if any) let it run as long as it did. Feed fixes back into the threat model.

The runbook is prose plus that numbered procedure. It belongs in the bundle as a Markdown file.

## Link 5 — residual risk against NIST CSF 2.0

No hardening is complete. The honest close is a residual-risk register organized by the six functions of <VocabTooltip slug="nist-csf">NIST Cybersecurity Framework 2.0</VocabTooltip>, used in their canonical order — **Govern, Identify, Protect, Detect, Respond, Recover**. (CSF 2.0, published 2024, added **Govern** as the sixth function ahead of the original five.)

| CSF 2.0 function | What this engagement did                                           | Residual risk you are accepting                                                  |
| ---------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------- |
| **Govern**       | Mapped each fix to an ASVS requirement so decisions are auditable  | No formal ownership/review cadence for the service after handoff                 |
| **Identify**     | STRIDE threat model + DFD of the three routes                      | Out-of-scope dependencies (the npm tree, the DB host OS) not threat-modeled here |
| **Protect**      | Access control, parameterized queries, Argon2id+MFA, AEAD, TLS 1.3 | No WAF; no secrets-rotation automation for the AEAD key                          |
| **Detect**       | Structured logs + one T1110.003 detection rule                     | Single detection; no coverage for injection attempts or data-exfil patterns      |
| **Respond**      | NIST 800-61 runbook for the spray scenario                         | Runbook covers one incident class; others (data breach, DoS) undocumented        |
| **Recover**      | Session revocation + forced reset in the runbook                   | No tested backup-restore drill; recovery time objective undefined                |

The right-hand column is the point. You are not claiming "secure" — you are handing the owner a precise, framework-organized list of what remains, so accepting the residual risk is a decision, not an accident.

## Practice — write the access-control fix

Before you assemble the full bundle, prove you can write the single most-cited fix in the engagement: the server-side ownership check that closes the IDOR. The logic is identical in any language; here you write it in TypeScript so you can run it.

Bundle those into one archive (`tar czf phase-s-capstone.tgz threat-model.md app.hardened.js detection.js runbook.md residual-risk.md ...`), compute its SHA-256, and submit to DURA `/verify` with the title "Phase S Capstone — Harden a Production Service."

> **What DURA /verify actually is.** `/verify` is a generic SHA-256 certificate lookup (`src/lib/verify/`). It does not run, scan, or grade your code — it has no idea whether your fix is correct. You compute the SHA-256 of your bundle; DURA records a certificate binding that hash to a title and a timestamp; anyone with the file recomputes the hash and looks it up at `/verify/{hash}`. A match proves the bytes a reviewer holds are the exact bytes you anchored, and _when_ you anchored them — authenticity and integrity, not quality. The security judgment in your threat model and runbook is still something a human reads and assesses. The hash only removes the question "is this the real submission, unaltered."

A <VocabTooltip slug="hash-anchored-artifact">hash-anchored artifact</VocabTooltip> is therefore a portfolio piece a hiring manager or auditor can trust: download, recompute, confirm, then spend their time on the substance — your threat model's coverage, your ASVS traceability, your residual-risk honesty — instead of wondering whether you edited it after a reviewer pushed back.
