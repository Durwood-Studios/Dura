## Why this matters

A penetration-test report just landed in your inbox. It contains one line: "A03:2021 — Injection. Login endpoint. Critical." No exploit walkthrough, no remediation steps — the report assumes you already know what A03 means, what the attacker can do with it, and how to close it. Your job is to read the code, find the defect, fix it, and prove the fix holds. The clock is the next release.

This is the daily reality of application security work. The <VocabTooltip slug="owasp-top-10">OWASP Top 10</VocabTooltip> is the shared vocabulary that lets a tester, an engineer, and an auditor talk about the same defect without re-explaining it each time. Learn to read code through these ten lenses and you can do the central task of a security engineer: look at a function and say "that is broken, here is the category, here is the fix, here is the requirement that verifies it."

## First principles: ten names for ten ways software breaks

Before the list, the idea behind the list. Every web application is a machine that takes untrusted input from the outside world and turns it into trusted actions on the inside — reading a database row, writing a file, calling another service. A vulnerability is any place where that boundary leaks: where outside input reaches an inside action without the check that should have stopped it.

The Top 10 is a ranked taxonomy of where that boundary most commonly leaks, compiled by the Open Web Application Security Project from real-world breach data. The 2021 edition is the current one. It is not a checklist of bugs — it is ten _categories of root cause_, each naming a class of missing check.

Here is the full 2021 list, in its published order. The order is by prevalence and impact, not alphabetical, so the order itself is information:

```text
A01:2021 — Broken Access Control
A02:2021 — Cryptographic Failures
A03:2021 — Injection
A04:2021 — Insecure Design
A05:2021 — Security Misconfiguration
A06:2021 — Vulnerable and Outdated Components
A07:2021 — Identification and Authentication Failures
A08:2021 — Software and Data Integrity Failures
A09:2021 — Security Logging and Monitoring Failures
A10:2021 — Server-Side Request Forgery (SSRF)
```

Two structural facts worth holding onto. First, **Broken Access Control moved to #1 in 2021** — it was #5 in the 2017 edition — because access-control defects turned out to be the most widespread when OWASP measured real applications. Second, **Insecure Design (A04) and SSRF (A10) are new categories in 2021**; SSRF was promoted from a single entry to its own category after a run of high-impact incidents.

## The mental model

> **A Top 10 category is a question you ask of every untrusted input.** A01 asks "is this user allowed to touch this object?" A03 asks "is this input being treated as data or as code?" A10 asks "is the server about to fetch a URL an attacker chose?" Security review is running those ten questions over the code paths where outside input meets inside action.

We will work the highest-frequency categories as vulnerable code → exploit → fix, then map each to a verification requirement in <VocabTooltip slug="asvs">ASVS</VocabTooltip> — the OWASP Application Security Verification Standard, a companion document that turns each Top 10 theme into concrete, checkable requirements (numbered like "V5.3.4"). The Top 10 tells you _what_ breaks; ASVS tells you _what to verify_ so it does not.

## A01 — Broken Access Control

<VocabTooltip slug="broken-access-control">Broken access control</VocabTooltip> is the failure to
enforce *what an authenticated user is permitted to do*. Authentication asks "who are you"; access
control asks "are you allowed to touch this." A01 is the gap where the second check is missing or
wrong.

The most common shape is an <VocabTooltip slug="insecure-direct-object-reference">insecure direct object reference</VocabTooltip> (IDOR): an endpoint takes an object id from the request and returns the object without checking that the caller owns it.

Vulnerable code — an Express route that returns an invoice by id:

```js
// VULNERABLE — A01: no ownership check on the requested invoice.
// req.user is populated by auth middleware (the caller IS logged in)...
// but being logged in is not the same as being allowed to see THIS invoice.
app.get("/api/invoices/:invoiceId", requireAuth, async (req, res) => {
  const invoice = await db.invoice.findById(req.params.invoiceId);
  if (!invoice) return res.status(404).json({ error: "Not found" });
  return res.json(invoice); // returns ANY invoice to ANY logged-in user
});
```

The exploit needs no special tooling. A logged-in user requests `/api/invoices/1001`, sees their own invoice, then requests `/api/invoices/1002` — and receives another customer's invoice, because the code never checks that invoice 1002 belongs to the caller. Iterating ids walks the whole table.

The fix is **deny-by-default ownership enforcement**: scope every object lookup to the authenticated principal, and treat "no row matched" as the default outcome rather than "row found, now decide."

```js
// FIXED — A01: the query itself is scoped to the owner.
// The database never returns a row the caller doesn't own, so there is
// no window between "found it" and "check permission" for a bug to hide in.
app.get("/api/invoices/:invoiceId", requireAuth, async (req, res) => {
  const invoice = await db.invoice.findOne({
    id: req.params.invoiceId,
    ownerId: req.user.id, // deny-by-default: ownership is part of the lookup
  });
  if (!invoice) return res.status(404).json({ error: "Not found" }); // same 404 whether it doesn't exist OR isn't yours — don't leak existence
  return res.json(invoice);
});
```

Two design choices matter here. <VocabTooltip slug="deny-by-default">Deny-by-default</VocabTooltip> means the lookup _fails closed_: access is denied unless a rule explicitly grants it, rather than granted unless a rule denies it. And returning the same `404` for "does not exist" and "exists but isn't yours" stops the endpoint from leaking which invoice ids are real.

> **ASVS mapping (A01).** ASVS V4 — Access Control. V4.2.1 requires that sensitive data and APIs are protected against IDOR by verifying authorization for the specific object requested. A reviewer citing V4.2.1 is asking: "show me the ownership check tied to the requested id."

## A02 — Cryptographic Failures

<VocabTooltip slug="cryptographic-failure">Cryptographic failures</VocabTooltip> — called "Sensitive
Data Exposure" in 2017 — cover everything from sending data in cleartext to using broken algorithms
to storing passwords recoverably. The category name was changed in 2021 to point at the *root cause*
(the cryptography was wrong or absent) rather than the *symptom* (data got exposed).

The canonical example is password storage. A fast, unsalted hash is a cryptographic failure even though it is technically "hashing."

```js
// VULNERABLE — A02: SHA-256 is a FAST hash built for speed.
// An attacker who steals this table can compute billions of guesses per
// second on a GPU. Unsalted means identical passwords share a hash, so one
// cracked entry cracks every account that reused that password.
const crypto = require("node:crypto");
function storePassword(plaintext) {
  return crypto.createHash("sha256").update(plaintext).digest("hex");
}
```

The fix is a **slow, salted, purpose-built password hash**. Use an algorithm designed to resist brute force — Argon2id is the current OWASP first recommendation; bcrypt and scrypt are also acceptable. These are deliberately expensive to compute and salt each password so identical passwords produce different hashes.

```js
// FIXED — A02: Argon2id is memory-hard and deliberately slow, with a
// per-password salt generated and stored inside the returned hash string.
// The cost parameters make large-scale offline cracking economically
// infeasible even if the database is stolen.
const argon2 = require("argon2");

async function storePassword(plaintext) {
  // argon2 generates a random salt per call and encodes it in the output.
  return argon2.hash(plaintext, { type: argon2.argon2id });
}

async function verifyPassword(plaintext, storedHash) {
  // Constant-time comparison is handled inside verify — never compare hashes
  // with === , which can leak timing information about how many bytes matched.
  return argon2.verify(storedHash, plaintext);
}
```

> **ASVS mapping (A02).** ASVS V2.4 — Credential Storage. V2.4.1 requires passwords to be stored using an approved one-way key-derivation function such as Argon2id, bcrypt, or scrypt. V6 covers cryptography at rest more broadly. A reviewer citing V2.4.1 is asking: "is this a password hash or a general-purpose hash?"

## A03 — Injection

<VocabTooltip slug="injection">Injection</VocabTooltip> is the failure to keep *data* and *code*
separate. It happens whenever untrusted input is concatenated into a string that an interpreter then
parses as a command — SQL, an OS shell, an LDAP query, an HTML page (cross-site scripting is a form
of injection). <VocabTooltip slug="sql-injection">SQL injection</VocabTooltip> is the classic.

Vulnerable code — a login query built by string concatenation:

```js
// VULNERABLE — A03: the user's input is glued directly into SQL text.
// The database parses the whole string as code, so input that contains
// SQL syntax becomes part of the query the database runs.
async function findUser(email, password) {
  const sql =
    "SELECT * FROM users WHERE email = '" + email + "' AND password_hash = '" + password + "'";
  return db.query(sql);
}
```

The exploit: an attacker submits the email `' OR '1'='1' --`. The query the database sees becomes `SELECT * FROM users WHERE email = '' OR '1'='1' -- ' AND password_hash = '...'`. The `OR '1'='1'` is always true and the `--` comments out the password check, so the query returns the first user row and the login succeeds without a valid password. The input was meant to be _data_ (an email) and was executed as _code_ (SQL logic).

The fix is the <VocabTooltip slug="parameterized-query">parameterized query</VocabTooltip> (also called a prepared statement). You send the SQL _structure_ and the _values_ to the database separately. The database compiles the structure first, then binds the values into placeholder slots — values are never parsed as SQL, so there is no syntax an attacker can smuggle in.

```js
// FIXED — A03: the SQL text contains only placeholders ($1, $2).
// The driver sends the query structure and the values on separate channels.
// The database treats the values as data, never as SQL, so OR '1'='1' is
// just a string that happens to equal no real email.
async function findUser(email, password) {
  const sql = "SELECT * FROM users WHERE email = $1 AND password_hash = $2";
  return db.query(sql, [email, password]); // values bound, not concatenated
}
```

The defense is structural, not a filter: you are not trying to _detect_ malicious input, you are removing the channel through which input could ever be interpreted as code. String-escaping blocklists fail because attackers find encodings you did not anticipate; parameterization succeeds because the data path is provably separate from the code path.

> **ASVS mapping (A03).** ASVS V5.3 — Output Encoding and Injection Prevention. V5.3.4 requires that database queries use parameterized queries or are otherwise protected from SQL injection. A reviewer citing V5.3.4 is asking: "show me a placeholder and a bound value, not a concatenated string."

## A04 — Insecure Design

<VocabTooltip slug="insecure-design">Insecure design</VocabTooltip> is new in 2021 and different in
kind from the others: it is a flaw in the *plan*, not the *code*. A perfectly implemented design can
still be insecure if the design never accounted for an abuse case. No amount of clean code fixes a
missing security requirement.

Example: a "reset password by answering a security question" flow. The code can be flawless — parameterized queries, hashed answers, rate-limited — and the _design_ is still insecure, because security questions ("mother's maiden name") are often publicly discoverable, so the whole mechanism is a weaker authenticator masquerading as a stronger one. The fix lives in threat modeling (the subject of lesson s-1, your prerequisite): you surface the abuse case at design time and choose a different mechanism — for example, a time-limited token sent to a pre-verified channel.

A04's lesson for the engineer: some defects cannot be found by reading a function. They are found by asking, at design time, "how would an attacker abuse this feature as specified?" That is why threat modeling precedes coding.

> **ASVS mapping (A04).** ASVS V1 — Architecture, Design and Threat Modeling. V1.1 requires a secure software development lifecycle that addresses security in every stage, including documented threat models for critical flows. A reviewer citing V1 is asking: "where is the threat model for this feature?"

## A05–A09, in brief

The remaining categories follow the same shape — a missing check at the boundary — and we name the question each one asks:

- **A05 — <VocabTooltip slug="security-misconfiguration">Security Misconfiguration</VocabTooltip>:** the software is fine but its _settings_ are not — a default admin password left unchanged, a verbose stack trace returned to users, an S3 bucket left public, debug mode on in production. The question: "is every default hardened, and is nothing exposed that a production system should hide?" _(ASVS V14 — Configuration.)_

- **A06 — <VocabTooltip slug="vulnerable-components">Vulnerable and Outdated Components</VocabTooltip>:** you are running a dependency with a known, published vulnerability (a CVE) and have not patched it. The question: "do you know every component and version you ship, and is any of them known-vulnerable?" The defensive practice is a software bill of materials plus continuous dependency scanning (`npm audit`, Dependabot, OSV). _(ASVS V14.2 — Dependency.)_

- **A07 — <VocabTooltip slug="authentication-failure">Identification and Authentication Failures</VocabTooltip>:** weaknesses in proving who the user is — permitting weak or breached passwords, missing rate limiting on login (enabling credential stuffing), broken session management. The question: "can an attacker become a user they are not?" _(ASVS V2 — Authentication, V3 — Session Management.)_

- **A08 — <VocabTooltip slug="software-integrity-failure">Software and Data Integrity Failures</VocabTooltip>:** trusting code or data whose integrity you never verified — installing an unsigned update, deserializing untrusted data, a CI/CD pipeline that pulls an unpinned dependency. The question: "do you verify that the code and data you load are the code and data you intended?" _(ASVS V10 — Malicious Code, V1.10 — integrity.)_

- **A09 — <VocabTooltip slug="logging-failure">Security Logging and Monitoring Failures</VocabTooltip>:** the breach happened and no one could tell, because logins, access-control failures, and high-value actions were not logged, or the logs were never watched. The question: "if an attack happened right now, would you see it, and could you reconstruct it afterward?" Log security-relevant events with enough context to investigate — and never log secrets or full credentials. _(ASVS V7 — Error Handling and Logging.)_

## A10 — Server-Side Request Forgery (SSRF)

<VocabTooltip slug="ssrf">SSRF</VocabTooltip> happens when an application fetches a URL supplied by
the user and that URL points somewhere the user should not be able to reach. The application's
server makes the request, so it runs with the *server's* network position — which usually means
access to internal services, cloud metadata endpoints, and admin interfaces that are firewalled off
from the outside.

Vulnerable code — a "fetch image from URL" feature:

```js
// VULNERABLE — A10: the server fetches any URL the user provides.
// The user controls where the SERVER points its request, so they can aim
// it at internal addresses the user could never reach directly.
app.post("/api/import-image", requireAuth, async (req, res) => {
  const response = await fetch(req.body.imageUrl); // attacker-controlled target
  const buffer = Buffer.from(await response.arrayBuffer());
  return res.json({ bytes: buffer.length });
});
```

The exploit: instead of an image URL, the attacker submits `http://169.254.169.254/latest/meta-data/`, the cloud metadata service address. The server fetches it from inside the trusted network and may hand back instance credentials. Internal-only addresses like `http://localhost:9200` (an unauthenticated internal Elasticsearch) are reachable the same way.

The fix combines an <VocabTooltip slug="allow-list">allow-list</VocabTooltip> with destination validation. You decide in advance the small set of hosts the feature is permitted to reach and reject everything else — deny-by-default, applied to network destinations.

```js
// FIXED — A10: validate the parsed URL against an explicit allow-list of
// hosts BEFORE making any request. Anything not on the list is rejected.
const ALLOWED_IMAGE_HOSTS = new Set(["images.partner-cdn.example"]);

app.post("/api/import-image", requireAuth, async (req, res) => {
  let target;
  try {
    target = new URL(req.body.imageUrl); // throws on malformed input
  } catch {
    return res.status(400).json({ error: "Invalid URL" });
  }

  // Allow-list the scheme and host; deny-by-default everything else.
  // Blocking known-bad addresses (a blocklist) is unwinnable — there are too
  // many ways to encode 169.254.169.254. Allow only what you intend instead.
  if (target.protocol !== "https:" || !ALLOWED_IMAGE_HOSTS.has(target.hostname)) {
    return res.status(400).json({ error: "URL not permitted" });
  }

  const response = await fetch(target.href);
  const buffer = Buffer.from(await response.arrayBuffer());
  return res.json({ bytes: buffer.length });
});
```

The same principle keeps recurring: **allow-list, never blocklist.** A blocklist enumerates the bad and fails the moment an attacker finds an encoding you missed (`0x A9.FE.A9.FE`, decimal IP, DNS rebinding). An allow-list enumerates the good — a far smaller, fully known set — and fails closed.

> **ASVS mapping (A10).** ASVS V12.6 / V5.2.6 — server-side requests must validate and restrict destinations against an allow-list and must not follow requests to internal or private address ranges. A reviewer citing this is asking: "where is the allow-list, and is it checked before the fetch?"

## What you learned

- The **OWASP Top 10:2021**, in order: A01 Broken Access Control, A02 Cryptographic Failures, A03 Injection, A04 Insecure Design, A05 Security Misconfiguration, A06 Vulnerable and Outdated Components, A07 Identification and Authentication Failures, A08 Software and Data Integrity Failures, A09 Security Logging and Monitoring Failures, A10 SSRF — each naming a class of missing check at the untrusted-input boundary.
- **A01** is closed by deny-by-default ownership checks (scope the lookup to the caller); **A03** by parameterized queries that separate code from data; **A10** by server-side allow-listing of destinations. The recurring principle: allow-list the known-good, never blocklist the known-bad.
- **A02** requires purpose-built, salted, slow password hashing (Argon2id) rather than fast general-purpose hashes; **A04** is a design-time flaw that threat modeling, not code review, catches.
- Every fix maps to a concrete, checkable **ASVS** requirement — V4.2.1 (IDOR), V2.4.1 (credential storage), V5.3.4 (injection), V12.6/V5.2.6 (SSRF) — so a reviewer can verify the fix, not just trust it.
- Security review is **running ten questions over the code**: for each untrusted input that reaches an inside action, ask which of the ten checks is missing.
