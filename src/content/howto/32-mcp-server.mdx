Build a complete, read-only document server using the official MCP SDK. The [downloadable lab](/labs/mcp-server/README.md) contains the entire implementation and a test that launches a real client and server process. It uses two public fixture documents so you can reproduce every result without API keys or an LLM.

## Step 1: Understand the Client and Server

An MCP client connects to a server, negotiates capabilities, and discovers the features it supports. **Tools** perform named operations, **resources** expose URI-addressed content, and **prompts** provide reusable messages. The host application controls which capabilities reach its model and when approval is needed. A server does not independently cause a model to call tools.

MCP uses JSON-RPC. Requests have IDs; notifications do not. Stdio transports messages through a child process's stdin and stdout. Reserve stdout for the protocol and log diagnostics to stderr.

## Step 2: Download and Run the Complete Project

Use Node 22 or later. Save these files together in an empty directory:

- [package.json](/labs/mcp-server/package.json)
- [server.mjs](/labs/mcp-server/server.mjs)
- [server.test.mjs](/labs/mcp-server/server.test.mjs)

```bash
npm install
npm test
npm start
```

The manifest pins the tested SDK and Zod versions. After installation this fixture runs offline. `npm start` waits for protocol input; it does not open a webpage. Configure your MCP client to launch `node` with the absolute path to `server.mjs` as its argument.

## Step 3: Register a Bounded Tool

Open `server.mjs`. `search_documents` accepts a trimmed string of 1–200 characters. The handler searches the in-memory document map and returns a JSON array inside a text content block. Searching `offline` returns the `welcome` document; searching `absent` returns an empty array. Invalid arguments return a tool error rather than executing an unbounded search.

The read-only and idempotent annotations describe the tool to clients. They do not enforce access control. This example enforces its boundary by having no filesystem, network, or write operations in the handler.

## Step 4: Register a Real URI Template

A dynamic resource uses `new ResourceTemplate("docs://document/{id}", ...)`. A plain string containing braces is not a dynamic registration. The list callback publishes the two concrete resource URIs; the read callback resolves the requested ID from the fixed map and returns the exact requested URI and document text.

Read `docs://document/privacy` and expect `Analytics requires explicit consent.` Request `docs://document/missing` and expect an explicit unknown-ID protocol error. No path supplied by the client reaches a filesystem API.

## Step 5: Add a Prompt and Exercise the Transport

The `summarize-document` prompt validates an ID, loads the same fixture, and returns a user message asking for a one-sentence summary. It does not call an LLM or pretend a summary was generated. Your host supplies the model if you choose to use one.

Run `npm test`. The test uses `StdioClientTransport` to spawn the server, negotiate MCP, discover tools/resources/templates, call the search tool, read a resource, and request the prompt. It also checks blank, oversized, and wrong-type search inputs plus unknown document IDs. The client closes in a `finally` block so the child process is cleaned up after failure.

## Step 6: Extend and Verify the Boundary

Add a third public document to the map and update the test to discover its URI, search a unique word in it, read its full text, and reject an unknown ID. Explain why a server that exposes private files needs authorization beyond tool annotations.

Keep this exercise on stdio. A production HTTP deployment needs the SDK's Streamable HTTP lifecycle, Origin validation, authenticated authorization, and correct session isolation. Reusing one transport for unrelated clients or connecting a new server for every POST breaks that lifecycle. The lab makes no HTTP hosting or production-security claim.
