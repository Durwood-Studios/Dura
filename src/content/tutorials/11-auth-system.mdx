## Overview

Most developers use auth libraries without understanding what happens underneath. In this tutorial, you'll build a local authentication learning exercise — email/password registration, login, JWT access and refresh tokens, bcrypt password hashing, protected route middleware, and session management.

**What you'll learn:**

- How password hashing works (bcrypt salting and rounds)
- JWT structure, signing, and verification
- Access token vs refresh token patterns
- Middleware-based route protection
- Secure cookie handling and session invalidation
- Common auth vulnerabilities and how to prevent them

We'll use Express, bcrypt, jsonwebtoken, and a SQLite database (via better-sqlite3) to keep the focus on auth logic rather than infrastructure.

## Step 2: Database Schema

Create `src/db.ts`. We store users with hashed passwords and a separate table for refresh tokens so we can revoke sessions.

```typescript
import Database from "better-sqlite3";

let db: Database.Database;

export function getDb(): Database.Database {
  if (!db) {
    db = new Database("auth.db");
    db.pragma("journal_mode = WAL");
  }
  return db;
}

export function initDb(): void {
  const conn = getDb();

  conn.exec(`
    CREATE TABLE IF NOT EXISTS users (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      email TEXT UNIQUE NOT NULL,
      password_hash TEXT NOT NULL,
      created_at TEXT DEFAULT (datetime('now'))
    );

    CREATE TABLE IF NOT EXISTS refresh_tokens (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      user_id INTEGER NOT NULL REFERENCES users(id),
      token_hash TEXT UNIQUE NOT NULL,
      expires_at TEXT NOT NULL,
      revoked INTEGER DEFAULT 0,
      created_at TEXT DEFAULT (datetime('now'))
    );
  `);
}
```

The key design decisions: passwords are never stored in plain text, refresh tokens are hashed in the database (so a database leak doesn't compromise active sessions), and tokens can be individually revoked.

## Step 3: Password Hashing with Bcrypt

Create `src/auth/password.ts`:

```typescript
import bcrypt from "bcrypt";

const SALT_ROUNDS = 12;

export async function hashPassword(plaintext: string): Promise<string> {
  return bcrypt.hash(plaintext, SALT_ROUNDS);
}

export async function verifyPassword(plaintext: string, hash: string): Promise<boolean> {
  return bcrypt.compare(plaintext, hash);
}
```

Bcrypt is specifically designed for password hashing. Unlike SHA-256, it's intentionally slow — the cost depends on the machine and configured rounds. This increases the cost of guessing passwords; it does not replace rate limiting or strong passwords. The salt is embedded in the hash output, so you never need to store it separately.

Twelve rounds is this exercise's starting point. Benchmark on your deployment hardware and choose a cost that balances resistance to guessing with acceptable latency. Bcrypt only uses the first 72 bytes of a password; reject longer UTF-8 inputs rather than silently truncating them.

## Step 4: JWT Token Generation

Create `src/auth/tokens.ts`:

```typescript
import jwt from "jsonwebtoken";
import crypto from "crypto";
import { getDb } from "../db";

export function requireSecret(name: string): string {
  const value = process.env[name];
  if (!value || Buffer.byteLength(value, "utf8") < 32) {
    throw new Error(`${name} must contain at least 32 bytes of randomly generated secret`);
  }
  return value;
}

const ACCESS_SECRET = requireSecret("JWT_ACCESS_SECRET");
const REFRESH_SECRET = requireSecret("JWT_REFRESH_SECRET");
if (ACCESS_SECRET === REFRESH_SECRET) throw new Error("Use distinct signing secrets");

interface TokenPayload {
  userId: number;
  email: string;
}

function checkedPayload(value: unknown): TokenPayload {
  if (typeof value !== "object" || value === null ||
      !("userId" in value) || typeof value.userId !== "number" ||
      !Number.isSafeInteger(value.userId) || value.userId <= 0 ||
      !("email" in value) || typeof value.email !== "string") {
    throw new Error("Invalid token payload");
  }
  return { userId: value.userId, email: value.email };
}

export function generateAccessToken(payload: TokenPayload): string {
  return jwt.sign(payload, ACCESS_SECRET, { algorithm: "HS256", expiresIn: "15m" });
}

export function generateRefreshToken(payload: TokenPayload): string {
  // A unique ID prevents simultaneous logins from producing identical JWTs.
  return jwt.sign(payload, REFRESH_SECRET, {
    algorithm: "HS256", expiresIn: "7d", jwtid: crypto.randomUUID(),
  });
}

export function verifyAccessToken(token: string): TokenPayload {
  return checkedPayload(jwt.verify(token, ACCESS_SECRET, { algorithms: ["HS256"] }));
}

function refreshTokenHash(token: string): string {
  // Tokens are high-entropy credentials. SHA-256 covers the entire JWT, unlike bcrypt's 72-byte limit.
  return crypto.createHash("sha256").update(token).digest("hex");
}

export function verifyRefreshToken(token: string): TokenPayload {
  const payload = checkedPayload(jwt.verify(token, REFRESH_SECRET, { algorithms: ["HS256"] }));
  const session = getDb().prepare(`
    SELECT id FROM refresh_tokens
    WHERE user_id = ? AND token_hash = ? AND revoked = 0 AND expires_at > ?
  `).get(payload.userId, refreshTokenHash(token), new Date().toISOString());
  if (!session) throw new Error("Refresh session is expired, revoked, or unknown");
  return payload;
}

export async function storeRefreshToken(userId: number, token: string): Promise<void> {
  const expiresAt = new Date(Date.now() + 7 * 24 * 60 * 60 * 1000).toISOString();
  getDb()
    .prepare("INSERT INTO refresh_tokens (user_id, token_hash, expires_at) VALUES (?, ?, ?)")
    .run(userId, refreshTokenHash(token), expiresAt);
}

export async function revokeUserTokens(userId: number): Promise<void> {
  getDb().prepare("UPDATE refresh_tokens SET revoked = 1 WHERE user_id = ?").run(userId);
}
```

Two tokens serve different purposes. The access token is short-lived (15 minutes) and sent with every API request. The refresh token is long-lived (7 days), stored in an HTTP-only cookie, and used only to get new access tokens. This limits the damage window if an access token is stolen.

Generate two independent secrets before starting the exercise. Do not commit or share the values:

```bash
export JWT_ACCESS_SECRET="$(node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))")"
export JWT_REFRESH_SECRET="$(node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))")"
npx tsx src/index.ts
```

Finish creating the remaining files before running the server. Missing or reused secrets fail startup. A valid JWT signature alone is insufficient for refresh: the stored hash must belong to the user, remain unrevoked, and be unexpired.

## Step 5: User Registration

Create `src/routes/auth.ts`:

```typescript
import { Router, Request, Response } from "express";
import { getDb } from "../db";
import { hashPassword, verifyPassword } from "../auth/password";
import {
  generateAccessToken,
  generateRefreshToken,
  storeRefreshToken,
  verifyRefreshToken,
  revokeUserTokens,
} from "../auth/tokens";

export const authRouter = Router();

authRouter.post("/register", async (req: Request, res: Response) => {
  try {
    const { email, password } = req.body;

    if (typeof email !== "string" || typeof password !== "string" || !email || !password) {
      res.status(400).json({ error: "Email and password are required" });
      return;
    }

    if (password.length < 8 || Buffer.byteLength(password, "utf8") > 72) {
      res.status(400).json({ error: "Password must be at least 8 characters and at most 72 UTF-8 bytes" });
      return;
    }

    const existing = getDb().prepare("SELECT id FROM users WHERE email = ?").get(email);

    if (existing) {
      // This educational response still exposes duplicate registration through its status.
      res.status(409).json({ error: "Registration failed" });
      return;
    }

    const passwordHash = await hashPassword(password);

    const result = getDb()
      .prepare("INSERT INTO users (email, password_hash) VALUES (?, ?)")
      .run(email, passwordHash);

    const userId = result.lastInsertRowid as number;
    const accessToken = generateAccessToken({ userId, email });
    const refreshToken = generateRefreshToken({ userId, email });

    await storeRefreshToken(userId, refreshToken);

    res.cookie("refreshToken", refreshToken, {
      httpOnly: true,
      secure: process.env.NODE_ENV === "production",
      sameSite: "strict",
      maxAge: 7 * 24 * 60 * 60 * 1000,
      path: "/auth",
    });

    res.status(201).json({ accessToken, userId });
  } catch (error) {
    console.error("Registration error:", error);
    res.status(500).json({ error: "Internal server error" });
  }
});
```

Notice the refresh token cookie configuration: `httpOnly` prevents JavaScript from reading the cookie, `secure` requires HTTPS in production, and `sameSite: strict` reduces cross-site request exposure. These do not eliminate XSS or every CSRF threat. The `/auth` path includes both refresh and logout so the server can receive and revoke the session at logout.

## Step 6: Login Endpoint

Add the login route to `src/routes/auth.ts`:

```typescript
authRouter.post("/login", async (req: Request, res: Response) => {
  try {
    const { email, password } = req.body;

    if (typeof email !== "string" || typeof password !== "string" || !email || !password) {
      res.status(400).json({ error: "Email and password are required" });
      return;
    }

    if (Buffer.byteLength(password, "utf8") > 72) {
      res.status(401).json({ error: "Invalid credentials" });
      return;
    }

    const user = getDb()
      .prepare("SELECT id, email, password_hash FROM users WHERE email = ?")
      .get(email) as { id: number; email: string; password_hash: string } | undefined;

    if (!user) {
      // Hash a dummy password to prevent timing attacks
      await hashPassword("dummy-password-for-timing");
      res.status(401).json({ error: "Invalid credentials" });
      return;
    }

    const isValid = await verifyPassword(password, user.password_hash);

    if (!isValid) {
      res.status(401).json({ error: "Invalid credentials" });
      return;
    }

    const accessToken = generateAccessToken({
      userId: user.id,
      email: user.email,
    });
    const refreshToken = generateRefreshToken({
      userId: user.id,
      email: user.email,
    });

    await storeRefreshToken(user.id, refreshToken);

    res.cookie("refreshToken", refreshToken, {
      httpOnly: true,
      secure: process.env.NODE_ENV === "production",
      sameSite: "strict",
      maxAge: 7 * 24 * 60 * 60 * 1000,
      path: "/auth",
    });

    res.json({ accessToken, userId: user.id });
  } catch (error) {
    console.error("Login error:", error);
    res.status(500).json({ error: "Internal server error" });
  }
});
```

The timing attack defense is critical. When a user doesn't exist, we still hash a dummy password to reduce the obvious timing difference from a failed password check. This does not guarantee identical timing or prevent enumeration; registration responses still expose account existence in this exercise.

## Step 7: Token Refresh Endpoint

```typescript
authRouter.post("/refresh", async (req: Request, res: Response) => {
  try {
    const { refreshToken } = req.cookies;

    if (typeof refreshToken !== "string" || !refreshToken) {
      res.status(401).json({ error: "No refresh token" });
      return;
    }

    const payload = verifyRefreshToken(refreshToken);
    const accessToken = generateAccessToken({
      userId: payload.userId,
      email: payload.email,
    });

    res.json({ accessToken });
  } catch (error) {
    res.status(401).json({ error: "Invalid refresh token" });
  }
});
```

## Step 8: Auth Middleware

Create `src/middleware/authenticate.ts`:

```typescript
import { Request, Response, NextFunction } from "express";
import { verifyAccessToken } from "../auth/tokens";

export interface AuthenticatedRequest extends Request {
  user?: {
    userId: number;
    email: string;
  };
}

export function authenticate(req: AuthenticatedRequest, res: Response, next: NextFunction): void {
  const authHeader = req.headers.authorization;

  if (!authHeader || !authHeader.startsWith("Bearer ")) {
    res.status(401).json({ error: "Missing or malformed authorization header" });
    return;
  }

  const token = authHeader.split(" ")[1];

  try {
    const payload = verifyAccessToken(token);
    req.user = { userId: payload.userId, email: payload.email };
    next();
  } catch (error) {
    res.status(401).json({ error: "Invalid or expired token" });
  }
}
```

## Step 9: Protected Routes

Create `src/routes/protected.ts`:

```typescript
import { Router, Response } from "express";
import { authenticate, AuthenticatedRequest } from "../middleware/authenticate";

export const protectedRouter = Router();
protectedRouter.use(authenticate);

protectedRouter.get("/profile", (req: AuthenticatedRequest, res: Response) => {
  res.json({
    userId: req.user?.userId,
    email: req.user?.email,
    message: "You are authenticated",
  });
});
```

Every route on `protectedRouter` runs through the `authenticate` middleware first. The middleware extracts the JWT from the Authorization header, verifies it, and attaches the user payload to the request object.

## Step 10: Logout and Security Hardening

Add logout to `src/routes/auth.ts`:

```typescript
authRouter.post("/logout", async (req: Request, res: Response) => {
  try {
    const { refreshToken } = req.cookies;

    if (typeof refreshToken === "string" && refreshToken) {
      try {
        const payload = verifyRefreshToken(refreshToken);
        await revokeUserTokens(payload.userId);
      } catch {
        // Token already invalid — still clear the cookie
      }
    }

    res.clearCookie("refreshToken", { path: "/auth" });
    res.json({ message: "Logged out" });
  } catch (error) {
    console.error("Logout error:", error);
    res.status(500).json({ error: "Internal server error" });
  }
});
```

Logout revokes **all refresh sessions** for this user. Already-issued access tokens continue working until their 15-minute expiry; this exercise does not implement immediate access-token revocation. Refresh tokens are reusable until expiry or logout: rotation and replay detection remain required extensions.

Test the full flow (use a disposable account and keep the local cookie file private):

```bash
# Register
curl -X POST http://localhost:3000/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"securepassword123"}'

# Login and save the refresh cookie
curl -c cookies.txt -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"securepassword123"}'

# Access protected route (use the accessToken from login response)
curl http://localhost:3000/api/profile \
  -H "Authorization: Bearer <your-access-token>"
```

After login, `curl -b cookies.txt -X POST http://localhost:3000/auth/refresh` should return an access token. Call `curl -b cookies.txt -X POST http://localhost:3000/auth/logout`, then repeat refresh with the same saved cookie: it must return **401**, proving server-side revocation rather than only browser-cookie removal. Remove `cookies.txt` afterward.

**Security work still required before any deployment:**

- Manage, rotate, and protect the required signing secrets
- Add refresh-token rotation, replay detection, password reset, and email verification
- Resolve duplicate-registration enumeration and validate normalized email input
- Add rate limiting to `/auth/login` and `/auth/register` (express-rate-limit)
- Add input sanitization with a validation library
- Enable HTTPS in production
- Add CORS configuration
- Set security headers (helmet middleware)
- Add account lockout after N failed login attempts
- Log authentication events for audit trails

You have exercised hashing, signing, session lookup, and revocation. This is not a production-ready identity provider: use these checks to evaluate a maintained auth solution and its documented guarantees.
