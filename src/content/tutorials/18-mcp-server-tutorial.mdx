## Overview

Build a versioned MCP server that exposes public sample product data through two typed tools and two resources. Start with a deterministic fixture, then connect the same operations to a **disposable PostgreSQL lab database**. The project includes complete assembly, pinned packages and a real protocol-client test.

This is a local teaching server, not a claim of production readiness. It exposes no arbitrary SQL or insert tool. Keyword filtering cannot establish a read-only SQL boundary: permissions and explicitly allowed operations must do that work.

**Prerequisites:** Node.js 22+, JavaScript modules, parameterized SQL and client-server concepts. PostgreSQL is required only for the optional database mode. For a first MCP introduction, complete [the document MCP lab](/howto/mcp-server).

## Step 1: Install the Complete Project

[Download PostgreSQL MCP lab 1.0.0](/labs/mcp-postgres.zip), extract it and open its directory. The [README](/labs/mcp-postgres/README.md) lists the exact runtime and database setup.

```bash
cd mcp-postgres
npm ci
npm test
npm start
```

The lockfile pins `@modelcontextprotocol/sdk` 1.30.0, Zod 4.3.6 and `pg` 8.23.0. Fixture tests need no database, model, key or external service after installation. `npm start` waits for an MCP client on standard input; it does not open a web page.

## Step 2: Understand the File Boundaries

```text
server.mjs       typed tools, resources, session budget and stdio startup
data.mjs         public fixture plus fixed-query PostgreSQL adapter
setup.sql        disposable table and narrow reader role
server.test.mjs  official SDK client and boundary regressions
```

`createProductServer(repository)` is independent of data storage. Both repositories implement `search`, `preview`, `stats` and `close`. This lets protocol tests cover the actual server while keeping database permission checks a distinct integration responsibility.

## Step 3: Make Operations the Permission Boundary

The search tool accepts `term` and an integer `limit` from 1 to 20. It cannot accept a SQL string, column name or table name. Read the fixed search statement in `data.mjs`: the term is `$1`, the limit is `$2`, and the table is explicitly `public.lab_products`.

```sql
SELECT id, name, category, price_cents
FROM public.lab_products
WHERE strpos(lower(name), lower($1)) > 0
ORDER BY id
LIMIT $2
```

A search for `'; DROP TABLE lab_products;--` is ordinary text. The adapter test asserts that this text remains a bound parameter and never changes the SQL statement. This is a stronger and more inspectable contract than trying to recognize safe SQL with regular expressions.

## Step 4: Register Typed Tools

Read the two `registerTool` calls. Zod validates argument types and bounds before the callback runs. `search_products` returns approved fields; `product_price_summary` returns count and min/max prices in cents. Neither tool writes data.

The MCP read-only annotation describes intent to a client; it is not an authorization mechanism. The fixed repository operations and database privileges enforce the boundary. Add an invalid-limit call to the SDK test and confirm `isError` is true.

## Step 5: Expose Only Approved Resources

`products://schema` describes four known columns. `products://preview` returns at most five public rows. Unknown resource URIs fail; the server does not enumerate every table in a connected database or allow a caller to choose arbitrary identifiers.

Resources and tools share the same session operation budget. Reading a preview cannot bypass the control by using a different protocol method.

## Step 6: Verify Protocol Assembly

`server.test.mjs` spawns `server.mjs` with `StdioClientTransport`, connects an official SDK `Client`, lists tools/resources, calls valid and invalid tools, reads the preview and closes the session. This includes initialization negotiation.

A single JSON `tools/list` line piped to stdin is not a complete protocol test. Keep logs on stderr so they cannot corrupt JSON-RPC on stdout. Configure your MCP client with `node` and an absolute server path; consult that client's documentation for its configuration location.

## Step 7: Exercise the Shared Session Budget

The server permits at most 60 data operations per minute and one operation at a time. It uses one bounded counter for the local session, not an unbounded map of caller-provided identities. The tests verify rejection, concurrent-operation exclusion and reset at the window boundary.

This is not a distributed rate limiter or user authentication. If you later expose a network transport, define authentication, session ownership, origin handling and deployment limits before accepting remote clients.

## Step 8: Prepare a Disposable PostgreSQL Source

Create a new local lab database. Review `setup.sql` before running it as that database's owner. It creates the three-row `lab_products` table and `lab_reader` role, grants schema usage and SELECT only on that table, and sets the role's default transactions to read-only.

Provision its login password separately using your database administration workflow. Do not run the setup against DURA's hosted database or another application's production schema. Do not reuse an application owner or superuser credential for the MCP server.

## Step 9: Connect the Real Adapter

Set `DATABASE_URL` in the server's environment using the dedicated reader credentials, then start:

```bash
MCP_DATA_MODE=postgres npm start
```

The adapter uses a one-connection pool, connection and query timeouts, read-only transaction defaults and a restricted search path. Fixed SQL is schema-qualified. For remote TLS, configure trusted certificates; disabling certificate verification is not a solution.

Use the same MCP client calls and compare the fixture/database results. Then independently verify that the role cannot write or read unrelated tables. The offline suite tests the protocol and parameter contracts; a real deployment still needs its own authentication, TLS and permission evidence.

## Step 10: Extend Without Expanding Authority Accidentally

Add a category filter as a typed value parameter and update both repositories plus their tests. Define the expected ordering and limit behavior. An insert or arbitrary query tool is a separate capability decision, not a minor enhancement to a read-only server.

Record separately what you executed: offline protocol tests, disposable SQL checks, and any real PostgreSQL client connection. Do not call those equivalent to a reviewed production deployment.
