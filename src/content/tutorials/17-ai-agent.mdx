Build a complete, bounded agent loop with a validated tool registry, explicit provider adapter, conversation memory and a CLI. The [runnable lab](/labs/ai-agent/README.md) has an offline fixture mode and optional live Anthropic mode. The offline fixture tests the protocol and tools; it is not an AI model.

## Step 1: Install the Complete Project

Use Node 22 or later. Save [package.json](/labs/ai-agent/package.json), [agent.mjs](/labs/ai-agent/agent.mjs), [tools.mjs](/labs/ai-agent/tools.mjs), [cli.mjs](/labs/ai-agent/cli.mjs), [agent.test.mjs](/labs/ai-agent/agent.test.mjs) and [fixtures/welcome.txt](/labs/ai-agent/fixtures/welcome.txt), preserving the fixture directory.

```bash
npm install
npm test
npm start
```

Dependencies are pinned in the manifest. No model credential is required for these commands. Enter a prompt: demo mode deliberately computes `2 + 3` for every prompt, so the expected tool result is `5`.

## Step 2: Validate Tool Inputs

Read `ToolRegistry` in `agent.mjs`. Each registered tool supplies a name, description, Zod schema and execution function. Duplicate names fail immediately. Unknown names and schema failures return explicit tool errors. The provider sees JSON Schema produced by Zod's supported `toJSONSchema` API.

## Step 3: Understand the Provider Contract

The Anthropic adapter sends `name`, `description` and `input_schema` for each tool. An assistant response can contain a `tool_use` block with an ID, tool name and input object. The application executes that tool and replies with a user `tool_result` block carrying the same ID. An OpenAI-style nested `function` object is not interchangeable with this format.

The lab validates returned blocks and checks HTTP status before using the response. Requests have a timeout; provider errors stay visible. See the [official lifecycle](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls).

## Step 4: Follow One Tool Loop

`Agent.run` appends the learner's prompt, requests a provider response and stores the assistant's complete tool-use blocks. It invokes requested tools serially, appends the corresponding results together and requests the next response. A response with text and no tool calls completes the turn.

Trace demo mode in the test: user prompt → fixture tool request → calculator returns `5` → result block → fixture final text. No helper is left undefined.

## Step 5: Bound Execution

The constructor limits tool turns to a configurable maximum of 1–20. Reaching the limit raises an error instead of claiming a final answer. The agent rejects concurrent `run` calls so two prompts cannot interleave the same history. It also rejects duplicate tool IDs within a response.

Tools run serially. Automatic retries are omitted because repeating an arbitrary write could repeat its effect. A real retry policy must distinguish retryable transport failures from actions that may already have succeeded.

## Step 6: Use Arithmetic Without Evaluating Code

The calculator accepts two finite numbers and one operator: `+`, `-`, `*`, `/` or `**`. Its implementation selects an arithmetic function directly. Division by zero and nonfinite results fail. It does not run `eval`, strip unknown names from expressions, or confuse JavaScript's `^` XOR operator with exponentiation.

## Step 7: Read a Scoped Document

The file tool accepts only `welcome.txt`. It resolves the fixture root and target with `realpath`, verifies containment and bounds returned text. Requesting `../secret` fails validation. This is a public fixture reader, not arbitrary filesystem access.

Before exposing private data, design authorization independently of the model's instructions. Tool descriptions and prompt text do not enforce access rights.

## Step 8: Report Progress Honestly

The CLI prints tool-call and tool-result events while waiting for the final answer. These are application events, not token streaming or hidden model reasoning. Native provider streaming requires incremental event parsing and assembly of tool arguments; it is outside this lab's implemented transport.

## Step 9: Manage Conversation Memory

The agent keeps the current conversation in process memory and imposes a message-count budget before accepting another prompt. `/reset` clears it. Restarting the process also clears it. The lab does not pretend to provide persistent memory or automatic summarization.

On provider failure the incomplete conversation is rolled back. This restores local state only; it would not undo external effects if you added write tools.

## Step 10: Inspect Failure Tests

Run `npm test`. Tests cover the actual offline tool loop, provider request envelopes and paired IDs, bad inputs, missing tools, file-path rejection, division by zero, provider errors, bounded looping and simultaneous requests. The provider adapter uses explicit local response fixtures in its tests.

These tests establish local behavior. They do not establish that a particular model is currently enabled on your provider account.

## Step 11: Opt Into a Live Provider

Set `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL` in your local environment, then run:

```bash
node cli.mjs --live
```

Choose a model available to your account. Live calls require network access and may incur provider charges. Do not place the key in source files. The local verification did not make a live paid request.

## Step 12: Extend With an Acceptance Test

Add a read-only tool that converts Celsius to Fahrenheit, with a bounded finite input schema. Add tests for zero, a negative temperature, a rejected string and a provider tool-use/result round trip. Explain why a subprocess timeout would not make model-generated code execution safe, and what authorization and isolation you would require before adding that capability.

The complete core now includes a working registry, provider adapter, bounded tool loop, memory and CLI. Web search, arbitrary code execution, persistent memory and native token streaming are extensions requiring their own implementation and tests.
