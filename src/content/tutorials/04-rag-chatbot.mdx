## Overview

Build a complete document Q&A teaching application. Its default mode runs offline: vocabulary-count vectors retrieve passages and an extractive answer quotes them. That mode is **not an LLM**. An optional server-side adapter replaces the fixture embeddings and extractive answer with OpenAI embeddings and generated text.

The web route calls the same real retrieval pipeline as the tests. It never invents a source or returns a canned answer about the question. Responses arrive as complete JSON; token streaming is an extension, not part of this project.

**Prerequisites:** JavaScript modules, async functions, HTTP requests and Node.js 22 or later.

## Step 1: Get the Versioned Project

[Download the complete RAG lab](/labs/rag-chatbot.zip), extract it, and open its folder. The source files and tests are also available in the [lab README](/labs/rag-chatbot/README.md).

```bash
cd rag-chatbot
npm ci
npm test
npm start
```

Open `http://127.0.0.1:4310`. Ask `returns receipt`. Expect a passage saying the sample shop accepts returns within 30 days and requires a receipt. The displayed source must be `returns#0`.

No API key is needed for this first run. The package is version 1.0.0 with no external runtime dependencies.

## Step 2: Trace the Real Pipeline

```text
documents.json → bounded chunks → provider.embed → in-memory index
question → same provider.embed → cosine ranking → retrieved passages
retrieved passages + question → provider.generate → answer + source passages
```

Read `rag.mjs`, `provider.mjs`, `server.mjs` and `client.js` in that order. Both providers implement `embed(texts)` and `generate(question, hits)`. Keeping that boundary explicit lets you test retrieval without model variability or API costs.

An embedding model change requires rebuilding the whole index. Comparing query vectors from a different model to the old document vectors is invalid even when their dimensions happen to match.

## Step 3: Chunk Without Losing Termination

The supplied `chunkText` validates `0 ≤ overlap < size`, advances by `size - overlap`, and exits when it reaches the document end. It retains a final short chunk. Run the chunk test with a five-character document: the function must terminate and return one chunk.

```javascript
import { chunkText } from "./rag.mjs";
console.log(chunkText("abcdefghijk", 5, 2));
// ["abcde", "defgh", "ghijk"]
```

These bounds use characters, not tokens. The lab limits document count, document length and total chunks before indexing. A production chunker would need language-aware segmentation and the chosen model's input limits.

## Step 4: Inspect Fixture Embeddings

The fixture builds a vocabulary from the documents and counts exact matching words. It is easy to inspect and deterministic. It does not understand synonyms, meaning or instructions. Ask `zzzzzzzz` and confirm the answer reports no matching evidence with an empty source list.

Change a document's wording and restart. Compare an exact-term question with a synonym-only question. Record which succeeds; do not interpret lexical fixture results as semantic-model quality.

## Step 5: Validate Similarity Inputs

`cosine` rejects missing, unequal-length and nonfinite vectors. A zero vector scores zero instead of producing `NaN`. Index construction requires one embedding per chunk and query retrieval requires one query vector.

The lab sorts matching chunks and returns at most three above a teaching threshold of 0.1. This threshold is not calibrated answer confidence, and a cosine score is not a probability that an answer is correct. Inspect the returned text, not just the number.

## Step 6: Keep Sources Attached to Answers

Each hit carries its original source ID, chunk ID and text. The fixture answer quotes those passages with citations. The API returns those same passages, and the UI displays them using `textContent` rather than HTML interpolation.

Add a public document with markup-like text, restart, and verify it renders as text. Add contradictory return policies and observe that retrieval alone cannot resolve their authority. Your application needs an explicit source/date policy before resolving such conflicts.

## Step 7: Test the Actual HTTP Route

`server.mjs` initializes the index once, serves the UI on loopback and handles `POST /api/chat`. It bounds request bodies, rejects cross-origin browser requests and allows one active question. The tests start a real ephemeral local HTTP server and assert that the response contains the actual `returns` source.

Malformed JSON and blank questions must return a visible error. The client checks HTTP status before using the response and keeps the form available for retry. This is a single-user teaching server; it has no hosted authentication or multi-tenant document permissions.

## Step 8: Explicitly Enable External Generation

Read the [embeddings API](https://developers.openai.com/api/reference/resources/embeddings/methods/create) and [Chat Completions API](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) before choosing model IDs available to your account. The supplied adapter uses native HTTPS requests with a timeout, checks embedding indexes and propagates provider failures.

Set `OPENAI_API_KEY`, `EMBEDDING_MODEL` and `CHAT_MODEL` in the server process environment through your local secret-management workflow. Then start:

```bash
RAG_MODE=openai npm start
```

This explicitly sends documents and questions to OpenAI and may incur API charges. The key stays on the server. Use public sample documents; never put a secret in `client.js` or `documents.json`. The fixture tests mock provider HTTP responses and make no paid model calls.

## Step 9: Evaluate Grounding Rather Than Promise It

The generation prompt asks for source-based answers and abstention. Prompt instructions cannot guarantee grounding or defeat every document prompt injection. Low temperature is not a factuality proof. A citation can be syntactically valid while the claim is unsupported.

Create a small evaluation set with answerable, unanswerable, synonym-only, contradictory and adversarial-document questions. For each, record the expected source, retrieval result, claim support and whether the system should abstain. Compare fixture and external modes separately. Do not advertise a quality rate from a single successful example.

## Step 10: Extend With Explicit Acceptance Tests

You now have an executable local UI, bounded indexing/retrieval, source display, an extractive offline mode, and an optional generation adapter. The included tests execute chunk boundaries, retrieval/abstention, provider contracts and real HTTP requests.

Persistent indexes, token streaming, upload parsing, source access controls and hosted deployment remain separate extensions. Pick one and define its failure tests before changing the app. For example, a persisted index must record model identity and reject incompatible query vectors after a model change.
