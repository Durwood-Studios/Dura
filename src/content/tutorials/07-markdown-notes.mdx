## Overview

Build a complete browser note app with create/select/delete controls, live preview, localStorage saves, search, tag filters and JSON backup. The downloadable project includes all wiring and tests. You will use a small documented Markdown subset rather than pretend a few regular expressions implement the entire Markdown language.

**Prerequisites:** HTML forms, JavaScript events and basic arrays/objects. Node.js 22+ serves the static files locally; the app itself has no runtime library or external service.

## Step 1: Run the Complete Project

[Download Markdown Notes Lab 1.0.0](/labs/markdown-notes.zip) and extract it. Open the folder in your terminal:

```bash
cd markdown-notes
npm start
```

Visit `http://127.0.0.1:4311`. Click **New note**, enter a title, and type `# My first note` into the Markdown field. Confirm that the preview shows a heading and the status changes from **Unsaved changes** to **Saved in this browser**.

The [README](/labs/markdown-notes/README.md) explains the files and limits. Keep this server and port for later sessions: localStorage belongs to the exact origin and browser profile. The app does not install a service worker, so reopening requires the static files even though editing uses no internet service.

## Step 2: Trace the UI and Data Flow

```text
input event → update the selected in-memory note immediately → render preview
            → debounce a validated archive save → visible saved/error status
```

Read `app.mjs` alongside `index.html`. Each visible action has an event handler, including sidebar selection and deletion. The note list uses actual buttons, so keyboard users do not need pointer-only list items.

A delayed save captures the archive, not the current editor fields. This matters when someone types in note A and immediately selects note B: note A's text was already copied into its own record before selection changed.

## Step 3: Render Markdown as DOM Nodes

Read `markdown.mjs`. It creates headings, paragraphs, code, simple emphasis, flat lists, blockquotes and HTTP/HTTPS links. It inserts source text using text nodes and `textContent`, never `innerHTML`.

Paste `<img src=x onerror="alert(1)">` into a note. You should see literal text and no image or script execution. Then put `<strong>literal</strong>` inside a fenced code block; it should remain literal code. A `javascript:` Markdown link must remain text rather than becoming a clickable script URL.

This parser is a deliberate subset. Nested formatting, images, tables, reference links and CommonMark compatibility are outside this exercise. A full parser would require a documented parser/sanitizer policy plus tests; escaping one field is not sufficient when another rendering path still accepts HTML.

## Step 4: Validate the Whole Note Archive

`model.mjs` defines a versioned archive. Each note has a stable ID, title, content, tags, creation timestamp and update timestamp. Empty content is valid; a blank note is still someone's data.

The validator rejects duplicate IDs, invalid types, impossible timestamps and oversized fields. Limits bound the work: 100 notes, 20,000 content characters each, 20 tags, and 1 MB per archive. Import validates before changing the active archive. Colliding imported IDs receive new IDs, preserving both copies instead of silently replacing local work.

## Step 5: Tell the Truth About Storage

The storage adapter only acknowledges success after `localStorage.setItem` completes. A quota or permission error leaves the prior stored value intact, keeps the draft visible and reports **Not saved**. Export includes the current drafts, so a failed save does not force someone to discard their work.

Saving takes a browser Web Lock and compares the last known serialized archive before writing. If another tab saved first, the stale tab is refused and asks the learner to export and reload. This is not collaborative merge. Unsupported Web Locks produces a visible error rather than silently promising race safety.

Browser storage is not a permanent backup. Clearing the profile or site data removes it. The notes are not encrypted. Export independent files before removing browser data or switching machines.

## Step 6: Compose Search and Tag Filters

Search matches note title, content or tag text. Selecting an exact tag adds a second condition rather than replacing the search query. The UI builds tag options and note titles with text nodes, so imported tag markup cannot become HTML.

Create two notes containing the same word, give them different tags, then search for that word and select one tag. Exactly the matching note should remain. Clear the tag and confirm both return. This simple behavior is easier to verify than attaching different ad hoc filters to separate click handlers.

## Step 7: Export, Import and Recover Deliberately

Use **Export all drafts** to download the versioned JSON. Import it into another browser profile or after reviewing the file. Importing into the original profile preserves collisions as separate notes. Test both a valid empty note and a malformed object; the malformed archive must fail without partially importing earlier records.

If startup storage is corrupt, the app disables editing and allows a raw recovery download. It does not replace unreadable storage with an empty successful save. Review that file manually before restoring it. If you exceed field limits in an unsaved draft, correct those fields before expecting its export to pass validation elsewhere.

Every keyboard shortcut has an equivalent visible control: Ctrl/Cmd+S, Ctrl/Cmd+/, and Ctrl/Cmd+Shift+N. Deletion asks for confirmation, and mobile controls have at least 48px targets.

## Step 8: Run the Regression Suite

Run the model/storage tests with Node, then the actual browser workflow:

```bash
npm test
npm ci
npx playwright install chromium
npm run test:browser
```

The browser suite uses a fresh profile and an ephemeral local server. It types into one note, switches before the debounce finishes, creates another, reloads and verifies both. It also checks hostile imports, literal code, quota failure, export, deletion and 320px layout. The pure tests cover schema bounds, empty records, ID collisions, search composition and stale-tab refusal.

The tested result is this local teaching application. Cross-device synchronization, encrypted storage, service-worker offline navigation and full Markdown conformance are separate extensions with their own acceptance criteria.
